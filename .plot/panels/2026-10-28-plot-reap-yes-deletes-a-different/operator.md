## (a) Problem statement

1. **A second cause is missing, and it accounts for the `feature/EWZREL-9391` row with no host involved.** Under `--yes`, the worktree kind runs before the branch kind (`reap.ts:1268-1269`) and removes each landed desk's checkout (`removeOnly`, `:906`). For a branch that was not given up, it keeps the branch (`:909-912` deletes only when `givenUp`). The branch kind then lists checkouts again (`:988-991`), finds the branch free and deletes it. Under `--dry-run`, nothing is removed, so the same branch reads `keep — checked out in a worktree`. I reproduced this deterministically:

   ```
   --dry-run:  keep     feat/held   checked out in a worktree — somebody is reading it
               summary: ... branches=1 branches_deleted=0 branches_kept=2
   --yes:      deleted  feat/held   merged into main, local ref deleted
               summary: ... branches=2 branches_deleted=2 branches_kept=1
   ```

   The issue's row `feature/EWZREL-9391 … not listed → deleted — merged into develop` has exactly this shape. `merged into develop` comes from `ctx.refs.contains` (`:1000`), a local ancestry reading, not from the host. The plan's cause paragraph attributes every divergence to the host and #2730, which misnames this one.

2. **The `migration-abw-rechnungsempfaenger` and "6 branches kept" rows are consistent with the host DEGRADING TO KEEP, not with a degraded `merged`.** Under a rate limit, `pr-merged` prints `unknown` (`plot-host.sh:658` `miss_or_unknown`, and the page-cap and failure paths in `_bb_paged_walk` return 3, which `host-shell.ts:309-315` reads as `unknown`). `runBranchKind` treats any non-`merged` answer as `merged = false` (`:1005-1009`), and `firstBranchRefusal` receives only a boolean `hasMergedPr`. So a 429 prints **`keep — unlanded work — no merged PR`**: the same words as a real "not merged". On Bitbucket, a `merged` answer requires a row with `state == "MERGED"` from a server-side filter on `state=MERGED AND source.branch.name=…` (`plot-host.sh:1190,4257`). That is positive evidence, and `mergedAt` cannot revert. The most likely reading of the issue table is therefore: the dry run got `unknown` for `migration-abw` and printed it as "no merged PR"; the `--yes` run got the true `merged`. In the other direction, `--yes` got `unknown` for the 6 branches and kept them. Both are safe outcomes. The operator was misled by the reason text, and the approved set changed because the run asked again.

3. **The `branches_deleted=` mismatch is not a counter drift in the code.** In `runBranchKind`, `deleted` increments only beside a `deleted` row (`:1049-1051`), and a failed delete writes `FAILED` and increments `kept` (`:1052-1055`). So `branches_deleted` equals the branch section's `deleted` rows by construction. What does confuse an operator: `branches=` is the *swept* count (would + deleted + FAILED), not the number of branches. A `FAILED` row counts in both `branches=` and `branches_kept=`. The claim section also prints `deleted` rows (`:1173`). The issue's real-run totals (37+19 = 56 = dry run's 38+18) show no FAILED row. The plan's diagnosis at Approach item 4 ("swept increments before the delete … so the counters can drift from the rows") describes a drift between `branches=` and the `deleted` rows, not one in `branches_deleted`. The issue gives no output to recount. The slice should name the counters correctly, not fix a count that is already correct.

4. Line citations hold at the current tree (`fb90a41c6`). `runBranchKind` is at `:980`, `contains` at `:1000`, `prMerged` at `:1005`, and `deleteBranch` at `:1048`. `deleteBranch` is `git branch -D` (`trees-git.ts:486-487`), and its stdout, which reads `Deleted branch X (was <sha>)`, is discarded.

5. `skills/plot/scripts/README.md:49` still says *"Branches and refs are untouched: it removes CHECKOUTS"*. The branch kind and the claim kind have deleted local refs since 2026-09-03. An operator who reads the README before `--yes` is told that no branch can go. That is part of this bug's surface.

## (b) Approach

- **"What is approved is what runs" must mean "a subset of what was approved", never "exactly".** If `--yes --plan <file>` deletes the recorded rows on trust, a hand-edited or stale file adds a `PR merged` row that no reading confirms. The safe contract: `--yes` deletes the intersection of the recorded `would` rows and what still holds at delete time. Two re-checks are local and free: the tip is unchanged, and the branch is not checked out and not the default. The recorded reason is accepted only where it is terminal. `merged into <default>` is monotone, because `origin/<default>` only grows. `PR merged` is terminal per *A Decision Reads The Index* ("Only a terminal answer is read from the index"). A re-ask then only shrinks the set, and the run deletes nothing the dry run did not show. With that rule, `--yes --plan` makes **no host call for branches**, so a 429 cannot change the set. That removes the cause from point (a)2, not only its symptom.
- **Validity of the record.** Rows need no clock expiry, because every accepted reason is terminal. The tip check is what bounds staleness. The file must carry the repository (common git dir) and the default branch, and `--yes` refuses a file written for another checkout. The record belongs under the **common git dir** (as `issues.json` does: "under the common git dir"), not `ctx.repoRoot/.plot/state` as `refusals.tsv` uses (`reap.ts:875`). A desk-relative path differs per worktree, and an adopting repo may not gitignore `.plot/state/` as this one does (`.gitignore:30`).
- **The tip check must be atomic and must still respect checkouts.** I ran: `git update-ref -d refs/heads/t1 <wrong-sha>` refuses with `is at … but expected …` (exit 1). But `git update-ref -d refs/heads/t1 <right-sha>` **deletes a branch that is checked out in a worktree** (exit 0), where `git branch -D main` refuses with `used by worktree`. So the port needs `deleteBranch(branch, expectedTip)`, the local twin of `deleteRemoteBranch`'s `--force-with-lease` (`trees-git.ts:489-497`), and it must keep the checked-out guard, either by re-reading `trees.list()` immediately before or by keeping `git branch -D` after a tip re-read. The plan must say which.
- **The worktree-then-branch cascade needs its own decision.** With a recorded plan, the dry run records `feat/held` as `keep — checked out`, so `--yes --plan` keeps it, which is safe but leaves work for a second run. The better operator answer: the dry run projects the cascade and prints `would  feat/held  merged into main, held only by a desk this run reaps`. The decision stays one function of readings, so it belongs in the domain (`checkedOut` minus the desks `firstReapRefusal` cleared). Without this, the record fixes the deletion and still leaves a dry run that under-reports.
- **Reason text is a domain property.** Per *Every rendered state is a domain property*, `unknown` must reach the rule as its own reading (`hasMergedPr: 'yes' | 'no' | 'unknown'`) and print `keep — host could not answer (rate-limited?)`. Today the rule cannot express it (`sweepable.ts:99`, boolean input).
- **Layering.** The plan puts the validity question in the domain, which is right. The record's reader and writer are file I/O and belong in an adapter or the entry, not in `rules/`.
- **Contract with existing callers.** fleetd runs `plot-reap.sh --sweep-temp --yes` unattended every hour (`skills/plot/units/com.plot-pm.fleetd.plist:36`, `plot-fleetd.service:58`, scripts README row for `plot-fleetd.mjs`). If `--yes` without `--plan` refuses, `--sweep-temp` must stay exempt, or fleetd's temp sweep breaks silently. No current caller runs the branch kind unattended. The plan's argument that the recorded plan "suits an unattended caller" therefore has no caller today. The real argument for it is the tip check and host-free deletion.

## (d) Open questions

- *Recorded plan or confirm in place?* Recorded plan, with confirm in place as the operator-facing default on a TTY: `--yes` with no `--plan` on a TTY prints the set and asks once. With no TTY, it refuses with the command to write a plan. Both feed one function: "delete these recorded rows, subject to the re-checks". The prompt only produces the record in memory.
- *Log or `refs/plot/reaped/*`?* Both, and the ref matters more. A log does not keep objects: a branch made weeks ago has loose objects older than `gc.pruneExpire` (2 weeks), and they can be pruned at the next auto-gc, which a `git fetch` can trigger. The issue's operator recovered only because they pinned the commits by hand. Use `refs/plot/reaped/<branch>` (overwritten on a repeat), plus one TSV line per delete (time, branch, tip, reason) under the common git dir. Every `deleted` row prints its own restore command: `deleted  <br>  <why>, tip <sha7> — restore: git branch <br> refs/plot/reaped/<br>`. The plan must also say who removes `refs/plot/reaped/*` and when. Otherwise the reaper accumulates refs that are themselves leftovers. A proposal: a later reap deletes a reaped ref older than N days whose tip is contained in `origin/<default>` or whose PR is MERGED, with the same tip check.
- *Does the host port report rate-limited or partial answers to `prMerged`?* Partly. The answer is `unknown` (exit 3, `host-shell.ts:309-315`), and `lastRefusal` carries the refusal kind, but the reap entry discards both. No new port signal is needed to stop a degraded `merged`, because none is produced. One residual risk to measure: `is_lookup_miss` (`plot-host.sh:2293-2296`) maps any stderr containing `not found` to `not-merged`. A Bitbucket error body under load that contains "not found" would print `not-merged`. That is safe for deletion but misleading.
- *Do worktree and claim kinds diverge?* Worktree kind: yes, it re-asks `prMerged` (`:784-790`), so a desk can flip between runs the same way. It removes a re-creatable checkout, though (README "THE ASYMMETRY BETWEEN KINDS IS DELIBERATE"), so a record for it is optional. Its side effect on the branch kind is the real problem; see (a)1. Claim kind: see (c).
- *Does `--yes` with no `--plan` still run?* Not unattended for branches. It must keep running for `--sweep-temp` (fleetd). New question: should `--max N` apply to the record (the first N rows) or be refused with `--plan`? An operator trims a plan by editing the file, so `--max` with `--plan` is redundant and should refuse.
- **New question:** should the CLI gain a per-target form (`--only <branch>`, repeatable)? With a recorded plan, deleting rows from the file already narrows the run, and that is enough, provided that **removing** a row is allowed and **adding** one is refused or re-validated by the subset rule above. I would not add `--only`.
- **New question:** should the reaper read the PR index's MERGED rows before asking the host? That is what *A Decision Reads The Index* licenses for a terminal answer, and it would make the dry run itself stable under 429. Measure whether ewz-kus-portal's Bitbucket index carries MERGED rows first.

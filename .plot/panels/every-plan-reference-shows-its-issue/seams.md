# Seams juror — every-plan-reference-shows-its-issue

Position: amend

The problem statement is accurate and the two user rules are buildable, but the plan as written is one slice that cannot land green and reviewable on its own. It touches one new domain rule, possibly the contract, four href/label helpers, about 14 render sites in at least 10 files, and 14 board test files that carry 26 `/plan/` href assertions. It has no slice headings and no `waits:`, and the order of work it implies (rule, then component, then sites, then helper removal) is not written down. The collision risk with in-flight work is low if the issue keys come from a client-side lookup, and medium if they go into the fleet payload, because that route edits `packages/board/src/server/fleet.ts` while the plan-walk slices are still landing. I require a four-slice split (three if Q3 is answered "client lookup") before approval.

## Findings

1. **high — one slice is too large for one agent and one review.** The single branch `feature/every-plan-reference-shows-its-issue` must change `lib/tuple-row.ts` (1674 lines; `planLink` :486, `planNameLabel` :1278, `tupleFromPlan` :1294, slice href :1517), `lib/agent-rows/rows.tsx` (2893 lines; `PlanLink` :354, plan head :649, `IssueRowView` inferred plan :2879), `plan-level-row.tsx` :168, `draft-plan-row.tsx` :24, `PlanCard.tsx`, `PlanModal.tsx`, `StoryModal.tsx`, `SprintModal.tsx` :203/:213, `AgentPanelFacts.tsx` :399, `AgentList.tsx` :2694, `lib/plan.ts` :13, plus a new domain rule. Checked: `git grep` over `origin/main` (251b2abfc) for the helper names and `/plan/${`; `git grep -l` found 14 board/domain test files that name these helpers and 26 `'/plan/` assertions in `packages/board/test`. Every label change from bare slug to `1090: slug` breaks some of those assertions, so the one PR also carries a wide test diff. A reviewer cannot separate the rule from the migration.
2. **high — the helper removal has an ordering the plan does not state.** Requirement 3 removes the duplicate helpers, but a helper can only go after its last caller moves. `planLink`, `planNameLabel` and `tupleFromPlan` have callers only in `tuple-row.ts`, `rows.tsx`, `plan-level-row.tsx` and `draft-plan-row.tsx`; `planHref` (`lib/plan.ts:13`) has callers in `PlanCard.tsx:5`, `PlanModal.tsx:2` and `StoryModal.tsx:3`. So the removals split cleanly along the same line as the sites: each migration slice deletes the helpers whose callers it moves. Without that written, a split by an agent either leaves a dead helper or deletes one a sibling slice still calls.
3. **medium — the plan misses a fourth href helper and three more link builders.** `planHref` in `packages/board/src/app/lib/plan.ts:13` builds the same `/plan/<basename>` href and is not named among "the duplicate label and href helpers". `App.tsx:952`, `:965` and `:980` call `location.assign('/plan/...')`. `StoryModal.tsx:16` (`rewritePlanLink`) and `server/board.ts:3186` (`rewritePlanLinks`) rewrite plan links inside rendered markdown. The plan must say whether markdown prose links are in scope; through this lens they are a separate surface and a separate (or excluded) slice, because `board.ts` is server code.
4. **medium — the Q3 answer decides whether this plan collides with the plan walk.** The payload route has one precedent: `planEstate`'s `fieldsBySlug` (`server/board.ts:2865-2950`) is read onto AgentRows at `server/fleet.ts:6732-6734` and `:6986-6988` (assignee/author/approver), destructured at `:7598`. Adding `issues` there edits `fleet.ts` (22 commits on `origin/main` since 2026-10-25) and `contract/schema.ts` (16 commits). Open PR #2992 (`feature/scan-once-walks-in-process`) edits `fleet.ts` at :88 and :2827 only, so a textual conflict is unlikely, but four more walk slices (`the-walk-caches-by-oid`, `the-scan-modes-run-the-walk`, `the-pulse-log-runs-the-walk`, `the-scan-script-is-a-launcher`) are still unwritten and touch the scan path in `fleet.ts` and `packages/fleet`. The client-lookup route touches no server file at all. Measured on the saved payloads: all 44 of 44 fleet rows with a `planFile` resolve to a board card by basename and by slug; 298 of 596 cards carry issue keys; the fleet rows carry none (`"issues" in row` is false for all 51).
5. **medium — the plan has no slice headings.** The brief and the estate's convention put each branch under its own `###` heading in `## Slices` with `waits:` between them (the plan-walk plan is the model: nine headings, nine `waits:`). This plan has one bare bullet. With "Impl: own branches" and one branch, the fleet can dispatch exactly one agent for the whole job.
6. **low — `AgentList.tsx` is the one file two migration slices both touch.** The row slice must thread the issue lookup from the board payload into the agent list (the rows render inside `AgentList`), and the panel slice edits the unplaced list at `AgentList.tsx:2694`. `AgentList.tsx` had 9 commits in the last week. A `waits:` from the panel slice on the row slice removes the conflict.

The comment must say "no bundle in the PR" so an agent does not commit `board-server.mjs`.
8. **low — one line number is off.** The slice row's inline href is at `tuple-row.ts:1517`, not about `:1500`. Every other cited line (`planLink` :486, `planNameLabel` :1278, `tupleFromPlan` :1294, `PlanLink` :354, plan head :649, `IssueRowView` :2879, `Card.issues` :748, `DraftPlan.issues` :4225, `plan-level-row.tsx` :168 with `issues: []`, `PlanCard` :373, `StoryModal` :310, `SprintModal` :203/:213, `AgentPanelFacts` :399, `AgentList` :2694) matches `origin/main`.

No active plan names `tuple-row`, `agent-rows/rows`, `PlanCard`, `SprintModal`, `AgentPanelFacts` or `StoryModal`. `packages/domain/src/rules/` has no `plan-reference` rule, so a new rule file conflicts with nothing; `rules/plan-link-click.ts` already decides what a click on a plan link does and the new rule must reuse it, not restate it.

## Open questions

- Which name does a reference show? Recommend the existing plan-head format, `1090: slug`, everywhere a row or list refers to a plan, with the title as the hover text. The plan head and its tests already use it, so the Rows slice changes fewer assertions. The Planning card keeps the title as its heading and adds the prefix, because the card is the plan, not a reference to it.
- Which link target is the standard? Recommend the in-app plan route `/plan/<file>`, opened through the existing `rules/plan-link-click.ts` decision (modal when the card is loaded, route otherwise). It needs no host and works on Bitbucket. The git-host file link stays only where the board has no plan file to serve.
- Does each payload carry the issue keys, or does the client resolve them? Recommend one client-side lookup, defined in the domain (Rule slice) over the board's cards plus the fleet's draft plans. It resolved 44 of 44 plan rows on the saved payloads, it adds zero bytes and zero server work per refresh, and it keeps every slice out of `server/fleet.ts` while the plan walk is still landing there. Add the Payload slice only if a measured row fails to resolve.

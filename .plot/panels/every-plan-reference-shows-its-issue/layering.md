# Layering juror — every-plan-reference-shows-its-issue

Position: amend

The plan names the right rule ("every rendered state is a domain property") and the right goal, but it leaves the three decisions that settle the layering open, and two of its facts are wrong. The estate already holds the pieces: `@plot-pm/domain` has view rules that the app imports (`rules/plan-card.ts`, `rules/plan-link-click.ts`), the fleet server already reads every plan's issue keys on its PR timer (`planMetasOf`, `server/fleet.ts:1562,1638`), and every plan that a fleet row or slice names has a board card (measured: 14 of 14, 0 missing). So the design is buildable as one domain rule, one per-payload plan index, and one anchor component. Without those three decisions in the plan, a worker has to invent the layering, and the likely result is a component that decides the label and a second click handler beside `TupleRow`'s.

## Findings

1. **high — The Delivery tab cannot meet rule (i) "always" through a card lookup.** Evidence: `App.tsx:1390-1401` passes `cardForPlanFile` and `planFileForSlugOnBoard` to `AgentList`; `rows.tsx:649-660` reads `card?.issues ?? []` for the plan head. The cards come from `/api/board`, which `App.tsx:123-146` documents at 4.4-4.9 s and as able to stay `null` indefinitely (`App.tsx` "aborted-poll path (#2083)"). The fleet rows come from `/api/fleet`, a cache read. So on the Delivery tab the prefix appears seconds after the row, and never while `/api/board` fails. Checked by reading App.tsx and comparing payloads: `board.json` 794,765 bytes, `fleet.json` 88,201 bytes. A client-side card lookup couples the Delivery tab's labels to the Planning tab's payload, which is the opposite of independent tabs.

2. **high — The plan does not say where the decision lives, and the estate has a clear answer.** Evidence: `packages/domain/src/rules/plan-card.ts` (`planCardView`) and `rules/plan-link-click.ts` (`planLinkClick`, imported at `App.tsx:9`) are board view rules in the domain package, as arrows with factual TSDoc. Today the label rule `planNameLabel` lives in `app/lib/tuple-row.ts:1278` and the existence rule (`planFile ? href : ''`) is repeated at `tuple-row.ts:491`, `:1301`, `:1517` and `rows.tsx:369`. Approach item 4 says "the domain gives each plan reference…" but does not say whether "domain" means `@plot-pm/domain` or the board's `lib/` projection. It must be `@plot-pm/domain` (`rules/plan-reference.ts`), by the CLAUDE.md rule "No domain-specific code or behaviour lives outside the domain".

3. **high — The plan does not answer Open Question 3, and the answer decides the payload contract.** Neither "each row carries keys" nor "the client resolves from the card" is right. Per-row keys repeat one plan fact on 51 rows and 44 slices (measured in `fleet.json`), and two rows of one plan can then disagree after a partial refresh. A card lookup fails finding 1. The layered answer is a third option: `/api/fleet` carries one plan index (`slug → { file, issues }`) per payload, built from the `metas` the server already reads in `referencedIssues`/`ticketPlansOf` (`fleet.ts:1562,1638`), so it adds no plan-parser run per refresh. `/api/board` already has the same facts on `Card.issues`/`Card.path`. Both tabs call one domain rule over whichever index they hold. Cost: 298 of 596 cards carry issues, 2,825 bytes in total, mean 9.5 bytes per card (measured in `board.json`); for the 14 plans on the fleet payload, the index adds under 1 KB.

4. **medium — Three different `onOpenPlan` signatures exist, and one component cannot serve them without a decision.** Evidence: `Board.tsx:136` and `Swimlanes.tsx:17` take `(card: Card) => void`; `AgentList`/`TupleRow.tsx:414`/`rows.tsx:366` take `(planFile: string) => boolean`; `SprintModal` (`App.tsx:1588`) takes `(slug)`. Rule (ii) "opens the plan the same way" needs one signature. The `(file) => boolean` form with the `planLinkClick` fallback is the one that already handles a missing card and an unloaded board, so it is the standard.

5. **medium — Two copies of the click-intercept rule exist, and the plan names neither.** Evidence: `PlanLink` (`rows.tsx:354-380`) and `TupleRowView`'s anchor (`TupleRow.tsx:410-418`) each implement "plain primary click → `onOpenPlan`, else native navigation". `TupleRow.tsx:414` also decodes the file back out of the href string (`link.href.replace(/^\/plan\//, '')`), so the plan's identity travels as a URL and is parsed back. A shared component must carry the plan file, not reconstruct it from an href, and `TupleRowView` must render a plan link through that component so that one click rule remains.

6. **medium — Plan-reference sites the plan misses.** Checked with `git grep '/plan/\${\|planHref\|onOpenPlan' origin/main -- packages/board/src/app`. Missed: `lib/plan.ts:13` `planHref` (a fourth href builder, used by `PlanCard.tsx:343`, `PlanModal.tsx:45`, `StoryModal.tsx:155`); `StoryModal.tsx:12-16` `rewritePlanLink` (a fifth, for links inside a rendered document); `App.tsx:952,965,980` (`location.assign` fallbacks); `WorkerLogModal.tsx:108,319` (passes `onOpenPlan` through to `AgentPanelFacts`); `Swimlanes.tsx:244` (opens a card). `planHref` takes a repo-relative path and splits on both separators, while `tuple-row.ts` takes a basename `planFile`: two input conventions for one route.

No plan-reference site on main links to the git host. This changes Open Question 2: the in-app route is already the only target, and only the open mode (modal, same tab, new tab) varies.

The plan must say whether the card heading takes the shared component (for the prefix only) or is out of scope.

## Amendments I require

- A1. Write the Approach with an explicit layer for each decision: `@plot-pm/domain` `rules/plan-reference.ts` decides the label (issue prefix plus name), the normalised issue keys, and existence (`file: string | null`); the board server builds one plan index per payload; `lib/tuple-row.ts` only projects the domain answer into a `TupleLink`; one React component renders it and decides nothing.
- A2. Answer Open Question 3 as "one plan index per payload": add `plans: Record<slug, { file, issues }>` (or equivalent) to `/api/fleet`, built from the `metas` already read in `fleet.ts`, and read `Card.issues`/`Card.path` on `/api/board`. No per-row `issues` field on `AgentRow`, `Slice`, `SprintMember` or `StoryPlanRef`. Delivery-tab labels must not wait for `/api/board`.
- A3. Name one `onOpenPlan` signature, `(file: string) => boolean`, with the `planLinkClick` fallback, and migrate the `(card)` and `(slug)` callers to it.
- A4. One anchor component holds the click-intercept rule; `TupleRowView` renders its plan link through it, and the reference carries the plan file so `TupleRow.tsx:414` stops decoding an href.
- A5. Add the missed sites from finding 6 to the site list, and name `lib/plan.ts:planHref` as the one surviving href builder (or remove it). State whether `rewritePlanLink` (links inside a document body) is in scope.
- A6. Correct the false "GitHub file in a new tab" claim (finding 7).
- A7. Split the one slice: (1) domain rule plus unit tests for label, normalisation and existence; (2) fleet plan index in the contract and server, with a contract test that every row's and slice's `plan` has an index entry; (3) the component plus the migration of the Delivery-tab sites; (4) the Planning-tab, modal and sprint sites, and the removal of `planLink`, `planNameLabel` and the inline hrefs. Each slice keeps existing board tests green, so a failure points at one layer.

## Open questions

- Q1 (which name): the slug, with the issue prefix, in the existing `planNameLabel` form `1090, 1091: <slug>`, on every reference; the title goes in the `title` attribute. The slug is the identity that rows, branches and slices already share, so a reader can match two elements; a title cannot do that. The Planning card heading is the plan itself, not a reference, and keeps its title (finding 9).
- Q2 (which link target): the in-app `/plan/<file>` route as a real anchor, with a plain click intercepted to open the modal through `planLinkClick`. Every site already uses this route (finding 7), it works without a card, and the git host is not reachable from every repository the board serves.
- Q3 (who carries keys): neither option as written. One plan index per payload, resolved through one domain rule (A2). Per-row keys duplicate a plan fact across rows; a client card lookup makes the Delivery tab's labels depend on the slow `/api/board`.

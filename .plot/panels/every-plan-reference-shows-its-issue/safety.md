# Safety juror: every-plan-reference-shows-its-issue

Position: amend

The two user rules are sound and the data to deliver them is already on the client: the board payload carries `issues` on every card, and the app already resolves a plan file or slug to its card (`App.tsx:888` `cardForPlanFile`, `App.tsx:906` `planFileForSlugOnBoard`). The danger is in scope, not in mechanism. Taken literally, rule (ii) "every element that refers to a plan is a link" turns slice names, confirm-button labels and grouped branch rows into plan links, and three of those are deliberate non-links on main today, guarded by tests. The plan also states one wrong fact about the link targets (no surface links a plan to the git host) and asks for a board artifact rebuild that CLAUDE.md forbids in a PR. With a defined scope, a resolve-or-text rule in the domain and a two-slice split, the plan is safe to approve.

## Findings

1. **high — `what: 'plan'` has three meanings, so "every plan reference" has no mechanical definition.** `tupleFromSlice` names a SLICE with `what: 'plan'` and `href: ''` on purpose (`packages/board/src/app/lib/tuple-row.ts:1474-1477`; its docstring says *"The name is text, never a link … three sibling slices three links to one document"*). `IssueRowView` names the INFERRED plan with `what: 'plan'`, `href: ''` (`lib/agent-rows/rows.tsx:~2879`). Only the plan head, `planLink`, and the slice row's `solePlan` (`tuple-row.ts:1514-1519`) name a real plan. A migration that keys on `what === 'plan'` gives a slice name an issue prefix and a link to its plan file, which the slice docstring forbids. Checked by reading all four producers on `origin/main` (251b2abfc).
2. **high — a deliberately absent plan link is guarded by a test, and rule (ii) read literally breaks it.** `packages/board/test/integration/agents-tab.browser.test.ts:545` asserts a branch row inside a plan group has ZERO plan links, because the plan head one line up carries it (`:550-557`). The plan does not say whether a reference the nesting already states is "an element that refers to a plan". Without that sentence an implementer re-adds the link on every grouped row and either breaks this test or edits it to pass.
3. **high — action labels name a plan and must never become links.** `ApproveButton.tsx:69-72`, `NeedsDesignButton.tsx:29`, `StartWorkButton.tsx:331` and `menus.tsx:1316` put `card.slug` inside a `<button>` label or `title`. An `<a>` inside a `<button>` is invalid interactive nesting: the click target becomes ambiguous and a confirm click can navigate instead of act. Rule (ii) needs an explicit exclusion for text inside a control.
4. **medium — the plan's link-target premise is false.** The issue text, which the plan carries into Open Question 2, says `PlanLink` without `onOpenPlan` opens "a GitHub file in a new tab". It opens the board's own `/plan/<file>` route in a new tab (`rows.tsx:~368`, `href={`/plan/${encodeURIComponent(planFile)}`}`, `target='_blank'`). `git grep "blob/"` over `packages/board/src/app` and `server/fleet.ts` finds zero hits: no surface links a plan to the git host today. So the git-host option would be a new target, not a standardisation on an existing one.
5. **medium — the route and the modal disagree for Draft plans, so "opens the same way" fails there.** `/plan/<file>` resolves the working tree, then `origin/<default>`, then every prefixed branch (`server/board.ts:3080-3116`), so an idea-branch plan does exist as a page. But `onOpenPlanFile` opens the modal only when `cardForPlanFile` finds a card (`App.tsx:924-936`), and the board payload I read holds cards only in Development, Testing and Released (596 cards). A Draft plan reached from a row therefore opens as a full-page navigation, not the modal, and its issue keys live in `DraftPlan.issues` (`schema.ts:4225`), not on a card. A lookup that consults cards only gives Draft references no prefix.
6. **medium — a reference must not link where nothing resolves it.** Today the safe paths are explicit: a sprint member with no card renders as text with a `?` badge titled "Plan not found in board" (`SprintModal.tsx:193-228`); a plan-level row with no card renders the slug with no link (`plan-level-row.tsx:150-160`); a planless branch renders text (`tuple-row.ts:486-494`). In the saved payloads every fleet row with a `planFile` has a card (51 rows, 44 with a plan, 0 without a card) and no two cards share a slug or a basename, so no row links to a dead route today. The plan must keep that property as a stated rule: a link only when a card or a draft resolves the file, text otherwise. The route matches by basename only (`board.ts:3102`, `:3113`), so a same-named file on two sources opens the first one found.
7. **medium — the issue prefix leads the label, and truncation removes the slug, which identifies the plan.** 298 of 596 cards carry issues and 28 carry two or three (`a-desk-and-its-manifest-name-each-other` carries `1085,1086,1101`). The label renders in `<span className="min-w-0 truncate">` (`components/TupleRow.tsx:~370`), so in the narrow slot-4 column a reader sees `1085, 1086, 11…` and no plan name. Two different plans that share issue 1090 (`a-slice-nobody-worked-on-reads-not-started` and `a-start-step-leaves-no-claim-and-no-desk`) then read the same. That defeats the plan's own goal ("tell that two elements name the same plan").
8. **low — the bare number is ambiguous beside a PR number.** Keys are stored without `#` (`schema.ts:744-748`), and a branch row shows a PR link `1234` and a plan link `1090: slug` in the same slot. The accessible name disambiguates (`linkLabel` gives `Pull request 1234`, `Plan 1090: slug`, `TupleRow.tsx:290-295`), the visible text does not. The ticket row uses the same bare form (`tuple-row.ts:1201`), so this is consistent, not a regression. A Jira key (`EWZKUS-3430`) is unambiguous. The prefix is part of the plan link and opens the plan, not the issue; the plan should say so, so nobody wires the prefix to the tracker.
9. **low — the data claim is partly wrong, and the smaller design follows from it.** `StoryModal` lists `Card` objects through `plansInStory(cards, …)` (`StoryModal.tsx:119`), not `StoryPlanRef`; `git grep StoryPlanRef packages/board/src/app` finds zero uses. `SprintModal` already receives the card slugs (`App.tsx:1586`). So the story modal and the sprint panel have the issue keys on the client today, and no payload must grow for them.
10. **low — payload and server cost are negligible either way.** Card issue arrays total 3,421 characters in a 794,452-byte board payload. Adding `issues` to the 51 fleet rows adds well under 1 KB to an 88,185-byte fleet payload, and `fleet.ts` already reads every plan's `Issue:` line for `referencedIssues`. A client lookup costs no server work. Its one cost: the fleet tab can render before the board arrives (`App.tsx:931-953` defers the click for exactly this), so the prefix appears one refresh late and the label shifts.
11. **low — click and modal behaviour change on two surfaces.** `StoryModal.tsx:305-311` opens a plan nested inside the story view (`setViewingPlan`); `SprintModal` closes itself first (`App.tsx:1596-1597`). "Opens the same way everywhere" changes at least one of them. `PlanCard` already has an `Open` anchor (`PlanCard.tsx:498`); a title link adds a second tab stop to the same target. No tuple row has its own row-level click handler (`TupleRow.tsx:673-685`), so a link inside a row starts no second action there.
12. **low — test breakage risk is bounded.** Browser tests locate plan links by hook (`data-tuple-link="plan"`, 7 sites) or by substring name; one asserts an exact name `Plan ${plan}` (`agents-tab.browser.test.ts:556`), and the fixtures carry no `Issue:` line, so a prefix does not change those names. The risk is finding 2, not label text.
13. **low — the Board impact comment contradicts CLAUDE.md.** It says "Rebuild the board artifact once the contract changes". CLAUDE.md (Testing) says a PR's diff carries no generated bundle (`scripts/check-no-bundle-diff.sh`) and main builds its own.
14. **Line numbers checked** against `origin/main` 251b2abfc: `planLink` 486, `planNameLabel` 1278, `tupleFromPlan` 1294, slice row 1474/1514, `PlanLink` 354, plan head 649, `plan-level-row.tsx` `issues: []` about 170, `PlanCard.tsx:373`, `StoryModal.tsx:310`, `SprintModal.tsx:203`, `AgentPanelFacts.tsx:~399`, `AgentList.tsx:2694`, `schema.ts:748` and `:4225` are all correct. Sites the plan does not name: the mixed-group `<h3>` heading through `PlanLink` (`AgentList.tsx:2162`), `PlanModal`'s own heading (`PlanModal.tsx:44-46`), and the action labels in finding 3.

## Amendments I require

- A1. Define "an element that refers to a plan" in the Approach: the plan head, a row's plan link in slot 4, the slice row's sole-plan link, the plan-level rows, the mixed-group heading, the Planning card title, the story modal list, the sprint members, the agent panel's plan fact, and the unplaced rows. Exclude by name: a slice's own name, the inferred plan on an issue row, text inside a button or a `title`, and a row whose plan the group head above it already links (keep `agents-tab.browser.test.ts:545` passing unchanged).
- A2. Make the link rule resolve-or-text, in the domain: a reference gets `/plan/<file>` only when a card or a `DraftPlan` resolves its file or slug; otherwise it renders as text, and a sprint member keeps its `?` mark. State that a resolved reference never renders as text and an unresolved one never as a link, and test both arms in a unit test.
- A3. The domain lookup reads cards AND `fleet.draftPlans`, so a Draft plan shows its issue prefix, and a click on a Draft reference opens the same view as any other plan (either the modal learns to show a draft, or the plan states that a draft opens the page and why).
- A4. Answer the truncation case: the full label (prefix and slug) stays in `title` and the accessible name, and the visible label keeps the slug readable when a plan has more than one key (for example the first key plus `+N`). Add a test with a three-key plan.
- A5. Correct the motivation: no surface links a plan to the git host today; `PlanLink` opens the board's `/plan/<file>` route in a new tab. Correct the `StoryPlanRef` claim: the story modal reads cards.
- A6. Replace "Rebuild the board artifact" in the Board impact comment with the CLAUDE.md rule: no generated bundle in the PR.
- A7. Split into two slices: (1) the domain `planReference` rule, the shared component, and the tuple-row sites (`planLink`, `tupleFromPlan`, the slice `solePlan`, the plan-level `issues: []`, the `PlanLink` heading); (2) the modal and card sites (`PlanCard`, `StoryModal`, `SprintModal`, `AgentPanelFacts`, unplaced rows), with the modal behaviour change of finding 11 stated.

## Open questions

- **Which name: title, slug, or both?** Recommend the slug, with the issue prefix, in rows and lists; the title only where it already is the heading of a card or a modal, with the prefix added. The slug is what the route, the sprint file and the fleet rows use, so it is the identity a reader matches across surfaces; the title is longer and truncates first.
- **Which link target?** Recommend the in-app `/plan/<file>` route, opened in the plan modal on a plain click and as the page on a modified click, exactly as `TupleLinkView` does now. A git-host file link fails for a plan that is not pushed (`Card.notPushed`), for a Draft before its branch is pushed, and on a host whose URL shape the board does not know, and no surface uses it today.
- **Payload or client lookup?** Recommend one client-side domain lookup over cards and `draftPlans`, keyed by plan file and then slug. Every surface already has those readings, it costs no server work, and it keeps one source for the keys. Add `issues` to fleet rows only if the late prefix of finding 10 is measured as a problem.

# Cost lens — this-sprint-cannot-select-one-sprint (#2399)

The change is cheap: the filter already supports a subset, and no payload or schema change is needed. The plan does not say so. It prices the work as new domain machinery plus three browser tests and per-viewer persistence. It does not name the four browser files that break, or the recorded decision it reverses.

## Findings

1. **The filter already selects a subset, so the change is the chip's setter and its readings, not new membership logic.** `AgentList.tsx:566` holds `sprintFilter: Set<string>`. `:625-628` sanitizes it against Active sprints, which is #1145's stale-slug rule. `:660-663` filters on `selectedSprints`, and `workersHiddenByFilter` (`:738-746`) also reads it. Only `toggleThisSprintChip` (`:639`) is all-or-nothing. The `sprint.visibleRows` reading (`:694-702`) maps `inSprint` against `allSprintSlugs`. The plan's "a slug that names no Active sprint reads as none" already exists as `sanitizeSelection` (`filters.ts:165`). Open Point: should slice 1 reuse `selectedSprints`/`sanitizeSelection` and only pass the selection into `SprintChipReadings`? The alternative is a second stale-slug rule in the domain beside the board's, which a corpus test would then have to hold.

2. **Row membership stays decided in the component, so the plan's "all decided in the domain" covers the chip count and not the filter.** `slugPassesSprintFilter`, `rowIsSprintExempt` and `sprintMembershipLookup` live in `packages/board/src/app/lib/filters.ts:24,309,355`. The Board tab and Swimlanes share them (`filters.ts:293-296`). If the domain recomputes `inSprint` from a selection while `filteredRows` (`AgentList.tsx:660`) still uses the board predicate, two implementations answer one question. Open Point: does slice 1 move the predicate into `@plot-pm/domain`? That touches three tabs. Or does `inSprint` stay a caller-supplied boolean, with only the selection added to the readings? That is narrower, and the plan should state it.

3. **The row slug needs no payload change, and Open Question 2 is already answered.** `AgentRowSchema.sprint` (`schema.ts:2550-2566`) is set by the server from Active-sprint membership. Where two sprints list one plan, the first Active sprint wins (`fleet.ts:6059`). Release, idea and plan-less rows carry `''` by design (`fleet.ts:6439`, `:6756`). Open Point: record "first-wins, per `schema.ts:2557`" as the answer and drop "measure first". The row-slug property should read `row.sprint` and not recompute membership. Note that an `idea/*` row carries `''` even when its slug looks sprint-bound, so a mixed list shows some rows with no slug.

4. **"Persists per viewer" reverses a recorded decision, and the plan does not name it.** `AgentList.tsx:556-565` says the sprint filter is "NOT PERSISTED: … a momentary focus" and "NOT SYNCED TO URL". Open Question 1 is answered in code. A filter that hides rows lives in `localStorage` under `plot-board:agents:*` (`mine-filter.ts:7-17`, `collapse.ts:40`). The URL is for shareable view state (`schema.ts:4500-4501`, and the Board tab's `?sprint=` at `App.tsx:1085`). Open Point: does the operator overturn the `:556` decision? If yes, slice 2 must also define how the stored slug interacts with the prune effect (`:653-659`). That effect deletes a selection only while the list is non-empty, and a persisted slug for a closed sprint reads as "all Active" on the next load. The issue asks for "remember the choice"; the code says the opposite. One of the two must be amended.

5. **The label change breaks four browser files' selector.** `DeliveryFilters.tsx:54` renders `data-chip={chip.label}`. Selectors `[data-chip="This sprint"]` appear at `sprint-switch.browser.test.ts:168`, `sprint-exempt.browser.test.ts:140`, `agents-tab.browser.test.ts:4417` and `delivery-filters.browser.test.ts:97,103`. With a sprint selected, the label names that sprint and no selector matches. Open Point: add a stable key (for example `data-chip-key="sprint"`) in slice 2, or keep the label fixed and name the sprint elsewhere. The plan lists none of these files.

6. **"One browser test per behaviour" is about three new board-server starts, against the precedent of one.** The delivered `2026-10-19-one-chip-row-and-a-sprint.md:57,84` shipped the chip row with ONE browser test. CLAUDE.md (*Every rendered state is a domain property*) moves deciding to unit tests and leaves browsers to show. The repo has 74 `*.browser.test.ts` files today, each starting a server. Open Point: is one browser test enough for slice 2, showing a click selecting a sprint and a row slug, with persistence tested as a unit test in the style of `readMineOnly` (`mine-filter.ts:54`)?

7. **The subset scenario that #2137 deleted comes back, and the plan does not reinstate its test.** `sprint-switch.browser.test.ts:216-226` records the removed case "one sprint stays selected through the other's closure" as a plan gap. This plan recreates that state. Open Point: list that scenario as a unit test over the selection rule in slice 1, with 2 Active sprints, select one, close the other, and close the selected one. A browser test is not needed for it.

8. **`estateTotals` (Open Question 3) is server-side and the cheap answer is "rows only".** `estateTotals` comes from `fleet.ts` (`fleet-sprints.test.ts:7`) and reaches the client as a payload value. Scoping it to the selection would need either a client recount or a payload field. Open Point: confirm "rows only", which needs no payload change, or accept a schema change the plan does not budget.

9. **No server-side filter exists, and the plan should state it.** `schema.ts:2561-2564` says `sprint` is "A VIEW, never a fetch". The selection is client-only, so no `/api` route, cache or pulse cost changes. Open Point: none. Adding one line to the Design keeps a later reader from budgeting a server change.

10. **The slices ship in a workable order, and slice 1 alone changes no rendered behaviour.** The `hiddenCount` change is visible only once slice 2 passes a selection. The Changelog describes slice 2's effect only. Open Point: accept slice 1 as an internal step, or merge both slices into one branch, since the domain diff is about 20 lines over `chip-row.ts:30-87` and `chip-row.test.ts` (115 lines today).

11. **There is no sibling collision.** None of the Approved plan or the six Draft siblings names `AgentList`, `DeliveryFilters` or `chip-row` (grep, below).

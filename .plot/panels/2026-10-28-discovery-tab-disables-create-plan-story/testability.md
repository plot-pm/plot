## (a) Problem statement

- Every cited line is correct at `282ca0161`: `App.tsx:516` is `if (tab !== 'delivery') return;`, `App.tsx:1338` is `issueAnswer={fleet?.issueAnswer ?? 'unsupported'}`, `CreatePlanButton.tsx:84` and `CreateStoryButton.tsx:94` are the `unsupported` branches, `StoriesTab.tsx:504` passes `issueAnswer` to `CreatePlanButton`. The probe reproduces the exact two sentences from the issue from a `null` fleet.
- A cause is missing: **the same null-fleet default hides the absence sentence.** `App.tsx:1328` passes `issueAbsence={fleet?.issueAbsence ?? null}` to Discovery. With no fleet, `discoveryGroups` (`discovery-groups.ts:69`) falls back to `TICKETS_NOT_READ_REASON` ("Tickets have not been read yet."), so a repository whose tracker no connector lists shows a "not read yet" sentence forever on a fresh Discovery page, instead of the board's declared reason. The probe asserts both outputs.
- A second cause is missing, on the server: `fleet.ts:2887–2889` seeds `entry.issueAnswer = 'unsupported'` before the first issue read, by design ("a board that has not asked must not render an empty inbox as a clear one"). So "not loaded yet" reads as `unsupported` on the server too, not only in `App.tsx`. Slice step 1 must decide what the new source reports before the first read, or a first `/api/fleet` (or `/api/board`) answer after a board start still prints the Bitbucket sentence.
- Why it escaped: `discovery-ticket-card.browser.test.ts:57` stubs `fleet: buildFleet({ issueAnswer: 'answered' })` and opens `tab: 'discovery'`, but Discovery never fetches `/api/fleet`, so that stub is dead config. The test at `:91–99` asserts only `[data-create-plan]` count = 1, never `aria-disabled`. The same dead stub sits in `discovery-mine-filter:81`, `discovery-groups-toggle:69`, `discovery-lanes-by-topic:64`.

## (b) Approach

- Option 2 (issue answer in the board payload) fixes the cause; option 1 (poll fleet on Discovery) fixes the symptom with a second clock. Evidence: `/api/board` already reads the same cache entry through `ticketLaneData` (`server/index.ts:493`, `fleet.ts:1682–1697`), and `ticketLaneData` returns `null` until `entry.issueSets` exists. The ticket rows and their answer then come from one read at one instant; with option 1 the rows come from the 30 s board poll (`App.tsx:39`) and the answer from the 4 s fleet poll (`App.tsx:40`), and a test must reason about two arrival orders. The server refreshes issues on its own timer (`fleet.ts:2957–2978`, `maybeRefreshPrs` → `refreshIssues` at `:2573`), so the board payload is not staler than the fleet's. This also closes the plan's "second effect" (stale answer after one Delivery visit) for free.
- Do not add a fourth member to `IssueAnswer`. The enum is declared twice (`contract/schema.ts:3662`, `domain/src/entities/issue.ts:12`), written by the server in ten places (`fleet.ts:1983–2258`) and compared in `AgentList.tsx:1160,2485,2500,2509,2617,2632`. A "loading" member would be a value the server never sends. Type the Discovery input as `IssueAnswer | null` and let the domain rule map `null` to loading.
- The new board field must not copy `Fleet`'s `IssueAnswerSchema.default('unsupported')` (`schema.ts:4559`). A board payload from an older server that lacks the field would then reproduce this exact defect. Absent must decode to `null`.
- Layering: the plan says the decision "belongs in a domain rule" but names no rule and no file. Today `refusalReason` lives in two `.tsx` files and is unit-tested from the component (`create-plan-button.test.ts:2`); there is no `CreateStoryButton` unit test (grep: no test imports it; `agent-list.test.ts` reaches it only through `storyRefusal` in `menus.tsx:211`). `discoveryGroups` is the precedent: a domain rule already takes `issueAbsence`.

## (c) Slices

- One branch is right; the change is small and every piece touches the same wiring. Do not split the loading state from the source change: the loading state alone leaves Discovery loading forever (no fleet poll), and the source change alone still renders `unsupported` before the first read.
- Add to the slice: route `issueAbsence` through the same source (the `App.tsx:1328` defect above). Same cause, same line block, same test.
- Nothing needs to ship separately first.

## (d) Open questions

- **Poll fleet or move to board payload?** Move to the board payload (see (b)). Cost of the contract change: one optional nullable field on the board schema, plus the catalogue `board()` builder; the four Discovery browser tests named in (a) move `issueAnswer: 'answered'` from their `fleet` stub to their `board` stub.
- **Other Discovery controls reading `fleet?.…` with a defaulting fallback?** Yes, one: `App.tsx:1328` `issueAbsence`. `App.tsx:1485,1498` `planAgeSeconds={fleet?.ageSeconds ?? null}` sit on the Planning tab and degrade to "no age", not to a false refusal; out of scope. `StoriesTab.tsx:504` is the same prop, not a second source.
- New question for the plan: what does the source report between board start and the first issue read, given `fleet.ts:2889` seeds `unsupported`? Proposed answer: `null` whenever `entry.issueSets === null` and the source is not `nobody`.
- New question: does Discovery render any button at all before the first read? With option 2, `tickets` is `null` until `issueSets` exists, so no ticket row and no button renders. The "loading" state is then reachable only through an older server or a future caller, and the plan should say which it serves.

## (e) Tests

Lowest tier that fails today: none in the repo. Every existing test passes (ran 32 of them), because the defect lives in `App.tsx` wiring that no unit test reaches and that the browser tests stub around. The scratch probe shows the failing assertion at domain-unit level once the decision is a function of `(dispatch, issueAnswer | null)`.

- **Domain unit (prove the rule):** a new rule, for example `packages/domain/src/rules/create-from-issue.ts`, returns `available | loading | refused` plus the sentence for each kind (plan, story). Cases: `null` → loading, never matching `/no issue read/`; `unsupported`, `failed`, binding refused, both refused (tracker named first, as `create-plan-button.test.ts:73` asserts today). This is the test that fails today in spirit; the probe's last case is its first assertion. Move or re-point `create-plan-button.test.ts` and add the missing story half.
- **Board unit (prove the source):** a `/api/board` payload test that the field reads `null` before `issueSets` exists and `answered` after a stubbed read, next to `board-reads-the-issue-index.test.ts`. A `renderToStaticMarkup` test of `StoriesTab` with `issueAnswer: null` that asserts no `aria-disabled` and no "no issue read" text, in the style of `an-unread-ticket-group-says-why.test.ts:7–24`.
- **Browser: needed, but one assertion in an existing file, not a new file.** The defect that shipped was wiring between `App.tsx`'s fetch effects and a prop, and only a browser test sees that; the unit tiers above cannot render `App`'s effects. Amend `discovery-ticket-card.browser.test.ts:91–99` to assert `aria-disabled` is absent on `[data-create-plan="1688"]` and `[data-create-story="1688"]` on its existing fresh `?tab=discovery` open, with `issueAnswer` set only in the `board` stub and the `fleet` stub set to `unsupported`. That assertion fails today and passes after the fix, and it makes the dead fleet stub a live trap.

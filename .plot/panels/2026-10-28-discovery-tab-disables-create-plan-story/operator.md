## (a) Problem statement

- Every cited line is right: `App.tsx:516` (`if (tab !== 'delivery') return;`), `App.tsx:1338` (`issueAnswer={fleet?.issueAnswer ?? 'unsupported'}`), `CreatePlanButton.tsx:84`, `CreateStoryButton.tsx:94`, `StoriesTab.tsx:504`. The probe reproduces the exact two sentences from the issue for `fleet === null`.
- What the reader sees, by entry path:
  - **Fresh load or reload on `?tab=discovery`:** `tab` comes from `parseTab` (`App.tsx:194`), the fleet effect returns at 516, so `fleet` stays `null` for the life of the page. Until `/api/board` answers, the whole tab reads `Loading…` (`App.tsx:1340-1342`). After it answers, ticket rows render from `board.tickets` and every Create button is refused with the Bitbucket sentence. This never corrects itself, because nothing on this tab fetches the fleet. The `visibilitychange` handler fetches the fleet only on Delivery as well (`App.tsx:746`).
  - **Discovery after a Delivery visit:** `fleet` keeps the last Delivery reading. Switching tabs does not reset it (`onTab`, `App.tsx:795-800`), and the poll stops (cleanup at 519). The buttons are right, but frozen at that reading. This is the plan's "second effect", and it is confirmed.
- **The cause is one layer deeper than the plan states.** The rows and the answer about those rows come from two endpoints. `/api/board` builds `tickets` from the same cache entry that `/api/fleet` reads its `issueAnswer` from (`index.ts:487-513`, `discovery-lanes.ts:41-44`, `fleet.ts:1682-1684`). The page then takes the rows from one payload and the verdict from the other. Also, `/api/board` alone warms that cache: `ticketLaneData` calls `ensureCache`, and `ensureCache` starts `refresh` and `maybeRefreshPrs`. So whenever `board.tickets` is non-null, the server already holds `entry.issueSets.answer`. The page simply is not told.

## (b) Approach

- **Change 2, option "move into the board payload", is the right fix for the reader, and the code shows it costs nothing.** The server computes the answer in the same request, from the same cache entry, so the rows and their answer arrive in one payload, atomically. Then the only "not yet known" moment on Discovery is "no board yet", and the tab already shows that as `Loading…`. The fleet-poll option has a different window: board rows are on screen while the fleet fetch is still in flight. That window needs a loading state on every row, and it adds a 4 s poll (`FLEET_POLL_MS`, `App.tsx:40`) to a tab that otherwise polls every 30 s (`POLL_MS`, `App.tsx:39`). The fleet poll would also make the Delivery-only failure accounting wrong: `failures` and `dimmed` key the fleet endpoint to Delivery only (`App.tsx:534,545`).
- **With the board-payload option, change 1 (a loading state) is mostly unreachable on Discovery.** A loading state is still correct for a defensive reason: an older server sends no field. But the plan should not sell it as what the reader sees in normal use. The reader sees enabled buttons as soon as the rows show. That is clearer than either "loading" or "enabled, then refused".
- **Do not add the unread state to `IssueAnswerSchema`** (`schema.ts:3662`, `['answered','unsupported','failed']`). That enum is the `/api/fleet` contract, and `AgentList.tsx` branches on it (1160, 2485-2632). `Fleet.issueAnswer` defaults to `'unsupported'` on purpose, for older servers (`schema.ts:4553-4559`). Keep "not read" as the absence of a reading on the client and domain side (for example `IssueAnswer | null` into the rule). For the new board-payload field, follow the board schema's own convention for "absent means not read": `.optional()`, not `.default('unsupported')` (compare `defaultBranch` and `tickets`, `schema.ts:1460-1482`).
- **Layering:** `refusalReason` lives in two `.tsx` files today (`CreatePlanButton.tsx:83`, `CreateStoryButton.tsx:93`), and `menus.tsx:211` re-exports it. The plan's move of the decision into a domain rule is correct under "Every rendered state is a domain property". Delivery's issue rows (`menus.tsx:1718,1731`) must call the same rule, so the two tabs cannot disagree. "A Decision Reads The Index" is not affected: this change passes an existing cached answer through. It makes no new host call.

## (d) Open questions

- **Q1 (fleet poll or board payload):** board payload. Evidence: `index.ts:487` already calls `ticketLaneData`, and the cache entry it reads holds `issueAnswer`, `issueAbsence` and `issueSets.answer` (`fleet.ts:2012-2016,2205-2210`). The field costs no host call and no second poll. It also fixes the "second effect" for free, because Discovery already polls `/api/board` every 30 s.
- **Q2 (other `fleet?.…` defaults that show a wrong state on a non-Delivery tab).** I found every one in `App.tsx`:
  1. **`App.tsx:1328`, `issueAbsence={fleet?.issueAbsence ?? null}` on Discovery. Same defect, inverted, confirmed by execution.** The rule is `discoveryGroups` (`discovery-groups.ts:71`). When `board.tickets` is null, it shows `issueAbsence ?? TICKETS_NOT_READ_REASON`. Take a repo whose source is `nobody`: `fleet.ts:2205-2210` sets `issueSets = null`, `issueAnswer = 'unsupported'` and an absence sentence. A fresh Discovery page then reads **"Tickets have not been read yet."** forever, which presents a standing host fact as "not loaded yet". After a Delivery visit it reads the true sentence. Fix it in this plan.
  2. **`App.tsx:1485` and `App.tsx:1498`, `planAgeSeconds={fleet?.ageSeconds ?? null}` on the Planning tab.** On a fresh page this is `null`, and `PlanSourceLine.tsx:145` correctly omits the age. After a Delivery visit, the line shows ` · Ns ago` frozen at the last fleet poll, and the number never ages. That is a stale age presented as a current one. This is the "second effect" on another tab. Planning is the default tab, so most readers see it.
  3. **`App.tsx:1558`, `planFileFromFleet(...)` in the sprint modal's `onOpenPlan`.** The sprint modal opens from Planning and Discovery. On a fresh page `fleet` is null, so a slug with no card does nothing when clicked. After a Delivery visit the same click navigates, using a possibly stale fleet. The same click behaves differently depending on tab history.
  - Not a defect: `App.tsx:545` and `App.tsx:775` test `tab === 'delivery'` before they read the fleet. `idea` and `story` at `App.tsx:1336-1337` come from the board payload.
- **New questions the plan should carry:**
  - What does the board-payload field read when the cache holds `issueSets === null` but `issueAnswer = 'unsupported'` (the `nobody` source)? It must send `unsupported` plus the absence sentence, not "not read". The field has to come from `entry.issueAnswer` and `entry.issueAbsence`, not only from `issueSets`.
  - Which wording does the unread state use? Suggested: "the issue read has not answered yet", never the Bitbucket sentence. Does it count as refused (`aria-disabled`) or as pending?

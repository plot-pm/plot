# Juror verdict: board server /api/board and /api/fleet payloads and polling

Position: amend

Evidence: Read the plan, issue #2833, `packages/board/src/app/App.tsx` (lines 39-40, 400-520, 632-653, 1320-1385), `packages/board/src/server/index.ts:461-566` (`/api/board`, `/api/fleet`, `/api/issues/closed` handlers), `packages/board/src/server/fleet.ts` (`ticketLaneData` 1682-1700, `refreshIssues` 1966-2095, `readIssuesFromStore` 2190-2260, `maybeRefreshPrs` 2560-2575, `freshCacheEntry` 2863-2918, `ensureCache` 2921-2980), `packages/board/src/server/discovery-lanes.ts`, `packages/board/src/contract/schema.ts` (1470-1482, 3662, 4550-4567), `CreatePlanButton.tsx:60-92`, `CreateStoryButton.tsx:93-100`, `StoriesTab.tsx`, `menus.tsx:211`, `AgentList.tsx` issueAnswer sites, `packages/domain/src/rules/cadence.ts:261-279`, `packages/domain/src/rules/discovery-groups.ts:41-72`. Ran: `pnpm install` in the worktree; `vitest run --project parallel test/unit/create-plan-button.test.ts` (7/7 pass); a throwaway vitest probe (copy kept at `scratchpad/juror-2833-server/zz-juror-2833.test.ts`, removed from the worktree after the run) that calls `freshCacheEntry()` and `refusalReason()`: a fresh server cache entry reads `issueAnswer: "unsupported"`, `issueSets: null`, and `refusalReason` on it returns `this git host has no issue read, so an issue cannot become a plan from here`. ## (a) Problem statement

- All four cited lines are correct at this tree: `App.tsx:516` (`if (tab !== 'delivery') return;`), `App.tsx:1338` (`issueAnswer={fleet?.issueAnswer ?? 'unsupported'}`), `CreatePlanButton.tsx:84`, `CreateStoryButton.tsx:94`.
- **The plan names only the client half of the cause. The server has the same defect.** `fleet.ts:2887-2889` initialises every cache entry with `issueAnswer: 'unsupported'` "before the first lookup". The comment explains that this avoids an `answered` before any read, but the value is still `unsupported`, and the button renders that as the Bitbucket sentence. The probe confirms it. `ensureCache` (`fleet.ts:2970-2971`) starts the first issue read with `void maybeRefreshPrs`, so the first `/api/fleet` or `/api/board` response after a board start goes out before that read lands. That response says `unsupported` on a GitHub repo whose read works. Removing the client default `?? 'unsupported'` alone does not fix a fresh board process, and a Delivery-tab poll in the first seconds after a start shows the same false sentence. `schema.ts:4559` `IssueAnswerSchema.default('unsupported')` is the third place the "no reading" value collapses into `unsupported`.
- **A second missed sibling is `App.tsx:1328`, `issueAbsence={fleet?.issueAbsence ?? null}`**. It has the same `fleet === null` source. The cost is milder: `discoveryGroups` (`discovery-groups.ts:71`) falls back to `TICKETS_NOT_READ_REASON`, which is true. But on Discovery the real absence sentence (for example `issueAbsence(source.reason)` for a `nobody` source) never shows until Delivery has been opened.
- **A third case maps a non-host fact onto the host sentence.** With fleetd running and no index, `readIssuesFromStore` sets `issueAnswer = 'unsupported'` with `issueAbsence = 'Open issues are not listed: the fleet has left no issue index to read.'` (`fleet.ts:2215-2219`). `refusalReason` ignores `issueAbsence` and prints "this git host has no issue read". That is wrong for the same reason the plan names: the fleet left no index, which is not a host fact.

## (b) Approach, and open question 1

**Move `issueAnswer` (and `issueAbsence`) into the `/api/board` payload. Do not poll `/api/fleet` on Discovery.** The evidence:

- **The server already holds the value while it builds `/api/board`.** The handler calls `ticketLaneData(opts)` twice (`index.ts:495`, and inside `discoveryLanes`), and that function opens with `const entry = ensureCache(opts)` (`fleet.ts:1683`). `entry.issueAnswer` and `entry.issueAbsence` sit on that same object. The added cost is one property read and a few bytes. It adds no host call, no file read and no scan.
- **One snapshot instead of two.** The Discovery ticket rows (`board.tickets`) come from `entry.issueSets`, the same entry. When the answer rides in the same response, a row and the answer that governs its buttons can never come from two different moments. With the fleet-poll option, rows arrive on a 30 s poll and the answer on a 4 s poll, and the two can disagree for up to 30 s, for example rows from before a failure under an answer from after it.
- **Request cost.** `/api/board` polls every 30 s (`App.tsx:39`, `POLL_MS = 30_000`) and refetches on `/api/events` pushes. `/api/fleet` polls every 4 s (`App.tsx:40`). Polling the fleet on Discovery adds 7.5 requests per 30 s. Each one serialises the whole fleet payload (rows, agents, PRs, waiting), only to read two fields. The comment at `App.tsx:513-514` already rejects this exact background cost: "a background 4 s poll would cost the same as a foreground one and answer a question nobody is asking."
- **Freshness.** The issue read changes at most once per `issueIntervalMs`, which is at least `ISSUE_REFRESH_MS = 120_000` (`cadence.ts:261, 278-279`). The read runs on the PR reader's 60 s beat behind that gate (`fleet.ts:2573`). A 30 s board poll observes a 120 s-cadence value with at most 30 s lag. A 4 s poll buys nothing measurable for this field. This also fixes the plan's second defect (a stale reading after one Delivery visit), because the board poll never stops on Discovery.
- **Board with no fleet.** `/api/board` does not depend on fleetd. With no fleetd, `maybeRefreshPrs` calls `refreshIssues` itself (`fleet.ts:2574`). `ensureCache` starts that pulse on the first `ticketLaneData` call from `/api/board`, so a Discovery-only page keeps the issue cache refreshing with no `/api/fleet` request. With fleetd running, `readIssuesFromStore` fills the same fields (`fleet.ts:2572`). Both paths land on `entry`, so the board payload carries a correct answer in both cases. The `/api/fleet` endpoint is served by the board process with or without fleetd, so "no fleet" never meant "no endpoint". But polling it ties Discovery's controls to a second endpoint's failure counter, and the dimming logic only counts `boardFailures` on non-Delivery tabs (`App.tsx:531, 542`). A failing `/api/fleet` on Discovery would freeze `issueAnswer` with no banner.
- **Contract change is additive.** `Board` already carries per-request capability fields (`idea`, `story`, etc., `index.ts:498-510`) and the Discovery lanes. Add `issueAnswer: IssueAnswerSchema.optional()` and `issueAbsence: z.string().nullable().optional()` to `BoardSchema`, following the `tickets` precedent (`schema.ts:1477-1482`, "absent means an older server … drawn the same as a cold read"). An absent field must render as "not yet known", never as `unsupported`. Keep `Fleet.issueAnswer`, because the Delivery tab's WAITING ON YOU reads it together with `fleet.issues` (`AgentList.tsx:1160, 2485-2632`).

**Slice 1 ("a loading state") must reach the server, or it does not fix a fresh process.** Add a fourth `IssueAnswer` value meaning "not read yet" (for example `unread`) to `IssueAnswerSchema` (`schema.ts:3662`). Make `freshCacheEntry` start with it (`fleet.ts:2889`), and keep the `.default('unsupported')` at `schema.ts:4559` only as the older-server reading, as its own comment says. Then every consumer of the enum needs the new arm: `refusalReason` in both buttons, `storyRefusal` at `menus.tsx:211`, the four `AgentList.tsx` comparisons (an `unread` WAITING ON YOU block should say "not read yet", not show nothing), and `discoveryGroups`.

**Layering.** `refusalReason` lives in `.tsx` today (`CreatePlanButton.tsx:83`, `CreateStoryButton.tsx:93`), and its test imports a component file. The plan is right to move the decision into the domain, as one rule for both buttons that takes `issueAnswer` and `issueAbsence` and returns `available | loading | refused(reason)`. The `issueAbsence` input fixes the "no issue index" wording in (a). Neither option for open question 1 conflicts with *A Decision Reads The Index*: both read the in-memory cache, and neither spends a host call.

## (d) Open questions

1. **Answered: move `issueAnswer` (and `issueAbsence`) into `/api/board`.** It costs one field read with no extra request, shares one snapshot with the ticket rows, its 30 s lag sits well below the 120 s issue cadence, and it works with and without fleetd (evidence in (b)).
2. **Partly answered:** `StoriesTab.tsx:504-505` takes the prop from `App.tsx:1338`, so it is fixed at the same place. The other `null`-defaulted Discovery read is `App.tsx:1328` (`issueAbsence`). `App.tsx:1485, 1498` (`fleet?.ageSeconds ?? null`) serve the Delivery-side views and read `null` honestly as unknown. The Delivery-tab `IssueRowActions` (`rows.tsx:2883`, `menus.tsx:1718-1731`) read the live `fleet.issueAnswer`, so they show the cold-start `unsupported` from `fleet.ts:2889` too.

New questions the plan should carry:

- What does the server answer before its first issue read? Today it answers `unsupported` (`fleet.ts:2889`), and the plan must name the new value and who renders it.
- Should the refusal sentence come from `issueAbsence` when the server has one, instead of the fixed Bitbucket sentence? Today a missing fleet index reads as "this git host has no issue read".
- Does the new enum value change `waitingOf`, or the `issues.json` index shape that fleetd writes? It should not: the index records reads, and "unread" is a property of this process's memory. The plan should say so, so that nobody persists `unread`.

## (e) Tests

- **Domain unit test** (`packages/domain`): the new refusal rule. `unread` gives loading. `unsupported` with an absence gives that absence. `unsupported` with no absence gives the host sentence. `failed` gives the failure sentence. `answered` with an unavailable binding gives the binding's reason. `answered` with an available binding gives available. Write it once and use it for both buttons.
- **Board unit test**: `freshCacheEntry().issueAnswer === 'unread'`. A `/api/board` handler or `discoveryLanes` test asserts that the payload carries `issueAnswer`/`issueAbsence` from the cache entry, and asserts `unread` before any `refreshIssues` (the probe above is that test, inverted). Extend `no-fleet-issue-gate.test.ts` or `issue-source-poll.test.ts` to assert that the board payload says `answered` after one `refreshIssues` with no fleetd.
- **Browser test**: a fresh `?tab=discovery` page against a mock that answers `answered` shows enabled Create plan and Create story with no Delivery visit. A second case serves `unread` and asserts the loading text, never the Bitbucket sentence. `issue-becomes-a-plan.browser.test.ts` is the existing home.

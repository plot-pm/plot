## What must change

New findings (the amendment added these claims):

1. **Design › Restart and Slice 4 › Mode: `process.execve` sets a Node floor for adopting repositories, and the plan cites the wrong pin.** The plan says "The repository pins Node 24 (`engines`)". That pin binds this repository's development, not an adopter's runtime. The bundles target `node20` (`command grep -n target packages/board/build.mjs`: 10 of 10 entries say `'node20'`). `node -e 'process.execve(...)'` on v20.19.4 fails with `TypeError: process.execve is not a function`, and `typeof process.execve` is `undefined` on v18.20.8 and v20.19.4 and `function` on v22.17.1 and v24.4.1. Slice 4 says the entry "`exec`s the shell body when the value is `shell`", and `shell` is the default. So from slice 4, before any JS evidence, every adopting repository on Node 20 loses its loop, not only those that opt into `js`. The plan must state the Node floor (22.15 or 24), say how an adopter learns it (the slice-4 "No bundle" refusal shape, or `/plot-board-setup`'s probe), or make the `shell` path a launcher-side `exec` that needs no Node.
2. **Design › Restart: "The main checkout only moves forward" is false, and the cost is the whole fleet.** Nothing in the estate fast-forwards the main checkout: `git grep -nE "ff-only|git pull|'pull'" -- packages/board/src/server skills/plot/scripts/` finds two comments and no caller. The checkout moves when the operator pulls, commits, checks out another branch, or runs `pnpm build:board` there. The memory "Board renders the checked-out branch" records that the operator's checkout does switch branches. A content-hash difference then restarts every running loop into older or unmerged code, which is the failure round 1 item 2 asked the plan to prevent. The restart needs a direction check (for example, the bundle's build commit is a descendant of the loaded one on `origin/main`), not only a hash difference. The CPU line "about ten times a day at the current merge rate" also assumes the checkout follows merges; the real rate is the operator's pull rate.
3. **Design › Restart: an `execve` into a bad bundle kills every agent at once.** A hash read during a `git pull` or a build can see a partial file, and an `execve` into a bundle that throws at load ends the process with the pid the wrapper waits on. All loops at a no-work point see the same new hash in the same pass, so all die together, and each death spends a supervisor relaunch (`rules/supervision.ts`, `MAX_ATTEMPTS`). The plan must say the loop proves the new bundle loads (a probe start, or `node --check`) before it calls `execve`, and that a failed probe keeps the old code with one log line.
4. **Slices 4–6: in `js` mode the BuildMonitor still starts, so two writers share one file and the host pays twice.** `plot-dispatch.sh:1491` starts `plot-build-monitor.sh` whenever it is executable, with no mode check, and slice 7 is the first slice that removes that start. Under `js` both the BuildMonitor and the JS loop write `.plot-worker.monitor.build.jsonl`. Both call the same host operation: the BuildMonitor asks `plot-host.sh run-for-sha` every 30 s (`plot-build-monitor.sh:147,165`), and `build-actions.ts` reaches `plot-host.sh run-for-sha` too (`build-shell.ts:127,157`). That is 180 calls an hour per waiting agent instead of 60. The REST bucket reads 5,000 an hour (`gh api rate_limit`), so eight waiting agents spend 1,440, which fits; the plan should still state it, and either skip the BuildMonitor start for a `js` agent or keep the JS loop from writing the file while a BuildMonitor runs. The orphan monitors in Motivation also keep their source until slice 7, so the "a loop process that outlives its desk" failure in slice 6 does not count them.
5. **Slice 6: "over the same window" cannot be measured with a repository-wide key.** `Worker loop` is a `## Plot Config` key, read once per repository. Status says #1255 closes here "until slice 4 runs the fleet on `js`", so in that window every slice runs `js` and no slice runs `shell`. The comparison then has no `shell` count. The plan must name how both loops run in one window (a per-agent value, for example in the agent registry or an environment override the launcher passes) or name a fixed `shell` baseline window before the switch.
6. **Slice 4 › Shell ratchet: the offset the plan names does not exist.** The plan pays for the launcher with "the body's own bundle-resolution and refusal preamble". The body has no such block. Its setup (`awk` over lines 60–200, non-comment) is `set -uo pipefail`, `script_dir`, `plot-tmp.sh`, `repo_root`, `cfg` and config defaults, and the moved body still needs all of them. Each bundle resolves inline at its call site (`plot-worker-loop.sh:878,917,1268,1439,1530,1751,3065`). A launcher is about four non-comment lines, so any four removed lines pay for it; the plan should name real ones or say the slice removes four lines elsewhere.
7. **Costs › CI: the matrix leg also re-runs end-to-end files.** Of the 30 files, 5 sit under `test/e2e` and round 1 counted 4 of them as driving the loop. CLAUDE.md names e2e suites at 5 to 10 minutes each. The CI cost line names only `workerloop.test.mjs` (141 s). The `validate` job took 19 m 24 s on run 37208059832 (`gh run view 37208059832 --json jobs`: 14:18:43 to 14:38:07). The plan should say whether the `js` leg includes the e2e files and how long the window lasts: from slice 4 until slice 7, which waits on slice 6's 20 slices.

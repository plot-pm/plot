## What must change

1. **The table's `agentState` column, against `rules/task.ts:87-88` (new).** `taskState` returns `finished` first when `hasPr` is true, and `hasPr` means "an open or merged PR" (`task.ts:43`). `agentState` reaches `taskState` on exit 0 (`agent-state.ts:143`). The row "checks fail, budget spent" follows a row that requires "a PR open", so with exit 0 it reads `finished`, not `waiting`. Today's exit 1 reads `finished` too, through `hasPr ? taskState : failed`. The row "a `PLOT-BLOCKED` marker" reads `finished` whenever the PR already exists, which holds for every marker written after a correction. The row "holding-work" reads `finished`, not `stalled`, when a correction prompt leaves uncommitted work beside an open PR. Design's sentence "agentState then reads the desk through taskState: waiting for a marker" therefore holds only for a desk with no PR. The table test the plan promises, which "asserts both columns through the two rules themselves", fails on these rows as written. The plan must split those rows by PR and give `finished` where a PR exists, or name a change to `taskState`'s order and argue against its docstring ("An open or merged PR outranks everything below it").
2. **The marker rows, against `rules/desk-lifecycle.ts:101-110` (new).** The plan says the spent-budget marker names the PR "so `markerRecordsWork` holds", and the blocked row reads `refused-with-work` or `refused-empty` "by what the marker records". The rule's field doc says the opposite: "A READING, NOT A PARSE … `markerRecordsWork` answers *is there more here*, never *what does the marker say*." It holds when the desk has a dirty path other than the marker or a file-changing commit. The conclusion for the spent-budget row still holds, because the pushed commits give `fileChangingCommits > 0`. The reasoning must change to that reading, and the blocked row's cell must say "by whether the desk holds work beside the marker".
3. **The CI wait's settle on a containing tip, against Design's own sentence (new).** Design says the containment condition means "the wait never settles on someone else's build". A tip that contains the agent's commit can also carry someone else's commit on top of it. #1199's measured case is that shape: an operator pushed `0e64fafd` on top of the agent's `f743e573`. The plan settles the wait on that tip's result, so a failure that the operator's commit causes becomes a correction prompt and spends the agent's `Correction budget`. That contradicts "never settles on someone else's build". The sentence "That is the end of the wait that #1199 asks for" also maps the wrong case: #1199 asks for an end when the branch "moves past the desk", which is the containing case, and the plan ends the wait only for the non-containing case. The plan must state what a failure on a tip with foreign commits does to the correction budget, and correct the #1199 mapping.

The port table (plan lines 100-105) lists none of these, and Design says "every new spawn sits inside `adapters/`".

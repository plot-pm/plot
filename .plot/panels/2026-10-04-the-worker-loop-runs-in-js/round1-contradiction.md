## What must change

1. **Design › "The CI wait reads the pull request's current head, through the host port", and the fourth Changelog line.** The estate already decided that CI checks do not go through the host port. `ports/host.ts:117-121` says "THE BUILD PIPELINE LEFT FOR THE SAME REASON … `CI` is a config key declared independently of `Git host`". `ports/build.ts` declares `BuildPort` with `runs(branch)` and `runForSha(branch, sha)` (lines 17 and 46 of the interface excerpt). The plan `2026-09-07-the-build-pipeline-is-its-own-connector` is Released. The slice must read the head's runs through `BuildPort.runForSha`, take the PR's head SHA from the host port, and say so. Read as written, the plan reverses a released decision and loses Bitbucket-plus-Jenkins repositories again.

2. **Design › the CI wait, against "A Decision Reads The Index".** CLAUDE.md says a decision reads the index and that `fleet.ts` is the one writer (`foldPrIndex`). It also names "a PR's checks" as an answer the index holds. The plan has each live loop buy a fresh check answer once a minute per waiting agent and decide from it, with no word on the index or on the connector's rate budget. The #1171 plan (line 62) chose the BuildMonitor path partly to keep one host reader. The plan must state which it does: read the index first and ask the connector on a miss, or ask the connector directly as a declared exception with its call rate per agent. It must also state that the loop never writes the index.

3. **Design › Slice 1 state table, `blocked` row, against `/api/continue`.** The table says `blocked` exits to `working` when "the marker is answered (`/api/continue`)". `packages/board/src/server/continue.ts:333` says the route spawns "a NEW worker in the branch's existing worktree" through `sh -c` on `Worker command`, and lines 336-342 refuse to continue where a second loop could share the desk. So `/api/continue` never moves a live loop from `blocked` to `working`; it starts a second process. Either the loop ends on `blocked` (and `blocked` exits to `ending`), or the plan changes `/api/continue` to signal the live loop. The plan must pick one and name the controller change, because two loops on one desk is the failure continue.ts was written to prevent.

4. **Design › Slice 1 states, against the Agent's eight states and CLAUDE.md "The Domain Package".** Three of the loop's states restate facts the Agent already carries, under different words. `blocked` is the Agent's `waiting` (a `PLOT-BLOCKED` marker; `STATE_SOURCE` in `transitions/agent.ts` sources it `desk`). `holding-work` is the Agent's `stalled` (unlanded work, sourced `desk`). `ending` overlaps `ended`. CLAUDE.md says a state answering "what is the process doing?" goes on the worker and one answering "what does this agent owe?" goes on the agent, and that the mixed enum "is not a licence to add a workflow state to the process side". `agentLoop` mixes both kinds in one set (`working`, `ending` are process facts; `blocked`, `holding-work` are desk facts). The plan must either reuse the existing words or add a table that maps each loop state to the `AgentState` and `DeskState` a reader derives for the same desk, and a test that asserts the mapping.

5. **Design › `holding-work`, against `deskLifecycle`'s `holding-work`.** The name already exists in `rules/desk-lifecycle.ts:29` with a different precondition: "unlanded work, no marker, **no live worker**" (the plan `every-desk-state-has-an-exit`, slice 3 table). `deskState` returns `working` first whenever `workerPid` is set (`desk-lifecycle.ts:158`). The plan's loop sits alive in its own `holding-work`, so the desk rule reads that desk as `working` with exit `re-read`, and never reaches its own `holding-work` exit to a person. The person the plan promises "named on the board" then comes only from `agentState`'s `orphaned` route (`agent-state.ts:133`). The plan must rename the loop state or state which reader names the person, and test that the board shows one for a live loop holding work.

6. **Design › "names every state an agent's loop can be in" (Changelog line 2), against rules the loop already obeys.** Two loop states that existing rules produce are missing from the table. `promptExit` answers `wait` for a usage limit with a known reset (`rules/prompt-exit.ts:76-85`), so the loop has a state "waiting for a limit to reset". `loopRegistration` answers `gone` when the manifest a waiting loop holds disappears (`rules/desk-manifest.ts:232`), and that ends the wait. Neither row exists. The Changelog claim "every state" is false until both rows are added or the plan says they fold into a named row.

7. **Design › correction budget, against `rules/supervision.ts`.** The supervisor already decides `correct` and `needs-a-person` with its own budget (`supervision.ts:120`, `:203` `attempts >= MAX_ATTEMPTS` gives `budget-spent`), and `workflows/supervise.ts:190-196` emits `agent-attempt` and `agent-resume`. The loop counts `Correction budget` separately (`plot-worker-loop.sh:261`, `:2830`). The plan moves the loop's count into `agentLoop` without naming the supervisor's. That makes two domain rules for one question. CLAUDE.md permits duplication only when declared. The plan must name both budgets, say why they stay apart (live loop versus dead worker), or fold them into one rule.

8. **Design › the action vocabulary, against `workflows/decision.ts`.** `decision.ts:1-7` says every workflow answers `readings -> Decision | Refusal`, and `Write` already holds `agent-resume`, `blocked-marker`, `commit`, `push`, `worker-signal` and `manifest-clear`. The plan defines a second list of actions ("take up, reset, run prompt, wait for checks, hand back a correction, write a marker, release, end"). Placing `agentLoop` under `workflows/` with a new action set breaks that shape. The plan must state whether `agentLoop` returns a `Decision` with existing `Write` kinds plus new ones, or why it is a rule outside `workflows/`. If its states are a `z.enum`, `scripts/check-state-declarations.sh` requires a `plot-state: lifecycle` marker and a `transitions/` rule, and the plan should name that file.

9. **Open Questions / Design, against Manifesto principle 13 and `Worker bound`.** Principle 13 says an unattended command "must bound how long it may run". The table gives the wait bound as an exit only from `free`. `blocked` and `holding-work` list only "a person" as exit, and the self-restart `exec`s "with the same arguments" without saying whether the bound restarts. The plan must state that the `Worker bound` applies in every state and that the restarted process keeps the original start time, so a restart cannot extend the bound.

10. **Design › "What does not change", against Manifesto principle 5 and the `Worker command` contract.** The plan says "`claude -p` is still the agent". The loop runs the project's `.plot/worker-prompt.sh` (`plot-worker-loop.sh:20`; `skills/plot-dispatch/SKILL.md:204`), and Plot names no harness by Principle 5. The JS loop must run the declared prompt file, and the plan should say so. The restart-on-new-code rule compares the bundle's hash at its own path. `skills/plot-dispatch/SKILL.md:207-210` says the bare name resolves to the loop beside the versioned plugin directory, and a plugin upgrade installs a new directory (`ls ~/.claude/plugins/cache/plot-marketplace/plot/` lists 13 versions). The bundle at the old path never changes, so the restart never fires for an adopting repository. The Changelog line "it never keeps running yesterday's code" must be narrowed to a checkout, or the plan must name how a plugin install learns of a new version.

## What holds

- The measurements hold on main: 891 code lines, 3,137 lines, 52 functions, 30 test files and the seven bundles, by the commands above.
- The direction holds. `docs/shell-and-domain.md:26` already says "a command is a JS entry point" and "a `.sh` file that remains is a launcher: it resolves its bundle and `exec`s it". The plan follows that target.
- Removing the declared duplicates once the loop is JS is consistent with the cost rule. `docs/shell-and-domain.md:18-24` justifies the duplicates only by the per-pass `node` start, and an in-process import removes that cost. The plan correctly scopes removal to loop-only helpers, which matters because `corpus/agent-state.corpus.test.ts` pairs `plot-worker-state.sh`, which `plot-dispatch.sh --status` also uses.
- The Layering Rule holds in shape. A board entry that wires adapters and calls a domain function matches `entry/registryd.ts`, which runs `supervise` and `assign` in a long-running process. The `processes` port has no operation to start or kill a prompt tree (`ports/processes.ts:37-83`), so slice 2 must add one to an adapter to keep the spawn ratchet from growing. The plan says processes go through "the process adapter" and should name the new operation.
- Keeping `Worker command` naming `plot-worker-loop.sh` holds against `skills/plot-dispatch/SKILL.md:350`, where `--start` refuses any `Worker command` that does not run `plot-worker-loop.sh`. Removing that name would break every adopting repository's free agents.
- `free` as a loop state does not contradict `rules/free.ts` ("derived, never stored") as long as the loop state is re-derived from the manifest on restart and never written. The plan's "the manifest on disk is the state" says this. One sentence stating that `agentLoop`'s state is never persisted would make it explicit, matching `transitions/agent.ts` ("Nothing anywhere writes an `AgentState`").
- No other plan claims #1199, #1246 or #1255.
- The #1148 open question is correctly left open. `docs/plans/2026-10-01-a-supervisor-restart-leaves-its-agents-running.md` sets `KillMode=process`, so systemd signals only the daemon, and the JS loop's process-group handling has to be measured under that setting, as the plan says.

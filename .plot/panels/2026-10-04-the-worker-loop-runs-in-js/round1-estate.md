## What must change

1. **Design › Slice 1 table: the loop states collide with three state vocabularies that already exist, and the plan names none of them.** `transitions/agent.ts:43-73` holds the eight observed agent states and their move graph (`NEXT`), and states that an agent's state "is observed, not stated" (`:5-13`). `transitions/worker.ts:5-9` refuses a second move graph over one set of states as "the Wave/Slice-shaped defect this repo already carries once". `rules/desk-lifecycle.ts:22-29` already declares a `DeskState` named `holding-work`, with the exit "a person decides whether to push it or let it go" (`:205-207`). That is the plan's `holding-work` row under the same name. #1246's own body names that state: "A desk that holds a slice's uncommitted work is the `holding-work` state in `every-desk-state-has-an-exit`". `rules/free.ts:9-13` already records that two vocabularies (the domain's eight and the board registry's five) spell availability. The plan must say how each `agentLoop` state relates to the eight states the board renders. It must derive `holding-work` from `deskLifecycle`/`deskState` and `checkoutYield`, and not from a second rule. It must state that the loop states are a third vocabulary, or else reuse the existing ones.

2. **Design › "The CI wait reads the pull request's current head, through the host port": the wrong port, and a port that cannot answer.** The `Host` port (`ports/host.ts:136-276`) has no checks-by-SHA question. `Pr` (`entities/pr.ts:47-…`) carries `head`, documented as "The branch this PR belongs to", plus an aggregate `checks` field. It carries no head SHA. The estate already has a reading by SHA: `BuildPort.runForSha(branch, sha)` (`ports/build.ts:105`), with adapters `build-actions.ts`, `build-jenkins.ts`, `build-none.ts` and `build-fixture.ts` under `adapters/build/`. Those adapters came from `the-build-pipeline-is-its-own-connector`. A Bitbucket-plus-Jenkins adopter gets its checks from the build connector and not from the git host. The plan must name `BuildPort` (and the PR head SHA reading it needs from `refs`). Two exports named `checksVerdict` exist: `rules/checks-verdict.ts:80` (the loop's, over BuildMonitor findings) and `rules/checks-reading.ts:130` (the board's, over host readings). The plan must say which one "moves whole", and what happens to the other.

3. **Design › Approach: "reads the world through the adapters that already exist" holds for reads and fails for writes.** `git grep` over `packages/domain/src/ports/*.ts` finds no operation that pushes a claim, resets a desk, commits, runs a prompt under a bound, kills a process tree, writes an agent manifest, writes `.plot-worker.ending.json` or writes a `PLOT-BLOCKED` marker. The one write port that starts processes, `Performer`, starts agents and not prompts (`ports/performer.ts:33,62`). Manifest writes live in the board (`packages/board/src/server/manifest-stamp.ts`), outside the domain adapters. "The registry adapter" is `packages/board/src/server/registry.ts`, not a domain adapter. The Layering Rule requires the domain to own a port for each of these writes. Slice 2 must list the new ports and adapters. As written, slice 2 hides the largest part of its work. For Open Question 1, `adapters/run-script.ts:58-66` already spawns `detached: true` and kills the group with `process.kill(-child.pid, 'SIGKILL')`. That is the estate's starting point for `_kill_tree` (15 uses in the loop) and should be named.

4. **Design › Slice 1: the workflow shape departs from the estate's shape without saying so.** `workflows/decision.ts:1-6,21` fixes the form `readings -> Decision | Refusal`, with ordered, typed `Write` values that a performer applies. `workflows/supervise.ts` states that the supervisor carries "no carried state … which is what makes `kill -9` cost one tick". `agentLoop(state, readings)` takes a carried state and returns a non-`Write` "action". The plan must either derive the state from the readings (the manifest and desk on disk, which the restart paragraph already relies on) and return `Decision`/`Write`, or give the reason for a new shape.

5. **Design › "The process restarts itself on new code": the estate has two reload policies already, and the plan's motivation case is a third one that this plan does not fix.** `pnpm board` runs `node --watch` (`package.json:14`). `plot-boardctl.sh --start` runs `exec node "$artifact"` with no watch (`plot-boardctl.sh:425`), so a board started through `/plot-board --start` never reloads. That is motivation item 5. `plot-registryd` has no reload. It relies on `launchd`/`systemd` keep-alive (`registryd-main.ts:81`, `units/plot-registryd.service:74`), so it has the same exposure. An adopting repository runs the loop from a versioned plugin cache directory (for example `~/.claude/plugins/cache/plot-marketplace/plot/2.22.2/skills/plot/scripts/`, with `PATH` set as `rules/adoption.ts:225-234` describes). An upgrade writes a new directory and leaves the old bundle unchanged, so a hash check on the loop's own path never fires there. The plan must state this scope (it fires in this repository and not after a plugin upgrade). It must say whether the mechanism is shared with registryd and the board, or is specific to the loop.

6. **Design › Slice 2: "The 30 test files run against both values" cannot hold for the files that read the shell's text.** `test/reconcile/refused-slice-record.test.mjs:35-78` extracts bash functions from the loop's source (`extractFunction('record_refused_slice')`). `checks-wait.test.mjs:163`, `deskreset.test.mjs` and `workerloop.test.mjs` each call `readFileSync(loop, 'utf8')`. A text assertion has no JS counterpart. The plan must name these four files and the behaviour each one pins, so that "reported, never rewritten" does not turn into four reports on the first run.

7. **Design › Slice 4: the removal list needs the callers it says it will check, and several of them are not loop-only.** `plot-worker-state.sh` is read by `adapters/processes/processes-shell.ts:79` (the board's process reading) and named by 22 other scripts, bundles and server files (`git grep -l plot-worker-state`). Three corpus tests that pair it (`agent-state`, `refs`, `sample`) have callers other than the loop. Only `corpus/desk-reset.corpus.test.ts` pairs a loop-only duplicate (`docs/shell-and-domain.md:84`). `plot-build-monitor.sh` is named by `entities/finding.ts` and `plot-monitor-subject.sh` as well as by the loop and `plot-dispatch.sh`. `plot-transcript-quiet.sh` holds: the loop is its only caller. Slice 4 should name `desk-reset` as the duplicate it removes and the loop's half of `agent-state` as the part it trims, not "the loop's declared duplicates" in general.

8. **Slice 2 and the shell ratchet: the plan adds shell and does not name the offset.** `scripts/check-shell-lines.sh` (`c2da54eed`, #1264) fails a change that grows the `.sh` line count. Slice 2 adds a `Worker loop` config read and an `exec` branch to `plot-worker-loop.sh`. The plan must name the offset. It must also give the launcher's behaviour when the bundle is absent. `docs/shell-and-domain.md:30` requires a refusal and not silent fallback. `the-shell-shrinks-into-the-domain` slice 4 sets the form: exit 2 with slice 3's message, following `plot-release-gate.sh:30-33`.

9. **Status and Changelog: the issues are claimed by a slice that ships no behaviour.** #1199 asks for a narrow fix: a rule change in `rules/checks-verdict.ts` plus a case in `test/reconcile/checks-wait.test.mjs`. #1246 asks for the loop's go-free path to consult `checkoutYield`/`deskLifecycle`, which already decide the case. Slice 1 ships `agentLoop`, which nothing calls until slice 2 runs behind a key that defaults to `shell`, and adopting repositories get it only at slice 3. The plan must say either that the fleet carries #1246, #1255 and #1199 until slice 3, or that narrow fixes land through the existing bundle seam first.

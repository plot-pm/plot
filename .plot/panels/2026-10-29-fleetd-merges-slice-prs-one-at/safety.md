## (a) Problem statement

- The motivation is correct: fleetd merges nothing today. Nothing under `packages/fleet/src` calls `merge`. `mergeAt` has one caller, `plot-ask.mjs merge` (`board/src/server/entry/main.ts:163`).
- **Wrong fact: "`default-branch-red` already does this" (hold the merge).** `default-branch-red` is a dispatch hold. `whyNotReady` (`rules/queue.ts:583`) holds a queued slice from being handed to an agent, and it never acts on a merge. What refuses a merge is the controller: `merge.ts:127` (`default-branch-red`) and `merge.ts:123` (`default-branch-stale`). The two use opposite staleness semantics. `defaultBranchRed` (`rules/default-branch.ts:262-270`) reads a stale red as **not red**, which lifts the hold. `merge()` refuses any stale reading. A builder who reuses `defaultBranchRed` for the rule's "red or stale → hold" row gets a rule that answers *merge* on a stale red. The controller then refuses, and the next 5 s scan asks again.
- **Wrong fact: "The design lifts the unattended refusal … This plan depends on #2900 for that identity."** Two errors:
  1. The merge controller has no unattended refusal to lift. `main.ts:150-172` reads no `PLOT_UNATTENDED`, and `gate.ts:651-700` refuses only an *unpinned* merge. A linked worktree (a desk, and later a fixer) is allowed outright (`gate.ts:684`, `if (linked) return null`). Today any unattended desk or role agent can run `plot-ask.mjs merge <pr> <sha>`. Sibling plan #2908 (line 24) makes the same false claim.
  2. #2900's plan (PR #2917) builds no caller identity. The identity is #2898's slice `feature/fleetd-caller-identity` (PR #2908, line 66).
- The plan does not name the cause the anti-goal turns on. The in-flight mark is "derived from the default branch's head and its settled reading". The only recorded copy of that reading is `.plot/state/default-branch.json`. fleetd refreshes that file on the PR beat, every 12th 5 s beat, so at most once per 60 s (`fleet-clock.ts:21-35`, `fleet-scan.ts:20-23`, `registryd-main.ts:2615`). The automatic writes, where a merge would naturally run, run on every 5 s scan (`registryd-main.ts:2598`, `auto-writes.ts:48-79`).

## (b) Approach, under the safety lens

1. **One merge in flight does not hold against the fleet's own merges (HIGH).** The tick merges PR A at scan N. Scans N+1 to N+11 still read the pre-merge file: `headSha` is the old head and `settled` is green on it. The derived mark reads "settled on head, nothing in flight", so the rule answers *merge* for PR B. `merge()` does not stop it. In my probe, `merge()` **passed** in each of these cases (1) the head is `pending` past a green settled commit, which is exactly a merge in flight; (2) the reading still names the pre-merge head; (3) there is no reading at all (`null`). `merge.ts:117-130` checks only red and stale and never compares `headSha` with `settled.sha`. Up to 11 merges can land inside one PR-beat window, and more when `prGateOpen` backs the PR beat off. A fleetd restart reads the same old file, so a crash after a merge call widens the window. **Fix:** confirm the mark where the host is re-asked. Read the default branch's tip fresh at merge time (`refsRemoteGit.remoteSha`, one `git ls-remote` call that costs no API budget, `refs-remote-git.ts:54-67`). Refuse a new `merge-in-flight` reason unless that tip equals the reading's `settled.sha` and the settled state is green. This follows "the index selects, the controller confirms", and it also covers a person's merge and a direct push, which this repo makes often (5163dbee5, 799a9f320 and 88ab8e4be are direct pushes on 2026-10-29). fleetd still stores no mark.
2. **A missing reading lets the merge through (HIGH for an unattended caller).** `merge.ts:121` treats `null` as "holds nothing", by design for a person. `decodeDefaultBranch` returns `null` for an absent file, an unparseable file *and any other `v`* (`entities/default-branch.ts:85-95`). A future `DEFAULT_BRANCH_VERSION` bump would therefore remove every main-red guard from the fleet's merges at once. For fleetd's merge, a `null` reading must hold.
3. **Bypass rights exist today, and the controller does not check `plot/review` (HIGH).** Ruleset 24412719 lists `{"actor_type":"RepositoryRole","actor_id":5,"bypass_mode":"always"}` (Admin). `gh api repos/plot-pm/plot` answers `admin: true` for the signed-in identity. `plot-host.sh pr-merge` merges as that identity unless a `Merger app` is declared (`plot-host.sh:4442-4453`, `docs/review-status-rollout.md:153`: *"Without the keys, the ruleset does not apply to an identity that holds `bypass_mode: always`"*). This repo's `## Plot Config` declares no `Merger app`. `merge()` checks the folded rollup only, and an *absent* `plot/review` status is simply missing from `statusCheckRollup`, which can therefore still fold green (`plot-host.sh:706`). So fleetd running as jwloka could merge a PR that has CI green and no review. That breaks the design's "No fleet merge bypasses the ruleset". On Bitbucket no ruleset exists to back this up. **Fix:** the controller re-asks `host.prReview` (`ports/host.ts:399-408`) and refuses unless `plot/review` is `success` on the pinned head. fleetd also refuses to merge when `plot-merger-token.mjs` answers 5 (no `Merger app`) on GitHub, or the plan states that it accepts this gap.
4. **The unattended rule points the wrong way for merge.** fleetd merges in-process through the domain, so it needs no caller identity. The design's role agents (fixer, unblocker, main-repair) never merge. The safety rule needs a refusal that does not exist yet: `plot-ask.mjs merge` should refuse `PLOT_UNATTENDED=1`. Without it, a fixer in its worktree can merge its own PR around the in-flight mark. Put this in this plan, or name it as a required change to #2908.
5. **Where the merge runs is unnamed.** "fleetd's tick" could mean the supervision tick (`registryd-main.ts` `tick`), which also runs under `--once`, or the scan clock's automatic writes. `plot-fleet --once` is documented as *"change nothing persistent"* (`skills/plot-fleet/SKILL.md:285`), and a merge cannot be undone. The plan must say that merges run only in the looping daemon and never in `--once`. Within one process, two scans never overlap (`fleet-clock.ts:85-96` in-flight guard). Across processes nothing serializes, so the fresh tip check in item 1 is the cross-process guard as well.
6. **Layering: the plan does not say where the merge's adapter code goes.** `mergeAt` lives in `packages/board/src/server/entry/merge.ts`, and `@plot-pm/fleet` depends only on `@plot-pm/domain` (`packages/fleet/package.json`). Slice 2 must move `mergeAt` into a shared place or compose the same ports in fleet, without a second copy that can drift from the one `plot-ask.mjs` uses. The plan should name which.
7. **No rule stops a retry when a host call fails or answers partially.** `mergeAt` maps every non-`answered` host result to `host-refused` (`entry/merge.ts:70-73`). That covers a timeout after GitHub actually merged, a ruleset refusal and a conflict. fleetd stores nothing, so the next 5 s scan selects the same PR again and spends another `pr-state --with-checks`. A timeout that did merge is safe only through item 1's fresh tip check, after which the PR reads MERGED. A persistent refusal at the same head (BLOCKED, DIRTY) repeats until the head moves. The rule should hold a row whose index `mergeable` is `CONFLICTING`. The plan should name how a `host-refused` at head H stops a retry every 5 s.
8. **A person acting at the same moment:** a push to the PR refuses `head-moved` (pin, `merge.ts:107`). A person merging the same PR gets `pr-not-open`. A person marking it draft gets `draft`. All three are safe. A person merging a *different* PR in the same seconds remains a two-in-flight window that only the item 1 fresh tip check shrinks. The plan should state that this window is accepted.
9. **"Settled" can stall forever.** `foldRuns` returns `unknown` for no runs or a cancelled run (`rules/default-branch.ts:78-84`). If the newest head never gets a declared run, `settled.sha` never equals `headSha`, and the in-flight hold never lifts. This is not red, so #2904 never starts repair either. The plan needs a bound and a notification, using the design's *Stalls*. Observed today: the live reading has head 5163dbee5 `pending` from 19:55Z, and CI was still `in_progress` at 20:09Z, so each direct docs push holds the queue for one full CI run.
10. **Conflict with #2904:** the fix PR "jumps the queue" while main is red, but `merge.ts:127` refuses every merge on red. Either this plan's hold rows carve out the repair PR, or #2904 owns that exception. One of the two plans must say so.

## (d) Open questions

- *Same `Default branch checks` for "settled"?* Yes. `refreshDefaultBranch` folds only `declaredRuns(…, world.checks)` (`default-branch-refresh.ts:114, 230`) into the one file that `default-branch-red` and `merge()` read. A mark derived from that file inherits the list. Caveat: item 9.
- *Merge by a person: index MERGED row or head?* The head, **read fresh at the merge step**. The index's MERGED row and the default-branch file both lag up to 60 s, and per CLAUDE.md the index "never says no", so it cannot prove that no merge happened.

- New: What bound and notification apply to a head that never settles (item 9)?

## (e) Tests

- Rule slice (domain vitest): one test per row. Hold when `headSha ≠ settled.sha`. Hold when the head is `pending` or `unknown`. Hold on a `null` reading. Hold on a **stale** reading whether red or green, which is the opposite of `defaultBranchRed`. Hold on red. Merge only when the review record's head equals the PR head and has no HIGH.
- Controller (domain vitest on `merge`): refuse `merge-in-flight` when the fresh tip differs from `settled.sha`. Refuse when `prReview` on the pinned head is not `success` while the rollup is green (absent review). Refuse a `null` reading for the fleet caller. My probe file reproduces the three current passes, and those cases should become the failing-then-passing tests.
- Tick (fleet vitest with seams and a manual clock): scan N merges PR A while the default-branch file is not refreshed, and scan N+1 must not merge PR B. This is the regression test for item 1. `--once` merges nothing. A `host-refused` at head H is not retried on every beat.
- Contract (`test/reconcile`): `plot-ask.mjs merge` under `PLOT_UNATTENDED=1` refuses before any host call (item 4).

## Amendments

1. Correct the fact: `default-branch-red` is a dispatch hold (`queue.ts:583`). The merge refusals are `merge.ts:123,127`. The rule must hold on a stale reading and must not reuse `defaultBranchRed`.
2. Derive the in-flight mark from the default branch's tip read **fresh at the merge step** (`git ls-remote`), confirmed in the controller as a new `merge-in-flight` refusal. The 60 s-old file and the index must not be the only source.
3. A `null` default-branch reading holds a fleet merge.
4. The controller re-asks `plot/review` on the pinned head and refuses anything but `success`. Either require `Merger app` before fleetd merges on GitHub, or state the admin-bypass gap the ruleset currently leaves open (bypass actor RepositoryRole 5, `always`).
5. Replace "depends on #2900 for that identity" with: it depends on #2900 for the review record and the rule file. Add (here or to #2908) an unattended refusal on `plot-ask.mjs merge`, which has none today.
6. Name where the merge runs: the daemon's scan-clock automatic writes, never `--once`. Name where `mergeAt` moves so that fleet can call it without depending on the board package.
7. Add a no-retry rule for `host-refused` at the same head, a stall bound for a head that never settles, and a decision with #2904 on the main-repair PR's exception to the red hold.

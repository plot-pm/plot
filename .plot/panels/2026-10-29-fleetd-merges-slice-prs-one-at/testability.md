## (a) Problem statement

- **Correct:** fleetd merges nothing. `mergeAt` has one caller, `plot-ask.mjs merge` (`packages/board/src/server/entry/main.ts:151-175`). No file under `packages/fleet/src` imports it.
- **Wrong dependency:** the plan says it "depends on #2900 for that identity" (Approach, last bullet). The caller identity belongs to #2898 / PR #2908 (`fleet-roles-are-declared-agents.md:66`, slice `feature/fleetd-caller-identity`). #2900 / PR #2917 is the reviewer plan, and it creates `rules/slice-pr-next.ts` (`fleetd-reviews-every-slice-pr-in.md:34,49`). The Notes line "No plan for #2900 exists on main" is true, but PR #2917 exists, and the plan should name it.
- **Wrong premise about the merge controller:** the plan and #2908 both assume that `merge` refuses an unattended caller. It does not. `mergeAt` (`board/src/server/entry/merge.ts:48-75`) and the `merge` arm in `main.ts:151-175` read no `PLOT_UNATTENDED`, and `grep -n -i unattended` over `merge.ts`, `ask.ts` and `main.ts` returns nothing. `controllerGateOf` (`gate.ts:651-660`) refuses an unpinned merge and CI suites at a desk. It does not refuse a pinned `plot-ask.mjs merge`. A fleetd tick that calls the merge in-process also passes through no hook. So for the merge arm the caller identity is not a blocker. Either drop the dependency or state what the identity must gate.

## (b) Approach

1. **The "review record" has no index source, and the index's `checks` already folds it in.** `PrIndexRowSchema` (`entities/pr-index.ts:30-98`) has no `plot/review` field. The only reader is the live `Host.prReview` (`ports/host.ts:396-407`). The rollup includes the status: `gh pr view 2895` returns `plot/review=SUCCESS` inside `statusCheckRollup`, and `plot-host.sh:706` folds every rollup entry into `checks`. So an index row with `checks: green` means "CI green AND (`plot/review` success OR absent)", and `checks: failing` means "CI red OR a HIGH". The rule cannot tell "no review on this head" from "review with no HIGH", or "CI red" from "HIGH", out of the index alone. The plan must name the review record's source (an index field that #2917 adds, or a fleetd-written file keyed by head SHA) and its shape. Without that, slice 1 has no fixture type to test against.
2. **"Red or stale → hold (today's `default-branch-red`)" is two different answers today.** Probe P3: on a red reading with `askedAt` older than `Checks wait`, `defaultBranchRed()` returns `false`, so the queue hold lifts, while `merge()` refuses `default-branch-stale`. The rule therefore needs its own stale arm. It must not reuse `defaultBranchRed`, which by design (`default-branch.ts:249-255`) lifts on stale.
3. **The merge controller does not enforce one merge in flight, and the reading lags the merge.** Probe P1: `merge()` permits when `headSha=NEW, head=pending, settled={OLD, green}`, which is exactly the in-flight state. Probe P2: `merge()` permits on `headSha=OLD, settled={OLD, green}` written before a merge moved the tip. Nothing in `MergeReadings` names the live tip. The reading is written on the PR reader's beat (`registryd-main.ts:2493-2538`, "It rides the PR reader's beat"). The automatic writes run on the scan clock (`registryd-main.ts:~2596`). `pr-reader` and `scan` report separate intervals (`:2742-2743`). So after fleetd merges PR 1, a scan pass that runs before the next PR beat sees the old head settled green and answers `merge` for PR 2. The index-only derivation the plan proposes ("from the default branch's head and its settled reading") cannot see the merge it just made. Proposed fix, in the plan's own idiom ("the index selects, the controller re-asks"): add `defaultBranchTip` (from `Refs.remoteSha`, `git ls-remote`, `ports/refs.ts:774-786`) to `MergeReadings`, and refuse a new `default-branch-unsettled` unless `tip === reading.headSha && reading.settled?.sha === tip`. Then the guard is live at the controller, and it also covers a merge by a person between beats.
4. **A missing reading.** Probe P4: `merge()` permits with `defaultBranch: null` (`merge.ts:121`, "absent holds nothing"). That rule suits a person's `plot-ask.mjs merge`. For an unattended fleetd merge with no reading, the in-flight mark cannot be derived at all. The plan should decide whether the rule holds on `null`. The anti-goal suggests it should.
5. **Fleet cannot reach the merge executor.** `mergeAt` (the host re-ask, `canPinMerge` and `pr-merge --match-head`) lives in `packages/board`. `packages/fleet/package.json` depends only on `@plot-pm/domain` and `zod`. Slice 2 has two options. It can move `mergeAt` to a place both packages import, or it can shell out to `plot-ask.mjs merge`, which adds a `spawn` site outside `adapters/` and breaks the plan's claim "No new spawn site appears" (ratchet at `ci.yml`, *One place reaches a process*). The plan must name which option it takes.
6. **Layering:** a synchronous rule over readings is right. It matches `merge()` and `defaultBranchRed()` and is testable without mocks.

## (d) Open questions

- **Q1, which reading of #2900:** the review record, not the caller identity. The identity is #2898's, and the merge controller has no unattended refusal to lift ((a)). The record's shape is the blocking dependency ((b)1).
- **Q2, same `Default branch checks` list:** yes, and automatically. `refreshDefaultBranch` folds only `declaredRuns(asked.value, world.checks)` (`default-branch-refresh.ts`, the `else` branch). `registryd-main.ts:2522` passes `checkNamesOf(... 'Default branch checks' ...)`. An in-flight mark derived from the same reading inherits that list. This repository's config declares `CI`, so a publish workflow on main never counts as "unsettled".
- **Q3, the PR index's MERGED row or the head:** neither alone. Both are written on the same PR beat and lag a fleet merge made on the scan clock ((b)3). Use the head, re-asked live at the controller (`Refs.remoteSha`), compared with the reading's `headSha` and `settled.sha`.
- **New Q4:** when two open slice PRs both answer `merge` in one tick, which one merges? The order (PR number, plan slice order, or oldest green) must be a rule property so that a test can assert it.
- **New Q5:** what does the tick do on `host-refused` (for example the ruleset blocks) or `head-moved`: retry next tick, or log a step for *Stalls*? A silent retry every tick is the "loops silently" failure the design names.
- **New Q6:** does the rule hold on a `null` reading ((b)4)?
- **New Q7:** where does the tick read "open slice PRs of the scope"? The frozen scope reader is an open question in #2917 (`:42`). Slice 2 cannot be tested without a scope fixture.

## (e) Tests

All the acceptance criteria below can be checked without a live fleet, a live host or a browser, provided the review record has a declared shape.

- **Controller guard (new slice), domain unit, `packages/domain/test/workflows-merge.test.ts`.** Extend the existing `reading()` / `readings()` fixtures (`:33-49`) with a `defaultBranchTip`. Assert `default-branch-unsettled` for (i) `tip=NEW, headSha=OLD`, which is probe P2, and (ii) `headSha=NEW, head=pending, settled.sha=OLD`, which is probe P1. Assert a permit for `tip=headSha=settled.sha, green`. Board unit `merge-entry.test.ts` / `merge-reads-the-estates-default-branch.test.ts`: assert that `mergeAt` passes the `refs.remoteSha` answer, and that `unknown` refuses `unaskable`.
- **Rule arms (slice 1), domain unit, new `packages/domain/test/slice-pr-next.test.ts`.** This is a table test over the rows. Use one fixture per row, built from a `PrIndexRow`, a review record keyed by head SHA, and a `DefaultBranchReading`. Assertions: (1) review success on `row.headSha` → `{kind:'merge', pr, sha: row.headSha}`. (2) Review success on an older SHA → not `merge`. This is the "new push makes the old review irrelevant" criterion. (3) A settled red within `Checks wait` → `hold('default-branch-red')`. (4) A red reading older than `Checks wait` → `hold('default-branch-stale')`, plus an assertion that `defaultBranchRed()` reads `false` on the same fixture, so that a reuse of it fails the test (probe P3). (5) A green reading older than `Checks wait` → stale hold. (6) `settled.sha !== headSha` → `hold('merge-in-flight')`. (7) A `null` reading → whatever Q6 decides. A mutation check: delete the in-flight arm, and only test (6) should fail. Run with `pnpm --filter @plot-pm/domain exec vitest run test/slice-pr-next.test.ts`.
- **Tick (slice 2), fleet unit, `packages/fleet/test/unit/`.** Follow the `auto-deliver.test.ts` pattern: a stub script records argv to a marker file, or use the domain's `host-fixture.ts`. Fixtures: two open scope PRs, both review-success on their heads, and a green settled reading at the tip. Assert that exactly one `pr-merge <n> --match-head <sha>` is recorded per pass (one merge in flight inside a tick) and that it is the PR that Q4's order names. Second pass: the PR store and the reading are unchanged and the stub tip moved. Assert zero merges. This is the scan-before-beat race. A `host-refused` stub: assert one action-log line and no exception. No live host, no `test:e2e`.
- **Layering gate:** after slice 2, the CI spawn ratchet count must not grow. That check proves that `mergeAt` was reused rather than spawned.

Position: amend

Evidence: Read the plan, issue #2902 (`gh issue view`), DESIGN-delivery-loop.md, CLAUDE.md (*The Layering Rule*, *A Decision Reads The Index*, *A Shell Script Asks The Domain*), `packages/domain/src/workflows/merge.ts`, `rules/default-branch.ts`, `entities/default-branch.ts`, `entities/pr-index.ts`, `ports/host.ts`, `adapters/refs/refs-remote-git.ts`, `packages/board/src/server/entry/merge.ts` and `main.ts:151-176`, `packages/board/src/server/entry/review.ts:494-526`, `packages/fleet/src/shared/default-branch-refresh.ts`, `registryd-main.ts:922-925,2500-2540`, `packages/fleet/package.json`, `rules/controller-gate.ts`, `.github/workflows/ci.yml` and `build-bundles.yml`, and the sibling plans #2917 (#2900), #2908 (#2898), #2912 (#2903), #2910 (#2904). Ran: an esbuild-bundled node probe that calls `merge()` and `defaultBranchRed()` with five default-branch readings (results below); `cat` of this machine's live `.plot/state/default-branch.json`; read-only `gh run list --commit` for the current main head; `git log --first-parent origin/main`.

## (a) Problem statement

- Correct: fleetd merges nothing, and the only merge caller is `plot-ask.mjs merge` → `mergeAt` (`packages/board/src/server/entry/main.ts:151-176`, `merge.ts:48`). `merge.ts` re-asks the host through `prState(pr, { withChecks: true })` (`board/.../entry/merge.ts:49`) and pins the write to the head (`workflows/merge.ts:131`).
- **Wrong: "A red or stale default branch holds the merge. `default-branch-red` already does this."** The queue hold `defaultBranchRed` returns **false** for a stale red reading (`rules/default-branch.ts:262-270`). Only the merge controller refuses stale, as `default-branch-stale` (`workflows/merge.ts:121-126`). Ran: probe case 4 prints `defaultBranchRed (queue hold) = false` and `merge() REFUSED default-branch-stale` for the same reading. The two readers answer opposite ways on purpose (CLAUDE.md, *One hold reads a non-terminal answer*). The plan must say which one the merge arm uses: for an irreversible step it must be the controller's stricter form.
- **Wrong: "The merge controller has no unattended caller today. The design lifts the unattended refusal…"** No merge path holds an unattended refusal. `main.ts:151-176`, `entry/merge.ts` and `workflows/merge.ts` contain no `PLOT_UNATTENDED` check (grep: zero hits). The only merge gate is the head-pin gate (`rules/controller-gate.ts:240-253`). Sibling #2908's claim that `merge` "refuses every unattended caller" is false for the same reason. So the dependency on #2900/#2898's caller identity is not what unblocks this plan; and if the design wants the merge restricted to fleetd's identity, that refusal must first be *added*, which nobody's plan builds.
- Missing cause: a **missing** default-branch reading lets `merge()` pass (`workflows/merge.ts:121`, `defaultBranchRead: false`). Ran: probe case 1 prints `MERGES (defaultBranchRead=false)`. For a person that is a reported fact; for an unattended fleetd it is a merge with no evidence about main, which is the anti-goal.

## (b) Approach — layering and the index

- **The in-flight hold lives only in the rule, and the destructive step does not re-ask it.** `merge()` has no notion of an unsettled head. Ran: probe case 2 (head pending, `settled.sha ≠ headSha`) and case 3 (this machine's live reading at 20:06Z: head `5163dbee` pending, settled `88ab8e4b`) both print `MERGES`. The design's one guard against the anti-goal therefore rests on a non-terminal file read in the rule, and nothing at the controller confirms it. CLAUDE.md permits the index to *select*; the controller must *confirm*. Amend: `workflows/merge.ts` gains a refusal (for example `default-branch-unsettled`) when `settled?.sha !== headSha`, and its caller re-reads the remote tip fresh through the existing `Refs.remoteSha` (`git ls-remote`, `adapters/refs/refs-remote-git.ts:54-66`) and refuses when the tip differs from the reading's `headSha`. This adds a reading to an existing port and no spawn site.
- **A same-tick race the plan does not close.** The rule answers "one next step per open slice PR". fleetd writes the reading once per tick (`registryd-main.ts:2538`), so after fleetd merges PR A the file still shows the old head with `settled == headSha` until the next refresh. A second PR evaluated in the same pass, or in the next pass before the refresh, also answers `merge`. "Derived, not stored" holds only if the derivation includes fleetd's own merge. Amend: the arbitration is a scope-level rule (`nextMerge(rows, reading, …)` returns at most one PR per pass), and the in-flight derivation also reads the PR index's newest terminal `MERGED` row: a `mergedAt` later than the reading's `askedAt` counts as in flight. A MERGED row is terminal, so reading it is within *A Decision Reads The Index*. This answers open question 3: both, not either.
- **The review record has no index.** The rule must read "`plot/review` on this head", but the PR index row's `review` field is the host's review verdict (`host-shell.ts:110`), not the `plot/review` status, and the row holds no findings (`entities/pr-index.ts:30-100`). Reading `Host.prReview` (`ports/host.ts:141-157`) per open PR per tick puts a host call inside the decision, against part 2 of *A Decision Reads The Index*. The plan must name the record the rule reads (for example the reviewer's verdict files under `<common dir>/plot/state/reviews/`, `board/.../entry/review.ts:414`, keyed by PR and head SHA), and #2900's plan must write it. "No HIGH" must be defined as `plot/review = success` on this head, which `review.ts:494` writes for zero HIGH and which the design also writes for a ticketed HIGH.
- **The controller does not check the review.** `merge()` reads checks rollup only (`workflows/merge.ts:111-116`); the `plot/review` ruleset is a GitHub setting on this estate, not a domain guarantee, and an adopting repository may lack it. Amend: `mergeAt` re-asks `host.prReview(pr)` and `merge()` refuses `review-not-passed` unless the state is `success` on the pinned head. A failed read is `unaskable`, never a pass (`rules/review-bypass.ts` already draws that line).
- **Where the controller lives.** `mergeAt` is in `packages/board/src/server/entry/merge.ts`, and `@plot-pm/fleet` depends only on `@plot-pm/domain` (`packages/fleet/package.json:29`). The tick cannot call it without a new cross-package dependency or a second copy of the glue. Amend: slice 1 or a new first slice moves `mergeAt` into the domain (a workflow over `Host`, `Scripts`, `DefaultBranchStore`, `Refs` ports) so both `plot-ask.mjs` and the tick call one function.
- Shell ratchet: the plan adds no shell. Spawn ratchet: the merge write goes through `scripts.hostSaid` (an adapter), so no new spawn site — correct as stated, provided the move above happens instead of fleet re-implementing a shell call.

## (d) Open questions

1. *Which reading of #2900?* Both: the review record (the rule cannot decide "no HIGH" without it). The caller identity does not unblock the merge, because no unattended merge refusal exists (see (a)).
2. *Same `Default branch checks` list?* Yes; the file is folded only over `declaredRuns` (`default-branch-refresh.ts`, `declaredRuns(asked.value, world.checks)`), so "settled" already uses that list. New question it raises: a head with no declared run stays `unknown` and never settles (`foldRuns`, `rules/default-branch.ts:78-84`), so the in-flight hold never lifts until another push. The plan needs a bound and a stall notification for that.
3. *Merge by a person: index or head?* Both (see (b)). The head catches direct pushes; the MERGED row closes the window between fleetd's own merge and the next refresh.
- New: does `default-branch-stale` (reading older than `Checks wait`, default 3600 s) make fleetd's merge wait when fleetd's own refresh fell behind? It should hold, not refuse into a stall; say so.
- New: every merge on this estate is followed by a second main commit from `build-bundles.yml` (pushed by the App, which starts CI). Does "settled since the merge" wait for that commit too? The design's "about 100 minutes for ten slices" doubles if it does.

## (e) Tests

- Controller slice (domain unit, vitest): `merge()` refuses `default-branch-unsettled` for probe cases 2 and 3; refuses a missing reading for the fleetd caller (or the plan states why it may pass); refuses `review-not-passed` for `absent`, `failure`, `pending` and `unread`; `mergeAt` refuses when `Refs.remoteSha` differs from `headSha`, with fake ports.
- Rule slice (domain unit): `nextMerge` over two green, reviewed rows answers one PR; with a MERGED row newer than `askedAt` answers hold; stale red answers hold through the controller's form, not `defaultBranchRed`.
- Tick slice (fleet unit over fake ports): one pass with two candidates calls the merge port once; a refused merge ends the action and records the reason; the spawn ratchet count does not move.

## Amendments

1. Correct the two false statements: stale is refused by `merge()`, not held by `defaultBranchRed`; no unattended merge refusal exists today.
2. Add an unsettled-head refusal and a fresh `Refs.remoteSha` re-read to the merge controller, so the in-flight guard is confirmed at the destructive step.
3. Derive "in flight" from the head **and** the newest MERGED index row; make the merge choice a scope-level rule that answers at most one PR per pass.
4. Name the review record the rule reads (not the host per tick), and add a `review-not-passed` refusal that re-asks `Host.prReview` at merge time.
5. Move `mergeAt` into the domain before the tick slice; the fleet package cannot reach the board's entry.
6. Mark slice 1 as extending #2900's `slicePrNext` with a `waits:` on it; state who owns the repair/revert exemption from `default-branch-red`.
7. Decide whether a missing reading permits a fleet merge, and bound the `unknown`-head hold with a stall notice.

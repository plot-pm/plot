## (a) Problem statement

- Correct: `planStateComment` writes one line, `Plan <phase>: <link>`, under `<!-- plot:plan-link -->` (`tracker-plan-state.ts:35,44-47`). The probe printed `"<!-- plot:plan-link -->\nPlan approved: docs/plans/x.md"`.
- Correct as a rule, wrong as a description of behaviour: "`issueStatusWrites` owes a write at `approved`, `delivered` and `released` today". The probe confirms that the rule owes `approved` (`[{"issue":"KUS-1","status":"In Progress"}]`). But nothing calls `plot-issue-status.sh` at Approved. Its only callers are `deliver.ts:531` (deliver) and `deliver.ts:944` (release). `approve.ts:1174` runs `plot-plan-state.sh` only. So `Tracker approved status` (`plot-config.sh:183-190`) is configured and never written. On Jira, the "same three points" are two today. The plan must name this gap, because slice 3 builds on it.
- Missing fact: `planStateComment` is in `adapters/`, not in `rules/`. Every line this plan adds (the count, the ticket list, the answers, the cut at N) is rendered state. Under "Every rendered state is a domain property" and "No domain-specific code or behaviour lives outside the domain", none of that may grow inside the adapter.
- Missing fact: Jira's `planStateWrite` answers `no-target` unconditionally (`tracker-jira.ts:294-300`: "A Jira issue takes no `plan:*` label, no plan comment"). On a Jira tracker, slices 1 and 2 write nothing at all. Only slice 3 reaches Jira.

## (b) Approach, read against the layering rule and the index rule

1. **The count source contradicts itself and picks the wrong layer.** Approach item 1 says the count comes from "`plot-pr-merged.sh` reads `mergedAt`". The last paragraph says "each write reads the PR index and the plan". Calling `plot-pr-merged.sh` once per slice is N host calls and a shell script reached for a rule input. The domain already holds the reading: the pulse carries per-branch `state` (`landedBranches`, `auto-deliver.ts:216-220`, probe returned 1 for merged/open/deferred), and `allSlicesMerged` and `allSlicesConfirmed` (`deliverable.ts:62,103`) define deferred exemption and subject evidence. A progress line is a reversible reflection, not a destructive step. So the "One Answer To Did This Land" section does not require a host re-ask, and the wave gate's licence (pulse plus merge subject) is enough. Amend: a pure rule `sliceProgress(pulsePlan) -> { merged, total }` in `packages/domain/src/rules/`, with deferred slices excluded the way `allSlicesMerged` excludes them. Delete the `plot-pr-merged.sh` sentence.
2. **The write point is named as an actor, not as a trigger.** "After each slice merge" plus "Needs #2902 (the fleet merges)" ties the write to fleetd's merge action. The design counts every merge, "the fleet's or a person's" (*One merge in flight*). A person who merges in the GitHub UI gets no progress line. Part 3 of *A Decision Reads The Index* already provides the trigger: `rules/index-findings.ts:105` emits `pr merged` from the PR index for every merge. Amend: the write is triggered by the index's `pr merged` finding, and the slice then does not depend on #2902 at all.
3. **The rendering must move into the domain before it grows.** Amend slice 1 to move `planStateComment` (and `PLAN_STATE_MARKER`) from `adapters/tracker/tracker-plan-state.ts` to a rule such as `rules/plan-issue-comment.ts`, taking readings as values: phase, link, version, progress, tickets and answers. The adapter keeps the three `plot-host.sh` steps and renders nothing.
4. **The port contract changes, and the plan does not say so.** `ports/tracker.ts:219-227` states "THE WRITES ARE FOUR FACTS … one comment" and `:52-54` says each write "carries only a fact Plot itself produced". Adding a count, ticket numbers and unblocker answers to `PlanStateWrite` widens the port. The widening is defensible, because each item is a fact Plot produced. But the port's doc and type change, and the plan must name that change as a deliverable, or the next reader treats the widening as the mirror the port refuses.
5. **"Rebuilt from recorded state on every write" breaks every existing caller unless the entry point reads the records itself.** `deliver.ts:546`, `deliver.ts:955`, `approve.ts:1174` and `/plot-idea` call `plot-plan-state.sh` with `--phase` and `--plan-link` only (`plan-state.ts:88-104`). If the body is rebuilt from arguments, the Delivered write erases the ticket and answer lines that the merge writes added. Amend: `plan-state.ts`'s `run` reads the progress, ticket and answer records through ports, so that every caller produces the whole body with no new flags. A test proves it: a delivered write after a ticket write still names the ticket.
6. **The records are machine-local, and the port forbids reading the comment back.** The HIGH-ticket record (#2903, "beside the PR index under `.plot/state/`") and the answers (#2913, `escalations.tsv` or the run log of #2909) live under the common git dir of one machine. A release from another checkout rebuilds the comment without them, and `ports/tracker.ts:225` ("NO RULE READS … THE PLAN COMMENT BACK") forbids a merge with what the issue already shows. This is an open question the plan must carry (see (d)).
7. **Slice 3 cannot add a transition point without shell lines.** `plot-issue-status.sh:44-46` reads the three status words in shell and passes them as flags. A fourth word (for example a "started" status at the first merge) is a new shell line under `scripts/check-shell-lines.sh`. The plan claims "the script stays a launcher", but it is not one today: it reads the plan meta and three config keys. Amend: slice 3 first moves the config reads into the bundle (as `plan-state.ts:117` already does through `scriptsShell(context).config`), so that the ratchet goes down and a new word costs no shell line.
8. **Decisions stay in the domain where the plan names them.** `issueStatusWrites` (`issue-status.ts:46-57`) and `planStateWrites` (`:87-93`) are pure. Nothing in the plan puts a decision in a controller, provided that items 1, 3 and 5 are amended. No write is destructive, so no write needs the host re-ask that `workflows/merge.ts` makes.

## (c) Slices

- **Slice 2 duplicates two sibling plans.** #2903's slice `feature/a-high-finding-is-fixed-before-ticket` already builds "a line in the plan issue's marked comment" for the HIGH ticket (its Approach, line 40, and slice line 65). #2913's slice `feature/an-answer-is-recorded-on-the-plan-issue` already builds "the answers list in the plan issue's Plot comment" (line 59). Three plans that edit one comment, which `issue-comment` replaces wholesale (`plot-host.sh:5745`, "edits the comment holding <marker>"), will erase one another's lines unless one renderer owns the body. Amend: this plan owns the one renderer (`rules/plan-issue-comment.ts`, item 3) and the full-body read (item 5). #2903 and #2913 each write their record and call the renderer, and they render nothing themselves. Slice 2 then shrinks to "the renderer reads the ticket and answer records", or leaves this plan.
- Order: the renderer move plus the progress line (slice 1, independent of #2902 once triggered by the index), then the records join (slice 2, waits on #2903 and #2913 records existing), then Jira (slice 3, independent of 1 and 2; it can go first).
- Missing: wiring `plot-issue-status.sh` at Approved (`approve.ts` beside `:1174`). Without it, "the same three points" stays false on Jira.

## (d) Open questions

- *Which points does Jira transition at?* Evidence: today Jira gets Delivered and Released only. The Approved write has no caller (see (a)). Answer: fix Approved first. A per-merge transition is not a status change (a status does not move from "1 of 3" to "2 of 3"), so the only candidate is one optional word on the first merge, read in the bundle (item 7), and empty by default, as the other three are.
- *Where does the unblocker answer record live?* It lives in #2913's record. This plan reads it through a port, as a value. It must not parse `escalations.tsv` in shell.
- *The sprint item.* Nothing in the code under `rules/sprint-tick.ts` needs this plan. The design table says the sprint item is ticked at delivery and closed after the release, which is #2911's work. Answer: add nothing here.
- *Comment size.* The cut at N is a rendered decision, so it goes in the domain renderer with a unit test on N+1 answers. Neither the adapter nor `plot-host.sh` may truncate.
- New: *Which machine's records does a rebuild read, and what happens to lines written on another machine?* (item 6).
- New: *Does the progress write also re-set the `plan:approved` label on every merge?* `githubPlanStateWrite` runs `issue-label` before `issue-comment` (`tracker-plan-state.ts:74-77`). That is one extra host call per merge from the git host's budget. A comment-only step for a progress write avoids it.
- New: *What does the count say for a merge proven only by subject evidence?* For a reflection the wave-gate licence holds, but the rule should state it.

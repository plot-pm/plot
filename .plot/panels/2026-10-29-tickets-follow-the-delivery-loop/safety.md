# Juror verdict: safety

Position: amend

Evidence: Read the plan, issue #2905 (`gh issue view`), DESIGN-delivery-loop.md, `tracker-plan-state.ts`, `rules/issue-status.ts`, `tracker-jira.ts:285-305`, `plan-state.ts` (board entry), `approve.ts:1160-1185`, `deliver.ts:520-560`, `plot-issue-status.sh`, `plot-host.sh:669-690` and `:5741-5760`, `packages/fleet/src/shared/auto-deliver.ts` (header), and the sibling plans #2902, #2903, #2913 and #2899. Ran: (1) the real `plot-host.sh issue-comment` twice concurrently against a fake `gh` (0.3 s listing latency) on an issue with no marked comment; (2) the real `plot-host.sh issue-label 7 plan:approved plan:draft,plan:delivered,plan:released` against a fake `gh` whose issue carries `plan:delivered`; (3) `vitest run test/tracker-plan-state.test.ts` in `@plot-pm/domain` (14 of 14 pass). Nothing was written to any host.

## (a) Problem statement

- Correct: `planStateComment` writes the marker and one line, `Plan <phase>[ in <v>]: <link>` (`tracker-plan-state.ts:44-47`). The comment is edited in place by marker (`plot-host.sh:5754-5757`).
- Correct only for the rule: `issueStatusWrites` owes a write at `approved`, `delivered` and `released` (`issue-status.ts:46-57`). No caller asks at `approved`. `plot-issue-status.sh` is called only from `deliver.ts:531` and `deliver.ts:944` (release). `approve.ts:1174` calls `plot-plan-state.sh` and nothing else; `approve.ts:31` imports only `trackerReportOf`. So the `Tracker approved status` key (`plot-config.sh:183`) is read and never written today. The plan states the opposite.
- Missing: a Jira-tracked repository gets nothing from slices 1 and 2. `tracker-jira.ts:297-300` answers every `planStateWrite` with `no-target`, and `issueComment` is `unaskable` (`:295`). The progress line, the HIGH ticket list and the unblocker answers never reach a Jira issue. The design's *A blocked agent* rule ("every answer is recorded on the plan issue") then holds on GitHub only.

## (b) Approach, read against the safety rules

1. **A progress write as an Approved-phase write moves a delivered issue backwards.** Approach item 1 makes the progress line "a field of the Approved-phase write". `githubPlanStateWrite` runs `issue-label` with `planStateLabelsToRemove(phase)` before the comment (`tracker-plan-state.ts:74-78`). Probe (2) shows the result on an issue that carries `plan:delivered`: `gh issue edit 7 --add-label plan:approved --remove-label plan:delivered`. The comment then reads `Plan approved`. Auto-deliver runs the delivery as a detached child (`auto-deliver.ts:150-186`), so the delivered write and a progress write for the last slice have no order. A progress write that is retried after a host failure, or a second tick's write, can land after `delivered`, or after `released` too. The design says "no lifecycle step runs backwards" (*A red main*, item 4). Fix: the progress write is comment-only (no label step), and it reads the plan's phase from the default branch at write time and writes nothing unless the phase is `approved`.
2. **Two concurrent writers post two marked comments.** `issue-comment` lists the comments, then PATCHes or POSTs (`plot-host.sh:5755-5757`). Nothing serialises that. Probe (1): two writers on an issue with no marked comment both listed, found none, and both posted. That left two comments, `writer 1` and `writer 2`. Later writes edit only `[0]` (`plot-host.sh:690`), so the second comment stays stale. This plan adds write points: after each merge, and on each ticket and answer. It also adds writers: fleetd, plus the board's approve, deliver and release controllers that a person runs. That makes the race more likely. An issue whose plan never wrote a draft comment hits it on the first fleet write. Fix: one writer for the loop's lines (fleetd), plus a per-issue lock around lookup and post on the machine. Also a post-then-relist check that folds a duplicate into the first comment.
3. **"Rebuilt from recorded state" loses lines when a second writer lacks the record.** The plan rebuilds the whole body on every write, so the last writer wins. The records are fleetd's state under `.plot/state/`: the attempts and ticket file (#2903 plan, *Approach*) and the answers (#2913). These files sit under the common git dir of one machine. A person's `/plot-deliver` or `/plot-release` on another machine rebuilds the body without those records. It erases the ticket list and the answers, which are the only place a person reads the answers. The existing callers also pass only phase, link and version (`approve.ts:1174`, `deliver.ts:546`, `deliver.ts:955`). Unless each caller changes, the delivered write wipes the lists on the fleet's own machine too. The plan names no change to these callers. Fix: `plot-plan-state.mjs` reads the records itself, as it already reads `planMeta` (`plan-state.ts` header, lines 27-30), so every caller renders the same body. Every record the comment renders must be readable from any machine (git, or a host read). Where it is not, a writer that lacks the record must keep the existing section, never drop it.
4. **Edge-triggered writes are lost when fleetd crashes.** "A new write point, after each slice merge" puts the write after #2902's merge as a separate step. A crash between the merge and the write loses the line until the next merge. A person's merge also triggers nothing, but the design says "after any merge" (*One merge in flight*, and *After a merge*). Fix: make the write level-triggered. Each tick computes the owed body from the readings and compares a hash of it with a last-written record under `.plot/state/`. It writes only on a difference. Two ticks then converge, and a crash only delays the line.
5. **The count's source contradicts *A Decision Reads The Index*.** Approach item 1 counts through `plot-pr-merged.sh`, which is one host call per slice branch. The last paragraph then says "each write reads the PR index". Pick one. Counting MERGED rows from the index can undercount, never overcount ("the index never says no"), and an undercount is reversible on the next write. Count with the same reading auto-deliver uses for "all slices merged". Otherwise "3 of 3" and the delivered decision disagree. Example: a merge-subject slice settles a wave but reads `unknown` for delivery (CLAUDE.md, *One Answer To "Did This Land"*). On a failed or partial host answer, write no progress line, rather than a count from a partial read.
6. **A host comment limit turns into a permanent failure.** The plan leaves "Comment size" open. The label step runs first and succeeds, so once the body passes the host's limit every later comment write fails. That freezes the comment, including the `Plan delivered` and `Plan released` lines. GitHub documents a 65,536-character body limit; this juror did not execute against it. The cut must be part of the composer, not an open question.
7. **Unattended callers.** `plot-plan-state.sh`, `plot-plan-state.mjs` and `plot-issue-status.sh` carry no `PLOT_UNATTENDED` refusal (`grep` found none), and they are not controller-owned actions. So fleetd needs no unattended lift for these writes, and the "fleetd's declared caller only, never release" rule is untouched. The plan should say so. It must not route the `released` write through fleetd, which stays with the person's approval (design, *Unattended callers*).
8. **Jira transitions on progress can move a ticket backwards.** A Jira workflow usually offers a transition back to `In Progress` from `In Review`. `noTransitionOutcome` covers only an absent transition (`issue-status.ts:227-228`). A late first-merge transition after delivery moves the Jira issue back, and Jira post-functions do not undo cleanly. Item 1 applies here as well.
9. **Shell ratchet.** A new status word read in `plot-issue-status.sh` (lines 44-46 read one key per line) adds shell lines. Read any new key in the bundle through the `Scripts` port's `config`, as `plan-state.ts:117` does.

## (c) Slices

- Three plans write into one comment. #2903's ticket slice writes "a line in the plan issue's marked comment", and #2913's `feature/an-answer-is-recorded-on-the-plan-issue` writes the answers list. This plan's slice 2 builds both lists again. Three independent writers of one body break "one writer" and race as in (b)2 and (b)3. Make this plan own the composer and the comment write. The siblings write their records only, and their comment slices leave them or wait on this plan.
- No slice carries a `<!-- waits: -->` on a sibling branch. Slice 1 needs #2902's merge step. Slice 2 needs the record shapes of #2903 and #2913.
- Slice 1 must also change how `approve`, `deliver` and `release` render the comment, or move the rendering into `plot-plan-state.mjs` (see (b)3). Otherwise the next phase write drops the progress line.
- Slice 3 reduces to the missing caller. `approve.ts` calls `plot-issue-status.sh` after its plan-state write. This matches the design's "the same three points" (Tickets table) without a new Jira transition.

## (d) Open questions

- **Which points does Jira transition at?** Answer: the three phase points, as the design's Tickets table says ("transitions at the same three points"). Approved has no caller today (see (a)), and adding it is the new work. Add no per-progress or first-merge transition: it is beyond the design, and (b)8 shows it can move a ticket backwards.
- **Where does the unblocker answer live?** It must be readable from every machine that writes the comment, or the comment loses it ((b)3). `escalations.tsv` is local. Ask #2913 for a record in git or on the host, not only under `.plot/state/`.
- **Comment size.** Cut deterministically in the composer: keep every HIGH ticket, the last N answers, and a count with a pointer for the rest. Test the cut at the limit.
- **New: Jira-tracked repositories.** `planStateWrite` there is `no-target`, so where do the answers and tickets go? Write them as a Jira comment (a new connector capability), or state that the record is GitHub-only.
- **New: which writer wins at the phase boundary?** State that a progress write after `approved` writes nothing, and test it.
- **New: does the double-post race need its own fix in `plot-host.sh`?** That fix means a shell change and its ratchet cost. The alternative is a single writer per issue, with a lock in the TypeScript caller.

## (e) Tests

- Domain unit (`packages/domain/test/tracker-plan-state.test.ts` pattern): the composer gives the same body for the same records whatever the write order. A body over the limit is cut to the limit and keeps every ticket. A progress write emits no `issue-label` step. A progress write against a plan read as `delivered` or `released` emits nothing.
- Domain unit: the progress-count rule over index readings. MERGED rows count, while a missing row and a failed read do not, and a failed read means no line.
- Board unit (`deliver-plan-state.test.ts`): the delivered and released writes keep the progress, ticket and answer sections.
- Fleet unit: a level-triggered write fires once for two ticks over the same readings. It fires again after a simulated crash between the merge and the write. It fires for a merge a person made.
- Contract (`test/reconcile`, fake `gh` as in probe (1)): two concurrent writers on one issue leave one marked comment.
- Board unit: `approve` calls `plot-issue-status.sh` and reports its outcome without failing the approval.

## Amendments

1. Make the progress write comment-only. Read the plan's phase at write time and write nothing unless it is `approved`. Never re-label.
2. Move the comment's rendering into `plot-plan-state.mjs`, fed from records every writer can read, so the approve, deliver and release writes keep every section. A writer that lacks a record keeps that section.
3. Make the write level-triggered with a last-written hash, so a crash, a repeated tick or a person's merge converges.
4. Count merged slices from the index reading auto-deliver already uses, never through a per-branch `plot-pr-merged.sh` call. A partial read means no line.
5. Name one writer of the marked comment, this plan's composer, and take the comment slices out of #2903 and #2913 or make them wait on this plan. Add a per-issue lock or a post-then-relist fold against the double post.
6. Replace slice 3 with "approve calls `plot-issue-status.sh`", and add no new Jira transition.
7. Put the size cut in the composer and close that open question.
8. State the Jira outcome, where `planStateWrite` is `no-target`, and state that no unattended lift is needed.

## (a) Problem statement

1. **The cited cause of problem 1 is the wrong arm.** Executed: `waitingTickets(rows, [], reader, {match:'tracker-account', prefix:'jira:'}, true)` returns `tickets: []`, `hidden: 3`, `notice: null` already today. Only `inbox === undefined` reproduces the banner (`The tracker names your tickets' assignee markus.ruepp@quatico.com; … add jira:markus.ruepp@quatico.com`). Reason: `waiting-tickets.ts:201` takes `inbox` as the candidates when it is defined, `:203` skips the notice for `candidates.length === 0`, and `:223-225` returns the empty union. So on the board the empty inbox reached the domain as `undefined`. Two upstream paths do that: `fleet.ts:2098` (the live read, used with no fleet index) calls `waitingOf` with no inbox argument at all, and `fleet.ts:2262` passes `index.inbox`, which `issue-index.ts:168-171` and `issue-refresh.ts:223` define as absent "where the read did not happen" (`inboxSkipped`, an `unaskable` read). The plan's slice 1 says "the arm where the inbox query did not run (`inbox === undefined`) keeps its current behaviour" — that is exactly the arm that produced the screenshot, so slice 1 as written changes nothing the operator saw.
2. **Problem 3's unassigned tickets are a consequence of problem 1, not of «Mine».** On the matched arm `waitingTickets` already requires `'mine'` (`:188`, `:223`) and hides an unassigned ticket, counts it in `hidden`, and the board renders `N open tickets are not assigned to you` plus the `show every ticket` control (`waiting-view.ts:85-95`, `hiddenSentence` `:235`). The 16 unassigned rows were visible because the fallback arm (`:213` `fallback = [...candidates]`, candidates = all project rows) rendered every row. Fix the inbox and they leave *Waiting on you* without slice 3.
3. **Problem 4's framing is wrong.** Executed: `prOwnership` (`ownership.ts:102-109`) answers `theirs` for every non-empty author that does not resolve to the reader, declared or not — `'Christian Kehl'` → `theirs`, `'{abc-uuid}'` → `theirs`, `''` → `unknown`. So no `People` spelling can make a PR row `unknown`; a declared or undeclared spelling both hide it. A Draft-plan row stays under «Mine» only if (i) its `pr.author` arrived `''`, or (ii) it is a plan card on Discovery/Design, which reads `ownedFromCard` with `author` from `planAuthors` on the default branch only (`board.ts:2416-2417`, `fleet.ts:6852-6856`), so a plan that lives only on its `idea/` branch has no author → `unknown`. The question to answer is "which of these two", not "which spelling".
4. Problem 2 (duplicates): `unionDedup` (`:99`) runs only on the two matched arms (`:189`, `:224`). The four fallback arms (`:178`, `:185`, `:197`, `:213`) render `rows` as given, with no dedup. The observed duplicates appeared on the fallback arm. A paged read that returns overlapping pages would show exactly "twelve rows twice in sequence". This is unmeasured; it narrows where slice 2 should look.

## (b) Approach

- Slice 1 must move to the server: make the live path (`fleet.ts:2098`) run or carry the inbox read, and make an answered-empty inbox reach the domain as `[]`, never `undefined`. Keep the domain change only as a guard (notice `raw` taken from the inbox only). Without that, the fix lands in a function that is already correct.
- Slice 3 changes the contract of the released plan `2026-10-23-only-my-work-waiting-on-you` and of `isMine`, which has four board consumers (`rowsForReader`, `agentsForReader`, `ticketsForReader`, `boardForReader`, `mine-filter.ts:155-224`) and one Discovery consumer (`lanes-for-reader.ts:67`). The plan says "the ownership rule stays the single source", but it does not say whether `isMine` changes (Discovery changes too) or whether the board filters switch to `ownership(...) === 'mine'` (Discovery keeps the looser rule, and the two tabs answer «Mine» differently for one ticket — `lanes-for-reader.ts` comment says "so both tabs answer alike").
- **Agents become invisible.** `agentOwnership` (`ownership.ts:247-250`) never answers `theirs`; it answers `mine` only for a manifest-declared agent with a desk here. Every inferred-desk agent and every `elsewhere` agent is `unknown`. «Mine» hiding `unknown` hides the reader's own dispatched desks that carry no manifest. The plan must exempt agents or state this.
- **Silent emptying is still possible.** A mis-resolved identity today already makes the reader's own PRs `theirs` (any non-matching author is `theirs`), and those are counted under "others", not "unknown". The proposed `N others · M unknown` therefore cannot reveal the failure mode the original design guarded against. A guard that does: when «Mine» on leaves 0 `mine` rows while the unfiltered set is non-empty, say so — the Discovery tab already has this signal (`hiddenByOwner`, `lanes-for-reader.ts:68`, rendered at `StoriesTab.tsx:335-336` as "Only my work hides every ticket in this lane").
- **Persisted preference changes meaning.** `mine-only` lives in `localStorage` (`mine-filter.ts:17`, default off `:36`). A reader who left «Mine» on before the upgrade reloads into a board that hides more, with no action of their own — the case `mine-filter.ts:22-30` calls "a board that lies by omission". Either a new key or a one-time notice.
- **The count already exists, and it counts less than the plan implies.** The chip renders `N hidden` inside itself (`DeliveryFilters.tsx:87-91`) from `chipRow` `hiddenCount` (`chip-row.ts:168`), counted over agent rows only (`chip-readings.ts:47`) — not tickets, agents or cards. Slice 3 must replace this count, not add a second one beside it, and must name which lists `N` and `M` count.
- Layering: the `N others · M unknown` text and the toggle's third state belong in `chipRow` (domain), which already owns the chip's label, on/off and count. That fits *Every rendered state is a domain property*. The plan says so; good.

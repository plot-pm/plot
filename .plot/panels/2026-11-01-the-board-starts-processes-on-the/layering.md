# Layering juror — the-board-starts-processes-on-the

Position: amend

The goal is right and the measurements are real (one request took 12.07 s at load 11.5 when this juror measured it, 2026-11-01 20:38). Through the layering lens, though, the plan puts its held values in the wrong place and misses the biggest starts. The domain already has the oid-keyed cache this plan wants to build a second time: `cachedRefs`, `cachedPlans` and `WalkCache` in `packages/domain/src/workflows/plan-walk-cache.ts`, built by `the-plan-walk-moves-into-the` (#2995, merged). Slice 2 builds a board-side Delivered cache next to that cache. Slice 1 builds a board-side config copy, but config reaches the request path through four different routes, and fleetd's walk also reads config per beat with no cache. Slice 3 has nothing to build, because `readSupervisor` is already off the request path; the sample counted every child of the board pid, refresh-loop children included. The three slices also leave the largest starts in place: the full-estate `plot-plan-meta.sh` parse that `buildBoard` runs on every request, a second estate parse through `planMetasAtDefault`, and `ticketLaneData` running twice. Amend: deliver behaviour 2 by extending `cachedRefs`, have the board read through `cachedRefs`/`cachedPlans` over the ref snapshot it already reads, put the held config at one adapter seam, and reword or drop slice 3.

## Findings

1. **high — The plan duplicates the domain's oid cache.** `plan-walk-cache.ts:230` `cachedRefs(inner, snapshot, cache)` already decorates `Refs` with oid-keyed answers for `resolve`, `branchTips`, `listBlobs`, `readBlobs`, `mergeSubjects`, `planAdditions`, `commitSubjects`, `changedFiles`, `conflictPaths` and `containsMany`, with mark-and-sweep pruning (`:41-61`). `plan-walk-cache.ts:375` `cachedPlans` holds parses keyed by (blob oid, path, prefixes, parser hash, config digest). Today only fleetd uses them (`fleet-scan.ts:707-722`). `buildBoard` already takes `Refs` as a port (`board.ts:2170` `refsFor(opts)`), and `boardState` already reads the ref snapshot on every request (`controllers/fleet-state.ts:139` `refsToken` → `refState('both')`). Behaviour 2 is one more `keyed` entry in `cachedRefs`. A board-local "Delivered record per origin oid" map is a second cache of the same kind, with its own key rule and no sweep. Checked by reading both files on `origin/main` at `0974e8956`.
2. **high — The plan misses the largest per-request starts, so "near zero" cannot be reached with its slices.** `buildBoard` parses the whole estate on every request: `collectPlanSources` (ls-tree, cat-file, rev-parse, rev-list `measureBehind`), staged writes, then `readPlanMeta` → `plot-plan-meta.sh` over about 625 plans (`board.ts:2316`, `:1454`). It has no cache, only in-flight sharing (`fleet-state.ts:212-241`). The same request parses the same `origin/main` estate a second time through `ticketLaneData` → `planMetasAtDefault` (`fleet.ts:1838`, `:1589`), which has its own oid-keyed `planMetaCaches` (`fleet.ts:1656`). `ticketLaneData` runs twice per request: `index.ts:486` calls it, and `discovery-lanes.ts:48` calls it again. Each call recomputes its key with a config read, `defaultBranchOf`, `resolve` and `branchTips`, and reads `Tracker` (`fleet.ts:1838`). So one request holds three estate readers with two cache rules. The walk plan measured one parse of 620 plans at 0.52 s CPU.
3. **medium — Config reaches the request path through four routes, and a held copy in "the board" would be a fifth.** The routes are: `board.ts:651` `readConfigAsync` → `packages/fleet/src/shared/config-reader.ts`, which builds `scriptsShell` directly and so bypasses the injected `opts.planStore` port; `scriptsFor(opts).config` (`fleet.ts:1838`, `planDirectory`); `planStoreFor(opts).config` (`server-info.ts:120`); and the synchronous `readConfig` in `interrogateAvailability` (`interrogate.ts:57`). That last one is a `runScriptSync` on the request's own stack. `a-read-route-spawns-nothing.test.ts:80-84` does not see it, because its `ENTRIES` list only `boardState`, `fleetState` and `serverInfo`, while the handler at `index.ts:478-518` also calls `interrogateAvailability`, `ticketLaneData` and `discoveryLanes` directly. `server-info.ts:139` (`cachedCi`) and `:179` (`cachedPeople`) also memoise config for the life of the process with no invalidation, which is a second staleness rule. `plot-plan-meta.sh:371` reads `Tracker` itself unless the caller passes `--tracker`. fleetd's `walkOnce` reads five keys per beat through `plot-config.sh` (`fleet-scan.ts:684-694`). The layering precedent for a held file reading is the adapter: `gate-contract-file.ts:76-106` keeps a size+mtime cache behind its port.
4. **medium — Behaviour 3 is already true. The issue's evidence does not separate request children from refresh children.** `readSupervisor` has one caller, `refresh` (`fleet.ts:2847`). `ensureCache` starts `refresh` with `void` (`fleet.ts:3185`), and the pulse runs it every 5 s beat (`fleet.ts:3199-3210`, `REFRESH_MS` `:176`). `/api/board` awaits none of it: `planRefAgeSeconds`, `prsByNumber` and `ticketLaneData` read the entry synchronously. `refresh` is single-flighted (`entry.running`, `:2780`), so a 4-13 s `plot-fleetctl.sh --status` runs again right after the last one ends. That is contention, not request-path work. Slice 3 as written builds nothing. The real question is the cadence and owner of that reading (for example, read fleetd's state instead of walking 22 desks every beat), and it belongs in a separately worded behaviour.
5. **medium — The Delivered read costs four processes per Delivered plan, not one process per plan file.** `board.ts:2323` asks `recordCommit` for `phase === 'delivered'` plans only: 17 on `origin/main` (`git grep -l '^- \*\*State:\*\* Delivered' origin/main -- docs/plans` → 17 of 625). Each call runs `defaultBranch()` (`refs-git.ts:641` → `:438-444`, `bash -c 'git symbolic-ref … | sed …'`, three processes) and then `git log -G` (`:647-656`). This repo's Plot Config declares no `Main branch`, so `defaultBranchOf` (`board.ts:1016`) also falls through to the same three-process pipeline on each call. The plan and the issue both say "per plan file". The cost is about 68 starts, sequential, for 17 plans.
6. **medium — An oid key over a read by ref name is unsound.** `recordCommit` reads `origin/${main}` by name (`refs-git.ts:651`). If the board computes the key from the snapshot oid and then reads by name, a fetch between the two stores the new answer under the old key. The walk plan states the rule: "A cached answer is a function of the objects in its key, read through those oids and never through a ref name" (Approach 4). `cachedRefs` honours it by passing the oid to `inner` (`plan-walk-cache.ts:284`, `:309`). So `Refs.recordCommit` needs a ref or oid parameter (`ports/refs.ts:406`). The plan does not name this port change. `refs-fixture.ts:365` and the two fleet callers (`auto-verify.ts:304`, `auto-design.ts:473`) change with it.
7. **low — There is a synchronous spawn in `buildBoard` on every request.** `spawnContractReadingFor` (`board.ts:353`) calls `refsFor(opts).hashFilesSync`, which is `runProcessSync('git', …)` (`refs-git.ts:783`). It runs after the first await, so the read-route gate does not count it, but it blocks the event loop on every build. A stat-keyed hold on the bundle file removes it.
8. **low — The walk's parse key omits `Tracker`.** The `fleet-scan.ts:720` digest is `mainBranch, planDir, activeDir, deliveredDir, prefixes`, but the parser's `issues` output depends on `Tracker` (`plot-plan-meta.sh:366-385`). If the board reuses `cachedPlans`, a `Tracker` change does not invalidate held parses. Either add `Tracker` to the digest or pass `--tracker` from the held config.
9. **low — A process-count test has a precedent, and that precedent counts the wrong population for this plan.** `packages/board/test/plan-read-shape.test.mjs` shims `git` and `bash` on `PATH` and starts the server with `PORT=0` (`helpers.mjs:216-223`), so it never touches port 7777. Its log also holds every refresh-loop child, so it cannot attribute starts to one request (the same flaw as finding 4). A counting-port test at the controller avoids that, but only after the config route stops bypassing `opts` (finding 3) and `draftPlanFiles`' direct `run('git', ['show', …])` (`fleet.ts:1812`) moves behind `Refs.showFile`.

## Amendments I require

- A1. Replace behaviour 2's board-side cache with an extension of `cachedRefs`: `Refs.recordCommit(file, field, ref)` reads by the ref it is given, and `cachedRefs` keys it by (snapshot oid of `origin/<default>`, file, field). Key `planAuthors` and the `measureBehind` count (HEAD oid, origin oid) the same way. Update the fixture and the fleet callers in the same slice.
- A2. Add a behaviour: the board reads the estate through `cachedRefs` and `cachedPlans` over one board-held `WalkCache` per `cacheKey(opts)`, built over the snapshot `refsToken` already reads. Then `planMetasAtDefault` reads through the same cache and its private `planMetaCaches` is removed, and `ticketLaneData` runs once per request (its result passed to `discoveryLanes`). Name the sweep: the board calls `begin`/`sweep` once per build, so the cache stays bounded by the live estate.
- A3. Reword behaviour 1 so that one held config reading lives at one adapter seam that both the board and fleetd's `walkOnce` use. Key it on the stat (mtime, size) of BOTH repo-root `CLAUDE.md` and `AGENTS.md` (`plot-config.sh:10-13`; the presence of `CLAUDE.md` decides which file is read). Route `board.ts:readConfigAsync`, `config-reader.ts`, `scriptsFor().config`, `planStoreFor().config` and `interrogate.ts:57` through it. Replace the process-life memos `cachedCi` and `cachedPeople` with it. Pass `--tracker` to `plot-plan-meta.sh` from it, or include `Tracker` in the parse digest.
- A4. Drop slice 3, or reword it as a separate behaviour about the supervisor reading's cadence and owner in the refresh loop, and state that the request path already does not await it (`fleet.ts:2847`, `:3185`). Answer the Open Question in the Design text.
- A5. Correct the Motivation facts: the Delivered read is per Delivered plan (17 today), at four processes each; the sample counted every child of the board pid, so it included refresh-loop children; and `buildBoard`'s full parse and the double `ticketLaneData` are request-path starts.
- A6. Specify the proof as a controller-level count. Move the `/api/board` handler body (`index.ts:478-518`) into a controller (for example `boardAnswer(opts, host, port, archived)`), as "Every rendered state is a domain property" and the layering rule ask. Call it twice with counting ports and fixtures, with no ref, config or plan change between the two calls. Assert that the second call starts exactly the named list. Do not assert a duration. Extend `a-read-route-spawns-nothing.test.ts` `ENTRIES` to that controller so the `interrogate.ts:57` sync spawn fails the gate.
- A7. Name the remaining starts that need their own held value or stay: `git status --porcelain` (`treesFor(opts).isClean`, a worktree reading with no oid), `hashFilesSync` (keyed by bundle stat), and `draftPlanFiles`' `git show` per draft branch (keyed by branch oid through `cachedRefs`).

## Open questions

- **Which remaining starts belong to the object-id key?** `git for-each-ref` is the snapshot itself: keep exactly one per request (it is `refsToken`'s read) and reuse it as the `cachedRefs` snapshot. `git rev-parse` is answered from the snapshot by `cachedRefs.resolve` (zero starts). `rev-list --count HEAD..origin/main` is keyed by (HEAD oid, origin oid). The `--diff-filter=AR` log (`planAuthors`) is keyed by (origin oid, plan directory), like `planAdditions`. The Delivered `git log -G` is keyed by (origin oid, file, field) after the port change in A1. `git status --porcelain` and the bundle hash have no oid and need their own held value or stay on the named list.
- **Why did `plot-fleetctl.sh --status` run inside the request window?** It is the refresh loop. It is not a cold first request or a second caller. `refresh` runs every 5 s beat in the same process (`fleet.ts:3199-3210`), and the request does not await it. The sampler watched the board pid's children, so it saw both populations. The fix is to the reading's cadence or owner, not to the request path.
- **What counts as warm, and what is the allowed count?** Warm means a second build after one build completes, with no ref, config-file or plan-file change between the two. The count is not zero: one `for-each-ref` (the snapshot that keys everything else) plus the named A7 list. Assert it with counting ports at the controller, not with a `PATH` shim on a live server, because the shim also counts refresh-loop children.

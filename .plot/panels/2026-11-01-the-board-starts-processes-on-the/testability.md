# Testability juror — the-board-starts-processes-on-the

Position: amend

The plan names the right defect, but it cannot be proven as written. It has no `Done when` rows, no test table and no `waits:` lines. Behaviour 3 is already true on `origin/main` (`0974e8956`), so its slice has no failing test to write. The evidence cannot tell the request's children from the refresh loop's children, so a count test built the same way fails at random. Config is read through four paths, and `BuildBoardOptions` has no port for three of them, so no unit test can count or fake a config read today. The plan also misses one synchronous spawn on every `/api/board` request. Each held value can be proven fresh and stale with no board server, and the count can be deterministic. The amendments below name the seams and the test shape that make this true.

## Findings

1. **high — Behaviour 3 already holds, and the evidence cannot attribute a child to the request.** `readSupervisor` has exactly one caller, `fleet.ts:2847` inside `refresh` (`fleet.ts:2779`). `ensureCache` starts `refresh` without an await (`fleet.ts:3145`, `void refresh(opts, entry)`), and the pulse runs it every `REFRESH_MS = 5_000` (`fleet.ts:176`). A 7.8 s request window therefore always contains at least one refresh tick in the same pid. The 0.2 s sample of the board's children counts the refresh loop's `plot-fleetctl.sh --status`, `for-each-ref`, `rev-list --count` and config reads together with the request's own. Checked: `git grep "readSupervisor("` over `packages/board/src` and `packages/fleet/src` on `origin/main`. Consequence for testing: slice `the-supervisor-reading-leaves-the-request` has no red test to start from, and a count test that counts the process's children (the PATH-shim precedent) also counts the refresh loop.
2. **high — A synchronous spawn runs on every `/api/board` request, and the existing gate cannot see it.** The handler builds `interrogate: interrogateAvailability(HOST, opts)` (`index.ts:506`). That calls `readConfig(opts, 'Interrogate command', '')` (`interrogate.ts:57`) → `config-reader.ts:20` `configSync` (`scripts-shell.ts:71`) → `runScriptSync` → `execFileSync` (`run-script.ts:182-188`). `board.ts:622-627` states that the sync reader's mtime cache is gone. `a-read-route-spawns-nothing.test.ts` walks only `boardState`, `fleetState` and `serverInfo` (its `ENTRIES`). It does not walk `interrogateAvailability`, `ticketLaneData`, `discoveryLanes` or `planRefAgeSeconds`, which the handler also calls (`index.ts:492-523`). The plan does not name this start.
3. **high — No seam exists to count or fake a config read.** Four paths read config on the request: `readConfigAsync` (`board.ts:651` → `config-reader.ts:36`, built from `repoRoot`/`scriptsDir` only), sync `readConfig` (finding 2), `scriptsFor(opts).config` (`fleet.ts:1832`, key `Tracker`; `scriptsFor` at `board.ts:419` always builds a real `scriptsShell`), and `planStoreFor(opts).config` (`server-info.ts:115`). Of these, only `planStore` is a field of `BuildBoardOptions` (`board.ts:98`; the optional ports are `refs`, `trees`, `planStore`, `hostAdapter`, `buildAdapter`, `spendRecord`, `defaultBranchStore`, `gateContract`, `readerLock`, `detached`, `processProbe`). A unit test for behaviour 1 cannot count `plot-config.sh` calls until one config reader is injectable and every path goes through it.
4. **medium — Two clock caches make "warm" depend on time.** `serverInfo` holds `currentBranch` on a 5 s TTL (the comment in `server-info.ts` beside `branch`) and `identity` on `IDENTITY_TTL_MS = 60_000` (`server-info.ts`, `identity`). A warm request that crosses a TTL boundary starts `git` and `plot-host.sh`. A count test with a real clock therefore fails when the machine is slow. Also, `cachedCi` and `cachedPeople` (`server-info.ts`) are module-level process-life memos with no invalidation and no reset. They contradict behaviour 1 ("once per config file change") and leak between test cases in one file.
5. **medium — The oid-keyed caches that exist still start processes to read their keys.** `planEstate` (`board.ts:2998-3021`) runs `defaultBranchOf`, `refs.resolve`, two config reads and `prefixedBranches` before it can return a hit. `planMetasAtDefault` (`fleet.ts:1589-1603`) runs `planDirectory`, `defaultBranchOf`, `refs.resolve` and `branchTips` before its hit, and the request calls it twice, through `ticketLaneData` at `index.ts:492` and again through `discoveryLanes` (`discovery-lanes.ts:49`). `refs.defaultBranch` is itself `bash -c 'git symbolic-ref … | sed …'` (`refs-git.ts:438-444`). If behaviour 2 reads its key the same way, "near zero" cannot be met and cannot be asserted. `boardState` already reads `refsFor(opts).refState('both')` once per request (`fleet-state.ts`, `refsToken`). The domain's `snapshotOf`/`RefSnapshot.oidOf('origin/<main>')` (`plan-walk-cache.ts:153-182`) turns that one read into every oid the held values need, with no further start.
6. **medium — The Delivered read is sequential and costs about four starts per plan, but it is the easiest value to prove.** `board.ts:2322-2332` awaits `refs.recordCommit(rel, 'Delivered')` once per Delivered plan in a loop. On `origin/main`, 17 plans read `State: Delivered`. Each call runs `defaultBranch()` (bash, git, sed) and then `git log -G` (`refs-git.ts:641-656`). `Refs` is injectable (`opts.refs`), and `refsFixture` already answers `recordCommit` from `recordCommits` (`refs-fixture.ts:88`, `:365`). A counting wrapper over the fixture proves stale and fresh with no board server: two builds at one `origin/main` oid call `recordCommit` N times and then 0 times; a moved oid calls it N times again. The key is sound, because `recordCommit` reads only `origin/<main>` (`refs-git.ts:652`), so the record cannot change while that oid stays. The holder must be keyed per estate (`keyFor` in `fleet-state.ts`), not by `repoRoot` alone as `planEstateCache` is (`board.ts:2952`), or two test cases with different fixtures share an answer.
7. **medium — The count-test precedent counts by PATH shim, and that counts the refresh loop too.** `packages/board/test/plan-read-shape.test.mjs` starts a server on `PORT=0` (`helpers.mjs:216-223`, so never on 7777), shims `git` and `bash`, and asserts only on named patterns (`cat-file --batch`). A total count from that shape includes every refresh tick in the window, and the board has no switch to stop the refresh loop. `stopFleetRefresh` (`fleet.ts:3323`) also clears `caches`, so it destroys the warm state the test needs. An in-process count is possible: `@plot-pm/domain` exports TypeScript source (`packages/domain/package.json` `exports`), so vitest transforms it and a `vi.mock('node:child_process', …)` pass-through wrapper reaches every adapter. `test/unit/setup/no-real-detached.ts` is the precedent for mocking a module under the board's unit project. Thirteen modules import `node:child_process` directly (including `fleet.ts:3` and `idea.ts`), so the module mock, not a port fake, is the only single seam that sees every start.
8. **medium — The plan has no `Done when` rows, no test table and no `waits:` lines.** Behaviour 4 says "near zero" and "fails when the count grows" but names no number and no list. Slice `a-board-request-counts-its-processes` names no dependency. If it lands last, slices 1-3 merge with no proof. If it lands first as a ratchet at today's count, each later slice lowers the number in its own diff, and each slice carries its own proof.
9. **low — "The config file's mtime" names one file, and `plot-config.sh` reads two.** The script reads `## Plot Config` from `CLAUDE.md` first and `AGENTS.md` as the fallback (`plot-config.sh` header). A stamp on one file misses a change in the other and misses a `CLAUDE.md` that appears. An mtime alone also misses two writes inside one timestamp tick. A stamp of (path, exists, mtimeMs, size, ino) for both files is testable with `fs.utimesSync` and a same-size rewrite.
10. **low — The plan walk already ships the cache rules this plan needs.** `WalkCache` (`plan-walk-cache.ts:87-116`) holds no `unknown` and no failed read, keys by oid and never by ref name, and keeps `additions` keyed by (default-branch oid, directory) and parses keyed with a config digest. PR #2995 merged these. The plan does not reference them, so it risks a second cache with different rules. A failed `recordCommit` must be re-asked on the next request, and a test must say so.

## Amendments I require

A1. Add a `## Done when` table with one row per behaviour. Each row names the test file, the injected fake and the asserted count or call list. No row may assert a duration.

A2. Remove slice `the-supervisor-reading-leaves-the-request`, or turn it into a test-only slice: a unit test that asserts `readSupervisor` runs zero times during one request on a warm entry, with the refresh clock stopped. Correct the Motivation: the sample cannot attribute a child to the request (finding 1), so name only the starts that the code path proves to be on the request.

A3. Add the sync `interrogateAvailability` read (finding 2) to the plan, move it behind the held config, and extend `ENTRIES` in `a-read-route-spawns-nothing.test.ts` to every function the `/api/board` handler calls (`interrogateAvailability`, `ticketLaneData`, `discoveryLanes`, `planRefAgeSeconds`, and the ten `*Availability` calls).

A4. Behaviour 1 adds one injectable config reader to `BuildBoardOptions` (or a `scripts` port) and routes all four config paths through it (finding 3). Its unit test uses a counting fake and a temp directory: read twice → one call; `fs.utimesSync` on `CLAUDE.md` → one more call; create `CLAUDE.md` when only `AGENTS.md` exists → one more call; a same-size rewrite in the same mtime tick → one more call (finding 9). `cachedCi` and `cachedPeople` join the held copy or the plan states why they stay process-life memos, and every module-level holder gets a reset that a test can call.

A5. Behaviour 2 takes `origin/<default>`'s oid from the one `refState('both')` read that `boardState` already makes, through `snapshotOf` (finding 5). The holder is keyed by `keyFor(opts)` plus the plan path, holds no failed read, and is proven with a counting wrapper over `refsFixture`: same oid → 0 calls on the second build; moved oid → N calls; a failed answer → re-asked (finding 6, 10).

A6. The process-count test runs in the board's `parallel` vitest project, starts no server and no port, and counts with a `vi.mock('node:child_process')` pass-through that records `spawn`, `execFile`, `execFileSync` and `spawnSync` (finding 7). It warms the estate with the refresh clock stopped and the cache kept, which needs a new test seam beside `stopFleetRefresh` that stops clocks without clearing `caches`. It pins time with `vi.setSystemTime` so no TTL expires between the warm-up and the counted request (finding 4). It awaits the request's own promise and asserts an exact list of command lines, not a count with a tolerance.

A7. Slice the plan with `waits:` and land the count test first as a ratchet at today's measured list. Each later slice removes its own lines from that list in its own diff (finding 8). State the end value: one `git for-each-ref` (the snapshot read) plus the named starts that remain, or zero if the request reads only held values.

## Optional

- O1. The smaller design: the request reads one payload that the refresh loop builds, and every start moves into the loop. Then the count test asserts zero with a spawner that throws, and staleness is a property of the refresh loop that `refresh` tests already cover. The cost is that a page can be up to one refresh (5 s) older than the refs, and the plan must name that.
- O2. Run the `Delivered` reads in parallel or as one `git log` over all Delivered plans on a cold key. This shortens a cold request, and a counting fake proves it the same way.
- O3. Collapse the two `ticketLaneData` calls per request into one (`index.ts:492` and `discovery-lanes.ts:49`).

## Open questions

- **Which remaining starts belong to behaviour 2's key?** `git for-each-ref` is the snapshot read in `boardState` and stays as the one start that supplies every oid. `git rev-parse` (`refs.resolve` in `planEstate` and `planMetasAtDefault`) and the `bash -c git symbolic-ref` of `refs.defaultBranch` go away when both take their oid and the default branch name from the snapshot and the held config. `git rev-list --count HEAD..origin/main` (`refs-git.ts:724`) and the `--diff-filter=AR` log (`refs-git.ts:859`, `:867`) are functions of `HEAD` and `origin/<main>` oids, so they join the same key: (HEAD oid, origin/main oid) and (origin/main oid, directory). The plan walk's `additions` cache already holds the second one.
- **Why did `plot-fleetctl.sh --status` run inside the request window?** Neither a cold request nor a second caller. `readSupervisor` has one caller, inside `refresh`, which the 5 s pulse runs concurrently with every request in the same process. The sample counted the refresh loop's child. The window contained it because the pulse does, not because the request awaits it.
- **What counts as warm, and what is the allowed count?** Warm means: one completed request on the same estate, the refresh clock stopped with the cache kept, the system time pinned, and no ref or config file changed since. The allowed count is an exact list, not "near zero": today's measured list when the ratchet lands, and at the end one `git for-each-ref` per request (or zero under O1). Any new line fails the test with the list printed.

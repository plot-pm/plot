# Safety juror: the-board-starts-processes-on-the

Position: amend

Through the safety lens the plan's direction is sound: a request that answers from held values stops the false "No contact" banner. But the plan names no invalidation rule precise enough to stop a held value from showing "fine" after its input changed. One of its three required behaviours already holds on `origin/main` at `0974e8956`. The real staleness risk sits elsewhere: the stored supervisor reading carries no age. Behaviour 1 also repeats a cache that main removed on 2026-08-31 without the lessons that cache recorded. Behaviour 2 does not say that the `git log` must run against the oid it is keyed by. Five amendments fix this. None of them changes the plan's goal.

## Findings

1. **high — Behaviour 3 already holds on main, and the issue's evidence misattributes the supervisor read.** `readSupervisor` has exactly one caller, `refresh` (`packages/board/src/server/fleet.ts:2847`). `ensureCache` starts `refresh` with `void` (`fleet.ts:3172`) and on the 5 s pulse (`fleet.ts:176`, `fleet.ts:3199-3211`). On a warm entry `ensureCache` returns at `fleet.ts:3148` before it starts anything. The `/api/board` handler (`packages/board/src/server/index.ts:462-540`) reads no supervisor field. So the request already reads only the stored `entry.supervisor`. The 0.2 s child sample groups processes by parent pid, and the background refresh is a child of the same board process. That puts `plot-fleetctl.sh --status` inside the request window by concurrency, not by an await. Checked: `git grep readSupervisor origin/main -- packages/board/src` (one call site) and the handler body. The risk: an implementer who "moves the supervisor read off the request" with nothing to move may slow its cadence instead. `fleet.ts:2843-2846` records why it runs on every tick: it is the liveness probe, and a skipped read keeps `supervisor: up` and the scan ownership for up to `OWNED_BRIDGE_MAX_AGE_MS` (180 s, `packages/domain/src/rules/scan-owner.ts:10`).
2. **high — The stored supervisor reading has no age, and under the measured load it can show `up` while fleetd is down.** `SupervisorRun` (`packages/domain/src/rules/supervisor-reading.ts:69-122`) has no asked-at time. `tickAgeSeconds` stays at the value it had when the script ran. `tickStale` (`supervisor-reading.ts:277-290`, 600 s) compares that frozen number. `refresh` is single-flight (`fleet.ts:2780`, `if (entry.running) return`). One pass is the registry read (no bound), up to 5 s for the supervisor (`supervisor-reading.ts:48`), up to 30 s for the scan (`runStreaming`, `fleet.ts:1029`), then `branchAges`, `releaseVersions`, `unmergedBranches` and `workerQuestions` with no bound of their own. With requests at 48–61 s, a reading served as `up` can be tens of seconds to minutes old, and nothing on the wire says so. The same value also feeds `fleetOwnsScan` (`fleet.ts:2459`, `scan-owner.ts:53-62`), which decides whether the board trusts the bridge. The plan says "no wire field", but the honest fix needs one: an asked-at time, so that render ages `tick_age` by `now − askedAt` and a reading older than a bound reads `unknown`, never `up`.
3. **high — Behaviour 1's invalidation key is under-specified and repeats a removed design without its lessons.** `plot-config.sh` reads the first of `$root/CLAUDE.md` and `$root/AGENTS.md` that contains `## Plot Config`, with `$root` taken from `PLOT_REPO_ROOT` or `git rev-parse --show-toplevel` (`skills/plot/scripts/plot-config.sh:290-301`). A key on "the config file's mtime" misses three cases. It misses a repository whose config lives in `AGENTS.md`. It misses a `CLAUDE.md` that is created, or that gains or loses the section. It misses two repositories that share mtimes. Main had exactly this cache, and `ceaf53689` removed it on 2026-08-31 (`the-read-path-stops-spawning`). The removed `configStamp` stat'ed both files and recorded absence as a fact. It put `repoRoot` in the stamp after a CI failure on 2026-08-31, when two temp repos with equal mtimes read each other's answers. It treated an empty stamp as a miss. Its comment rejects a TTL: *"An expiry would answer was it recent? when the question is did it change?"* The plan cites the Released plan but not this removal, and does not say when the mtime is checked. It must be checked on every read, never on a timer.
4. **medium — Two held config values already never learn of a change, and they also hold a failed read.** `server-info.ts:137-180` memoises `CI` (`cachedCi`) and `People` (`cachedPeople`) for the process's life, including the fallback (`''`, `{}`) that a failed `plot-config.sh` spawn returns. On a machine where a process start costs 180 ms and can time out, one bad read at startup shows "no CI system" and no person spellings until the board restarts. Behaviour 1 should replace both with the stamp-checked copy and must never store an answer from a failed read. "Not through `plot-config.sh`" means a second parser in TypeScript. No TypeScript `## Plot Config` parser exists today (`git grep -il "plot config" origin/main -- packages/domain/src` finds only fixtures and corpus helpers). Under CLAUDE.md "A Shell Script Asks The Domain", a second parser is a declared duplicate that needs a corpus test. A smaller and safer option keeps `plot-config.sh` as the one parser and stores its answer per (stamp, `get`|`get-raw`, key).
5. **medium — Behaviour 2 keys on an oid but does not say that the read runs against that oid.** `recordCommit` (`packages/domain/src/adapters/refs/refs-git.ts:640-657`) resolves the branch name again on every call. It runs `defaultBranch()`, a `bash -c` pipeline of `git symbolic-ref` and `sed` (`refs-git.ts:438-444`): three processes per Delivered plan that the plan does not name. It then runs `git log … origin/<name>`, using the name and not an oid. The board calls it serially, once per Delivered plan (`packages/board/src/server/board.ts:2321-2332`). Suppose the key oid is read first and the log runs later by name. A fetch between the two stores a newer answer under an older key, and the cache serves it until the next move. `planMetasAtDefault` avoids exactly this by passing the resolved oid to `listBlobs` (`fleet.ts:1563-1568`, `fleet.ts:1596-1604`). Three further gaps exist. First, `recordCommit` reads `origin/HEAD` and ignores the `Main branch` key, while `defaultBranchOf` honours it (`board.ts:1016-1025`), so "origin/<default>" names two different refs. Second, a failed read must not be stored (`board.ts:2330` skips it today). Third, `verificationOf(plan, deliveryCommit)` (`board.ts:2520-2530`) compares plan text with the delivery commit. If the two come from different oids, the card shows a wrong verification badge for one cycle.
6. **medium — The plan's list of request-path processes is incomplete.** Every `/api/board` request also starts these processes. `interrogateAvailability(HOST, opts)` (`index.ts:506`) calls the synchronous `readConfig` (`packages/board/src/server/interrogate.ts:57`), which blocks the event loop for the length of one `plot-config.sh` spawn on every request. That is the defect class `the-read-path-stops-spawning` removed. `ticketLaneData` runs twice per request (`index.ts:493`, and `discovery-lanes.ts:49`). Each call reaches `planMetasAtDefault`'s key computation: `planDirectory` (config), `defaultBranchOf` (config, then the bash pipeline), `resolve` (`git rev-parse`) and `branchTips` (`git for-each-ref`) (`fleet.ts:1593-1601`). Each call also reads `config('Tracker')` (`fleet.ts:1832`). `serverInfo` reads `Board command` (`server-info.ts:237-238`) and the current branch. `countBehind` runs `git symbolic-ref` and `git rev-list --count HEAD..<ref>` (`refs-git.ts:717-728`). `planAuthors` and `planAdditions` run `git log --diff-filter=AR` (`refs-git.ts:856-870`). On a warm cache the planMeta parse itself is a hit, but its key costs about five starts per call, ten per request.
7. **medium — An instant answer can hide a stuck refresh.** Today "No contact" fires partly for the wrong reason, but it fires. When the request answers from held values, the page needs another way to see that the values stopped moving. `planRefAgeSeconds` (`fleet.ts:3219-3222`, from `fetchedAt`) covers the plan source only. Config needs no age if it is stat-checked on every read. A Delivered record needs none if it is keyed by the oid that the request itself reads. The supervisor reading needs one (finding 2). If the plan takes the smaller design (serve the last refreshed payload), that payload must carry its build time, and the page must mark it stale past a bound.
8. **low — The board's controls do not act on the held readings.** Write routes read config live (`approve.ts:108`, `approve.ts:123-124`, `deliver.ts:167-169`, `interrogate.ts:110-111`), and controllers refuse by the domain's answer. A stale card can therefore offer a button whose controller then refuses, which is safe. The plan should keep it that way: write routes read config through the stamp-checked copy or live, never through a snapshot held for a request.
9. **low — A shim count without a paused pulse counts the refresh too.** `packages/board/test/plan-read-shape.test.mjs` puts `git` and `bash` shims on `PATH` and logs every child the board starts. The 5 s pulse runs in the same process, so a per-request count picks up whatever refresh beat overlaps the request. That is the misattribution behind the issue's own `fleetctl` claim, and it would make the test fail by timing. The shims see `node` bundles only through `bash`.

## Amendments I require

- A1. Rewrite slice `the-supervisor-reading-leaves-the-request`. State that on main the request already reads the stored reading (`fleet.ts:2847`, one caller), and that the issue's sample saw the concurrent refresh. Replace its behaviour with three requirements. The stored reading carries its asked-at time. Render ages `tick_age` by the reading's age. A reading older than a stated bound reads `unknown` for both the verdict and `fleetOwnsScan`, never `up`. The read stays on every refresh tick. Allow the wire field this needs, and drop "no wire field" from Board impact.
- A2. Specify behaviour 1's key exactly. The stamp is `repoRoot` plus mtime and size of both `CLAUDE.md` and `AGENTS.md`, with absence recorded as a fact. The stamp is checked on every read, never on a timer. An unstat-able pair is a miss. An answer from a failed read is never stored. The cache is keyed by (stamp, `get`|`get-raw`, key). Keep `plot-config.sh` as the one parser, or declare a TypeScript parser as a duplicate with a corpus test. Replace `cachedCi` and `cachedPeople` (`server-info.ts:137-180`) with the same copy. Cite `ceaf53689` and say why a cache that was removed is now right (process starts cost 20–180 ms even off the event loop).
- A3. Specify behaviour 2's key and read. The key is (resolved oid, branch name, path, field). `git log` runs against the oid and not the ref name. The default branch is resolved once per request, never once per plan. A failed read is never stored. The oid is the same one the plan text was read from. Settle `Main branch` against `origin/HEAD` in one direction, and name that direction.
- A4. Complete the inventory in Motivation with every start in finding 6, at file:line. Move `interrogateAvailability`'s synchronous `readConfig` onto the held copy. Correct the claim that `fleetctl` ran inside the request: it ran concurrently with it.
- A5. Count per request with the pulse paused, or count at the ports in-process, and never start a board on port 7777. Assert a named list of allowed starts. Add one staleness test per held value: an edit to `CLAUDE.md`, and the creation of `AGENTS.md` in a repository that has none, are seen by the next request; a moved `origin/<default>` re-reads the Delivered record; a supervisor reading older than the bound reads `unknown`.

## Optional

- O1. The smaller design is acceptable through this lens if the payload carries its build time and the page shows it stale past a bound. That design moves every start into `refresh`, so the request answers from the last refreshed payload. It also removes the per-request oid read. The cost is that a config edit and a fetch become visible one refresh later (5 s at best, about 40 s under the measured load), not at the next request.
- O2. Add inode to the config stamp. An editor that saves by rename can then never produce an equal mtime and size.
- O3. Resolve the default-branch name once per refresh, not once per `recordCommit`. This removes three starts per Delivered plan even before any caching.

## Open questions

- Q1, which starts belong to the oid key: `git rev-parse` and `git for-each-ref` are the key computation of `planMetasAtDefault` and the plan source (`fleet.ts:1596-1601`). Read the oid once per request and share it, or take it from the refresh. The `--diff-filter=AR` logs (`refs-git.ts:856-870`) key on the origin oid. `git rev-list --count HEAD..origin/main` (`countBehind`, `refs-git.ts:717-728`) must NOT key on the origin oid alone. It answers whether the checkout is behind, so it also needs the `HEAD` oid and the attached-or-detached state. Otherwise a held "0 behind" survives a local reset or a detach: a cached "fine".
- Q2, why `plot-fleetctl.sh --status` was in the request window: not a cold request and not a second caller. It has one call site (`fleet.ts:2847`). `refresh` runs concurrently on the 5 s pulse, and the sample counted the board's children by parent pid. The run competes with the request for the loaded machine but is not awaited by it.
- Q3, what "warm" means and what count is allowed: warm means the cache entry exists, one complete refresh has finished, the pulse is paused for the counted request, and neither the config stamp nor `origin/<default>` has moved since the previous request. The allowed count is a named list. Zero is the target. If one oid read per request stays, the list names it (`git rev-parse`, 1), and any start not on the list fails the test.

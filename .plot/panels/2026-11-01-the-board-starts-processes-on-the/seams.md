# Seams juror — the-board-starts-processes-on-the

Position: amend

The plan names a real defect, and its first slice relieves the operator most, so the order is mostly right. Through the seams lens it has four problems. First, slice 3 targets a call that is not on the request path: `readSupervisor` has one caller, the refresh tick at `fleet.ts:2847`, and the sample counted every child of the board pid, not the request's await chain. Second, slices 1 and 2 build two new private caches while the domain already holds the shared mechanism for slice 2 and for most of the remaining git starts: `cachedRefs` and `WalkCache` in `packages/domain/src/workflows/plan-walk-cache.ts:230`, keyed by one `refState` snapshot that `boardState` already reads on every request (`fleet-state.ts:139`). Third, the plan misses the largest uncached start on the request path, `plot-plan-meta.sh` over every plan (`board.ts:2318`), so behaviour 4 ("near zero") cannot pass after the four slices. Fourth, the count test already has a precedent (`packages/board/test/plan-read-shape.test.mjs`, PATH shims for `git` and `bash`), and a warm count over the whole server picks up the refresh loop's children unless the test stops the pulse first (`stopFleetRefresh`, `fleet.ts:3323`).

## Findings

1. **high — slice 3 moves a call that the request does not await.** `git grep readSupervisor origin/main -- packages/board/src packages/fleet/src` finds one caller: `fleet.ts:2847`, inside `refresh` (`fleet.ts:2779`). `refresh` is started, never awaited, by `ensureCache` (`fleet.ts:3145-3190`) and then runs on every 5 s beat (`REFRESH_MS = 5_000`, `fleet.ts:176`; divisor 1, `boardDivisors`). The issue measured `plot-fleetctl.sh --status` at 3.9 s, 4.3 s and 12.8 s, so with a 5 s beat it overlaps almost every request window. The comment at `fleet.ts:2835` is true. The issue's sampler read the board pid's children, which include the refresh loop's. Behaviour 3 is already the code; the slice as written proves nothing and relieves nothing. The real cost is load: one desk walk every 5 s whether or not anyone views the board. That is a cadence question, not a request-path one.

2. **high — the plan misses the largest start, and the four slices cannot reach "near zero".** Per warm request on `origin/main` (`0974e8956`), the handler at `index.ts:462-540` awaits these starts in addition to the three the plan names:
   - `readPlanMeta` → `plot-plan-meta.sh` over every plan file, uncached (`board.ts:1454`, called at `board.ts:2318` and `:2916`). `origin/main` holds 626 plan files.
   - `collectPlanSources` → `readPlansFromRef`, `refs.resolve`, `measureBehind` → `git rev-list --count` (`board.ts:901-935`, `:856`).
   - `collectBranchPlans` (`board.ts:1132`) → branch tips and per-branch reads.
   - `refs.planAuthors` → `git log --diff-filter=AR --name-status` (`board.ts` in the `buildBoard` tail; `refs-git.ts:864`). This is the issue's `--diff-filter=AR` start.
   - `treesFor(opts).isClean` → `git status`; `spendRecordFor`, `defaultBranchStoreFor`, `spawnContractReadingFor` reads.
   - `refsToken` → `git for-each-ref` (`fleet-state.ts:139`), on every request.
   - `ticketLaneData` runs twice per request, once at `index.ts:493` and once inside `discoveryLanes` (`discovery-lanes.ts:49`). Each run calls `planMetasAtDefault` (`fleet.ts:1589`), whose cache key itself costs `planDirectory` (config), `defaultBranchOf` (config, then `bash -c git symbolic-ref | sed`), `refs.resolve` and `draftBranchTips` before the cache is consulted, plus a `Tracker` config read.
   - `serverInfo` (`server-info.ts:229`) reads `Board command` on every request; its other four reads are memoised (5 s, 60 s and process TTLs).
   The plan's Open Question 1 asks about four of these. It does not mention `plot-plan-meta.sh`, the double `ticketLaneData`, or `planMetasAtDefault`'s key reads.

3. **high — slice 2 duplicates a mechanism the domain already has.** `cachedRefs(inner, snapshot, cache)` (`plan-walk-cache.ts:230-371`, merged in #2995) decorates `Refs` from one `refState('both')` snapshot and holds `resolve`, `branchTips`, `listBlobs`, `readBlobs`, `planAdditions`, `mergeSubjects`, `commitSubjects`, `changedFiles`, `conflictPaths` and `containsMany` by oid. It does not hold `recordCommit`, `planAuthors`, `countBehind` or `defaultBranch` yet. Each of those has the same shape as `planAdditions` (a ref plus a path). `boardState` already reads the snapshot input on every request (`refsToken`, `fleet-state.ts:139-143`) and throws it away after it compares tokens. One board-held `WalkCache` with `cachedRefs` over `refsFor(opts)` would serve behaviour 2 and most of finding 2 from one key, and `cachedPlans` (`plan-walk-cache.ts:373`) would hold the plan parse by blob sha. A second oid cache in `board.ts` would be the third oid cache in the estate beside `planMetaCaches` (`fleet.ts:1655`) and `WalkCache`.

4. **medium — the Delivered read costs four processes per Delivered plan, not one per plan file.** `board.ts:2321-2331` loops over metas whose phase is `delivered` and awaits `refs.recordCommit` one at a time. `recordCommit` (`refs-git.ts:640-658`) first calls `defaultBranch()` (`refs-git.ts:438`: `bash -c 'git symbolic-ref … | sed …'`, three processes) and then `git log -G`. `git grep -l "**State:** Delivered" origin/main -- docs/plans` finds 17 plans, so about 68 sequential starts per request. The issue says "one per plan file"; the count is per Delivered plan. The slice should key by `snapshot.oidOf('origin/<default>')` plus file and field, and should also stop `recordCommit` from re-reading the default branch on every call. `recordCommit` has three other callers that the change reaches: `entry/design.ts:170`, `entry/verify.ts:400`, `fleet/src/shared/auto-design.ts:473` and `auto-verify.ts:304`. A cache inside `refs-git.ts` would change their behaviour too; a decorator the board applies would not.

5. **medium — slice 1 re-adds a cache an earlier plan removed, and does not say why this one differs.** `board.ts:124-128` and `:621-626` record that the mtime cache around `readConfig` was removed as "dead code pretending to be an optimisation", because it wrapped the synchronous reader. The plan must cite that decision and state the difference: the new cache sits on the async path. It must also name where the cache sits. Config reaches `plot-config.sh` through four routes: `packages/fleet/src/shared/config-reader.ts` (17 importers in `packages/fleet/src/shared` plus `board.ts`), `scriptsShell.config` (`scripts-shell.ts`), `plan-store-shell.ts:222`, and the tracker adapters (`tracker-github.ts:134`, `tracker-jira.ts:128`). A cache in `config-reader.ts` serves the request path and fleetd. The key must cover both `CLAUDE.md` and `AGENTS.md` (`plot-config.sh:296` reads the first that carries the section), `repoRoot`, the key, the fallback and `get` versus `get-raw`. "Not through `plot-config.sh`" in behaviour 1 would mean a TypeScript parser: that is a declared duplicate under "A Shell Script Asks The Domain" and needs a corpus pair, which the plan does not name. Each `plot-config.sh get` starts about five processes (`bash`, `grep -q`, `awk`, `grep -m1`, `sed`; `plot-config.sh:290-324`), so 24 reads are about 120 starts. That makes slice 1 the slice that relieves the operator first, and the order is right.

6. **medium — the proof needs isolation from the refresh loop, and a precedent already exists.** `plan-read-shape.test.mjs` starts a board on `PORT=0` (`helpers.mjs:216-223`) with `git` and `bash` shims on PATH that log each start, then counts one build. It counts a cold build, has no Delivered plan in its fixture (so the `recordCommit` loop is invisible to it), and tolerates the refresh loop's children because its bound is loose ("< HOW_MANY_PLANS"). A warm count with a near-zero bound would count the beat's scan, `plot-fleetctl.sh` and PR reader as request starts, which is the same conflation as finding 1. `stopFleetRefresh()` (`fleet.ts:3323`) exists; the test can warm the board, stop the pulse, truncate the log, then send one request and count. The read-route gate `a-read-route-spawns-nothing.test.ts` walks only `boardState`, `fleetState` and `serverInfo` (its `ENTRIES`), and its table says `/api/board` calls only `boardState` and `serverInfo`. The handler also calls `ticketLaneData` (`index.ts:493`), `discoveryLanes` (`:520`) and `planRefAgeSeconds` (`:500`) directly, so the gate does not walk them.

7. **medium — collisions with in-flight work.** The plan walk's remaining slices `feature/the-last-scan-modes-run-the-walk` and `feature/the-scan-script-is-a-launcher` change the board's fleetless fallback in `refresh` (`fleet.ts:2855` `--stream`, the `scanOnce` call at about `fleet.ts:2917`), the same function slice 3 edits at `:2835-2847`. #2993's `feature/the-fleet-payload-indexes-its-plans` builds `/api/fleet`'s plan index from `planMetasOf` and its consumers in `fleet.ts`; any slice that changes `planMetasAtDefault` or `ticketLaneData` (finding 2) shares that region. #2997's plan-source slice (#3003) is merged and added `planMetasAtDefault`; this plan should read it rather than add a fourth plan-parse path. Open PR #3015 edits `board.ts` at `rewritePlanLinks` (`:3182`), which is disjoint from `buildBoard`'s Delivered loop; #3013 and #3012 touch only `entry/` files. `fleet.ts` changed in 24 commits in one week (#2997's notes), so every slice here that touches it rebases on `origin/main` before review.

8. **low — the board's fleetless scan runs cold every beat.** `ScanState.walkCache` is absent on the board's cache entry ("Absent, the walk runs cold every beat, as the board's fallback does", `fleet-scan.ts` `ScanState`). When fleetd does not own the scan, the board walks the whole estate with no oid cache every 5 s. That is load on the same machine, not a request-path start, and it is a likely source of the `git for-each-ref`/`rev-parse`/`--diff-filter=AR` children the issue sampled. One field on the cache entry would give it the walk cache. It is out of this plan's scope unless the plan widens to "the board's load".

9. **low — fact checks that hold.** `fleet.ts:2835` says what the plan quotes. `refs-git.ts:652` is the `-G` argument inside `recordCommit`. The handler is at `index.ts:462`. In-flight builds are shared (`fleet-state.ts:163`, `inFlight`), so two concurrent polls do not double the starts; sequential polls each pay a full `buildBoard`, because nothing holds a finished build.

## Amendments I require

If the plan keeps a supervisor slice, its subject is cadence (one desk walk every 5 s, 3.9–12.8 s each), and it must wait on `feature/the-scan-script-is-a-launcher`, which edits the same function.
- A2. Make slice 2 extend the domain's `cachedRefs` (`plan-walk-cache.ts`) with `recordCommit`, `planAuthors`, `countBehind` and `defaultBranch`, and have the board hold one `WalkCache` per cache entry and wrap `refsFor(opts)` with the snapshot `boardState` already reads (`refsToken`). Name the slice for that, not for the Delivered record alone. Corpus rows for the new keyed operations go in `plan-walk-cache.corpus.test.ts`.
- A3. Add a slice for the plan parse: `buildBoard`'s `readPlanMeta` reads default-branch plans through `cachedPlans` (by blob sha) or through `planMetasAtDefault`'s held parse, so a warm request starts no `plot-plan-meta.sh` for unchanged blobs. Remove the second `ticketLaneData` call per request (pass the first answer into `discoveryLanes`), and move `planMetasAtDefault`'s key reads onto the same snapshot.
- A4. Slice 1 names its location (`packages/fleet/src/shared/config-reader.ts`, async path only), its key (mtime and size of `CLAUDE.md` and `AGENTS.md`, `repoRoot`, key, fallback, mode), and cites `board.ts:124-128`/`:621-626` with the reason it differs. It keeps `plot-config.sh` as the one reader and holds its answers; if it parses in TypeScript instead, the slice names the corpus pair and the shell-lines cost.

It extends the precedent in `plan-read-shape.test.mjs` (PATH shims for `git` and `bash`, `PORT=0`), adds Delivered plans to the fixture, warms the board, calls `stopFleetRefresh()`, truncates the log, and counts one request. No timing assertion. It also adds `ticketLaneData`, `discoveryLanes` and `planRefAgeSeconds` to `ENTRIES` in `a-read-route-spawns-nothing.test.ts`, and corrects that file's route table.
- A6. Add `waits:` or a rebase note: any slice that edits `refresh` waits on `feature/the-scan-script-is-a-launcher`; the slice for A3 names its order against #2993's `feature/the-fleet-payload-indexes-its-plans`, which reads the same `planMetasOf` metas.
- A7. Correct the Delivered claim: four starts per Delivered plan (17 on `origin/main`), not one per plan file.

## Optional

- O1. The smaller design: a third pulse subscriber builds the board on the beat (skipped while no request arrived in the last minute, through `lastRequestAt`), and `/api/board` answers the held build plus its per-request enrichment. That takes every start off the request in one slice. It costs a background build on each beat while a viewer is present, a staleness of up to one beat, and a forced rebuild after a write route. I prefer A2–A4 because each held value names the input that invalidates it, but the panel should weigh this as the fallback if A3 grows.
- O2. Give the board's cache entry a `walkCache` so the fleetless scan stops running cold (finding 8).
- O3. Memoise `Board command` in `serverInfo` with the same process TTL as `CI`.

## Open questions

- Q1 (which starts belong to the object-id key): all four do, through one snapshot. `git for-each-ref` is the snapshot read itself and stays at one per request. `git rev-parse` is `resolve`, already a snapshot hit in `cachedRefs`. `git rev-list --count HEAD..origin/main` is `countBehind`, keyed by the local head oid and the `origin/<default>` oid. The `--diff-filter=AR` log is `planAuthors`, keyed like `planAdditions`. None needs its own held value.
- Q2 (why `plot-fleetctl.sh` ran in the window): not a cold request, not a stale reading, and not a second caller. It is the refresh tick's call at `fleet.ts:2847`, which runs every 5 s and takes longer than 5 s, so it overlaps every request. The sampler counted the pid's children. The comment at `fleet.ts:2835` is correct.
- Q3 (what "warm" means and the bound): warm means one request has answered, the refresh pulse is stopped, and no ref, config file or working-tree plan changed since. The bound starts at the measured count and is lowered by each slice; the target is one start (the `refState` snapshot) plus the per-request working-tree reads the plan names explicitly (`git status` for `checkoutClean`, if it stays). Zero is not reachable while `boardState` compares refs on every request, and that one start is the price of a fresh answer.

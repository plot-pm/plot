Evidence: Read the plan, issue #2907 (`gh issue view`), `DESIGN-delivery-loop.md` (whole), CLAUDE.md's layering, index and shell sections, `packages/domain/src/workflows/release.ts`, `workflows/merge.ts`, `ports/host.ts` (op list), `packages/board/src/server/release.ts`, `server/entry/merge.ts`, `server/entry/deliver.ts:660-880`, `server/entry/gate.ts:615-700`, `rules/controller-gate.ts`, `skills/plot/scripts/plot-host.sh` (verb list, `runs` doc at :295-312), `scripts/check-shell-lines.sh` and `scripts/check-host-cli-callers.sh` headers, `.github/workflows/release.yml:20-40,140-180`, `entities/pr-index.ts`, and sibling plans #2900, #2902 and #2899. Ran read-only `gh` calls: the last three release PRs, the workflow runs, statuses and `validate` check runs on #2810's head `46a92390`, and the `main` ruleset's required checks.

## (a) Problem statement

- The plan cites no file:line at all. Its facts come from the design, and the design's facts that this plan leans on hold: `merge.ts:21-34` re-asks the host, and `entry/merge.ts:48-75` (`mergeAt`) is the existing pinned-merge path.
- **"`release` stays refused for every unattended caller" describes nothing that exists today.** Ran: `release(readings, { unattended: true, … })` returns `decided` with writes `plan-phase, plan-record, commit, push`. `unattended` turns the Should-Have prompt into a `PLOT-UNASKED` line (`release.ts:236-243`) and refuses nothing. `POST /api/release` (`server/release.ts:115-217`) has no unattended check, and the controller gate (`entry/gate.ts:651-700`) is a PreToolUse hook on an agent's Bash command, so it never sees a call fleetd makes in-process. The plan must **build** this refusal, and it does not say so.
- **"No other route reaches `release`" (Approach step 3) is false as written.** `POST /api/release` and the bundle the board starts for it (`plot-deliver.sh --release <version> <slug>`, `server/release.ts:37,213`) stay reachable. The plan has to scope the claim to "no unattended route", or gate the existing routes.
- **The "/api/release sweep" does not exist.** `/api/release` takes one `slug` and one `version` (`server/release.ts:144-155`). Each call books one plan in its own worktree and makes its own push to the default branch (`entry/deliver.ts:826-880`, `bookRelease` at `:713`). A sprint of N plans means N pushes to `main`, and each push starts a main CI run. That conflicts with the design's *one merge in flight, counting every merge into main* (DESIGN:89, :175). The recent release `parallel-release-calls-exhaust-their-push` (commit `21bae07b0`) shows that parallel calls of this route already broke once. The domain's `release()` already accepts many `deliveredPlans` and emits one `commit` and one `push` (`release.ts:296-344`), so a batched booking is possible.
- A fact the design missed: `release.yml:144-175` (`dispatch-ci`) already starts CI on the release PR through `workflow_dispatch`. On #2810's head both the dispatched run and the `pull_request` run reported `validate` success under app 15368. The dispatched run finished at 12:57Z, and the `pull_request` run finished at 13:28Z after a hand approval. The ruleset requires `validate` (app 15368) and `plot/review` (app 5317669). If the dispatched check alone satisfies the ruleset, the "approve the `action_required` run" step and its new host write are unnecessary. The plan should measure this before it builds the write.

## (b) Approach, against the layering lens

- **Prepare is a domain rule over readings. This is right, but the rule's inputs are unnamed.** The index row already carries `checks`, `review`, `headSha` and `checksSha` (`entities/pr-index.ts:40-50`). So `releasePrepareNext(readings)` can choose its step from the index, the frozen scope (#2900's `feature/fleetd-reviews-sprint-scope`) and the plans' phases. This is the *A Decision Reads The Index* shape, and choosing is reversible. The plan should list the readings: scope plans with phases, the release PR's index row, the prepared record, and the run reading.
- **Two new host operations are unnamed, and they collide with the shell ratchet.** The `Host` port (`ports/host.ts:187-373`) has no workflow-run read and no run-approve write. `plot-host.sh` has a branch-scoped, sha-blind `runs` verb (`:295-312`, `:4995`) that answers `unavailable` on Bitbucket, and no approve verb. "Wait for the publish workflow" needs a run-by-sha read, and "approve the CI run" needs a write. If either lands in `plot-host.sh`, `check-shell-lines.sh` refuses the growth unless the same change removes equal lines. `check-host-cli-callers.sh` scans only `*.sh` (`:130`), so a TypeScript connector adapter can reach `gh` without breaking that gate (`tracker-github.ts` already does). The plan must say which of the two it takes, and it must name the port operations and the answer on a backend with no such concept (`unaskable`, never "no run").
- **The approval controller must compose `merge()`, not re-implement it.** `merge()` checks state, head, draft, rollup, `checksSha` and the default branch (`merge.ts:95-136`), but it does not read the review on the head. Ran: a green rollup with no review field decides `pr-merge`. The new refusals (`not-release-pr`, `not-prepared`, `review-missing`, `unattended`) belong in a domain workflow `releaseApprove(readings, input)` that runs first and then delegates to `merge()` through the existing `mergeAt` adapter path. A second pinned-merge rule would be an undeclared duplicate.
- **Re-ask at the destructive step: right, and it must cover the review too.** The plan says the controller "re-asks the host". This must include the `plot/review` status on the host's head, read fresh, and not the index's `review` column. A merge cannot be undone (CLAUDE.md, *Only a terminal answer is read from the index*).
- **The "prepared" record must hold actions, not a verdict.** Per *Answers, never verdicts*, the record may hold what fleetd did: which run it approved, which head it started the reviewer on, which head it notified at. It must never hold "ready". The approval re-derives "ready" from the host. Open question 1 should be answered that way.
- **The finish step (wait, sweep, close) is where the layering and the design's *Decided* list collide.** If fleetd resumes the finish after a restart, fleetd reaches `release`, an unattended caller, which DESIGN:144 and :180 forbid. If the person's `plot-ask.mjs` call blocks through the publish workflow, a board-button route blocks the single-threaded server (`server/release.ts:117-121` documents why that route detaches). The plan has to choose, and the choice decides open question 3.
- **Closing the sprint through `plot-sprint-state.sh` is acceptable** only when an adapter starts it through the `Scripts` port. The script is a launcher over `board/plot-sprint-transition.mjs` (`plot-sprint-state.sh:29,89`), and the state gate receipt comes with it. The plan should say "through the `Scripts` port".

## (c) Slices

- The **Prepare** slice holds four things: the domain rule, two new host operations, the reviewer start and the notification. Split the host operations (port ops, adapter, `unaskable` on Bitbucket, with the run-approve write only if (a)'s measurement shows it is needed) into a slice of their own that comes first. Then the rule and its tick wiring. The reviewer start reuses #2900's `agent-run` path. The notification uses the existing `ports/notifier.ts`, which the plan should name; #2899 already uses it.
- **Approve** depends on Prepare only for the prepared record. The unattended refusal for `release`, and its gate entry (a `ControllerAction` for `release-approve` in `rules/controller-gate.ts:12`, with a receipt like `merge`'s), belong in this slice and must be stated.
- **Finish** needs a batched booking (one commit and one push for the sprint's plans), or a serial loop with a stated one-push-at-a-time bound. "Run the `/api/release` sweep" must not mean N HTTP calls from a controller to another controller.
- The **dependencies** read only "#2900 and #2902". #2900 supplies the scope reader and the reviewer start. #2902 supplies the in-flight mark that a release merge must respect. Name which reading of each this plan consumes.

## (d) Open questions

1. *What state records "prepared"?* A file under `.plot/state/` written by fleetd's adapter, holding actions only: `{pr, head, runApprovedAt?, reviewStartedAt, notifiedAt, version}`. "Ready" is never stored. The approval refuses `not-prepared` when the host's head differs from `head`, the same `sameCommit` floor `merge()` uses.
2. *How long to wait for publish, and what if it fails?* From my lens: the wait is a domain rule over a run reading `(pending | success | failure | unaskable)`, `Checks wait` and the clock. A failure after the merge reports and sweeps nothing, because `release()` refuses `tag-absent` until the tag exists (ran: `refused tag-absent`). The tag-absent refusal already guards the sweep. The bound value stays open.
3. *Same call or a resumed step?* The design permits only the person's action to reach `release`. So either (i) the person's call records an approval receipt bound to `(pr, head, version)` and a detached process **started by that call** finishes, with a re-run of `release-approve` on a merged PR idempotently resuming the finish, or (ii) the design's *Calls made* line is amended to let fleetd finish on such a receipt. Option (i) needs no design change. The plan must not leave this open, because it decides which caller reaches `release`.
4. *How does the board show it?* Per *Every rendered state is a domain property*: a `releaseStage` value (`waiting-scope | preparing | ready | merging | publishing | swept | failed`) computed in the domain from the same readings. The button's disabled state comes from that value, not from `.tsx`.

New questions the plan should carry:
- Does the dispatched `validate` run satisfy the ruleset alone? If so, drop the run-approve write (see (a)).
- Where do the new host operations live, in `plot-host.sh` against the ratchet or in a TypeScript connector?
- How are the existing `/api/release` and `plot-deliver.mjs --release` routes treated once "no other route" is claimed?
- What does the rule answer on Bitbucket with Jenkins, where `runs` is `unavailable` and no `action_required` concept exists?

## (e) Tests

- Host operations: adapter contract tests in `test/reconcile/` with a stubbed `gh` (shape of `host.test.mjs`): a run read by sha, the approve write, and `unaskable` on Bitbucket. Run `check-shell-lines.sh pr` as a gate test that must pass unchanged.
- Prepare: a vitest table over `releasePrepareNext` in `packages/domain`. Rows: a scope plan not Delivered gives `none`; no release PR gives `none`; `action_required` gives `approve-run`; pending gives `wait`; green with no review on the head gives `start-reviewer`; green and reviewed but not notified at the head gives `notify`; notified at the head gives `none`; a moved head re-notifies. Use pure readings and no ports.
- Approve: a vitest refusal table over `releaseApprove`. Cover `unattended`, `not-release-pr`, `not-prepared` (head moved), `review-missing` (green rollup, no `plot/review` on the head, the case my probe showed `merge()` lets through), and a pass that yields `merge()`'s pinned `pr-merge` write. Add one board-package unit test that `plot-ask.mjs release-approve` under `PLOT_UNATTENDED=1` exits with the refusal.
- Finish: a vitest table over the finish rule: run pending, failure, success with the tag absent (then the `release()` refusal), and success with the tag present (then one batched decision for N plans with exactly one `push`). Add one integration test that N plans produce one commit.
- Board: one browser test that the button shows the domain's `releaseStage`, and nothing more.

## (a) Problem statement

- **The premise "`release` stays refused for every unattended caller" is false today.** The probe called `release(readings, { unattended: true, ... })` with a resolvable tag and got `outcome: "decided"`, with plan-phase, plan-record, commit and push writes. `unattended` only turns the Should-Have prompt into a `PLOT-UNASKED` line (`workflows/release.ts:239`). `/api/release` passes no unattended input at all (`entry/deliver.ts:725`), and `controller-gate.ts:12,294` checks only for a receipt. Sibling #2908 repeats the error with "`release` *still* refuses". No code refuses yet, so the plan has to build this refusal and test it. It cannot inherit it.
- **"No other route reaches `release`" is not true after this plan either.** `POST /api/release {slug, version}` (`board/src/server/release.ts:114-217`) stays, and the plan's own Finish step uses it. The plan does not say whether `/api/release` now refuses a call that no `release-approve` started. A test cannot check the claim until the plan says what enforces it.
- **The `action_required` approval may no longer be needed.** `release.yml`'s `dispatch-ci` job, from plan `2026-10-01-the-release-pr-is-checked-before-it-merges` (Released), already starts `ci.yml` by `workflow_dispatch` on every release-PR head, so `validate` reports. Measured on `changeset-release/main`: heads `a81a630`, `6554199` and `b323579` each carry an `action_required` pull_request run *and* a `success` workflow_dispatch run. The `main` ruleset requires only `validate` and `plot/review`. The Notes call that plan unrelated ("answer other questions"), but it answers the question Prepare step 1 depends on. Prepare should measure first whether a green dispatch run alone lets the release PR merge. If it does, the approve-run step becomes a no-op or an `unaskable` arm, not a new connector write.
- **The release sweep does not record every plan.** The probe ran `release()` with `tagExists: true` and a plan whose `tag` is `''`. It returned `decided` with `writes: []` and `notMarked: [{reason: 'unresolvable'}]`, so it succeeded silently and recorded nothing. `docs`/`infra` plans are always skipped as `docs-live-on-merge` (`release.ts:304-307`). The Changelog says "records the release in the sprint's plans" with no qualifier. The operator's standing preference (memory `docs-infra-plans-get-a-released-record-too`) is that docs/infra plans get a `Released` record too. Today the master agent writes those by hand with an unowned receipt, and the fleet cannot do that.
- **`plot-sprint-state.sh` writes the sprint file and does not commit it** (the script ends after its `awk`/`mv` write; it has no `git` call). The plan says the Finish step "closes the sprint through `plot-sprint-state.sh`" but does not say who commits and pushes the closed sprint to `main`, or under which push lock. Since #2804 the lock covers the whole booking.

## (b) Approach

- Slice 1 crosses the layering boundary and does not say which port it uses. `ports/build.ts` has `runs`, `runForSha` and `runsForSha` (`:76,103,120`). It has no approve-run operation, and `Host` has none either (`ports/host.ts:187-427`). Approving a run is a connector write on the build-pipeline port, and Jenkins and Bitbucket would need an `unaskable` arm. The plan should name the port operation, or drop it per (a).
- `release-approve <pr>` has no sha. The design lets the person approve what the notification named. If the controller pins to the head it reads at approval time, it merges whatever was pushed after the notification. `merge` already takes `<pr> <sha>` (`entry/main.ts:151-176`) and refuses `head-moved`. `release-approve` should pin to the head stored in the prepared record, or take `<pr> <sha>`, so a moved head refuses by name.
- `workflows/merge.ts` does not read `plot/review`. The probe merged a release PR with `review: ''` and got `decided`, and `mergeAt` never calls `host.prReview` (`entry/merge.ts`). The refusal for a release PR with no review, or a review on another head, is new domain code. It needs `host.prReview` (`ports/host.ts:408`), which already returns `{sha, state}`.
- The Finish step waits for the publish workflow inside one controller call. `plot-ask.mjs` is a one-shot process (`entry/main.ts:131`), and `/api/release` is detached and answers 202. A wait of several minutes inside the approval call is fragile. A test can only prove it with a fake clock.

## (c) Slices

- Slice 1 holds a pure rule, a connector write, a reviewer start (which depends on #2900's agent start), a notifier and a state record. Split it in two. **1a**: the domain rule `releasePrepare` plus the prepared-record shape, testable with values only. **1b**: the fleetd wiring and the port calls.
- The unattended refusal for `release` has no owner. #2908's slice `feature/fleetd-caller-identity` claims it. This plan claims "No other route reaches release". Pick one owner, and make that slice carry the test. The dependency list names only #2900 and #2902, but this plan also depends on #2908 for the caller identity, and on #2900's `feature/fleetd-reviews-sprint-scope` slice in particular for the frozen-scope reader.
- Slice 3 (Finish) should be resumable. Make it a fleetd step that reads "release PR merged, tag exists, sweep incomplete" from recorded state, not a continuation of the approval call. `release()` already skips `already-released`, so it is idempotent and a re-run is safe.

## (d) Open questions

1. **What records "prepared"?** One file, `.plot/state/release-prepared.json`: `{ pr, headSha, version, scope: [slugs], reviewState, notifiedHead, at }`. Keep the decision fresh: `release-approve` re-asks `prState` and `prReview` (the *A Decision Reads The Index* split; see `merge.ts` and the design's Constraints). It compares the result with `headSha` from the file. The file only keeps "notified once per head" and the scope the person saw.
2. **How long is the publish wait, and what happens on failure?** Reuse `Checks wait` (3600 s, `## Plot Config`) and read the run through `Build.runsForSha('main', mergeSha)`. On failure, notify and record `publish-failed`. Do not sweep. The probe shows `release()` refuses `tag-absent` without a tag anyway.
3. **Same call or separate step?** A separate step, per (c). Evidence: `plot-ask` is one-shot, `/api/release` is detached, and `release()` is idempotent.
4. **How does the board show it?** The four states (ready, merged, publishing, swept) must be one domain property. Per CLAUDE.md, *Every rendered state is a domain property*: one domain unit test covers each state, and one browser test proves the button renders.

The plan should also carry these new questions:
- Does a release PR with an `action_required` pull_request run and a green dispatch run merge? Measure this read-only on the next release PR before slice 1 is built.
- Which tiers count toward "every plan in the scope is Delivered": Must only, as the `release()` gate does, or every tier? Does a `withdrawn` item count as done?
- Do docs/infra plans get `Released` from the sweep, against `release.ts:304`, or is the operator's preference dropped?
- Does the Finish step close the sprint when a plan stays `notMarked: unresolvable`?
- Who commits and pushes the closed sprint file, and under which lock?

## Amendments

1. Correct the premise. `release` does not refuse unattended callers today (`release.ts:239`, `deliver.ts:725`, probe C). Name the slice that adds the refusal and its test. Add #2908 to Dependencies, and name #2900's scope-reader slice.
2. State what makes "no other route reaches `release`" true for `POST /api/release` and `plot-deliver.sh --release`, or weaken the claim.
3. Pin `release-approve` to the prepared head (the stored sha, or `<pr> <sha>`), and refuse `head-moved` and `review-missing` by name. `merge()` checks neither review nor release-PR identity.
4. Measure the `action_required` step against `dispatch-ci` (plan `2026-10-01-the-release-pr-is-checked-before-it-merges`) before building it. If the step stays, name the `Build` port operation and its `unaskable` arm.
5. Split slice 1 into a pure rule slice and a wiring slice. Make Finish a resumable fleetd step, not part of the approval call.
6. Write per-slice acceptance criteria. Include "every scope plan ends as marked or as `notMarked` with a reason", and decide on docs/infra plans (`release.ts:304`) and on closing a sprint with an unresolvable plan.
7. Say who commits and pushes the closed sprint file (`plot-sprint-state.sh` only writes it), and under which push lock.

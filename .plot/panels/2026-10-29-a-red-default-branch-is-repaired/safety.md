# Juror verdict: safety

Position: amend

Evidence: Read the plan, issue #2904 (`gh issue view`), DESIGN-delivery-loop.md, the sibling plans #2898, #2900 and #2902, and on the worktree tree (a5f3fb0ec, current main): `packages/domain/src/workflows/merge.ts`, `packages/domain/src/entities/default-branch.ts`, `packages/domain/src/rules/default-branch.ts`, `packages/fleet/src/shared/default-branch-refresh.ts`, `packages/fleet/src/server/entry/registryd-main.ts:1560-1570,2858-2863`, `packages/domain/src/rules/auto-dispatch.ts:220`, `.github/workflows/ci.yml:62-64`. Ran: a node probe (`juror-2904-safety/probe.mjs`, a resolve hook over the domain `.ts` sources) calling `merge()` and `defaultBranchRed()` on synthetic red, pending-after-red and stale readings; `git log --first-parent origin/main --since=2026-10-20` classified by subject. Not run: any vitest file, any host write.

## (a) Problem statement

- Correct: `registryd-main.ts:2863` maps `'default-branch-red': 'queue'`. `default-branch-refresh.ts` records `settled` and `failingRuns` in `.plot/state/default-branch.json` (`entities/default-branch.ts:44-73`).
- Wrong in part: *"The inputs to a repair exist"*. The reading holds the newest settled commit and its failing runs only. It does not record (1) the last green commit, (2) the commit that turned main red, or (3) when red first settled. `advanceSettled` (`rules/default-branch.ts:110-115`) overwrites `settled` on every concluded head. `headSince` is per head and resets on a new head. The probe shows this: `headSince` goes from `10:00` to `11:59` when a pending commit lands on a red main. So the rule's inputs "the merge that turned it red" and "the first red reading that settled" must be new recorded state. The *Anti-goal check* line depends on that record and has no source today.
- Missing cause: most commits on main are not PR merges. Of 1273 first-parent commits since 2026-10-20, 169 read `Merge pull request` and 134 end in `(#N)`. The other 970 are direct pushes (`plot:` 764, `plot-implement:` 132, `sprint:` 56, …), most of them lifecycle records. The plan says "revert the merge" throughout. The commit that turns main red can have no PR, or can be a `State:` write that `plot-state-gate.sh` refuses to revert without a receipt. Reverting it would also run a lifecycle step backwards, which the design forbids.

## (b) Approach, against the anti-goal and the safety rules

1. **Both repair merges are refused by the controller the plan names. This finding blocks the plan.** Approach step 3 merges the revert "through `workflows/merge.ts`". Step 2's fix PR "jumps the queue". `merge.ts:127-129` refuses every merge while `settled.state === 'red'`, and that includes the merge that would make main green. Probe output: `revert PR, main red, fresh : {"outcome":"refused","reason":"default-branch-red",…}`, and the same holds when a newer head is pending. #2902 also holds every merge while main is red (its plan, line 38/44). As written, neither repair PR can ever merge, so main stays red: the anti-goal. The plan needs a narrow, named exception in `merge()`. It permits only the PR that the repair record names, pinned to that head, and only while the settled red SHA equals the one that started the repair. Every other refusal stays (`default-branch-stale`, `checks-not-green`, `checks-unbound`, `head-moved`). This is a contract change to `merge()` and to `plot-ask.mjs merge`. It needs its own slice and tests. It must not become a flag that a caller sets.
2. **The `plot/review` requirement has no producer for repair PRs.** #2900 starts the reviewer only on "every green slice PR of the sprint's frozen scope". A fix PR or a revert PR belongs to no plan's slice and to no scope. The ruleset requires `plot/review` and the fleet gets no bypass (*Decided*). Without a reviewer arm for repair PRs, the revert waits for a person, and the bound "`Main repair bound` plus one merge round" does not hold. The plan must add that arm, or depend on a plan that adds it.
3. **A revert can merge after main is already green.** `merge()` checks only that main is not red at merge time. Take this sequence: the revert opens at T+60. A person or the fix PR makes main green at T+65. The revert's CI goes green at T+70. `merge()` then permits it, and fleetd reverts good work on a green main. The rule must close the revert PR, or stop pursuing it, when the settled SHA no longer equals the recorded red SHA, or when the settled state is green. The merge-time check must pin to the red SHA (see 1). The fix PR has the same problem in a milder form. When main turns green by other means, an open main-repair PR should be closed or handed to the normal loop, not merged as "repair".
4. **Revert while a newer head is pending.** `defaultBranchRed` stays true while a newer head is pending after a red settled commit (probe: `defaultBranchRed pending : true`). A fix that a person pushed, or one that just merged, may be running. Opening a revert at the bound in that window stacks a revert on a candidate fix. The `revert` answer should require `headSha === settled.sha` (nothing newer is in flight), or wait one settle.
5. **Crash between start and record.** "One repair at a time" holds only if fleetd writes the record before it acts. The order must be: write the intent (red SHA, `redSince`, attempt n) → start the agent or push the branch → record the PR. On restart, fleetd adopts a record that names no live worker and no PR after a bound as a spent attempt. It does not start a second agent. Today's in-flight guards for dispatch are in-memory `Set`s (`auto-dispatch.ts:103,164`). This record must not copy that pattern, or a crash produces two main-repair agents writing two fix PRs.
6. **Two ticks.** Within one fleetd, ticks never overlap (`registryd-main.ts:1565-1568`). That is not true across machines: the record lives under `.plot/state/` on one machine, and a claim from another machine is invisible here. Two fleetds on one repository would each revert. A deterministic branch name (`revert/<red-sha>`) makes the second push fail. A ref claim (as dispatch claims by ref push) makes the second start fail. The plan should choose one and name it as the one-writer gate for the repair.
7. **Host failures and partial answers.** The revert step pushes a branch and then opens a PR. If `pr-create` fails after the push, the next tick must find the branch's PR by asking the host (`pr-list --branch`). An absent PR-index row is never proof that no PR exists (*A Decision Reads The Index*: "the index never says no"). An `unaskable` answer holds. It never opens a second PR and never counts as "no repair PR". For the reading itself, `merge()` already refuses `unaskable` and stale readings (`merge.ts:118-126`). The rule's `revert` answer is irreversible and must use the same strict reading as `merge()`, not the lenient `defaultBranchRed`, which lets a stale red lift (probe: stale red → `defaultBranchRed` false, `merge` `default-branch-stale`).
8. **Controllers and unattended callers.** Opening the fix PR and the revert PR has no controller. `plot-open-pr.sh` opens slice PRs only, and the repo rule forbids `gh pr create`. The plan must name the route (an adapter call through `plot-host.sh pr-create`, as a sprint PR does) and say that a controller is missing. The `merge` call relies on #2898's caller identity. The plan does not say so. "main-repair never pushes to main directly" is a rule unless #2898's `PreToolUse` hook refuses `git push` to the default branch. The agent runs with the operator's credentials, and the operator pushes to main directly (970 commits above), so the ruleset does not stop it.
9. **The reverted work does not come back for a Delivered plan.** `dispatchPhase` accepts only `approved` and `design` (`rules/auto-dispatch.ts:220`). A new slice heading on a Delivered plan is never dispatched, and it leaves a Delivered plan with an unmerged slice, which reconcile reads as drift. For a Delivered plan the ticket is the real return path, and the plan should say that. Writing the heading into a plan file on main is a further hand edit of a plan with no controller (*The Master Agent Uses The Controllers*).

## (c) Slices

- Missing slice, first in order: **the repair record and the red-onset record** (`redSince`, last green SHA, red SHA, candidate commits, attempt, PR, written before any action). The rule slice cannot be tested without them.
- Missing slice: **`merge()` permits the recorded repair PR on a red main**, pinned to the red SHA. This needs a matching change in #2902's hold, or a declared ordering with it.
- Missing dependency or slice: a reviewer arm for repair PRs (#2900 excludes them).
- The revert slice holds three concerns: revert PR + merge, the plan-file heading, and the ticket. The ticket and the heading are reversible and independent of the merge. Split them out so the revert, which is the anti-goal's guard, can merge alone.
- `waits:`: slice 2 needs #2898 (role definition + caller identity). Slices 2 and 3 need #2902 and the reviewer arm. Write these as `waits:` annotations, not only as issue links, so the fleet does not dispatch them early.

## (d) Open questions

- *#2902 dependency, `waits:` or link?* `waits:`, and on more than #2902: #2898 (identity, `main-repair.md`) and a reviewer for repair PRs. The merge exception in 1 also changes #2902's hold.
- *Add `main-repair.md` here?* No. #2898's slice `feature/role-agent-definitions` builds `main-repair.md`, and its caller-identity slice is what lets `merge` accept fleetd. Wait for it.
- *Which merge turned main red?* The proposal ("earliest merge at or after the last green reading") has no input today, because the last green SHA is overwritten. CI runs once per push (`ci.yml:62-64`, group per `run_id`), so intermediate commits do settle, and the walk can name the first red commit exactly, if fleetd records it. Proposal: revert only when that commit is a PR merge whose PR the host reads as `MERGED` and that changes no `State:` line. Otherwise, notify and keep the repair agent, with no revert. When more than one PR merged between the last green and the first red (a person merged in parallel), notify instead of guessing.
- *Conflicting revert?* Stop at a notification. A conflict resolution written by the repair agent is a new change that nothing proves. It is no longer a revert.
- *Stale reading?* Yes, and stricter than stated: `hold` uses `defaultBranchRed`, and `revert` uses `merge()`'s rule (a stale reading permits nothing).
- New questions the plan should carry:
  - How many main-repair attempts run before the bound, and does a failed attempt start another?
  - Is a red that no merge caused (flake, runner outage, scheduled job) re-run once before a repair starts, so that a flake does not revert innocent work?
  - What happens to an open fix or revert PR when main turns green by other means? (See b3.)
  - Which one-writer mechanism guards the repair across machines? (See b6.)
  - If fleetd was down for longer than the bound, does it revert at once on restart, or start a repair first?

## (e) Tests

- Rule (domain unit, vitest, synchronous): a table over readings × record. It must cover fresh red with no record → `start-repair`; red with a record inside the bound → `await-repair`; past the bound with `headSha === settled.sha` → `revert`; past the bound with a newer pending head → `await-repair`; stale or `unaskable` reading → `hold`, never `revert`; settled green with an open revert recorded → close; red commit not a PR merge → no `revert`; red commit changes a `State:` line → no `revert`.
- Merge exception (domain unit on `merge()`): the recorded repair PR on red main at the recorded red SHA → `pr-merge`; the same PR after the settled SHA moved → `default-branch-red`; any other PR on red main → `default-branch-red`; a stale reading → `default-branch-stale` even for the repair PR. Add a mutation check: dropping the red-SHA pin must fail a test.
- Crash and idempotence (fleet unit with fakes): a crash after the intent write and before the agent start → the next tick starts no second agent. A crash after the push and before the PR → the next tick asks `pr-list --branch` and opens at most one PR. `pr-list` `unaskable` → nothing opened. Two runs of the tick on the same record → one start.
- Ticket and heading: unit tests over the adapters' fakes; a failed ticket write retries and never blocks the revert merge.

## Amendments

1. Add a `merge()` exception for the recorded repair PR, pinned to the red SHA, as its own slice with domain tests. Reconcile it with #2902's red hold.
2. Record `redSince`, the last green SHA and the first red SHA, because the current reading loses them. Correct the Motivation's "the inputs exist".
3. Revert only a PR merge the host reads as `MERGED` that changes no `State:` line. Otherwise notify. Name the direct-push case (970 of 1273 commits since 2026-10-20).
4. Require `headSha === settled.sha` for `revert`. Close or abandon the revert PR when main is green or the settled SHA moved.
5. Write the repair record before acting. Give the repair branch a deterministic name, or take a ref claim, as the one-writer gate. Ask the host, not the index, before opening a PR.
6. Name the reviewer arm for repair PRs, and the PR-open route (`plot-host.sh pr-create`, no controller yet).
7. Add `waits:` on #2898, #2902 and the reviewer arm. Leave `main-repair.md` to #2898.
8. State that for a Delivered plan the ticket is the return path. `dispatchPhase` never dispatches a new heading on it. Split the heading and the ticket out of the revert slice.
9. Decide the conflict case (notify), the flake case (one re-run first), and the fleetd-downtime case.

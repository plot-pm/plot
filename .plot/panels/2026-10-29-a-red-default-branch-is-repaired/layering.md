# Juror verdict: layering

Position: amend

Evidence: Read the plan, issue #2904 (`gh issue view`), DESIGN-delivery-loop.md, sibling plans #2908 and #2914, and at the worktree (a5f3fb0ec): `packages/domain/src/workflows/merge.ts`, `rules/default-branch.ts`, `entities/default-branch.ts`, `entities/pr-index.ts`, `rules/queue.ts:570-590`, `ports/agent-run.ts`, `ports/trees.ts`, `ports/refs.ts`, `fleet/src/shared/default-branch-refresh.ts:200-260`, `registryd-main.ts:2850-2870`. Ran one vitest probe (scratch file, outside the repo) against `merge()`, `defaultBranchRed()` and `DefaultBranchReadingSchema`: (1) a green, open, undrafted PR with bound checks on a red, fresh reading returns `{"outcome":"refused","reason":"default-branch-red"}`; (2) the reading's keys are exactly `v,branch,headSha,head,settled,walked,failingRuns,headSince,askedAt,at`; (3) the schema is `.strict()` and rejects an extra `lastGreen` field.

## (a) Problem statement

- The core fact holds. Nothing acts on a red main: `default-branch-red` holds dispatch of new slices (`rules/queue.ts:583`, `whyNotReady`) and refuses merges (`workflows/merge.ts:127-129`). No `main-repair` or `Main repair bound` exists anywhere in `packages/` or `skills/` (grep: 0 hits).
- `registryd-main.ts:2863` is misread. That line is an entry in `HOLD_SCOPE`, the log-scope record (`'estate' | 'queue'`) that decides how a hold is counted in the log. It does not map the hold to anything that acts. The hold itself is `queue.ts:583`, and the merge refusal is `merge.ts:127`. The plan should cite both, because the second one is the one this plan collides with (see (b)).
- "The inputs to a repair exist" is half true. `failingRuns` and `askedAt` exist (`entities/default-branch.ts:62,69`). Three inputs the rule needs do not exist anywhere: (1) **the merge that turned main red** — the reading holds only the newest settled commit (`settled`, `:54`), and the PR index row carries no merge-commit SHA (`entities/pr-index.ts:60-90`; only `entities/pr.ts:64` has `mergeCommit`); (2) **the last green commit** — `advanceSettled` (`rules/default-branch.ts:~117`) overwrites `settled`, so the green SHA is gone once red settles; (3) **when the red first settled** — `headSince` (`:63`) is when the head was first seen, not when red settled, and `askedAt` moves on every answer. The 60-minute bound in Approach step 3 and the anti-goal check ("measured from the first red reading that settled") have no recorded source today.

## (b) Approach, under the layering lens

1. **The rule is the right shape.** One domain rule over readings, with answers `hold | start-repair | await-repair | revert | none`, synchronous and spawning nothing, fits `reap(readings, input)`. The start and the PR open are adapter calls. No new shell. Nothing here grows `plot-*.sh`, so the shell line ratchet is not at risk, provided the revert's git work goes into a `Trees` adapter op in TypeScript. `ports/trees.ts` has `commit`, `push`, and `resetOnto`, but no revert operation, so the revert slice adds a port method and an adapter, not a script.

2. **The merge controller refuses both PRs this plan wants to merge.** Approach step 3 says the revert PR merges "through `workflows/merge.ts`", and step 2 says the fix PR "goes through the same loop". `merge()` refuses every PR while `settled.state === 'red'` (`merge.ts:127-129`, which I executed). Sibling #2914's `slice-pr-next` table also holds on "Default branch red or stale" with no exception. As written, neither repair PR can ever merge, and main stays red: the anti-goal. The fix is a domain decision, not a bypass. `MergeReadings` gains a repair reading (the repair record's PR number and the breaking commit it repairs). `merge()` lets exactly that PR past `default-branch-red` and still applies `default-branch-stale`, `head-moved`, `checks-not-green` and `checks-unbound`. #2914's rule gets the matching row. No slice carries this change today. Because it changes the contract of `plot-ask.mjs merge` and of #2914, it needs its own slice or an explicit place in the Rule slice.

3. **Recording the missing inputs must not touch `default-branch.json`'s schema.** The schema is `.strict()` (`entities/default-branch.ts:73`), and `decodeDefaultBranch` turns any parse failure into `null`, which "holds nothing" (`:79-80`). If fleetd adds a field such as `lastGreen` or `redSince` without bumping `v`, every reader built before the change parses the file as `null`. Those readers are the board (`board/src/server/estate.ts`, `board.ts`), `plot-ask.mjs merge`, and an older bundle. A red main would then read as no reading and lift the hold. Bumping `v` makes the same readers read `null` until they rebuild. So the transition facts belong in the **repair record**, a separate file that only this rule reads. The refresh writes the record at the green-to-red transition, when `previous.settled` (`default-branch-refresh.ts:210`) still names the green SHA. The plan leaves the record's shape to the builder. It should still say that the record holds `lastGreenSha`, `redSettledAt` and `redSha`, and that `default-branch.json` stays at `v: 1`.

4. **"Which merge turned main red" is a git question asked by hash.** It belongs in the domain as a pure function over readings. The inputs are the first-parent commits between `lastGreenSha` and `redSha` from `Refs`, plus each commit's subject. That is CLAUDE.md's sanctioned case, "a commit NAMED BY HASH", kind `evidence`, so any ancestry call gets a `# plot-ancestry: evidence` declaration (`scripts/check-ancestry-decisions.sh`). `rules/merge-subject.ts` (`mergedBySubject`, `:88`) parses only the two merge-commit forms. A squash merge on GitHub has the subject `Title (#N)`, and this estate squash-merges. So the commit-to-PR step either adds a squash-subject form or asks the host through the `host` connector. The rule must answer `unknown` when a window holds more than one candidate and none can be tested alone. A wrong revert is a merge into main and cannot be undone.

5. **A Decision Reads The Index.** The choice to revert reads recorded state (the reading and the repair record). That is correct for choosing. The revert is destructive, so the destructive step re-asks: `merge()` re-reads the PR and refuses a reading older than `Checks wait` (`merge.ts:121-126`). The plan should also add a fresh confirmation before the revert PR is **opened**: main is still red on the same `redSha`, the breaking commit is still on main's first-parent line, and no later commit has reverted it. Opening is cheaper than merging but leaves a branch and a PR to clean up. The IndexMonitor already emits the `default branch red` finding (`rules/index-findings.ts:167`). The plan should use it as the trigger (part 3 of the section) instead of a new poll.

6. **Two writes have no controller.** (i) "The plan gets a new slice heading with its own branch" is a write to a plan file on the default branch. *The Master Agent Uses The Controllers* rules out a hand `sed`, and no controller appends a slice heading. `reslice` rewrites `## Slices` only after a person confirms. The plan must name the controller, or build one, or move this step out of the plan. Today it is a write with no owner. (ii) The ticket for a Delivered plan goes through the `tracker` connector. That is correct, but it overlaps #2916 (tickets follow the loop). Name which plan owns the writer.

7. **`plot/review` on the repair PRs.** The ruleset requires `plot/review` on main. The plan says the ruleset "is not bypassed" but does not say who writes the status on the fix PR and the revert PR. That takes the reviewer start from #2917. Without it, both PRs wait forever, and the anti-goal timing ("bound plus one merge round") leaves out a review round.

## (c) Slices

- The cut into rule, then repair, then revert is sound. The Rule slice is pure domain plus a config key and is independently mergeable.
- Missing: the `merge()` and `slice-pr-next` repair exception, from (b)2. Put it in the Rule slice, or in its own slice that lands before Repair, since both later slices depend on it.
- Missing: the repair-record writer at the green-to-red transition in `default-branch-refresh.ts`, from (b)3. It belongs with the Rule slice or as a first slice.
- *Revert* bundles four things: the revert PR, the revert merge, the new slice heading, and the ticket. Split the plan-heading write and the ticket into their own slice, or move them out to #2916 or a follow-up. They have no controller yet, and they should not block the revert, which is what protects main.
- Dependencies: Repair waits on #2908 (`main-repair.md` and the fleetd caller identity for `merge`), on #2914 (the merge loop) and on #2917 (the reviewer). Revert waits on #2914. These belong as `waits:` annotations on the slices, not only in the issue text.

## (d) Open questions

- **Q1 (`waits:` or issue link only):** Use `waits:` on Repair and Revert for #2914, and on Repair for #2908 and #2917. An issue link does not hold a dispatch, and `waits:` does (`queue.ts:585`).
- **Q2 (who adds `main-repair.md`):** #2908's `feature/role-agent-definitions` builds it (#2908 plan, line 62). This plan should not add it, and should wait on it.
- **Q3 (which merge turned main red):** The proposal needs `lastGreenSha`, which is not recorded today (see (a)). Take the first-parent commits strictly after `lastGreenSha` up to and including `redSha`. With one commit, that commit is the answer. With several, prefer the oldest commit whose own runs read red, since `settleBehindHead` already asks ancestors. If none can be told apart, answer `unknown` and notify, and do not revert. Never pick by time alone.
- **Q4 (a conflicting revert):** Under the design's *Stalls* rule, this is a notification and not a stop. Do not let main-repair resolve the revert. That would put a judgement step inside the one action whose value is that it is mechanical. Keep fixing forward.
- **Q5 (reading age):** Yes. Reuse `defaultBranchRed(reading, now, checksWaitMs)` (`rules/default-branch.ts:262`) for `hold` and `start-repair`. Use `defaultBranchAgeMs` for the stricter revert, as `merge()` does at `:122`. Do not write a third age check.
- **New:** Which branch prefix does the fix PR use? `Branch prefixes` lists `idea/ feature/ bug/ docs/ infra/`. The board and the reaper key on these prefixes.
- **New:** What happens when a person pushes a fix while main-repair runs? Does `await-repair` end when main turns green from any commit, and who stops the agent then?
- **New:** Does the bound run from `redSettledAt` or from the repair start? The anti-goal requires `redSettledAt`.

## (e) Tests

- **Rule (domain unit, vitest):** A table test of `redMainStep(readings, input)` over: green; red but stale (treated as no reading); red and fresh with no record (`start-repair`); a record in flight inside the bound (`await-repair`); a record past the bound (`revert`); a second red reading during repair (no new start); an `unknown` breaking commit (no revert).
- **Merge exception (domain unit plus a contract test):** `merge()` passes the recorded repair PR on red, still refuses it when stale or when `head-moved`, and refuses an unrecorded PR on red. A `plot-ask.mjs merge` contract test shows the same refusal for an unrecorded PR.
- **Breaking-commit picker (domain unit):** One candidate; several candidates with a red ancestor; a squash subject `Title (#N)`; no candidate.
- **Repair-record writer (fleet unit):** The green-to-red transition in `refreshDefaultBranch` writes `lastGreenSha` and `redSettledAt` once, and a later red-to-red pass does not move them. `default-branch.json` stays at `v: 1`. A test asserts that the board decoder still parses it.
- **Fix forward and revert (fleet unit with fake ports):** fleetd calls `AgentRun.run` with role `main-repair` exactly once per record. The revert opens through `Host.prCreate` and merges only through `merge()`. No `spawn` is added outside `adapters/`, so the spawn ratchet does not move.

# Correctness juror: ci-reuses-green-runs

Position: amend

Lens: where the plan can go wrong silently. Checked in the worktree of `idea/batch-refs-from-files` against `.github/workflows/ci.yml` (2,675 lines), `release.yml`, `scripts/check-host-cli-callers.sh`, `origin/idea/ci-cancels-superseded-runs` (`ccdfe9b82`), and the Actions API on 2026-11-09.

## Open Questions

- **Where the base SHA is recorded.** Use the artifact, as recommended, but read its contents too, not only its name. The name carries the two SHAs; the reuse rule also needs the earlier run's changed-path list and its selection (see Finding 1 and 2), and neither fits in a name. The pin and retention to copy exist: `ci.yml:686` (`upload-artifact@043fb46d…`) and `:693` (`retention-days: 7`). One download per candidate source, through the same retry helper, costs little against a 25-minute run.
- **`gh api` in the workflow or a `plot-host.sh` op.** `gh api` in the step, as recommended. `check-host-cli-callers.sh:82` sets `ROOTS='skills scripts hooks'`, so a workflow step is outside the gate, and `release.yml:258-272` holds the three-attempt `api()` helper to copy. The read is this repository's CI, not a Plot helper that another host needs.
- **A failed run as a source.** Keep it: a job's `success` is final whatever the run's conclusion, and `validate` reads jobs one by one (`ci.yml:2657-2671`). Apply the same argument to a `cancelled` run (Finding 3): a job that ended `success` before the cancel is equally final.

## Leftovers

- **Branch and group key of `ci-cancels-superseded-runs`.** Confirmed: `refs/heads/idea/ci-cancels-superseded-runs` at `ccdfe9b82`, PR #3305. Its plan keys the group `format('pr-{0}', github.event.pull_request.number)` for `pull_request` runs, keeps `github.run_id` for `push` and for the release PR, and keeps `release-dispatch` for dispatches. The reuse plan reads no group key and touches no `concurrency:` line, so the two merge in either order as stated. The interaction is in Finding 3, not in the lines.
- **The reuse rule (base SHA unchanged).** The plan implements it as `recorded base == HEAD^1`. That compares the right SHA. It does not make the head diff equal the tree diff (Finding 1).
- **`pull_requests` on an earlier run.** Measured: run 42613010489 (head `5b38808be`) still lists `[3310]` while PR #3310's head is `509f18f60`, so the field survives a new push on an open PR. A fork run lists `[]`, so a fork PR never reuses. That is safe.

## Findings

1. **The head diff is not the tree diff.** The plan says two runs with the same `HEAD^1` "differ only by the head change `HEAD^2(earlier)..HEAD^2(now)`". That is false when the merge base moves between the two heads (a rebase, or a merge of the base into the branch). Counterexample: `main` changes `f` from `x` to `y`; the head H1 never touched `f`, so the first merge holds `y`. The author merges `main` into the branch and resolves `f` back to `x` (H2). `H1.f == H2.f == x`, so `git diff H1 H2` omits `f`, yet the second merge holds `x` where the first held `y`. A job whose input is `f` is reused on a tree it never tested. Change: compute the reuse diff as `diff(H1, H2) ∪ (P1 △ P2)`, where `P2` is this run's `changed.txt` (`ci.yml:175`) and `P1` is the earlier run's `changed.txt`, stored in the record. A path in neither `P1` nor `P2` equals the base in both merges, so the union covers every clean-merge difference. Add a `ci-reuse.test.ts` row for this case. Name the residual (a three-way textual merge of one file under two merge bases) in *What reuse cannot see*.
2. **The selection rule can change while no selecting path does.** `CLAUDE.md` holds the `Local checks` key that `ciSelection` reads. It is markdown outside `skills/`, so the job map drops it from `$wide` (`ci.yml:203`), and a head diff that edits only `CLAUDE.md` selects no job. The earlier `helper-contracts` ran only the subset `contracts_tests` named then (`ci.yml:213`). A push that adds a `Local checks` row for an already-changed path makes this run's selection name more tests, and reuse skips them silently; the same holds for `corpus_tests`. Change: reuse a job only when the earlier run's recorded selection for that job (`contracts_tests`, `corpus_tests`, and the job's flag) equals this run's selection. The plan already writes the selection into the record; make `ciReuse` compare it, and add a test row.
3. **With `ci-cancels-superseded-runs`, the cancelled-run refusal disables reuse where it pays.** Measured on run 42605350975: `validate` ended at 11:15:59, and the run completed only at 11:24:52, after `census-compare`. Under a per-PR group, any push in that nine-minute census tail cancels a run whose required jobs all ended `success`, and the plan then refuses every job of it. Sprint branch history shows the push rate: 7 of the 10 newest `pull_request` runs on `sprint/the-board-reads-the-channel` ended `cancelled`. This is not a wrong answer, but it misses the motivation's target on the sprint PR. Change: judge per job, as the third Open Question already does for `failure`; a job that ended `success` is a source whatever the run's conclusion. Keep the run's `completed` status out of the rule for the same reason, or state why it stays.
4. **No `validate` loosening found.** `validate` needs `gates` and requires it `success` (`ci.yml:2613`, `:2669`), so a reusable job skipped because `gates` failed still fails the run. The `^reused:[0-9a-f]{40}$` match and the `if:` guard `reuse_<key> == ''` fail open when `select` fails, because a failed job's outputs are empty. Add one row: `skipped` with a reuse value passes only while `gates` ended `success`, to hold that order in the test and not only in the current `needs:`.
5. **A forged or stale `reused:<sha>`.** The value comes only from `select`'s output, and a pull request's own `ci.yml` already controls every job in its run, so a forged record adds no new trust boundary. A head that changed `ci.yml` and reverted it re-runs everything, because `ci.yml` is not markdown and widens the map. Staleness is bounded by the 20-run window and 7-day retention; both fail closed (no source).
6. **Concurrent push.** A run still in progress is no source, and `select` pins its tree by `github.sha`, so a push during the read cannot change what this run tests. No race found that yields a wrong reuse.

## The change that matters most

Finding 1: diff `H1..H2` plus the symmetric difference of the two runs' recorded changed-path lists, not `H1..H2` alone. Without it, the plan's one safety claim ("the rule leaves one input to compare: the head diff") is false for any branch that merges or rebases on an unchanged base, and the miss is silent until the run on `main`.

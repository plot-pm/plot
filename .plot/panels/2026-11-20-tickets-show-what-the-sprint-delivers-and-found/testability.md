## Findings

1. **The domain rule's main input does not reach the client, so its unit tests can pass while the shipped board shows no titles.** The plan says an open delivered ticket "shows its title from the index" (plan:33) and the rule takes "the issue rows" (plan:37). The Delivery tab's only issue rows are `FleetResponse.issues`, documented as "Open tracker issues no plan references" (`packages/board/src/contract/schema.ts:4768-4777`). The server builds them with `inboxOf`, which drops every key a plan's `Issue:` names and caps the rest at `ISSUE_LIMIT = 50` (`packages/board/src/server/fleet.ts:2170-2172`, `:257`, called at `:2454`). The client narrows them again to `waitingBlock.tickets` (`AgentList.tsx:867`, `:1251`). So every ticket a scope plan names is absent by construction, and every Delivered row renders key-only. A unit test that feeds a planned ticket into the rule's issue rows proves a state production never reaches. The reverse claim also fails: the server does hold the open and closed rows unfiltered in `entry.issueSets` (`fleet.ts:932-939`), and `ticketLaneData` already serves both to the Discovery tab (`fleet.ts:1964-1985`), so "no payload holds closed tickets" is not the whole picture. RAN (grep + sed over the files). **Change:** add to *Design › Approach* a bullet naming the payload the rule reads: either a new `FleetResponse` field built server-side from `entry.issueSets.rows` (and `closed.rows`) restricted to the scope plans' `Issue:` keys and the finding titles, with a schema default, or an explicit statement that Delivered rows are key-only by design. Add a server test (`packages/board/test/unit/…`) that asserts a ticket a plan names reaches the payload with its title, so the domain test is not the only proof. Correct the Open Questions so the operator decides with the real data path in view.

2. **The plan does not decide whether a finding also stays in the "no plan" group, so no test can pin it.** `ticketPlansOver` keys only `meta.issues`, the `Issue:` field (`fleet.ts:1811-1836`). A review-finding issue or a refuted-claim issue is named by no `Issue:` line, so `inboxOf` keeps it as unplanned and `splitTicketRows` lists it today (`packages/board/src/app/lib/agent-rows/waiting-view.ts:122-139`). After this plan the same ticket shows in *no plan* and in *Found during the sprint*. The listed unit tests (plan:37) cover "delivered and a finding" but not "a finding and unplanned". RAN. **Change:** state in *Approach* which group a finding belongs to when it is also unplanned (one group or both), put that decision in the association rule, and add the case to the rule's unit-test list.

3. **The plan's state text has no named owner.** The row shows "Approved · 2 of 3 slices merged" (plan:16, :33), but the rule in plan:37 answers only group, plan or PR, and kind. The words already exist twice: `sliceProgress`-style text in `packages/domain/src/rules/deliverable.ts:366-392` ("M of N slices merged"), and `TicketPlan {state, total, merged}` built server-side in `fleet.ts:1825-1832`. Without a named function, the builder composes the text in `TicketsSection.tsx`, which CLAUDE.md's *Every rendered state is a domain property* forbids. RAN. **Change:** name the function that produces the state word and progress (extend or reuse `deliverable.ts:366`), make it an output field of the association rule, and list its cases (Approved with progress, Released, Delivered, unread pulse with `merged: null`) among the unit tests.

4. **The count-gate sentence describes the wrong move.** Plan:44 says "Moving assertions into unit tests updates `stubbed-tests-start-no-board.test.ts`". This plan moves nothing; it adds groups that a browser test must prove are seen. The gate pins `EXPECTED_FILES = 99` and `EXPECTED_TESTS = 719` (`packages/board/test/integration/stubbed-tests-start-no-board.test.ts:569`, `:956`), and every earlier addition is logged there as "A PLAIN ADDITION" with the file and `it(` count (`:375-400`). The natural home is `packages/board/test/integration/tickets-section.browser.test.ts` (six `it(` today), whose fixtures come from `packages/board/test/catalogue/index.ts`. RAN. **Change:** replace plan:44 with: "One browser test, in `tickets-section.browser.test.ts`, proves both groups render folded with their label and `— none` when empty; it raises `EXPECTED_TESTS` by its `it(` count as a plain addition, served from a catalogue state with scope cards, PRs and finding issues, and starts no board."

5. **Refuted-claim ids are read only for Delivered plans, and the plan claims more.** The server reads plan text for refuted claims only where `meta.phase === 'delivered'` (`packages/board/src/server/board.ts:2528-2535`, `:3038-3048`). A Released scope plan carries its `## Verification` record but no refuted ids would reach the card. The plan says "over the plan file it already reads" (plan:40) without naming that limit. RAN. **Change:** state which phases carry the new card field, and add a server test that a Delivered plan with one `Claim-1 refuted — … — #1712` line yields `["1712"]` and a plan with no section yields `[]` (the schema default).

6. **The slice bundles four independently testable parts.** One branch carries the server card field, the domain rule, the view groups and the summary chips (plan:55). The card field and its server test can merge alone with no UI change and no waits; the rule can merge alone with unit tests. As one PR, the reviewer proves the payload, the rule and the render together. READ. **Change (optional):** split into `feature/refuted-issues-on-the-card` (no waits) and the existing slice, which then waits on it too.

7. **Mine has no named rule for "its plan is mine".** Plan:38 extends ownership to "assigned to the reader or its plan is the reader's". Ticket ownership today is `ownedTicket`/`ownership`/`isMineStrict` over assignees (`packages/domain/src/rules/ownership.ts:225`, `:298`, `:326`). The plan names no function that joins a ticket to its plan's owner, so it risks a filter in `AgentList.tsx`. RAN. **Change:** name the rule that answers it and add "assigned to another, plan mine → mine" and "assigned to me, plan another's → mine" to the unit-test list.

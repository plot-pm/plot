## Findings

1. **The client holds no issue index, so "open shows its title, closed shows its key" cannot be decided from what the payload carries.** The plan (lines 33, 34) says a ticket "the issue index carries" shows its title and one it does not carry is closed. The client receives two row sets, and neither is the index. `Fleet.issues` holds only open issues **no plan references**, cut to 50: `inboxOf` filters out every referenced key and slices to `ISSUE_LIMIT` (`packages/board/src/server/fleet.ts:2170-2173`, schema doc `packages/board/src/contract/schema.ts:4770-4777`). So a ticket a scope plan names is never in `Fleet.issues` by construction. `Fleet.waiting.tickets` carries planned tickets, but only the reader's own selection: `waitingTickets` keeps rows `ownership` answers `mine` for, hides unassigned ones, drops rows whose plans are all released, and cuts to 50 (`packages/domain/src/rules/waiting-tickets.ts:141-198`). Result as written: an open ticket of a scope plan that is assigned to someone else, or to nobody, renders as "closed" (key and plan only), and every Released plan's ticket is absent from both sets. Read and opened code. **Change:** the plan must name the row set the rule reads and what a missing row means. Either (a) add the scope's ticket rows (open and closed) to the payload from `entry.issueSets` server-side, or (b) state that absence means "not in the reader's rows", not "closed", and word the row accordingly. Option (a) is a new payload field over a source the server already reads (`entry.issueSets.rows`, `fleet.ts:2433-2442`).

2. **"No payload holds closed tickets" is false in this repository.** `ticketLaneData` serves the Discovery tab the open rows and the closed rows of the last `ISSUE_INDEX_CLOSED_DAYS` days from the same cache entry (`packages/board/src/server/fleet.ts:1963-1986`), and `GET /api/issues/closed` answers up to 1000 closed issues (`fleet.ts:2006-2090`, route `packages/board/src/server/index.ts:568`). The spec repeats the same premise (spec line 104), so this is a spec error the plan inherits. Read and opened code. **Change:** delete the sentence "because no payload holds closed tickets (no new data source)" and decide whether closed scope tickets read their title from `entry.issueSets.closed` (server-side, no new tracker call) or show key only by choice.

3. **"Found during the sprint" reads from a row set that hides the findings.** fleetd opens review finding issues with a title and a label and no assignee (`packages/fleet/src/shared/auto-ticket.ts:112-116`). `waitingTickets` hides unassigned rows for a matched reader (`waiting-tickets.ts:105-112`, `:194-197`), and the Tickets section reads `waitingView(fleet.waiting, fleet.issues, …)`, which prefers `fleet.waiting` (`packages/board/src/app/components/AgentList.tsx:855-867`). Such a finding is present only in `Fleet.issues`, and there only if it is among the first 50 inbox rows, with no completeness flag. Read and opened code. **Change:** name the row set for findings (`Fleet.issues`, or a server-side list over `entry.issueSets.rows`), add a unit test for a finding beyond the 50-row cut, and state how the count reads when the read is incomplete (`complete` exists on `IssueSets`, `fleet.ts:2433-2442`).

4. **The plan's state label duplicates an existing domain rule.** The plan's example "Approved · 2 of 3 slices merged" (lines 16, 33) is a new wording. `ticketPhase` (`packages/domain/src/rules/ticket-phase.ts:32-66`) already derives a ticket's plan state from its `Issue:` plans, including merged/total counts (`in progress 2/3`), and `waitingTickets` already uses it for planned tickets (`waiting-tickets.ts:165-169`). The server also already builds the `TicketPlan` map per ticket (`ticketPlansOf`, `fleet.ts:2445`). Read and opened code. **Change:** reuse `ticketPhase` and `TicketPlan` for the state cell, or state why a second label vocabulary is needed.

5. **A review finding is also a "no plan" ticket, and the plan does not say where it appears.** No plan names a finding issue in `Issue:`, so `inboxOf` and `splitTicketRows` (`packages/board/src/app/lib/agent-rows/waiting-view.ts:122-137`) put it into today's "no plan" group too. The plan's unit-test list covers "both delivered and a finding" (line 37) but not "both no plan and a finding". Read and opened code. **Change:** state whether a finding leaves the no-plan group or shows in both, and add that case to the rule's tests; the no-plan header count (`tickets-section.ts:63`) changes if it leaves.

6. **Refuted-claim ids exist only on Delivered cards.** The server reads the plan text for verification only from `reads.delivered` (`packages/board/src/server/board.ts:3038-3048`), so the new card field is filled for plans with a readable delivery commit and defaults to empty otherwise. That matches where refuted claims are written, but the plan says "over the plan file it already reads" without the condition. Read and opened code. **Change:** say the field is filled where `card.verification` is, and default `[]` elsewhere.

## Findings

1. **`ticketPhase` reads `TicketPlan` records that the client does not receive, so its unit cases can pass while production has no input.** Plan:44 makes the state cell `ticketPhase` "over the ticket's `TicketPlan` records (built per ticket by `ticketPlansOver`)". `ticketPlansOver` is a server function (`packages/board/src/server/fleet.ts:1811-1836`), and its output reaches only server-side callers: `waitingTickets` (`fleet.ts:2255`) and the Discovery lanes (`fleet.ts:1943`, `discovery-lanes.ts:42`). No board app file imports `TicketPlan` or `ticketPhase` (grep over `packages/board/src/app`: zero hits). `scopeTickets`' stated inputs (plan:49) are the cards' `issues`, `prs`, `refutedIssues` and phase, plus `planTicketRows`; a card carries `sliceSummary` with `slices`, `branches`, `claimed`, `eligible`, `deferred` and no merged count (`schema.ts:292-299`, `:607`). So "in progress 2/3" has no source on the client, and a unit test that hand-builds `TicketPlan {merged: 2, total: 3}` proves a state the client never reaches. RAN (grep, sed). **Change:** in plan:37, add to `planTicketRows` (or a sibling payload field) the `TicketPlan[]` per row key from `ticketPlansOver`, and extend the slice-1 server test to assert that a named ticket of an Approved plan with one of two slices merged carries `{state: 'approved', total: 2, merged: 1}`; in plan:49, add `TicketPlan` records to `scopeTickets`' input list. Alternatively state the client-side derivation and its source field, with a test.
2. **The "no plan" header's unassigned count is a server number that still counts the findings.** Plan:48 says the "no plan" group "and its header count (`tickets-section.ts:63`) exclude" the finding keys. The header's `N more unassigned` is `input.unassigned` (`tickets-section.ts:62`), which `AgentList.tsx:1797` passes as `fleet.waiting?.unassigned`, computed server-side in `waitingTickets` over every hidden open row with no assignee (`waiting-tickets.ts:176-179`). fleetd opens review findings with no assignee (`auto-ticket.ts:112-116`), so each one is in that count, and the client cannot subtract a key it does not know was counted. `hidden` (`AgentList.tsx:1798`) has the same shape. RAN. **Change:** in plan:48, name where the exclusion happens for the counts: either `waitingTickets` takes the finding keys server-side (then slice 1 owns it and its server test), or the server ships the unassigned keys so the client rule subtracts them. Add a unit case "an unassigned review finding is not in `N more unassigned`".
3. **The fold-key sentence names a list that cannot be joined, and misses the test that pins the default.** Plan:42 says the keys "join `KNOWN_KEYS` and `COLLAPSED_BY_DEFAULT` (`collapse.ts:6,17`)". `KNOWN_KEYS` is derived from `DELIVERY_LAYOUT` (`collapse.ts:6`, `delivery-placement.ts:12-18`), which has no Tickets entry; plan 2 adds its `tickets` key the same way (`every-delivery-section-folds.md:44`) without naming the mechanism either. `agent-list.test.ts:1384` pins `COLLAPSED_BY_DEFAULT` to `['free']`, which plan 2 changes to `['free', 'not-placed']`. RAN. **Change:** state in plan:42 that the two keys enter `KNOWN_KEYS` by the same mechanism plan 2 uses for `tickets`, and that `agent-list.test.ts:1384` gains `tickets-delivered` and `tickets-found` in the expected default.
4. **The server's review-finding filter names a function that builds one title, not a predicate.** Plan:37 keeps a row "whose title is a review-finding title (`reviewIssueTitle`, `review-issue.ts:20`)". `reviewIssueTitle(pr)` returns one exact string for one PR; the server, which has no scope at that point, needs a prefix-and-suffix test over any PR number, the shape `findOpenReviewIssue` uses (`review-issue.ts:33-34`). Without a named predicate the builder writes a regex in `fleet.ts` with no unit test. READ and OPENED. **Change:** name a domain predicate (for example `isReviewIssueTitle(title)` beside `findOpenReviewIssue`) with unit cases `PR #1` versus `PR #12` and a `plot-review:` title of another form, and have plan:37 use it.

# The contradiction lens — a fresh agent after a wait

## What I looked at

I read code and docs, and I ran read-only commands: `gh issue view` for #1950, #1903, #1917 and #1273 (state, close reason, comments), `git log -S` over the parser and the plan-store adapter, and `bash skills/plot/scripts/plot-plan-meta.sh docs/plans/2026-10-04-the-worker-loop-runs-in-js.md` (the plan #1273 measured). I ran no test suite. Everything below is on the worktree `jury-1954` (origin/main plus the plan, a26254dfc).

## 1. Is each slice's problem real on current code?

**#1273, part 1 (branch-line `waits:`) — not shown to be real today, and the plan states it as present fact.** Motivation (plan:27) says "the registry's plan reading carried no `waitsOn` for a `waits:` written on the branch bullet line". On current code the chain reads it end to end:

- `plot-plan-meta.sh` on the measured plan emits `'waits_on': ['infra/the-shell-loop-holds-unlanded-work']` for `infra/the-loop-has-a-workflow`, `unread_waits: []` (command output).
- `plan-store-shell.ts:74-78` (`branchOf`) maps `waits_on`, list or bare string, to `waitsOn`; the registry reads plans through `planStoreShell` (`registryd-main.ts:475`, `:732`, `:1908`).
- `queue.ts:849-873` (`planQueue`) turns every `waitsOn` into a `waitHeld` hold.

The parser change that made `waits_on` a list, #1265 (`8e5fe3e18`, 2026-10-04 00:15), landed the day of the first measurement; the "BOTH SHAPES ARE ACCEPTED" tolerance in `branchOf` came in the same commit. The 2026-10-04 23:04 and 2026-10-05 08:19 hand-overs may come from a daemon that ran an older bundle (the board and fleetd do not reload bundles), not from a reading defect. The plan's Design (plan:35) says "Find where the registry's plan reading builds `waitsOn`", which is the right first step, but the Motivation and Changelog already assume the answer. That is the plan's main internal contradiction for this slice.

**#1273, part 2 (slice 2 held only on `no-brief`) — likely not a hand-over defect.** `planQueue` sets `claimable` from `sliceVerdicts` (`queue.ts:823-840`; `eligible.ts:157-163`), which blocks every slice after an incomplete one. Slice 2 was held, not handed. Which word names the hold is `whyNotReady`'s precedence (`queue.ts:442-475`). The issue's "the registry lists neither slice 1 under any held reason" fits `planQueue`'s `claimed.has(line.branch)` skip (`queue.ts:847`): a released claim with a surviving ref is still out of the queue. The plan's Open Question (plan:46) asks the right thing. The slice line (plan:52), "never treats a later slice as next while an earlier one is unmerged", promises a behaviour that `sliceVerdicts` already enforces.

**#1917 — plausible on current code, and the plan's description matches it.** `agentLoop` ROW 2 (`agent-loop.ts:473-484`) exits 124 with no ending. Its own comment, "No slice was ever held", conflicts with the issue's premise that the desk still has the last slice's branch checked out. That conflict is the defect in small, and the plan does not mention it. `killedWorkerEnding` (`ending-action.ts:552-563`) fires on any non-zero exit with a branch. `freshAgentCandidateTrees` (`registryd.ts:639-642`) admits a desk that is unregistered and plan-named, and an agent whose exit trap removed its manifest fits that description. So `endingAction`'s `bound`/`unreadable`/`quiet` row decides for a slice this desk no longer worked. Not reproduced, as the plan says.

**#1903 — the plan treats as open and unbuilt something the code and a DESIGN doc already describe.** `assign` (`workflows/assign.ts:170-178`) emits `worker-start` writes through `scaleUp` (`:211-240`) when a ready slice is held on `no-free-agent`. At `agents=0`, `matchQueue` holds every ready slice on `no-free-agent` (`queue.ts:668-679`). `DESIGN-agent-first-class.md:64` states: "`--start-agents` is opt-in on the daemon and starts free agents toward the board's `Parallel agents` cap … So the supervisor already starts agents from a queue it cannot staff." `registryd-main.ts` is `plot-fleetd.mjs` (`:148`, `:175`). The plan never names `assign`, `scaleUp` or `--start-agents`. So the real #1903 question is why the observed fleet stayed at 0 with this machinery present. Possible causes: the flag was off, the slices were held on `no-brief`/`not-claimable`, or a stale registration counted as running (`assign.ts:229`). The question is not whether to build a start.

## 2. Is each proposed change in the right layer?

- Slice 1: the Design lists `plan-store-shell.ts` (adapter), `rules/queue.ts` and `rules/eligible.ts` (domain). If a defect remains, it is in the adapter mapping or the bundle the daemon runs. A domain-rule change is not indicated, because `planQueue` already holds on every `waitsOn`.
- Slice 2: "The fix lives in the domain rule; the controller only passes readings" (plan:36) fits the layering rule. The claim-owner reading has to be a value in `KilledWorkerReadings` or `FreshAgentCandidateReadings`, which `registryd.ts` builds. No reading today says which agent a claim names: `KilledWorkerReadings` (`ending-action.ts:521-530`) carries ending, exit, loopAlive and branch only. The plan has to name the source, for example the claim ref's tip commit or the desk's last manifest. It has to state whether that source is an index read or a fresh remote read, and what an unanswerable read does. The `dirtyTreeReading` precedent (`registryd.ts:787`) says a failed read must never reach `release-claim`.
- Slice 3: the change belongs in `assign`/`scaleUp` (domain workflow), which reads `QueueReadings` as values. That location is right. It is not "fleetd" in the sense of a new controller path. The condition "approved, startable slices are waiting" matches `no-free-agent` (ready: approved, claimable, briefed, not held). The plan should say so instead of introducing a new predicate. Under "A decision reads the index", the start decision must come from the tick's queue reading and not from a fresh host call, and `assign` already works that way.

## 3. What is missing, wrong or contradicted

1. **Ordering contradiction (Design vs Slices vs DESIGN-slice).** Design (plan:33) says "The slices … have no ordering between them". The plan still writes three `###` headings. `DESIGN-slice.md:49` says "a slice may not start until every prior slice has landed", and `:492`/`:514` say the ordering is document order. `sliceVerdicts` enforces it. As written, #1917 cannot start until #1273 lands, and #1903 waits behind both. Independent work belongs under one heading as one wave of branches, or the plan must accept the order.
2. **Terminology collision: "fresh agent".** The title and #1903 use "a fresh agent" for a new free agent with no slice. The code already uses "fresh" for something else: `freshAgentCandidateTrees`, `FreshAgentCandidateReadings`, `readFreshAgentCandidates` (`registryd.ts:620-830`) and `endingAction`'s `start-fresh` (`ending-action.ts:117`, `:137`) all mean a fresh session on an ended desk's slice. That is the very arm #1917 is about. One plan that uses the word both ways in adjacent slices invites the implementer to change the wrong path. The DESIGN vocabulary for the #1903 case is "starts free agents" (`DESIGN-agent-first-class.md:64`) and `worker-start` with `branch: ''` (`assign.ts:178`).
3. **#1903 vs the settled decision.** Design item 3 (plan:37), Open Question 1 (plan:43) and the Changelog's third clause (plan:17, "the plan records whether fleetd starts…") all leave the decision open. The Open Question's argument, "a fresh agent has nothing new to take until the registry assigns something", contradicts the decision's own condition: startable slices are waiting, so there is something to assign. The slice line "implemented if the answer is to start" (plan:60) is conditional work, and a slice that may ship nothing does not fit the definition "one branch's worth of a plan's work".
4. **"One fresh agent" vs `scaleUp`'s request.** The decision says "one fresh free agent … bounded by the configured fleet size". `scaleUp` requests `fleet.size` and not the waiting count ("THE REQUEST IS THE CAP, NOT THE QUEUE", `assign.ts:200-203`, `:232`), so one waiting slice at `agents=0` can start up to the full cap. The plan must say which it means and test it. The plan's "configured fleet size" and the DESIGN doc's "the board's `Parallel agents` cap" also need to name one key.
5. **Changelog does not state behaviour.** CLAUDE.md "Text that persists → State current behaviour" rules out "the plan records whether …". The Changelog also states the #1273 effect as a fix, while the plan has not shown a defect on current code.
6. **No done-when per slice.** Slice 2 starts with "reproduce first" and Slice 1 with "find where", but no slice says what proves it done. A slice that finds no defect needs a stated outcome, such as "a test pins the branch-line shape through `planStoreShell` → `planQueue` and the slice closes with that test only".
7. **Motivation/Issue status.** #1903, #1917 and #1273 are closed as NOT_PLANNED ("Folded into #1950"). That is consistent, but the `Issue:` field lists them as if open. A reader of the field cannot tell that only #1950 tracks the work. This is a minor point.
8. **Board-impact note.** "No change to … helper scripts" (plan:19) holds only if Slice 1 changes nothing in `plot-plan-meta.sh`. The current parser already reads the line, so the note is probably true, but it is stated before the measurement that decides it.

## 5. Position

Amend. The plan's three findings point at real code areas, and the layering it prescribes is right. Its account of current code contradicts the code, the DESIGN docs and itself in four places. Slice 1's defect is stated as present while the parser, the adapter and `planQueue` read a branch-line wait today. Slice 3 is framed as unbuilt while `assign`/`scaleUp` and `DESIGN-agent-first-class.md:64` already start free agents at `agents=0`. "No ordering" sits beside three ordered headings. "Fresh agent" names two different things. Each point is fixable by editing the text, and none argues against the plan's direction.

Every issue without a marked comment gets a new comment and a notification to its watchers. The written-hash file is local to one machine, so a re-run on a second machine writes everything again. The #2924 login filter at `plot-host.sh:700` makes a second account post a second comment. The #2935 lock release (`tracker-plan-state.ts:114-156`) applies to every one of these writes.

5. **medium: the In-progress lane ignores the plan phase, and the plan's gap 1 fix keeps that.** `ticketLane` (`packages/domain/src/rules/ticket-lane.ts:52`) returns `in-progress` for any open issue that a plan names. `referencedIssues` (`fleet.ts:1558`) collects every plan's `Issue:`, plus open draft plans from idea branches (`draftPlanFiles`, `fleet.ts:1676`), with no phase. So an issue of a Draft plan, or of a Delivered plan whose issue stays open until the release, reads *In progress*. Required behaviour 1 says "while the plan is started and not delivered". Today 13 open issues carry `plan:delivered` (#2898-#2907, #2970, #2974, #2978). Each is named by a Delivered plan, so each reads In progress. A source switch alone fixes the stale-checkout half and leaves this false lane.
6. **medium: "consume the plan walk's resolved set" can drop released plans and send their issues back to *Open*.** The comment on `referencedIssues` (`fleet.ts:1540-1547`) refuses `pulse.plans` on purpose: the pulse holds the release scope, and a released plan dropped from it "puts the issue back on the board". The walk of `the-plan-walk-moves-into-the` feeds the pulse. If gap 1 reads the walk's output instead of every plan on the default-branch ref, the 342 released-plan issues lose their reference. The plan must name which set it reads.
7. **medium: a standing backfill can close an issue that another plan or a person still owns.** The released write closes the issue on every call (`tracker-plan-state.ts:219-227`), and it removes every other `plan:*` label (`planStateLabelsToRemove`, `:29`). An issue can be named by more than one plan: #333 and #912 are each named by a Released and a Rejected plan today. If a later Draft, Approved or Delivered plan names a released plan's issue, or a person reopens the issue because the defect came back, a level-triggered backfill closes it again and removes `plan:approved` on each pass. No such case exists today, but the plan's Open Question 2 offers a standing writer, which turns a one-time risk into a loop.
8. **medium: no gap 2 or gap 3 write refuses an unattended caller.** `packages/board/src/server/entry/plan-state.ts` has no `PLOT_UNATTENDED` check (`grep -n UNATTENDED` gives nothing). `skills/plot-reconcile/` is read-only by contract ("prints the commands and runs none"), so a reconcile section that writes would break that skill. A bulk loop of `plot-host.sh issue-label` calls would bypass the plan-state controller. CLAUDE.md, "The Master Agent Uses The Controllers", forbids that.
9. **medium: "says why it stays open" has no idempotence rule.** If a level-triggered closer comments each time a ticket stays open, it comments on every pass. 196 open tickets at one comment per beat floods the tracker. The plan must name one marked comment, edited in place and written only when its text changes, as the writer already does for the plan comment.
10. **low: gap 5's direction "a newer index answer replaces an older one" by `updatedAt` can still show the wrong head.** `PrIndexRow` (`packages/domain/src/entities/pr-index.ts:60-79`) carries `headSha` and `checksSha`, and `checksSha` binds `checks` to a commit. `updatedAt` moves on comments and labels, not only on pushes. The safe rule is that a row says "checks failing" only where `checksSha === headSha`. Where `checksSha` is absent (Jenkins, Bitbucket), the row keeps today's reading instead of hiding a real failure. The row placement is a view and decides no lifecycle action, so reading an OPEN row here stays inside "A Decision Reads The Index".
11. **low: line citations mostly hold.** `referencedIssues` is at `fleet.ts:1558`, `stuck.ts:303` is `ci-failing`, and `prEvidence` is at `fleet.ts:3618`. `ticketLanes` is at `ticket-lanes.ts:184`, not `:149`. The `namedByPlan` call is at `:157`.

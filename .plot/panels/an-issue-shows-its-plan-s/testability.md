# Testability verdict: an-issue-shows-its-plan-s

Position: amend

Through the testability lens, the plan names five real gaps and five required behaviours, but it names no test and no fixture for any of them, and three of its premises are measured false or incomplete on `origin/main` today. Gap 1 and gap 5 can each be proven by a domain unit test with no browser and no host, but only after the plan names the missing domain seam: `PlanRecord` carries no `issues` field, and `prRowPlacement` reads no head sha. Gap 2's count is wrong (114, not 38), and the drift still grows after the release write exists, so a one-off backfill has no test that can fail after it runs. Gap 3 describes a ticket writer that stopped on 2026-10-29. Two Changelog clauses ("says why not", "within one PR index refresh") are not testable as written. The plan is worth keeping; it needs an Approach with a test table before approval.

## Findings

1. **high — gap 1 has no domain seam to test against: the plan walk does not carry issue numbers.** `packages/domain/src/ports/plan-store.ts:10-63` (`PlanRecord`) has no `issues` field, although `plot-plan-meta.sh:261` emits one and the board's `PlanMetaSchema` (`packages/board/src/contract/schema.ts:132`) reads it. `git grep -i issue` over `packages/domain/src/workflows/plan-walk*.ts` and `rules/plan-walk-estate.ts` returns zero lines. So "`referencedIssues` consumes the walk's resolved plan set" (Approach) is not a wiring change: `PlanRecord` must gain `issues`, and the corpus reader `packages/domain/corpus/production.ts:403` (`readEstatePlanMeta`) must carry it. The proof is a unit test on `readEstate` (`packages/domain/src/workflows/plan-walk-estate.ts:65`) with a fake `Refs` whose `origin/main` lists a plan blob naming `#N` and a worktree `PlanStore` that holds no such file. Old code: no issue reaches the estate. New code: `#N` is in the named set. `ticketLanes` (`ticket-lanes.ts:184`) already takes `named` as a value, so a test on `ticketLanes` alone cannot make old and new code disagree; the disagreement lives in the reader. Checked by reading the files at `origin/main`.

2. **high — gap 1 has three consumers, and the plan names one.** `referencedIssues` exists twice: `packages/board/src/server/fleet.ts:1558` (Stories lanes via `ticketLaneData` at `:1728`, and the inbox filter of unplanned issues) and `packages/board/src/server/idea.ts:401` (the precondition that refuses a second `/plot-idea` for a planned issue). Both read `fs.readdirSync` of the checkout's plan directory. A plan merged to `origin/main` and absent from a stale checkout therefore also shows its issue in *Waiting on you* as unplanned and lets a second `/plot-idea` start. One fixture (a git sandbox whose `origin/main` is one commit ahead of the checked-out tree, the new commit adding a plan naming `#N`) proves all three; the plan must list all three as test subjects, or the fix moves one surface and leaves two.

3. **high — required behaviour 5 has no failing fixture until the stale read is named, and Open Question 5 admits that.** `prRowPlacement` (`packages/domain/src/rules/pr-row.ts:38`) reads only `{ mergeable, checks }`; no head sha and no `updatedAt` reach it, so "a row reads the checks of the PR's current head" has no domain property to assert today. The index already refuses to carry a colour across a head move (`carriedChecks`, `packages/domain/src/rules/pr-index.ts:528`, tested at `packages/domain/test/pr-index.test.ts:981-1024`), and the board's store path re-reads the index on its own PR timer (`readPrsFromStore`, `fleet.ts:2495-2506`). A second checks reading exists: the scan parses `"checks"` from its carried listing (`skills/plot/scripts/plot-fleet-scan.sh:1180`). The 7-minute lag (13:03 to about 13:10) fits neither source on its own without a measurement. The fixture that makes old and new disagree is the issue's own: reading A `{ headSha: dc98f4a02, checks: failing, updatedAt: 12:44 }`, reading B `{ headSha: 75da18f94, checks: pending, updatedAt: 13:02:59 }`; old code places the row in *Waiting on you*, new code places it in *Working*. The reverse fixture (B older than A) must keep A, or the rule is "the index always wins", which Open Question 5 leaves open.

4. **high — gap 2's count is 114, not 38, and the drift continues after the release write exists.** Method: every `docs/plans/*.md` on `origin/main` whose `State:` starts with `Released`, every `#N` on its `Issue:` line (342 issues), joined against `gh issue list --state all --limit 3000 --json number,state,labels` (1077 issues). 114 of the 342 lack `plan:released`; all 114 are closed. Three of them (#2697, #2705, #2714) belong to `docs/plans/2026-10-27-the-reaper-keeps-leftovers-that-no.md` (`Released: 2026-10-28, v2.29.0`), whose first issue #2757 does carry `plan:released`. #2697 was closed 2026-10-28T11:07Z and carries no `plan:*` label at all. So the cause list in the Motivation ("released before the release write existed, or outside `/plot-release`") is incomplete: a release made by the release write left three of four issues unlabelled. A one-off migration over a fixed list cannot be proven by a test that fails later, and it would be re-broken by the next such release. The proof needs a fixture with `Issue: #A, #B, #C`, #B closed before the release, run through the release write; the test asserts all three carry `plan:released`. Caveat: my count may differ from the plan's 38 by method; the plan must state its query.

5. **medium — gap 3 describes a writer that no longer opens tickets.** `reviewIssue` (`packages/domain/src/rules/review-issue.ts:20`) answers `none` for every count since commit `7f277875e` (2026-10-29, "plot-review: a review opens no follow-up issue"). Follow-up tickets are now opened by `packages/fleet/src/shared/auto-ticket.ts:113` (after the fixer's attempts on a HIGH fail, #2903). `gh issue list --search "plot-review: findings on PR in:title"` returns 196 open and 4 closed; the newest was created 2026-10-29T23:03Z. So the closure rule has two populations with different meanings: 196 legacy tickets with any finding, and auto-tickets for an unfixed HIGH. One test per population is needed, and "settled" must be a function of readings the index already holds (`plotReview`, `plotReviewSha` on the merged row) or it has no fixture.

6. **medium — gap 4's acceptance is a ticket state, and gap 3 can change that state.** #2935 and #2924 are themselves `plot-review: findings on PR …` tickets (verified with `gh issue view`). If gap 3 ships a closure rule, it can close them; "done when #2935 and #2924 close" then proves nothing about required behaviour 4. The marked-comment lookup is jq inside shell (`skills/plot/scripts/plot-host.sh:700`, `gh_marker_comment_id`; the issue cites `:691`, which is its comment block), so its only proof is a `test/reconcile` contract test with a `gh` stub: a marked comment by login X, current login Y, one write, and the test asserts one comment edited and zero created. `withIssueLock` (`packages/domain/src/adapters/tracker/tracker-plan-state.ts:127`) is an adapter; its proof is `packages/domain/test/tracker-plan-state.test.ts` with a lock file held by a live foreign pid. Neither test exists for these two defects today (`git grep -n "login\|lock"` over that test file returns nothing).

7. **medium — required behaviour 1 says "started and not delivered", and today's rule says "any plan names it".** `ticketLane` (`packages/domain/src/rules/ticket-lane.ts:53`) returns `in-progress` for an open issue whenever `namedByPlan` is true, whatever the plan's phase, and the `fleet.ts:1538-1547` comment keeps released plans in the set on purpose. A Draft plan naming an open issue is *In progress* today; under the required behaviour's wording it is not. The plan must say which, because the fixture "Draft plan on an idea branch names `#N`" gives opposite answers under the two readings, and moving the reader to the estate (which reads prefix branches, `plan-walk-estate.ts:78`) keeps idea-branch drafts in the set.

8. **low — two Changelog clauses have no test that can fail.** "or says why not" (gap 3) names no text, field or condition, so no assertion exists. "within one PR index refresh" is wall-clock; a unit test can only assert "on the next board PR read after the index row changes", which is what the clause must say. The Changelog also states nothing for required behaviour 4, which is correct only if gap 4 is tracked rather than built (see Open questions).

9. **low — cited line numbers hold.** `approve.ts:1177`, `deliver.ts:546` and `:969`, `auto-progress.ts:39`, `ticket-lanes.ts:149`, `fleet.ts:1558`, `stuck.ts:303` each point at the code the plan names (read with `git show origin/main:<path> | sed -n`).

## Open questions

- Gap 1 (walk set directly, or a shared client-side index): read the estate directly on the server, through `PlanRecord.issues`. A client-side index cannot feed the `/plot-idea` precondition, which runs on the server, and only the server path has a no-browser test.
- Gap 2 (one-off or standing): standing. The measured drift includes a release on 2026-10-28, after the release write existed, so a one-off list goes stale and has no test that fails afterwards.
- Gap 3 (what is "settled"): a re-review reading on the merged PR's final head, from index fields (`plotReview` success with `plotReviewSha` equal to the merged head). A person marking findings fixed has no recorded field to test against.
- Gap 5 (which read is stale; newest by `updatedAt` or always the index): measure first (A3). Then choose by head sha first and `updatedAt` second: a reading for a head the PR no longer carries never wins, whichever source it came from. "Always the index" fails the reverse fixture whenever the scan has read a newer head than the index.
- Gap 4 (own slices or external dependency): external dependency, with its two tests named in this plan's acceptance (finding 6), not the ticket states, because gap 3 can close those tickets without the defects being fixed.

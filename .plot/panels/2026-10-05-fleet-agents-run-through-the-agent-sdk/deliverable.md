# Deliverable lens: fleet-agents-run-through-the-agent-sdk

Position: amend

Juror lens: DELIVERABLE. I read the plan as the fleet agent who implements each slice from its brief. Evidence comes from `git show origin/main:<path>` and `git grep ... origin/main` at 3cfc60c9b unless a finding says "reading only".

## HIGH

**H1. Slice 4 flips a default that does nothing for workers until another plan's slice 5 lands, and it waits on nothing.** SDK mode lives only in the JS loop: the plan says that slice 1 waits on `infra/the-loop-runs-in-one-process` "because the JS loop must exist". That loop runs behind `Worker loop`, and that key defaults to `shell` until `infra/js-is-the-default-loop` (docs/plans/2026-10-04-the-worker-loop-runs-in-js.md:123, :178, :203). The shell body runs `.plot/worker-prompt.sh` through `claude -p`, which has no SDK path. So after slice 4 a repository with no config edit still runs every worker on `command`, and the Changelog line "after the flip it runs on the SDK with no config edit" is false for workers. The plan also never says what `Agent runner: sdk` does together with `Worker loop: shell`: refuse, warn once, or ignore. Slice 4 needs `<!-- waits: infra/js-is-the-default-loop -->`, and slice 1 needs a stated answer for the sdk+shell combination with a test.

**H2. The SDK run has no mapping to the loop's prompt-exit reading, so the usage-limit path is left to no slice.** Today the loop classifies a prompt exit by matching the log against `HARNESS_LIMIT_LINES` (packages/board/src/server/entry/prompt-exit.ts:6, :138) into `wait`, `end-limited`, `unstarted` or `ran` (prompt-exit.ts:64-80). The `limited` and `unstarted` endings depend on that classification (packages/domain/src/entities/ending.ts:42, :65). Slice 1 replaces the prompt run with `query()` and defines only the four `next` values and "no `structured_output` reads as `done`". Under that rule a run stopped by a usage limit, or a CLI child that fails to start, reads as `done`, and the loop restarts it into the same limit. `SDKRateLimitEvent` reaches the budget record only in slice 2. Slice 1 needs a rule that maps the SDK result (`subtype`, `terminal_reason`, a rejected `rate_limit_info`, a spawn failure) to the existing `PromptExit` answers, with a fixture-test row for each, before the SDK path can replace the prompt run.

**H3. The prompt template that SDK mode reads does not exist, and no slice writes this repository's prompt.** The plan says SDK mode reads `.plot/worker-prompt.md`, or otherwise "the shipped `skills/plot-dispatch/templates/worker-prompt.md`", and fills `{branch}`, `{brief}`, `{scripts}`. Command: `ls skills/plot-dispatch/templates` gives "No such file or directory". The shipped template is `skills/plot/templates/worker-prompt.sh`, a shell script that interpolates `$PLOT_BRANCH`, with no `{…}` placeholders (`git show origin/main:skills/plot/templates/worker-prompt.sh | grep -n "{branch}"` gives no match). This repository's own instructions (changesets, "never commit a generated board bundle", "use trash not rm") live only in `.plot/worker-prompt.sh:186`. The plan keeps `plot-install-prompt.sh` unchanged, so no repository receives a `.md`. A slice-1 agent must therefore invent the template's path and placeholders. In SDK mode this repository's workers then get the generic text and lose the repository's own instructions. Slice 1 must name the template as a deliverable at a real path, and it must name who writes `.plot/worker-prompt.md` for this repository (or derive it from the `.sh`).

## MEDIUM

**M1. The slice-spend record cannot hold the line slice 2 describes, and its reader takes the newest line rather than a sum.** `SliceSpendSchema` is `.strict()` with `branch`, `at`, one summed `tokens`, `turns` and `models` (packages/domain/src/entities/slice-spend.ts:38-56). It has no per-model counts, no cost, no role and no session id. The board's read takes `latest` as "what the branch cost on its last run" (packages/domain/src/rules/slice-spend-record.ts:31-38). Per-run lines therefore need a schema change, a decoder that still reads seal lines, and a reader that stops taking the newest line. A slice that switches runner mid-life holds both kinds of line. Slice 2's Done names "the board's spend reader sums a slice's run lines" and nothing about the strict decoder or a mixed record, so a naive implementation that adds optional fields and sums every line passes and double-counts a mixed slice. Add a Done item: a record that holds a seal line and run lines for one branch reads the right total.

**M2. No limit bounds the `checks` → resume cycle.** `Worker bound` "bounds each run" (Approach), `maxTurns` bounds each run, `Agent max spend` bounds each run, and `Slice max spend` defaults to none. The correction budget counts only CI corrections (packages/domain/src/workflows/agent-loop.ts:126-127, :227). An agent that hands back `checks` after every failed local check resumes without end, and nothing ends the slice. Today one prompt run under `Worker bound` is the whole budget for that phase. Slice 1 needs a count of local-check resumes that ends `blocked`, or it must state which existing limit covers that count, with a test.

**M3. After the flip, board roles lose their `--model` flag without notice.** In SDK mode a role reads `Agent models`, then `PLOT_MODEL`, then the CLI default. The board fragments carry the model as a CLI flag, `claude -p --model opus` (AGENTS.md:75, :96), not as `PLOT_MODEL`. So a repository without an `Agent models` key runs idea, story and interrogate on the CLI default after slice 4, although the plan says it "edits nothing". Slice 3 or 4 must read `--model` from the fragment, or slice 4's Done must prove that the model a role runs on does not change.

**M4. Slice 1 is too large for one branch, and most of it does not need the JS loop.** Slice 1 holds a port, three adapters, `pollRefusal`, the PreToolUse hook, new `agentLoop` rows, a local-checks runner, a new prompt template, a 1.2 MB dependency in the bundle, a group-stop test on two OSes and a live run. The port, `pollRefusal`, the fixture adapter and the `agentLoop` hand-back rows are pure domain work and could merge now. Only the wiring needs `infra/the-loop-runs-in-one-process`, whose remote branch holds only its claim commit (`git log origin/main..origin/infra/the-loop-runs-in-one-process` gives 7a277c960 "plot: claim …"). Split slice 1 into a domain slice with no wait and a wiring slice that waits on the loop.

**M5. Slice 1's live-run Done item cannot be done by the agent that builds the slice.** "The PR records one live slice on `Agent runner: sdk`" needs a fleet worker that runs the branch's unmerged bundle with `Worker loop: js` and `Agent runner: sdk` set. A fleet agent cannot start a fleet worker on its own desk. The item is an operator action after the merge, the same way the other plan's slice 3 says "After merge. The operator sets `Worker loop: js`" (docs/plans/2026-10-04-the-worker-loop-runs-in-js.md:187). Move it to an operator step after the merge, and say which commit sets `Agent runner: sdk` here. Slice 4's 20-slice window also needs that step, and no slice or note names it.

**M6. `spend-spent` sits beside an existing `spent` that means something else.** `spent` already means "the agent's context ran out" (packages/domain/src/entities/ending.ts:34, :100), and `isSpent` reads that reason (ending.ts:266-269). A reader who greps `spent` finds both. A name such as `budget-spent` avoids the clash with the existing word.

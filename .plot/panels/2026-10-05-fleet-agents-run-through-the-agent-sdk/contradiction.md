## HIGH

**H1. Summing per-run spend lines counts the earlier runs of a resumed session again, so "no token is counted twice" cannot hold.** The plan resumes the session after every `checks` result and every CI correction (plan:112). It appends one slice-spend line per run from `modelUsage` and `total_cost_usd` (plan:114), and the board and `sliceSpendRefusal` sum a slice's run lines (plan:21, plan:129). The SDK types say both fields carry over on a resume: `sdk.d.ts:5789` says "a resumed or forked session continues from the totals its transcript saved … (so the first result already carries the earlier turns)", and `sdk.d.ts:5781` says the same for `total_cost_usd`. A slice with one `checks` resume and two corrections therefore records run 1 up to four times. `Slice max spend` then trips early, and the board's plan cost goes up with every resume. The existing reader takes the newest line per branch and does not sum (`packages/domain/src/rules/plan-spend.ts:93-94`, `read.latest`). `SliceSpendSchema` is `.strict()` with four summed counters and no per-model, cost, role or session field (`packages/domain/src/entities/slice-spend.ts:13-56`). The plan names `entry/slice-spend.ts` as what slice 2 extends (plan:204) and does not name the entity. Sources: the SDK .d.ts (command) and the repository (reading). Fix: record each run as the difference from the previous result of the same session, or keep "newest line per session, sum across sessions", and name the entity change.

**H2. `Slice max spend` and the promised fresh session contradict each other.** Changelog plan:19 and Done When slice 2 (plan:192) say that a run reaching its spend limit gets one fresh session from the supervisor before a person is asked. Plan:129 says that when the run lines of a slice have reached `Slice max spend`, "the loop starts no run and ends `spend-spent`". The fresh session's loop sums the same lines (H1 makes the sum larger), refuses at once, and ends `spend-spent` again. So for the slice-level limit the "one fresh session" is a no-op that uses up the slice's one fresh-session allowance. The plan must say whether a fresh session gets new headroom, or whether `spend-spent` from the slice limit goes straight to a person. Also, `freshAgentAfterCorrections` in the approved plan answers `start-fresh` only for `corrections-spent` (`docs/plans/2026-10-05-a-spent-correction-budget-gets-a-fresh-agent.md:41`). "Reuses its fresh-session path" (plan:149) therefore changes an in-flight approved rule, and the plan does not say so. Reading only.

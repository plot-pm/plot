# Juror: Contradiction

Position: amend

Subject: `docs/plans/active/delivery-fleet-rows-per-agent.md` at HEAD `a154ced7a`. Lens: where the plan disagrees with the cited design, a sibling plan, or a decision the estate already made.

## Findings

1. **The switches do not write config keys, and the estate decided they never will.** Done When says the switches "write their config keys through their controllers". `FleetControls.tsx:35` posts to `/api/fleet-controls`, and `packages/fleet/src/shared/fleet-settings-store.ts` (header, section "In `.plot/state/`, beside the pulse — never in a committed file") states: "A switch written into `CLAUDE.md` would arrive in a commit … so `## Plot Config` supplies the DEFAULT at startup and nothing more. The file is the running answer." The Done When item therefore contradicts a settled decision. A slice built to it would either fail the item or start editing `CLAUDE.md`. Amend: "write `.plot/state/` fleet settings through `/api/fleet-controls`, as today".

2. **The switches move, and the plan does not say so.** At HEAD the four switches and the stepper already exist and already sit in the Fleet section: `AgentList.tsx:1403-1418` renders `AutoDispatchSwitch`, three `AutoSwitch`es and `ParallelAgentsStepper` in a `div` under the `h2`, with `WorkingCounts` on the left. The header-switches slice moves existing controls into the header line and builds none of them. The plan also does not name `FleetControls.tsx`. Plan 1's own open point (`delivery-tab-header-and-my-sprint.md:75`) asks for `FleetControls.tsx` to be named as the component the read-only fleet card and the Fleet header share. Neither plan owns that shared or read-only variant, and neither declares a `waits:` between plan 1's `feature/delivery-tab-header-cards` and this plan's `feature/delivery-fleet-header-switches`. `FleetControls.tsx:6-13` also records an earlier decision ("Each renders on the section it is ABOUT … two controls in two places, not one panel"). The 2026-11-16 design replaces that decision (*Changes*, point 5), and the plan should name the comment it retires.

3. **Plan 1's section header has no slot for controls.** Plan 1 defines the header as "a domain summary … the section's name, its icon, and a list of counts … The section header component renders that summary and lists no items" (`delivery-tab-header-and-my-sprint.md`, Approach, "Section header pattern"). This plan depends on `feature/delivery-section-header` and puts interactive controls right-aligned on that same line. Nothing in plan 1's slice carries a controls slot. The dependency is declared, but the dependency's shape does not support what the plan builds on it. One of the two plans must say who adds the slot.

4. **Plan numbering disagrees across siblings.** The subject calls itself "Plan 4 of 6", which matches the design's *The Plans* list (Fleet = 4). Plan 1's open point (`:75`) calls the Fleet section header "plan 5". This is plan 1's defect, but it makes the cross-plan switch ownership ambiguous to a reader of either file.

5. **The role chip has two owners.** Plan 3 (`delivery-work-items-show-gates.md`, Approach) says: "The role chips are the ones plan 4 shows in Fleet; this plan adds them to the row form in `packages/domain/src/rules/delivery-row-form.ts`." This plan also builds role chips "on the agent row form in `delivery-row-form.ts`". Neither slice waits on the other. Plan 3's round-1 panel already recorded this. The subject still names no owner. The estate side: `AgentRole` holds six roles (`delivery-placement.ts:93`: loop, fixer, reviewer, approver, idea, brief), and the design lists eight (adding design and verify). Every agent at HEAD reads `loop`: `delivery-readings.ts:302` reads `role: agent.role ?? 'loop'`, and `RegistryAgent = AgentEntry & { role?: AgentRole }` (`:29`) adds a role that the registry schema (`schema.ts` agent entry, fields at about `:3940-4065`) never carries. The plan has to say which slice widens `AgentRole` and which reading supplies a role.

6. **Tokens: the design says "current run", and `slice-tokens.ts` is not a current-run reading.** The design's Fleet section (`design.md:129`) says "Tokens: what the agent spent on its current run". The plan says `slice-tokens.ts` "already answers per-slice token counts and is read, not replaced". `sliceTokens` sums every session of a desk per **branch** (`slice-tokens.ts:211-249`, "THE SUBJECT IS THE BRANCH WITHIN A DESK, NOT ONE SESSION"). It is written once, at `seal_declaration`, when a slice finishes (`workflows/slice-spend.ts`, `recordSliceSpend` doc: "CALLED AT `seal_declaration`, WHICH IS THE ONLY MOMENT THAT KNOWS WHICH BRANCH JUST FINISHED"). A **working** agent therefore has no token record until it seals. The registry entry carries only `contextTokens` and `contextSpend` (`schema.ts:4054,4063`), which are context readings, not output spend. The slice-tokens rule says outright that those two are kept apart (`slice-tokens.ts:22-27`). With *Non-goals* forbidding new reads (`design.md:221`), the Tokens column for a Working row has no source at HEAD. The plan must name this gap alongside the "today" gap and not only the "today" gap.

7. **Open Question 1 (output tokens per day) has a partial answer in the estate.** The slice-spend record lines carry `at` and `outputTokens` (`entities/slice-spend.ts:45-61` seal line, `:93-109` run line, with `role` on run lines). A per-day sum over **finished** slices and SDK runs can therefore be derived from a record that already exists, with no new host read. It cannot include running agents (finding 6). The question should be closed with that scope rather than left open.

8. **Open Question 2 (bounds for non-loop agents) is answered in code, and the answer contradicts "time left" for one role.** `auto-verify.ts:42-43` and `auto-design.ts:43-44` use `Worker bound` (default 28800). The reviewer uses `REVIEW_BOUND_MS = 3_600_000` (`auto-review.ts:64`, `board/src/server/entry/review.ts:94`). The fixer uses `FIXER_BOUND_SECONDS = 3600` (`domain/src/rules/fixer-attempts.ts:8`), so "the fixer's bound" is a constant and not a config key. The brief run has **no time bound by decision**: `brief-ask.ts:105-107` says "The run has no time bound, because a bound turns a usage-limit wait into an end". A Time left bar for a brief agent therefore contradicts an estate decision. The plan has to say that a brief row shows no bar. I did not find a bound for idea runs. The approver role was not checked.

9. **"Every agent shows once, in exactly one of Working, Blocked or Free" disagrees with the existing placement rule.** `agentGroup` (`delivery-placement.ts:262-267`) returns `null` for an agent whose process is unread, and `placeDelivery` (`:300-305`) sends it to `unplaced` with reason `unread`. The design's Footer section keeps an unplaced list ("desks not placed · details"). The Done When either changes that rule, which the design's *Non-goals* forbids ("No change to the placement rule's decisions"), or it should read "every placed agent".

10. **Waits on targets the design names are not readings yet.** `DeliveryGate` holds `ci | review | machine | rate-limit | person` (`delivery-placement.ts:27`), but the board sets `blockedOn` only to `'person'`, from `state === 'waiting'` (`delivery-readings.ts:303`). "`CI ⟳` with its run" and "a rate limit" have no reading at HEAD, and *Non-goals* forbids a new host read. The plan should name these as gaps, as it does for tokens.

11. **Groups fold today, and the design says groups are always open.** `AgentList.tsx:1430` wraps each group header in `fold(group.key, …)`. The design (*Rules for the Whole Tab*, `design.md:166`) allows collapsibles in three places only, one of them the Free line. The plan adds the Free collapsible but does not remove the fold from Working and Blocked.

12. **The rebuild instruction contradicts a gate.** Board impact says "Rebuild the board artifact (`pnpm build:board`) with each slice". CLAUDE.md (Testing, board artifact paragraph) and `scripts/check-no-bundle-diff.sh` refuse a committed bundle: "Run `pnpm build:board` only to test the result locally, then restore the generated paths before you push." Plans 1 and 3 carry the same defect, and their panels recorded it.

The plan extends this row form and does not replace it. This matches design Approach A.

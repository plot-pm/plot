# Testability juror — the-reporter-sigterm-test-fails-on

Position: amend

The flake reproduces on demand on this machine, and the cause is a race in the production script `reporterShell`, not in the test's wait and not in the 5 s bound. The reporter subshell installs `trap '' TERM` as its own first command, after the fork. The test's only sync points (the outer `sh` exit and the `ready` file) prove the reporter was forked, never that its trap ran. A group `SIGTERM` that lands in that window kills the reporter with the default action, so no finding is ever written. A standalone loop of the test's exact sequence missed 7 of 300 iterations against `origin/main`'s script; moving `trap '' TERM` into the parent, before the reporter's `&`, missed 0 of 300. The plan's three-way investigation is mostly already answered, and its cause 1 (raise the bound) would not fix the miss. Through the testability lens, the plan must name this cause, put the fix in `reporterShell`, and state how the slice proves the race is gone and stays gone.

## Findings

1. **high — the cause is reporter-trap ordering, and it is reproducible now.** Evidence: `packages/fleet/src/shared/continuation.ts:879-884` on origin/main — `( trap '' TERM; if [ -n "$fifo" ] ...) &` sets the ignore inside the forked child; the parent `exec 3>&-` and exits without waiting for it. The test (`packages/fleet/test/unit/continuation.test.ts:729-736`) waits on the outer exit (`rig.start`) and on `ready`, which the AGENT subshell writes, so neither orders the reporter's trap before the kill. What I checked: I extracted `reporterShell` from origin/main into a node script under my scratch dir and ran the test's sequence (spawn detached, await outer exit, await `ready`, `process.kill(-pgid,'SIGTERM')`, wait 3 s for the finding) with `/bin/sh` (bash 3.2) at load average ~5 on 16 cores. Original script: 3/100 and 4/200 misses (7/300, about 2.3 % per iteration, so about 37 % per 20-run test on this machine). In every miss the exit file held `143` (the agent's trap ran) and the FIFO still existed (the reporter never reached `rm -f "$FIFO"`): the reporter died, it did not run late. Same script with `trap '' TERM;` moved to the parent before `( ... ) &`: 0/100 and 0/200 misses.
2. **high — raising the 5 s bound (the plan's cause 1, listed first) cannot fix it.** Evidence: the failing CI runs log the test at 5709 ms (run 41361916665 attempt 1) and 5854 ms (run 41376720118 attempt 1); the passing rerun of 41361916665 logs it at 912 ms for 20 iterations, about 45 ms each. A failing run is therefore about 5000 ms of one fruitless wait plus a few fast iterations: the finding never came, it was not slow. A longer bound only makes the red run slower. The plan must drop cause 1 as a candidate fix, or at least forbid it unless the reproduction shows a late (not absent) finding.
3. **medium — the plan states a false fact about the evidence.** Plan, Approach: "The failure message names no line. Two `expect(...).toBe(true)` calls in the test can produce it, and only the first is unambiguous." Both failing logs name `continuation.test.ts:736:75` (log lines 344 and 5884 of the saved logs), and the SIGTERM test holds exactly one `toBe(true)` (line 736). The next bullet of the plan then says the other waits are not asserted, so the plan contradicts itself. The plan also says the test "failed once on main"; it failed twice, the second time on PR #3036 at `609cc0c34` (run 41376720118).
4. **medium — the plan names no proof that the flake is gone, only "make the test deterministic".** A race between fork and a builtin `trap` cannot be widened by the rig's PATH shims (`trap` is a builtin, and the reporter starts no external before it), so no deterministic before/after reproduction exists inside the existing rig. What does exist: (a) a statistical A/B with strong numbers (7/300 against 0/300 here; at p = 2.3 %, 0/300 by chance has probability about 0.001), run once and recorded in the PR; (b) a structural assertion in the suite, the same kind as the existing "holds no sleep and no absolute path between the open and the tail" test at line 657, that `trap '' TERM` appears in the parent script before the reporter's `(` and its `&`. With the fix, the test's existing wait becomes sufficient by a happens-before chain: parent sets ignore, then forks (the child inherits `SIG_IGN` atomically at fork), then exits, and the test awaits that exit before it signals. The plan should write that chain down, because it is what makes the 20-run loop deterministic rather than lucky.
5. **medium — the fix keeps what the test proves, and the plan should say so explicitly.** The assertion stays `findings().length === 1` within 5 s, `exitFile === '143'`, `finding: gone`, FIFO removed. No retry, no tolerance and no second accepted outcome is needed. A plan that leaves cause 1 or a "readiness signal in the rig" open as fixes leaves room to change the test instead of the script; a rig-side readiness signal would need a production hook (the reporter writes nothing before its trap), which the Layering rule and "test the behaviour, not a hook" both argue against.
6. **medium — this is a production bug, not only a test flake.** A real fleet stop that sends `SIGTERM` to the group in the same window loses the desk's `WorkerMonitor` finding the same way. The plan's `Type: feature` and branch `feature/...` should be `bug` / `bug/...` per the config's branch prefixes, and the changelog line should state the production effect: "a group SIGTERM right after a continuation starts no longer loses the reporter's finding".
7. **low — a residual window exists outside what the test exercises.** With the fix, a `SIGTERM` sent the moment the outer shell exits, without waiting for `ready`, still missed 3/200 here; each such miss had no exit file, the FIFO present and `ready` present, which points at the agent's inner `( cmd )` subshell surviving a signal during bash's post-fork trap reset, so the agent never exits and the reporter correctly waits. That is a different window (the agent's, not the reporter's) and the test's `ready` wait already excludes it. It needs no work in this plan, but the plan should not claim the reporter "always" reports a group SIGTERM.
8. **low — the CI shell differs from the local shell.** CI runs `ubuntu-latest` (`/bin/sh` = dash, `.github/workflows/ci.yml:96`); locally `/bin/sh` is bash 3.2. Both inherit `SIG_IGN` across fork, so the fix holds on both, but the reproduction numbers above are bash-only. The slice should run its A/B once on Linux (a container, per the repo's own practice for CI-only failures) or say it did not.
9. **low — "until #3028 lands".** #3028 is an open issue ("fleetd's fixer and main-repair agents never start"), not a PR; the plan should say "until #3028 is fixed".

## Amendments I require

- A1. Replace the three candidate causes with the measured cause: the reporter subshell installs `trap '' TERM` after its fork, so a group `SIGTERM` before that line kills it silently. Cite the reproduction (exit file `143`, FIFO left, no finding) and the CI durations (5709 ms and 5854 ms against 912 ms passing).
- A2. Put the fix in `reporterShell`: install `trap '' TERM` in the parent shell after the agent's `&` and before the reporter's `( ... ) &`, so the reporter is born ignoring `TERM`. Remove the in-child `trap '' TERM` or keep it as a no-op; update the TSDoc sentence "The reporter ignores `SIGTERM`" to say it inherits the ignore from its parent. Do not raise the 5 s bound and do not add a rig readiness signal.
- A3. Keep the SIGTERM test's assertions unchanged (finding within 5 s, exit `143`, `gone`, FIFO removed, 20 runs).
- A4. Add a test table with at least: (a) a structural test that the script text sets `trap '' TERM` before the reporter subshell's `&` and after the agent's `&` (fails on origin/main's script, passes after); (b) the existing 20-run SIGTERM test, unchanged.
- A5. Record in the PR a mutation A/B of at least 300 iterations of the group-SIGTERM sequence, original script against fixed script, on Linux `sh` (dash) and on macOS `sh`, with miss counts. The original must miss at least once and the fixed must miss zero times; if the original never misses on Linux, say so and keep the macOS numbers.
- A6. Correct the factual errors: the log names line 736; the SIGTERM test has one `toBe(true)`; it failed twice (main `4d33c00dd`, PR #3036 `609cc0c34`); #3028 is an issue.
- A7. Change `Type:` to bug and the slice branch to `bug/the-reporter-sigterm-test-fails-on`, and state the production effect in the changelog line.

## Optional

- O1. Add a second, faster stress case that kills the group the instant `rig.start` resolves (no `ready` wait), asserting only that the exit file and finding agree when a finding appears. It exercises the reporter window harder, but it also hits the agent-side window in finding 7, so it must not assert a finding unconditionally.
- O2. Note the agent-side window (finding 7) in the plan's Notes as a known residual, not as work.

## Open questions

- **Does the failure reproduce locally under load, or only on the CI runner?** It reproduces locally: 7 misses in 300 iterations of the test's exact sequence, macOS `/bin/sh` (bash 3.2), load average about 5. No CPU-stress harness is needed; normal machine load suffices. Recommendation: close the question with these numbers and run the A/B once on Linux too (A5).
- **Is 20 iterations still the right count once the miss is fixed?** Keep 20. The loop is the amplifier that found this race in CI, it costs under 1 s when green (912 ms), and after the fix the happens-before chain makes every iteration deterministic, so the count no longer multiplies a miss chance. Do not reduce it to make a flake rarer; that is the weakening the operator ruled out.

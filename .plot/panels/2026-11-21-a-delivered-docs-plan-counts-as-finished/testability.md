## Findings

1. **The carried-card test cannot fail today, and the Motivation's carried-card claim does not hold.** The carried card counts `unsprintedPlans(sprints, carried.approved)` against `carried.slicesByPlan` (`packages/domain/src/rules/release-card.ts:157-158`). `carried.approved` is `[...new Set(counted.map((s) => s.plan))]` (`packages/board/src/app/lib/agent-rows/delivery-view.ts:893`, returned at `:958`), so it holds only plans with a pulse slice, and every such plan gets an entry at `delivery-view.ts:917-926`. A sprint member is never in `unsprinted`, and a plan the walk dropped is never in `approved`. So a delivered docs plan cannot make the carried card read `RELEASE_READING_MISSING`, and the named test "the targeted card and the carried card for such a sprint draw a bar" passes on `origin/main` for the carried half. Read (opened code). **Change:** in Motivation, delete "and for the carried card (`:162-173`)"; in the `release-card.test.ts` bullet, assert the targeted card only, or assert that the carried card is unchanged, and label it as a pin rather than a fix proof.

2. **`sprint-card-slices.test.ts` cannot "stay green unchanged" if the board copy is replaced.** The file imports the board function and calls it with the board signature `countedSlicesByPlan(items, input)` (`packages/board/test/unit/sprint-card-slices.test.ts:5,14,19-25,31`). It does not say whether the board export survives as a wrapper. Read. **Change:** state one of two options in the first slice. Option A: the board keeps `countedSlicesByPlan(items, input)` in `delivery-readings.ts` as a wrapper that only builds `seen` and `slices` and calls the domain, and the three board cases stay. Option B: the board export is removed and the three cases at `:7-33` are deleted from the board file and live only in the domain test. Then edit the "stay green" bullet to match.

The Approach says a plan with no counted slice gets `sliceItemId(plan, '')`, and the domain test says "a delivered docs plan with no slice id gets one merged slice", but the domain cannot build that id, and if the client puts it into `sliceIds` when `slices` is empty, the rule "a plan with no slice still scores delivered" sits in the board, which CLAUDE.md's layering rule forbids. Read. **Change:** add a field to the plan facts, for example `{ plan, phase, type, sliceIds, planId }`, where the client passes `planId: sliceItemId(slug, '')` as a value, and the domain chooses `planId` where `sliceIds` is empty. In `counted-slices.test.ts`, assert that the seeded entry is `[{ id: planId, merge: 'merged' }]`.

## Open question `[question-release-counts-docs]`

Recommend the plan's answer: **count the member as delivered on the release cards.** The reason is testability. One counting path keeps the release, sprint and person bars equal for one sprint, and `delivery-view.test.ts:170-190` already pins that equality between the person card and the sprint card, so a test that extends it to the release card is one more assertion. The other option needs a second map beside `slicesByPlan`, a second seeding rule, and a new test that pins an intended inequality between bars that users read side by side. The merged code also ships in the tag, so the bar describes the release truthfully. The `docs-live-on-merge` skip in `release.ts:296` concerns the Released record, not what the tag carries.

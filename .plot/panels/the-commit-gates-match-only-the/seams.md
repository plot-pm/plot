# Seams juror — the-commit-gates-match-only-the

Position: amend

The problem is real and the plan measures it correctly: the four gates at `gate.ts:87`, `:153`, `:232` and `:371` test `command.includes('git commit')`, and the five Motivation rows reproduce exactly on `origin/main`. The launchers and the hook registration add no second substring test, and no open PR touches `gate.ts`, so the change has one place to land. The design does not fit its seams yet. The plan says no existing commit test exists, but two readers of git invocations are already in the domain, and the plan adds a third. Its "never matches less" guarantee covers only `readShell` returning `null`, and an executed experiment shows six forms that the substring catches today and the new rule drops, `bash -c 'git commit …'` among them. The plan does not specify the `-C` directory for `cd`, for repeated `-C`, for an unknowable path or for more than one commit in a line. Half of the newly matched subcommands commit content that is not in the index when a PreToolUse gate runs, so matching them adds cost and protects nothing. Each of these has a small fix, and the slice stays one branch.

## Findings

1. **high — the plan says no commit reader exists, but two exist and the plan adds a third.** The plan says "The deliverable search found no existing commit test". `controller-gate.ts:87-99` (`commitIndex`) finds `commit` in `git [options] commit` over `readShell` words and skips the git global options in `GIT_VALUE_OPTIONS` (`:43`, 5 entries) and `GIT_FLAG_OPTIONS` (`:46`). `main-checkout-write.ts:183-205` (`writeDirOf`) and `:284-311` (`writeDirsWhere`) read every git call in a line: they skip the global options in `GLOBAL_VALUE_OPTIONS` (`:65-73`, 7 entries, with `--config-env` and `--super-prefix`), join successive `-C` paths, follow a literal `cd`/`pushd`, and already take an `accepts(sub, args)` predicate. `MUTATING_GIT_SUBCOMMANDS` (`:38-62`) already lists `commit`, `merge`, `rebase`, `pull`, `cherry-pick`, `revert` and `am`. `makesCommit` is `writeDirsWhere(command, isCommitting)` plus a predicate. The plan's option list copies the 5-entry set from `controller-gate.ts` and follows neither reader. Checked by reading both files at `origin/main` and by running `gitWriteDirs` (bundled with esbuild from `origin/main` sources) on the plan's test rows. It returns `["/x"]` for `git -C /x commit -m y`, `[null]` for `git merge --continue`, `["x"]` for `cd x && git commit -m y`, and `[]` for `git commit-tree abc`.
2. **high — the "never matches less than today" guarantee does not hold for lines that `readShell` reads.** The fallback runs only when `readShell` returns `null`. An executed experiment ran `readShell` and `gitWriteDirs` on `origin/main` sources. These six lines contain `git commit` (the gates run today), and in each one the simple command's program word is not `git`: `bash -c 'git commit -m x'` (words: `bash -c git commit -m x`), `sh -c "cd /d && git commit -m x"`, `command git commit`, `nice git commit`, `timeout 60 git commit -m x`, `sudo git commit`. `gitWriteDirs` returns `[]` for all six. A rule that tests the program word stops gating them, so `bash -c 'git commit -m x'` carries a hand-written `State:` line past the `state` gate, which refuses it today. That is a new evasion route of the gate that `plot-state-gate.sh` exists for.
3. **high — the plan does not specify the directory, and its own test row needs it.** The Design says the gate takes "the last `-C` of the matching simple command". (a) git joins successive `-C` paths, and `gitWriteDirs('git -C a -C b commit')` returns `["a/b"]`, not `b`. (b) The test table has `cd x && git commit`, but the rule returns only a `-C` directory, so that gate reads `process.cwd()`, which is the wrong tree. `gitWriteDirs` already returns `x`. (c) `git -C "$desk" commit -m x` is newly matched (`readShell` gives the `-C` value `null`), and the plan does not say which tree the gate reads then. `main-checkout-write.ts:266-271` leaves such calls out, and `main-checkout-write.ts:398-399` recommends `git -C <desk>` and the `cd "$desk"` form. (d) `git -C a commit && git -C b commit` makes two commits in two trees. The plan gives one directory, and the main-checkout gate already loops over every directory (`gate.ts:553-561`).
4. **medium — a PreToolUse gate cannot see what a plain `merge`, `pull`, `cherry-pick`, `revert` or `am` commits.** The hook runs before the command. Every gate reads the index (`refs.stagedEntries`, `gate.ts:104`, `:253`; `stagedPaths`, `:170`, `:408`), and before these commands run, the index does not hold the content they commit. A conflict-free `git merge`, or `git cherry-pick <sha>` whose commit hand-edits `State:`, finds a clean index and is allowed, the same as today. Only `commit` and the `--continue` forms (`merge`, `rebase`, `cherry-pick`, `revert`, `am`) commit what the index holds at hook time. So the Changelog sentence "run on every Bash call that makes a commit" is true, but it implies protection that half of the listed forms do not get. The Motivation bullet "A `git merge` that commits with no conflict, and `git pull`, `git cherry-pick`… match no gate" stays true in effect after the slice.
5. **medium — the phase gate newly runs on a merge in progress, and it reads main's paths as the branch's own.** `holdRefusal` (`phase-gate.ts:149-161`) refuses any commit on a branch in `.plot/hold` that carries a path outside the plan or story directory. The implementation arm (`gate.ts:433-434`) reads any such path as implementation. A `git merge --continue` on such a branch stages main's paths, so the gate refuses the conflict merge. That merge passes today because nothing matches it. The brief's context names this case: a gate that newly runs on `git merge --continue` must not refuse a legitimate repair. The `state` gate reads `MERGE_HEAD` versions (`gate.ts:277-282`) and the bundle gate reads them through #2971's merge base (`gate.ts:109-122`). The phase gate does not read them. The test table has no merge-in-progress row for `phase`, `state` or `brief-name`.
6. **low — `takesModifiedOf` reads the whole line.** `state-transition.ts` `takesModifiedOf` matches ` --all` or a standalone `-a`/`-am` anywhere in the command. On a newly matched line such as `git fetch --all && git merge origin/main`, `effectivePaths` then treats every working change as carried. A dirty plan file then makes the `state` or `phase` gate refuse a merge that does not commit it. Today that line does not match.
7. **low — the reuse pointer is wrong.** `mergesBy` (`controller-gate.ts:266-280`) reads `gh pr merge` and `plot-host.sh pr-merge`, not git. It splits segments with `withoutQuotes`/`withoutComments` first and uses `readShell` only as a fallback (`:275-276`). The plan's order is the reverse. The reader to follow is `commitIndex` or `writeDirsWhere`, as finding 1 says.
8. **low — Open Question 2's premise is false for `main-checkout`.** `gate.ts:553-555` already resolves `cd` and `-C` through `gitWriteDirs` and only falls back to `process.cwd()` for the `null` entry. `controller` (`:668`) and `role-deny` (`:795`, `:808`) do read `process.cwd()`.
9. **low — `-C=<dir>` is not a git form.** The plan says the global options are read "in both `--opt value` and `--opt=value` forms". git takes `=` only on the long options (`--git-dir=`, `--work-tree=`, `--namespace=`), and `gitWriteDirs('git -C=/x commit')` reads `[null]`. The plan must not add a test that makes `-C=` a supported form.
10. **sound — launchers and hook registration.** `plot-state-gate.sh:18` and `plot-bundle-commit-gate.sh:17` are `exec node "$bundle" <gate> "$@"` with no substring test. `plot-gates.sh:15` runs `--all`. `hooks/hooks.json` registers one `Bash` matcher with no `if` filter. `plot-install-hooks.sh:305,325,340` drives the gates with `git commit -m x`, which still matches. No launcher needs a change. Checked by `git show origin/main:` on each file.
11. **sound — open plans.** Plan PR #2971 (`the-bundle-gate-refuses-the-repair`) is Delivered, and its implementation PR #2976 merged 2026-10-31T11:30:36Z. Its gate change is on `main` at `gate.ts:109-122`, and its Out of scope names this gap. The only open non-release PR, #2983, touches none of `gate.ts`, `main-checkout-write.ts`, `controller-gate.ts` or `shell-reading.ts`. No active plan on `origin/main` names those files. The slice has no merge collision to plan for.
12. **sound — Motivation facts.** The four line numbers are correct on `origin/main`. `includes('git commit')` gives the five results in the table (executed).

## Amendments I require

- A1. Build `makesCommit` on the existing reader, not on a third one. Export a variant of `writeDirsWhere` (`main-checkout-write.ts:284`) that takes a commit predicate, or extract one git-invocation reader (program word, global options, subcommand, `-C` and `cd` directory) that `writeDirOf` and `commitIndex` both call. Use one global-option set. Correct the sentence "The deliverable search found no existing commit test" and the `mergesBy` reference.
- A2. Keep today's floor exactly: `wants = command.includes('git commit') || makesCommit(command)`. Add test rows for `bash -c 'git commit -m x'`, `command git commit`, `timeout 60 git commit -m x` and `sudo git commit`, each still matched.
- A3. Specify the directory: one entry per committing call, with successive `-C` paths joined and a literal `cd` followed, as `gitWriteDirs` does. An entry the text cannot place (`-C "$desk"`, `cd "$desk"`) reads `process.cwd()`, which is today's behaviour. Each gate asks every entry and refuses when any entry refuses. Add rows for `git -C a -C b commit`, `cd x && git commit`, `git -C "$d" commit` and two commits in two trees.
- A4. Match only the forms whose commit the index holds at hook time: `commit`, and `merge`, `rebase`, `cherry-pick`, `revert` and `am` with `--continue`. Move plain `merge`, `pull`, `cherry-pick`, `revert` and `am` to Out of scope, with the reason that a PreToolUse gate reads the index before they run. Reword the Changelog and Motivation to match. This also removes finding 6 for the common `fetch --all && merge` line.
- A5. Add merge-in-progress rows (`MERGE_HEAD` present, main's paths staged) for `phase`, with a held branch and with an implementation branch, for `state` and for `brief-name`. Decide in the Design whether `phase` treats paths that equal a `MERGE_HEAD` version as not the branch's own. Without that decision, A4's `merge --continue` refuses the conflict-merge repair that the brief protects.
- A6. Correct Open Question 2's premise (`main-checkout` already threads `-C` and `cd`) and drop the `-C=` form from the option list.

## Optional

- Compute `makesCommit` once per Bash call and share it across the four `wants`. `plot-gates.sh` runs `--all` on every Bash call, so four separate readings run where one is enough.
- Name `controller-gate.ts`'s `commitIndex` in the TSDoc of the new rule as the reader it shares, so the next gate author finds it.

## Open questions

- Q1 (a plain `git pull` or `git merge` matches even when it fast-forwards): do not accept it. Before such a command runs, the gates find a clean index and cannot refuse what it commits, so matching costs latency and can only add false refusals (finding 6). Match the `--continue` forms instead (A4).
- Q2 (`main-checkout`, `controller`, `role-deny` and `-C`): `main-checkout` already does this (`gate.ts:553-555`). Handle `controller` and `role-deny` in a follow-up with its own issue. They do not test for a commit, and changing which tree they read changes what they refuse beyond this plan's Changelog.

# Juror verdict: testability

Position: amend

The defect is real and the plan names it correctly. I reproduced it: with a staged `State:` change in a fixture repository, `plot-gate.mjs state` refuses `git commit -m x` (exit 2) and allows `git -C <F> commit -m x`, `git  commit -m x` and `git merge --continue` (exit 0), from the same working directory. The test table does not prove the Changelog, for three reasons. First, the table tests only the matcher and has no row that runs a gate's `ask` through the launcher, so the `-C` directory threading and the wiring into the four gates have no test that fails without the change. Second, the proposed rule matches less than the substring test on readable lines that are not in the table (`command git commit`, `sh -c '…'`, `sudo`, `xargs`), which contradicts the plan's own "never matches less" claim. Third, the new forms reach state that the gates do not model: I measured that the `state` gate refuses a legitimate `git rebase --continue` once it runs on it, and `merge --abort` falls inside the plan's `merge` rule. The estate also holds two existing parsers that the plan says do not exist. Each problem has a clear repair, so the position is amend, not reject.

## Findings

1. **high: the `state` gate refuses a legitimate `git rebase --continue` once it runs on it.** Evidence: `gate.ts:232` and the `state` gate's `ask` read only `MERGE_HEAD` through `refs.mergeParents()`. `git grep REBASE_HEAD\|CHERRY_PICK_HEAD` over `packages/domain/src` and `packages/board/src` finds nothing. Experiment (`scratchpad/juror-test/rebase.sh`): branch `b` commits `State: Draft → Approved`, `main` edits the same file, `git rebase main` stops on the conflict, and the resolution keeps `Approved` and is staged. `plot-gate.mjs state` with `git commit -m x` exits 2: "a lifecycle field has one writer, and this commit is not it". With `git rebase --continue` it exits 0 today, but only because `wants` is false. The plan makes `wants` true for `rebase --continue`, so this exact repair stops at the gate. The receipt for the original transition was spent when the branch commit was made, so no receipt can clear the replay. The same holds for `cherry-pick --continue`, `revert` and `am`. The brief's survival condition ("must not refuse a legitimate repair") fails, and the plan's test table has no row for it.
2. **high: the table has no gate-level row, so the wiring and the `-C` threading are unproven.** Evidence: Notes list only matcher cases. The plan's own Changelog claim, "A gate that reads the working tree reads the tree `-C <dir>` names", is a property of `ask`, not of `makesCommit`. A unit test of `makesCommit` returning `/x` passes even when a gate still calls `process.cwd()` (`gate.ts:95`, `:160`, `:242`, `:388`). `test/reconcile/bundle-commit-gate.test.mjs:69-70` already runs the launcher with `cwd: dir`. The same harness, run from a `cwd` outside the fixture with `git -C <fixture> commit`, is the test that fails without the change. I ran that shape against the `state` gate (`scratchpad/juror-test/wire.sh`): exit 0 today, and it must be exit 2 after the change. The plan needs one such row per gate (four gates), or one per gate kind with a parametrised name.
3. **high: on readable lines the rule matches less than the substring test.** Evidence: `readShell` on the following lines returns the program word list shown, and `command.includes('git commit')` is true for all of them today. `command git commit -m x` gives `["command","git",…]`. `sh -c 'git commit -m x'` gives `["sh","-c","git commit -m x"]`, and `bash -lc "git -C /d commit"` gives the same shape. `sudo git commit` gives `["sudo","git","commit"]`, and `xargs git commit` gives `["xargs","git","commit"]`. A rule that compares `basename(program[0]) === 'git'` misses all five, so they lose the four gates that run on them today. The plan states "the rule never matches less than the gates match today" but provides the fallback only for a `null` reading. `controller-gate.ts:232` already skips `command`, `builtin` and `exec` (`PREFIXES`), and the rule needs the same treatment. A `sh -c`/`bash -c` argument needs a recursive read or a substring fallback on that word. The table needs a row per form, each asserting "matches".
4. **medium: the plan says no commit test exists, but the estate holds two.** Evidence: `main-checkout-write.ts:183` `writeDirOf` skips the same git global options (`:65`, which also holds `--config-env` and `--super-prefix` that the plan omits). It joins successive `-C` paths (`git -C /a -C b commit` gives `/a/b` in my probe), threads `cd`/`pushd` (`:140`), treats `"$desk"` as unknowable (`:119`), and already lists `commit`, `merge`, `cherry-pick`, `revert`, `am`, `pull` and `rebase` (`:40-48`). `controller-gate.ts:87` `commitIndex` finds `commit` after git options over `readShell` words. A third parser needs a corpus or shared-table test that holds all three to one answer, or it should extend `writeDirOf` with an `accepts` predicate, as `treeStrandingResetDirs` does at `:308`. Without that, the next fix to one parser leaves the other two behind, and no test notices.
5. **medium: the `-C` threading covers `commit` but not the chained `git add` that the gates also read.** Evidence: `chained-add.ts:20` finds `indexOf('git add')`, and `brief-name.ts:86` finds `indexOf('git mv')`. For the master agent's real #2965 form, `git -C <wt> add -A && git -C <wt> commit -m x`, `chainedAddsOf` returns `[]`, so `effectivePaths` (`state-transition.ts:456`) reads only the pre-add index of `<wt>`. The gate then runs and allows a `State:` change that the same command stages. The plan's table row `git add -A && git -C y commit` hides this, because its `add` runs in the session directory and not in `y`. The Changelog claim "reads the tree `-C <dir>` names" is therefore half true. The table needs the row `git -C y add -A && git -C y commit` with a staged `State:` change, expecting a refusal.
6. **medium: for `merge`, `pull`, `cherry-pick`, `revert` and `am` without `--continue`, the gates cannot refuse anything.** Evidence: the gates are PreToolUse hooks, so `ask` reads the index and `MERGE_HEAD` before the command runs (`gate.ts:113`, `:138-141` of the `state` gate's region). A clean `git merge origin/main` has a clean index and no `MERGE_HEAD` before it runs, so every gate allows whatever the merge then commits. The Changelog claim "the gates run on … `git merge` … `git pull`" is literally true, but a test of `wants` cannot show that it protects anything, and no test can show a refusal. The claim needs a narrower wording, or the plan needs to drop those forms and keep only the forms that commit the index as staged: `commit`, `merge --continue`, `rebase --continue`, `cherry-pick --continue`, `revert --continue` and `am --continue`.
7. **medium: under the plan's rule, `--abort`, `--skip` and `--quit` run the gates and can be refused.** Evidence: the Design says "`merge` (unless `--no-commit`)" and "`merge --continue` is a `merge` without `--no-commit`". So `git merge --abort` matches, and so do `cherry-pick --abort`, `revert --abort` and `am --skip`. During the #2965 conflict shape, with a locally rebuilt bundle staged, the `bundle-commit` gate refuses `git commit`, as `bundle-commit-gate.test.mjs:72` shows. That gate reads the same index for `git merge --abort` and refuses the escape hatch too. The table has no `--abort` row. Expected: no match.
8. **low: the table leaves several parser edge cases unstated.** Verified with `readShell` (`scratchpad/juror-test/probe.mjs`) and all handled correctly today. `FOO=1 git commit` and `env FOO=1 git commit` give `["git","commit"]`. `/usr/bin/git commit` needs `wordBasename`. `git commit <<< "msg"` gives `["git","commit"]`. `git \<newline>  commit` gives `["git","commit",…]`, and `gitWriteDirs` misses it. `time git commit` and `! git commit` need keyword stripping, like `withoutLeadingKeywords` (`main-checkout-write.ts`). `x=$(git commit -m y)` is found inside the substitution. `git commit -F - <<EOF … git commit … EOF` reads the heredoc body as data. `case a in a) git commit;; esac` returns `null` and must take the fallback. Each case is a row that fails if a later edit to the rule regresses it, and none is in the table.
9. **low: `git -C "$desk" commit` and `cd /desk && git commit` have no stated directory.** Evidence: `readShell` gives the raw `"$desk"` with a `null` value. `plot_desk_root` produces exactly this form, and the main-checkout refusal text recommends it (`main-checkout-write.ts`, `commonRefusalLines`). The plan says only that the gates use "the last `-C` … resolved against the session directory", which turns `"$desk"` into a path that does not exist. The `cd x && git commit` row has no expected directory, and the plan threads only `-C`. Each row needs its expected answer: matches, directory unknown, and then allow with UNVERIFIED or read `cwd`. The plan must choose one.
10. **low: one existing test name becomes false.** `bundle-commit-gate.test.mjs:134` is named "a command with no "git commit" is ignored". It uses `git status`, so it still passes, but its name states the old rule. The renamed test should say "a command that makes no commit".

Facts I checked and found true: `gate.ts:87`, `:153`, `:232` and `:371` each read `command.includes('git commit')`. The five Motivation rows give the stated substring result (my probe). `readShell` splits on `&&`, `;`, `|` and subshells and removes quotes. `mergesBy` is at `controller-gate.ts:266`. `plot-state-gate.sh` and `plot-bundle-commit-gate.sh` are launchers that decide nothing. The brief's `.claude/settings.json` does not exist on `origin/main`. The wiring is `hooks/hooks.json` → `plot-gates.sh`.

## Amendments I require

- A1. Add one launcher-level test per gate (`bundle-commit`, `brief-name`, `state`, `phase`) that runs from a `cwd` outside the fixture with `git -C <fixture> commit` and expects exit 2. The `bundle-commit-gate.test.mjs` harness is the model. The test must fail on `main` today.
- A2. Add a test for the chained form `git -C y add -A && git -C y commit` with a staged `State:` change, expecting a refusal. Thread the same directory, and the `-C`-aware match, into `chainedAddsOf` and `chainedStagesOf`, or state in the Changelog that a `-C` chained add is not covered.
- A3. Before `rebase --continue`, `cherry-pick --continue`, `revert` or `am` join the rule, the `state` gate must read `REBASE_HEAD`/`CHERRY_PICK_HEAD`/`REVERT_HEAD`, or a replayed transition must clear by another rule. Add the test from Finding 1 (rebase replays a receipted `State:` change after a conflict, expecting allow). The same applies to `brief-name` and `phase`, each with one replay row. Otherwise, remove those forms from this plan.
- A4. Exclude `--abort`, `--skip` and `--quit` from the rule, and add a row for each, expecting no match.
- A5. Make the "never matches less" claim true and tested: skip `command`/`builtin`/`exec` and `sudo`/`xargs`/`nice`/`nohup` prefixes, fall back to the substring test on a `sh -c`/`bash -c` argument, and add one row per form. Alternatively, add a property test asserting `makesCommit(c) || !c.includes('git commit') || /commit-tree/.test(c)` over the whole table.
- A6. Build on `writeDirOf`/`gitWriteDirs` with an `accepts` predicate (as `treeStrandingResetDirs` does), or add a corpus test that holds `makesCommit`, `commitIndex` and `gitWriteDirs` to agreement on the shared table. Correct the sentence "found no existing commit test".
- A7. Give every table row its expected answer as a pair: matches yes/no and directory. Add the Finding 8 rows and the `"$desk"` and `cd` rows with the chosen behaviour.

## Optional

- O1. Narrow the Changelog to the forms that commit the staged index (Finding 6). This removes the fast-forward over-match and the cost of four gate reads per `git pull`/`git merge`. `scriptsShell(...).config` spawns a script per gate per call.
- O2. Mutation-test the four `wants` lines once: revert each to `includes('git commit')` and confirm that one A1 row turns red.

## Open questions

- OQ1 (fast-forward over-match): do not accept it as stated. The cost is small, but the match buys nothing. Before a plain `git merge` or `git pull` runs, the index is clean, so no gate can refuse what that command commits (Finding 6). Match only `commit` and the `--continue` forms. If the plan keeps plain `merge`/`pull`, the Changelog must say that the gates run on them but cannot see what they commit.
- OQ2 (other gates' directory): the premise is partly false. `main-checkout` already reads `-C` and `cd` directories through `gitWriteDirs` (`gate.ts:555`). `controller` and `role-deny` read `process.cwd()`, and they belong in a follow-up. Neither of them tests for a commit, and changing them widens this slice's test surface without serving its Changelog.

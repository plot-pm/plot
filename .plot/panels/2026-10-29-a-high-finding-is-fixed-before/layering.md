Ran: `pnpm install` in the worktree, then `vitest run test/workflows-agent-loop.test.ts -t "row 13|checks pass"` (6 passed: a green settle writes `declaration, slice-spend, assignment-clear`), and a node probe of `reviewBypasses` with one clean `success`, one accepted-HIGH `success` and one `failure` (answer `{"bypasses":[3]}`: the domain cannot tell the first two apart).

## (a) Problem statement

- `review.ts:494` is correct: `const state = counts.high === 0 ? 'success' : 'failure'`. `openFollowUp` is called for any finding count above zero (`review.ts:486-488`). Both facts hold.
- The status decision lives in an entry, not in the domain. `review.ts:494-519` composes state and description inline. The plan changes exactly this decision (success with a ticket) and does not say where the new decision lives. Under the layering rule and *every rendered state is a domain property*, it belongs in a domain rule.
- The board-impact comment is wrong. It says `plot-reconcile-scan.sh` and the board's review badge "read [the description] as text today". §20a (`plot-reconcile-scan.sh:2648-2667`) prints the answer of `board/plot-review-bypass.mjs`, which calls `reviewBypasses` over `PrReviewReading` (`ports/host.ts:143-150`: `sha`, `state`, `bypass`; no description). The probe shows a ticketed-HIGH `success` and a clean `success` give the same answer. The design's claim that "`plot-reconcile-scan.sh` and a reader can tell an accepted HIGH from a clean review" holds only for a person reading the GitHub UI.
- A cause is missing: the PR index cannot answer "review on this head has a HIGH". `PrIndexRow.review` (`entities/pr-index.ts:41`) holds the GitHub review decision (`APPROVED | CHANGES_REQUESTED | REVIEW_REQUIRED | ''`, `entities/pr.ts:38`), not the `plot/review` commit status. The HIGH fact exists only as `failure` on the head (via `host.prReview`, a per-PR host call) and in the verdict file. The plan's rule "reads it as a value" without naming the record the value comes from.

## (b) Approach, through this lens

1. **Arm 1 ("HIGH, desk alive → correction") cannot work on today's agent loop. This is a fact the design missed.** The reviewer starts only on CI green (design table, row 3). On CI green the desk's loop takes ROW 13 (`agent-loop.ts:455-478`) and seals: `declaration`, `slice-spend`, `assignment-clear`. The desk is then a free loop that no longer holds the branch. The loop resumes an agent only from `agent-resume` writes on red checks, a dropped turn or a continuation (`worker-loop.ts:1848-1872`). `correctionText` comes from the CI run evidence (`worker-loop.ts:1077`), never from an appended `PLOT-CORRECTION.md`. A correction that fleetd appends through `Desk.appendCorrection` (`ports/desk.ts:137-145`) is therefore read by nobody. The process stays alive, so arm 2 never fires either, and the PR holds on `failure` with no stall from the plan's own arms. Either the agent loop gains a domain row ("a free loop whose last slice has a review correction re-takes that slice"), with its own tests in `workflows-agent-loop.test.ts`, or "desk alive" is defined as "a live worker assigned to this PR's branch" and a sealed desk takes the fixer arm. The plan must pick one and name it as a correction of the design's call.
2. **Arm 2 starts a second fixer while the first one runs.** The fixer runs in its own worktree (design, *Role agents*: isolation `worktree`). The desk stays dead, the review on the head still shows `failure` until the fixer pushes, so the next tick reads the same values and answers "start fixer" again. The rule needs a reading "fixer in flight on PR #n" (from the attempts record, written before the start), or "one writer per branch" fails.
3. **The attempts record must be written before the start.** The plan says "written by one place". It must also say *when*: the tick reserves the attempt in the record, then calls `agent-run`. A crash between start and write otherwise refunds an attempt and permits a third fixer.
4. **The ticket write is not idempotent and needs a record.** `Tracker.issueOpen` (`ports/tracker.ts:400-417`): "the same call twice opens two issues … The caller records what it opened." A tick that re-evaluates on every pulse opens a ticket per pulse unless a recorded "ticket for PR #n: pending | <id>" is written before the ask and read by the rule. `review.ts:251-280` (`openFollowUp`, the `pending` issue file and `ISSUE_MAY_EXIST`) already solves this. The success write must read the ticket id from that record, not from an in-memory step result, so a crash between the two steps resumes correctly.
5. **The tracker port cannot assign.** `IssueOpen` carries `title`, `body`, `labels` only (`ports/tracker.ts:123-130`). "Assigned to the plan's author" widens the port and every connector (GitHub, Jira, Bitbucket). That is a port change and belongs in a named slice. The plan also does not say how the plan's author is read (no field in the plan's `## Status`) or mapped to a tracker account (`People`, `jira:` prefix in `tracker-listers.ts:10-31`).
6. **The ticket is opened through a resolution that lives in an entry.** On a repository with no declared `Tracker`, the git-host tracker's `issueOpen` answers `unaskable`; only `review.ts`'s local `reviewTracker` (`review.ts:560-575`) swaps in `githubIssueOpen`. fleetd's tick cannot reach an entry-local function. The resolution must move to an adapter export, or fleetd opens no ticket on any GitHub repository without a `Tracker` key, including this one.
7. **Duplicate HIGH tickets across plans.** #2900 stops `plot-review` from opening an issue for MEDIUM and LOW only. A HIGH review still opens a follow-up issue at review time (`review.ts:486-488`). This plan then opens a second ticket after attempts are spent. The design says a ticket exists "only for a HIGH the fleet could not fix". One of the two plans must stop the review-time HIGH issue, or this plan must reuse it.
8. **Two rules decide the fixer for the same desk.** Arm 4 (CI red, desk dead) and #2915's `freshSessionFailedFixer` both answer "start the fixer" from overlapping readings. The design asks for one rule with exactly one next step. Arm 4 should be the only decision, and #2915 should feed it a reading.
9. **What passes:** no new shell (the shell ratchet in `scripts/check-shell-lines.sh` is not touched); the ticket goes through the tracker connector, never `gh`; the merge stays with `workflows/merge.ts`, which re-asks the host, so the destructive step is covered. The attempts file is fleetd's own record of a step it took, not a bought answer, so a decision may read it.

## (c) Slices

- **A slice is missing: the tick.** Slice 1 builds the rule and the attempts file; slice 2 builds the ticket and the status. No slice makes fleetd act on arms 1, 2 and 4 (write the correction, start the fixer). #2915 assumes "#2903 (the fixer runner and the attempt count)". #2902 has a separate tick slice; this plan needs one too, after #2898's `agent-run` role parameter.
- A port slice is missing for the assignee (finding 5) and for the tracker resolution export (finding 6). Both can precede the ticket slice and merge on their own.
- If finding 1 is solved by a new agent-loop row, that row is its own slice in `workflows/agent-loop.ts`.
- Order: rule → (agent-loop row | none) → tick → tracker port → ticket. The ticket slice waits for the tracker port slice.

## (d) Open questions

- **Q1 (who writes `success`):** A second writer already exists: `entry/approve.ts:72-95` writes `plot/review` `success` with `approved by <who>` for plan PRs through `host.commitStatus`. Writing the status needs no judgement (design goal 4), so the reviewer agent does not need to re-run. Recommend a domain rule `reviewStatus(counts, ticket | null)` that answers `{ state, description }` and is used by both `review.ts` and a domain workflow `acceptHigh` (ports: tracker, host) that fleetd's tick calls. A ticketed-HIGH write then cannot be composed without a ticket id. That is the gate the plan wants.
- **Q2 (alive, corrections spent):** With corrections spent, ROW 15 (`agent-loop.ts:500-506`) ends the loop with a `PLOT-BLOCKED` marker and a `loop-end`. That desk is not live. The real gap is the sealed desk (finding 1). Define "alive" as a running worker whose assignment is this PR's branch.
- **Q3 (`trackerNone`):** The decided rule is "an unfixed HIGH passes `plot/review` only through its ticket". With no ticket, the PR holds, and #2899's stall rule notifies. It must not merge. The case is wider than `trackerNone`: any undeclared tracker on a non-GitHub host answers `unaskable` (finding 6).
- **Q4 (one or many tickets):** One ticket per PR head. `reviewVerdict` reads only counts (`review-verdict.ts:15-38`), so findings are not individually addressable today.
- **New:** Where does the rule read "review on this head has a HIGH"? Today only `host.prReview` (a per-PR host call, `state: failure`) or the verdict file. Either #2900's review record writes this into a file fleetd reads, or the rule takes a fresh host reading. That contradicts *A Decision Reads The Index* unless the plan names it as an accepted exception.
- **New:** What key does the attempts record use for a desk with no PR, which #2915 reads?

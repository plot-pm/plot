## (a) Problem statement

- `review.ts:494` writes `failure` for any HIGH count above zero: correct. `openFollowUp` (`review.ts:269`) runs for any finding of any severity (`review.ts:483-488`): correct.
- "Nothing reads a HIGH and starts a fix": correct. The only writer of `PLOT-CORRECTION.md` is the desk's own loop (`worker-loop.ts:1663`, `:1858`, `:1865`), and it reacts only to CI and dropped turns, never to `plot/review`.
- **Missing cause, and it breaks arm 1.** When CI turns green the desk loop seals the slice and clears its assignment: `agent-loop.ts:460-475` (row 13), verified by the test run above. The reviewer starts only on green CI (#2917). So when a HIGH review exists, the desk loop no longer holds the branch. It is free, or it has hopped to another slice in the same worktree. "Desk alive" in the plan's sense almost never holds when a HIGH lands, and a correction written into that worktree either reaches no session or reaches the wrong slice.
- The Open Questions say #2900 and #2902 "name no plan yet". This is false: PR #2917 and PR #2914 exist. The plan also says the fixer role definition comes from #2902. It comes from #2898 (PR #2908). #2898 is a missing prerequisite.
- The board-impact note says `plot-reconcile-scan.sh` reads the status description as text. Section 20a reads the state only. Ran: `reviewBypasses` over an accepted-HIGH `success` (#1) and a `failure` (#2) answers `{"bypasses":[2]}`. An accepted HIGH cannot be told apart from a clean review there. The design's sentence "so `plot-reconcile-scan.sh` ... can tell" has no reader today.

## (b) Approach, judged against the anti-goal and the safety rules

1. **Two fixers on one PR (one writer per branch broken).** Arm 2 reads "desk dead, attempts left". A fixer runs in its own worktree (#2908 table: isolation `worktree`), so it leaves no pid in the desk's pid sources. Ran: `deskLoopAlive({pids:[{source:'.plot-worker.pid',pid:''}]})` answers `none` while the fixer runs. After attempt 1 is counted, one attempt is still left. So the next tick takes arm 2 again and starts fixer 2 beside fixer 1. The in-process guard (`fleet-clock.ts:85-95`) stops overlapping ticks only. It does not stop a later tick, and a fleetd restart loses it. The rule needs a recorded "fixer running on this PR" reading (pid plus start time, with the TTL pattern of `in-flight-store.ts`) that holds the arm. A live fixer must count as alive in the `continue` and `restart` refusals too. Otherwise a person's `/plot-continue`, or the unblocker (#2913) answering the row-15 `PLOT-BLOCKED` (`agent-loop.ts:505-508`), starts a desk loop on the same branch while the fixer pushes.
2. **The order of the attempts write decides what a crash costs.** Count the attempt before the start: a crash between the two then spends an attempt that never ran, which is the safe direction. Counting after the start lets a crash produce an uncounted extra fixer. The plan leaves this to the builder. It must be stated, because the safe order is the safety property.
3. **Arm 3 is three steps, not one.** The rule "answers exactly one next step" (design, *The loop*). Arm 3 must be three states, each selected from recorded state: (i) no ticket recorded → open the ticket; (ii) ticket recorded and not `pending`, no accepted-HIGH status on this head → write the status; (iii) status `success` on this head → take #2914's merge arm with all its holds (red or stale main, a merge in flight). Arm 3 must never merge directly. A crash between any two steps then resumes at the next one.
4. **Ticket idempotency.** `review.ts:269-340` already has the safe pattern: a `pending` write first, a search for an existing issue (`openIssueOfPr`, `review.ts:229`), then the open, and a `pending` record that refuses (`ISSUE_MAY_EXIST`). The plan must reuse it. The key must be **per PR**, not per head (`review.ts:420` keys per PR and SHA). After the ticket exists, a person's push makes a new head, and a per-head key opens a second ticket.
5. **A new HIGH can pass under an old ticket.** Attempts are per PR. If a person pushes after the ticket and the new head's review finds a *different* HIGH, arms (ii)-(iii) write `success` naming a ticket that does not describe that finding. Each head's findings must be commented on the ticket before the status is written, as `openFollowUp` does per head. The status description must name the ticket and the run marker.
6. **The `success` write is a self-granted pass, so it must be a gate.** "Reads the ticket's number from the ticket step" proves only that a local file holds a string. The write must refuse unless all of these hold: the review record on this exact SHA has HIGH > 0; the attempts file reads ≥ 2 for this PR; the ticket record is a number and not `pending`; and the tracker confirms the ticket on a fresh read. Without this, any caller with the App credentials writes `success` over a HIGH, which is the bypass the design forbids. The write must stay in the one writer of `plot/review` (`review.ts`, through `host.commitStatus`). Open Question 1 below has the reason.
7. **Every irreversible step must re-ask the host, not only the merge.** The PR index's OPEN rows are not terminal (CLAUDE.md, *A Decision Reads The Index*). If a person merges or closes the PR by hand between the read and the act, the index still says OPEN. The ticket open, the status write and the fixer start must each re-read the PR state and head first, as `merge.ts` does (`head-moved`, `pr-not-open`), and refuse by name. The fixer gets the head SHA it was started for. It pushes without force, so a person's concurrent push makes it fail rather than overwrite.
8. **A failed or partial host read is not a clean answer.** A `plot/review` read that fails must read `unread` and hold. It must never read as "no review" (which starts a reviewer) or as "no HIGH" (which merges). `review-bypass.ts:8` draws the same line. On Bitbucket, `commitStatus` answers `unaskable` (`host.ts:358-372`). The plan must say that arm (ii) then holds and notifies, and never treats the write as done.
9. **The `review.ts` interaction is not covered.** #2917 removes the issue only for MEDIUM and LOW findings. So after #2917, `review.ts` still opens an issue for every HIGH at review time, before any fix runs. This contradicts *Decided*: "a ticket only if the fix fails". `openIssueOfPr` would then find that early issue and reuse it as "the HIGH ticket". One of the two plans must stop `review.ts` from opening any issue. This plan is the natural owner.
10. Layering, shell ratchet and the unattended rules: no defect found. The plan adds no shell. It keeps the ruleset and adds no bypass right. It does not touch `release`. The fixer start and the merge go through the `agent-run` port and `merge.ts`.

## (c) Slices

- Slice 1 holds the rule and the attempts file. Slice 2 holds the ticket and the status. **No slice connects the arms to the tick.** Nothing starts the fixer, writes the attempts count, or delivers a correction. #2915 also names "#2903 (the fixer runner and the attempt count)" as its prerequisite, while this plan puts the runner out of scope. The runner falls between the two plans. Add a tick slice: start the fixer through `agent-run` with the running-fixer record from (b)1, and pass the review findings to it.
- Add a slice, or a named change in slice 1, for the desk-side half of arm 1. Either the desk loop waits for a `plot/review` reading on its head before row 13 seals, and turns a HIGH into a correction itself (which keeps the single writer of `PLOT-CORRECTION.md`), or arm 1 is narrowed to "the loop's current assignment is this branch". Writing the desk's correction file from fleetd would create a second writer of that file.
- Move the `review.ts` change from (b)9 into slice 2, or name it as #2917's job.
- Slice order: the rule first, then the tick, then the ticket. Both later slices wait on #2898 (the role and the caller identity) and on #2914 (the merge arm that arm 3 hands over to).

## (d) Open questions

1. *Who writes `success`?* The reviewer *agent* runs read-only (`review.ts:50`, `:459` `capabilities: ['read-only', ...]`) and cannot write a status. The one status writer is the `review.ts` entry through `host.commitStatus`. It should gain a gated "accepted HIGH" path, and fleetd should call it as a controller. A second writer of `plot/review` would make the gate in (b)6 impossible to hold in one place.
2. *Desk alive with corrections spent?* At row 15 the desk ends with `corrections-spent` and a `PLOT-BLOCKED` marker (`agent-loop.ts:503-508`), so the desk is no longer alive and the dead-desk arm applies. The real risk is the unblocker reopening that desk while a fixer runs: see (b)1.
3. *`trackerNone`?* Hold and notify. *Decided* says an unfixed HIGH passes only through its ticket. That outranks the *Calls made* line "delivery must not stop". An `unaskable` ticket open must never lead to a `success` write.
4. *Two HIGH findings on one head?* One ticket per PR, with each head's findings as a comment on it ((b)4-5).
5. *Prerequisites?* Read #2917 and #2914 now. Add #2898.
- New: what does a CI-red PR do with both attempts spent? Arm 4 covers only "attempts left". This must be an explicit hold plus a stall notification, never a ticket-and-merge. CI red cannot merge anyway (`merge.ts` refuses `checks-not-green`), but the rule must answer the state.
- New: does a fixer that ends without pushing spend an attempt? It should, so that two silent failures reach the ticket instead of looping.
- New: does the plan need to change the Board-impact note? Yes. Nothing reads the description today (see (a)).

## (e) Tests

- Slice 1 (domain unit, vitest, `packages/domain/test/`): one test per arm, plus: a recorded running fixer holds arm 2 with one attempt left; `unread` review holds; arm 3 answers exactly one step per state (i)/(ii)/(iii); a missing or unreadable attempts file reads 0; CI red with attempts spent answers hold.
- Tick slice (fleet unit with a fake `agent-run`): two consecutive ticks start one fixer, not two; a crash between the attempts write and the start leaves the count at n+1 and starts nothing extra; a fleetd restart while the fixer runs starts no second fixer.

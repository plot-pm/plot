# Cost juror: delivery-work-items-show-gates

Lens: what the plan spends (attention, CI, blast radius, host calls, merge conflicts, artifact rebuilds), where its data comes from, and whether the plan says so.

## Findings

**1. The gate glyphs and most of the group column already exist; the plan does not say so, so a builder may pay for them twice.** Verified by reading. `packages/domain/src/rules/delivery-row-form.ts:91` holds `GATE_MARK = { running: '⟳', failed: '✗', passed: '✓' }`; `:139-146` `gateValue` renders `CI ✗ <run>` / `review ⟳|✗|✓`; `:228-233` builds `ci-run` and `review` link targets; `:43-52` already has the row shapes `slice-queued`, `slice-being-built`, `slice-at-a-gate`; `:237` renders `waits on <slice>` linked to the slice; `:406-419` `groupHeader` builds the group header. `delivery-placement.ts:16` already orders Work items as `at-a-gate, being-built, queued`. The Notes line "Deliverable search for 'gate glyphs' … found no artifact" is wrong at HEAD. The real remaining domain work is small: `gateValue` shows ONE gate (CI when read, otherwise review, `:141-145`), not both (`CI ✗ validate · review –`); there is no mark for an unasked gate; and Being built's cell is hard-coded `null` (`:238-239`). The plan should name these as the delta so the slice is sized honestly.

**2. The Open Question points at the wrong file.** Verified. `packages/board/src/app/lib/glyphs.ts` holds Octicon SVG paths keyed by item kind (`ticket`, `plan`, `pr`, …), not gate marks. The gate marks live in `delivery-row-form.ts:91`. Answering the question in `glyphs.ts` would add a second glyph table.

**3. Gate links have no data source at HEAD, and the cheapest source is not named.** Verified by reading. `itemRowFactsOf` (`packages/board/src/app/lib/agent-rows/delivery-row-facts.ts:31-57`) never sets `ciRun`, so the domain's `ci-run` link is never built. `resolveLink` returns `{ kind: 'none' }` for `ci-run` (`delivery-link-targets.ts:71-73`), and `AgentList.tsx` passes `prUrl: () => null` (around line 1097), so `pr` and `review` targets resolve to nothing either. Sources that exist without a new host call: the row's `pr.url` (`schema.ts` AgentRow `pr.url`), `checksUrlOf` (`packages/board/src/server/board.ts:2370`, used for cards at `:3004`, not for rows), and the PR index's `failing_checks` names (`packages/domain/src/entities/pr-index.ts:46`), which today reach only the stuck panel (`server/fleet.ts:7503`, `:7820`). A per-check run URL is read by the GitHub adapter (`adapters/host/github-pr-listing.ts:77`, `detailsUrl`) and then dropped; the index has no field for it. Storing it means a PR-index schema change, which this repo treats as costly (a version move makes every store fall through to the host, per CLAUDE.md "A Decision Reads The Index"). On Bitbucket/Jenkins no per-check URL exists. The plan says "links to its run" and names none of this. It should say: link the PR's checks page and the check NAME from `failing_checks`, no new host call, no index version move — or state the cost if it wants per-run links. The design's Non-goals (cited by plan 4: "no new reads from a host or tracker") binds this plan too and the plan does not repeat it.

**4. "4 commits" has no field on the payload.** Verified. AgentRow carries `localAhead` (commits not yet pushed, local-only, `schema.ts:3050`) and no count of commits ahead of the base. The server computes ahead counts in `server/monitors.ts:189` `aheadCounts` (one git spawn per branch on old git, cached per moved ref) but does not put them on the row. Progress therefore needs a server change and a contract field — no host call, but a `fleet.ts`/schema change and contract-test churn that the plan's "Board impact: changes the Work items section's rows" understates. Plan 4's "writing code · 4 commits" needs the same field; neither plan owns it, so both may add it.

**5. Fixer attempt "1/2" needs readings the board does not take, and the plan names the wrong budget.** Verified. `deliveryMapping` states it sets no `corrections` "because the payload does not state them" (`delivery-readings.ts:252-256`). The board reads `.plot/state/fixer-attempts/<pr>.json` only for planless open PRs (`server/fleet.ts:6612-6623`, `fixerInFlight`). Registry entries carry no role (`AgentEntrySchema`, `schema.ts:~3954-4010`, no `role` field), so `role: agent.role ?? 'loop'` (`delivery-readings.ts:302`) makes every agent a loop agent; fleetd fixers run from `.plot/state/fixer/<pr>` (`packages/fleet/src/shared/auto-fixer.ts:161-162`), and I found no path that brings them into the board's agent list (not fully verified — I did not trace every registry writer). The fixer's budget is `FIXER_ATTEMPTS_BUDGET = 2`, a hard-coded constant counted per finding kind (`rules/fixer-attempts.ts:5`, `:34-37`), not the `Correction budget` config key, which counts worker-loop corrections (`workflows/agent-loop.ts:237-238`). Both read 2 today, so a Done When test against `Correction budget` passes by coincidence and breaks the day either moves. Cost: one local file read per open PR per render (cheap, no host), plus a fixer-agent reading the plan does not name a source for.

**6. Plan 4 builds the same role chips, with no ordering between the two.** Verified by reading the sibling. `delivery-fleet-rows-per-agent.md` slice `feature/delivery-fleet-agent-rows` builds "role chip" and lists eight roles; `AgentRole` has six (`delivery-placement.ts:92`, no `design`, no `verify`). This plan's `feature/delivery-work-items-by-chips` says it "adds them to the row form". Both wait only on `feature/delivery-section-header`. Two branches extending one union and one chip component in parallel is a duplicate build and a near-certain conflict.

**7. Parallel slices collide on two files.** Verified by reading. Both of this plan's slices edit `itemRowCells` in `delivery-row-form.ts` (448 lines; status/by cells in one function, `:222-302`) and render in `AgentList.tsx` (1632 lines). Plan 2's `feature/delivery-you-groups` and `feature/delivery-you-plan-rows`, plan 4's agent rows (`agentRowCells`, same file `:312-334`) and plan 1's header slice touch the same two files, all released together by one `waits:` marker. Up to six branches open at once on one domain function and one component. The plan should either chain its own two slices (chips waits on gates) or say why they do not overlap.

**8. Cross-plan placements the plan relies on are not ordered.** Verified by reading siblings. "Unless plan 2's PR rule places it under You" and "closed PR … moves to You › Unblock (plan 2)" depend on `feature/delivery-you-groups`; "a not-started slice shows only in … Release delivery (plan 5)" depends on `feature/delivery-release-plan-rows`; "My sprint applies here" depends on plan 1's `feature/delivery-my-sprint-scope`. None is a `waits:` target. Removing not-started slices from Work items before plan 5 lands hides them from the tab for the interval — a visible regression whose length depends on merge order. Plan 1's scope slice already claims to apply the scope to Work items, so this plan building it too is duplicate work.

**9. "Rebuild the board artifact with each slice" contradicts a CI gate.** Verified. `scripts/check-no-bundle-diff.sh` refuses a PR that carries a generated bundle; `main` builds bundles after every merge (#1249). All seven active plans carry the same sentence (grep count 7), so this is the batch's defect, not this plan's alone, but following it here costs a refused commit and a CI round trip per slice.

**10. "Oldest waits <age>" is cheap.** Verified. Row `ageMinutes` exists (`schema.ts:2772`) and reaches `ItemRowFacts.ageMinutes` (`delivery-row-facts.ts:50-51`, minimum across the item's rows). The header's oldest is a max over placed items — a pure domain function, no new reading.

## Summary of cost

No new host call is needed if the plan settles for the PR's checks page and the check names already in the index. The unstated costs are: a payload field for commits ahead (server + contract), a fixer reading for every open PR plus a source for fixer agents and roles that does not exist at HEAD, an unnamed overlap with plan 4 on roles, and two parallel slices on one function that four sibling slices also edit. The plan should state these and correct the budget key, the glyph file and the artifact line.

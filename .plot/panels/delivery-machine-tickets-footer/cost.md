# Cost lens: delivery-machine-tickets-footer

Position: amend

Lens: what the plan spends (attention, CI, host calls and rate budget, board-artifact rebuilds, the wait on plan 1, Delivery-tab blast radius) and whether it says so.

## Findings

- blocks: The plan orders "Rebuild the board artifact (`pnpm build:board`) with each slice that changes the board" (plan line 22). CLAUDE.md (Testing) says a PR diff must carry no generated bundle: `scripts/check-no-bundle-diff.sh` refuses it at commit time and in CI, and `main` builds the bundles after merge. All three slices change the board, so each would follow an instruction that its own CI gate refuses. The Changelog's "Board impact" line should say "no bundle in the PR; run `pnpm build:board` only to test locally".
- misleads: "no host call is added" is stated only as intent ("the plan names the gap rather than adding a host call", line 40; spec line 221). It is mostly true, but the plan never says which readings exist. At HEAD the payload carries `prAgeSeconds` and `prNextInSeconds` (`packages/board/src/contract/schema.ts:4548,4565`, set at `packages/board/src/server/fleet.ts:8679`). `readMachine` (`packages/fleet/src/shared/machine-reading.ts`) holds spawn cost, load average and cores, but I found no field carrying them to the board payload (grep of schema.ts for machine/load/cores: no payload field). I also found no "CI queue" count and no remaining/limit value for GitHub (schema.ts has `prSpenders` and a bound, not "4,210 / 5,000 left"; "GraphQL"/"resets" do not occur). So the healthy line's four figures (load, cores, GitHub left, CI queue) have three or four gaps, and each gap costs either a new payload field and a new scan read or a dropped figure. The plan counts none of them.
- misleads: Open Questions lists only the next-read question. Load/cores/CI queue/GitHub budget are the larger unknown and are missing. The next-read question is answerable now: `prNextInSeconds` exists and is null where no reader has scheduled a read (schema.ts:4565-4580), so with no fleetd the footer shows age only. File it as Settled, with that degradation stated.
- misleads: Every slice waits on `feature/delivery-section-header` of plan 1 (plan lines 34, 68-76). That is one shared dependency for 3 slices, which is cheap in attention only if plan 1's slice 1 lands first. Plan 1 itself lists "slices 2 to 4 carry no waits" as an open defect (`delivery-tab-header-and-my-sprint.md:67`). The plan does not say what the three slices do while plan 1 is unmerged: they cannot start, and the Delivery tab has no Tickets target in the meantime (plan 2's own open question, `delivery-you-blocks-or-feeds.md:63,93`, depends on this plan). Name the order: plan 1 slice 1, then these three in parallel.
- misleads: The three slices are independent after the header, but all touch `packages/board/src/app` Delivery components and probably `schema.ts`; the plan does not warn of merge collisions on those shared files (each requires a rebase and a full `test:board` run in CI). Three small PRs is the right size; the cost is stated nowhere.
- cosmetic: Blast radius is understated. The Machine text "none — nothing — a machine is working" lives in `packages/board/src/app/lib/agent-rows/host-notes.ts:24` and carries documented rulings (host-notes.ts:176-206, "a board that has not asked the host prints no `none`"). The plan says those rulings "stand", which is right, but removing the default hint touches a file whose tests encode those rulings; say so in the slice.
- cosmetic: "<n> more unassigned" in the Tickets header needs an unassigned count. `waiting-view.ts:91` already carries `waiting.unassigned`, so no new read is needed. The plan could say so and thereby support its no-new-host-call claim.

## Verdict on the claim
"No host call is added" holds only if the missing readings (GitHub left, CI queue, load/cores in the payload) are dropped or taken from data already on the machine. That choice is a cost decision and belongs in Open Questions.

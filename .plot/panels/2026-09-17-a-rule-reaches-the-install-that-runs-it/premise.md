# Premise lens — a-rule-reaches-the-install-that-runs-it

Position: amend

The defect is real, the fix direction is right, and **the stated cause is false**.
The plan says the rule sources cannot be imported "because they are TypeScript
and the plugin cache has no build." Node 24 imports them fine. What fails is one
missing runtime dependency — `zod` — reached through `machine.ts`. Measured
against the exact install the report names.

---

## 1. Is the problem real, and stated correctly?

**Real: yes.** **Stated correctly: no.**

The install in the report exists on this machine, at the path the error quotes:

```
$ ls -d ~/.claude/plugins/cache/plot-marketplace/plot/2.17.0/packages/domain/src
.../plot/2.17.0/packages/domain/src            # present
$ ls -d .../plot/2.17.0/node_modules .../plot/2.17.0/packages/domain/node_modules
ls: No such file or directory                  # both absent
$ ls -d .../plot/2.17.0/packages/*/dist
no matches found                               # no build, as the plan says
```

`--start` imports two modules (`plot-dispatch.sh:1928` and `:1931`). I ran each
against that install:

```
=== [A] fleet-size.ts from the REAL plugin install ===
OK: DEFAULT_FLEET_SIZE,fleetSize

=== [B] machine.ts from the REAL plugin install ===
Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'zod' imported from
  .../plot/2.17.0/packages/domain/src/entities/machine.ts
```

**The TypeScript rule imports successfully.** Type stripping works; `node
--version` is v24.4.1. The `.ts` extension is not what fails.

The reason is visible in the source. `fleet-size.ts:1` is `import type { Headroom }
from '../entities/machine.js'` — erased at strip time, so nothing is resolved.
`machine.ts:1` is `import { z } from 'zod'` — a **value** import, resolved at
runtime, and the plugin cache has no `node_modules`.

So the plan's sentence **"All 40 rule sources ship; none of them can be imported,
because they are TypeScript"** is false on both halves. There are 43 rule
sources, not 40; and only 4 of them import `zod`. The other 39 import cleanly
with no build and no `node_modules` — verified for two of them in a tree with
`node_modules` absent:

```
rules/reapable.ts      IMPORTS OK
rules/movable.ts       IMPORTS OK
```

Those two are the rules `plot-reap.sh:206` and `plot-release-refs.sh:155` import
the same way. **They work in a plugin install today.** That is the direct
disproof of the plan's cause: if TypeScript-in-a-plugin-cache were the failure,
those would fail identically. They do not.

The sharpest confirmation is `headroomFor` itself — the only thing `--start`
uses from `machine.ts`:

```ts
export const headroomFor = (spawnCostMs: number | null): Headroom => {
  if (spawnCostMs === null) return 'unmeasured';
  if (spawnCostMs < HEADROOM_THRESHOLDS.clearBelowMs) return 'clear';
  if (spawnCostMs > HEADROOM_THRESHOLDS.starvedAboveMs) return 'starved';
  return 'tight';
};
```

Pure arithmetic. It touches no zod. The import dies on `HeadroomSchema`, a
**sibling export in the same file** that `--start` never calls.

**What the plan gets right, verified:**

| claim | result |
|---|---|
| `git ls-files 'packages/*/dist'` is 0 | **true** — 0 |
| 24 tracked bundles under `skills/plot/scripts/board/` | **true** — 24 `.mjs` (25 files incl. README) |
| `plot-propose-stack.mjs` is among them | **true** — tracked, and 23 of the 24 ship in the 2.17.0 install |
| the report's "would fail identically" is false | **true** — it is a tracked bundle and reaches the install |
| `plot-propose-stack.mjs` is 1.9 KB vs `plot-ask.mjs` 491 KB | roughly — measured **2,820 B** and **514,272 B** (2.8 KB / 502 KB) |

**One correction the plan states too broadly.** It writes:

```
$ git check-ignore -v packages/domain/dist
(no output — not ignored, simply absent)
```

True for `domain`. **False for `board`:**

```
$ git check-ignore -v packages/board/dist
packages/board/.gitignore:2:dist/	packages/board/dist
```

So "the bundles have never been committed; they exist only in a development
checkout" holds, but `packages/*/dist` is *partly* ignored. The plan corrects the
report's reading and then overstates its own. Minor, but this plan's whole
argument is that a misstated condition costs more than silence.

## 2. Is the proposed change the right fix, or a symptom fix?

**The direction is right; the argument for it is not the one that holds.**

A tracked bundle under `skills/plot/scripts/board/` genuinely fixes this: esbuild
inlines `zod`, so the dependency stops being resolved at runtime. It follows the
settled `a-shell-script-asks-the-domain` shape, the route is machine-checked
(`bundles.generated.ts` is generated by `build.mjs` and its freshness asserted by
`test/reconcile/resolveartifact.test.mjs`), and the cost rule fits — `--start`
runs once per operator command, not once per agent per pass.

**But the plan reaches the right answer from a false premise, and that has two
consequences it does not see:**

**(a) The blast radius is understated.** The plan frames `--start` as "the one
caller that went a different way and imported the source." Three scripts import
domain `.ts` directly:

```
plot-dispatch.sh:1928      rules/fleet-size.ts   + entities/machine.ts
plot-release-refs.sh:155   rules/reapable.ts
plot-reap.sh:206           rules/reapable.ts
```

The other two survive **only because `reapable.ts` happens to import nothing but
types**. That is luck, not design — and it is load-bearing luck. One future
`import { z }` added anywhere in their transitive value-graph silently breaks
reaping and ref-deletion in every plugin install, with no gate to catch it. The
plan converts one caller and leaves two sitting on the same undeclared
precondition, believing it has addressed a general cause.

**(b) A cheaper fix exists and is not considered.** Moving `HeadroomSchema` out of
`machine.ts`, or importing `headroomFor` from a zod-free module, would fix
`--start` with no new bundle. I am **not** recommending it — the bundle is the
better long-term shape and matches the settled rule — but a plan that
misidentifies the cause cannot weigh the alternative, and this one does not
mention it. It should say why the bundle wins over removing the dependency.

## 3. Does `Done when` contain a gate that cannot be satisfied by plumbing?

**Partly — and the strongest-sounding gate tests the wrong condition.**

Gate-by-gate:

| gate | verdict |
|---|---|
| "tracked in git, asserted by `git ls-files`" | **real gate**, objective, but weak — passes on any committed file |
| "under 50 KB" | **real gate** — measurable, and would catch the wrong import path |
| "number identical to today's for the same machine reading, compared on one reading" | **strong gate.** Explicitly forbids asserting a constant; forces both paths on one input. Cannot be plumbed |
| "refusal names the condition that failed, asserted for a missing bundle and a wrong node major **separately**" | **strong gate.** The word `separately` is what makes it one — a single generic message fails it |
| "`--start` in a development checkout behaves byte-identically" | **real gate** |
| `test:contracts` + `test:board` pass | standard |

**The headline gate is miscalibrated.** It reads:

> `--start` answers from a tree carrying **no** `packages/domain/` at all, pinned
> by running it against a copy with that directory removed — **the condition a
> plugin install is in**

The parenthetical is **false, and I measured it**: the real 2.17.0 install *has*
`packages/domain/src`. Its condition is *directory present, `node_modules`
absent*.

This gate is satisfiable and still leaves the bug reachable. A tree with no
`packages/domain` passes trivially once the bundle exists. It does not prove the
bundle inlined `zod` — an implementation that bundled `fleet-size` but left
`headroomFor` resolving through `machine.ts` would pass the stated gate and fail
in the actual install. **Amend it to: `node_modules` removed and
`packages/domain/src` present.** That is the measured condition, it is strictly
harder, and it is the only one that pins the real defect.

## 4. What the plan claims that I could not verify, or found false

**False:**

1. **"none of them can be imported, because they are TypeScript and the plugin
   cache has no build."** Disproved twice — `fleet-size.ts` imports cleanly from
   the real install, and `reapable.ts`/`movable.ts` import cleanly with no
   `node_modules`. The cause is a missing `zod`, not the `.ts` extension.
2. **"All 40 rule sources ship."** `ls packages/domain/src/rules/*.ts | wc -l`
   → **43**. Only **4** import `zod`; 39 import without any build.
3. **"`--start` is the one caller that went a different way."** Three scripts do
   (`plot-reap.sh`, `plot-release-refs.sh`, `plot-dispatch.sh`).
4. **"the condition a plugin install is in"** — the install carries
   `packages/domain/`. Verified by `ls`.
5. **"not ignored"** — true of `domain`, false of `board`
   (`packages/board/.gitignore:2`).

**Unverifiable as stated:** the design comment at `plot-dispatch.sh:1908` claims
this is "the same shape `plot-reap.sh` uses for `reapable.ts`." It is not the
same shape in the way that matters — `reapable.ts` reaches zero value imports and
`machine.ts` reaches one. That comment is part of the defect and the plan does
not name it.

**Correct and load-bearing:** `dist` untracked (0), 24 bundles, `plot-propose-stack.mjs`
tracked, the report's "would fail identically" refuted, the `plot-ask.mjs`
18.3 s argument, bundle sizes.

## 5. What a premise reader would notice that the plan missed

1. **The message will still be wrong.** The plan's whole framing — "a refusal that
   names the wrong condition costs more than one that says nothing" — is right,
   and it then writes a refusal for *missing bundle* and *wrong node major*. The
   condition that actually failed here was **neither**: it was an unresolvable
   runtime dependency. Implemented as written, the next operator hitting a
   variant sees a message naming two conditions that hold. The plan reproduces
   the defect it diagnoses, one layer up. The refusal should surface the
   import error rather than substitute a guess for it — note `2>/dev/null` at
   `plot-dispatch.sh:1932` discards the very text that identified this bug.

2. **`2>/dev/null` is the reason this took a bug report.** The `ERR_MODULE_NOT_FOUND`
   naming `zod` was printed by node and thrown away by the script, leaving an
   empty `$start_answer` and a hand-written guess. The plan never mentions it.
   Capturing stderr into the refusal is a smaller, independently valuable fix.

3. **No gate stops the next one.** `reapable.ts`'s zero value-imports is an
   undeclared invariant with no test. Nothing fails if someone adds `import { z }`
   to it or to anything it reaches, and the breakage appears only in installs no
   developer runs. A contract test — *every domain module a shell script imports
   resolves with `node_modules` absent* — is the gate this estate's own "Gates
   Over Rules" section asks for, and it would have caught this class at
   authoring time. The plan ships a point fix for one of three call sites.

4. **The bundle count will drift.** The 2.17.0 install ships 23 of the 24 tracked
   bundles (`plot-slice-spend.mjs` is newer). Expected, but it means "24 tracked
   bundles reach every install" is true of the repo and not of any given
   release — worth stating precisely in a plan whose argument rests on it.

---

## What would move me to proceed

Three amendments, all to the Design and the gate, none to the chosen fix:

1. **State the real cause.** `machine.ts` imports `zod` as a value; the plugin
   cache has no `node_modules`. TypeScript type-stripping works and is not the
   failure. Drop "all 40 rule sources ship; none can be imported."
2. **Amend the headline gate** to *`node_modules` removed, `packages/domain/src`
   present* — the measured condition of a plugin install, and the only form that
   pins this defect.
3. **Name the two sibling callers** (`plot-reap.sh`, `plot-release-refs.sh`) as
   surviving on an undeclared invariant, and either gate that invariant or record
   it as the follow-up.

The fix is right. The reasoning is wrong in a way that weakens the gate, and this
plan's own thesis is that a confidently misnamed condition is worse than silence.

## (a) Problem statement

- **The decision the plan replaces is in `rules/ending-action.ts`, not in `rules/fresh-agent.ts`.** `fresh-agent.ts:52-75` only composes the prompt text. The verdict "second failure asks a person" is `endingTableAnswer` at `ending-action.ts:351`, `:354` and `:361` (`priorFreshSessions > 0 ? 'needs-a-person' : 'start-fresh'`), applied by `freshAgentDecisions` (`registryd.ts:1011`) and `applyFreshAgentDecisions` (`registryd.ts:1139`, called at `registryd-main.ts:1872`). The plan names neither file. A new rule `freshSessionFailedFixer` that sits next to `endingAction` without changing it gives two answers for one desk: `needs-a-person` writes a `PLOT-BLOCKED.md` marker, and the new rule starts a fixer.
- **The fresh-agent record holds starts, not failures.** `ports/fresh-agent-record.ts:3-18` stores plan, branch, worktree, `at` and `runUrl`, with one row per start. "The fresh session has failed" can only be derived as "a second fresh-earning ending arrived while `priorFreshSessions > 0`". The plan should state that derivation.
- **`dispatch.ts:42` is a doc comment** (the `DispatchAvailability` docblock). The unattended refusal is in `workflows/dispatch-verbs.ts:194-199`, and `PLOT_UNATTENDED` is read at `board/src/server/restart.ts:68`. `fleet/src/shared/restart-command.ts:41` carries the flag between the two.
- **`dispatch-verbs.ts` is in `packages/domain/src/workflows/`**, not in the board's `server/`.

## (b) Approach, read against the anti-goal and the safety rules

1. **Two rules give conflicting answers for the same dead desk (a HIGH safety finding).** The restart rule's population is "claimed, worker `failed`/`ended`/`none`, no PR, no marker". `endingAction` already answers for every desk in that population that carries an ending:
   - `nothing-done`, no PR: `endingAction` answers `release-claim` (probe). The restart rule answers `restart`. If one tick applies both, the release removes the claim and the restart starts a worker on an unclaimed branch. A dispatch on another machine can then claim the branch, and two writers push to it. This breaks *one writer per branch*.
   - `permission-denied`, `unstarted`, `run-limit`, `checks-unanswered`: `endingAction` answers `needs-a-person` on purpose, because a new session meets the same failure (`ending-action.ts:201-217`). The restart rule fires before the marker exists, or where the marker write failed (`applyFreshAgentDecisions` records no ask then, `registryd.ts:1120-1124`). Each restart then hits the same refusal. `continueOnDesk` bounds this at `Slice max runs`, default 12 (`rules/run-limit.ts:13`; checked at `continuation.ts:938-940`), so it is 12 paid runs, not an infinite loop.
   - `bound`/`unreadable`/`quiet` with commits and no PR: `endingAction` answers `start-fresh` the first time. A restart in the same tick races the fresh start. The continue lock (`continuation.ts:854-858`) refuses the second start, so this is wasteful but not unsafe.
   **Amendment:** the restart rule must run only on desks that `endingAction` answers `leave` for, or on desks with no ending file. Better still, it should become one more row of `endingAction` (a `restart` verdict), so one rule answers each desk once. This follows the design's goal 4.

2. **The fixer start bypasses the per-desk continue lock.** Restart and the fresh session both start through `continueOnDesk`, which takes `takeContinueLock(worktree)` before any read or write (`continuation.ts:854-858`). A person's `POST /api/continue` or `/api/restart` therefore loses the race cleanly with `loop-alive`. The plan starts the fixer through the `agent-run` port, which takes no such lock. `restartWorker` and `continueTarget` read the worker loop and the manifest, and a `claude -p --agent fixer` process writes neither. While a fixer runs on a branch with no PR (case 3 below), the following each start a second writer: a person's restart, the plan's own restart rule, or the unblocker from #2913 answering a marker. **Amendment:** the fixer start takes the desk's continue lock for its whole run, or leaves a record that `restartWorker` (`dispatch-verbs.ts:222-233`) and `continueTarget` read as a live loop. Add a test in which a restart during a running fixer refuses.

3. **A fresh session can fail with no PR, and the fixer is a PR role.** `endingAction` answers `needs-a-person` for a second `bound`/`unreadable`/`quiet` ending whose branch holds commits but no PR (probe: "bound, commits, no PR, second => needs-a-person"). The design defines the fixer as "start fixer on the PR" (*The loop* table). The plan does not say what happens to that desk. If the fixer starts there, finding 2 applies. If nothing starts, the desk waits for a person, and goal 1 fails. **Amendment:** name this case. The candidate answer is a restart under the run limit, plus a stall notification.

4. **"Fixer runs `isolation: worktree` on the PR's branch" conflicts with the desk worktree.** The dead desk's worktree still has the branch checked out (`freshAgentCandidateTrees` reads it as a desk). `git worktree add` refuses a branch that another worktree has checked out. Either the fixer works inside the desk worktree, which the reaper and the restart rule must then see as occupied, or it uses a detached worktree and pushes to the branch, in which case the desk's local branch diverges from origin. **Amendment:** choose one, and state how `plot-reap.sh` and the restart rule see a desk while a fixer runs.

5. **After two failed fixer attempts, a red PR must never take the merge arm.** The plan says: "After both fail, the PR merges with the HIGH finding ticketed". A failed fresh session is a red build (`corrections-spent`), not a HIGH finding. The design's merge-with-ticket row exists only for HIGH review findings, and *The loop* table has no row for "CI red, attempts spent". Under the anti-goal that row is *hold and notify*, never *merge*. The `plot/review` ruleset would refuse the merge anyway, but `slice-pr-next` would keep selecting the merge every tick. **Amendment:** state "CI red, fixer attempts spent → hold; the stall rule notifies", and add a test that pins it.

6. **The fixer start duplicates #2903, and so does the controller change with #2898.** #2903 arm 4 ("CI red, desk dead or corrections spent → start fixer, same two attempts") already covers a failed fresh session, because that desk is dead and its corrections are spent. Two rules that start fixers on one PR in one tick double-start and double-count. #2898's slice `feature/fleetd-caller-identity` already lifts the unattended refusal on `restart` for fleetd's caller. **Amendment:** this plan changes `endingAction` so that a second fresh-earning ending on a PR-bearing desk answers a non-escalating verdict (no marker), hands the PR to `slice-pr-next`'s arm 4, and starts nothing itself. The restart slice only *calls* the lifted controller, and does not change it.

7. **Crash mid-step.** The fresh session already records before it starts, through `beforeStart` (`registryd.ts:1145-1158`): a crash after the append counts the attempt, and a refused start records nothing. The fixer attempt must use the same order. If it appends after the start, a crash between start and append gives a third attempt. A restart writes the manifest under the lock, so the next tick reads `running` and does nothing. That part is safe.

8. **A host call that fails or answers partially.** `restartWorker` refuses `pr-unanswerable` (`dispatch-verbs.ts:208-213`), and `restartBranch` refuses when the process table is unreadable (`restart-command.ts:129-131`). Both are safe. The fixer attempt count, however, inherits #2903's "a missing or unreadable file reads as zero attempts". For the one fresh session that was a deliberate choice (`fresh-agent-record.ts:44-47`). For fixers it allows a new opus fixer on every tick while the file stays unreadable, unless the append in `beforeStart` also fails. **Amendment:** a fixer start requires its record append to succeed (`beforeStart` returns false otherwise), so an unwritable store starts nothing.

9. **fleetd must call `restartBranch` in-process, not the board route.** `restart.ts` is an HTTP handler that needs a running board. fleetd starts fresh sessions through `continueOnDesk` directly. The restart should go through `restartBranch` (`fleet/src/shared/restart-command.ts:114`), the same controller that `plot-restart-command.mjs` reaches. This keeps *The Master Agent Uses The Controllers* and avoids a board dependency. Minor: `RESTART_ANSWER` (`restart-command.ts:19-20`) says "A person restarted this worker". That text is wrong when fleetd is the caller.

10. **No release path.** The plan touches no release path, so *release never* is not at risk here.

## (c) Slices

- Slice 1 as written duplicates #2903's arm 4. Re-cut it as "endingAction stops escalating a second fresh-earning ending on a desk with a PR, and leaves it to slice-pr-next". It changes one rule and starts nothing. Its prerequisite is #2903's rule slice, not the whole of #2903.
- Slice 2 should be "a `restart` row in `endingAction` / a restart rule that defers to `endingAction`", called through `restartBranch`. Its prerequisite is #2898's `feature/fleetd-caller-identity` alone.
- The two slices are not independent as the plan claims ("can run in parallel"). Both change the verdict for the same desk population (`bound` with no PR is in both), so they need an order. Slice 2 goes after slice 1, or both go into one slice.

## (d) Open questions

- *Does a restart count as a fixer attempt?* No. Restarts are already bounded by `Slice max runs` (default 12, counted from the manifest, `continuation.ts:938`), which is a separate budget. Agree with the recommendation.
- *Which record holds the fixer count?* #2903's file. It must be appended before the start (finding 7), and an append failure must refuse the start (finding 8).
- *How long before a restart?* `Claim stale after` is 24 (hours) in this repo's config, which defeats goal 1 for a desk that died quickly. A safer gate needs no clock. Require all of these: no manifest names the desk; the worker reads `failed` or `ended` with a recorded exit (`plot-worker-state.sh`: these are recorded exits, not absences); and `endingAction` answered `leave`. For `none`, which means no record at all and can be a dispatch that has not spawned yet, require the claim to be older than one supervisor tick plus the dispatch bound. Never restart `none` in the same tick that saw the claim appear.
- *`elsewhere`?* Never. `restartBranch` refuses `no-worktree` anyway (`restart-command.ts:120-123`), but `restartWorker` returns `decided` for `elsewhere` (probe), so the domain rule must exclude it itself.
- New: what does fleetd do about a `stalled` desk (uncommitted or unpushed work, no PR, no ending)? `restartWorker` accepts it (probe), and the plan's state list leaves it out.
- New: what happens when a person removes or answers the marker while the fixer from #2903 runs on the same PR? See finding 2.

## (e) Tests

- Domain unit (vitest, `packages/domain/test/rules-ending-action.test.ts`): a second `corrections-spent` with an open PR answers the new non-escalating verdict and writes no marker. The same ending with no PR answers restart-or-person, as amended. `nothing-done` with no PR still answers `release-claim` and never `restart`. `permission-denied` never answers `restart`. `elsewhere` and `none`-inside-the-dispatch-window never answer `restart`.
- Domain unit for `restartWorker`: with fleetd's declared caller and `unattended: true`, it decides. With any other unattended caller, it refuses `unattended`.
- Fleet unit (`registryd` apply step with fake ports): a fixer start whose record append fails starts nothing. A crash (throw) after the append leaves one row, and the next tick does not start a third attempt. A restart while a fixer holds the desk refuses.
- Fleet unit: one tick over a desk that both the `endingAction` table and the restart rule read produces exactly one action.
- Corpus/e2e: none needed locally. CI's e2e covers the dispatch-and-restart choreography.

# Safety juror — a-slice-held-by-an-open (#3050)

Position: amend

The defect is real and the plan names the right readers on the board, but two parts of it are unsafe as written. First, Approach 1 tells the builder to combine the verdict with each branch's `held` value, and in the pulse `held` is a boolean that means "a local desk holds this branch". The evidence branch carries `"held":false`, so a literal build leaves the reported slice `eligible`. The wait is already folded into the branch `state` (`waiting`/`blocked`), and the rule must read that. Second, the dispatch refusal as worded ("no startable branch") also fires when the bridged pulse is missing, older than 15 minutes, or older than the plan's approval. In those cases `briefBranchFromPulse` already returns `null` today and the dispatch proceeds. A refusal on that `null` blocks a legitimate dispatch, and the controller rule ("what the controller refuses does not happen") gives the operator no override. The rule must also read a slice of one merged and one waiting branch as waiting, and it must never change the pulse `verdict` enum. With those amendments the change only removes offers that `plot-dispatch.sh` refuses anyway, so it cannot stall the fleet.

## Findings

1. **high — the `held` field in Approach 1 is the wrong field, and a literal build misses the evidence case.** `packages/domain/src/entities/fleet.ts:337` declares `held: z.boolean().default(false)`. `packages/domain/src/workflows/plan-walk-assembly.ts:495` sets it to `desk !== null && b.state !== 'merged'`, which records a local desk and not a wait. The `held: '' | 'waiting' | 'blocked'` parameter of `isClaimable` (`packages/domain/src/rules/eligible.ts:195-199`) is not in `FleetReading`. The scan and `plan-walk-assembly.ts:301-305` (`branchState({...readings, waits})`) fold the wait into `state`. The live pulse shows the evidence branch as `"state":"waiting","own_state":"open","held":false`. Checked with `jq` over `.plot/state/last-pulse.json`, and with `git show origin/main:` over the files above. A rule that reads `b.held` leaves the Fleet index slice `eligible`. It also marks a slice as waiting when its branch has a local desk.
2. **high — the refusal fires on an absent reading, which blocks a legitimate dispatch.** `briefBranchFromPulse` (`packages/fleet/src/shared/dispatch-command.ts:75-76`) returns `null` in two cases: when the pulse is `null`, and when `startableBranches` is empty. `fleetStateFile.readSync` returns `null` for a bridge older than `BRIDGE_MAX_AGE_MS` = 15 min (`packages/domain/src/adapters/fleet-state/fleet-state-file.ts:17,80`), so every board-free dispatch reads `null` while fleetd is stopped. `startableBranches` (`packages/domain/src/rules/auto-dispatch.ts:581-608`) also returns `[]` when the pulse predates the plan's approval (`dispatchPhase` false) or does not contain the plan. The common case is "approve, then Start work at once". Today each of these cases dispatches, and at worst it costs a brief run. A refusal on "no startable branch" turns each one into a hard stop. The board's own `pulseFor` (`packages/board/src/server/fleet.ts:3267`) is `null` on a cold cache, so `POST /api/dispatch` has the same problem.
3. **medium — "every non-deferred branch is held" leaves the mixed shapes `eligible`.** A slice of one merged branch and one waiting branch has a non-deferred branch (the merged one) that is not held, so the plan's wording keeps the bug for that slice. The safe predicate works over the unsettled branches (not `merged`, not `deferred`). It holds when none of them is startable (`dispatchable`: `open` and not `ref_held`, `auto-dispatch.ts:275`), none is taken (`claimed`/`wip`), and at least one is `waiting` or `blocked`. A slice with one `open` branch and one `waiting` branch must stay `eligible`, because the dispatch can take the open branch. Holding it would stall real work.
4. **medium — `blocked` and `waiting` need different words, or the operator waits forever.** The scan reads `blocked` when a `waits:` names a branch that has no PR and that no live plan names as a slice. Examples are a typo, a branch in a deferred slice of another plan, or a branch nobody created (`skills/plot/scripts/plot-fleet-scan.sh:88-102,3546-3551`). Only a plan edit clears it. A slice note "waiting on X" for that case tells the operator to wait for a merge that never comes. The board already has both sentences at branch level (`packages/board/src/server/fleet.ts:4775-4783`: `waits for X, which has no pull request` / `waits for X`), and the slice must reuse them. The other `waits:` targets are safe upstream: a merged prerequisite is asked of the host by `mergedAt` and clears to `""` even after `plot-release-refs.sh` deleted its ref (`eligible.ts` `waitVerdict` doc and `:257-265`). An unstarted slice named by another live plan reads `waiting`. An unreachable host reads `waiting`, and the next scan reverses it.
5. **medium — a new pulse verdict word would break old readers.** `SliceVerdictSchema` is a strict `z.enum(['complete','eligible','blocked','unapproved','empty'])` (`packages/domain/src/entities/fleet.ts:102`). If the scan emits `verdict: "waiting"` (Open Question 2, first option), every reader with an older bundle rejects the whole pulse. Such readers include a board that has not restarted, fleetd, and `plot-dispatch-command.mjs`, so auto-dispatch and the board stop together. The shell/domain corpus pair (`eligible.corpus.test.ts`) and the open scan migration #3048 (it touches `plot-fleet-scan.sh`, `plan-walk-branches.ts` and the corpus files) also carry this contract.
6. **medium — the plan names the wrong source for the *Not started* section, and it gives no destination.** `sections.ts:108` is `sliceSection`, which only moves a merged+unfinished split and returns `null` otherwise. The section comes from `deriveSlices` (`packages/board/src/server/fleet.ts:3621`, `complete ? 'done' : 'not-started'`) and from `classify`, which deliberately puts a waiting branch in `not-started` with a `waits for` note (`fleet.ts:4783`). Slices blocked by an earlier slice also stay in *Not started* (`fleet.ts:4462`). "The row moves out of Not started" names no target section. A move to *Waiting on you* would assign a task to the operator that nobody can do, which is the same error in a new place.
7. **low — the other plan-text claims are true on main.** Checked with `git show origin/main:`. `rows.tsx:937` gates the sole-slice menu on `soleSlice?.verdict === 'eligible'`. `rows.tsx:1163` shows `approved — nobody has taken it`. `rows.tsx:1469` gates `SliceActions`. The note path in *Not started* passes no `soleRow` (`rows.tsx:1430` comment), so the slice verdict sentence wins over the branch's correct note. `isClaimable` is at `eligible.ts:195-199`. The plan's name is correct here, and the issue and the panel brief say `isStartable`, which is a different, state-only predicate in `auto-dispatch.ts:234`. The pulse holds `"verdict":"eligible"` over `"state":"waiting"` for Fleet index.
8. **low — the readers that already answer correctly need no change.** `/api/attention` uses `row.waitingOn === 'click' && row.state === 'open'` (`packages/board/src/server/attention.ts:320`). `waitingOnFor` returns `time` for a waiting branch (`fleet.ts:3442`). Auto-dispatch counts with `dispatchable(b)`, which rejects `waiting` (`auto-dispatch.ts:554`). `skippedPlans` counts a waiting branch as `unstartable` (`auto-dispatch.ts:768`). So fleetd never auto-dispatched this slice, and the cost came only from the manual controller.
9. **low — two readers still ignore the branch state.** `nextWork` (`packages/domain/src/rules/waiting.ts:81-110`) answers `none` for a plan whose only unsettled slice is `eligible` with a waiting branch, because it looks for blockers only before a `blocked` slice. So a worker ends instead of waiting on the named prerequisite. `firstBrieflessBranch` (`auto-dispatch.ts:657-672`) returns the first briefless branch of an eligible slice without the `dispatchable` test. On a mixed slice it can name the waiting branch for the brief writer. Neither reader stalls the fleet, but both disagree with the new reading.

## Amendments I require

- A1. Replace "each branch's `held` value" in Approach 1 and in the `builds:` comment with the branch `state` (`waiting`/`blocked`) from `FleetReading`. Add one sentence that `FleetReading`'s `held` is the desk boolean and the rule must not read it. Add a unit test with a fixture whose waiting branch has `held: false` and another whose open branch has `held: true`.
- A2. Define the predicate over unsettled branches (Finding 3): the slice reads held when it is `eligible`, no unsettled branch is `dispatchable` or taken, and at least one is `waiting` or `blocked`. The test table must include merged+waiting (held), open+waiting (stays eligible), claimed+waiting (stays as in-progress), deferred+waiting (held), and all-deferred (unchanged).
- A3. The refusal fires only on positive evidence: the pulse is non-null and within its bridge age, the plan is in it at a dispatch phase, at least one slice is `eligible`, and the A2 predicate holds for every eligible slice. A `null` pulse, a missing plan, or a pulse that reads the plan as not approved must dispatch exactly as today. Name each of these as a test in the second slice, beside the refusal tests.
- A4. Give the refusal a reason word of its own (for example `slice-waiting`, and `slice-blocked` where any branch is `blocked`). The detail names each branch and its `waits_on` list. The refusal never reuses `ref-held`, `in-flight` or `no-eligible-wave`, and it never names a prerequisite for a slice that holds no `waiting`/`blocked` branch.
- A5. Settle Open Question 2 in the plan: the domain derives the reading at the consumer from the slice `verdict` plus the branch `state`. The pulse schema, `SliceVerdictSchema` and `plot-fleet-scan.sh` do not change.
- A6. Give the slice row two words: `waiting` (tone `time`, note `waits for <list>`) and `blocked` (tone `you`, note `waits for <list>, which has no pull request`). Take the sentences from the branch arms in `fleet.ts:4775-4783`, or move those sentences into the domain reading so that both levels share them.
- A7. State the section: the held slice stays in *Not started* with its new word, as a slice blocked by an earlier slice does today. Correct the Motivation citation from `sections.ts:108` to `fleet.ts:3621` and `fleet.ts:4783`.

## Optional

- O2. Make `firstBrieflessBranch` skip a branch that is not `dispatchable`, so that the brief writer never receives a waiting branch from fleetd.
- O3. Merge the two slices into one branch. The refusal is about 10 lines over the same predicate, and one branch keeps the board and the controller from shipping apart. Keep two slices only if the second carries the A3 test set.

## Open questions

- Q1 (one held branch, one open branch): the slice stays `eligible` and dispatchable, because the open branch is real work and `plot-dispatch.sh` claims only that branch. Hiding the control here stalls the fleet. The note can add "1 branch waits for X", but the word and the menu stay `eligible`.
- Q2 (scan emits, or consumer derives): the consumer derives, through one domain function that the board (`deriveSlices`/`sliceReadings`) and `briefBranchFromPulse`'s caller both call. A new pulse enum word breaks every older reader at once (Finding 5) and collides with #3048.
- Q3 (`blocked` versus `waiting` at slice level): yes, they need different words. `waiting` ends when a merge lands. `blocked` ends only with a plan edit, so it needs a person and it must say "no pull request" (Finding 4). Where a slice holds both, `blocked` outranks `waiting`, the same order `waitVerdict` uses.

# Layering juror: a-slice-held-by-an-open

Position: amend

The plan finds the right symptom and asks for the right shape: one domain property, read by the board and by the controller. Its file references are true on `origin/main`. But it puts the new property one level too high and misses the domain property that already exists for the same question. `startabilityVerdict` (`packages/domain/src/rules/verdict.ts:48`) is the per-branch "may I start this" rule that the server ships as `row.startability`, and it answers `needs-brief` for a `waiting` or `blocked` branch. I evaluated it on `origin/main`: `waiting`, `blocked` and `unknown` all return `needs-brief` (brief missing) or `start-work` (brief present). That one defect feeds the branch menu's *Write the brief* item, the row's *brief failed* word, and the brief writer. The plan's slice reading must be built over a corrected branch rule, or the board keeps two answers for one fact. The plan also names the controller as two surfaces when it is one function, misses `/api/implement`, and proposes a section move that contradicts the server's classifier.

## Findings

1. **high — the existing branch-level domain property is wrong for held branches, and the plan does not name it.** `packages/domain/src/rules/verdict.ts:48-72` (`startabilityVerdict`) tests `wip|claimed`, `merged|deferred`, `draft`, then `verdict !== 'eligible'`, then the brief. It never tests `waiting`, `blocked` or `unknown`. I copied the function body from `git show origin/main:` and ran it under node 26: `startabilityVerdict('waiting','approved','eligible','missing')` returns `needs-brief`; with `present` it returns `start-work`. The server ships this as `row.startability` (`packages/board/src/server/fleet.ts:6523`) and derives `briefWriter` from it (`fleet.ts:6705`). The client reads it in `needsBrief(row)` (`packages/board/src/app/lib/agent-rows/row-identity.ts:135`), which gates *Write the brief* in the branch menu (`menus.tsx:565`) and the brief word on the row (`rows.tsx:1648`). So the held branch of the evidence slice offers a brief run by itself, independently of the slice row. The plan's Approach 1 adds a slice-level reading beside this rule rather than fixing it; a slice reading that is right over a branch reading that is wrong is the two-answers shape the Layering rule forbids.
2. **high — the controller is one function, it already computes the answer, and it ignores it.** `plot-dispatch-command.mjs` and `POST /api/dispatch` both call `startDispatch` in `packages/fleet/src/shared/dispatch-command.ts:89` (board side: `packages/board/src/server/dispatch.ts:348`). `startDispatch` takes `briefBranch` from `briefBranchFromPulse` (`dispatch-command.ts:75`), which is `startableBranches(pulse, slug, ∅)[0]` — and `startableBranches` (`packages/domain/src/rules/auto-dispatch.ts:~585`) already excludes a `waiting` branch through `dispatchable` (`auto-dispatch.ts:275`, `isStartable` = `open|wip`). So for the evidence plan `briefBranch` is `null`, and `startDispatch` starts the implement run anyway (`dispatch-command.ts:~140`, `input.briefBranch(slug)` passed as the last argument). The refusal belongs in `startDispatch`, once, from a domain answer. But `null` today also means "no pulse"; the domain rule must separate *no reading* (`unaskable`, ask anyway or refuse by its own name) from *a reading with nothing startable* (refuse, naming each held branch and its `waits_on`). The plan's "the two surfaces" wording invites two refusals.
3. **medium — `/api/implement` is a third caller with the same gap.** `packages/board/src/server/implement.ts:255` computes `briefBranchFromPulse(...)` and calls `startImplement` with whatever it gets, including `null`. The plan's slice 2 names only the dispatch controller. The *Write the brief* menu item (finding 1) posts here, so after slice 2 the operator can still buy the same 5-minute run from the branch menu.
4. **medium — the plan uses `held` for a value the pulse spells as `state`.** Approach 1 says the reading "combines the slice verdict with each branch's `held` value". In the domain, `branchState` already folds the `waits:` verdict into `BranchState` (`packages/domain/src/rules/branch-state.ts:394`, `waitVerdict` → `'waiting'|'blocked'`), and the enum carries both (`packages/domain/src/entities/fleet.ts:54-63`). The pulse branch also carries a field literally named `held`, which means something else: the evidence branch reads `"state":"waiting"` and `"held":false` in `.plot/state/last-pulse.json`. An implementer who reads `b.held` gets `false` and ships the bug. The `held` parameter of `isClaimable` (`eligible.ts:195`) is redundant for any caller that passes a scan `state`.
5. **medium — the section move contradicts the server classifier, and `sections.ts:108` does not decide the section.** The branch's section is decided server-side: a `waiting` branch already returns `{ group: 'not-started', note: 'waits for …' }` (`packages/board/src/server/fleet.ts:4782`), and its tone is `time` (`fleet.ts:3452`). `sliceSection` (`sections.ts:104-117`) only relocates a mixed merged-plus-unfinished slice; for the one-branch evidence slice it returns `null`. A slice blocked by an earlier slice also stays in *Not started* with tone `time`. So "the row moves out of *Not started*" either moves it against the server's own section or needs a server change the plan does not list. The consistent answer is: the row stays in *Not started*, reads tone `time`, names the prerequisite, and offers no dispatch.
6. **medium — "startable" already has five spellings; the plan adds a sixth.** `isClaimable(verdict,state,held)` (`eligible.ts:195`, open only), `isStartable`/`dispatchable` (`auto-dispatch.ts:234,275`, open or wip, minus ref), `nextWork`'s `claimableExists` (`waiting.ts:81`, open only), `startabilityVerdict` (`verdict.ts:48`, no held test), and the server's `isClaimable(row)` (`attention.ts:320`, `waitingOn==='click' && state==='open'`). The new slice property must be defined over one of these, by name, and the plan must say which. Through this lens the right base is the branch `startability` once finding 1 is fixed, because it is the value the board already ships and renders.
7. **low — the slice-row decisions are made in `.tsx` today, and the plan keeps them there.** `rows.tsx:937`, `:1120-1128` (tone), `:1159-1171` (note) and `:1469` (menu) each compute from `group.verdict` inside the component, so the only proof of the defect is a render. The plan's Approach 2 says the board "reads the new property", but does not say whether the property is computed on the server and shipped, or imported from `@plot-pm/domain` into the client (the client does import the domain, e.g. `AgentList.tsx`). Either is legal; the test table must show a domain unit test per rendered state and one render test per surface.
8. **low — other readers of `verdict === 'eligible'` are correct or harmless.** `/api/attention` reads the branch row (`attention.ts:320,413`) and is correct, because a `waiting` branch never has `waitingOn: 'click'`. Auto-dispatch counts with `dispatchable` (`auto-dispatch.ts:546-560`) and never starts a held branch; `skippedPlans` reports it as `no-eligible-wave` (`auto-dispatch.ts:769`), which is true but unspecific. `packages/fleet/src/shared/auto-dispatch.ts:256,295` gate only log lines on `verdict === 'eligible'`, so a held slice prints *at cap … refusing* lines for work nothing can take. `fleet.ts:1160` and `board.ts:1333` already require `state === 'open'`.
9. **low — factual claims checked.** `rows.tsx:937`, `:1163`, `:1469` and `sections.ts:108` hold the expressions the plan quotes (read with `git show origin/main:` and line offsets). `isClaimable` is the right name on main; the issue's `isStartable` (`eligible.ts:199`) is wrong in the issue only. The *Not started* slice row receives no `soleRow` (`AgentList.tsx:1875` comment), which is why the one-branch slice prints the verdict sentence rather than the branch's *waits for* note — the plan's causal chain holds.

## Amendments I require

- A1. Fix `startabilityVerdict` first: a `waiting` or `blocked` branch returns no start offer (a new word such as `waiting-on-prerequisite`, or `null`), and `unknown` returns `null`. Name `verdict.ts:48` in the Motivation and add it to slice 1. This one change removes the branch menu's *Write the brief*, the row's brief word and the `briefWriter` state for held branches.
- A2. Define the slice reading as a pure domain function over the branch rule, by name: for example `sliceStartability(verdict, branches[])` that answers `start` where the verdict is `eligible` and some branch's startability offers a start, `held` with the held branches and their `waits_on` where the verdict is `eligible` and none does, and the verdict's own word otherwise. Do not add a sixth independent spelling of "startable".
- A3. Replace "`held` value" with "branch `state` `waiting` or `blocked`" throughout, and state that the pulse's `held` field is not this fact.
- A4. Put the refusal in `startDispatch` (`packages/fleet/src/shared/dispatch-command.ts`), once, and name it as the one place both `plot-dispatch-command.mjs` and `POST /api/dispatch` reach. The domain answer separates *no pulse* from *nothing startable*; only the second refuses, with a named reason (for example `nothing-startable`) and each held branch with its prerequisites.
- A5. Cover `POST /api/implement` (`implement.ts:255`) with the same answer, or state in the plan why it is out of scope.
- A6. Drop "the row moves out of *Not started*", or name the server change that moves it. Recommended: the row stays in *Not started*, tone `time`, note `waits for <prerequisites>`, no *Start work*.
- A7. Say where the slice reading is computed — server field on the row, or a domain import in the client — and give a test table: one domain unit test per answer of A1 and A2 (open, waiting, blocked, unknown; all-held slice, mixed slice, no pulse), one `startDispatch` unit test for the refusal and one for *no pulse*, and one render test per surface (slice row note, slice row menu, plan-row sole-slice menu at `rows.tsx:937`, branch menu).

## Optional

- O1. Make `skippedPlans` report a held plan as its own reason (`waiting`) instead of `no-eligible-wave`, so auto-dispatch logs name the prerequisite.
- O2. Gate the two fleet log lines (`packages/fleet/src/shared/auto-dispatch.ts:256,295`) on the A2 reading, so a held slice stops producing *refusing new dispatch* lines.
- O3. Collapse the slices to one branch. With A1 and A2 in the domain, the controller refusal is a few lines in `startDispatch` and the board change is a field read; the `waits:` between the two branches only serialises work that shares one predicate. If two branches stay, put the controller first: it is the one that stops the 5-minute model runs.

## Open questions

- Q1 (mixed slice): the slice reads `eligible` and offers a dispatch, because a dispatch claims the open branch and `plot-dispatch.sh` skips the held one. The held branch's own row keeps its `waits for …` note. A2's function answers `start` here; a test pins it.
- Q2 (scan or consumer): derive at the consumer, in the domain. `sliceVerdict` answers ordering plus approval and is a scan contract that `plot-dispatch-command.mjs` and the fleet read; changing its word is a contract change with no gain, because the pulse already carries every branch's `state` and `waits_on`. No scan or pulse change.
- Q3 (`blocked` versus `waiting` at slice level): keep the branch words the server already writes. A `waiting` slice reads `waits for <prerequisites>`; a `blocked` one reads `waits for <prerequisites>, which has no pull request`, the sentence at `fleet.ts:4772-4780`. Both keep tone `time` as the branch does today (`fleet.ts:3452`); a separate slice tone for `blocked` is a later decision and not needed for this plan.

# Testability juror — a-slice-held-by-an-open

Position: amend

The defect is real and the pulse proves it: on 2026-11-02 the slice `Fleet index` reads `"verdict":"eligible"` while its one branch reads `"state":"waiting","own_state":"open"`. The fix is small and every rendered state can be a unit-tested property. But the plan has no test table at all, so nothing in it proves the fix. Step 2 promises a section move that contradicts a deliberate, unit-pinned rule (a waiting branch lives in NOT STARTED). Step 3 names `isClaimable`, but the controller reads `startableBranches`/`dispatchable`. The plan also does not see that the controller already holds the answer: `briefBranchFromPulse` returns `null` for this plan, and `startDispatch` starts the brief run anyway. Four existing tests pin "null brief branch → started". The plan can be approved after the amendments below. No redesign is necessary.

## Findings

1. **high — The plan has no test table.** The plan names one unit test in prose ("A unit test asserts it with no browser") and no file, no case, and no refusal assertion. Through this lens the plan cannot be judged "proven as written". The states that need a named unit case are: the slice word (slot 5, `tupleFromSlice` in `packages/board/src/app/lib/tuple-row.ts:1546-1549`), the slice note (`rows.tsx:1159-1170`), the slice tone (`rows.tsx:1119-1127`), the two dispatch gates (`rows.tsx:937`, `rows.tsx:1469`), and the controller refusal (`packages/fleet/src/shared/dispatch-command.ts:89`). Checked: the plan file on the branch, and `git grep` of `origin/main` for each reader.

2. **high — The controller already has the answer and ignores it.** `startDispatch` calls `input.briefBranch(slug)` and passes the result to `startImplement` (`packages/fleet/src/shared/dispatch-command.ts:155`). `briefBranchFromPulse` (`:75-76`) returns `startableBranches(pulse, slug, new Set())[0] ?? null`. `startableBranches` (`packages/domain/src/rules/auto-dispatch.ts:578-605`) admits only `dispatchable` branches, and `dispatchable` (`:275`) is `state === 'open' || 'wip'` and no held ref. A `waiting` branch therefore yields `null`. `startImplement` takes `null` as "brief the plan, no branch" (`packages/fleet/src/shared/implement-run.ts:585-590, 659`) and runs for up to `IMPLEMENT_TIMEOUT_MS` (`:126`, 5 min). The refusal is one guard in `startDispatch`, not a new rule. Both callers share it: `plot-dispatch-command.mjs` (`packages/fleet/src/server/entry/dispatch-command.ts:115`) and `POST /api/dispatch` (`packages/board/src/server/dispatch.ts:348-352`).

3. **high — Existing tests pin the wrong behaviour, and the plan does not list them.** `packages/fleet/test/unit/dispatch-command.test.ts:73`, `:84` and `:94` run the entry with `pulse: () => null` and expect a start or an implement exit. `:227-229` call `startDispatch` with `briefBranch: () => null` and expect `kind: 'started'`. A guard on "brief branch is null" flips all four. `null` today means two things: "no pulse to read" and "the pulse says nothing is startable". The second is the defect. The first is a missing reading, and the *index never says no* rule (CLAUDE.md, *A Decision Reads The Index*) says a missing reading is not proof of absence. The plan must split the two and state the expected outcome of each pinned test.

4. **high — "The row moves out of Not started" contradicts a deliberate, unit-pinned rule.** `classify` sends a `waiting` or `blocked` branch to `group: 'not-started'` with the note `waits for <list>` (`packages/board/src/server/fleet.ts:4782-4794`), and `waitingOnFor` gives it tone `time` (`fleet.ts:3452`). `packages/board/test/unit/a-slice-with-no-work-waits-in-not-started.test.ts:44-48` and `:56-64` pin exactly that. `sections.ts:108` (`sliceSection`) does not decide this row's section: it relocates only a slice that holds both a merged and an unfinished branch (`:109-118`), and the observed slice holds one branch. The plan names no target section. NOT STARTED with tone `time` and a "waits for" note is already the right home. The defect is only the slice row's note, word, tone and menu.

5. **medium — The plan's input does not exist on the wire.** Approach 1 combines "the slice verdict with each branch's `held` value". The pulse carries no `held` field. The scan writes the hold into `state` (`waiting`/`blocked`) and keeps the earlier state in `own_state` (checked with `jq` on `.plot/state/last-pulse.json`). `AgentRow` carries `state` but no `waitsOn` (`git grep waitsOn packages/board/src/contract/schema.ts` finds none), so the client cannot name the prerequisite. The new reading must take `state` and `waits_on` as input and run on the server, in `rowsFromPulse`, where `wave.branches[].waits_on` is in scope (`fleet.ts:6285`). It then goes on the row as a field, the way `startability` does (`row-identity.ts:116`).

6. **medium — Two predicates, and the plan names the wrong one for the controller.** Step 3 says the controller refuses where "`isClaimable` false for every branch". `isClaimable` (`packages/domain/src/rules/eligible.ts:195-199`) admits `open` only and ignores refs. `dispatchable` admits `open` and `wip` and refuses a held ref. They disagree on `open` with `ref_held`. The controller reads `dispatchable`. "The two surfaces call one rule" is true only if the plan names `startableBranches` as that rule for the refusal. The board reading should then be asserted to agree with it on one shared fixture.

7. **medium — Changing the scan's `verdict` (Open Question 2) breaks a corpus gate.** `packages/domain/corpus/eligible.corpus.test.ts` compares the board and `--next` on the pulse's `verdict` per slice. `SliceVerdict` is also the type of slot 5 (`tuple-row.ts:1378`) and of `verdicts.ts` (`packages/board/src/server/entry/verdicts.ts:136`). A new verdict word is a contract change across the scan, the corpus and the bundle. A derived reading beside the verdict changes none of them.

8. **medium — One reader is missing from the scope.** `rows.tsx:1122` gives an `eligible` slice the amber tone `you` ("this needs a decision"). A held slice needs no decision; `fleet.ts:3452` gives its branch `time`. The plan lists status, note, section and menu, and omits the tone.

9. **low — The present proof of the slice note is a browser test.** `packages/board/test/integration/slice-head-says-its-verdict.browser.test.ts:145` asserts `approved — nobody has taken it`. The note, tone and gates are computed inline in `SliceRow` (`rows.tsx:1119-1170`), so today only a render can assert them. That is the shape *Every rendered state is a domain property* rules out. The fix should move the decision out of `.tsx`, not add a second browser test.

10. **low — Other `verdict === 'eligible'` readers are correct or log-only.** `/api/attention` reads `waitingOn === 'click' && state === 'open'` (`packages/board/src/server/attention.ts:320`), which a waiting row fails. Auto-dispatch counts with `dispatchable` (`auto-dispatch.ts:548-556`). The branch menu reads `isStartable(row)` over `startability` (`row-identity.ts:116`, `menus.tsx:554`). The counts at `fleet.ts:1160` and `board.ts:1333` require `state === 'open'`. `packages/fleet/src/shared/auto-dispatch.ts:258, 297` use `verdict === 'eligible'` only to decide whether to print a log line. These need no change. One sibling has the same null-brief path: `POST /api/implement` (`packages/board/src/server/implement.ts:255`).

11. **low — The second slice does not depend on the first.** The refusal reads `startableBranches`, which exists. It needs no board reading. The `waits:` annotation on it delays the half of the fix that saves 5 model-minutes per click.

## Open questions

- Q1 (one held branch and one open branch): it reads `eligible`. One branch is startable, and `plot-dispatch.sh` dispatches the eligible slice and takes the startable branch. The held reading applies only where no non-merged, non-deferred branch is startable. A test case must pin the mixed shape (A1a).
- Q2 (scan or consumer): the consumer, on the server. Derive the reading in `rowsFromPulse` from `state` and `waits_on`, which the pulse already carries, and leave `verdict` alone. A new scan word breaks `eligible.corpus.test.ts`, `verdicts.ts` and the `plot-dispatch-command.mjs` pulse contract for no gain (Findings 5 and 7).
- Q3 (`blocked` versus `waiting` at slice level): word them differently, and do not use the word `blocked`. The slice verdict `blocked` already means "an earlier slice has to land first" (`rows.tsx:1164`), so a second meaning makes slot 5 ambiguous. Use `waiting` as the slice word for both. Reuse the branch sentences from `fleet.ts:4782-4794` as the note: `waits for <list>` for a wait, `waits for <list>, which has no pull request` for a typo. Give a wait tone `time` and a typo tone `you`, because only a plan edit clears a typo (`eligible.ts:228-231`).

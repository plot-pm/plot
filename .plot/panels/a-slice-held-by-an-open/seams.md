# Seams juror — a-slice-held-by-an-open (#3050)

Position: amend

The defect is real and the plan's headline claims hold on `origin/main` (4bf18723f). Through the seams lens the plan misses the domain rule that already answers "can I start this branch" (`startabilityVerdict`), names the wrong field (`held`) and one wrong reader (`sections.ts:108`), and its third Open Question points at the scan, which open PR #3048 removes. No open PR other than #3048 touches the files in scope, and #3048 touches none of them except the scan script. A fix that keeps the pulse and `/api/fleet` schemas unchanged is available and smaller: one guard in `verdict.ts`, one domain slice reading the client already can import, and one refusal in `startDispatch`. The two slices are independent and the second one carries the measured cost, so the declared `waits:` between them is wrong.

## Findings

1. **high — the plan does not name `startabilityVerdict`, the branch rule that is wrong for a waiting branch.** `packages/domain/src/rules/verdict.ts:48-71` gates on `wip|claimed`, then `merged|deferred`, then `draft`, then `verdict !== 'eligible'`, then the brief. A branch in state `waiting` or `blocked` passes every gate, so with a slice verdict `eligible` it returns `needs-brief` (brief missing) or `start-work` (brief present). `fleet.ts:6523` stores that as `row.startability`; `fleet.ts:6705` derives `briefWriter` from `needs-brief`; `row-identity.ts:116` (`isStartable`) and `row-identity.ts:135` (`needsBrief`) read it; `menus.tsx:554` and `menus.tsx:565` offer *Start work* and *Write the brief* from it; `rows.tsx:1648` renders the brief gap note from it. The comment at `row-identity.ts:110` claims "`start-work` is only returned for `open` branches", which is false for `waiting`. Checked by reading `verdict.ts`, `entities/fleet.ts:54-63` (`waiting` and `blocked` are `BranchState` members) and the pulse row (`state:"waiting"`, `own_state:"open"`). This is a second reader of the slice verdict without the branch's held state, beside the ones the plan lists, and it explains the *brief failed* note the plan cites. A two-line guard (`if (state === 'waiting' || state === 'blocked') return null;`) needs no schema change: `null` is already a documented value in `StartabilityVerdictSchema`'s consumers.

2. **high — "each branch's `held` value" names a different field on the pulse.** On the pulse `Branch`, `held` is `z.boolean()` (`entities/fleet.ts:337`) and means a worktree lock on the scanning machine; the pulse row in the evidence reads `"held":false`. The `held` parameter of `isClaimable` (`eligible.ts:195-199`) is `waitVerdict`'s output, which the pulse does not carry: at the consumer the same fact is `state ∈ {waiting, blocked}` (the scan replaces `open`/`unknown` with it, `entities/fleet.ts:38-43`). An implementer who follows Approach step 1 literally reads the lock boolean and fixes nothing. Checked with `jq` over `.plot/state/last-pulse.json` and the schema.

3. **high — Open Question 2's first option collides with #3048 and changes three contracts.** Open PR #3048 (`feature/the-scan-script-is-a-launcher`, +297/−8074) shrinks `plot-fleet-scan.sh` to a launcher and deletes `corpus/eligible.corpus.test.ts`; after it, the slice verdict comes from `sliceVerdicts` in `workflows/plan-walk-assembly.ts`. Emitting `waiting` as a slice verdict means adding a member to `SliceVerdictSchema` (`entities/fleet.ts:102`), which every reader of `verdict === 'eligible'` sees: `auto-dispatch.ts:546,588,633,673,754`, `fleet.ts` `waitingOnFor` and `blockedBy` (`:6719`), `sections.ts:107`, `rows.tsx:937,1122,1163,1469`, and `/api/fleet`'s schema. It also changes the meaning of `eligible` (prior slices landed), which `rows.tsx:1561` documents as staying true after a claim. Checked with `gh pr view 3048 --json files` and `git grep "verdict !== 'eligible'"`.

4. **medium — `sections.ts:108` does not place this slice, and moving the row out of *Not started* would split the slice from its branch.** `sliceSection` (`sections.ts:103-118`) only relocates a merged-plus-unfinished slice and returns `null` for this one; its `unfinished` set excludes `waiting`. The section comes from `classify` (`fleet.ts:4782-4783`: `waiting` → `not-started`, note `waits for …`) and `isUnbegun` in `AgentList.tsx:1725`. The *approved — nobody has taken it* sentence comes from the NOT STARTED slice row, which `AgentList.tsx:1889` renders without `soleRow`, so `rows.tsx:1159-1163` falls through to the verdict. Approach step 2's "the row moves out of *Not started*" contradicts the branch's own group and recreates the `Inverted` split `sliceSection` exists to prevent. The row should stay in *Not started* with `waitingOn: 'time'`, the `waits for X` note, and no dispatch.

5. **medium — the dispatch refusal needs no new rule and does not depend on slice 1.** `startDispatch` (`packages/fleet/src/shared/dispatch-command.ts:89`) already computes `briefBranchFromPulse`, which calls `startableBranches` (`auto-dispatch.ts:581`), which already excludes a `waiting` branch through `dispatchable` (`isStartable(state)` = `open|wip`, `auto-dispatch.ts:234-277`). For this plan it returned `null`, and `startImplement` ran with `branch = null` (`implement-run.ts:585`) — the three runs the plan measured. The refusal is one arm: no startable branch in a present pulse → 409 with a new reason, before `startImplement`. The `waits:` from slice 2 to slice 1 therefore orders two disjoint packages (`packages/fleet` versus `packages/domain` + `packages/board`) and delays the fix that saves 5 model-minutes per click.

6. **medium — "no pulse" and "nothing startable" are both `null` today.** `briefBranchFromPulse` returns `null` for a missing pulse and for a pulse with no startable branch (`dispatch-command.ts:75-76`). A refusal on `null` alone refuses every dispatch on a machine where the fleet has written no `last-pulse.json`; that is the *index never says no* failure the CLAUDE.md section *A Decision Reads The Index* names. The refusal must read the pulse and refuse only when the pulse is present and the plan's eligible slices hold no `dispatchable` branch.

7. **medium — `/api/implement` has the same seam and the plan does not name it.** `packages/board/src/server/implement.ts:255` calls `briefBranchFromPulse` and starts `startImplement` with a `null` branch the same way. After finding 1 the *Write the brief* menu disappears for a waiting branch, but the plan-level implement route still accepts the click. Either refuse there too through the same domain function, or state that the plan-keyed brief run without a branch is intended.

8. **low — auto-dispatch reports a waiting plan as `no-eligible-wave`.** `skippedPlans` (`auto-dispatch.ts:769`) counts a `waiting` branch as `unstartable`, so the skip reason reads `no-eligible-wave` while the slice verdict reads `eligible`. Auto-dispatch never starts the branch, so this is wording only; a `waiting` reason would name the prerequisite.

9. **low — `/api/attention` is already correct.** `attention.ts:320` reads `waitingOn === 'click' && state === 'open'`; `waitingOnFor` (`fleet.ts:3452`) answers `time` for `waiting`/`blocked`. No change needed; a test that pins it is cheap.

10. **low — the textual seam with the Fleet index slice is small if the fix stays in the client and the domain.** `feature/the-fleet-payload-indexes-its-plans` edits `contract/schema.ts` and `server/fleet.ts`, and `bug/an-issue-reads-its-plan-from-main` edits `fleet.ts` `planMetasOf`. A fix that adds a field to the row payload would edit the same two files. Findings 1, 4 and 5 need neither: `verdict.ts` is domain, the slice reading can run in the client (`rows.tsx:3` already imports `@plot-pm/domain`), and the refusal lives in `packages/fleet`. Note also that the evidence slice is itself held by #3048: once #3048 merges, the live case disappears, so the tests must use a fixture.

11. **low — the issue says `isStartable` at `eligible.ts:199`; the function there is `isClaimable`.** The plan corrected this; `isStartable` exists twice elsewhere with other meanings (`auto-dispatch.ts:234`, `row-identity.ts:116`). The plan's new name `sliceStartable` would be a fourth "startable" spelling.

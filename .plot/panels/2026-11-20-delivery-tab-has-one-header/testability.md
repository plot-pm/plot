## Findings

1. **"The Mine filter does not change the header" contradicts today's inputs, and the plan names no test for it.** Today `TodoList` reads `todoListOf(view, …)` (`packages/board/src/app/components/AgentList.tsx:1541`), and `view` is built from `deliveryMapping(mappingInput)` with `mode` = the Mine mode (`AgentList.tsx:639`, `:1177`, `:1189`, `:1194`). So today's to-do counts follow Mine. The header's You and Work items numbers need a reading that is independent of the mode (a second mapping in mode `all`, or counts taken before the mode applies), and only a unit test that feeds two modes and asserts equal header facts proves it. Ran: read the code. Change to the plan: in *Approach*, name which reading the header counts from (not the Mine-filtered `view`), and add "a unit test asserts that `deliveryHeader` returns equal facts for Mine off, Mine on and Mine strict over one fixture, and different facts for `release` and `my-sprint` scope".

2. **The status line combines two inputs, and today one of them is read inside a component.** The plan makes the disabled reason the Release group's status line, and otherwise shows "Release PR #N ready · waits on you 43 min". Today the reason comes from `releaseCardApprovable(card, releaseReadingOf(pr), held)` inside `ReleaseApprove.tsx:24`, where `held` is the passkey registration that `useEffect` reads (`ReleaseApprove.tsx:16-21`). If the builder keeps that shape, the choice between "ready · waits" and the reason happens in `.tsx`, and only a browser test can see it. No current field gives the wait time: `ReleasePrReading` (`packages/domain/src/rules/release-approvable.ts:13-20`) and `ReleaseCardView` (`release-card.ts:43-70`) carry no time the PR became ready. Ran: read the code. Change to the plan: add "the status line is one domain function of (release group, PR reading, passkey answer, now) that returns the text and the button state, with unit tests for: ready, disabled with each `releaseApprovable` reason, passkey unread, no release targeted"; name the field the wait time reads ("43 min" since what?), or drop the wait from this plan.

3. **"No release targeted · last vX.Y.Z <date>" has no named source, and "No new data sources" names only the Machine meters.** `ReleaseCardView` has no last-release field (`release-card.ts:43-70`). The value can come from the plan cards' `Released: <date>, vX.Y.Z` record (`packages/board/src/contract/schema.ts:713`), but the plan does not say so, and a rule that picks the latest released version needs its own unit test (no released plan, two on one day, an unparseable record). Ran: grep over the schema. Change to the plan: name the reading and add its unit test cases, or say what the line shows when no plan is Released.

4. **The combined bar has four states and the existing bar has five; the plan does not map `being-built`.** The plan's table lists "delivered / at gates / blocked / not started" (plan line 36, as the spec and the mockup legend `header-and-sections-v2.html:129`). `releaseCards` returns five segments in `SLICE_STATES` order, including `being-built` (`release-card.ts:53`, `SprintCard.tsx:3-17`). A test can only pin the combined bar after the plan says whether `being-built` merges into another segment, shows as a fifth segment, or is dropped. Read plan and spec; opened code. Change to the plan: state the mapping, and add "a unit test asserts the combined bar's segment sums equal the sum of the per-sprint bars".

5. **`my-sprint` scope can hold several sprints, but the plan renders one.** `deliveryScope` returns every owned and selected Active sprint (`packages/domain/src/rules/delivery-scope.ts:20-22`, `:59-62`), and `SprintCard` renders one block per sprint (`SprintCard.tsx:32`). The plan's scope line is "my sprint · <title>" (plan line 43), singular. Without a decision for two owned sprints, the header has a state that no test covers. Ran: read the code. Change to the plan: state the scope line and Release group for two owned sprints, and include that case in the unit tests. The same applies to `unknownOwners` (`SprintCard.tsx:51-55`): the plan does not say if the header keeps that warning.

## Findings

1. **The header has no could-not-read or stopped state for any group.** The spec's anti-goal is *"Could not read" that looks like "empty"* (spec line 41), and every input the header reads can be unread today. `todoList` gives a triage count of `null` unless the tracker answered (`packages/domain/src/rules/todo-list.ts:99-100`). A release card carries `readingMissing` and `RELEASE_READING_MISSING` where a plan has no merge answer, and its `bar` is then `null` (`packages/domain/src/rules/release-card.ts:40,52-57`). `FleetMachineSchema` has `load1`, `cores` and `host` all nullable (`packages/board/src/contract/schema.ts:4475-4481`). A stopped fleet has no agents, which `fleetCard` reads as `idle` with three zeros (`packages/domain/src/rules/fleet-card.ts:15-21`), so it looks the same as a running fleet with no work. The plan names only the "No release targeted" state. As a reader, I cannot tell from the plan what the You group shows when the tracker read failed, what the combined Release bar shows when one of several sprints has no merge answer, what the Fleet group shows when fleetd is stopped, or what the Machine meters show when no limit is recorded. Read in the plan and spec; opened the code. **Change:** add a bullet "Unread and stopped in the header". It must name one domain property per group for the unread or stopped kind, using the same three kinds as plan 2 (clear, unread, stopped). It must also give the rendering: the Release bar is grey and the status line says `RELEASE_READING_MISSING` when any sprint in scope has no merge answer, and the combined bar never shows a partial count. The triage clause reads "tickets not read" rather than being dropped or shown as 0. The Fleet group reads "fleet stopped" with the marks still shown. A Machine meter reads "no reading" when `load1`/`cores` or the bucket is `null`. Each of these gets a unit test.

2. **"open ›" and the triage link can be dead links once sections fold.** `scrollToAnchor` returns without doing anything when the id is not in the DOM (`packages/board/src/app/components/DeliveryRows.tsx:20-22`). A folded section renders no rows, and the board already works around this for one case, `jumpToReleasePlan`, which opens Release delivery and then polls for the anchor (`packages/board/src/app/components/AgentList.tsx:525-535`). Plan 2 makes every section fold, including Tickets (`docs/plans/2026-11-20-every-delivery-section-folds.md:15,32`), and no plan says that "open ›" unfolds its target. So "open ›" on a folded You, Work items, Fleet or Machine section, and the "N tickets need triage" link to a folded `#tickets`, would scroll to a one-line header at best. That is a control that looks usable and does not do what its label says (spec line 42). Read the plan and spec; opened the code. **Change:** in Approach, state that every "open ›" and the triage link open their target section, persisting that fold state, before they scroll. This reuses the `jumpToReleasePlan` pattern. Also state where each target anchor is: the five section ids and `#tickets`. Add plan 2's `feature/every-delivery-section-folds` to the slice's `waits:`, or state why the header can merge before folding exists.

3. **My-sprint scope is underspecified for a reader who owns more than one sprint, and for the Fleet and Machine groups.** `deliveryScope` returns *every* owned and selected sprint as the `my-sprint` scope (`packages/domain/src/rules/delivery-scope.ts:20,56-61`), and `sprintCards` returns a view over several sprints (`packages/domain/src/rules/sprint-card.ts:154-160`). The plan's scope line is singular ("my sprint · <title>") and its Release group shows "that sprint". The plan also says *"every group counts only the reader's sprint"*. Free agents belong to no sprint, though, and load and rate limits have no sprint. So "N working · M free" and the Machine meters have no defined my-sprint meaning. The plan does not say what the action slot holds under my-sprint either. Today the to-do list's "Approve release" line reads every Active sprint in both scopes (`AgentList.tsx:1196-1200`). Read the plan; opened the code. **Change:** state that with two or more owned sprints the Release group lists their titles in the scope line ("my sprints · A · B") over one combined bar, as the release scope does with versions. State which groups the scope narrows: Release, You and Work items. Fleet and Machine show the whole machine in both scopes, and the plan says so. State what the action slot holds under my-sprint: the release PR that the reader's sprint's `Release:` version binds, or disabled with `unboundReason` (`release-card.ts:163`).

4. **The header must ignore Mine, but the plan does not name the reading that makes that true.** Today the to-do list is built from `placement`, and `placement` is placed from `deliveryMapping`, which applies the Mine mode (`AgentList.tsx:1169-1172,1194,1541`; `packages/board/src/app/lib/agent-rows/delivery-readings.ts:461-465`). So today's header counts follow Mine, and the spec's rule *"the header follows the scope selector only"* (spec line 89) is a change in behaviour. A builder who extends `todoList` as the plan says would inherit the Mine-filtered input. The release cards already read "in Mine mode `all`" (`release-card.ts:112`), so a precedent exists. Read the plan; opened the code. **Change:** state that the header's You and Work items numbers come from a placement made with mode `all` under the current scope selection. Add a unit test showing that toggling Mine and strict leaves every header number unchanged under both scopes. Note that the folded section summaries (plan 3) do follow Mine, so a header number and a section chip can differ by design.

The plan's bar is "delivered / at gates / blocked / not started" (plan line 36), which drops `being-built` with no reason given. As written, slices being built either vanish from the legend or get counted wrongly. Read the plan; opened the code. **Change:** keep the five segments and the five legend entries, with `being-built` in blue, as the mockup's `.bb` class allows (`header-and-sections-v2.html:29`). Or name the state each `being-built` slice folds into.

Read the plan; opened the code. **Change:** name the field the clause is derived from and the domain function that picks the newest one.

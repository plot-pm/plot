## Findings

1. **`releaseStatusLine` cannot read the passkey if `ReleaseApprove` stays unchanged.** Today `ReleaseApprove` holds the passkey registration in its own state (`useState` and `useEffect(readRegistration)`, `packages/board/src/app/components/ReleaseApprove.tsx:16-21`). It computes the button state and the reason itself through `releaseCardApprovable(card, releaseReadingOf(pr), held)` (`ReleaseApprove.tsx:24`). If the component stays unchanged (plan:82), the header's status line has no `passkey` value to pass, and the button and the status line make the same decision twice, in two places. Only a browser test could then show that the two agree. I opened the code to confirm this. Change to the plan: in plan:82, replace "reused unchanged" with "`ReleaseApprove` takes the button state from `releaseStatusLine` as a prop; the passkey reading moves up to the Release group, and the click and the controller call stay unchanged". Also add a unit test that the button state and the status line come from one `releaseStatusLine` result. Drop `now` from the signature, or name what it reads, because the plan removed the wait time.

2. **A Mine test in the domain does not cover the board's narrowing.** The Mine narrowing happens in the board, not in `placeDelivery`. `deliveryMapping` filters `rows` and `drafts` by ownership before it builds the placement, unless the board mode is `all` (`packages/board/src/app/lib/agent-rows/delivery-readings.ts:459-470`). It passes the domain `DeliveryMine` only as `input.mine`, through `MINE = { all: 'off', 'mine-and-unknown': 'mine', mine: 'strict' }` (`delivery-readings.ts:143`). A domain test of `deliveryHeader` over the three `DeliveryMine` values (plan:48) can pass while the tab still builds the header from the narrowed `mapping`. Today `AgentList.tsx:1194-1195` builds `placement` and `view` from that narrowed mapping. Plan:48 also uses both vocabularies: the bullet title says Mine mode `all` and its text says `off`. I opened the code to confirm this. Change to the plan: state that the header reads `deliveryMapping({ ...input, mode: 'all' })`, as `releaseCardsOf` and `sprintCardViewOf` already do (`delivery-readings.ts:541,571`). Move the equality test to the `agent-rows` level: one board unit test feeds the header's view function with `MineMode` `all`, `mine-and-unknown` and `mine`, and asserts equal facts. Keep the domain test for the scope difference.

3. **The slice 1 test list misses one file, and one listed test fails in slice 1.** `release-approve.browser.test.ts:82` clicks the `[data-todo-name]` line "Approve release 2.7.0" (`packages/board/test/integration/release-approve.browser.test.ts:89-92`). `TodoList` renders that line, and slice 1 removes `TodoList` (plan:74). The test therefore fails when slice 1 merges, but plan:92 assigns it to slice 2. `packages/board/test/unit/delivery-link-icons.test.ts:9,86` renders `TodoList`, and plan:91 does not list it. I ran a grep and read the files. Change to the plan: move the `release-approve.browser.test.ts:82` rewrite to slice 1, which removes the to-do jump and keeps the card-position assertion. Add `delivery-link-icons.test.ts` (its `TodoList` case) to slice 1.

4. **The slice 2 test list misses three files.** `packages/board/test/integration/sprint-exempt.browser.test.ts:168,174` asserts `[data-release-card="untargeted"]` and `[data-sprint-card-sprint]`. `packages/board/test/unit/release-plan-parts.test.ts:8` imports `SEGMENT_CLASS` from `SprintCard.js`, and plan:59 moves that constant. `delivery-link-icons.test.ts:10,106` renders `ReleaseCard`. Plan:92 lists none of the three. The `catalogue/states.ts:892,905` comments also name the ReleaseCard, the SprintCard and the *Approve release* to-do. I ran a grep. Change to the plan: add these files to the slice 2 list, and add the catalogue comment to the files that change. Each slice records its `EXPECTED_FILES` and `EXPECTED_TESTS` delta (`stubbed-tests-start-no-board.test.ts:569,956`) over the complete list.

5. **Slice 2 does not wait on slice 1.** Slice 2 draws the Release group in the header frame that slice 1 builds, in the same `[data-tab-header]` markup and `delivery-header.css`, and its tests open that frame. Without a `waits:` marker, slice 2 can be dispatched in parallel, and the two slices then conflict on `AgentList.tsx:1537-1552` and on `delivery-tab-header.browser.test.ts`. I read the plan and opened `AgentList.tsx`. Change to the plan: add `<!-- waits: feature/delivery-tab-has-one-header -->` to `feature/delivery-header-release-group` (plan:108).

6. **No slice owns the header-against-summary agreement test.** Plan:48 asserts that the header numbers and plan 3's folded summaries agree under Mine `off`. Plan 3's `feature/folded-sections-summarise-visually` waits only on plan 2 (`docs/plans/2026-11-20-folded-sections-summarise-visually.md:70`), and this plan's slices do not wait on it. Whichever merges first has nothing to compare against. I read both plans. Change to the plan: name the slice that writes the test, and its dependency. For example: "the test lands with whichever of `feature/delivery-tab-has-one-header` and `feature/folded-sections-summarise-visually` merges second; plan 3's slice carries it if it merges second". The simpler option is to add plan 3's slice to slice 1's `waits:`.

7. **Minor, for the builder.** The stopped Fleet group must not read `idle` (plan:54). `fleetCard` takes only agents (`packages/domain/src/rules/fleet-card.ts:24-31`), so `deliveryHeader` must take `supervisorVerdict`'s answer as an input value, not as a port, following CLAUDE.md's readings-as-values shape. The four `SupervisorState` values (`supervisor-reading.ts:58`) each need a case in the unit test.

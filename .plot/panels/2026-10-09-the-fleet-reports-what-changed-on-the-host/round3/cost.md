## 3. Findings

**C1 (HIGH): the `default-branch-red` hold is off for most of the time that `main` is red, because it reads only the HEAD SHA and a new HEAD reads `pending`.** The plan holds only while the reading is `red`; `pending` and `unknown` hold nothing. Every push to `main` starts `ci.yml`, `build-bundles.yml` and `release.yml` (`on: push: branches: [main]` in all three), and `validate` has a 25-minute ceiling (`ci.yml` comment above `concurrency`). Measured with `git log` on `main` for 2026-10-09: 121 gaps between commits, 103 of them under 20 minutes. So for most of a working day HEAD is a commit whose runs are still going, and the hold lifts in each of those windows even when every earlier commit failed. The fleet makes this worse itself: 108 of that day's commits are record commits by the operator's identity and 17 are `plot-build[bot]` bundle commits, and a dispatch that the lifted hold lets through writes a `record Started` commit, which starts the next `pending` window. On the 2026-10-09 incident (#1432) the hold would have held only in the gaps between record commits. The cost side: slice 2 spends its ~400 REST calls per day on a reading whose hold has a low duty cycle. The done-when test (red holds, green releases) passes and does not show this. Amendment: `defaultBranchRed` answers from the newest SHA with a concluded reading, so a `pending` HEAD keeps the previous concluded `red` until a newer SHA concludes `green`. Store that SHA and state in `DefaultBranchReading`. This adds no host call: one `gh run list --branch <default>` already returns the runs of several recent SHAs. Add a done-when case: red SHA, then a newer pending SHA, still holds.

**C2 (MEDIUM): the `failing` re-ask has no stated stop rule, so the "at most 12 per hour" bound depends on how the brief reads it.** Today the streak grows only when a re-asked PR is still `pending` with the same `updatedAt` (`pr-refresh.ts:1508-1517`, `noProgress = pr.checks === 'pending' && …`); any other answer deletes the streak. A slice that adds `failing` to the candidates and keeps this code never grows a streak for a failing PR, so it re-asks on every refresh (`PR_REFRESH_MS`, 60 s on GitHub) for the whole `Checks wait` hour: up to 60 rich GraphQL listings per hour, not 12. `PR_REQUESTS_PER_REFRESH` also says the re-ask is "DELIBERATELY NOT COUNTED" because the count bound keeps it finite (`pr-refresh.ts:163-172`); the time bound replaces that argument, and the plan does not say whether the stretch now counts it. Amendment: define no-progress as "same `checks` and same `updatedAt`" for both `pending` and `failing`; state that after five no-progress answers the PR is re-asked at most once per 5 minutes until `headSince + Checks wait`; add a done-when case that a `failing` PR with no progress is asked at most 12 times in a simulated hour; and state whether the comment at `:163-172` changes.

**C3 (MEDIUM): slice 4 cites a desk-port read that does not exist.** The plan says fleetd reads each desk's newest finding "through the desk port (`ports/desk.ts:215-235`), the same read the board makes". Those lines are writers. The board's read lives in `packages/board`, which fleetd must not import. An implementer either adds a port method or copies `findings.ts` into the fleet package, and the second gives two parsers of one file. Cost is small and the plan states it right (three bounded file reads per desk per 60 s tick, `TICK_INTERVAL_MS`, `registryd.ts:76`; the monitors append only on change, `plot-agent-monitor.sh:526-543`). Amendment: name a new `Desk` port read (for example `readFindings(worktree)`) that `findings.ts` and the relay both call, with the 256 KiB bound, and cite `findings.ts` as the read to move.

**C4 (MEDIUM): the measurement gate cannot run before merge.** "Slices 1 and 2 measure requests per hour over one working day from the budget log, against the day before, and state both figures in the PR." A fleet agent runs under `Worker bound` 28800 s (8 h), shorter than a working day. A branch `plot-fleetd` running beside the operator's would be a second PR-index writer, which `one-pr-index-writer.test.ts` and CLAUDE.md *One writer* forbid. And `budget.tsv` rows carry the bucket and no operation (sample row: `b1 github jwloka graphql <ts> 1 - - - unknown`), so the re-ask tail cannot be told from the refresh. Amendment: each of slices 1 and 2 proves its row with a unit test that counts host calls over a simulated hour with a fixture clock (one PR pending, one failing, `main` moving every 10 minutes), and the live day's figure is a post-merge note, not a review condition.

**C5 (LOW): `git ls-remote` per refresh is free of API budget but not of time.** `board.ts:163` measured `git ls-remote` at ~459 ms against ~8 ms for `for-each-ref`, and chose the mirror for that reason. At the 60 s PR refresh that is 1440 network calls a day and about 13 % of the measured 3.5 s tick (`TICK_COST_MS`, `registryd.ts:102`) if it runs inside the tick. Amendment: state the figure, give it the timeout `refs-remote-git.ts` uses, and say that a failed read keeps the last reading rather than moving it to `unknown`. The `Refs` port has `remoteTip(branch, sha)` (`ports/refs.ts:538-560`), which answers equality, not the SHA, so slice 2 also adds a port operation; say so.

**C6 (LOW): `runs-for-sha` must not copy `run-for-sha`'s extra `gh run view`.** `run-for-sha` spends one more call per failed or cancelled run (`plot-host.sh:4583-4590`). Over 12 re-asks of a red `main` with two failing workflows that is 24 extra REST calls per red SHA, outside the slice-2 row. `foldRuns` needs only conclusions. State that the new verb makes one call.

**C7 (LOW): `action_required` keeps the default-branch reading `pending` for the whole hour.** `foldRuns` maps it to `pending`, which no re-ask can resolve without a person. That is 12 wasted reads per such SHA and no hold. `ci.yml`'s header records 18 of 20 bot-branch runs ending `action_required`; on `main` it is rarer. Consider `unknown` for it, which stops the re-asks.

**C8 (LOW): the mod's turn bound has no daily ceiling.** One turn per 5 minutes is up to 288 turns a day in the operator's session if the operator lists `checks failing`. Name a default empty list, or state the daily worst case.

**Volumes that hold.** Publish on change keeps the channel quiet: the IndexMonitor writes one finding per state change per slice PR, the relay one per monitor-log append, and the page refetches at most once per 2 s per event burst. Each `/api/board` build runs `boardState` with no cache (`server/index.ts:444-470`) at about the cost of one 30 s poll, so tens of events per hour cost less than the 120 polls per hour per tab today. The 24 h `pr merged` retention holds one slot per merged slice PR, tens at most, in the `welcome`. One log line per publish stays under `process-log.ts`'s ceiling.

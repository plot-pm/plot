## Findings

1. **The plan's Mine rule is not today's rule, and no slice of any plan builds the change.** Lines 64-65 require unit cells for {`release`, `my-sprint`} × {off, mine, strict} for You, Work items, Fleet and Tickets. Mode `mine` must show "a row that is assigned to the reader or whose plan is the reader's, by `ownership` with kind `plan`", and `strict` must keep `isMineStrict`. Today's filters do something else. `ownedFromRow` (`packages/board/src/app/lib/agent-rows/mine-filter.ts:141-146`) gives a row with a PR the PR author's ownership, not the plan's. `agentsForReader` (`mine-filter.ts:236-244`) reads the agent's `identity`/`state` (`ownedFromAgent`, `:155`), not a plan. `ticketsForReader` always uses the lenient rule and never `isMineStrict` (`mine-filter.ts`, TSDoc above `ticketsForReader`: *"`mine` mode does not sharpen it"*). The board's mode type is `MineMode = 'all' | 'mine-and-unknown' | 'mine'` (`packages/domain/src/rules/mine-mode.ts:12`), and `DeliveryMine` (`delivery-placement.ts:32`) is a second vocabulary for the same three modes. Plan 5 states the same rule (`2026-11-20-delivery-rows-act-from-one-place.md:60`), but its slice lines (`:97-113`) build only `rowSprintMembership`. Plan 3 restates it too (`2026-11-20-folded-sections-summarise-visually.md:51-54`). A user sees the cost. Suppose slice 2 computes the hidden count with today's filter and a later slice changes the filter. The sentence "3 hidden by Mine" then disagrees with the rows the Mine chip leaves. Suppose instead slice 2's tests pin the new rule. The builder then has to change three filters that the slice line does not name. Read the plans, opened code. **Change to the plan:** name one slice that changes `rowsForReader`, `agentsForReader` and `ticketsForReader` to the spec's `mine` rule (and gives Tickets a `strict` mode), with its unit tests. If that slice is plan 2's `feature/delivery-section-empty-kinds`, add the change to its slice line. If it is another plan's, add a `waits:` on that slice. State that the hidden count comes from `mineHiddenCount` (`mine-mode.ts:95`) over the same filter the rows use, so the count and the rows cannot disagree.

2. **The "frame or — none" rule contradicts the Machine row.** Line 67 says "A section with zero rows shows the frame and no group". Machine has no groups and no rows (`DELIVERY_LAYOUT`, `delivery-placement.ts:17`, `groups: []`), so under line 67 it always shows the frame. Line 58 says Machine is empty only while headroom is `unmeasured`. Release delivery also has `groups: []`, and line 54 measures it by `releasePlanCount`. A user who opens a measured Machine section must see its meters (`MachineSection`, `AgentList.tsx:1710`) and no stopped frame. Read the plan, opened code. **Change to the plan:** in line 67, define "rows" through each section's "Empty when" column, for example: "A section shows the frame when `sectionEmptyKind` answers non-null, and otherwise its content." Add a unit test that a measured Machine section answers `null`.

3. **Fleet's empty sentence must not name the scope.** The spec says "Fleet and Machine show the whole machine in both scopes" (spec line 82). Lines 64-65 make every empty sentence name the scope, and they ask for `my-sprint` cells for Fleet that assert "the sentence". The sentence "No agent runs in my sprints" states a false fact: an agent of another sprint is not hidden by the scope. Read the spec and plan. **Change to the plan:** add "Fleet and Machine take no scope: their sentence never names it, and the Fleet `my-sprint` cells equal its `release` cells." Mine still applies to Fleet.

4. **A jump can open its section and still find no anchor.** Line 36 covers folded sections and groups. A target can also be unmounted because Mine or the scope hides its row, or because Tickets' inner fold `… n more · show` hides it (line 79). In those cases the link opens the section and the scroll does nothing, and `jumpToReleasePlan` gives up after 10 frames without a sign (`AgentList.tsx:527-535`). A `null` answer from `anchorOwner` "scrolls only" (line 36), which for an unmounted anchor is also nothing. Read the plan, opened code. **Change to the plan:** state what a jump does when its anchor stays unmounted after the open. For example, `anchorOwner` answers `hidden` with the filter that hides the anchor, and the link shows disabled with that reason, per "no hidden UI". Or the jump also opens the Tickets inner fold. Add a unit test for the filtered case.

5. **Minor, for the builder.** The frame "shows the control that removes the filter (the Mine chip or the scope toggle)" (line 64). Say whether this is a second button that calls the same setter as the chip, or a jump to the chip, so the plan does not create a second Mine control with its own state.

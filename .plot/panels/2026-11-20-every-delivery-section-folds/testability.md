# testability — every-delivery-section-folds

Position: amend

## Findings

1. **Section foldability and the folded state stay decisions in `AgentList.tsx`, and the plan names no function that takes them over.** Today the fold control's presence is computed inline: `fold` (`packages/board/src/app/components/AgentList.tsx:1482-1505`) sets `foldable = !always && isCollapsible(count)`, `isFolded` (`AgentList.tsx:1480-1481`) gates the folded state on `isCollapsible(count)`, and `releaseFold` (`AgentList.tsx:1511-1532`) repeats both for Release delivery. The plan says "the fold control's presence ... [is a] view or domain property with unit tests", but names only `sectionEmptyKind` as the thing the slice builds, and its `isCollapsible` bullet leaves open whether `isCollapsible` changes at all (groups keep `rowCount > 0`, sections always fold). A builder can satisfy the text by writing `section ? true : isCollapsible(count)` inside `fold`, which no unit test reaches. Ran: opened the lines above. **Change:** in Approach, name one exported function in `agent-rows/collapse.ts` (for example `isFoldable(level: 'section' | 'group', rowCount)` and `isFolded(level, key, rowCount, collapsed, always)`) that both `fold` and `releaseFold` call, and require unit tests for: an empty section is foldable; an empty group is not; a stored key folds an empty section (today `isFolded` returns false for it, `AgentList.tsx:1481`); the Fleet `working`/`blocked` groups never fold (`fleetOpen`, `AgentList.tsx:1713`).

2. **"Empty" has no definition per section, so the empty kind's input cannot be tested.** `section.count` is the sum of group counts (`packages/board/src/app/lib/agent-rows/delivery-view.ts:617`); Release delivery and Machine have no groups (`packages/domain/src/rules/delivery-placement.ts:13,17`), so Machine's count is always 0 and Release delivery uses `view.releasePlanCount` instead (`AgentList.tsx:1512`). Machine always renders `MachineSection` (`AgentList.tsx:1708-1710`), and the plan's Machine row ("no reading" when no process has recorded a limit) names no kind of the three and no reading from `machineHealth` (`packages/board/src/app/lib/agent-rows/machine-health.ts:21`). Fleet's "no agents" row also names no kind. Read in plan, ran: opened the files. **Change:** add to the empty-kind table, for each of the seven sections, (a) the input the function reads (`releasePlanCount`, `section.count`, `fleet.supervisor`, `fleet.issueAnswer`, `machineHealth(...)`), (b) the predicate that makes it empty, and (c) the kind (clear, unread or stopped) for Machine "no reading" and Fleet "no agents". State the signature of `sectionEmptyKind` so its unit tests are one case per table row, plus the non-empty case returning `null`.

3. **Folding Machine and the Fleet footer hides nothing today, and the plan does not say what folding them removes.** `WorkingCounts`/`FleetAlert` (`AgentList.tsx:1699-1707`) and `MachineSection` (`AgentList.tsx:1708-1710`) render without a `!folded` guard; only the groups are guarded (`AgentList.tsx:1712`). A toggle on Machine would then flip `aria-expanded` and change nothing on screen — the same "offer that leads nowhere" that `isCollapsible`'s comment (`packages/board/src/app/lib/agent-rows/collapse.ts:93-106`) names as a defect. Ran: opened the lines. **Change:** state in Approach that a folded section renders its header line only, list the Fleet footer and `MachineSection` as content the fold hides, and add one browser assertion that a folded Machine section renders no `MachineSection`.

4. **Retry has no target.** The plan and the spec require Retry on every unread frame; the board has no Retry control today (`grep -rn Retry packages/board/src/app` returns nothing). The plan names no endpoint, refetch or controller that Retry calls, and no property that says whether Retry is enabled. Ran: grep. **Change:** name what Retry does (for example refetch `/api/fleet` or the issue read) and carry it as a field of the empty-kind result (`retry: { action, disabledReason } | null`), with a unit test that every unread result carries it and the Tickets `unasked` case resolves the Open Question explicitly (with or without Retry).

5. **Browser tests that iterate `[data-group-toggle]` change behaviour when empty sections gain a toggle, and the plan does not name them.** `agents-tab.browser.test.ts:4780` and `spec-run-rows.browser.test.ts:60` click every toggle whose `aria-expanded` is `false`; `row-withholds.browser.test.ts:357,362` take `[data-group-toggle]`.first() and the first section that holds one; `agents-tab.browser.test.ts:1915` asserts an empty group has no toggle (still true for groups, and should stay). If the section toggle keeps the `data-group-toggle` attribute, `.first()` can move to a section that had none before. Ran: grep and read the lines. **Change:** state whether section toggles use `data-group-toggle` or a new attribute (for example `data-section-toggle`), and list these four files as ones the slice re-reads. The stubbed-tests gate pins `EXPECTED_FILES = 99` and `EXPECTED_TESTS` (`packages/board/test/integration/stubbed-tests-start-no-board.test.ts:569,322-324`); the plan names it correctly, and a new `release-delivery-fold`-style browser file for the frame moves `EXPECTED_FILES` too.

6. **One slice holds four separable changes.** The frame and fold rule, the empty-group render (`AgentList.tsx:1712` filter), the empty-kind function with seven cases, and the Tickets and Not placed keys can each be verified alone, and plan 3 waits only on the frame. One slice is buildable, but a failure in the empty-kind work then blocks plan 3. Read in plan. **Change (minor, builder's call):** split into `feature/every-delivery-section-folds` (frame, fold rule, keys) and `feature/delivery-section-empty-kinds` (empty kinds, empty groups, Retry), with plan 3 waiting on the first.

## (a) Problem statement

1. **The scan is not in the 60 s tick.** The plan says *"The tick runs `plot-fleet-scan.sh --stream` through `scanOnce`"*. On main the scan runs on its own clock: `startFleetClock` (`fleet-clock.ts:77-114`) beats every `REFRESH_MS = 5_000` (`fleet-scan.ts:20`), and the `fleet-scan` subscriber takes every beat with an in-flight guard (`fleet-clock.ts:29-35`, `:84-104`). The supervision tick is the separate `for (;;)` loop in `registryd-main.ts:2629+`, paced by `args.intervalMs`. So the scan's frequency is `max(5 s, scan duration)`, not 60 s. `fleet-scan.ts:547` is the `world.scripts.stream(FLEET_SCAN, ['--stream'], …)` call, which is correct as a location but not as a claim about the tick. Slices 1 and 3 both name "the tick" and therefore target the wrong loop.
2. **A budget gate already exists for the scan's listing.** Cause 4 says *"nothing reads it to slow the tick"*. True for the supervision tick. False for the scan: `scanOnce` calls `listingSpend` with `spendRateFor` (`fleet-scan.ts:503-519`), which stretches the listing interval up to `MAX_CADENCE_STRETCH = 8` (`cadence.ts:32`). Probe result, Bitbucket, cost `branches × 3` (`fleet-scan.ts:133-137`): the base share is **720 req/hr whatever the branch count** (base interval = 5 s × cost; 5 branches → 75 s, 20 → 300 s, 40 → 600 s). At an account rate of 1000 or 4500/hr the listing settles at 8× and **90 req/hr**. So the scan listing's rate stretch already works when listings succeed. The plan does not mention it, and slice 3 risks building a second copy.
3. **What the existing gate misses is refusal, and that is the safety-relevant cause.** A refused or throttled listing writes no `.list-arrived` (`plot-fleet-scan.sh:1047-1060`, `report_listing` at `:973`), so `scanOnce` does not move `state.listingAt` (`fleet-scan.ts:578-585`). The next beat is `due` again, and `listingSpend` permits it. Probe: a cold fleetd (`listingAt === null`) whose every listing is refused is permitted on **720 of 720 beats per hour** at 4500/hr; a warm fleetd whose last good listing is 1 h old is permitted on every beat too. `cadence.ts` states the reason: *"A REFUSAL IS NOT AN INPUT."* A throttled Bitbucket account therefore gets its open-state sweep re-asked every 5 s (or every scan duration). The plan does not name this cause.
4. **`mine=` counts invocations, not requests, and does not see the scan.** `tally.calls` is incremented once per `host.prList`/`prState` call in the tick world (`registryd-main.ts:852-853`, `:895`, `:937`, `:941`), and `mine=` is `boardSharePerHour(intervalMs, calls)` (`:461`). On Bitbucket one `pr-list --state merged --limit 50` costs about 3 requests (`:845-850`), and one swept `pr-list` costs `branches × states` requests (`plot-host.sh:4890-4896`). The scan's calls run on another clock and never reach `tally`. The cause is right, but the undercount has two factors, not one.
5. **The sampled verbs come from at least three loops, plus possibly the agents.** `pr-list --state open` and `--state settled` come from the scan shell (`plot-fleet-scan.sh:1047`, `:1063`). `pr-list --state merged` comes from the tick's `mergedBranches` (`registryd-main.ts:854`, `:896`). Bare `pr-list --rich` comes from the PR reader (`pr-refresh.ts:1510`). `pr-state` comes from the tick (`viewLanded`, `prOpen` at `:1807`, `:1964`), from the scan's no-ref `--ask` arm (`plot-fleet-scan.sh:1357`), and from worker loops (`worker-loop.ts:980`). The issue attributes invocations "to its top-level ancestor". If fleetd-started agents are descendants of fleetd, their `pr-state` calls are counted as fleetd's. The plan's first open question is the right gate. Slice 2 should not start before that measurement.
6. **Cause 3 is resolved for the PR reader and does not apply to the scan.** `fleetPrs` elects under `ReaderLock` (`fleet-clock.ts:240-281`). Boards do not scan while fleetd owns a fresh bridge (`fleet.ts:2720-2727`, `scan-owner.ts:37-43`). This is consistent with the measured "boards 0". Remove cause 3 from the plan.

## (b) Approach, read for stale facts and runaway spend

- **Slice 3 as written can multiply the spend.** If fleetd stops scanning while backing off, the bridge's `at` stops moving. `fleetOwnsScan` refuses a bridge older than `OWNED_BRIDGE_MAX_AGE_MS = 180_000` (`scan-owner.ts:10`, `:41-42`). After 3 minutes every open board falls back to its own `scanOnce` (`fleet.ts:2727-2730`), and each board scans live. A back-off longer than 180 s that skips the scan turns one reader into N readers during the exact window where the account is over its limit. The back-off must keep running the scan with the carried listing (`PLOT_PR_LISTING`) and keep writing the bridge. It must skip only the host listing. "Skip the tick's host read" has to say this.
- **A back-off on `account=` alone can fail to start, or fail to end.** `budget.tsv` is per `$HOME` (column header: version, connector, account, bucket, ts, count, …; no machine and no process). Two machines on one Bitbucket account each see only their own spend, so `account=` never crosses the limit on either machine while the host refuses both. The reverse also holds: a rate taken from a sliding window over local lines stays high for the length of the window after the burst ends. Combined with an 8× stretch on top, the scan's listing can sit at a 600–4800 s interval (probe) well after the account recovers. The trigger should be the connector's refusal (exit 5 or exit 6, already classified in `pr_list_verdict`, `plot-fleet-scan.sh:768-835`) with a bounded `backoffUntil`, as the PR pass already does (`prGateOpen(state.prNextAt, state.prNextIsBackoff)`, `fleet-clock.ts:257`). Observed rate stays the stretch input. That gives the two signals the cadence rules already separate.
- **Slice 2 option B breaks "A Decision Reads The Index".** *"Let the shell take the listing from the PR index"* would hand the scan OPEN rows and check rollups from the index. CLAUDE.md allows only terminal (MERGED) rows to be read from the index, because OPEN, CLOSED and draft rows are stale in both directions. Drop option B, or limit it to MERGED rows.
- **Slice 2 option A only saves requests if it leaves the sweep.** On Bitbucket, a windowed *sweep* still costs `branches × states` requests: `bb_branch_query` adds `updated_on>=` to each per-branch query (`plot-host.sh:1207`, `:4890-4896`). Only the windowed *listing* (`bb_window_listing`, `:1311-1360`) costs one request per state per page. So the delta has to be a listing without `--branch`, folded onto a carried full sweep. The fold then needs a stated rule for its completeness claim, and that is where stale facts come in:
  - **Existing hazard that slice 2 must not widen (read, not executed).** On Bitbucket the full read is a sweep over `TRACKED_BRANCHES`, which holds only branches with a remote ref (`plot-fleet-scan.sh:766`). Its "sweep complete" claim licenses `.list-complete` (`:1263-1271`). `host_pr_state --ask` then answers `NONE` for any branch absent from the cache (`:1346-1352`). The `--ask` arm exists for **no-ref** branches (`:1515-1524`), which are exactly the branches the sweep never asked about. A squash-merged slice whose ref was deleted can then read `NONE` instead of `MERGED` on a cold terminal cache. That is "dispatches onto a branch already reviewed" in its most direct form. Today `PLOT_TERMINAL_CACHE` and the merge-subject evidence partly cover it. A carried and folded listing keeps the same `.list-complete` for longer, and for a tracked set that grows between reads (new pushes), so the window gets wider. Slice 2 must scope `.list-complete` to the branches the base sweep asked, or withhold it for any branch outside that set.
  - The fold's refusal rule for a carried OPEN row absent from both answers (`scan-listing.ts`) carries over unchanged. Bitbucket's delta needs the same: an OPEN row that drops out with no MERGED or DECLINED row forces a full read.
- **Stale `checks` is low-risk for fleetd today.** fleetd runs the scan as `--stream` without `--loose` (`fleet-scan.ts:547`; `--loose` is opt-in at `plot-fleet-scan.sh:282`). A stale green rollup therefore cannot open the next wave on the strict path. A stale listing mostly causes holds, which is the safe direction. Agent start and restart decisions re-ask the host live (`restart-command.ts:67`, the tick's `prOpen`). Slice 3 should state this so that a later change to `--loose` re-checks it.
- **Layering.** Slice 1, if done by "attributing `budget.tsv` entries to its own run", needs a process identity that the record deliberately does not carry (`cadence.ts:84-86`: *"Counting its own lines would need the record to carry a process identity it deliberately does not have."*). The workable form is for the scan to report its own request count. The shell already prints `listing: .branches N` on stderr (`plot-fleet-scan.sh:963-964`), and the scan can sum it per pass as `scan=` on the tick line, kept separate from `mine=`.

## (c) Slices

- Slice 1 should go first, but as "the tick line names every fleetd loop's spend in requests": tick, scan, PR reader, issue reader. Each figure comes from its own counter, not from `budget.tsv`. The plan's own argument (an honest figure first) supports this.
- Add a slice before slice 2: **a refused scan listing backs off** (`bug/a-refused-scan-listing-backs-off`). A refusal sets a bounded `backoffUntil` on `ScanState`. The scan still runs with the carried listing and still writes the bridge. This is the cause the probe shows, it is independent of slice 2, and it is the smallest change that stops the 429 storm. It replaces most of slice 3.
- Narrow slice 3 to what the existing stretch does not cover, or merge it into the new slice. As written it duplicates `listingSpend`.
- Slice 2 depends on the open-question-1 measurement. If `pr-state` from agents or from the tick dominates, the delta saves less than the plan assumes.

## (d) Open questions

- *Sweep, `pr-state`, or both?* Not answerable without the measurement. The code shows the scan's per-pass cost is `2 × branches × states` when not reused, and `pr-state` arrives from four call sites (see (a)5). Add: count the agents' calls separately from fleetd's own.
- *Is cause 3 still true?* No for the scan's readers on one machine (see (a)6). Drop it.
- *Which limit?* `spendRateFor` already parses `limit` and `basis` (`fleet-scan.ts:213-232`). Use refusals as the back-off trigger and the rate only for the stretch, because a per-machine record cannot see another machine on the same account.
- *Does `mine=` count the scan when a board ran it?* A board scan never touches fleetd's `tally`, and with fleetd up a board does not scan (`fleet.ts:2720-2727`). So the question only applies with fleetd down, where no tick line exists.
- New: what is the maximum age of a carried listing before the fleet must refuse to act on it, rather than reuse it? Today the stretch alone allows up to 8 × base (4800 s at 40 branches).
- New: must a back-off longer than `OWNED_BRIDGE_MAX_AGE_MS` keep writing the bridge? (Yes. See (b).)

## Amendments

1. Correct the problem statement: the scan runs on the 5 s fleet clock, not in the 60 s tick. Name `listingSpend` as the existing stretch and its 720 req/hr base share on Bitbucket.
2. Add the missing cause: a refused listing never moves `listingAt`, so it is re-asked every beat. Add a slice that backs off on refusal with a bounded `backoffUntil`, before slice 2.
3. Rewrite slice 3 (or fold it into 2.): the back-off skips only the host listing. It keeps scanning with the carried listing and keeps writing the bridge within `OWNED_BRIDGE_MAX_AGE_MS`, so boards do not take over.
4. Slice 1: count requests, not invocations, per loop from in-process counters. Do not attribute `budget.tsv` lines, which carry no process identity.
5. Slice 2: drop the PR-index option (OPEN rows are not readable from the index). Use the windowed listing, not a windowed sweep. Scope `.list-complete` to the branches the base sweep asked, so no-ref merged branches cannot read `NONE`.
6. Drop cause 3. Add a measurement step that separates agent-descendant calls from fleetd's own.

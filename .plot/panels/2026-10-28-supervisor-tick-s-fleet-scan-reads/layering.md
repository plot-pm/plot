## (a) Problem statement

1. **The scan does not run on the 60 s tick.** The plan says "The tick runs `plot-fleet-scan.sh --stream` through `scanOnce`". `fleet-clock.ts:61-68` says the scan runs "on every beat and the PR refresh on every twelfth, apart from the supervision tick", on a 5 s beat with an in-flight guard; `registryd-main.ts:2570` starts that clock separately from the tick loop at `:2700-2740`. The title, cause 1 and slice 1 inherit the issue's "every 60 s". This matters for slice 1: the `mine=` tally (`tally.calls`, `registryd-main.ts:2726`) belongs to one loop and the scan to another.
2. **Cause 4 is wrong as stated.** "Nothing reads `account=` to slow the tick" is true for the tick (`registryd-main.ts:2725`, "Reported, never acted on") but the scan's listing already reads the account's rate: `scanOnce` calls `listingSpend` with `spendRateFor` (`fleet-scan.ts:504-515`), which stretches the interval up to `MAX_CADENCE_STRETCH = 8` (`cadence.ts:32`). Probe result (Bitbucket, 4 tracked branches): unread rate → 720 listing requests/hr; rate 1000/hr → 120/hr; rate 3664/hr → 96/hr. With 11 branches: 660 → 132 → 99. So the listing is already throttled by share, but never against the host's limit (`cadenceStretch` divides own share against others and has no `limit` input, `cadence.ts:173-215`). The defect is "the stretch ignores the limit and caps at 8×", not "no back-off exists".
3. **Cause 1 conflates three readers in one fleetd.** The issue's per-verb counts are attributed to the fleetd process tree, which holds: the scan's sweep (`pr-list --state open/settled --branch …`, `plot-fleet-scan.sh:1047, 1063`); the PR-index beat `refreshPrs` (`pr-list --state all`, three Bitbucket listings per refresh, `pr-refresh.ts:222, 1510`); and the tick's merged listing (`host.prList('merged', …)`, `registryd-main.ts:854, 896`) and per-agent `prState` (`:938, 1807, 1964`). `pr-list --state merged` 11/90 s matches the tick's `mergedBranches` or `bb_states_for settled` sub-calls, not only the scan. The plan's open question 1 asks about the sweep versus `pr-state`; it must also separate the PR-index beat and the tick, or slice 2 can land and the spend stays.
4. **`pr-state` per branch is not the scan's normal path on Bitbucket.** `host_pr_state --ask` answers `NONE` without a host call once `.list-complete` exists (`plot-fleet-scan.sh:1344-1352`), and a complete Bitbucket sweep writes that marker (`:1263-1274`). The 15 `pr-state`/90 s fit better with `registryd-main.ts:938/1807/1964` (tick, counted in `tally`) or a scan whose sweep did not complete. Open question 1 should name this.
5. **Cause 3 is already answered for the scan.** The board scans only when `fleetOwnsScan` is false (`board/src/server/fleet.ts:2715-2727`), which is a single-scanner rule. The issue's own measurement shows boards at 0. The remaining duplicate is inside fleetd: the scan's sweep and `refreshPrs` both read the same Bitbucket PRs every few minutes. The plan should drop cause 3 as stated and name that duplicate instead.
6. Cited lines check out: `fleet-scan.ts:547` is the `stream(FLEET_SCAN, ['--stream'])` call; `registryd-main.ts:461` is `minePerHour: boardSharePerHour(intervalMs, calls)`.

## (b) Approach, by layer

**Slice 1 (`mine=`).** The plan says "the tick attributes those entries [budget.tsv] to its own run". `budget.tsv` rows carry no caller (sample row: `b1 github jwloka graphql <at> 1 - - - unknown`), so the tick cannot attribute them without a new field. Two layer-correct routes exist:
- `scanOnce` counts what it spent and stores it in `ScanState`: the `readGithubListing` calls it makes itself, plus the shell's measured `.branches` line (`report_listing`, `plot-fleet-scan.sh:963`), priced by the existing `scanListingCost`. The tick reads that figure. This adds no shell line, except that `pr-state --ask` calls are not reported today, which needs one tagged stderr line (`asked: N`) in the shell.
- `plot-host.sh`'s `budget_record_call` writes a caller tag from an env var (`PLOT_BUDGET_CALLER`), and a domain rule derives `mine=` from the record. This is more general because it also covers `refreshPrs` and the issue gate, but it changes the budget record's format (`entities/budget.ts` decode) and grows `plot-host.sh`.
Either way, the per-hour arithmetic belongs in the domain (a sibling of `boardSharePerHour`), not in `registryd-main.ts`. The plan must also say over which interval `mine=` is computed, because the scan's beat is not `args.intervalMs`.

**Slice 2 (Bitbucket delta).** Reuse is possible and mostly TypeScript, but dropping the `backend === 'github'` guard at `fleet-scan.ts:535` alone gives a fold that refuses most deltas. Measured and read:
- `foldScanListing` accepts a Bitbucket sweep as a whole full read (probe: `ok: true, complete: true` for a stderr carrying `pr-list sweep complete …`, matching `pr-status.ts:58`), and refuses a repo-wide Bitbucket listing truncated at `pagelen=50` (probe: `no-whole-page-claim`). So **the full read must stay a branch sweep**, not `--state all` unbranched.
- The tracked set does not need the shell. `Refs.listBranches(true)` exists (`ports/refs.ts:183`), and `world.refs` is already in `ScanWorld`. TypeScript can build the `--branch` arguments itself, as the shell's `TRACKED_BRANCHES` does (`plot-fleet-scan.sh:766`). That is a second implementation of one rule (drop `HEAD`, empty set disables the sweep), so it is a declared duplicate under "A Shell Script Asks The Domain" and needs a corpus pair, unless the shell's copy stops being reached once `PLOT_PR_LISTING` is always handed over.
- **The delta's `--state all --since` answer makes no whole-page claim on Bitbucket.** `plot-host.sh:1602-1608` skips the truncation report when `PR_LIST_SINCE` is set, and `pr_sweep_report` is silent without branches (`:1544`). `wholePage` (`scan-listing.ts:183-186`) then accepts only an empty answer. So an idle delta (0 rows) folds, and any delta with one changed PR is refused and costs a full sweep. Two fixes: the adapter states a window claim (`bb_window_listing` already refuses a short window, so it is whole; a new `NOTICE_PATTERNS` entry plus one `echo`, which grows `plot-host.sh` and must be offset under `check-shell-lines.sh`), or the domain's `wholePage` learns a backend-specific rule. The first is the right layer: the adapter knows the window is whole and the domain reads claims.
- The delta's `--state open --rich` call must go **without** `--branch`, or it is a sweep again (N requests). Unbranched, `bb_state_listing` claims `page complete` only below 50 open PRs (`plot-host.sh:3346-3347`). Above that, every delta refuses. Name this limit.
- A carried listing's watermark is its newest row `updatedAt` (`scan-listing.ts:59`). The Bitbucket sweep rows must carry `updatedAt` through `parseScanListingRows` for this to work. The shell's own `listing:` lines carry none (`plot-fleet-scan.sh:982`), so the full read must be made by `scanOnce` through `askPrList`, as on GitHub, and never adopted from the shell's report.
- On "or let the shell take the listing from the PR index": under "A Decision Reads The Index", only MERGED rows may be read from the index, and the scan needs OPEN rows with checks. That route needs a new licence paragraph in CLAUDE.md and is the larger change. The plan should choose the carried-listing route and strike the index alternative, or state the licence it would add.
- Every change to `scanOnce` also changes the board's fallback scan (`board/src/server/fleet.ts:2728`), which shares the function and passes its own `entry` as `ScanState`. Name that reader.

**Slice 3 (back-off).** "The tick skips its host read" puts the decision in the wrong place, for the same reason as (a)1. The scan's listing decision is `listingSpend` → `refreshIntervalMs` → `cadenceStretch`, all domain rules. The fix that follows the layering rule extends that rule with the connector's `limit` (`SpendRate.limit` is already parsed in `spendRateFor`, `fleet-scan.ts:220-227`, and then not passed; `listingSpend` takes only `Pick<SpendRate, 'perHour'>`). The scan does not need to "join" the issue gate's `backoffUntil` (`issue-refresh.ts`) unless the plan argues that, since the PR pass reads that gate already and a third reader of `issues.json` adds a cross-file dependency. Whatever the rule decides, the per-tick `prState` and merged-list calls in `registryd-main.ts` stay outside it; say whether they are in scope.

## (c) Slices

- The cut is mostly right: three independent branches. The order should be **slice 2 first or with the measurement**, because slice 1's figure only matters if the plan uses it to judge slices 2 and 3, and the probe already shows the listing's spend for a given branch count without it.
- Slice 3 should be re-scoped to "the listing cadence reads the host's limit" in `listing-spend.ts`/`cadence.ts`. As written, it builds a second back-off beside the existing one.
- Missing: the in-process duplicate between the scan's sweep and `refreshPrs` (both read Bitbucket PRs in one fleetd). Either a slice or an explicit out-of-scope line.
- Missing as a prerequisite: the adapter's whole-window claim for `bb_window_listing`. It can ride inside slice 2 because it is small, but it touches `plot-host.sh` and `pr-status.ts` and needs a shell-line offset.

## (d) Open questions

- Q1 (source of spend): partly answerable by reading. With a complete sweep, `pr-state --ask` makes no call (`plot-fleet-scan.sh:1344`). The `pr-state` calls are probably the tick's (`registryd-main.ts:938/1807/1964`). The `--state merged` calls match the tick's `mergedBranches` (`:854/896`). Measurement must tag the parent: scan subprocess versus fleetd's own `hostSaid`.
- Q2 (cause 3): for the scan, `fleetOwnsScan` already elects one scanner; `ReaderLock` covers `fleetPrs` only. Drop cause 3 as worded; carry the scan/`refreshPrs` duplicate instead.
- Q3 (which limit): `SpendRate` already carries `limit` and `basis` (`actual|predicted|unknown`) from `plot-host.sh spend-rate`. Use that and do not add a config key. A `basis: unknown` limit must not cause a back-off, by the same rule that an absent rate holds the cadence (`cadence.ts:181-189`).
- Q4 (board-started scan): when a board scans, fleetd does not own the scan (`fleetOwnsScan`), so the tick's `mine=` has nothing of it to count. The question resolves to "no, by design".
- New: what is the full-read interval for a Bitbucket sweep? `PR_FULL_READ_MS` is 24 h (`pr-refresh.ts:342`). A branch pushed after the full read with no PR answers `NONE` correctly, but the plan should state that a branch whose PR predates the full read and that had no ref at that time is caught by the delta's `updated_on` or by the next full read.
- New: what does the delta cost on Bitbucket? One unbranched open listing plus three windowed listings (open, merged, declined) is 4 requests, or more with pages, against `branches × 3` for a sweep. `scanListingCost` (`fleet-scan.ts:133-140`) must price a delta, or `listingSpend` keeps stretching against the sweep's price.
- New: `scanListingCost` is a pricing rule in `packages/fleet`. If it gains a delta arm, it should move to the domain beside `listing-page.ts`.

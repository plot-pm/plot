3. **Slice 2 puts a decision in `ci.yml` shell that this repo's precedent keeps in the domain.** The push base has to be chosen: the newest green push run's head, on `HEAD`'s first-parent line within 50, or every job for one of four named reasons. That is a decision with refusal reasons, the same shape as `ciReuse`. `ciReuse` is a domain rule (`packages/domain/src/rules/ci-reuse.ts:205`) that reads `event`, `runAttempt` and the earlier runs as values the shell collected (`ci.yml:404-413`), and `plot-ci-reuse.mjs` decides (`ci.yml:417-421`). Every reason then lives in bash and is asserted only through a fake `gh`. RAN. **Amend:** add a domain rule, for example `pushSelectionBase({ greenHead, firstParent, depth })`, that answers `{ base }` or `{ every: 'api-failed' | 'no-green-run' | 'off-line' | 'past-depth' }`, with unit rows for each answer. The shell then collects the API answer and `git rev-list --first-parent -n 50 HEAD`, asks the bundle, and the harness keeps one row per wiring path. If the plan keeps the shell, it must say why `ciReuse`'s split does not apply.

4. **`--arg event` breaks the second caller of `ci-job-map.jq`.** The map has two callers: this run's map (`ci.yml:228`) and the reuse read, which maps each earlier run's diff (`ci.yml:398`). If the program reads `$event`, jq refuses to compile at the caller that does not pass it. At `:398` that failure is inside an `&&` chain, so `map=null` and the reuse is lost silently, and no job goes red. The reuse fixture copies the real jq (`ci-selection-jobs.test.mjs:522`), so it would catch this only if one reuse row asserts a non-null `jobMap`. RAN. **Amend:** read the event as `($ARGS.named.event // "pull_request")`, or pass `--arg event` at both callers. Name a reuse row that asserts `jobMap` is set after the change. The guard `[ "$EVENT" = "pull_request" ] || every …` (`ci.yml:224`) must also change. The `map()` harness runs that step's script (`ci-selection-jobs.test.mjs:58-83`), so the split push rows cover the guard.

5. **The proof of the re-run group is placed where it cannot happen.** The plan says "the builder records in the PR that a re-run's group reads `ci-<run_id>` on the first re-run on `main`". A fleetd re-run on `main` happens only after the slice has merged, so the PR cannot carry it. The repo also cannot test what GitHub does with the group: that a newer push cancels the pending run and leaves the running one, and that a re-run evaluates the group again with `run_attempt` 2. `release-pr-ci.test.mjs` only evaluates the expression (`:150-176`). READ and RAN. **Amend:** replace that sentence with a post-merge check that the plan states. Take two pushes inside one running run: the first push's run concludes, the middle push's run reads `cancelled` with no jobs, and the newest push's run starts after the first. Then, at the first re-run on `main`, `gh api …/runs/<id>/attempts/2` shows its own group. Record both in the delivery, and name who runs the check.

6. **Slice 1 drops gate ranges and names no test for that.** On a push, the gates compare against `github.event.before`. `check-shell-lines.sh push` runs at `ci.yml:1857-1863` and `check-decision-count.sh push` at `:1866-1874`. Once a pending run is cancelled, the range of the cancelled head is never measured: the next run measures only `before..HEAD` of its own push. Push mode reports and does not refuse, so a lost range loses a warning and not a gate. The plan does not mention it. RAN. **Amend:** name the loss as accepted in slice 1's Approach. Better, have slice 2 hand these two steps the same last-green base, and add a harness row for it.

## Open questions

- **`[question-cancel-in-progress]`: confirm `false`.** The plan measures a median push gap of 1.9 min against a green run of at least 19.9 min. At that rate, `true` lets a run conclude only in a 20-min gap, and the plan counts 2 such gaps in 5 h. The reading would stay settled on an old head for longer than it does today. `false` bounds that wait to about two run lengths. The release-PR and dispatch groups keep `true`, and the expression row tests them.
- **`[question-plot-panels]`: keep `.plot/panels/` out.** `syncPathSet` is also the set `settledPast` trusts past a green settled commit for fleetd's merges (`auto-merge.ts:314-329`). Widening it widens merge trust to buy one push in 60. The pull request selection already treats a panel path as plan data (`ci-selection.test.ts:159-167`), so a panel-only push that runs every job is slower and not wrong. A builder should keep the plan's `false` row for a `.plot/panels/` path, so that the two meanings of "plan data" in `ciSelection` stay visible.

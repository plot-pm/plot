## Findings

1. **Slice 1 changes the unknown-head bound, and the plan says "No change".** The plan says that with slice 1 "a head's run is pending until it concludes, so the bound fires only for a run cancelled by hand". That is not what the reading sees. A run waiting in `ci-main-push` has created no jobs. The plan says so itself for a cancelled pending run. The in-process connector adds a `CI/validate` entry only for a job that exists (`packages/domain/src/adapters/build/build-actions.ts:84-108`). `declaredRuns` keeps only that job-form name (`default-branch.ts:61-64`). So the head's declared runs are empty and `foldRuns` reads `unknown` (`default-branch.ts:97-103`), not `pending`. Today every push run starts at once with queued jobs, so the head reads `pending`. With slice 1, the head reads `unknown` for as long as it waits, which is up to one full run (median 148.5 min in the Motivation). `unknownHeadBound` (`packages/domain/src/workflows/merge.ts:200-209`) then lets a person's `plot-ask.mjs merge` pass `default-branch-unsettled` after `Checks wait` (3600 s), over a head that no run has tested. That would happen routinely, not only after a hand cancellation. Read and opened. **Change:** in the "`plot-ask.mjs merge` and fleetd's merge arm" bullet, replace "No change" with this effect. Then do one of two things. Accept it, and give it a changelog line and a test row in `merge.test.ts` (a person, head `unknown` for longer than `Checks wait` while its run waits in the group, passes). Or say how the bound must tell an in-group pending run apart from a head with no run. One possible test: the run-level row's status is `pending`/`queued`, and `runsForShaOf` already returns that row.

2. **The `--arg event` guard in `ci-job-map.jq` has two callers, and the plan names one.** The map runs at `ci.yml:228` (this run's selection) and again at `ci.yml:398` (the reuse read for each earlier head). If the program refers to `$event`, jq fails to compile wherever `--arg event` is missing. At `:228` that falls into `every`. At `:398` the reuse source is dropped quietly, so pull-request reuse stops without any red check. Opened. **Change:** keep `ci-job-map.jq` unchanged and put the push guard in the shell step, where it is today (`ci.yml:224`): `[ "$EVENT" = "pull_request" ] || [ "$(jq -r '.planDataOnly // false' selection.json)" = true ] || every "a $EVENT run"`. If the plan keeps the jq argument, it must name both call sites and give the `:398` call `--arg event pull_request`. Either way, add a contract row that runs the reuse read's jq call unchanged.

3. **The plan does not show that the narrowed run outpaces the push rate.** The deliverable needs a bookkeeping head's run to conclude within the 5-commit cover of `settledPast` (`ANCESTOR_ASKS_MAX`, `default-branch.ts:137`; `settled-past.ts:44-50`). The plan states no duration for a 5-job run. Plan-only PR runs, which run the same job set, took 9.3 to 17.3 min today: runs 44893921544, 44894023149, 44877522071, 44876592328, 44876462684 (read with `gh api …/workflows/ci.yml/runs?event=pull_request&status=success`). At the median push gap of 1.9 min, that is 5 to 9 commits per run, at or above the cover of 5. So fleetd's merge arm still holds for part of every run. Also, the hold fleetd's selection gives in that case is `merge-in-flight` (`slice-pr-next.ts:487-489`), not `default-branch-unsettled`. Only `plot-ask.mjs merge` refuses `default-branch-unsettled` (`merge.ts:389-391`). Ran and opened. **Change:** add the measured plan-PR run time and the expected commits per run to the Motivation or Approach. Name `merge-in-flight` for fleetd. State whether the plan expects the cover to hold, or accepts a shorter hold rather than none.

4. **`.plot/hold` is in the set, but the map widens it to every job.** `FIXED_SYNC_PATHS` holds `.plot/hold` (`state-sync.ts:49`), so `planDataOnly` is true for a push that changes it. The path is not `.md`, though, so it lands in `untested`. `$wide` (`scripts/ci-job-map.jq:11`) then sets `$all`, and the run runs every job. That fails safe, but the plan's sentence "then it maps the answer as it maps a pull request's … 5 of 11 jobs" does not hold for it. Read. **Change:** add one row to `ci-selection-jobs.test.mjs` for a push of `.plot/hold` (every job), or say why the hold file is out of scope.

## Open questions

- **`[question-cancel-in-progress]`: confirm `false`.** Finding 3 supports it. Even the narrowed run (about 9 to 17 min) is 5 to 9 times the 1.9 min median gap. With `true`, a bookkeeping head would still finish only in a quiet gap, so the reading would trail longer than today. `build-bundles.yml` uses `true` for a different reason: an older build must not overwrite a newer one. That reason does not apply to a test run.
- **`[question-plot-panels]`: keep `.plot/panels/` out.** `syncPathSet` has three readers, not two. The third is the sync-PR gate (`packages/board/src/server/entry/state-sync-gate.ts:46` → `syncPathVerdict`), which decides what a sync pull request from the state ref may carry. Adding the path there widens an auto-merged change set to cover a review product, all to save a full run on 1 commit in 60. If the saving is wanted later, add the path to the set that `planDataOnly` reads, not to `syncPathSet`.

# Juror verdict: safety

Position: amend

Evidence: Read the plan, issue #2901 (`gh issue view`), DESIGN-delivery-loop.md, sibling plans #2898, #2899 and #2915, and the code at the worktree's tree (4de186a03): `packages/fleet/src/shared/{continuation.ts,continue-command.ts,escalations.ts,worker-question.ts,restart-command.ts}`, `packages/fleet/src/server/entry/{continue-command.ts,registryd.ts,registryd-main.ts,loop-writes.ts}`, `packages/domain/src/{rules/question-escalation.ts,rules/continue-lock.ts,rules/controller-gate.ts,rules/run-limit.ts,workflows/agent-loop.ts,ports/agent-run.ts,adapters/agent-run/agent-run-command.ts,adapters/desk/desk-fs.ts,adapters/tracker/tracker-plan-state.ts}`, `skills/plot/scripts/{plot-controller-gate.sh,plot-host.sh}`. Ran: `plot-continue-command.mjs` and `plot-restart-command.mjs` from the worktree's bundles with `PLOT_UNATTENDED=1` in an empty scratch repo. Both refused `unknown-branch` before any caller check, so the run does not tell the two apart. The claim about the continue controller below rests on the source. No unit tests run.

## (a) Problem statement

- **The plan says `continue` has an unattended refusal to lift, and it has none.** The plan says "The controller lifts its unattended refusal only for a caller that declares itself as fleetd's". `continueOnDesk` (`continuation.ts:815-1015`) and `continueBranch` (`continue-command.ts:68-100`) never read `PLOT_UNATTENDED`. The `ContinueRefusal` member `'unattended'` is commented "`restart`: the caller runs unattended" (`continuation.ts:162-163`), and only `restart-command.ts:40,81,138` and `board/src/server/restart.ts:68` read it. `controller-gate.ts` has no rule for `continue` either. The design (line 144) and #2898 make the same mistake. Today any unattended process on the machine, including a desk worker answering its own question, can already call `plot-continue-command.mjs`. The safety rule "unattended refusals lifted only for fleetd's declared caller" therefore needs a refusal that is ADDED, not lifted. Adding it is a behaviour change and needs its own slice and test. fleetd's fresh-agent step calls `continueOnDesk` in-process (`registryd.ts:1146-1160`), so it is not a CLI caller that a new refusal would break.
- **Not every `PLOT-BLOCKED` marker is an agent's question, and the plan does not say so.** The loop itself writes terminal markers: checks failed after the budget is spent (`agent-loop.ts:503-507`), conflicts after the budget (`:548-551`), a usage limit that cannot be waited out (`:807-809`), every write refused (`:907-909`), dropped background work (`:962-964`), and others (`:793`). fleetd writes one for `needs-a-person` after a failed fresh session (`registryd.ts:1208-1232`). The plan's trigger, "When an agent writes a `PLOT-BLOCKED` marker", reads all of these as questions. The motivation's "99 questions" count does not separate them either.
- "fleetd only escalates (`escalations.tsv`)" is correct: `notifyEscalations` (`registryd-main.ts:1515-1560`) appends rungs keyed on worktree and marker mtime (`escalations.ts:6-31`, `recordedRungsFor` `:88-99`).

## (b) Approach, read against the anti-goal and the safety rules

1. **One writer per branch breaks on loop-written markers.** Row 15 (`agent-loop.ts:503-507`) writes "checks failed after N corrections" exactly when the design's loop table says "CI red, desk dead or corrections spent → start fixer" (DESIGN line 76). On that tick `unblockerDue` and the fixer rule (#2903/#2915) both fire for one desk. The unblocker's `continue` starts a new worker on the desk (`continuation.ts:1160-1200`) while the fixer pushes commits to the same branch: two writers. The same holds for fleetd's own `needs-a-person` marker, which #2915 replaces with a fixer. Answering the usage-limit marker (`:807`) starts a run into the same limit, which writes a new marker and starts the cycle again. **`unblockerDue` must exclude loop- and fleetd-written markers** (they need a recognisable author or prefix) and leave those to the fixer and restart rules. Otherwise the unblocker becomes a second path past the correction budget and the fresh-agent budget.
2. **"Once per question" has no durable key in the plan.** The plan says "The rule answers once per question, so a restarted fleetd does not start a second unblocker". It names no record, and it demotes `escalations.tsv`, the only per-marker record today. The #2899 run log is keyed by slice, PR and head, and a blocked desk often has no PR. Precedent: the fresh-agent step appends `.plot/state/fresh-agents.tsv` in `beforeStart`, before the spawn (`registryd.ts:1150-1160`). The unblocker needs the same: a record keyed on (worktree, marker mtime or content hash) and written before the agent starts. Crash cases:
   - **fleetd crashes after the start and before the record.** The restarted fleetd starts a second unblocker. `takeContinueLock` (`continuation.ts:857-860`) and the `loop-alive` check (`:898-901`) refuse the loser's `continue`, but only if the winner already started.
   - **The record is written and the start fails.** The marker stays, the desk reads `waiting`, and the record says the question is answered: the desk stalls silently. The record needs an outcome (`started` / `refused <reason>` / `failed`). The rule re-answers only `failed`, and it bounds that.
   - **`agent-run` is awaited.** `AgentRun.run` "runs one agent turn to its end" and "the run stays in its caller's process group" (`ports/agent-run.ts:6-25`). Called inside the tick, it stalls every other loop step, including holding the merge queue on a red main, for the unblocker's whole run. Started detached, it needs the record above plus a pid. The plan must choose one.
3. **Stale answer to a new question (two ticks, or a person and the unblocker at once).** `plot-continue-command.mjs <branch> <answer>` (`entry/continue-command.ts:14-18`) carries no question identity. Unblocker A reads Q1 and takes minutes. Meanwhile a person answers Q1 on the board, the continued worker writes Q2 and exits. A's `continue` then passes the lock, the marker check (`continuation.ts:829-837`) and `continueTarget`, and delivers Q1's answer as the answer to Q2. This is the same race `merge` closes with a head pin. **Amendment: `continue` takes the question it answers (marker mtime or hash) and refuses `question-moved` on a mismatch.** The board's route can send the same pin. If the person wins the lock, the unblocker gets `loop-alive` and must record that refusal, not retry it.
4. **Who answered must be recorded by the controller, not by the agent.** The recorded author has to be the caller `continue` accepted. Otherwise an unblocker that lost to a person records itself as the author. The local answer record should be written by `continueOnDesk` beside `.plot-continuation.md`, and the issue comment derived from it.
5. **The issue comment is overwritten whole on every phase change.** `planStateComment` returns `marker + "Plan <phase>: <link>"` (`tracker-plan-state.ts:44-47`), and `issue-comment` "edits the comment holding <marker>" (`plot-host.sh:5745`). A `delivered` or `released` write erases an answers list kept in that comment. Two writers that read, modify and write the comment (answers here, the progress line from #2914 or #2916) lose each other's updates. Size: `ANSWER_MAX` is 8 KiB (`continuation.ts:84`), so 99 answers reach about 810k characters against GitHub's 65,536-character comment limit. An oversized body fails step 2 of `githubPlanStateWrite`, and that function stops before step 3, `issue-close`, on `released` (`tracker-plan-state.ts:73-89`). The answers list must go in its own marked comment, regenerated whole from the local record and size-bounded. The plan-state comment must never carry it.
6. **A host failure must not change what the fleet does.** The answer is recorded locally first. The comment is a projection retried each tick. A failed or partial `issue-comment` never re-starts the unblocker and never blocks `continue`. `issue-comment` is GitHub-only (`plot-host.sh:470`), so a Bitbucket/Jira estate has nowhere to post. OQ2 must cover that case as well as the missing `Issue:` case.
7. **The answer itself can authorise a rule break.** A desk can ask "may I edit the gate / bump the ratchet / skip the review?". An unblocker that "always answers" can answer "yes". The fixer's hard rules (DESIGN line 138: never edit gates or the CI ratchet, never join lines, never write "Fixes #N"), no bypass of `plot/review`, and no release must bind the unblocker's ANSWERS too. The reversible answer to an exemption request is "no; keep the rule and say so in the PR body". Also, "read-only" isolation cannot run `plot-continue-command.mjs` without Bash. The definition needs a `PreToolUse` allowlist (the continue bundle, read-only `gh`/`git`/`plot-host.sh` verbs). Its cwd must not be the desk worktree (`AgentRunRequest.worktree` is "the desk", `ports/agent-run.ts:37`), or a read-only role can become a second writer there.
8. Layering and ratchets: the plan adds no shell, and a domain rule plus an adapter start fits the layering rule. *A Decision Reads The Index* holds only if `unblockerDue` reads the recorded answer file (2 above), not a fresh `continue` result.

## (c) Slices

- **Slice 1 duplicates #2898.** `feature/role-agent-definitions` in #2898 already "builds: reviewer.md, fixer.md, unblocker.md, main-repair.md". Two branches writing `.claude/agents/unblocker.md` will conflict, and the second one to merge overwrites the other's hooks. Drop slice 1, or make it extend #2898's file (charter text and answer rules only) and wait on that branch.
- **Slice 2 is not safe alone.** Merged before slice 3, the fleet answers questions with no record anywhere a person looks, which breaks the call "every answer is recorded". Move the durable local answer record (the idempotency key, item 2) into slice 2, and leave only the issue projection in slice 3.
- **Missing slice: the continue controller.** It adds the unattended refusal with the fleetd-caller exception, the question pin and refusal `question-moved`, and the controller-written answer record (author = accepted caller). It must merge before slice 2. Alternatively #2898's caller-identity slice must name `continue` as gaining a refusal rather than losing one.
- Order dependency with #2903/#2915: `unblockerDue` must ship with its marker-author exclusion, or after the fixer rules, so the two never both fire on one desk.

## (d) Open questions

- **OQ1 (fallback loop bound):** a bound already exists. `continue` counts itself as a run and refuses past `Slice max runs`, default 12 (`run-limit.ts:13`, `continuation.ts:947-951`), and past `Slice max spend` (`:952-965`). A second counter that reuses the correction budget would be a third count of the same runs. The open defect is what happens AFTER that refusal: the marker stays, and without a recorded `refused run-limit` outcome every tick starts a new sonnet unblocker to be refused again. Proposal: record the refusal, stop for that marker, and send one stall notification through #2899.
- **OQ2 (no `Issue:`):** agreed, local record only. Extend the answer to every estate whose tracker has no `issue-comment` verb (GitHub-only today, `plot-host.sh:470`).
- **OQ3 (size):** a separate marked comment, regenerated whole from the local record, holding the last N entries with each entry truncated, and naming the local record for the rest. Never inside the plan-state comment (item 5).
- **New questions the plan should carry:**
  - Which marker authors does the unblocker answer?
  - What is the key of "one question": mtime, content hash, or a marker id? Note that `writeBlockedMarker` no-ops on an existing file (`desk-fs.ts:135-139`), so a continued worker that never deletes the old marker can never raise a new question through the loop.
  - Is the unblocker awaited in the tick or detached?
  - Where does it run (cwd)?
  - What does the board's WAITING ON YOU read to know "answer in flight", and from which recorded file?
  - Is a desk "elsewhere" (`continue-command.ts:84-91`, `no-worktree`) excluded from the rule?

## (e) Tests

- Domain unit (vitest, `packages/domain`), `unblockerDue` as a readings-as-values rule:
  - A loop-written marker (each `agent-loop.ts` row text) and a fleetd `needs-a-person` marker answer `leave`.
  - A recorded `started` for (worktree, key) answers `leave`. A recorded `failed` answers `start` once, then `leave` with a stall.
  - A recorded `refused run-limit` answers `leave`.
  - A running worker answers `leave`.
  - A new marker key on the same desk answers `start`.
- Fleet unit for `continueOnDesk`:
  - A pinned key that differs from the marker refuses `question-moved` and writes nothing (no `.plot-continuation.md`, the same no-trace contract `:875-879` keeps).
  - Two concurrent calls (person and unblocker) start exactly one run, and the answer record names the winner.
  - `PLOT_UNATTENDED=1` without the fleetd identity refuses `unattended`. With it, the call proceeds.
- Crash test (fleet unit, fixture ports): kill between record and start, then a fresh tick, gives one start. Kill between start and record cannot happen when the record is written in `beforeStart`. Assert that ordering, as `registryd.ts:1150` does.
- Tracker unit: the answers comment uses its own marker. A `delivered` plan-state write leaves it intact. The body stays under 65,536 characters with 99 maximal answers. A failed `issue-comment` changes no local record and starts no unblocker.

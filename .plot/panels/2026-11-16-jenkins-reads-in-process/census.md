# Census and measurement juror

Position: amend

Lens: whether the goal (an idle fleetd pass starts no `jen`; Jenkins reads run in-process) is proved by a census row that runs in CI, on a fixture that exercises Jenkins, with a stated limit and a baseline. The plan has the right shape (a baseline slice before any read moves, a zero row P12 that turns green at cutover, a stub-server count against a shell baseline), but five gaps would let P12 go green without proving the goal, or would corrupt the census report.

## 3. Done-when rows: fail before, pass after

- "The census measures Jenkins" (Client) is a presence check, not a fail-before/pass-after check. It fails before only because the row does not exist. Acceptable for a baseline slice, but it needs a non-trivial assertion (see edit 3).
- "An idle pass starts no process for a Jenkins read" (Cutover, P12 green) fails before (the shell rich read runs `plot-host.sh pr-list` and `jen` each beat) and passes after. But it also passes after a defective cutover in which the client never reaches Jenkins (edit 3).
- "The request count does not grow" is `≤` only, as P5/P10/P11 are (`fleetd.census.test.ts:335`, `:347`, `:361`). With Jenkins this is weaker than with the precedents: a client that cannot resolve the stub URL answers `unknown` and makes 0 requests, and 0 ≤ N passes.
- "The removed processes are counted" (Cutover) names a PR statement, not a check. It cannot fail.
- "GitHub and Bitbucket without Jenkins are unchanged" passes before and after; it is a regression guard, which is fine, but it names S4/P5/P10/P11 and not the measured rows S5, S6, S8 that the census also compares (see edit 5).

## 4. Missing or wrong

a. **The census comparison key has no CI field, so a second Bitbucket fixture with 3 desks and 5 PRs collides with the existing one.** `census-report.ts:145` keys a row on `${id} ${host} desks=${desks} prs=${openPrs}`, and `CensusFixture` (`census-report.ts:20`) holds no `ci`. `census-report.ts:187`: "Where a report holds one key twice, the last entry counts." The plan puts P12 on "the Bitbucket fixture with `CI: jenkins`, 3 desks and 5 open PRs" and also records S4 on that fixture. If that fixture joins `FIXTURES` (`fleetd.census.test.ts:36-40`), its S4, S8, P3, P4, P7, P8, P10 and P11 lines overwrite the plain Bitbucket fixture's lines in the report, and `census-gate.mjs --compare` silently compares one of the two. `rowTitle` (`census-rows.ts:186`) also gives both fixtures the same test titles.

b. **The plan does not say how the client reaches the stub server.** The fixture writes `Jenkins instance: census` (`sandbox.ts:83`), which `jen_url_for`'s default pattern expands to `https://jenkins-ci-census.internal.quatico.dev`. The precedents inject a base URL by environment (`GITHUB_API_URL`, `BITBUCKET_API_BASE`, `PLOT_JIRA_BASE_URL`, `sandbox.ts:244-257`), as the story's Phase 1 note requires ("the stubs become an injectable base URL and a local HTTPS server", story line 125). The plan names no variable. If the sandbox sets `JEN_URL_PATTERN=http://127.0.0.1:<port>/{slug}`, the `jenkins-url` corpus row must cover an `http:` pattern; if it adds a Plot-specific override, the plan must name it. Without it, the cutover's client fails DNS on CI and P12 reads 0 for the wrong reason.

c. **Credentials on the census runner are not named.** Open Question 1 (option A) reads only the environment, `.env` and `jen`'s file backend, and keeps the shell where none resolves. The sandbox sets no `JENKINS_USER`, `JENKINS_API_TOKEN`, `JEN_TOKEN` or file-backend blob today. The plan must say which source the fixture uses, and the stub route must check both headers as the Bitbucket and Jira routes check theirs (`stub-host.ts:312`, `:377`), or the census does not exercise the credential path at all. An in-process bearer refresh on the census needs a token endpoint on the stub server too, or the census row only ever sees a non-expiring `JEN_TOKEN`.

d. **The existing `bitbucket-jenkins.census.test.ts` asserts the opposite of the cutover.** Its first case, "reads the rich open pull requests through the shell" (`:52-56`, `bbOpenReads > 0`), fails once `SHELL_RICH_CI` is empty. The plan names only its start line (`:64-67`). The cutover slice must invert or remove that case.

e. **P12's predicate is narrower than the goal.** The claim reads "starts no jen and no plot-host.sh pr-list"; the Changelog promises "no `bash`, `jen`, `security`, `curl` or `jq` process for these reads". A regression that moves the overlay to `plot-host.sh runs-for-sha` or to `plot-jenkins-pr-checks.mjs` on each beat passes P12. S4 would catch it only if S4 is asserted zero on the Jenkins fixture, and the plan says S4 there is "recorded", not asserted. Note also that declaring `CI: jenkins` re-enables the default-branch tip read that the Bitbucket S4 zero depends on not running (story Measures, S4 row), so S4 on the Jenkins fixture may not be 0 for reasons unrelated to Jenkins reads.

f. **Runtime and flake budget.** The census step cap is 20 minutes against 830 s measured (`ci.yml:887-892`). A fourth traced fleetd fixture plus its shell baseline run adds one more traced run and one more untraced run (the existing fleetd suite took 358 s for three fixtures). The plan does not measure or state the cost. Separately, S6 was observed flaky on 2026-11-16 (881 against a limit of 648.8, `{ratio: 0.1, plus: 2}`, `census-rows.ts:72-77`), and the census job is not in `validate`'s `needs:` (`ci.yml:2850`), so a P12 `it` row is a census-job pass, not a required merge check. The plan should say what holds P12 after cutover.

## 5. The five decisions against the design

Consistent in the main. OQ5 (one switch) fits the census exactly: the baseline block already sets `PLOT_HOST_TRANSPORT=shell` once and reads every connector's shell counts in one run (`fleetd.census.test.ts:223-245`), so the Jenkins baseline costs no extra fleetd run if P12 shares that block. OQ1 (environment only, no `security`) makes the census predicate "a `PATH` stub `security` counts zero calls" meaningful on Linux only trivially, since `security` does not exist there; that Done-when row is a macOS-meaningful check that CI's Linux census cannot fail. OQ4 (GitHub with `CI: jenkins` also cuts over) has no census fixture: the GitHub fixtures declare `CI: github-actions` (`sandbox.ts:81-82`), so the GitHub arm of the cutover is proved by a corpus row only and no census row measures it. OQ2 and OQ3 do not touch the census.

## Required edits

1. Add `ci` to `CensusFixture` and to the comparison key (`census-report.ts:20`, `:145`) and to `rowTitle`/`sizeLine`, in Slice 1, or give the Jenkins fixture a size no other fixture uses (for example 0 desks, as `bitbucket-jenkins.census.test.ts:36` already does); name which, and add a `census-report.unit.test.ts` row that two fixtures differing only in `ci` produce two keys.
2. Name the injection that points the Jenkins client and the stub `jen` at the stub server (for example `JEN_URL_PATTERN=http://127.0.0.1:<port>/{slug}`, or a `PLOT_JENKINS_BASE_URL`), and add that pattern shape to `jenkins-url.corpus.test.ts`.
3. Give P12 a lower bound at cutover: the stub server's Jenkins route receives at least one request per PR beat on the in-process run, and the fixture PRs' `checks` words in the store equal the shell run's. Keep the `≤` bound against the shell baseline beside it.
4. Name the census fixture's credential source under Open Question 1, have the stub Jenkins route refuse a request missing either header, and serve a token endpoint so one census pass exercises a refresh (or state that the refresh is proved by the client row only).
5. Widen P12's predicate to the Changelog's claim: no `jen`, and no `plot-host.sh` whose argv names `pr-list`, `runs`, `run-for-sha`, `runs-for-sha` or `pr-state` in an idle pass; and state whether S4 on the Jenkins fixture is asserted zero or only recorded, with the reason.
6. In the Cutover slice, name the inversion of `bitbucket-jenkins.census.test.ts:52-56` (rich read through the shell) alongside the start line at `:64-67`, or fold that file into the P12 fixture.
7. State the census time cost of the new fixture against the 20-minute step cap (`ci.yml:887-892`), and say how a red S5/S6/S8 tolerance row on a slice PR is treated (rerun of the same commit, as on 2026-11-16), since none of the three slices changes the GitHub fixtures those rows measure.

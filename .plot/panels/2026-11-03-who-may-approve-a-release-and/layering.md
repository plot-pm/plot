# Layering juror — who-may-approve-a-release-and

Position: amend

The plan names real defects, and every line reference holds on `origin/main` at `f017f976e` (no change under `packages/` since `a518552f1`). The plan leaves its three layering questions open, and that is correct for a Draft. But four facts that decide those questions are absent from the plan, and one proposed shape ("a domain rule over the `Refs` port") conflicts with the domain's stated shape. A Sonnet agent cannot build any slice from the plan as written. Each slice needs the amendments below first.

## Findings

### 1. Where a caller identity is established today

- The domain never reads identity. `Caller` is a reading (`packages/domain/src/workflows/decision.ts:11-23`, "never read from `process.env` inside a workflow"). `releaseApprove` checks it first (`release-approve.ts:73`), and `releaseFinish` refuses `unattended` and `fleetd` (`release-finish.ts:115`). This part of the layering is sound, and the plan must keep it.
- Every entry and controller builds `Caller` from the env of its OWN process, with one repeated expression: `process.env.PLOT_UNATTENDED === '1' ? 'unattended' : 'person'`. On `origin/main` it appears at `packages/board/src/server/entry/main.ts:156` (`plot-ask.mjs merge` / `release-approve`), `main.ts:260` (`repair-pr`), `entry/deliver.ts:791`, `server/restart.ts:70`, `packages/fleet/src/server/entry/continue-command.ts:103`, `restart-command.ts:91`, `restart-stopped-command.ts:105`. `entry/release-gate.ts:191` reads it from `--unattended` instead. That is eight sites and two spellings. A new caller value that is added at one site leaves the other seven answering `person`. The plan names three sites (`deliver.ts:791`, `restart.ts:70`, `release.ts:211`) and does not name this set.
- One HTTP controller already passes every request as a person: `packages/board/src/server/continue.ts:184` hardcodes `caller: 'person'` with the comment "A browser hitting this same-origin route is always a person". A `curl -X POST /api/continue` from an agent passes as a person today. This is the exact failure the plan's first open question predicts for release and restart, and it is already live on a third route. The plan does not cite it.
- An env reading cannot fix the release-approve defect. `PLOT_UNATTENDED` describes the process that started the entry, not the requester. That is why a board an unattended process started refuses a person's click (#2918 LOW). Claude Code sets `CLAUDECODE=1` in an agent's shell (observed in this juror's own shell). Nothing in `packages/*/src` or `skills/plot/scripts/*.sh` reads it (git grep: 0 hits). But a board that an agent's Bash call started inherits it, so a "`CLAUDECODE=1` means agent" reading is the mirror image of the #2918 LOW: every person click on that board would read as an agent. An env reading is a valid reading only for the process that runs the action directly (`plot-ask.mjs` run from a shell), never for a long-lived server.
- The one layer that observes "an agent issued this command" is the PreToolUse hook. It fires for an agent's tool call and does not fire for a person at a terminal. The controller gate is that hook (`skills/plot/scripts/plot-controller-gate.sh` launches `controllerGateOf`, `packages/board/src/server/entry/gate.ts:942-993`). Today it does not gate `release-approve` at all: `controllerInvocation` returns `GatedAction = 'dispatch' | 'approve' | 'deliver' | 'release' | 'restart'` (`packages/domain/src/rules/ci-suite.ts:216`, `:256`), and `release-approve` is absent, although `ControllerAction` lists it (`controller-gate.ts:12`) and `controllerRefusal` has text for it (`controller-gate.ts:353-355`). Also, `if (linked) return null` (`gate.ts:982`) allows every named action from any linked worktree, which includes an idea worktree a master agent works in, not only a fleet desk.

Consequence: "refuse a master agent at release-approve" is a gate, not a domain refusal. The domain cannot see the requester, and the entry sees only its own env. The plan's slice text says the workflow "carries a caller that tells a person from a master agent", which puts the decision in a reading no layer below the hook can produce. The board half (a click) needs a second, different mechanism (a per-board token the served page holds, checked in the controller, mapped to `Caller` before the domain call). These are two mechanisms at two layers, and the plan presents them as one slice.

### 2. Where the release-finish scope rule lives

- The scope list is computed outside the domain. `scopeSlugs` in `packages/board/src/server/entry/release-finish.ts:38-50` parses the sprint's Must/Should/Could items in the board entry, and its comment states it is a copy kept out of `sprint-transition.ts` for a bundling reason. The domain receives `scope: ScopePlan[]` already filtered (`release-finish.ts:205-225`). Extending scope in that entry adds domain behaviour outside the domain, which the layering rule forbids ("No domain-specific code or behaviour lives outside the domain").
- The domain already owns the split this slice needs. `groupChangesets` (`packages/domain/src/rules/release-prepare.ts:128-136`) splits changesets into `scope` and `outside` by their `plan:` line, and fleet reads `ReleaseChangeset { file, plan }` over the `Refs` port with `listBlobs`/`readBlobs` and `planOfChangeset` (`packages/fleet/src/shared/release-world.ts:74-84`). The plan does not name either. Without them, a builder writes a third changeset-to-plan parser in the board entry.
- The reading source is not named, and the obvious one is wrong. After the release PR merges, its own `changeset version` commit has deleted the consumed `.changeset/*.md` files, so `origin/<default>` after the merge holds none of them. The changesets that shipped under the tag are the `.changeset/*.md` paths the release merge removed, read from the merge's first-parent side (`Refs.commitFiles`, `-m --first-parent`, per CLAUDE.md's "what did MAIN gain" reading) with their text from the merge's first parent. A builder needs this decision written down.

### 3. Whether one role-file loader over the `Refs` port fits the layering rule

- "A domain rule over the `Refs` port" contradicts the domain's shape note in CLAUDE.md: "No rule or workflow imports a port or awaits anything." The precedent that exists is the `*At` workflow (`releaseApproveAt`, `mergeAt`), which composes ports asynchronously beside a pure rule. The loader fits that shape: a pure part (`roleAgentsJson`, `roleCommand` in `packages/domain/src/rules/role-command.ts`, already pure) and an I/O part that reads `origin/<default>:.claude/agents/<role>.md` and `.claude/settings/<role>.json` through `Refs.showFile` (`ports/refs.ts:503`). The I/O part also WRITES `agents.json` and `settings.json` under `.plot/state/<role>/` (`repair-role.ts:117-121`). The purity gate forbids `node:fs` in the domain outside `adapters/`, so the write cannot move into a domain rule. It belongs in `packages/fleet/src/shared/` (board depends on `@plot-pm/fleet`, so `entry/review.ts` can import it) or behind a port.
- The plan says "no code loads `.claude/agents/reviewer.md`". That is true, but the reviewer already loads a role definition from a different file: `.plot/charters/reviewer.json` (tracked; `CHARTER_DIRECTORY = '.plot/charters'`, `entities/charter.ts:14`), read from the MAIN CHECKOUT's working tree (`entry/review.ts:586-589`) and refused unless declared (`review.ts:333-336`). It carries `model: opus` and `effort: high`, which `reviewer.md` also declares. So the reviewer has a third load from a third source, and the plan does not mention it. Moving to `reviewer.md` without deciding the charter's fate leaves two definitions that can disagree.
- The reviewer does not start through `roleCommand`. `reviewerCommand` (`rules/review-verdict.ts:157-188`) builds a hardened read-only command (`--tools` allowlist, `--disallowedTools`, `--permission-mode dontAsk`, `--strict-mcp-config`, never `bypassPermissions`). `roleCommand` (`role-command.ts:62-83`) builds `--agent <role> --agents <json> --settings <file>` and relies on the settings file for permissions. `origin/main:.claude/settings/` holds `fixer.json`, `main-repair.json` and `unblocker.json`, and no `reviewer.json`. "Through one role-file loader" therefore either needs a new reviewer settings file or a loader that returns the definition text and leaves the command to `reviewerCommand`. That choice changes the reviewer's permission boundary, and the plan does not state it.
- The two existing loaders differ in more than the source. The fixer passes `.claude/settings/fixer.json` as a path INTO the main checkout (`auto-fixer.ts:460`), so its settings come from whatever branch that checkout holds; main-repair copies both files from `origin/<default>`. The fixer takes `maxTurnsOf(text)` (`auto-fixer.ts:461`); main-repair hardcodes `MAIN_REPAIR_MAX_TURNS = 80` (`repair-role.ts:18`). A shared loader settles both, and the plan must say which answer wins.
- `unblocker.md` and `unblocker.json` are on main and no code starts them; #3067's unblocker becomes the fourth caller. The loader slice and #3067 should agree on order, which the plan's last open question already raises.

## Amendments required

(a) A gate slice: `controllerInvocation` recognises `plot-ask.mjs release-approve`, and the controller gate refuses it from any agent tool call with no receipt escape and no `linked`-worktree exemption. Name the refusal. (b) A board slice: a per-board token the served page holds, checked in the HTTP controller for `POST /api/release`, `POST /api/restart` and `POST /api/continue` (add `continue.ts:184` to scope), mapped to `Caller` before the domain call. A request without the token is not `person`.
2. Name the eight caller-construction sites above and replace the repeated expression with one helper outside the domain (for example `callerOfProcess()` beside the entries), so a new value reaches every site. State that `CLAUDECODE` is read only by a direct-run entry and never by the board or fleetd.
3. Keep `Caller` a reading. If a new value (`agent`) is added, `releaseApprove` and `releaseFinish` refuse it by name, and each workflow that takes `Caller` states its answer for it; list those workflows (`merge`, `continue`, `restart`, `release`, `repair-pr`, `release-approve`, `release-finish`, `dispatch-verbs`).
4. Release finish: put the outside-sprint rule in `releaseFinish` as a new reading (`shipped: readonly ReleaseChangeset[] | 'unaskable'`), reuse `groupChangesets` and `planOfChangeset`, and name the reading source: the `.changeset/*.md` paths the release merge removed, read through `Refs` at the merge's first parent. `'unaskable'` names a refusal and books nothing extra. Do not extend `scopeSlugs` in the board entry.
5. Reviewer: state that the loader is an `*At`-style composition (or a fleet-shared helper) returning the definition and settings texts, with the pure translation staying in `rules/role-command.ts` and the file writes outside the domain. Name the fate of `.plot/charters/reviewer.json`, whether the reviewer keeps `reviewerCommand`'s flags, and the turn-limit source for every role.

## Decisions that need a person

- Which file is the reviewer's authority: `.plot/charters/reviewer.json` or `.claude/agents/reviewer.md`. Retiring the charter changes the `charter` entity's only reviewer caller.
- Whether the reviewer keeps `reviewerCommand`'s hardened flags or moves to `roleCommand` with a new `.claude/settings/reviewer.json`. This is a permission boundary.
- Whether a release-approve refusal for an agent has any receipt escape. The current `--unowned-action` escape exists for every other gated action, and an escape here returns the defect.
- Whether a board token is in scope for this plan or a separate one, since `continue` has the same defect.

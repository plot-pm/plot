## Findings

1. **Slice 3's limit reading can produce a permanent `exhausted` with no test, and its limit rule differs from slice 2's.** The shell computes `limit = min(ceiling, declared)` and `reset = now + wait_seconds` only where `wait_seconds > 0` (plan:75). With `Host rate limit: 500`, `bb`'s ceiling 800 and 600 counted requests, the line reads `limit 500, remaining 0, reset null`: `bb` is below its own ceiling, so `wait_seconds` is 0. `rateLimitOf` reads `remaining === 0 && resetAt === null` as `exhausted` (`packages/board/src/app/lib/agent-rows/delivery-readings.ts:97-99`), and `exhausted` stops a loop agent (`:80`). Nothing would end that reading except the next read. Slice 2's client takes a different ceiling: `BB_HOURLY_LIMIT`, else the declared limit (plan:66). With the default environment and `Host rate limit: 10000`, the client therefore reads 10000 while the shell reads 800, both over one ledger. Two implementations of one reading, with no corpus test holding them together, is the undeclared duplicate that *A Shell Script Asks The Domain* forbids. (Read in the plan; opened `delivery-readings.ts` and `machine-health.ts:129-183`.) **Change:** take the limit and remaining arithmetic out of the shell. Put it in one domain rule, for example `bbLimitReading({requests, ceiling, wait_seconds}, declared, now)` in `rules/bb-ledger.ts`. Have the client's `spend` and the shell's `limit` arm both ask that rule (the shell through a bundle, which is allowed for a once-per-command op), or declare the pair in the corpus. State that `remaining 0` always carries a reset: the next free second by the declared limit, or the start of the next hour. Add unit cases for `requests: null`, `ceiling: null`, declared < ceiling, and declared > ceiling.

2. **The corpus leaves out the one value that makes the two ledgers meet: the account key.** The recorder lifts `bb_hour_stamps`, `bb_budget_count`, `bb_pause_read`, `bb_pause_is_stale` and `bb_pause_after_429` (plan:70). It does not lift `bb_account_key` (`cli/bb:335`), `bb_state_path` (`:295`), `bb_hourly_limit` (`:355`), `bb_pause_write`'s merge (`:488`) or `bb_budget_prune` (`:399`). The plan puts the key in the adapter, built with `node:crypto` (plan:68). `bb` lowercases with `tr '[:upper:]' '[:lower:]'`, which depends on the locale and leaves non-ASCII characters alone, while `String.prototype.toLowerCase` folds Unicode. A key that differs fails open in silence (plan:65), and every test still passes. (Ran: fetched `cli/bb` at `2c904ab17` and read `:240-660`.) **Change:** name a pure `bbAccountKeyInput(email)` (the lowercase step) and the state-path choice as rules. Add `bb_account_key`, `bb_state_path`, `bb_hourly_limit` and `bb_pause_write` to the lifted set, with cases for mixed case, a non-ASCII email, an empty `BB_STATE_DIR` and `XDG_STATE_HOME`, `BB_HOURLY_LIMIT` values `0`/`010`/10 digits/`abc`, and a merge against a longer stored pause. State what the client does with an invalid `BB_HOURLY_LIMIT`, where `bb` exits 1 (`cli/bb:360-363`). The plan says *"with `bb`'s rule"* and does not say this.

3. **Tests that pin today's behaviour and break in slices 1 and 3 go unnamed.** Slice 1 names only `bitbucket-api.test.ts:272` and `:286` (plan:56). The 10000 default is also pinned at `packages/domain/test/declared-host-limit.test.ts:10-16`, `packages/domain/test/host-reads.test.ts:161,179`, `packages/domain/test/bitbucket-api.test.ts:350` and `test/reconcile/host.test.mjs:7389`. Slice 3 inverts `host.test.mjs:7390-7391`: *"remaining null"* and *"bb has nothing to answer — do not ask it"*, asserted as `argvOf(stubs.bbArgv) === null`. The probe removal deletes `test/reconcile/bb-capability-probe.test.mjs` (4 tests) and `host.test.mjs:6169`, `:6183`, `:6229` and `:6257`. The "request-budget test" is `host.test.mjs:8034-8058` (`CAPABILITY_CHECK_OVERHEAD = 2`), and the plan does not name the file. (Ran grep; opened each line.) **Change:** list these per slice, so a reviewer can tell an intended deletion from dropped coverage. Add `expect(shellValues).toContain('800')` to the corpus's "not vacuous" check (`declared-host-limit.corpus.test.ts:63-66`), which today proves only the declared cases.

4. **The plan's "counts zero" and "sends nothing" claims fail if the new `bb` calls go through the `bb()` wrapper.** Inside `plot-host.sh`, a bare `bb` is the function at `:3957`, and that function records a budget row for every exit (`budget_record_call bitbucket bitbucket`, `:3962`). The probe's `bb --version` (`:2803`) is counted for that reason. Slice 3 adds two calls: one cached `bb --version` (plan:76) and `bb rate-limit --json` (plan:75). Both send no HTTP request, and both would write a row to `budget.tsv` unless they call `command bb`. The overhead in `host.test.mjs:8055` would then read 1, not 0, and every `limit` read would spend one request in Plot's ledger. (Opened `plot-host.sh:2743,2803,3957-3963`.) **Change:** require `command bb` for both calls. Add one assertion: the `limit` op and a `pr-list` record zero bitbucket rows beyond their API calls.

5. **The exit-75 mapping has no stated mechanism, so its test has no defined subject.** `die3` (`plot-host.sh:704`) receives only a message, and the plan notes that the code is lost in command substitution (plan:74). A mapping placed in `die3` must therefore key on words. `die3` serves every backend, so a word match changes GitHub, Jira and Jenkins exits too. `bb`'s real exit-75 lines are `error: rate limited — …` (`cli/bb:629`, `:645`) and the 429 tail (`:196-200`), which avoids the digits 429 on purpose (`:287-290`). A stub that exits 75 with other words proves nothing about real `bb`. (Opened `plot-host.sh:704,799-811`; ran a grep over `cli/bb` for exit 75.) **Change:** state the mechanism, by code or by words and on which backend. Record `bb`'s exit-75 stderr lines (pause, ceiling, 429, paginated 429 at `:719-724`) into the corpus fixtures, and have the stub print them. Add one test that a GitHub op whose stderr says "rate limit" keeps its current exit.

6. **Nothing holds slice 3's stub `bb rate-limit --json` to the real output, and slice 2's recorder cannot run on this machine.** The plan measured `bb 1.13.0` here (plan:54). The `jen` precedent refuses a wrong version (`record-jenkins-reads.mjs:39-41`), so slice 2's builder needs `bb` 1.15.0 installed, and the plan does not say so. `bb_now` honours `BB_NOW` only while `BB_API_URL` is set (`cli/bb:246-251`), so the recorder must set a loopback `BB_API_URL` or define `bb_now` itself. `jen-outputs.json` holds the census stub to real `jen` output (`record-jenkins-reads.mjs:17-19`), but the plan has no equivalent for `rate-limit --json`. **Change:** make "`bb` 1.15.0 on PATH" a stated precondition of slice 2. Have the recorder also write `rate-limit --json` outputs (idle, at ceiling, paused, count unknown, ceiling off) to `fixtures/bb-ledger/`, and require slice 3's stub to serve those files.

7. **The default seam can write into the operator's real `bb` state from tests.** The ledger adapter is a seam "with a production default" (plan:68). The census sandbox sets `HOME` but does not strip `BB_STATE_DIR`, `XDG_STATE_HOME` or `BB_HOURLY_LIMIT` (`packages/fleet/test/census/sandbox.ts:266,296-300`). `test/fixtures/bitbucket-replay.ts:117-122` and `census/sandbox.unit.test.ts:176,195` build the client with no ledger. The domain vitest suite in `CI suites` runs outside `scripts/owned-run.sh`, so no leak check runs. A test that answers 429 writes a real pause file, and if that test's email matched a real account, the pause would block that person's real `bb`. **Change:** state that the adapter reads the state path from `options.env` and never from `process.env`. Require every existing `bitbucketApi(...)` test construction to pass a temp ledger or `BB_STATE_DIR`. Add the three variables to the census sandbox's strip list.

8. **The rendered state changes for Bitbucket and no test is named for it.** Today a Bitbucket reading has `remaining: null`, so `rateLimitOf` answers `unknown`. After slice 2 or 3 it answers `free` or `exhausted`, and `machine-health.ts:155` prints `N / M left`. Both are domain or `agent-rows` properties, which is right, but the plan names no unit case for a `predicted` Bitbucket bucket with a number. **Change:** add `delivery-readings.test.ts` and `machine-health` cases for a predicted Bitbucket bucket: free, at 0 with a reset, and no Delivery-tab change for GitHub.

9. **The concurrency and fail-open claims need tests named, not only argued.** The plan argues that `O_APPEND` writes under `PIPE_BUF` never interleave (plan:64). `test/reconcile/budget.test.mjs:342-373` is the six-writer precedent for Plot's own ledger. The plan names no parallel-writer test for `bb-ledger-file.ts`, and no byte-exact test of the line formats (`<epoch>\n`, `<end> <len>\n`) that `bb`'s readers accept. It also names no test that each fail-open path sends exactly one request and logs one warning per process. **Change:** name these three tests in slice 2. Add one interop check at record time: a file written by the TS adapter, read by the lifted `bb_budget_count` and `bb_pause_read`.

Slices verified alone, with no `bb` in CI: slice 1 yes. Slice 2 yes once the fixtures are committed, with the precondition in finding 6. Slice 3 yes with stub `bb`, but its stub output is held to nothing (finding 6).

## Findings

1. **The fleet-scan sentence cannot read `bbThrottleCause`, because the scan summary carries no refusal text.** Plan:105 says the fleet-scan sentence (`host-notes.ts:499`) reads `bbThrottleCause(said)`. `scanHostNote` (`packages/board/src/app/lib/agent-rows/host-notes.ts:489-499`) reads only `fleet.summary.host` and `prNextInSeconds`. `summary.host` is the enum `ok | throttled | secondary | failed | unknown` (`packages/domain/src/entities/fleet.ts:855`), and the scan produces it, so no `said` string reaches the board. The quota sentence works differently: `prStatus` receives `fleet.prError`, the message text (`host-notes.ts:315-322`), so the cause can be derived there. For the scan sentence the plan needs a new field on the scan summary, with its producer, its `plot-state:` declaration (`scripts/check-state-declarations.sh`) and a guard for an older pulse. Without that field, the builder has two options: a sentence that cannot tell the three causes apart, or a field invented mid-slice with no test named. (Opened `host-notes.ts:299-362,470-504` and `fleet.ts:835-870`; grepped for the schema.) **Change:** in slice 3, name the field, for example `summary.hostCause: 'ceiling' | 'paused' | 'host'` with `.catch` and a default of `host`. Say which component writes it: `fleet-scan.ts` for the in-process read, or the scan shell from `bb`'s stderr. Name a schema test that an older pulse with no field reads `host`. Put the quota sentence's cause on the domain's `prStatus` result (`packages/domain/src/rules/pr-status.ts:195`), tested in `pr-status.test.ts`, and not in a call inside `host-notes.ts`. Name the test files for the two sentences: today `scanHostNote` and `prStatusEntry` are tested in `packages/board/test/unit/agent-list.test.ts` and `pr-footer-sign-in.test.ts`.

2. **The exit-code file can turn a later, non-`bb` failure into exit 5, and no test covers that case.** Plan:120 says `die3` exits 5 where the per-run file reads 75. An op that survives a refused `bb` call can still fail later for another reason: a fallback, or a `jq` or argument error after the call. That later `die3` then reads a stale 75. A Jira op that the same script runs in a Bitbucket repository fails the same way. The only negative test the plan names is a GitHub op, where `bb()` never runs. (Read the plan; opened `plot-host.sh:685` and `:3846-3853` at `21ae2c638`.) **Change:** state that each `bb()` call overwrites the file and that a `die3` reached after a successful `bb` call keeps exit 3. Add one test: a stub `bb` exits 75 on the first call and 0 on the second, then the op fails for a non-`bb` reason, and the exit is 3. Also state that the file comes from `plot_tmpfile` and is removed through `plot_on_exit`. `scripts/check-temp-paths.sh` refuses a `mktemp` call or a second `trap … EXIT` in a shipped script, and *"removed on exit"* (plan:120) names neither helper.

A `Date.now()` inside the mapper makes the shell-side unit cases depend on the wall clock. `tracker-shell.ts:188` exports its own `limitOf` over the same `plot-host.sh limit` lines (`:416`), and the plan does not name it. (Opened both files at `21ae2c638`; grepped the `limit` callers.) **Change:** give the shell line an `at` epoch second, printed by `plot-host.sh`, or give `hostShell` a clock seam. Say which ceiling the shell passes: `bbCeiling` applied to the JSON's `ceiling` and the declared key. Add a `host-shell.test.ts` case per recorded `rate-limit --json` fixture. State that `tracker-shell.ts`'s `limitOf` either keeps filtering the Bitbucket line out (`:422`) or calls the same rule.

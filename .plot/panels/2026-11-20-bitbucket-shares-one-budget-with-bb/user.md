## Findings

1. **A raised `Host rate limit` with the recommended ceiling locks the operator's own `bb` out.** Under the Open Question's recommendation, an operator who sets `Host rate limit: 10000` and leaves `BB_HOURLY_LIMIT` unset gets a fleetd ceiling of 10000 and a `bb` ceiling of 800 over ONE ledger. fleetd then appends up to 10000 lines to the file that `bb` counts, so once fleetd passes 800 in an hour, every `bb` command of that account on the machine exits 75: the person's own `bb pr list`, and every `plot-host.sh` op (which slice 3 then reports as throttled). Today the same operator's `bb` 1.15 counts only its own requests and keeps working. The plan names the 10000-versus-800 split in Open Questions but not this consequence. Evidence: plan, *Open Questions* first item (READ); `bb_hourly_limit` reads only `BB_HOURLY_LIMIT`, else 800 (`cli/bb` at `2c904ab17`, lines 355-367, OPENED); `bb_request_guard` counts all lines of the account's file regardless of writer (PR #133 body, *Design notes*, READ). **Change:** resolve the Open Question in the plan text as "the in-process client applies the smaller of the declared host limit and `BB_HOURLY_LIMIT` (800 where unset)", or else require that a `Host rate limit` above 800 is honoured only where `BB_HOURLY_LIMIT` is also set, and say in the `Host rate limit` doc (`plot-config.sh:233-238`) that an access-token operator raises both.

2. **A refusal from the local ledger shows on the board as "the host's rate limit is spent", and names neither `bb`'s ledger, nor the pause, nor who caused it.** The board's quota sentence is fixed text plus a reset phrase: `PR data paused: the host's rate limit is spent, service returns in ~X` (`packages/board/src/app/lib/agent-rows/host-notes.ts:355-361`, OPENED), and the fleet-scan sentence says "the git host's rate limit was spent" (`host-notes.ts:497-503`, OPENED). Neither shows the refusal's `said`. After slice 2, a `throttled` answer can mean three different things: Bitbucket answered 429, `bb`'s 800-per-hour ceiling on this machine refused before sending, or a pause that another `bb` process (possibly the person's own loop) wrote. The plan says the refusal "keeps `throttledOf`'s kind and words" (`connector-https.ts:126`) but a request that was never sent has no host words, and the plan specifies no `said` text for it. The operator therefore cannot tell from the board whether to wait for Bitbucket, stop their own `bb` loop, or clear a pause, and the board claims the host refused when nothing left the machine. **Change:** in slice 2, state the refusal's `said` for each guard verdict, in `bb`'s own words (`rate limited — <n> requests in the last hour from this machine; next request at <HH:MM:SSZ> (in <s> s)` and `paused until <HH:MM:SSZ> after a rate limit`), and add to slice 2 or 3 a domain/`agent-rows` property that distinguishes `ceiling`/`paused`/`host-429` with a unit test per wording, plus the sentence change in `host-notes.ts`. Without this, the plan's Board impact note ("the board reads `LimitReading` unchanged") is true and is the problem.

3. **The craftamap probe goes with nothing in its place, so a machine with craftamap `bb` first on `PATH` reads every Bitbucket PR list as "no PRs".** The probe's own comment records the failure it prevents: craftamap rejects `--json`, the error is swallowed, `jq` exits 0 on empty input, "so every Bitbucket PR list reads as *no PRs*", and craftamap 0.6.0 segfaults on a 429 (`skills/plot/scripts/plot-host.sh:2772-2779`, OPENED). Today that machine gets exit 3 naming which `bb` answered (`plot-host.sh:2915`, OPENED). The probe costs no Bitbucket request (`bb pr list --help --json`), so removing it saves no budget. "Plot supports only Quatico `bb`" is a fine decision; silently empty listings are not. **Change:** slice 3 keeps one identity check on the cached `bb --version` it already reads for `bb_list_page_length`: an answer that does not carry Quatico's banner (`bb 1.13.0 (quatico-bb — brew install quatico-solutions/tap/quatico-bb)` on this machine, RAN `bb --version`) exits 3 with the install command, and a test drives it with a stub craftamap `bb`.

4. **The `Host rate limit` override cannot apply to a workspace or repository access token through either client, so the Changelog's first bullet promises a path that does not exist.** fleetd's client sends only `Basic email:token` (`packages/domain/src/adapters/host/bitbucket-api.ts:224`, OPENED; `CREDENTIAL_FIX` asks for "an Atlassian API token"), and `bb` 1.15 sends only `-u "${email}:${token}"` (`cli/bb:664`, `:712`, `:782`, OPENED); neither has a Bearer path, which Bitbucket's access tokens use for the REST API as far as I know. The override still works as a number for anyone who sets it. **Change:** reword the Changelog bullet and the `plot-config.sh` doc to say the key overrides the prediction, and that neither `bb` nor fleetd sends an access token today, or name the follow-up that adds one.

5. **With `bb` 1.13.0 (this machine) the "one budget" holds on one side only, and the plan's Changelog does not say so.** Slice 2 writes fleetd's lines into `$HOME/.local/state/bb` whatever `bb` is installed, and honours a pause file that 1.13.0 never writes; 1.13.0 itself counts nothing and refuses nothing. So on an older `bb`, fleetd's own pacing improves (800 instead of 10000) but the `bb` calls of `plot-host.sh` and of people stay outside the count. Nothing that works today stops working on 1.13.0: slice 3's fallback keeps today's `limit` line for `unknown command: rate-limit` exit 1 (plan, *Slice 3*, READ; RAN `bb --version` → 1.13.0). **Change:** one sentence in the Changelog or Notes: "with a `bb` older than 1.15.0, only fleetd's requests are counted; upgrade with `brew upgrade quatico-bb`."

6. **"Logs the key so a person can compare it with `bb rate-limit`" cannot be done: `bb rate-limit` prints no key.** Its text output is the count, the ceiling, the pause end and the next request; its JSON is `{requests, ceiling, paused_until, wait_seconds}` (`cli/bb:3313-3331`, OPENED). **Change:** log the key together with the file path written (`<state dir>/requests-<key>-<YYYYMMDDHH>.log`) and say to compare it with `ls` of that directory, or log fleetd's own count so it can be compared with `bb rate-limit`'s `requests`.

7. **The `limit` op's `bb rate-limit --json` call should not go through the `bb()` wrapper.** The wrapper takes a host slot and writes a `budget.tsv` row for every call (`plot-host.sh:3957-3963`, OPENED), so a call that sends nothing would show as spend on the board. **Change:** slice 3 says it calls `command bb rate-limit --json`, and a test asserts the `limit` op adds no `budget.tsv` row.

8. **Lockout protection is bounded by the 200-request margin and the website, which the plan states correctly.** 800 plus parallel overshoot plus a person browsing bitbucket.org must stay under 1,000; heavy browsing can still trigger a 429, after which the shared pause (300 s doubling to 3,600 s) is the reaction. The plan's Notes say this (*What the ledger does not cover*, READ). No change; recorded so the operator's expectation is explicit.

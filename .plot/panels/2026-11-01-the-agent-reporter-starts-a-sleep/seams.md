# Seams juror: the-agent-reporter-starts-a-sleep

Position: amend

The plan names the right loop, and its facts about `continuation.ts` are true on `origin/main` (`c023c7c60`). The reporter at `continuation.ts:1398` is the only short-interval poll loop that TypeScript builds into a shell string, and no open PR or in-flight slice touches it. One claim is false: the reporter is not the only per-agent poll whose cost grows with the number of agents and their run time. The AgentMonitor's `plot_monitor_wait` (`plot-monitor-subject.sh:193-203`, called at `plot-agent-monitor.sh:565`) starts 3 processes per second per agent for the agent's whole life, for dispatched AND continued agents, and a continued agent runs both loops. The plan must either take that loop as a second slice or name it out of scope with a filed issue. The other six short polls in shipped shell are bounded, operator-run, or one-shot, and stay out.

## Findings

1. **medium — the "only loop that grows" claim is false; the AgentMonitor wait is a sibling of the same mechanism.** `skills/plot/scripts/plot-monitor-subject.sh:193-203` naps `sleep 1` and then calls `$(plot_monitor_subject "$pid_file")`, which runs `pid=$(cat "$pid_file" | tr -d ' \n')` (`plot-monitor-subject.sh`, `plot_monitor_subject`) and `kill -0`. `skills/plot/scripts/plot-agent-monitor.sh:565` runs `while plot_monitor_wait "$interval" "$pid_file"` for the agent's life. Measured in my scratch dir with PATH shims for `sleep`, `cat`, `tr` and `dirname` against a live pid for 5 s: 5 `sleep`, 5 `cat`, 5 `tr` — 3 process starts per second, independent of load because the nap is fixed. Every dispatched agent gets an AgentMonitor (`plot-dispatch.sh` `start_worker`, the `PLOT_AGENT_MONITOR` start), and every continued or restarted agent gets one through `startMonitors` (`continuation.ts:790-805`, `desk-monitors-shell.ts:9`). The plan's Motivation says "This loop is the one whose cost grows with the number of continued agents and with their run time"; the AgentMonitor wait grows with ALL agents and their run time.
2. **medium — the realised reporter rate depends on load, and the plan does not reconcile 20/s with its own measurement.** The plan states 20 starts per second and 576,000 per 28800 s (arithmetic correct), and in the next bullet measures 49 starts in 10 s (about 5/s) on pid 24682. My shim run reproduced the same effect: 8 `sleep` starts in 5 s, not 100, because each start cost about 600 ms on this machine today. So under `syspolicyd` load the reporter's real rate falls toward the AgentMonitor's 3/s, and with 6 agents the AgentMonitors alone start 18 processes per second. The 20/s figure is a ceiling at low load; the plan must say so, because it decides which loop dominates.
3. **low — the normal dispatch path has no poll, and the plan does not say so.** `plot-dispatch.sh` `start_worker` (line 1035, the `sh -c` near line 1542) backgrounds the agent and then runs `wait "$agent"` in the wrapper, which is the agent's parent. It starts no process per poll. `plot-dispatch.sh --restart` reaches `continueOnDesk` (`test/e2e/monitors-attached.test.mjs:34-35`, `bug/a-stopped-slice-has-a-restart-controller`), so the restart route does run the reporter. The plan should state this split, because it is why the fix lives in `continuation.ts` only and why the `wait` shape cannot be copied from `start_worker` (the ppid-1 test at `packages/board/test/unit/continue-route.test.ts`, named at `continuation.ts:1272`).

## Open questions

- **EOF on `SIGKILL` with a held descriptor:** Yes on macOS and Linux, provided only the outer agent subshell holds the write end. The inner `( ${cmd} )` and every descendant inherit it, so close it there (`( exec 3>&-; ${cmd} )`), and the `sh -c` wrapper must close its own copy after it forks the agent. That matches today's `kill -0` meaning: the reporter reacts to the agent subshell's death, not to `cmd`'s orphans. Prove it with a probe that `SIGKILL`s the recorded pid while `cmd` still runs, in the fleet vitest file that runs on CI's Linux and on the operator's macOS.
- **Builtin wait for the bounded poll:** None is portable. bash 3.2 as `/bin/sh` has `read -t`; dash has neither `read -t` nor a builtin `sleep`. A 1 s poll on Linux therefore still starts `sleep` once per second, which fails requirement 1 as written and reproduces the AgentMonitor's cost shape. Recommendation: the held descriptor, with no poll.
- **How the test counts:** PATH shims for every external the reporter can name (A5), and a growth assertion across two agent run times rather than an absolute or a duration. A process-table sample depends on load and misses short children, as the issue's own `ps` sample shows; do not use it as the gate.

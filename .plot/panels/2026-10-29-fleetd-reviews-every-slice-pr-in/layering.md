## (a) Problem statement

- The motivation is right: fleetd never calls `plot-review` (no caller under `packages/fleet/src`; the only `agentRunCommand` users are `review.ts:9`, `agent-run-for.ts:3` and tests).
- `review.ts:58-66` is the docstring, not the behaviour. The behaviour is `review.ts:483-493` (`findings !== 0` → `openFollowUp`) and `openFollowUp` at `review.ts:269-345`. The citation should name the code lines.
- The plan says the rule "reads the PR index row, the review record". **The PR index holds no review record.** `PrIndexRow.review` (`entities/pr-index.ts:39`) is GitHub's `reviewDecision` (`plot-host.sh:4788,4807`), not the `plot/review` status, and it is not bound to a head. The `plot/review` state per head is only reachable through `host.prReview` (`ports/host.ts:143-150,408`, `plot-host.sh:115-120,4407`) — a per-PR host call — or the local verdict files `<common>/plot/state/reviews/<pr>-<sha>.md` (`review.ts:413-416`), which are machine-local.
- **The index's `checks` colour already contains the review.** `plot/review` is a `StatusContext` in the GitHub rollup (measured: PRs #2880-#2895 all carry `StatusContext:SUCCESS`), and `CHECKS_OF` folds every rollup entry. Executed: `plot/review=FAILURE → checks=failing`, `PENDING → pending`, `SUCCESS → green`. So "CI green" read from the index is not CI alone: a HIGH review turns the row `failing` and lands the PR in the *CI red* arm of the design table, not in a HIGH arm. The plan does not name this.

## (b) Approach, against the lens

1. **Decision placement.** `slicePrNext` as a pure rule over readings is right, and it matches the auto-verify precedent (`rules/auto-verify.ts:92,162` `autoVerify`/`verifyStart`, wired from `fleet/src/shared/auto-writes.ts:63`). But the plan leaves its inputs undefined, and two of the three are not in the index:
   - *Review record:* not indexed (above). If the tick calls `host.prReview` per open slice PR per pass, the decision reads a freshly bought answer, which *A Decision Reads The Index* Part 1-2 forbids, and it costs one host call per PR per pulse. Starting a reviewer is not destructive, so an index reading is licensed — but the index must carry it. The cheap route: the GitHub rich arm already fetches `statusCheckRollup`, so `pr-refresh.ts` (the one writer) can store a `reviewState` bound to `checksSha` at zero extra calls. Bitbucket needs `pr-review` per open slice row, written by the same writer. This is a `PR_INDEX_VERSION` bump (now 5, `entities/pr-index.ts:11`) and belongs in slice 1 or its own first slice.
   - *CI green:* the rule must read CI **excluding** `plot/review`. On GitHub, `failing_checks` names contexts, so `failing_checks` minus `plot/review` works for `failing`; a `pending` produced by a `plot/review=pending` cannot be told apart without a stored review state. Simplest: store CI colour and review state as two fields at fold time.
   - On Bitbucket without `CI: jenkins`, `checks` is `unknown` (`plot-host.sh:4847-4851`), so the review arm never fires there. The plan should say so, because the story's test estate is a Bitbucket repository.
2. **The reviewer start is not an `agent-run` call.** The plan says the reviewer starts "through the existing `agent-run` port and `agentRunCommand`". `agentRun.run` (`review.ts:447`) is awaited for up to `REVIEW_BOUND_SECONDS = 3600` (`review.ts:100`), and it runs inside `reviewPr`, which also re-asks the host for the head (`review.ts:398-404`), builds the worktree, parses the verdict, writes the status and the comment. A tick that calls `agentRun` directly skips the status write, so the required `plot/review` check never appears. `reviewPr` lives in `packages/board/src/server/entry/review.ts`, and `@plot-pm/fleet` depends only on `@plot-pm/domain` (`packages/fleet/package.json`), so fleetd cannot import it. Two layering-correct options: (i) fleetd starts `plot-review.mjs <pr>` detached through an adapter, as `startBoardRun` does for verify (`board-run.ts:184`); or (ii) move `reviewPr` into `domain/workflows/review.ts` and keep the entry as a launcher. Either way the plan must name it.
3. **No in-flight mark.** A review runs up to an hour. Between start and status write, the head still has "no review", so every pulse answers *start reviewer* again. The rule needs an in-flight reading (a `running` map, as `auto-verify-in-flight.json` holds — `fleet/src/shared/auto-verify.ts:129-153`) and a headroom/concurrency input. Ten green PRs would otherwise start ten opus reviewers in one pass.
4. **The controller does not re-check.** The design's pattern is *the index chooses, the controller confirms* (merge re-asks). `reviewPr` re-asks the head (`review.ts:398`) but never asks whether `plot/review` already exists on it, so a stale index row buys a second full review. Add that check in `reviewPr` (one `prReview` call it already has a port for), and the index is safe as a selector.
5. **Slice 3 adds a decision outside the domain.** "Which severities open a ticket" is today an inline condition in a board entry (`review.ts:486`). The slice should move it into `rules/review-issue.ts` as a pure function of `ReviewCounts` and test it there, with the entry reading the answer. Otherwise the rule ships testable only through `review.test.ts`'s rig.
6. **Slice 3 loses findings on Bitbucket.** `host.prComment` answers `unaskable` on Bitbucket (`host-shell.ts:505-512`, `plot-host.sh:6061` exits 4). Removing the issue for MEDIUM/LOW leaves those findings only in the local verdict file on a Bitbucket estate. The plan must name the Bitbucket outcome (keep the tracker issue where the PR comment is unaskable, or accept the loss explicitly).
7. **Slice 3 versus the design's HIGH rule.** The plan removes the issue only for MEDIUM/LOW. A review with HIGH 1, MEDIUM 2 still opens an issue at review time (`review.ts:486`), but the design says a HIGH ticket exists only after fixer attempts fail. #2912 builds the late HIGH ticket and does not say it removes the early one. One of the two plans must remove the review-time issue for HIGH too, and the plan should say which.
8. **Shell ratchet.** No new shell is proposed. Good. But `skills/plot/scripts/plot-review-status.sh` already answers `needs_review` per sprint item from a sprint annotation `review_sha` and `git ls-remote`, a second review record that disagrees with the `plot/review` status. Under *A Shell Script Asks The Domain* this becomes an undeclared duplicate of `slicePrNext`'s review arm. The plan should either name it as a launcher target (shrink it to ask the rule) or as a declared duplicate with a corpus test.
9. **Scope reader.** A reading from git is right: the sprint file at the commit that set `State: Active` is re-derivable, so a state file written at sprint start would be a persisted derivation git can already reach (*Answers, never verdicts*). It must sit behind an adapter (`plan-store`/`refs`), with a pure `sprintScope(...)` rule over the texts.

## (c) Slices

- **Order is wrong for cost.** Slice 1 ("Rule") wires the tick with no scope, so between slice 1 and slice 2 fleetd reviews every green, unreviewed open PR in the repository, including plan PRs (`idea/*` — 10 open now, all `plot/review` absent). Put the scope slice first, or have slice 1 restrict to slice PRs of Approved plans and leave the sprint freeze to slice 2.
- **A missing slice:** the index carries the review state and a CI colour without `plot/review` (index version bump, `pr-refresh.ts` writer, decode tests). It is a precondition of slice 1 and touches a shared contract that #2914 and #2912 also read.
- Slice 3 is independent and could merge first.
- `slice-pr-next.ts` is created here and extended by #2912 and #2914. The plan should fix the input type (the readings record) in slice 1 so the siblings add arms without changing the signature.

## (d) Open questions

- **Freeze point.** Measured on `docs/sprints/2026-W44-follow-ups-2-29-1.md`: the sprint went `Active` at `f92415d23` with 2 plan items and ended with 11, added by three `sprint: scope change` commits by a person (`991ceb6bd`, `755ea7c91`, `1753e46e1`). A freeze at the `Active` commit would have kept 2 of 11. So the question is not "which file holds the freeze point" but "does a person's scope change re-freeze". Recommendation: the scope is the sprint file's plan items at HEAD, read from git; plans enter only through an explicit sprint edit, and nothing in fleetd writes the sprint file's items. That honours "an approved plan does not join" without a state file, and it needs no freeze record. If the freeze must be literal, read the file at the `State: Active` commit and treat each later `sprint: scope change` commit as a new freeze.
- **Comment shape.** The code already answers it: `findingsMarker(pr)` is per PR (`review.ts:358`) and `prComment` with a marker edits in place (`ports/host.ts:385-397`). One comment per PR, edited per head, with the head SHA and run marker in the body, reuses the existing writer.
- New questions the plan should carry: where the review state enters the index; what the in-flight mark is and what bounds concurrent reviewers; whether `reviewPr` refuses a head that already has `plot/review`; what Bitbucket does when `prComment` is unaskable; which plan removes the review-time issue for HIGH; what happens to `plot-review-status.sh`.

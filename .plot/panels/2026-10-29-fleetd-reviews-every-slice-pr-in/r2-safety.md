## (a) Fold of round 1's safety findings

The amendment folds all five safety findings as **design text**. Three of the five have gaps that make the text unbuildable as written, or let it fail open.

1. **Two concurrent reviews of one head.** Folded in the text: "`reviewPr` refuses before it removes any file when another run holds the same PR and head" (plan line 50). **Gap: the plan names no mechanism for "holds".** Today `review.ts:424-425` removes the files before `trees.add` at `:430`. The in-flight file belongs to fleetd only, and a person's `plot-review.mjs` never writes it. The `pending` mark is a host read, so two runs can each read "no pending" and then each write one. The local case needs an exclusive lock file (`O_EXCL`), keyed `<pr>-<sha>` under `plot/state/reviews/`, that is taken before the first `removeFile` and released in the `finally` at `:465`. The same lock with its pid is also the "live owner" that the leftover-worktree removal needs (line 50). The plan names no test. Round 1's probe was never made a regression test.
2. **Last-writer-wins on `plot/review`.** Partly folded: a `pending` mark with a run id, plus "an unattended run never replaces a `failure`". **Gap 1: the guard has no input.** D1 (plan line 57) says "this plan builds no caller identity", and `review.ts` reads no `PLOT_UNATTENDED` or caller (0 matches). So `reviewPr` cannot tell an unattended run from a person's run. **Gap 2: the run id cannot be read back.** `PrReviewReading` (`host.ts:143-150`) holds `sha`, `state` and `bypass`, with no description, no run id and no time. The rollup's `StatusContext` holds `context`, `state`, `startedAt` and `targetUrl` and no description (read with `gh pr view 2895`). **Gap 3: the converse order is still open.** Run B writes `success`, #2902 merges, and run A then writes `failure` on a merged head. After slice 1 no issue is opened, so A's HIGH lives only in an edited PR comment on a merged PR, and no reader acts on it. Before slice 1, that HIGH opened an issue. Slice 1 therefore adds this loss path. The fix that closes all three gaps: a run writes its final status only when its own run id is still the newest `pending` on the head. A superseded run writes nothing. Make the `failure` guard unconditional, so no `reviewPr` replaces a `failure` on the same head, and leave the person's override to #2903's accepted `success` or the existing `review-bypass:` comment. Then no caller identity is needed.
3. **An unattended run overwrites a `failure`.** Same as gap 1 in item 2. As written, the guard is not implementable without #2898's `feature/unattended-callers-are-refused`, and slice 4 carries no `waits:` on it.
4. **Endless re-review when no status is written.** Folded as "a start budget with backoff" and "the next step writes the status again". **Gap 1:** the plan does not say where the per-head start counts live. If they live in fleetd's memory, a fleetd restart resets them. **Gap 2:** "when a verdict file exists and only the status write failed, the next step writes the status again". No input in the rule's record (plan line 49) reads verdict files, and the step union `none | review | merge | hold | fixer | ticket` has no re-status step, so slice 4 cannot build this sentence. **Gap 3, new and executed: a written status does not reach the index, so the loop also runs when the status IS written.** See (b)1.
5. **`PR_INDEX_VERSION` bump during rollout.** Executed: `PrIndexSchema` takes `v` as a literal and the row is `.strict()` (`pr-index.ts:12,98,123`). A v6 file read by v5 code decodes to `null`, and so does a v5 file with one extra row field and no bump. Every reader in `pr-index-lookup.ts`, `deliver.ts`, `registry.ts`, `pr-reader.ts`, `fleet.ts` and `deliverability.ts` already treats `null` as "ask the host", so the rollout fails safe. The cost is one full read when fleetd restarts on the new bundle, and host fallbacks from desks whose shell bundles predate the bump. The reader lock keeps a v5 writer and a v6 writer from alternating, because a live fleetd heartbeat makes `plot-pr-reader.mjs` exit. **Gap:** the plan does not say what the review arm answers on a `null` store or on a row whose review field was never asked. It must answer `none`, because the index never says no. Bitbucket makes this concrete: a failed per-row `pr-review` must leave the field absent ("not asked"), never `absent` ("asked, none").

Dropped from round 1: the notification after N refused starts (round-1 amendment 5). #2899's idle rule (`Slice idle after`, default `2h`) probably covers it, because a budget-spent head takes no step. The plan does not say so, and it states it "does not depend on" #2899 (line 92). Also dropped: every proposed test. The amended plan has no test list.

## (b) Cited facts, and facts the plan is missing

All cited lines check out: `review.ts:57-68,100,269,358,395,424-425,430-431,486,506`, `pr-index.ts:12,41`, `plot-host.sh:702-707,6061`, `host-shell.ts:505-512`, `host.ts:122-130,376-397,408`, `sprint-transition.ts:162`, `sprint.ts:150`, `auto-verify.ts:162` (domain), `board-run.ts:184`, `auto-verify.ts:153` (fleet), and `review.test.ts:608`.

1. **The claim "the fields cost no extra host call" (line 47) holds only for rows a delta returns, and a review write does not return its row.** `pr-refresh.ts:1617-1620`: "A COMPLETED CHECK DOES NOT TOUCH `updatedAt`, so a delta keyed on that field never sees it." A delta re-asks only rows stored as `pending` or `failing` (`rules/pr-index.ts:295-301`). Executed with the domain function: rows `green`, `pending` and `failing` give the re-ask list `[2,3]`, so the green row is not re-asked. Executed with the `CHECKS_OF` fold: CI green plus no review gives `green`. So a head that is about to be reviewed is stored `green`. The reviewer's `pending` write and its final `success` then change neither `updatedAt` nor the stored colour that the re-ask keys on. A clean review posts no comment, so nothing else moves `updatedAt` either. The row reads "review absent" until the next full read, up to `PR_FULL_READ_MS` = 24 h (`pr-refresh.ts:348`). Consequences: the review arm answers `review` again on every pass once the in-flight entry ends. Each start is refused by `reviewPr`'s re-ask and spends the head's budget. #2902's merge arm, which reads `success` from the same row (#2902 plan line 56), never sees it. This fails safe, because no merge happens, but it stops delivery on every clean review. It also makes "every machine sees the mark" (line 50) true only at the controller, because no machine's index sees `pending`. A finding review converges only by chance: the findings comment at `review.ts:503` moves `updatedAt` just before the status write at `:512`. I could not execute this against a live status, because no open PR carries a `plot/review` status today and merging moves `updatedAt`. The code comment and the re-ask rule are the evidence.
2. The row needs a time for "pending younger than `REVIEW_BOUND_SECONDS`". Slice 2 stores only the state and the SHA. `StatusContext.startedAt` is in the rollup at no cost (read from #2895's rollup), so store it.
3. Slice 2 does not say whether the existing `checks` keeps `plot/review` in its fold. It must. `pendingOpenPrNumbers` keys on `checks`, so a `checks` without the review would stop re-asking `pending`/`failure` reviews, and readers of `checks` would change meaning silently. Add the review-free colour as a new field.

## (c) Slices

- The order (findings comment, index, scope, rule) is right against the anti-goal: no unscoped review and no fleet-volume issues.
- Slice 2 has to carry the re-ask fix in (b)1. That is the slice that makes the index's review field true. Without the fix, slice 4's arm and #2902's merge arm read a field that stays stale for up to 24 h.
- Slice 4 is too wide for one branch: the rule, the detached start, the in-flight file, the budget store, the lock in `reviewPr`, the `failure` guard, and "a desk holding a `PLOT-BLOCKED` marker is not dead". The last item is not a review concern. It belongs with #2903 or #2906. Split the `reviewPr` changes (lock, `pending` write with run id, superseded-run guard, unconditional `failure` guard) into a slice before the tick wiring. Those changes also protect a person's run, and they need no fleet.
- `waits:` is missing. Slice 4 needs `feature/unattended-callers-are-refused` if the guard stays caller-specific. With the unconditional guard proposed above, it needs no `waits:`.

## (d) Open questions

- OQ1 (`plot-review-status.sh`): this lens takes no position. Whichever form is chosen must read `pending` as "not reviewed", or the script reports `needs_review` while a review runs.
- OQ3 (cost): the stale-index loop in (b)1 is a cost multiplier on top of the 60 reviews. Each refused start spawns a process and makes 2–3 host calls per pass per head until the budget is spent. Fix (b)1 before a per-sprint budget is sized.
- New: on Bitbucket, slice 2 asks `pr-review` per open slice row per pass. That is a paged walk over statuses and comments (`plot-host.sh:4390-4402`), so at least three calls per row. No bound is stated against the Bitbucket budget. A spent budget holds every read, including merges.
- New: what the review arm answers on a `null` store and on an unread review field. The answer must be `none`.

## (e) Tests the plan should name

- Slice 1, board unit (`test/unit/review.test.ts`): a MEDIUM-only and a HIGH verdict each open no issue, edit the marked comment and write the right status. A Bitbucket run (`prComment` unaskable) names the verdict file and the exit code.
- Slice 2, domain unit: a rollup with a CI pass and no `plot/review` stores the review as absent with colour green. `pending` stores `pending` with its `startedAt`. A Bitbucket row whose `pr-review` failed carries no review field. `checks` is unchanged by the bump. A v5 file decodes to `null` in v6 code (the executed probe as a test). Fleet unit: a delta pass re-asks an open row with an in-flight review or an absent review on a green head, so `pending` and then `success` reach the store within one re-ask cadence.
- `reviewPr` slice, board unit: round 1's concurrent probe as a regression test (the second run removes neither file of the first). A run whose run id is no longer the newest `pending` writes no status. No run replaces a `failure` on the same head. A stale lock with a dead pid is removed.
- Slice 4, domain unit (values): a `null` store gives `none`. Fresh `pending` gives `none`, and stale `pending` gives `review`. A spent budget gives `none`. A verdict file present with no status gives the re-status step. Fleet unit: two ticks over one in-flight file start one review, and the budget survives a restart.

## Amendments

1. Slice 2: keep `checks` as it is and add a review-free CI field. Store the review state, its SHA and `startedAt`. Extend the delta's re-ask to open rows in scope whose review is absent or `pending` on a green head, so a written status reaches the index. Remove "no extra host call" or qualify it.
2. Distinguish "review not asked" (field absent) from "asked, none" (`absent`). The review arm answers `none` on a `null` store and on an unread field.
3. `reviewPr`: take an `O_EXCL` lock `<pr>-<sha>` before any `removeFile` and release it in the `finally`. Write `pending` with a run id. Before the final write, re-read and write only when the run's own id is still the newest `pending`. Never replace a `failure` on the same head, whoever the caller is. Extend `PrReviewReading` with the description (run id) and the time. Put these changes in their own slice before the tick wiring.
4. Name where the per-head start counts live: the in-flight file or a `.plot/state/` file in the common git dir, not memory. Add a re-status step to the step union and a verdict-file reading to the rule's input, or remove the sentence.
5. Name #2899's idle rule as the notification for a head whose budget is spent, or add the notification.
6. Add a Tests section per slice, as listed in (e).
7. Move "a desk holding a `PLOT-BLOCKED` marker is not dead" out of slice 4.

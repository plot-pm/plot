## (a) Problem statement

- The motivation is right: `review.ts:57-68` (the plan cites 58-66) states that any finding opens one follow-up issue, and the code that does it is `review.ts:483-493` with `openFollowUp` at `review.ts:269-345`. Slice 3 changes those lines and the doc comment, not only 58-66.
- The ruleset fact is right and more specific than the plan says. `gh api repos/plot-pm/plot/rulesets/24412719` requires `validate` (integration 15368) and `plot/review` **pinned to integration 5317669** (the `Review app`). So only a writer that holds that app's key turns the check green. fleetd must hold the key from `## Plot Config` `Review app` on its machine.
- The ruleset has two bypass actors with `bypass_mode: always`: RepositoryRole 5 (admin) and Integration 5173644. The design's "no bypass rights" holds only when fleetd's host identity is neither of them. This plan writes the status that the merge arm (#2914) then reads, so the plan should record whose token fleetd uses.
- **Missing cause: the index does not hold the review record.** `PrIndexRowSchema` (`pr-index.ts:30-98`) has `checks`, `failing_checks` and `review`. `review` is GitHub's `reviewDecision` (`plot-host.sh:4808`), not `plot/review`. `checks` folds the whole `statusCheckRollup` (`plot-host.sh:706-707`), and that rollup includes the `plot/review` status. So from the index, (i) "no review" and "review success" both read `checks: green`, and (ii) a HIGH review (`failure`) reads `checks: failing`, the same as red CI. On GitHub only `failing_checks` containing `plot/review` tells them apart. On Bitbucket `failing_checks` is absent (`pr-index.ts:19-21`), so nothing does. The plan claims "the decision reads the index", but no field in the index answers "a review on this head". Today the only reader is `Host.prReview` (`host.ts:400-409`), which is one host call per PR.

## (b) Approach, read against the anti-goal and the safety rules

1. **Two starts of one review corrupt the first run (executed).** `reviewPr` deletes `<pr>-<sha>.md` and `<pr>-<sha>.diff` (`review.ts:424-425`) *before* it tries the worktree (`review.ts:430-431`). Probe result: the second run refused with `could not create the review worktree …/review-7-aaaaaaa` (exit 3), but it had already deleted the first run's diff file. When the first reviewer read it, it found `diff file exists when reviewer reads it = false`. A diff over `REVIEW_INLINE_DIFF_LIMIT` (98,304 bytes, `review-verdict.ts:44-55`) is only in that file. In that case the first reviewer reviews nothing it can read, and can still answer `Findings: HIGH 0` and write `success`. Two ticks, two processes on one machine (`in-flight-store.ts:9-16` documents boards and fleetd ticking the same repo), or a person running `plot-review.mjs` on the same head all cause this. The plan names no in-flight mark for the review step.
2. **The start step as worded blocks the tick.** "The reviewer starts through the existing `agent-run` port and `agentRunCommand`": in `review.ts:447-463` that call is awaited to completion with `boundSeconds: 3600`. Called from the tick, it stalls fleetd's beat for up to an hour, and with it the PR reader heartbeat. Called around `reviewPr`, it skips the status write, the charter check and the diff read. The safe shape is the shape `auto-verify.ts` uses: start `plot-review.mjs <pr>` detached through an adapter, and record pid, PR, head and start time in a state file read with `pidAlive` plus a start grace (`auto-verify.ts:44,129-200`).
3. **Last writer wins on `plot/review`.** `CommitStatusWrite` overwrites per context and sha (`host.ts:117-120`). Two reviews of one head (two machines, a person and fleetd, or a re-run after a crash) can write `failure` and then `success`, because reviewer verdicts are not deterministic. The merge arm (#2914) then merges a head on which a HIGH was found. That is the anti-goal's entry path, and it is exactly what #2912's "ticket before success" rule exists to prevent. A local lock cannot close the cross-machine case. A host-visible mark can: write `plot/review=pending` with a run id on the head at start, and treat a pending status younger than `REVIEW_BOUND_SECONDS` as in flight. Pending keeps the required check unmet, so it fails safe. Separately, an unattended run must never replace a recorded `failure` on the same head. Only #2912's ticket step may do that.
4. **Crash mid-review.** If the process dies between `trees.add` (`review.ts:430`) and the `finally` (`review.ts:465`), it leaves `.worktrees/review-<pr>-<sha7>`. `trees.prune` (`review.ts:429`) does not remove a directory that exists, and `git worktree add --detach` into it fails (`trees-git.ts:471-477`). Every later review of that head then refuses until a new push. This fails safe (no status, no merge), but it stalls silently unless #2909's stall rule sees it. The rule needs a per-head recovery: remove the stale review tree when no live in-flight run owns it.
5. **A partial or failed host answer loops at full price.** These cases write no status: the status write fails (`review.ts:522-524`), the verdict is refused (`review.ts:474-475`), the run ends without finishing (`review.ts:468`), or the reviewer gives no final answer (`review.ts:471`). In each case the rule reads "no review on this head" on the next pass and starts another opus run of up to 3600 s, with no limit. The plan needs a per-head start count with a backoff, and a stop that notifies after N. When a verdict file for `<pr>-<sha>` exists and only the status write failed, the next step is to write the status again, not to run the review again.
6. **"CI green" must exclude `plot/review` and must be bound to the head.** Otherwise a HIGH review reads as "CI red" to every other arm of the rule (#2912's CI-red fixer arm), and a green `checks` from an earlier commit starts a review on an unbuilt head. Require `checksSha === headSha` where the adapter supplies it. Where it does not (Bitbucket, Jenkins), require a host read. The `checksLookup: skipped|broken` rows (`pr-index.ts:92-96`) must read as "not green".
7. **Slice 3 loses findings on Bitbucket.** `pr-comment` exits 4 (unaskable) on Bitbucket (`plot-host.sh:600-608`), so `review.ts:501-507` leaves MEDIUM/LOW findings "only in" the local verdict file. Today a Jira-tracked Bitbucket repository gets them in the follow-up issue. After slice 3 they reach no reader on ewz-kus-portal. The plan must name a Bitbucket target (keep the issue there, or add a Bitbucket comment arm) or state the loss as accepted.
8. **Slice 3 does not say what a HIGH does.** "MEDIUM and LOW … open no issue" leaves a verdict with HIGH ≥ 1 opening today's issue at once. That contradicts design goal 2 ("a follow-up ticket exists only for a HIGH the fleet could not fix"), and #2912 would open a second ticket later. Recommend: slice 3 opens no issue for any finding and posts all findings in the marked PR comment, and the HIGH ticket is #2912's alone. The `failure` status still blocks the merge, so a HIGH without a ticket in the interval is safe.
9. **Unattended refusals and controllers.** `plot-review.mjs` has no unattended refusal and is not one of the controllers in *The Master Agent Uses The Controllers*, so this plan lifts nothing. That is consistent with the design. `release` is not touched.
10. **Armed auto-merge bypasses "one merge in flight".** `allow_auto_merge: true` on the repo. A PR with auto-merge armed merges the moment fleetd's review writes `success`, outside #2914's mark. 0 open PRs were armed when I read. The rule should not review, or #2914 should not count on serial merges for, a PR whose `autoMergeRequest` is set. Alternatively, record that #2914 owns this case.

## (c) Slices

- **The order widens the scope before the scope exists.** Slice *Rule* wires the tick before slice *Scope* lands. Merged alone, it reviews every green slice PR of every plan, at opus price, for as long as the gap lasts. Put *Scope* first, or ship *Rule* with the rule and its tests only and wire the tick in *Scope*.
- The review in-flight mark, the per-head start budget and the stale-tree recovery (b1, b4, b5) are missing from every slice. They belong in *Rule*, or in a fourth slice before the tick is wired.
- *Tickets* (slice 3) does not depend on the others and can merge first. It changes the human path too, so its tests must cover `plot-review.mjs` run by a person.

## (d) Open questions

- **Freeze point (OQ1), with measurement.** `docs/sprints/2026-W44-follow-ups-2-29-1.md` held **2** plan items at `f92415d23 sprint: start` (State: Active) and **10** at `1753e46e1`, after five `sprint: scope change` commits that the person made on the same day. At close it held 11. A freeze at the start transition would have excluded 8 of the 11 plans that the person put into that sprint through the sprint controller. The design's sentence covers "a plan approved during the run". The plan must decide whether a person's `scope change` counts as a re-freeze. Recommend: derive the scope from git (the sprint file at its last `State:`/scope-change commit written by `plot-sprint-state.sh`), not from a new state file. That way it survives a crash, has no second writer and reads the same on every machine. Also remove struck items (`~~[slug]~~`) at read time, so a withdrawn plan's PR is never reviewed or merged.
- **Comment form (OQ2), already answered in code.** `findingsMarker(pr)` (`review.ts:358`) and `Host.prComment(pr, body, marker)` (`host.ts:385-396`) edit one marked comment per PR in place, and the body names the head and the run. Reuse that: one comment per PR, edited per head. Per-head comments would add a new path for no reader.
- New: whose host identity fleetd merges and writes with, given the two `always` bypass actors (a).
- New: where the rule reads the review record: an index field (a `PR_INDEX_VERSION` bump from 5 to 6, plus every store reader) or `Host.prReview` per candidate PR (one call per PR per pass, against the rate budget). #2912 and #2914 both wait on this answer (#2914 asks it as its first open question).
- New: the exit code contract for an unattended caller after slice 3. Today `EXIT.issueNotOpened` (4) also means "findings not posted" (`review.ts:527`).

## (e) Tests

- *Rule* (domain unit, vitest, readings as values): green + `checksSha === headSha` + no review gives `review`. Green with no `checksSha` or with `checksLookup` set gives `hold`. `failing` with `failing_checks = ['plot/review']` does not read as CI red. A review on an older sha gives `review`. A run in flight (live pid, or pending younger than the bound) gives `none`. N refused starts on one head give `notify` and no start.
- *Rule* tick (fleet unit): two passes over one in-flight file start one review; a dead pid past the grace starts again after the stale tree is removed.
- `review.ts` (board unit, extend `test/unit/review.test.ts`): the concurrent-start probe above as a regression test. A second run on the same head must not delete the first run's diff or verdict. An existing `failure` on the head is not replaced by an unattended run.
- *Scope* (domain unit over git fixtures): start commit with 2 items, then a scope change to 10, then a strike, gives the scope the plan chose.
- *Tickets* (board unit): a MEDIUM-only verdict opens no issue, edits the marked comment and writes `success`. A HIGH verdict opens no issue (if amendment 6 holds). Bitbucket (`prComment` unaskable) names the loss and exits with the documented code.

## Findings

1. **The grouping rule is wider than the spec, and a grouped row outside Unblock has no consequence a test can assert.** The spec says "Similar **unblock** items group into one row" (spec *Section contents (open)*, You bullet, line 127) and its decision list speaks only of a grouped "Release or delete" row (spec line 195). The plan's answer groups any rows with "the same verb and the same object kind within one group" (plan lines 84, 91). Under that rule two `review-pr` PRs under Blocks delivery become one row "Review · 2 PRs", and two `plan-approval` plans one row "Approve · 2 plans". The consequence table (lines 69-82) gives one consequence per single item ("the merge waits" · age; "N slices wait" · age) and none for a group of them, so the grouping unit test has no expected value outside `loose`. Grouping a blocks-delivery row also hides each PR behind a ⋯, which changes `delivery-rows` assertions the plan does not name. READ (plan, spec). **Change:** limit grouping to the `unblock` group (`loose`), as the spec states, and say that every other You row stays one row per item; or, if wider grouping is wanted, add the grouped consequence per reason to the table and name it as a spec deviation in Notes.

2. **The menu unit tests for two row kinds belong to no slice.** The Row menu column slice requires "a unit test per row kind (You, Work items, Release plan row, Release slice line, Fleet agent, Tickets)" (line 66), but its slice line renders only `PlanActions`, `ResliceMenu`, `SliceActions`, `BranchMenu` and `IssueRowActions` from the items (line 97). The inventory sends `StartWorkButton` to the Release delivery unfold slice and `BrokenAgentMenu`/`DropAgentButton` to the Fleet switches slice (lines 45, 47), and neither of those slice lines names a menu item list or its unit test (lines 109, 113). The You row's per-branch items come from `CleanUpMenu` in the You rows slice (line 40), so the "You" row-kind test is also not in the first slice. A reviewer of slice 1 cannot tell which row-kind tests to expect in it. READ (plan). **Change:** in *Per slice › ⋯ column*, list the row kinds whose item lists slice 1 builds and tests (Release plan row, slice row, branch row, Tickets); and add to the You rows, Release delivery unfold and Fleet switches slice lines "the `rowMenuOf` items of this row kind with a unit test of each item's `enabled` and `reason`".

3. **`statusPills` has one signature and three inputs.** The plan names `statusPills(placement, facts)` (line 85), where `placement` is an `ItemPlacement` and the value kinds are `gate`/`progress`/`wait` (`delivery-work-columns.ts:21`, opened). The Release unfold calls it "over `PlanLine['state']`" (line 86), which is `SliceState | 'unread'` (`release-plan-rows.ts:37`, opened), and the Fleet slice "over the agent state (`doing`)" (line 87), an agent placement rather than an item placement. The Work items "no sprint" pill needs `rowSprintMembership`'s answer (line 60), which is not a parameter either. Today the slice-line words and hues live in a `.tsx` map, `LINE_STATE` in `ReleasePlanParts.tsx:179-180` (opened), which the plan does not name; plan 4 forbids a new `.tsx` word map (plan 4 line 59), so moving `LINE_STATE` is the work this slice must state. READ and RAN (opened files). **Change:** name three pill functions or one function over a discriminated input (for example `statusPills({ kind: 'work', placement, facts, sprint } | { kind: 'slice', state } | { kind: 'agent', state })`); name in the Release slice that `LINE_STATE` moves into it; name the Fleet slice's pill unit test; and add the "no sprint" pill to the Work items slice line.

4. **The plan says plan 4 removes `todo-list.ts`; plan 4 keeps it, so the verb change reaches a test the plan does not name.** Plan line 84: "`reasonVerb` also feeds `todo-list.ts`, which plan 4 removes." Plan 4 extends `todoList` (`docs/plans/2026-11-20-delivery-tab-has-one-header.md:59`) and states "`reasonVerb` keeps its other callers" (`:74`); it removes only the `TodoList` component. `todo-list.ts:120` calls `reasonVerb`, and `packages/domain/test/todo-list.test.ts:41,89` asserts the verbs. Changing `draft-plan` from `open` to `Interrogate` therefore changes the header's You lines (plan 4) and their test, in a slice that does not wait on plan 4. A second consumer is `itemRowCells`' Do link, which reads `REASON_DO[...].action` (`delivery-row-form.ts:526`, opened); the new record `{ verb, tone, consequence }` has no `action`, and the plan does not say what the Do link's target becomes beyond "the verb opens the same choice as ⋯". RAN (grep) and READ (plan 4). **Change:** replace "which plan 4 removes" with "which plan 4 keeps for the header's You group; the new verbs reach the header, and `todo-list.test.ts` is updated in this slice"; and state that the verb cell's target is the row's `rowMenuOf` menu, with a unit test asserting it, so `action` leaves the record knowingly.

5. **The same-x claim has no named test.** "A fixed last column at the same x across groups and sections" and "an empty last cell of the same width" (lines 16, 66) are layout facts only a browser can see. Slice 1 lists `tickets-section`, `menu-fits-the-kind`, `delivery-rows` and `tuple-row` (line 66), none of which measures the column across sections today. READ (plan). **Change:** in slice 1, name the browser test that asserts the ⋯ cell's left edge is equal across You, Work items, Release delivery, Fleet and Tickets rows, including a row with no action, and count it in the slice's delta.

6. **Minor, for the builder.** The spec's Fleet row is "circle, agent, working-on tuple, status pill, duration, ⋯" (spec line 129); the plan keeps role, tokens and time left and has no duration (line 87). The plan's reason ("no value is lost") is acceptable, but it is a spec deviation and belongs in Notes. The bulk-delete removal deletes the `it(` "the group deletes its quiet branches one by one" in `loose-ends-show-under-unblock.browser.test.ts` (recorded in the gate's 714 → 718 comment, `stubbed-tests-start-no-board.test.ts:953`), so the You rows slice lowers `EXPECTED_TESTS` by at least one. READ and RAN.

## Findings

1. **The Work items slice cites the wrong column set.** The plan says "Today's columns are `ROW_COLUMNS` (`packages/domain/src/rules/delivery-row-form.ts:18`)". Work items rows render from `WORK_ITEM_COLUMNS = ['kind', 'item', 'where', 'group', 'by', 'age']` (`packages/domain/src/rules/delivery-work-columns.ts:14`) through `workItemCells` (`delivery-work-columns.ts:40`, called at `AgentList.tsx:1237,1245`). Each group has its own column, Gates / Progress / Waits on (`WORK_GROUP_COLUMN`, `delivery-work-columns.ts:24-28`, read at `delivery-view.ts:608` and `AgentList.tsx:1756`). `ROW_COLUMNS` holds the seven generic columns and the Do column. `workByCell` (`delivery-row-form.ts:373`) already moves the agent into By, and `gatesCell` (`delivery-row-form.ts:286`) already returns one `CellPart` per gate with an `outcome`, which is the status pill's dot colour. The plan names none of these. It also does not say what happens to the per-group Progress and Waits on values when the grid has one status column. The plan's grid (item, plan, status, by, age, ⋯) has no Where column, yet the plan says "the branch column gives way". The mockup `work-items-columns.html:22,55` has Item, Where, Status, By, Age, ⋯ and no Plan column. RAN (opened the files). Change: replace the `ROW_COLUMNS` reference with `WORK_ITEM_COLUMNS`/`workItemCells`/`WORK_GROUP_COLUMN`. State that the slice extends `gatesCell`'s `parts[].outcome` for the pills and keeps `workByCell`. Say where Progress and Waits on go. Decide whether the grid has a Where column or a Plan column, and name which column gives way.

2. **The ⋯ for Tickets rows already exists as `IssueRowActions`.** `IssueRowActions` (`packages/board/src/app/lib/agent-rows/menus.tsx:1689`) is a ⋯ on a ticket row that holds Create plan, Create story and Open on host. Its TSDoc (`menus.tsx:1670-1688`) records that it moved *Create plan* out of the cell into ⋯. It renders in the Delivery tab through `IssueRowView` (`rows.tsx:2500,2600`; `AgentList.tsx:1309`). The Tickets section alone still renders a bare `CreatePlanButton` (`TicketsSection.tsx:114-116`, with `data-tickets-do`). RAN. Change: name `IssueRowActions` as the menu the Tickets rows adopt, instead of building a new *Plan it* item in `rowMenu`.

3. **The menu inventory is incomplete.** The plan says the new menu "extends today's `menuState` … and `CleanUpMenu.tsx`; it is not a second menu". The repository holds at least nine row menus or action sets today: `BranchMenu` (`menus.tsx:439`), `RowActions` (`:511`), `SliceActions` (`:1058`), `ResliceMenu` (`:1154`), `PlanActions` (`:1401`, rendered on every Release plan row at `AgentList.tsx:1660-1670`), `IssueRowActions` (`:1689`), `BrokenAgentMenu` (`:1800`), `CleanUpMenu`, and the inline `StartWorkButton` on slice lines (`AgentList.tsx:1685-1687`). The view-model type for the Delivery row menu is `RowMenuView`/`rowMenuOf` (`packages/board/src/app/lib/agent-rows/delivery-view.ts:100,119`), and the plan does not cite it. The plan's list of controllers (release-claim, loose-delete, restart, passkey release approval, interrogate, design, *Plan it*) leaves out approve, deliver, implement, dispatch, continue and reslice. Today's rows reach those through `PlanActions`, `StartWorkButton` and the You Do cell (`REASON_DO`, `delivery-row-form.ts:216-229`). A builder who follows the list as written drops them. RAN. Change: list each existing menu or button that the one ⋯ replaces, name `RowMenuView` as the type it extends, and add the missing controllers to the list.

4. **"Design starts" names no board controller.** The board routes (`packages/board/src/server/index.ts:290-497`) contain `/api/interrogate` and `/api/needs-design` (which moves a plan to Design) and no design-run start. A design run starts only from fleetd's auto-design (`packages/fleet/src/shared/auto-design.ts`). The spec non-goal carries the same phrase. The plan's "drop" is `/api/registry/drop` (`index.ts:483`, `DropAgentButton`), which drops an agent, not a plan. RAN. Change: name `needs-design` and `registry/drop` exactly, or remove "design starts". The plan must not add a route, because it rules out controller changes.

5. **The You rows slice must build on the existing verb table and the bulk delete.** `REASON_DO`/`reasonVerb` (`delivery-row-form.ts:216-239`) already give each You reason a verb, and `youRowCells`/`YOU_COLUMNS` (`:22,844`) already shape the row. The verbs differ from the spec: `draft-plan` is "open" where the spec says "Interrogate", and `loose` is "plan" where the spec says "Release or delete". The group-wide `CleanUpBulkDelete` (`CleanUpMenu.tsx:110`, rendered in the unblock group header at `AgentList.tsx:1744`, words from `bulkDeleteWords`, `delivery-view.ts:160`, tested in `test/unit/delivery-view.test.ts`) is a bulk action that runs today. The plan adopts the spec call "no bulk action" but does not say that this removes a shipped control. `reasonVerb` also feeds `todo-list.ts`, which plan 4 removes. RAN. Change: state that `REASON_DO` changes (name the new verbs), state that the slice removes `CleanUpBulkDelete` and `bulkDeleteWords` with their tests, and cite `youRowCells` as the function it rewrites.

6. **The Release unfold slice depends on plan 2 and does not say so.** The slice "gives it the shared fold control". Plan 2's `feature/every-delivery-section-folds` builds the shared 28 px fold control (`2026-11-20-every-delivery-section-folds.md:61`). This slice has no `waits:` on it. The unfold itself exists today: `PlanName` toggles (`ReleasePlanParts.tsx:104-115`) and `plan.lines` from `planLines` (`packages/domain/src/rules/release-plan-rows.ts:117,154`) render slice lines with `LineState`, `LineSlice`, `LinePr` (`AgentList.tsx:1673-1690`). The slice's real work is the tuple, the pill and the ⋯ on each `PlanLine`. RAN. Change: add `<!-- waits: feature/every-delivery-section-folds -->` and name `PlanLine` as the type that gains the menu and the pill.

7. **The Fleet slice drops agent columns and an anchor without saying so.** Agent rows today use `AGENT_COLUMNS = ['agent', 'role', 'actingOn', 'doing', 'tokens', 'timeLeft']` (`delivery-row-form.ts:540`). The plan's row (circle, agent, working-on, status pill, duration, ⋯) has no role, tokens or time left, and the plan does not cite `AGENT_COLUMNS` or say where these values go. The spec non-goal "all current information" (Decided by the operator) is at risk. The switches already sit in the Fleet section, in its heading row, under `id="fleet-controls"` (`AgentList.tsx:1622-1630`). The held-switch links in group headers scroll to that anchor (`AgentList.tsx:1735`), and `fleet-settings.browser.test.ts` and `delivery-fleet-look.browser.test.ts` pin `data-fleet-control-column`. If the switch row moves into the body, a folded Fleet section hides them. The plan must keep the anchor and the hook, or name the tests it changes. Plan 2 also rewrites that heading row and has no `waits:` here. RAN (did not run the board to see the stopped state; the render condition at `AgentList.tsx:1622` tests only `section.key`). Change: cite `AGENT_COLUMNS` and state the fate of role, tokens and timeLeft. Keep `#fleet-controls`. Add a wait on `feature/every-delivery-section-folds`.

8. **References that hold.** `CreatePlanButton` at `TicketsSection.tsx:115`, `DeliveryScopeKind` at `delivery-scope.ts:8`, `menuState` at `menus.tsx:250`, `planItReason` at `tickets-section.ts:83` with the three reasons, `YOU_GROUP_OF` at `delivery-placement.ts:211-224` (only `loose` goes to unblock), `PlanName` at `ReleasePlanParts.tsx:104`, the switches at `AgentList.tsx:1624-1628`, `FleetMachineSchema` at `schema.ts:4475-4481`, and the sibling slugs in the `waits:` markers (`feature/delivery-tuples-in-every-row`, `feature/delivery-tab-has-one-header`) are all where the plan says.

## Findings

1. **`rowMenu` has no named home, no shape and no existing seam it replaces, and today's reasons are decided in `.tsx`.** The plan says the menu "extends today's `menuState` (`menus.tsx:250`) and `CleanUpMenu.tsx`; it is not a second menu". `menuState` returns only `{ present: boolean; enabled: boolean }` (`packages/board/src/app/lib/agent-rows/menus.tsx:250-322`): it holds no item list and no reason, so it cannot carry "every action listed with its disabled reason". The reasons are composed inline in components today, for example `SliceActions` builds `dispatch.reason ?? \`Cannot start ${wave} from here\`` in JSX and disables the whole ⋯ trigger when `!willAct` (`menus.tsx:1106-1110`), which hides every item behind a disabled button. The same file holds eight menu components (`BranchMenu` :439, `RowActions` :511, `SliceActions` :1058, `ResliceMenu` :1154, `PlanActions` :1401, `IssueRowActions` :1689, `BrokenAgentMenu` :1800, plus `CleanUpMenu`). A view-level seam already exists: `RowMenuView` / `rowMenuOf` (`packages/board/src/app/lib/agent-rows/delivery-view.ts:100-122`), tested in `packages/board/test/unit/delivery-view.test.ts`. `menuState` is also a function declaration in a `.tsx` file; rewriting its body makes it an arrow under CLAUDE.md's "the rule follows the diff". RAN (opened files). **Change:** in *Per slice › ⋯ column*, state that `rowMenu` extends `RowMenuView`/`rowMenuOf` in `delivery-view.ts` (or a `packages/domain` rule) and returns, per row, a list of items `{ action, label, enabled, reason | null, confirm | null }`; name which of the eight menu components it feeds in this slice and which keep their own logic; state that the ⋯ trigger is never disabled while it lists a disabled item; and require a unit test per row kind (You, Work items, Release slice line, Fleet agent, Tickets) asserting each item's `enabled` and `reason`.

2. **The Work items reference does not hold, and the pill mapping is unspecified.** The plan names `ROW_COLUMNS` (`delivery-row-form.ts:18`) as today's Work items columns. Work items renders `WORK_ITEM_COLUMNS = ['kind','item','where','group','by','age']` (`packages/domain/src/rules/delivery-work-columns.ts:15`), whose `group` column holds a different kind of value per group (`WORK_GROUP_COLUMN`, :25-29: Gates = one linked mark per gate from `gatesCell`, Progress = PR state plus unpushed count, Waits on = what the item waits on). It is pinned by `packages/domain/test/delivery-work-columns.test.ts`. The plan does not say how these three value kinds become pills, whether each gate pill keeps its own link (today each mark links to its checks or review page), or what happens to `where`. RAN. **Change:** cite `WORK_ITEM_COLUMNS`/`WORK_GROUP_COLUMN`; name the pill function (for example `statusPills(placement, facts)`) and its mapping from each `GroupValueKind` to pill words, dot tone and link; and state that `delivery-work-columns.test.ts` is rewritten to the new columns rather than deleted.

3. **Two You-row decisions have no expected value a test could assert.** Grouping is the plan's one Open Question ("which rows are similar enough"), so the slice's grouping test has no oracle until it is answered. Verb and consequence are given only by two spec examples, while `YOU_GROUP_OF` has 12 reasons (`packages/domain/src/rules/delivery-placement.ts:211-224`); the builder would invent eleven verbs and consequences. The verb's tone (red/amber/grey) is a rendered state the plan's list of domain properties omits. READ (plan, spec) and RAN (placement file). **Change:** answer the Open Question in the plan (the suggestion "same verb and same object kind within one group" is testable); add a table of verb and consequence per `YouReason`, or require them as a `Record<YouReason, …>` so `tsc` proves every reason has one; add "verb tone" to the list of domain properties in *Shared rules*.

4. **Today's bulk delete contradicts the spec call and the plan does not remove it.** The Clean up group has a group-wide delete: `CleanUpBulkDelete` (`packages/board/src/app/components/CleanUpMenu.tsx:110`), rendered at `AgentList.tsx:1744`, with `bulkDeleteWords` and `cleanUpBranches` in `delivery-view.ts`, and tests in `delivery-view.test.ts` and `loose-ends-show-under-unblock.browser.test.ts`. The plan says "no bulk action (spec call)" but names neither the removal nor the tests that change. RAN. **Change:** in the You rows slice, state that `CleanUpBulkDelete`, `bulkDeleteWords` and `cleanUpBranches` are removed with their unit and browser assertions, and record the count change; or state that the bulk delete stays and the spec call is overridden.

5. **Status pills outside Work items have no builder.** The Release unfold and Fleet slices each render a "status pill", but their `builds:` markers name `releasePlanSlices` and `fleetSwitchRow`, and only `workItemsGrid` names pills. Slice line state is `PlanLine['state']` (`ReleasePlanParts.tsx:179`) and agent state is the eight-state enum; neither has a pill mapping. READ (plan) and RAN. **Change:** name in each of the two slices the domain property that maps its state to pill words and tone, with its unit test, or state that the Work items slice's pill function takes those states too.

6. **The Scope and Mine rule belongs to no slice.** *Shared rules* states that Mine in the `release` scope shows the reader's items in no active sprint, and that such a row says "no sprint". Only the You rows slice mentions "no sprint"; Work items is not covered. `delivery-scope.ts` has no "no sprint" concept (`deliveryScope`, :50), and the Mine filter lives in `agent-rows/mine-filter.ts`. Whether this is a behaviour change or today's behaviour is not stated. RAN. **Change:** say whether today's filter already does this; if not, assign it to one slice with a named domain property (for example `rowSprintMembership`) and a unit test over the spec's scope × Mine table.

7. **The count gate is a shared hotspot; each slice should state its delta.** `stubbed-tests-start-no-board.test.ts` pins `EXPECTED_FILES = 99` (:569), `EXPECTED_TESTS = 719` (:956) and `EXPECTED_EXCEPTIONS = 5` (:1014). Five slices here and six other plans on the same sprint edit these constants. The browser tests this plan touches by selector: `tickets-section` (`data-tickets-do`, `data-plan-it-reason`), `loose-ends-show-under-unblock` (`clean-up-bulk`), `menu-fits-the-kind`, `delivery-work-items`, `delivery-rows`, `release-delivery-fold`, `fleet-settings` and `delivery-fleet-look` (`#fleet-controls`, `data-fleet-control-column`), `tuple-row`. RAN (grep). **Change:** require each slice to list the browser tests it edits and to record its `EXPECTED_FILES`/`EXPECTED_TESTS` delta and reason in its PR body.

8. **The Fleet slice's two claims need named tests.** "Visible when the fleet is stopped" and "no switch outside the Fleet section" are a state and a negative. Today the switches sit in the section heading's `data-section-controls` span with id `fleet-controls` (`AgentList.tsx:1621-1629`), which two browser tests select. READ and RAN. **Change:** name the view property that decides the switch row shows (for example `fleetSwitchRow(fleet)` returning the row for a stopped fleet), its unit test, and whether the `#fleet-controls` anchor is kept so the two browser tests keep their selector.

9. **References that hold:** `planItReason` with its three reasons (`tickets-section.ts:83-87`); `YOU_GROUP_OF` sending only `loose` to unblock (`delivery-placement.ts:211-224`); `DeliveryScopeKind` (`delivery-scope.ts:8`); `FleetMachineSchema` (`schema.ts:4475-4481`) with no process fields; `PlanName` with its toggle (`ReleasePlanParts.tsx:104`); `CreatePlanButton` labelled "Plan it ›" (`TicketsSection.tsx:115`); the switches at `AgentList.tsx:1624-1628`. Cross-plan slice names `feature/delivery-tuples-in-every-row` and `feature/delivery-tab-has-one-header` exist in plans 1 and 4.

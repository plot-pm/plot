## Findings

1. **The mockup's You row "Approve release · 3590 · ready 43 min" cannot appear under "today's placement".** The reference mockup puts the release approval as the first You › Blocks delivery row, and the header's You group counts it ("1 blocks delivery"). The plan keeps today's placement, and today `placeDelivery` sends every `release` item and every item with `approvalOwed === 'release'` to `releases` and to no section (`packages/domain/src/rules/delivery-placement.ts:435-437`); the `release-approval` entry in `YOU_GROUP_OF` (`:215`) is therefore never reached by a release. The plan also lists "release approval with passkey" among the controllers its ⋯ items call, but names no row whose ⋯ holds it. A person sees an empty Blocks delivery group while the header's Release group says the release waits on them. Evidence: READ mockup `header-and-sections-v2.html` (You › Open), RAN grep and read `delivery-placement.ts:428-445`. **Change:** in *You rows*, state either that a release owing approval also places a You › Blocks delivery row (verb "Approve release", object the release PR tuple, ⋯ holding the passkey approval) as a placement change with its unit test, or that it does not and the mockup row is out of scope, and then remove "release approval with passkey" from the ⋯ controller list.

2. **Existing controls the plan silently drops or does not place.** (a) `CleanUpBulkDelete` renders today in the Unblock group heading (`packages/board/src/app/components/AgentList.tsx:1744`, `CleanUpMenu.tsx:110`); the plan adopts "no bulk action" but does not say it removes this control and its tests. (b) The Release delivery plan row carries `PlanActions` (approve, deliver, implement, dispatch) and each slice line a `StartWorkButton` (`AgentList.tsx:1663-1673,1683-1685`); the plan's ⋯ controller list ("release-claim, loose-delete, restart, release approval, interrogate and design starts, Plan it") omits all five, so a builder cannot tell whether they move into ⋯ or stay as buttons beside it. (c) The Fleet section shows `WorkingCounts` (with the hidden-by-filter count) and `FleetAlert` (`AgentList.tsx:1695-1704`); the Fleet slice's row list does not mention them. (d) The held-group link "· review off · turn on ›" scrolls to `#fleet-controls` (`AgentList.tsx:1736-1740`), whose id sits on the switch span in the Fleet header (`:1623`); after the switches move into the open body, the link lands on nothing while Fleet is folded. Evidence: READ `AgentList.tsx:1610-1745`. **Change:** add to *Approach › Per slice* one sentence each: the Unblock group's bulk delete is removed (named, with the tests it removes); `PlanActions` and Start work become ⋯ items of the plan row and slice line (or stay, stated); `WorkingCounts` and `FleetAlert` stay at the top of the open Fleet section; the `#fleet-controls` anchor moves with the switch row and the "turn on ›" link opens the Fleet section before it scrolls.

3. **"Mine on" names no mode, and the Mine-off cell of the scope table is not addressed.** The board has three Mine modes, `off`, `mine` and `strict` (`DeliveryMine`, `packages/domain/src/rules/delivery-placement.ts:32`; `mineMode`, `packages/domain/src/rules/mine-mode.ts:40-43`), and `mine` keeps rows of unknown owner. The plan's Scope-and-Mine rule says only "Mine on". The spec's table also says `release` + Mine off shows "every item of every active sprint", while today the `release` scope does not narrow rows at all (`selection` is `[]`, `delivery-scope.ts:25-27`; `AgentList.tsx:832`), so items in no active sprint show with Mine off today. Finally, "no sprint" is planned only as You-row consequence text; a Work items row under Mine on in the `release` scope has no consequence column and gets no mark. Evidence: READ the spec's scope table, RAN grep on `mine-mode.ts`, `delivery-placement.ts`, `AgentList.tsx`. **Change:** in *Shared rules › Scope and Mine*, name which of `mine` and `strict` the table's "Mine on" means (or both); state whether `release` + Mine off narrows to active sprints (a behaviour change) or keeps today's unnarrowed rows; and state where a Work items row shows "no sprint" (for example as a status pill), each as a domain property with a unit test.

4. **The Work items grid has no named home for today's Progress and Waits-on values, and the plan cites the wrong column list.** Work items rows render from `WORK_ITEM_COLUMNS = ['kind','item','where','group','by','age']` and `WORK_GROUP_COLUMN` (Gates / Progress / Waits on) in `packages/domain/src/rules/delivery-work-columns.ts:14,24-28`, through `workItemCells` (`AgentList.tsx:1237,1245`), not `ROW_COLUMNS` (`delivery-row-form.ts:18`) as the plan says. Being built's Progress (PR state and unpushed count) and Queued's Waits-on text ("claimed 2 days ago, no work committed", and the quiet "claimed on another machine" line in `work-items-columns.html`) have no column in the new item / plan / status / by / age grid. The plan also says "the branch column gives way" for a grid that lists no branch column; the branch is a segment of the item tuple. Work items also holds plan blocks with indented slice rows today (`delivery-view.ts:444-451`; the mockup's Queued plan row), and the plan does not say they stay. Evidence: RAN grep, READ both mockups. **Change:** in *Work items grid*, cite `WORK_ITEM_COLUMNS`/`WORK_GROUP_COLUMN`/`workItemCells`; state that Gates, Progress and Waits-on values become status pills (with the "claimed on another machine" line as a pill or a second line); replace "the branch column gives way" with "the branch segment of the item tuple gives way"; and state that plan blocks keep their indented slice rows.

5. **Fleet slice and plan 2's stopped frame have no stated order.** The spec's stopped state shows the switch row above the grey ■ stopped frame with "Start fleet". Plan 2 builds that frame and the "— none" empty groups (`2026-11-20-every-delivery-section-folds.md:35,43,61`); this plan's Fleet slice waits only on plan 4, and its Work items grid rewrites the same group-render block (`AgentList.tsx:1711`) that plan 2 changes. Either can merge first, and the person may see the switches below or inside the stopped frame, or a grid with no "— none" row. Evidence: READ plan 2 and the mockup's Fleet / Work items states. **Change:** add `waits: feature/every-delivery-section-folds` to the Fleet switches slice (and to the Work items grid slice, or say in Notes which side places the "— none" row in the new grid).

6. **A row with no action must still reserve the ⋯ column.** `CleanUpMenu` returns `null` when it has no item (`CleanUpMenu.tsx:43`), and `menuState` hides a menu that has no present item (`packages/board/src/app/lib/agent-rows/menus.tsx:250`, invariant in its TSDoc). The plan says "one ⋯ per row with an action" in a fixed column, but not that a row with no action keeps an empty last cell, which goal 12 needs so every other ⋯ keeps its x. The plan also extends `menuState` and `CleanUpMenu` but not `rowMenuOf`/`RowMenuView` (`packages/board/src/app/lib/agent-rows/delivery-view.ts:100-123`), which is where a Delivery row's menu is decided today. Evidence: READ the files cited. **Change:** in *⋯ column*, add "a row with no action keeps an empty last cell of the same width" and name `rowMenuOf` as the view that grows the menu items and disabled reasons.

7. **The grouped Unblock row's object is not defined.** The changelog says "Release or delete · 2 loose branches · 36–37 days old", but the mockup draws one branch tuple (`idea/scratch-board`) under "Unblock · 3" with two rows, and the Open Question leaves grouping open. Evidence: READ `header-and-sections-v2.html` You › Open. **Change:** resolve the Open Question in the plan (same verb and same object kind within one group) and state that the grouped row's object is a count ("2 loose branches"), each branch tuple appearing in its ⋯.

## (a) Problem statement

- The cited lines hold at this tree: `App.tsx:542` is `if (tab !== 'delivery') return;`, `:772` is `if (tab === 'delivery') void loadFleet();`, `:1524` and `:1537` pass `planAgeSeconds={fleet?.ageSeconds ?? null}`, `:1597` calls `planFileFromFleet(slug, fleet.rows, fleet.draftPlans)`, `PlanSourceLine.tsx:145` prints `· ${ageSeconds}s ago`, `schema.ts:4285` is `ageSeconds: z.number()`.
- One citation is wrong: Approach says the Planning tab's own poll is "`load`, `App.tsx:772`". Line 772 is the visibility handler. The board poll is the effect at `App.tsx:527–532` (`setInterval(() => void load(), … POLL_MS)`, `POLL_MS = 30_000` at `:48`).
- The plan says the fleet age "dates a different read from the one the sentence describes". The code states the opposite intent: `PlanSourceLine.tsx:53–58` says the fleet age is used *because* "the scan and this read see the same refs, and the scan is what fetches them, so its age dates this too", and `Board.tsx:151–158` repeats it. The plan must name this documented reason and say why it no longer holds. The answer matters to the tests, see (d).
- The sprint modal is not a Planning-tab-only surface. `SprintModal` opens through `onOpenSprint`, which `StoriesTab` (Discovery) also receives (`App.tsx:1373`), and through `StoryModal` (`:1578`). The fallback defect therefore also shows on Discovery. The test must cover the click from a surface the plan does not name, or the plan must say why one surface is enough.
- Probe output, current behaviour: `PlanSourceLine` with `ageSeconds: null` prints no age; with `0` it prints `· 0s ago`. The server sets `ageSeconds = 0` when the fleet cache has no scan (`fleet.ts:7506`, `entry.at === null ? 0 : …`), so today a Delivery visit before the first scan can make the Planning line print `0s ago`. This is the "0s ago for an unknown age" the plan forbids, and it already happens.

## (b) Approach

- **A "board timestamp" is the time of the poll, not of the plan read's freshness.** `/api/board` builds the board on every request (`fleet-state.ts:196–240`: only concurrent requests share one `buildBoard`), and `buildBoard` sets `generatedAt: new Date().toISOString()` (`board.ts:2659`). Option 1 of the first open question therefore shows "seconds since the page last polled": a sawtooth from 0 to about 30 s (`POLL_MS`), reset early by each channel event (`App.tsx:537`). Option 2 ("time the server last read the plan sources") has the same value, because the server reads them on each request. Neither dates the last `git fetch` of the ref, which is the fact `PlanSourceLine.tsx:53–58` says the line exists to show. The plan's browser test passes for both options and proves only that a number ticks.
- **The page-clock mechanism differs from the estate's precedent.** `AgentList.tsx:578–600` dates its footer as the server's `ageSeconds` plus a client tick since the payload arrived. The tick resets on `fleet.generatedAt` and stops when the fetch is stale. The plan proposes `Date.now() − generatedAt`, which mixes the browser clock with the server clock. A skewed client prints a negative age or a wrong one. The existing precedent `agent-facts.test.ts:60` ("-3s ago is not a thing to render") shows this repo already met that case. If the plan keeps the wall-clock form, the domain rule must clamp, and a unit test must pin the clamp.
- **Behaviour while the board is unreachable is unstated.** The Delivery footer freezes its clock when the fetch is stale (`AgentList.tsx:584–594`). The plan does not say whether the Planning age keeps growing or freezes behind the dim overlay (`App.tsx:571`). Either answer is testable, but the plan must choose one, or no test can fail.
- **The sprint fallback's first candidate is empty by construction.** The fallback runs only after `allCards.find((c) => c.slug === slug)` failed (`App.tsx:1586`), and `allCards` is every card in `board.columns` (`:1141`). Any lookup over "the board's own cards" therefore answers `''` for every slug that reaches it. The probe confirms it: `planFileForSlug(cards, 'ghost')` returns `''`, and `planFileFromFleet('ghost', [], [{plan:'ghost', …}])` returns the file. The server also already marks this exact case: `collectSprints` receives `new Set(cards.map((c) => c.slug))` (`board.ts:2652–2654`) and sets `known: false` on any member outside it (`board.ts:1645–1649`). A slug with no card is a member with `known: false`.
- Layering: a plan-age rule in `packages/domain` with a pure `(timestamp, now) → number | null` signature fits "Every rendered state is a domain property". The unit test can assert the value. The unit test cannot assert "never reads a fleet payload": that is a fact about the `App.tsx` wiring, and only the browser test (or the rule's signature) states it.

## (c) Slices

- If the first open question resolves to "date the last fetch of the ref", the slice needs a server change and a new optional `/api/board` field. That is still one branch, but its Board-impact comment must then name the server change.

## (d) Open questions

- **Which event does "Ns ago" date?** Neither listed option dates what the line describes (see (b)). A third answer exists: the time the local ref was last fetched, which the board server can read without a host call (for example the reflog time of `refs/remotes/origin/<default>`). That is the only option where a test fixture states a fetch time and the assertion distinguishes it from the poll time. If the plan keeps option 1, it must say that the line then dates the poll, and change the `PlanSourceLine.tsx:53–58` and `Board.tsx:151–158` docs to say so.
- **Where does the fallback get its plan file?** Not from the board's cards, which are empty by construction (see (b)). The remaining choices: (1) a new board field naming plan files the cards do not cover, the way `fleet.draftPlans` does (`schema.ts:4559–4569`, drafts read from the working tree); or (2) remove the fallback, so a `known: false` member stays open in every session. Choice (2) needs no server change, and `SprintModal.tsx:177` can render a `known: false` member as text rather than as a button, which is a domain-testable property. The plan must say which, because the browser test asserts a destination and the two choices have different destinations.
- **Does any other Planning read use `fleet`?** The grep at this tree finds three Planning uses (`App.tsx:1524`, `:1537`, `:1597`). `:1224` and `:1385–1456` sit in Delivery or Discovery blocks. `Swimlanes`, `Board`, `SprintModal` and `PlanSourceLine` contain no `fleet` reference beyond doc comments.
- New question: **what does the line show while `/api/board` is unreachable?** See (b).
- New question: **is a `known: false` member clickable at all?** Today `SprintModal.tsx:177` renders any non-empty slug as a button, whether or not the board knows it.

## (e) Tests

**Do the proposed tests fail before the fix?**

- Browser, fresh page: before the fix `fleet` is `null`, so the line has no age, and "the age increases between two ticks" fails. It passes after the fix. **Valid discriminator.**
- Browser, after a Delivery visit with a frozen fleet `ageSeconds`: before the fix the line shows the frozen number and "still moving" fails. **Valid discriminator**, if the stub's `ageSeconds` differs from every value the fixed rule can produce (use 999, not 0 or 1; the catalogue default is `ageSeconds: 1` at `build.ts:172`).
- Browser, sprint item: "opens the same destination on a fresh page and after a Delivery visit" fails before the fix only if the fixture's fleet names the slug in `draftPlans` or `rows`, and the sprint member has no card. Without that fleet stub, both visits already stay open today and the test passes before the fix. The test must state that fleet stub, and it must assert the destination by name (the URL `/plan/<file>`, or "dialog still visible"). "The same in both visits" is also true of a fix that breaks both.
- Unit: "null for an absent timestamp" and "grows with the clock" fail before the fix only because the function does not exist yet. Add the cases that pin decisions: a timestamp later than `now` (clock skew) clamps to 0 or reads `null`; an unparseable timestamp reads `null`. Tier: domain unit (`packages/domain/test/`), with `now` passed in rather than read from `Date.now()`.

**Clock flakes, and how to avoid them.**

- The catalogue pins `generatedAt` to `2026-08-30T12:00:00Z` (`build.ts:67–68`: "A catalogue whose ages move is a catalogue that flakes"). A test with no fake clock prints the age against the real date. The probe printed `· 5170221s ago` today. Every assertion on that number then depends on the day CI runs.
- Use the precedent at `page-hears-channel.browser.test.ts:35–41`: `page.clock.install({ time: Date.parse(generatedAt) + 10_000 })`, then `page.reload()` so the fake clock is in place before the app's scripts run. Assert the exact text `· 10s ago`, run `page.clock.runFor(5_000)`, and assert `· 15s ago`. The test then compares exact strings and never reads two real seconds apart.
- Keep each `runFor` below `POLL_MS` (30 s), or accept that the board poll fires. With the catalogue's fixed `generatedAt` a re-poll does not reset the age, so a real server's reset is not proven. If the rule resets on a new payload, add one step that serves a new `generatedAt` (route over the baseline, as `plan-source.browser.test.ts:100–121` does) and asserts the age drops.
- The Delivery visit needs the fleet poll to answer once. Run `runFor(FLEET_POLL_MS + 500)` on Delivery, then switch back to Planning and run the clock again.
- Every `[data-plan-source="ref"]` page in the catalogue gains an age after the fix. The existing assertions use `toContain`, so they keep passing. A new test that compares the line's whole text must install the clock.

**Existing tests that assert the fleet-sourced behaviour.**

- None of the board's tests asserts the Planning age today. `grep "s ago"` over `test/integration` and `test/unit` finds no assertion on `[data-plan-source]` text with an age, and `plan-source.browser.test.ts` asserts only the ref, `not pushed` and `behind`. No test asserts the sprint modal's fleet fallback either: `plan-link-click.browser.test.ts:311–343` opens the sprint modal and stops there. So no test changes for the fix to pass. The cost is that the current behaviour shipped untested, and the new tests are the first to pin it.
- `plan-level-row.test.ts` covers `planFileFromFleet` (it passed, 38/38 with the other two files). `AgentList.tsx:564` still uses that function on the Delivery tab, so the slice must keep it and its test unchanged.
- The doc comments that state the fleet source must change in the same slice: `PlanSourceLine.tsx:53–58`, `Board.tsx:151–158`, and the comment at `App.tsx:1592–1603`.

## (a) Problem statement

- **Cited lines check out, with one slip.** `App.tsx:542` (`if (tab !== 'delivery') return;`), `:772` (visibility handler's fleet guard), `:1524`, `:1537` (`planAgeSeconds={fleet?.ageSeconds ?? null}`), `:1597` (`planFileFromFleet(...)`), `PlanSourceLine.tsx:145`, `schema.ts:4285`, `schema.ts:1473` are all right. The slip: "The Planning tab already fetches `/api/board` on its own poll (`load`, `App.tsx:772`)" — the poll is `App.tsx:527-532`; `:771` is the visibility handler's `load()`, and `:772` is the fleet line.
- **A third symptom the plan does not name: "0s ago", frozen.** `buildFleet` computes `ageSeconds = entry.at === null ? 0 : …` (`fleet.ts:7506`). `readRefAge` is the honest twin (`null` when `entry.at === null`, `fleet.ts:7658`), but `App.tsx:1524/1537` pass `ageSeconds`. So an operator who visits Delivery during a cold server's first scan and then returns to Planning reads `Plans read from origin/main · 0s ago` for the rest of the session. The model prints `0s` in the `current` column at every sample from t=29 to t=359. `PlanSourceLine.tsx:54-58` documents the opposite ("Null where no scan has landed … never 0"), so the comment and the wiring disagree today. The plan's rule "never prints `0s ago`" is right; its Motivation should state that the current code breaks it.
- **The cause is named correctly but is one layer short.** The line's age is not "the board's read of the plan sources". `/api/board` reads the ref fresh on every request (`board.ts:2192`, comment at `:2202` "read fresh this call"), so the board's read is always as old as the last poll. What makes the cards stale is how long ago `origin/<default>` was **fetched** — and only the fleet scan fetches it (`plot-fleet-scan.sh:371`). That is why `PlanSourceLine.tsx:54-55` takes the age from the scan: "the scan is what fetches them, so its age dates this too." The plan's sentence "`ageSeconds` … dates a different read from the one the sentence describes" (Motivation, bullet 1) is therefore backwards: the scan age is the closer of the two to the question the sentence asks.

## (b) Approach — what the operator sees at each moment

| Moment | Today | Open Question 1, option "`generatedAt`" | Scan age carried on `/api/board` (`entry.at`, null-aware) |
|---|---|---|---|
| Fresh page, Planning, warm server | no age | `0–29s`, sawtooth | true age of the last scan, ticking |
| Fresh page, cold server, first scan running | no age | **an age** (`5s`, `29s` in the model) for a fetch that has not happened | no age |
| After a Delivery visit, cold server | **`0s ago` forever** | as above | as above |
| After a Delivery visit, warm server | the last Delivery value, frozen | as above | as above |
| Fetch failing for minutes (offline, 503) | frozen value | `29s` max — **looks fresh** | `29s` max — **also looks fresh** (model: shows `29s` at t=269 while the last good fetch is 149 s old) |
| Board server unreachable (poll gap) | frozen value | must decide: tick or freeze | must decide: tick or freeze |
| Server restarted, fleetd running | frozen value | `0s` on first poll | bridge's age (`ensureCache` seeds `entry.at = warm.at`, `fleet.ts:3015`) |
| Server restarted, no fleetd | frozen value | `0s` on first poll | no age until the first scan finishes |
| Older server, newer page | age after a Delivery visit | no age (field absent) | no age (field absent) |

- **Option "`generatedAt`" answers a question nobody asked.** It dates the HTTP response, which the page already knows to within one poll. It is always 0–29 s, so it makes every board look fresh, including a board on a laptop that has been offline for an hour. That is the 2026-08-27 drift (`PlanSourceLine.tsx:7-19`) with a reassuring number beside it. Reject it.
- **Option "time the server last read the plan sources" is the same value** as `generatedAt`, because the read happens per request. It does not need a new field to be wrong.
- **The value to carry is the scan's age from the cache entry `/api/board` already holds.** `discoveryLanes` calls `ensureCache(opts)` on every `/api/board` (`discovery-lanes.ts`, line with `const { issueAnswer, issueAbsence } = ensureCache(opts)`), and that entry's `at` is what `readRefAge` reads. Carrying it is the #2833 pattern exactly: same entry, same request, no host call, no new poll. Carry it as **seconds, computed on the server, `null` when `entry.at === null`** (the `readRefAge` rule, not the `ageSeconds` rule). Seconds rather than a timestamp, because the page's clock and the server's may differ when the board is viewed from another machine; the page adds only "seconds since this payload arrived", as `AgentList.tsx:578-600` already does.
- **Even the scan age overclaims while the fetch fails.** The scan keeps running and `entry.at` keeps moving (`plot-fleet-scan.sh:338-343`, `fleet.ts:2879`); the scan emits `fetch_failed` (`plot-fleet-scan.sh:5279`), but the bridged pulse drops it (live file probe above) and no TypeScript reads it. Fixing that is out of this plan's scope, but the plan must not claim that "Ns ago" answers "how fresh is `<ref>`" — it answers "when did a scan last finish". Name it as a known limit and file it.
- **The tick needs a stated rule, and a precedent exists that points the other way.** `AgentList.tsx:578-600` stops its client clock when `stale` (polls going out, nothing coming back), on the argument that a number the server has not confirmed is false. The Planning tab shows "The cards below are frozen at the last answer" in the same situation (`App.tsx:1498-1507`). For an AGE (not a countdown) ticking on is true — no scan is reaching the operator, so the cards really are getting older — but the plan must choose, say why it differs from `AgentList`, and test it. Either choice is defensible; silence is not.
- **Where the clock lives matters to the operator.** A 1 s `setInterval` in `App` state re-renders `Swimlanes`/`Board` and every card each second. Put the tick inside `PlanSourceLine` (or a small wrapper) so only one line re-renders; `AgentList` keeps its tick local for the same reason.
- **Layering and "every rendered state is a domain property":** the rule "age to print, or nothing" (`null` in → nothing out; elapsed seconds added; never `0` for unknown) belongs in `packages/domain` as the plan says. The server-side half (`entry.at` → seconds or `null`) is one line in `index.ts` or `discoveryLanes`; it should reuse the expression behind `readRefAge` rather than `ageSeconds` so the two cannot drift.
- **Sprint fallback: delete it rather than replace it.** `planFileFromFleet` reads `fleet.rows[].planFile` (`fleet.ts:6369`, from the scan's plans), `fleet.draftPlans` (from `readPlanEstate`: `origin/<default>` plus the working tree, `board.ts:2828-2838`), and idea-branch plans (`fleet.ts:6755`). The board builds its cards from the same three sources: `collectPlanSources` and `collectBranchPlans` over the configured prefixes (`board.ts:950-990`). So whenever both payloads are current, a slug with no card has no fleet file either. The probe shows the real population: 16 sprint slugs name a plan that was renamed or removed. For them, today's click does nothing on a fresh page AND after a Delivery visit. The fleet only names a different answer when it is out of step with the board — a stored payload from an earlier Delivery visit naming a file since renamed (navigation to a dead `/plan/<file>`), or a fleet poll that saw a new plan the board's 30 s poll has not. Both are the inconsistency the issue is about. A new board field that lists draft plans (Open Question 2, second option) would duplicate data the cards already carry.
- **The dead button remains, and the operator sees it.** The plan keeps "a slug that neither source names leaves the modal open". `SprintModal.tsx:177-185` renders such a slug as a button that does nothing on click. The decision "does this member resolve to a card" is a rendered state; make it a domain property (member slug vs. the board's cards) and render an unresolved member as text with a short reason (for example "no plan file on `origin/main`"), the way a bare item already renders as text (`SprintModal.tsx:171-176`).

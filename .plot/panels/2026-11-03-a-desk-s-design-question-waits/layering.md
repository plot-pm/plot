# Layering juror: a-desk-s-design-question-waits

Position: amend

The plan names the right two gaps, but it places both fixes in the wrong layer, and it misses the actual cause of #3048's unanswered question. On `origin/main` the unblocker has no production start: `applyUnblockDecisions` has no caller outside `packages/fleet/test/unit/registryd-tick.test.ts`, and no production code passes the `unblock` world to the tick. A class rule added to `unblockerDue` or `applyUnblockDecisions` changes code that never runs. Part 2 adds a refusal to `approve` for a brief that does not exist at approval time, and it duplicates the panel verdict gate that `/plot-approve` already has.

## Findings

1. **high — The unblocker never runs in production, and this, not a missing class rule, is why #3048's question got no answer.** `registryd.ts:388-394` adds unblock writes only when `options.unblock !== undefined`. `git grep "applyUnblockDecisions\|unblock:"` over `origin/main` `packages/*/src` and `skills` finds only the definition (`registryd.ts:1575`) and its doc references; `registryd-main.ts` names neither. The panel on `2026-11-01-fleetd-s-fixer-and-main-repair` recorded the same fact (`.plot/panels/2026-11-01-fleetd-s-fixer-and-main-repair/seams.md:11,18`: "the unblocker has no production start. Not reachable"). On this machine, `.plot/logs/fleetd.log*` and `fleetd.err` hold zero `unblock` lines, and the answer record holds zero `started` rows for a real desk. The plan's Motivation ("The unblocker (#2901) answers `PLOT-BLOCKED` questions, but it did not answer this one: a choice between two scopes") states a cause the code refutes. The first slice must wire the tick and the applier in `registryd-main.ts` (adapter for `UnblockPorts.run` through `roleCommand`, `record`, `start` = `continueOnDesk`), or the rest of Part 1 is dead code.

2. **high — The answer-or-escalate decision cannot live in `unblockerDue`.** `unblockerDue` (`packages/domain/src/rules/unblocker-due.ts:63-70`) decides whether to START a run, from the marker's author, `deskDead`, `liveFixer` and recorded outcomes. It never sees the question text and it runs before the agent has read anything. Which questions the plan or the code decides is a judgement over prose, so it belongs to the role agent (the charter). The domain's share is narrower and testable: a schema for the run's hand-back (`{ kind: 'answer', text } | { kind: 'escalate', reason }`), a pure rule that maps a parsed hand-back to the record row and to the `continueOnDesk` call or no call, and the refusal for a hand-back that parses as neither. `UnblockPorts.run` (`registryd.ts:1521`) returns `{ ok: true; answer: string }` today, free text with no place for an escalation. The parse belongs in the adapter, the schema in the domain, as `handBackProtocolFor` already does for other roles (`agent-run-sdk.ts:150-151`, cited in `.plot/briefs/role-agents-start-detached.md:30`).

3. **high — The charter forbids the escalation the plan asks for.** `.claude/agents/unblocker.md` (origin/main) says "Never answer 'wait for a person.'" and "still answer the question asked". Part 1 needs the charter to permit a named escalation with a reason. The plan names the charter as a location but does not say that this rule changes. An unattended Sonnet agent that edits only `unblockerDue` leaves the charter in conflict with the new outcome.

4. **high — The escalation recipient already exists; the plan's open question 2 ignores it.** `questionEscalation` (`packages/domain/src/rules/question-escalation.ts:15-29,58-71`) already walks a desk's marker through `listed` (the board's *Waiting on you*) and `notified-N` rungs through the `Notify command`, keyed on the same `(worktree, askedAt)`. It suppresses rungs only for `recordedOutcome === 'started'`; `refused` and `failed` "fall through to the ordinary age-based rungs, unchanged". So an escalation is one new outcome value in `answers.tsv` (for example `escalated <reason>`), written through `AnswerRecordStore.append` (`packages/domain/src/ports/answer-record.ts:70`), and the existing ladder reaches the person. `unblockerDue`'s `already-recorded` (`unblocker-due.ts:68`) then stops a second run. No new recipient, store or port is needed. Building a second notification path would put the same decision in two places.

5. **medium — A failed run records nothing and retries every tick, which contradicts "decides or records".** `applyUnblockDecisions` drops a failed run without a row (`registryd.ts:1558-1561`, code at `:1582-1585`), so the next tick starts the unblocker again. Under Part 1's own rule ("a run that produces neither is a defect") the plan must name what a failed run records and the bound on retries. The fixer plan's panel set the precedent (one failed start per head, then hold).

6. **medium — The answer record cannot tell the unblocker from a person.** `continuation.ts:1502` writes `author: input.author ?? 'unblocker'` for every continuation that omits an author, so a person's or the master agent's answer reads as the unblocker's. On this machine every real-desk row reads `unblocker answered`, although the fleetd applier writes `started` and never ran. The plan's "recorded outcome" claims rest on this record. Part 1 must either make the author mandatory at the controller entrance or state that the record cannot distinguish them.

7. **high — Part 2 has no subject at approval, and its condition is not objective.** The plan's own open question 4 says a brief is written after approval. Briefs are booked by `plot-brief-book.mjs` / `brief-booking.ts` at dispatch, after `approve`. The `approve` workflow (`packages/domain/src/workflows/approve.ts:197`) is a pure function over readings; a claim checker needs prose extraction (judgement, so an agent) and a grep or test run (an adapter), and "the callers' tests do not move" is a prediction about a diff not yet written, refutable only by doing the work. That fails the *Gates Over Rules* test the plan invokes. A refusal added to `approve` would also need every entrance (`plot-approve.mjs`, `POST /api/approve`, `plot-approve.sh`, the skill) to supply a new reading.

8. **medium — Part 2 duplicates a gate that exists.** `/plot-approve` already holds the panel verdict gate (`skills/plot-approve/SKILL.md:173-224`, section 2c): a juror's `reject` refuses the approval. The plan-questioning mechanism (`plot-panel`, delivered as `a-plan-is-questioned-before-it-is-approved`) is where an agent reads a plan's claims against the code, and this panel is doing so now. The layering-correct home for "a claim the code refutes" is either a panel lens at approval (over the plan's claims) or a self-check in the brief writer at brief time (over the brief's claims), not a new domain refusal in `approve`.

9. **low — Board impact note.** The HTML comment says an escalation reason "may add a field to the answer record". `AnswerRecord.outcome` is already a free string (`answer-record.ts:15`); an `escalated <reason>` outcome needs no new column. A new column changes the TSV shape every reader parses.

## Required amendments

- A1. Rewrite the Motivation's cause: the unblocker has no production start on `origin/main` (finding 1). Add a first slice, or make it the first part of the unblocker slice, that wires `options.unblock` and `applyUnblockDecisions` in `registryd-main.ts` through an adapter for `UnblockPorts`. Name the test: a tick with a production-built world and an untagged marker on a waiting desk yields one `unblock` write and one `run` call.
- A2. Move the class rule out of `unblockerDue`. State the split: the charter (`.claude/agents/unblocker.md`) holds the judgement and drops "Never answer 'wait for a person'" in favour of "answer, or escalate with one named reason"; the domain holds a hand-back schema and a pure rule from hand-back to record row and continue call; the adapter parses the run's output; `applyUnblockDecisions` applies the decision.
- A3. Resolve open question 2 in the plan: an escalation is an `escalated <reason>` outcome appended through `AnswerRecordStore`, and the existing `questionEscalation` ladder (board `listed`, `Notify command` rungs) is the recipient. Add a test that an `escalated` row lets `questionEscalation` return a new `notified-1` rung where a `started` row returns none.
- A4. State what a failed or unparseable run records and the retry bound (finding 5).
- A5. Make the record's author honest at the controller entrance, or state the limit (finding 6).
- A6. Replace Part 2's `/plot-approve` refusal. Either (a) add a code-claims lens to the existing panel at approval, reading the plan's claims, or (b) add a self-check to the brief writer that runs the greps a brief's claims name before it books the brief, and writes the refuted claim into the brief. Drop the claim that this is a gate in `approve`.
- A7. Answer open question 5 with a decision or move it to Notes; an unattended agent cannot choose between "the unblocker answers scope questions" and "`/plot-reslice` prevents them".

# Layering juror: pr-review accepts a plot/review status from any writer

Position: amend

The defect is real and the plan's one layering sentence ("the identity comparison is a rule the domain owns, and `pr-review` stays a reading that reports the writer") points the right way. The plan does not carry that sentence through: it names no port field, no domain rule, no way for the `Review app` id to reach the domain, and it misses two of the consumers and the whole index path. An unattended Sonnet agent following the Slice line ("`pr-review` keeps a `plot/review` status only from the `Review app` identity") builds the check in jq inside `plot-host.sh`, which is the placement the Approach rejects.

## Findings

1. **The Slice line contradicts the Approach.** The Approach says `pr-review` reports the writer and the domain compares. The Slice says `pr-review` "keeps a status only from the `Review app` identity and reports any other writer as a named refusal". That puts the rule and the config read in the adapter script (`plot-host.sh:4395`, one jq line), against "No domain-specific code or behaviour lives outside the domain" and against the `the-shell-shrinks-into-the-domain` direction. It also forces `plot-host.sh` to read `Review app` and resolve it to a login in bash, which adds shell lines that `scripts/check-shell-lines.sh` then demands back.

2. **The writer is cheap to report and the reading has room for it.** Measured on PR #3067's head: the REST statuses endpoint returns `creator.login = "plot-review[bot]"`, `creator.type = "Bot"`, `creator.id = 342578638` for both `plot/review` statuses. Adding `writer: ($m.creator.login // "")` to the existing jq object at `plot-host.sh:4395` costs zero shell lines. `PrReviewReading` (`packages/domain/src/ports/host.ts:150`) gains one field; `host-shell.ts:522` decodes it with `asJson`; `host-fixture.ts:72` gains it.

3. **The `Review app` key holds an id, and a status carries no id.** Statuses carry no app or integration id; only `creator`. The ruleset names `integration_id: 5317669` (read via `gh api repos/{owner}/{repo}/rules/branches/main`), which does not give a login either. The id-to-login mapping needs a source, and the plan leaves it open (Open Question 1). The repo already holds one: `plot-github-app.mjs` exports `resolveApp`, `appJwt` and `call` (lines 45, 67, 74); `GET /app` with the App JWT returns the App's `slug`, and the bot login is `<slug>[bot]`. That is a connector call with credentials, so it belongs in the host adapter, not in the domain and not in jq. Hardcoding `plot-review[bot]` breaks Project-Agnostic Design.

4. **`release-approve` is a second consumer the plan does not name.** `packages/domain/src/workflows/release-approve.ts:92` accepts `review.state === 'success'` exactly as `merge.ts:210` does, and it reaches `mergeAt` afterwards. A fix in `merge` alone leaves `release-approve`'s own `review-missing` gate reading a forged success, then `mergeAt` refuses it with a different reason than the release gate reported.

5. **The plan's claim about the slice-PR rule is false.** The plan says the slice-PR rule reads "the answer of `pr-review`". It does not. `slicePrNext` (`packages/domain/src/rules/slice-pr-next.ts:181`, `:227`, `:324`) and `release-prepare.ts:199` read `plotReview` from the PR index. The index is filled by `pr-list --rich` from `statusCheckRollup` (`plot-host.sh:4803`), not by `pr-review`. Measured: the rollup's `plot/review` entry carries the keys `__typename, context, startedAt, state, targetUrl` and no creator. So the index cannot carry a writer through `gh --json`, and a forged newest `success` reads as `success` in the index after this fix too.

6. **That gap turns a refusal into a stall.** With a forged `success` in the index: the review arm answers `status-written`/`not-passed` paths as if the review passed, so no re-review starts; the merge arm selects the PR every pass; `mergeAt` (after the fix) refuses every pass. `reviewReaskPrNumbers` (`rules/pr-index.ts:343`) re-asks only absent/pending/older-sha rows, so it never corrects a `success` row. The "Decision Reads The Index" bound ("a stale row costs one refused start") does not hold here: it costs one refused start per pass, forever, and ends in a person. That works against the sprint goal.

7. **Other `prReview` consumers need a stated answer.** `packages/board/src/server/entry/review.ts:303` and `:498` read `prReview` for newest-pending-wins; a foreign `pending` with a forged `run <id>` description can steer that rule. `review-bypass.ts:62` audits merged PRs; PRs merged before `Review required since` legitimately carry no App status. The plan must say for each whether it reads the trusted status, the newest status, or both.

8. **Bitbucket cannot report a writer.** `bitbucketReview` (`packages/domain/src/rules/bitbucket-pr-reading.ts:128`) reads build statuses that keep one status per `key` and replace it on a later write (its own header says so). The build status object carries no creator. So a forged write overwrites the dedicated account's status, and no reading can tell. The arm must report the writer as unknown, and the domain's answer to an unknown writer is a decision (finding below), not something the arm "states in its header".

9. **`bypass` has the same hole.** `pr-review` sets `bypass` from any comment that starts `review-bypass:` (`plot-host.sh:4395`, `bitbucket-pr-reading.ts:140`), whoever wrote it. `merge` does not read `bypass`, so it is outside this defect, but the plan should name it as out of scope so the slice does not half-fix it.

## Amendments required

1. Rewrite the Slice line to match the Approach: `pr-review` reports, per `plot/review` status, its state, description, time and writer login; it decides nothing and reads no config. Prefer routing the GitHub arm's raw statuses through a domain decode called from a bundle, the way the Bitbucket arm calls `bitbucketReview` through `plot-jenkins-pr-checks.mjs review`; at minimum add the writer inside the existing jq expression with no new shell lines.
2. Name the port change: `PrReviewReading` carries the writer of each reported status (or of the newest status plus the newest trusted one), with `''` where the host holds none, and `host-fixture.ts` follows.
3. Name the trusted identity's path: a host-adapter operation (for example `Host.reviewWriter(): PortResult<string>`) resolves `Review app` through `plot-github-app.mjs` `GET /app` to `<slug>[bot]`, and answers `unaskable` where the key is absent, unreadable or the call fails. The value enters `merge` and `releaseApprove` as a reading value, consistent with "readings as values".
4. Name one domain rule (for example `trustedReview(reading, writer)` in `packages/domain/src/rules/`) that both `merge.ts:210` and `release-approve.ts:92` call, and name the new refusals in both refusal unions (for example `review-foreign-writer`, `review-writer-unknown`).
5. State the index path and its bound: the PR index cannot carry the writer, so say how a forged index `success` ends. Options: the merge refusal for a foreign writer marks the row for re-ask or re-review, or `pr-list --rich` drops to `pending` where the rollup's newest `plot/review` cannot be attributed. Correct the Motivation sentence that says the slice-PR rule reads `pr-review`.
6. Name every `prReview` consumer (`merge.ts:366`, `release-approve.ts:132`, `review.ts:303`, `review.ts:498`, `review-bypass.ts:62`) and the reading each one uses.
7. Name the tests: `packages/domain/test/workflows-merge.test.ts` and `workflows-release-approve.test.ts` refuse a `success` from a foreign writer and accept the trusted one; `test/reconcile/host-pr-review.test.mjs` asserts the GitHub arm emits the writer from a stubbed statuses payload where a foreign `success` is newer than an App `failure`; `packages/domain/test/host-shell.test.ts` decodes the new field.
8. Scope `review-bypass:` comment authorship out by name.

## Decisions that need a person

- **Semantics of a foreign status.** Either the newest status from the trusted writer decides and foreign statuses are ignored (the ruleset's own semantics, and no stall from an accidental operator write), or any newer foreign status refuses fail-closed (names the forgery, but stalls the PR until someone clears it). I lean to the first, with the foreign writer named in the detail, because it matches what GitHub enforces.
- **No `Review app` key, or an unresolvable one.** Keep today's behaviour with a one-line notice, or refuse `review-writer-unknown`. Refusing breaks repos that never adopted the App.
- **Bitbucket's unknown writer.** Trust the status as today (and document that Bitbucket offers no writer), or refuse. No reading can distinguish the writers there.
- **A cheaper mitigation exists in config.** Declaring a `Merger app` makes `pr-merge` run as an App without the Admin bypass (`plot-host.sh` pr-merge arm, #1730), so the ruleset's integration-id check holds again for the merge itself. It does not fix Plot's own reading, but it closes the admin-bypass half of the issue without code.

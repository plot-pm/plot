# Layering juror — two-test-teardowns-turn-main-red

Position: amend

The plan puts both fixes in the test layer, and for slice 1 that is the wrong layer. The `plot-plan-store-ref-*` leak is a production defect in a domain adapter. No test starts the spawn that `parseBlobs` awaits: the board server does, in its own process, since `0846ab0e1` ("scanOnce walks the plan in process", 2026-11-01 00:15). The tests that stop that server already wait for its whole process tree to exit (`helpers.mjs` `kill()`, which uses `untilGoneSync`). The server ends by SIGTERM in the middle of a parse, and the `finally` at `plan-store-ref.ts:149` never runs. The board already solved this exact shape for its own stage directories on 2026-10-15 (`stage-dirs.ts`, #1802), and `planStoreRef` does not use that mechanism. The domain cannot import it, because it lives in `packages/board`. A test-side wait cannot fix this, and it would hide a leak that also reaches an operator's real TMPDIR each time `node --watch` restarts `pnpm board` during a scan. Slice 2 belongs in the test, which the plan has right, but it waits on the wrong process. The process that writes last into the desk is the reporter subshell, not the agent, and the reporter has no pid file.

## Findings

1. **high: slice 1 fixes the wrong layer.** Evidence: `packages/domain/src/adapters/plan-store/plan-store-ref.ts:113` uses a raw `mkdtempSync(join(tmpdir(), 'plot-plan-store-ref-'))` and cleans up only in the `finally` at `:149`. `packages/board/src/server/stage-dirs.ts` (from `fb75fdd31`, #1802) records stage directories and removes them on `exit`/SIGTERM/SIGINT/SIGHUP. Its header names the identical failure: "CI left a `plot-board-plans-` directory … after a test stopped its server mid-build". `board.ts:2337` uses it. `index.ts:1055` installs `removeStageDirsOnExit()`. `fleet.ts:2936` hands `planStoreRef` to `scanOnce`'s walk inside the board server, so the server's own SIGTERM handler runs, removes only the directories it knows about, and re-raises the signal. `helpers.mjs:269-288` already stops the server and waits for its tree to die, so "a test waits for every spawn it starts" is already true and changes nothing. Checked: I read all four files at `origin/main` and ran `git log -S` for when the in-process walk landed.
2. **high: the leak is deterministic under SIGTERM, not a rare race.** I reproduced it in my scratch directory with a script that has the same shape as `parseBlobs` (mkdtemp, then await a child, with removal in `finally`) and sent SIGTERM after staging. The directory stayed in 5 of 5 runs. With a `stage-dirs`-style registered SIGTERM handler, 0 of 5 stayed (`scratchpad/j3008/shape.mjs`). What varies is only whether the test's stop lands during a parse. That is a deterministic proof a slice can use: start the server (or the scan-walk entry) with a parser that blocks, send SIGTERM after staging, and assert that no `plot-plan-store-ref-*` remains.
3. **high: the plan undercounts the failure. It recurred on 7 of 9 failed main runs, not 2.** `gh run list --branch main` since 2026-11-01 11:00 shows 8 failures against 36 successes. The board-integration jobs of runs 41303723233, 41304794037, 41310373655, 41314420918 and 41319588779 each left one `plot-plan-store-ref-*` entry (`FUn8gk`, `VJpNIs`, `8WdwDK`, `Qvxj5i`, `i0BrUR`), in addition to the two runs the plan names. The first failure is about 11.5 h after `0846ab0e1`. "The next commit ran green, so it is a race" understates a defect that fails most red runs today.
4. **medium: the leaking test can be named to a window, and it is a server-stopping test on `tiny-garden`.** The 9 staged files are exactly the 9 plans under `packages/board/test/fixtures/tiny-garden/docs/plans/`. Run 41322195284 staged at 15:44:32.84, inside `tiny-garden.browser.test.ts` (15:44:24.9–15:44:36.9), whose second describe calls `startServer(FIXTURE)` and `server?.kill()` (`tiny-garden.browser.test.ts:348,354`). Run 41323069974 staged at 15:59:24.998, inside `dead-fetch.browser.test.ts` (36 s, ending 15:59:29.4), which uses the same `startServer`/`kill()` pair. So no single test is guilty. Every real-board test on that fixture can trigger it. This also supports finding 1: the plan's Open Question cannot be closed by naming one test.
5. **medium: the other production entries that reach `planStoreRef` have the same exposure.** `packages/board/src/server/entry/scan-walk.ts:76` (`plot-scan-walk.mjs`, spawned by `plot-fleet-scan.sh`) installs no signal handler at all, so a bounded-run kill or a tree SIGTERM leaks there too. `registryd-main.ts:1317,1364,2819` (fleetd) ends within the tick on SIGTERM (`:2864`), so its `finally` runs and it is the one safe caller. `refs-git.ts:400` and `adapters/index.ts:22` are further callers the plan omits. The plan names only `fleet.ts` and `scan-walk.ts`.
6. **medium: slice 2 waits on the wrong process.** `continuation.ts:1394-1398` starts two detached subshells that `init` re-parents: the agent, whose pid goes to `.plot-worker.pid`, and a reporter sibling. The reporter polls `kill -0` every 50 ms and then appends `.plot-worker.monitor.worker.jsonl` into the desk (`reporterTail`, `:1376`). The test passes `scriptsDir: '/s'`, so the `[ -f "$PLOT_SCRIPT_DIR/…" ]` guard fails, `wd` stays the worktree, and the reporter writes into the desk the test removes. With `Worker command` = `true`, the agent exits at once, so a wait on the agent's pid returns before the reporter's last write. The writer the brief asks about is the reporter subshell. A correct end condition is the reporter's own final write: wait for the `WorkerMonitor` line in `.plot-worker.monitor.worker.jsonl` (bounded), then remove the desk with `removeTree`. The production design (detached and answered at once, `:1251-1262`) is intended and must stay.
7. **medium: a sibling case has the same latent race, and the CI gate does not see either case.** `continuation.test.ts:169-175` (`records the spawned pid's own start time`) SIGKILLs the agent and waits for it to die. The reporter then writes `137` and the jsonl line after it notices, and the `afterEach` races that write. The CI step *A teardown does not race a child* (`ci.yml:1736-1753`) greps only `fs\.rmSync\s*\(…recursive`. `continuation.test.ts` imports `rmSync` by name (`:3`), so its four `rmSync(desk, { recursive: true, force: true })` calls (`:74,107,174,219`) do not count. A grep for a bare `rmSync(…recursive` finds 94 sites in 35 files under `packages/{board,fleet}/test` (64 in fleet) that the gate cannot see. `packages/fleet/test/rm-tree.mjs` (`removeTree`) exists for exactly this, and the test does not use it.
8. **low: the plan cites the wrong precedent and mislabels its own scope.** It cites `2026-09-01-a-teardown-does-not-fail-a-suite`, a test-only retry. The direct precedent is #1802 (`fb75fdd31`), which fixed the production side, the server's stage directories on signal, for the same symptom. "Type: feature" contradicts the issue and the `bug/` slice names. "Board impact: none" and a test-only changelog no longer hold once slice 1 changes `packages/domain` and `packages/board/src`, and that change needs a changeset.
9. **low: the plan does not contradict CLAUDE.md or the manifesto as written, but the amended slice 1 must place each part correctly.** The registry is an adapter concern (it touches fs, inside `packages/domain/src/adapters/`, which the purity gate allows). Installing process-wide signal listeners is an entry concern (`board/src/server/index.ts`, `entry/scan-walk.ts`, and optionally `registryd-main.ts`), and it is not done inside the adapter. Moving `stage-dirs.ts` into the domain must leave one implementation and no copy. New code is arrow functions, which the existing file already uses.

## Amendments I require

- A1. Re-scope slice 1 to production. Move the stage-directory registry from `packages/board/src/server/stage-dirs.ts` into `packages/domain/src/adapters/` (one implementation). `parseBlobs` creates and removes its directory through it. The board server keeps calling the install function from `index.ts`, and `entry/scan-walk.ts` installs it as well. Rename the slice, for example `bug/the-ref-plan-store-stages-through-the-registry`, and state that no test teardown changes.
- A2. Give slice 1 a deterministic proof: a unit test that starts a child process running `planStoreRef(...).readPlansAt` against a parser stub that blocks, sends SIGTERM after the stage directory exists, and asserts that the child's private TMPDIR holds no `plot-plan-store-ref-*`. It fails on `origin/main` and passes after the fix. Also add a unit assertion that the registry is empty after a normal parse and after a parse that fails.
- A3. Correct the Motivation: there are 7 occurrences on 2026-11-01 (list the five extra runs), the onset follows `0846ab0e1`, the full caller list (fleet.ts, scan-walk.ts, registryd-main.ts, refs-git.ts), and the fact that the leaking process is the board server or `plot-scan-walk.mjs` ended by SIGTERM, not a test spawn.
- A4. Re-scope slice 2's end condition: the `afterEach` waits, with a bound, for the reporter's `WorkerMonitor` line in `.plot-worker.monitor.worker.jsonl` (the last write any detached process makes into the desk), and then removes the desk with `removeTree` from `packages/fleet/test/rm-tree.mjs`. Apply this to both real-spawn cases (`:71-102` and `:154-212`), not only the one that failed. The proof is a test that removes the desk immediately after `started` and observes the reporter's write. Run it in a loop, for example 200 rounds with `Worker command` = `true`, so that it fails on `origin/main`.
- A5. Fix the metadata: `Type: bug`, a Board impact line that names the `packages/board/src/server` change, a changelog entry for the production fix, and #1802 cited as the precedent.

## Optional

- O1. Tighten the CI step *A teardown does not race a child* so that it also counts a named-import `rmSync(…recursive`. This means a ratchet set at today's measured count, which drops as files move to `rmTree`/`removeTree`. It is a separate slice or plan, because the count is 94 and the plan should not convert those sites.
- O2. Give the detached reporter a pid file (`.plot-worker.reporter.pid`), so that tests and `removeTree` can wait on it by pid instead of by output. This is a production change and needs its own plan.
- O3. Give fleetd the same install call even though its tick-bounded stop already lets the `finally` run. Then a SIGKILL after a stop timeout is the only remaining way to leak.

## Open questions

- "The leaking test for slice 1 is not yet named — identifying it is part of that slice's work." Answer: close it now and do not make it slice work. No single test leaks. Any real-board test on `tiny-garden` that stops its server during a scan can leak, and the two named runs fall in `tiny-garden.browser.test.ts` and `dead-fetch.browser.test.ts`. The fix therefore does not depend on a name. It belongs in the adapter and the entries (A1), and the proof is a SIGTERM reproduction (A2), not a test that was named.

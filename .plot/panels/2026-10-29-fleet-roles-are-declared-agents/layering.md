## (a) Problem statement

1. **Wrong fact: two of the three controllers have no unattended refusal.** The plan's Motivation says "`continue`, `restart`, `merge` refuse every unattended caller". Measured:
   - `merge`: `MergeRefusal` (`workflows/merge.ts:11-19`) has no `unattended` reason, and `MergeInput` has no caller field. The probe merged with no caller stated. `grep -i unattend` over `workflows/merge.ts`, `board/src/server/entry/merge.ts` and `entry/main.ts` returns nothing.
   - `continue`: `ContinueRefusal` carries `'unattended'` only for restart (`continuation.ts:162`: "`restart`: the caller runs unattended."). No `continue` path reads `PLOT_UNATTENDED`.
   - `restart`: refuses, in the domain (`dispatch-verbs.ts:194-198`), from a boolean reading the entry fills from the environment (`fleet/src/server/entry/restart-command.ts:89`, `board/src/server/restart.ts:68`).
   Sibling #2914 states the same fact correctly ("The merge controller has no unattended caller today").
2. **Wrong fact: `release` does not refuse an unattended caller today.** `release.ts:21` states the estate's principle: "`PLOT_UNATTENDED` answers *may I ask?* and never *may I proceed?*". `release.ts:239-245` turns the Should-Have prompt into a warning when unattended. The probe got `decided` with `unattended: true`. The plan's "release still refuses every unattended caller" describes a refusal that does not exist; building it is new behaviour against a stated domain principle. The design (line 144, "stays refused") carries the same error, so this is a fact the design missed, and the plan may correct it.
3. **Incomplete fact: the port already takes a role.** `AgentRunRequest.role` exists (`ports/agent-run.ts:47`, "`worker`, or a board role such as `idea` or `brief`"), and the reviewer already passes `role: 'reviewer'` (`review.ts:451`). The SDK adapter already branches on it (`agent-run-sdk.ts:396`, `handBackProtocolFor(request.role)`). The slice does not add a parameter; it gives an existing field a second meaning.
4. **Omitted adapter.** The plan names only `agentRunCommand`. A second adapter of the same port, `agentRunSdk`, runs the worker loop (`fleet/src/server/entry/worker-loop.ts:2199`) and the board's SDK roles (`board/src/server/sdk-runner.ts:57`). "One runner" in the design means one port; it has two adapters today.

## (b) Approach, read against the layering rules

1. **`--agent <role>` in `agentRunCommand` breaks that adapter's contract.** The port says "NAMES NO HARNESS-SPECIFIC OPTION" (`ports/agent-run.ts:30`). `agentRunCommand` runs whatever fragment the project configures and states it has "no CLI flag vocabulary" to inject a model with (`agent-run-command.ts:45-47`). Appending `--agent` there breaks every non-`claude` fragment and every existing role (`worker`, `idea`, `brief`) that has no definition. The decision "which fragment starts role R" is a pure function of readings, and the estate already has one: `reviewerCommand` (`rules/review-verdict.ts:157`) builds the reviewer's fragment in the domain and is unit-tested. The slice should add `--agent <role>` in a domain rule of that kind (one `roleCommand(role, charter, declared)` per declared role), and leave `agentRunCommand` unchanged. The SDK adapter then translates the same reading into its own option.
2. **Reading the definition from the reviewed tree undoes the reviewer's trust boundary.** `reviewerCommand` passes `--setting-sources user` "so no hook or permission rule from the reviewed tree applies" (`review-verdict.ts:144-146`), and the reviewer runs in a detached worktree at the PR's head (`review.ts:42-45`). A `.claude/agents/reviewer.md` read in that worktree is the PR's own version: a PR can change the reviewer's hooks, tools and prompt and then review itself. The fixer has the same exposure on the PR's branch. The definition must come from a tree the PR does not control (the default branch or the plugin's shipped copy), for example through `--agents <file>`, which `claude --help` (2.1.312) lists for `--print`. Whether `--agent` resolves project agents at all under `--setting-sources user` is not stated in the help; slice 1 must measure it.
3. **The caller identity is a domain reading, and the plan does not say so.** The plan says the controllers "read" it. Under the layering rule, the entry reads the environment and the domain rule receives a value. The shape that fits `restartWorker` is a widened reading (`caller: 'person' | 'fleetd' | 'unattended'`) instead of `unattended: boolean`, with the refusal and its lift both decided in `dispatch-verbs.ts`. Where the identity is an environment variable that a gate also reads, `SPAWN_CONTRACT` must rise by one in the same change (`rules/spawn-contract.ts:15-24`, enforced by `test/reconcile/spawn-contract-gate.test.mjs`). The plan names neither.
4. **For `merge` and `continue`, "lift" means "add a refusal".** Since neither refuses today (a.1), the slice either adds a new refusal for every unattended caller except fleetd (which changes what every desk worker and every agent calling `plot-ask.mjs merge` may do today) or does nothing for them. The plan must choose and name the callers that the new refusal stops. I found no evidence that any unattended caller merges today, but I did not search the transcripts.
5. **A Decision Reads The Index.** This plan adds no index-reading decision, which is right for its scope. One constraint must be written down for the restart lift: `restartWorker` reads the branch's PR from the host (`RestartReadings.pr`, `dispatch-verbs.ts:131`) and refuses `reached-review`. A restart under the fleetd identity is a write that replaces a desk's worker, so that reading must stay a fresh host answer and must never be served from the PR index.
6. **Shell ratchet.** `check-shell-lines.sh` counts `.sh` under `skills/` only. Hooks under the repo's `.claude/agents/` are not counted, but the copies that `/plot-init` ships from `skills/` are. The hooks should call the existing `board/plot-gate.mjs` bundle with a new arm (the shape `plot-controller-gate.sh` already uses: a 19-line launcher), and the decisions should be domain rules beside `rules/controller-gate.ts`, not new hook scripts.
7. **`/plot-init` as skill prose regresses a settled lesson.** `rules/adoption.ts` (header) moved adoption's writes out of skill prose on 2026-09-09 because a hand write had "no diff of a script, no test, no PR, and no rule that could have fired". Providing four files is an adoption write; it belongs in `adoption.ts` as a decision and in the performer as the write.
8. **Two sources of the reviewer's model.** The charter names `"model": "opus"` (`.plot/charters/reviewer.json`) and `reviewerCommand` passes it as `--model`. A `reviewer.md` with `model:` is a second answer. The plan must say which one wins; the CLI flag most likely overrides the definition, which makes the definition's field inert.

## (c) Slices

- The cut is mostly right. Order matters: **Definitions** must land before **Runner**, because a runner that starts `--agent reviewer` with no `reviewer.md` on main breaks the existing reviewer, which `plot/review` requires on every PR. Add `<!-- waits: feature/role-agent-definitions -->` to the runner slice, or make the runner add `--agent` only when the definition is present on the default branch.
- **Caller identity** has no caller inside this plan: nothing here starts a role with the identity set. That is the `setSprintState` shape this estate measured (nine refusals, zero callers). Either keep the slice and name its first caller (#2915's restart), or move the lift into the plan that first calls it. Note the cross-plan inconsistency: #2914 says it waits on **#2900** for the identity; #2913 and #2915 say **#2898**.
- The `release` refusal is not a lift; it is a new refusal (a.2). It conflicts with sibling #2911, whose fleet-run sweep (step 4, `/api/release`) is an unattended release. Move the `release` decision to #2911, where the person's approval can be the reading that permits it.

## (d) Open questions

1. *Caller identity: environment variable, flag or signed marker?* An environment variable, set only in `AgentRunRequest.env` for the role run and read by the entry into a domain reading. Reasons: the estate's precedent is `PLOT_MAIN_CHECKOUT_WRITER` (`rules/main-checkout-write.ts:24-35`), and on one machine under one user no choice stops a determined agent (a marker file in `.plot/state/` is as readable as an environment). Accidental forgery is what a gate can stop: a `plot-gate.mjs` arm can refuse a Bash command that sets the variable by hand. Two conditions: bump `SPAWN_CONTRACT`, and make sure that desk workers fleetd starts do not inherit the variable. `agentRunCommand` merges `request.env` over the inherited environment (`agent-run-command.ts:68`) and clears only `PLOT_REPO_ROOT` (:65), so fleetd must not hold the variable in its own environment.
2. *Hooks for "never join lines" and "never commit built bundles"?* Neither needs a new hook. Joining lines is already neutralised: the ratchet counts commands, not lines, "so joining statements never lowers it" (`check-shell-lines.sh:10-12`). Built bundles are gated twice: `skills/plot/scripts/plot-bundle-commit-gate.sh` at commit and `scripts/check-no-bundle-diff.sh` in CI. "Never edit a gate or the CI ratchet" can be checked by path (`scripts/check-*.sh`, `skills/plot/scripts/*-gate.sh`, `.github/workflows/ci.yml`), and it is the one rule that should get a `PreToolUse` arm.
3. *Copy or template?* The estate copies: `/plot-init` copies `skills/plot/templates/plan.md` to `.plot/templates/plan.md` (`SKILL.md:568`). Drift is a fact either way. A domain check in `adoption.ts` that compares the adopter's copy with the shipped one would make the drift visible.
4. New questions the plan should carry:
   - Which tree supplies the definition the reviewer and the fixer run with: the PR's tree or the default branch? (b.2)
   - Does `claude -p --agent X` resolve `.claude/agents/X.md` under `--setting-sources user`, and what does it do for an undeclared `X`? Measure it before slice 1.
   - Does `agentRunSdk` take the role definition, and through which SDK option? (a.4)
   - Do `isolation: worktree` and `memory: local` apply to a top-level `--agent` session, or only to a subagent spawned through the Agent tool?
   - For `merge` and `continue`: add a refusal, or leave them open? (b.4)

Extend `review-verdict` tests so that `reviewerCommand` keeps `--setting-sources user`. Plus one adapter test that `agentRunCommand`'s argv is unchanged.

One test per hook arm through `plot-gate.mjs`, with the decision unit-tested in the domain.

A test that `release` with no person's approval reading refuses, if the plan keeps that decision. The `spawn-contract-gate` test after the bump.
- **Adoption:** an `adoption.ts` unit test that an adopting repository gets the four files, and a test that an existing differing copy is reported rather than overwritten.

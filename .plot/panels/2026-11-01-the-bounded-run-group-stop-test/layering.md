# Layering juror — the bounded-run group-stop test

Position: amend

The defect is in `boundedRunProcess` and not in the test. A deterministic probe against the real adapter at `origin/main` shows the mechanism. When the prompt's exit and the caller's `SIGTERM` reach the caller's event loop in the same libuv signal batch, and the child-exit message comes first, `finish()` removes the last `SIGTERM` listener. Node then stops the signal watcher, libuv drops the queued `SIGTERM`, and the caller lives on. A group stop is exactly the case where both arrive together, because the prompt gets the same `SIGTERM`. The plan's slice only rewords the failure (Required behaviour 2) and leaves `main` able to go red. It also files the real fix under "its own plan" and names the cause "not yet measured" when one probe measures it. The plan needs an adapter slice, a deterministic regression test, and a corrected cause list before approval.

## Findings

1. **high — the wrapper really survives, and `boundedRunProcess` causes it.** Evidence: `packages/domain/src/adapters/bounded-run/bounded-run-process.ts:137` adds `exitOnSignal` for SIGTERM/SIGINT/SIGHUP. `:139-144` (`finish`) removes those listeners on the child's `close`. `:156` runs `finish` on `close`, which Node emits synchronously inside the child's exit callback because stdio is `['ignore', out, out]`, with no pipes. What I checked: a probe (`/private/tmp/claude-501/-Users-jwloka-Quatico-Agentic-Tools-plot/ca0ab00d-98d3-4ca8-8a1b-8a43a4eda657/scratchpad/layering-exp/race-probe.mjs`) imports the real adapter, starts `sleep 30` through `boundedRun.run`, and busy-blocks the main thread for 1 s. During the block it delivers the child's death and the caller's `SIGTERM`. Results:
    - Linux (`node:26`, v26.13.0, docker): child death first gives `SURVIVED` 2 of 2. `SIGTERM` first gives exit 143 2 of 2.
    - macOS (v26.13.0): `SURVIVED` in both orders.
    - Controls (`race-control.mjs`): `SIGTERM` alone, idle or busy, gives exit 143 on both platforms. A caller with its own `process.once('SIGTERM')` gives exit 143.
2. **high — the plan's slice cannot stop `main` going red, and a test-side fix that made the test pass would hide the defect.** Evidence: the plan's Approach ("The fix for cause 3 is in `boundedRun` and needs its own plan") and its single slice. If the signal is lost, the wrapper's `exit` event never fires. The new wait then fails with a new message, at the same rate. Any change that turns the test green without an adapter change (a longer bound, a `SIGKILL` fallback, a second signal, accepting a live wrapper) masks a real dropped-stop defect in the adapter that the test exists to guard (`bounded-run-group-stop.test.ts:1-11`).
3. **medium — the cause list is wrong in two places.** (a) "none yet measured": finding 1 measures it. (b) Cause 1, the zombie wrapper: `kill(pid, 0)` does succeed on a zombie, but `waitForExit` (`test:49-56`) polls through `setTimeout` on the same event loop that reaps the wrapper's `SIGCHLD`. A zombie cannot persist through 100 polls over 5 s while that loop runs. This point is reasoning, not a measurement. (c) Cause 2: `killTreeSync` (`bounded-run-process.ts:54-70`) runs about 3 `pgrep` calls. 5 s is not credible for that, and the prompt and grandchild were gone in the same run (only line 140 failed, `CI log 124912486260`).
4. **medium — the stand-in is not a faithful model of the production caller, and the plan does not say so.** Evidence: `packages/fleet/src/server/entry/worker-loop.ts:2013-2019` (`onStop`, called at `:2508`) adds its own `once` listeners for the same three signals. A caller with its own listener keeps the signal watcher alive after `finish()`, so the worker loop does not lose the stop (control `own-listener` exits 143). `bounded-run-group-standin.mjs:57-64` adds no listener of its own, so the defect shows in the test and not in the worker loop. The plan must state this. Other `boundedRunProcess` callers (`packages/board/src/server/entry/review.ts:573`, `packages/fleet/src/shared/agent-run-for.ts:83`, `packages/fleet/src/shared/auto-fixer.ts:27`) depend on whether their host process adds its own listener. I did not check that.
5. **medium — #2380 is probably the same defect, misread as a timeout.** Evidence: `docs/plans/2026-10-23-bounded-run-group-stop-test-times.md`, Motivation. Before #2390 the test ran under vitest's 5000 ms default, and `waitForExit` also gives up at 5000 ms. A lost `SIGTERM` therefore showed as `Test timed out in 5000ms`. #2390 raised the outer bound to `TEST_TIMEOUT_MS = 20_000` (`test:24`), and the same event now shows as the inner assertion. This is inference: the #2380 runs were not re-read here. If it holds, the plan's statement "This failure is a different assertion" is true but misleading.
6. **low — the plan repeats a design #2390 approved and did not ship.** Evidence: the 2026-10-23 plan, Approach step 3: "the wrapper's `exit` event for the wrapper, `waitForExit` for the descendants". `test:134-138` on `origin/main` still polls the wrapper with `waitForExit`. The plan must name that history in one line so a reviewer does not count it as new.
7. **low — frequency.** I searched the last 100 failed `main` runs (`gh run list --branch main --status failure`) for this assertion and found 1 occurrence (run 41328179417, `926339afd`). Other hits were the text `survived` in workflow script listings. I did not finish the scan, so read this count as a floor and not as a rate.
8. **low — Open Question 2's premise is weaker than stated.** The `--exit-normally` test (`test:166-169`) and the three signal-to-caller tests (`test:215,221`) already await the wrapper's `exit` event. They call `waitForExit` only for the prompt and grandchild, which are not the runner's children. A signal to the caller's pid alone does not signal the prompt, so those tests do not have the child-exit-first race.

## Amendments I require

- A1. Replace the three "candidate causes, none yet measured" with the measured mechanism (finding 1). Cite `bounded-run-process.ts:137,139-144,156` and the probe result per platform. Remove cause 1 and cause 2 as candidates, or keep each with the reason it cannot produce a 5 s survival.
- A2. Put the adapter fix in this plan as a slice, not in a later plan. The slice ends the drop: a caller with an active run must never lose an ending signal that arrives in the same loop turn as the child's exit. One shape: add the ending-signal listeners once per process, count the active runs, and never remove the listeners while a run is active. When a signal arrives with no active run and no other listener, remove the listener and re-raise the same signal at the process. The process then dies by the default disposition, as it would without the adapter. Deferring the removal with `setImmediate` only narrows the window and is not enough. State the effect on callers that add their own listener (`onStop`, `pr-reader.ts:256`, `registryd-main.ts:2390`).
- A3. Add a deterministic regression test in `packages/domain/test/bounded-run-group-stop.test.ts`, as a new stand-in mode: block the caller's main thread, deliver the child's death and then `SIGTERM`, then assert that the caller exits 143 inside a named bound. The test must fail on `origin/main` (it does on Linux and macOS, per the probe) and pass with A2. Record a mutation proof: revert A2 and see the test fail. "CI ran green once" is not proof of a race fix.
- A4. Keep the plan's test change: read the wrapper's end from its `exit` event, use one named bound constant, and give a message that names `boundedRun`. Order the slices adapter first, then test, or put all three in one slice (see Optional). A test-only slice must not merge before the adapter slice, or the test fails as before under a new name.
- A5. State that the worker loop's `onStop` listeners mask the defect in production (finding 4). Say which other `boundedRunProcess` callers run in a host process with no ending-signal listener of its own, or say that the slice checks this.
- A6. Name in Motivation that #2390's approved step 3 was not shipped, and that #2380's timeouts are consistent with the same lost signal (findings 5 and 6).

## Optional

- O1. One slice instead of two: the adapter change, the race test and the `exit`-event wait touch two files in one package and are about 40 lines. One branch is the smaller design and gives one proof. Two slices only add a merge-order constraint.
- O2. Write the probe into the Linux CI shape (the `node:26` container) in the plan's test table. On Linux the race is order-dependent and on macOS it is not, so the regression test must force the order and must not rely on timing.
- O3. Add a corpus or doc line to `ports/bounded-run.ts` that states the contract: a run never swallows an ending signal sent to its caller.

## Open questions

- Q1 (which cause produced the 2026-11-01 failure?): Cause 3, a real survival. Mechanism: `finish()` removes the last ending-signal listener, Node stops the watcher, and libuv drops the `SIGTERM` already queued behind the child's exit. The reproduction is deterministic and needs no CPU hog or loop: block the caller's main thread and order the two signals (finding 1). On CI, load makes the child-exit-first order occasional.
- Q2 (do the sibling tests need the same change?): No. They already await the wrapper's `exit` event (`test:166-169`, `test:215,221`) and poll only pids that are not the runner's children. They also do not signal the prompt, so they do not hit the race. Only the group-stop test changes, and A3 adds one new case beside it.

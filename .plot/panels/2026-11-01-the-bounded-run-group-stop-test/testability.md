# Testability juror — the bounded-run group-stop test

Position: amend

The direction is right: the fix belongs in the test, the wrapper's end is better read from its `exit` event than from `kill -0`, and a surviving wrapper must read as a `boundedRun` defect. But the plan cannot prove its fix as written. Its only reproduction is a probabilistic load loop for a failure seen once in the last 40 failed CI runs on `main`, and a deterministic reproduction exists: a slow `pgrep` on `PATH` reproduces the exact CI message in 6.0 s on an idle machine (run below). The proposed `exit`-event wait also keeps the same deadline race as `waitForExit`, and the proposed message cannot tell a slow wrapper from a surviving one, so it would name ordinary load as a `boundedRun` defect. The plan also has no test table and no "Done when", so nothing but a green CI run would close it.

## Findings

1. **high — A deterministic reproduction exists, and the plan proposes a probabilistic one instead.** I ran the one named test (`vitest run test/bounded-run-group-stop.test.ts -t together`) at `origin/main` in a scratch worktree, with a `pgrep` stub first on `PATH` that sleeps 7 s and then execs `/usr/bin/pgrep`. Result: `× ends the wrapper, the prompt, and the prompt's own child, together 6014ms` and `AssertionError: wrapper 2227 survived the group stop: expected false to be true`, the exact CI text. This works because the stand-in inherits `process.env` (`bounded-run-group-stop.test.ts:31-36`, no `env` option) and the wrapper's exit handler calls `execFileSync('pgrep', ['-P', …])` by name (`bounded-run-process.ts:57`) before it can exit. The plan's Open Question 1 ("a loop of the test beside a CPU hog, in a Linux container") may never fire: I scanned the failed logs of the last 40 failed `CI` runs on `main` and found this assertion in one (41328179417). A loop that does not reproduce decides nothing between the three causes.
2. **high — The `exit`-event wait keeps the deadline race of `waitForExit`.** A timer fires in the event loop's timers phase, and libuv delivers `SIGCHLD` (and so the `exit` event) only in the later poll phase. I measured this with `node -e`: after a 1.5 s synchronous stall following a child's exit, `kill(pid, 0)` read `true` and the `exit` event had not fired; one `setImmediate` later, `kill -0` read `false` and the event had fired. `waitForExit` decides at `bounded-run-group-stop.test.ts:55` (`return !alive(pid)`) in the same turn as the deadline timer, so a stall across the deadline reads a zombie wrapper as alive. A `Promise.race([exit, timeout])` has the same defect: the timeout wins in the timers phase although the wrapper already exited. The plan does not name this, and its fix would not remove it.
3. **high — The proposed message cannot meet Required behaviour 2.** The plan words the failure as "the wrapper's `exit` event never fired inside the bound (a `boundedRun` defect)". Cause 2 (slow cleanup) produces the same observation: my `pgrep`-stub run is a wrapper that exits correctly after 7 s, and the plan's message would call it a `boundedRun` defect. The issue requires the opposite separation ("names that as a defect of `boundedRun`, not as a flake"). The test needs a discriminator: after the bound, a further grace wait used only for the message, so "exited after N ms (slow)" and "never exited (survived — `boundedRun` defect)" read differently; and the `exit` event's `code`/`signal`, where `143` proves `exitOnSignal` ran (`bounded-run-process.ts:81-83`) and `signal: 'SIGTERM'` with `code: null` proves the handler was absent.
4. **medium — "The wrapper assertion is the first of three and the only one that failed" is not known.** Vitest stops a test at its first failed `expect`; line 140 threw, so lines 141 and 142 never ran. The job log (job 124912486260) holds one `AssertionError` and no reading of the prompt or the grandchild. Which pids were alive is the one fact that separates the causes, and the current test throws it away.
5. **medium — The CI timing favours cause 2 over a sustained zombie, and the plan does not use it.** In the failing run the file took 10797 ms (`❯ test/bounded-run-group-stop.test.ts (8 tests | 1 failed) 10797ms`); the same file on the same commit in the "systemd unit" job took 5244 ms. The ~5.5 s difference matches one full `waitForExit` bound spent polling. A zombie survives a poll only while the runner's loop does not reach its poll phase, and a loop that runs the 50 ms poll reaches it, so cause 1 explains only a stall that crosses the deadline, not 5 s of live polling. Cause 1 remains possible at the boundary (finding 2); cause 2 needs only a wrapper that did not get CPU for its signal handler and three `pgrep` forks under `--coverage` load.
6. **medium — The plan has no test table and no "Done when", so a green CI run is its only proof.** One failure in many runs means a green run after the change proves nothing. The slice needs named arms that fail before and pass after on an idle machine (see A2).
7. **low — Cause 3 by listener removal is ruled out by reasoning, not by a test.** `finish()` removes the `SIGTERM` listeners when the prompt closes (`bounded-run-process.ts:143-144`), so a wrapper that handled the prompt's `close` before its own `SIGTERM` would drop the signal and live on. I checked the order: `kill(-pgid)` queues `SIGTERM` on every member before any member can exit, Linux delivers the lower-numbered pending signal first (`SIGTERM` 15 before `SIGCHLD` 17), and libuv reads its signal pipe in order. So `SIGTERM` is handled first. The survival arm in A2 would still catch a regression here.
8. **low — "`init` reaps them" is imprecise.** An orphan goes to the nearest child subreaper, else pid 1. It does not change the test: the prompt and the grandchild are never children of the runner, so the runner's `kill -0` cannot see them as its own zombies.
9. **low — `Type: feature` for a test fix.** The change repairs a defect in a test; `bug` with a `bug/` branch matches the 2026-10-23 sibling plan's intent better. Optional.

Observation outside the plan: while checking for leaks after my run, `pgrep` showed a live stand-in and prompt (pids 75870, 75927) from `.worktrees/free-b71b8ae4` with out file `/tmp/pgid-test/out.log`. They are not mine and I did not touch them.

## Amendments I require

- A1. Replace the load-loop reproduction with the deterministic one: a test arm that passes `env: { ...process.env, PATH: <stubDir>:$PATH }` to `spawnStandin`, where `<stubDir>` is inside the test's own `mkdtempSync` directory (CLAUDE.md, Testing) and holds a `pgrep` that sleeps and then execs the real `pgrep`. State in the plan that this arm, with a delay above the bound, fails on `main` with the CI message.
- A2. Add a test table with these arms, each deterministic on an idle machine: (a) slow cleanup below the bound — `pgrep` delay of about 1 s — passes, and the wrapper's `exit` gives `code` 143; (b) slow cleanup above the bound but inside the grace — the message reads "slow", not "defect"; (c) a surviving wrapper — a stand-in flag that removes `boundedRun`'s `SIGTERM` listeners after `READY` and keeps the process alive — fails with a message that names `boundedRun`; (d) a unit arm for the wait helper: spawn a child that exits, stall the loop synchronously past the bound, then the helper answers "exited" (on `main`, `waitForExit` answers `false`). Arms (b) and (c) may be a pure verdict helper unit-tested from fixed readings instead of real processes, if their wall time is too high to keep.
- A3. The wait helper yields one `setImmediate` after the deadline before it decides, for the `exit`-event wait and for `waitForExit`. It checks `exitCode`/`signalCode` before it attaches the `exit` listener, and it attaches the listener before the group `SIGTERM` is sent.
- A4. Read all three outcomes, the `exit` `code`/`signal` and the elapsed milliseconds, and assert once with a message that carries all of them, so the next CI failure answers Open Question 1 by itself.
- A5. Add "Done when": arms (a)–(d) pass locally and in CI; reverting A3's `setImmediate` yield makes arm (d) fail; replacing the `exit`-event wait with `kill -0` makes arm (d) fail; removing the survival flag's effect makes arm (c) pass, which is the mutation check that arm (c) tests something. No item reads "CI ran green".
- A6. Correct the two factual claims: the prompt and grandchild assertions never ran (finding 4), and the CI timing points at a full bound spent waiting (finding 5).

## Optional

- O1. Raise the wrapper's bound (one named constant, as the plan says) and raise `TEST_TIMEOUT_MS` by the same amount plus the grace, so a slow but correct wrapper under `--coverage` stops failing `main`.
- O2. Move `waitForExit` and the new `exit`-event wait into one shared test helper with the other process-exit waits (`packages/fleet/test/rm-tree.mjs`), so the deadline yield is written once.
- O3. Change `Type:` to `bug` and the branch prefix to `bug/`.

## Open questions

- **Which of the three causes produced the failure on 2026-11-01?** Recommendation: do not try to decide it by a load loop. The evidence available favours cause 2 (finding 5), cause 1 is possible only at the deadline (finding 2), and cause 3 by listener removal is ruled out by signal order (finding 7). Build the deterministic arms (A1, A2) and the full-reading assertion (A4); the arms prove the fix for causes 1 and 2 now, and the next CI failure, if any, names its own cause.
- **Do the two sibling tests need the same change?** Recommendation: not the wrapper change. The `--exit-normally` test (`bounded-run-group-stop.test.ts:166-168`) and the signal tests (`:215`) already read the wrapper from its `exit` event; their `waitForExit` calls are on the prompt and grandchild, which are not children of the runner and cannot be its zombies. They need only the shared helper's deadline yield (A3), which they get for free.

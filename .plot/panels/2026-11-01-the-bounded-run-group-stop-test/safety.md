# Safety juror — the-bounded-run-group-stop-test

Position: amend

The plan is right to keep a bounded wait and to fail a really surviving wrapper as a `boundedRun` defect, and the exit-event wait does not hide a survivor if the bound stays finite. But the plan's leading cause is wrong on measurement, one of its facts cannot be known from the log, its proposed container reproduction gives false results without `--init`, and it leaves the leak path open that has already left a stand-in tree running on the operator's machine for 9 days. I measured the wrapper's stop locally: about 97 % of the time between the group `SIGTERM` and the wrapper's `exit` event is `killTreeSync`'s synchronous `pgrep`, and a `pgrep` shim that sleeps makes the current test fail with exactly `wrapper <pid> survived the group stop` while the prompt and the grandchild are already dead. That is a deterministic reproduction of cause 2, and it shows that the current message calls a slow stop a survival.

## Findings

1. **high — Cause 1 (zombie) is refuted, cause 2 (slow synchronous exit path) is reproduced.** Evidence: `packages/domain/src/adapters/bounded-run/bounded-run-process.ts:81-83,129-137,54-70` (SIGTERM handler calls `process.exit(143)`, the `'exit'` listener runs `killTreeSync`, which calls `execFileSync('pgrep', ['-P', pid])` with no timeout). What I checked: a scratch script (`scratchpad/exp3019/measure.mjs`) spawned the real stand-in from a scratch worktree at `origin/main`, sent `kill(-pgid, 'SIGTERM')`, and timed the signal handler, the end of the `'exit'` listeners, and the parent's `exit` event. Over 16 runs: handler reached in 0–1 ms, `killTreeSync` took 101–662 ms, Node teardown 3–5 ms, exit code 143 every time. `kill(pid, 0)` read the wrapper gone 2–6 ms after the `exit` event (the 5 ms poll granularity), so the runner reaps the wrapper at once and a zombie cannot hold for 5 s while the test's own loop runs timers. With a `pgrep` shim on `PATH` that sleeps 3 s, the wrapper's exit took 3289–3528 ms and the prompt and grandchild were already dead; a sleep above 5 s therefore fails the current test deterministically. CI agrees: the failed test ran 5282 ms (job 124912486260, log line 197), that is readiness about 280 ms plus the full 5000 ms poll.
2. **high — A real survivor on a real machine is never escalated, so this test is the only guard.** Evidence: `skills/plot/scripts/plot-dispatch.sh:1804` sends one `kill -TERM -- "$stop_target"`, then writes a `stopped` ending and exits; nothing waits, re-checks or sends `SIGKILL`. A wrapper that hangs in its exit listener (for example a `pgrep` that blocks on the process table) keeps its desk, its claim and its group forever, and the ending file says `stopped`. So the slice must keep the bound finite, keep a bound expiry a test failure, and never retry or extend the wait until it passes.
3. **high — The test's own teardown leaks the tree in exactly the defect case it guards, and a leak from the earlier fix is still running.** Evidence: `packages/domain/test/bounded-run-group-stop.test.ts:83-96` kills only `-wrapper.pid`. If `boundedRun` detaches the prompt (the mutation #2380's plan required as proof), the prompt and grandchild lead their own group and survive the teardown. What I checked: `ps -A -o pid,ppid,pgid,lstart` on this machine shows pid 75870 (`bounded-run-group-standin.mjs` from `.worktrees/free-b71b8ae4`, out file `/tmp/pgid-test/out.log`, ppid 1) and pid 75927 (`bounded-run-prompt.mjs`, its own pgid and session, state `SNs`), both started 2026-10-23 11:24:39, alive 9 days. The worktree is gone. I did not kill them; they are the operator's to remove.
4. **medium — The plan states a fact the log cannot show.** The plan says the wrapper assertion "is the first of three and the only one that failed". `bounded-run-group-stop.test.ts:140-142` are three `expect` calls; vitest stops at the first failing one, so the prompt and grandchild states on 2026-11-01 were never evaluated. My local measurement shows they die from the group signal itself, but the CI run does not prove it.
5. **medium — A container reproduction without an init process gives false survivals.** The Open Question proposes a Linux container. When the wrapper dies, the prompt and grandchild reparent to PID 1. In `docker run` without `--init`, PID 1 is the command (node or a shell), which does not reap foreign children, so the descendants stay zombies and `kill(pid, 0)` reads them alive forever. The plan's own sentence "`init` reaps them" holds on the GitHub VM and on macOS, not in a bare container.
6. **medium — The earlier plan already promised the exit-event wait and it did not ship.** Evidence: `docs/plans/2026-10-23-bounded-run-group-stop-test-times.md`, Approach step 3: "the wrapper's `exit` event for the wrapper, `waitForExit` for the descendants". The plan is Released, but `bounded-run-group-stop.test.ts:134-138` still polls the wrapper with `waitForExit`. The new plan repeats the step without naming why it was dropped, and nothing checks it lands this time.
7. **medium — A raised bound can hand the failure back to the vitest timeout.** `TEST_TIMEOUT_MS = 20_000` (`:24`) covers readiness 10 s plus the exit wait. A named bound above 10 s leaves no headroom, and the vitest timeout then fires first with `Test timed out`, which loses the `boundedRun` defect message — the #2380 failure again.
8. **medium — The signal-to-caller tests have an unbounded wrapper wait.** `bounded-run-group-stop.test.ts:215,221` and `:166-168` await the `exit` event with no bound. A wrapper that survives a single-pid `SIGTERM`, `SIGINT` or `SIGHUP` fails only by the vitest timeout, with no message that names `boundedRun`.
9. **low — The teardown signals a pgid number after the group can be gone.** `:86-91` sends `SIGKILL` to `-wrapper.pid` even when every member is dead. On a machine with sequential pids the number is very unlikely to be reused within milliseconds, but a teardown that first checks the `exit` event and the recorded pids removes the question.
10. **low — The plan's other facts hold.** I checked: the test name, the message and job 124912486260 (log lines 196–197, 427–448: 1 failed, 8670 passed of 8671); `926339afd` is a CI run on main; `waitForExit` polls every 50 ms with a 5000 ms default (`:49-56`); #2390 / #2380 fixed the `Test timed out in 5000ms` failure. In the last 300 CI runs on main, this assertion failed once (run 41328179417); the four other failed runs that mention the file passed it.

## Amendments I require

- A1. Replace "Candidate causes, none yet measured" with the measured cause: the wrapper's stop time is `killTreeSync`'s synchronous `pgrep` (101–662 ms locally), the zombie window is under 10 ms, and cause 1 is not the explanation. Keep cause 3 as the defect the test must report.
- A2. Prove the fix deterministically with a `pgrep` shim on `PATH` that sleeps longer than the old 5 s: on `main` the test fails with `wrapper … survived`; on the branch the test passes when the shim sleeps less than the new bound and fails with a message that names `boundedRun` and says the wrapper is still in its exit path when the shim sleeps longer. "CI ran green once" is not proof.
- A3. At the deadline, the failure message reports all three states in one assertion (wrapper `exit` event fired or not, with its code or signal; prompt alive; grandchild alive), and for a wrapper that has not exited, its `ps -o stat=` and its child pids, so a reader can tell "stuck in its exit listener" from "ignored the signal".
- A4. The teardown kills the reported `promptPid` and `grandchildPid` by pid as well as `-wrapper.pid` by group, so the detached-prompt mutation and a real detach defect leak nothing. Re-run the mutation proof of #2381 (`detached: true` in `bounded-run-process.ts:111`) and show with `ps` that no stand-in, prompt or grandchild remains afterwards.
- A5. State the arithmetic: `TEST_TIMEOUT_MS` is greater than the readiness bound plus the named exit bound plus headroom, so the named bound always fires before the vitest timeout.
- A6. Any container reproduction runs with `docker run --init` (or an equivalent reaping PID 1), and the plan says why.
- A7. Correct the sentence "the only one that failed" to "the first assertion failed; the other two were not evaluated".
- A8. Say why #2390 did not ship the exit-event wait that #2381 approved, and add a check (a mutation or a grep in the test) that the wrapper wait reads the `exit` event.

## Optional

- O1. Assert exit code 143 in the group-stop test as well: it proves `boundedRun`'s handler ran rather than the default `SIGTERM` disposition.
- O2. A separate plan for `boundedRun`: give `killTreeSync`'s `execFileSync('pgrep')` a timeout, or read the process table once instead of once per node. A hung `pgrep` today makes a wrapper that never exits, and finding 2 shows nothing would end it.
- O3. A separate issue for `--stop` to check, after a bound, that the group is gone and to report a survivor.
- O4. Tell the operator about pids 75870 and 75927 (finding 3).

## Open questions

- Which cause produced the failure on 2026-11-01? Recommendation: cause 2. The local measurement puts almost all of the wrapper's stop time in `killTreeSync`'s synchronous `pgrep`, the zombie window is milliseconds, and a slowed `pgrep` reproduces the exact message with no process left alive. A loaded GitHub runner that slows one `pgrep` spawn past 5 s is consistent with the 5282 ms test time. Use the `PATH` shim (A2), not a CPU hog, as the reproduction; a container run is optional and needs `--init` (A6).
- Do the sibling tests need the same change? Recommendation: yes for the wrapper wait. The `--exit-normally` and the three signal tests await the wrapper's `exit` event with no bound (finding 8); give each the same named bound and the same `boundedRun` message, and the same teardown by recorded pids (A4). Their descendant polls already have a bound and need only the shared constant.

## (a) Problem statement

The facts in the Motivation are concrete (times, exit 143, the pulse words, the two bundle refusals) and the gap is real: no board endpoint and no board-free bundle reaches `plot-dispatch.sh --restart`, and fleetd deliberately leaves a `stopped` desk alone (ending-action.ts:149, ending.ts:117-120). An operator who ran `/plot-fleet --stop` then `--start` gets every claimed slice back as a dead row, with no button on it.

Three statements are wrong or misleading and change the design:

1. "five free desks stayed idle" is presented as a symptom of this gap. It is not. A free desk takes only an `open` slice (no ref); a claimed slice is never offered to any caller, by design (dispatch.sh:1899-1910, 2026-08-27 plan:197 "the board's auto-dispatch would begin restarting stalled work on a five-second timer with nobody deciding anything"). Also, `fleetctl --stop` skips detached free desks and leaves them running (fleetctl.sh:1259-1267), so `--start 8` stacked new free desks on old ones. The idle desks are idle because nothing was open, and neither route in the plan changes that: route 1 restarts on the slice's OWN desk. The plan must say so, or a reader (and a fleet operator) expects idle desks to pick the slice up after this ships.
2. "*The Master Agent Uses The Controllers* forbids calling the script directly, so a master agent ... has no route." Mechanically false today: the controller gate exempts `--restart` (ci-suite.ts:333, dispatch.sh:4215-4217 "the gate exempts each of them: they are reads, or writes no endpoint owns"). The gap is a missing controller (the CLAUDE.md rule "where no controller exists, the gap is the finding"), not a blocked route. This matters for slice scope: adding the endpoint means removing `--restart` from NO_ENDPOINT, which is a gate change the plan does not name.
3. Open question 2 says "`ending-action.ts` has no row for an ending that `--stop` writes." It has one: `stopped` is an ending reason (ending.ts:117-120, :160) and endingAction answers `leave` for it on purpose (ending-action.ts:149). The decision to leave it is documented as "the person who stopped it decides". The question is therefore not "add a missing row" but "overturn a recorded decision", which needs its own argument.

## (b) Does the approach solve it without a new defect?

Route 1 (a `restart` controller) solves the operator's problem for one desk and is consistent with the 2026-08-27 design (explicit, by branch, a person decides). As written it has four defects or gaps:

- The domain rule is narrower than the script it fronts and drops the measured guard. The plan's rule accepts "claimed, worker `failed` or `ended`, desk exists". The script's gate is ordered PR first, then live loop (including a free-waiting loop), then `PLOT-BLOCKED` marker, and accepts `stalled`, `failed`, `ended` and `none` (dispatch.sh:1013-1066, :1957). The PR-first order comes from a measurement: five of five `failed` desks held a PR (dispatch.sh:1933-1944). If the domain rule refuses before the script asks, `stalled` (uncommitted work, the 2026-08-27 motivating case) becomes unrestartable through the controller; if it accepts and the script refuses, the operator gets two refusal vocabularies. The rule must carry the same refusals in the same order, or the controller must pass straight to the script's own gate and report its refusal by name.
- A restarted worker that later crashes is read as a person's stop. `--restart` does not remove `.plot-worker.ending.json` (start_worker removes only `.plot-worker.exit`, dispatch.sh:1205); the ending is removed only when a slice declares `ok` (desk-fs.ts:181-190). killedWorkerEnding writes `unreadable` only where the ending is ABSENT (ending-action.ts:636), so a restarted worker that exits non-zero with no ending leaves the stale `stopped` record, endingAction answers `leave`, and fleetd neither starts a fresh session nor writes a marker. Today this needs a rare manual `--restart`; route 1 puts it on the normal recovery path after every fleet stop. I did not execute this; it follows from the three lines cited and wants a test before approval.
- Receipt spending. The plan says "the gate lists the action and its receipt", but the only spend site is the fan-out (dispatch.sh:4218); `--restart` exits at :1994 before it. A receipt taken for a board-free restart would never be spent, so one licence would cover repeated restarts. The slice must add a spend on the restart path.
- Two start paths for a desk. fleetd already starts a worker on an existing desk in TypeScript through continueOnDesk (registryd.ts:1142, continuation.ts:716), with its lock, live-loop and manifest refusals. Route 1 adds a second path through shell `start_worker`. Both are legal under the layering rule, but they will disagree on locking (`takeContinueLock`, continuation.ts:755) and on the ending read; a restart and a fleetd fresh start racing on one desk are protected by the shell's loop read only. Either reuse continueOnDesk with a new `restart` precondition (an existing `stopped`/`unreadable` ending, no marker), or state why the shell path is chosen and take the continue lock in it.

Route 2 (`fleetctl --start` restarts what `--stop` stopped) has a defect as stated: `--stop` from fleetctl and a person's single `plot-dispatch --stop` write a byte-identical ending (`detail: "plot-dispatch --stop"`, dispatch.sh:1887). `--start` cannot tell "stopped by the fleet stop" from "a person deliberately parked this one" and would restart the parked desk, overturning ending.ts:119. Route 2 needs `fleetctl --stop` to record which branches it stopped (a list file, or a distinct `detail`/actor), and `--start` to restart only those, through the same restart controller so the PR/loop/marker refusals apply. It also must respect the machine bound that `--start N` already spends on free desks.

Open question 2 (fleetd restarts a `failed`/`stopped` slice by itself) reintroduces exactly the timer-driven restart the 2026-08-27 plan rejected (:197) and contradicts ending.ts:119. A crashed worker WITHOUT a person's stop is already handled: no ending -> killedWorkerEnding writes `unreadable` -> the bound row starts one fresh session where the branch holds work (ending-action.ts:356-361). So "route 2 alone does not help a worker that died for another reason" is only true for the stale-ending case above.

## (c) Slices: missing, wrong, out of order

- The Changelog (:15) promises route 2 ("`plot-fleetctl.sh --start` no longer leaves the slices that `--stop` stopped without a worker"), but the only slice (:53) builds route 1. Either add a route-2 slice or drop the sentence; as written delivery would ship a changelog line nothing implements.
- The single slice holds rule, adapter, endpoint, bundle and gate change. The gate change (drop `--restart` from NO_ENDPOINT, add the receipt spend) should be in the same slice as the endpoint, otherwise there is a window with an endpoint and an ungated script; name it explicitly.
- Missing: clear (or supersede) the `stopped` ending when a restart starts, with a test that a restarted worker exiting non-zero reaches killedWorkerEnding.
- Missing board slice content: the pulse row reads `startability: someone-is-on-it` (verdict.ts:56) for a claimed slice whose worker is dead. The operator sees "someone is on it" beside `worker: failed`. The row in *Waiting on you* should offer the Restart action and word the state truthfully; the plan's board-impact note mentions "its row state" but no slice owns the wording or the button.
- Missing: what `--status`/the fleet section shows after a fleet stop, so the operator can see how many claimed desks need a restart before running `--start`.
- Out of order: three open questions remain unticked while the slice is already named; route choice determines whether there are one or two slices.

## (d) Decisions before approval

1. Route 1 only, or route 1 plus route 2? Recommend route 1 now, route 2 as a second slice that calls route 1's controller per branch, conditional on `fleetctl --stop` recording its own stop set.
2. fleetd auto-restarts a `stopped` desk, or never? Recommend never: keep `stopped` -> `leave` (ending.ts:119, 2026-08-27 plan:197). Rewrite open question 2 to say the row exists and is deliberate.
3. Restartable set: `failed`/`ended` only, or the script's set (`stalled`, `failed`, `ended`, `none`) behind PR -> loop -> marker refusals? Recommend the script's set and order; do not add `finished` (it means the work reached review or completed; the script refuses it).
4. Shell `--restart` behind an adapter, or extend continueOnDesk with a restart precondition? Recommend continueOnDesk, which already holds the lock and the manifest refusals and keeps one desk-start path in TypeScript; if the shell path is kept, it must take the continue lock.
5. Restart clears the old ending, or leaves it? Recommend clear (or overwrite with a `restarted` record) at start, so a later crash reaches killedWorkerEnding.

## (e) Position

Amend. The gap is real and route 1 is the right shape, but the plan misstates three facts (idle free desks, the gate, the missing ending row), its domain rule drops the PR-first guard, route 2 as written would restart a person's deliberate stop, the receipt would never be spent, and a restarted worker that crashes would be read as stopped by a person. Fix the motivation, pick the route, align the rule with handover_refusal, and add the ending-clear and receipt work to the slice.

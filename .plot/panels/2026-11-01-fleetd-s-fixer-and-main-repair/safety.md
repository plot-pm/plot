# Safety juror — fleetd's fixer and main-repair agents never start

Position: amend

The command fix is correct and small. The plan does not bound what the two roles can do once they start, and it should. Today every fixer and main-repair run dies about 2 seconds after its spawn, so the role gate, the in-flight mark and the attempts budget have never held a live agent. The plan turns them on but sets no limits on run time, on how many fixers run at once, on force pushes, or on what a failed start costs. Main-repair is already well bounded: one attempt per episode, a re-run first, a claim by ref push, and `Main repair bound` 3600 s. The fixer is not bounded in the same way. The plan also says nothing about the race with the master agent's hand fix agents or with a live desk. Each gap needs a few lines of code or one sentence in the plan, so the plan can stay small.

## Findings

1. **high — A fixer run has no wall-clock bound.** `auto-fixer.ts:495` passes `boundSeconds: 0`, and `bounded-run-process.ts:211` arms the timer only when `boundSeconds > 0`. The only limit is `--max-turns 80` from `.claude/agents/fixer.md` (opus, effort high). While the run lives, `fixerInFlightArm` (`slice-pr-next.ts:202`) holds the PR at `fixer-in-flight`, so the review, merge and HIGH arms do not run. `roleRunAlive` reads an unanswerable pid as alive for the fixer. A fixer that hangs therefore holds its PR with no end. Main-repair passes `deps.boundSeconds` (`repair-role.ts:181`), so this gap is the fixer's alone. Checked: `git show origin/main:` for both files and `bounded-run-process.ts`.
2. **high — Nothing caps how many fixers run at once.** `auto-writes.ts:78` calls `runAutoFixerPass` behind `stopped()` only, and `fixerTick` starts one fixer per PR whose `slicePrNext` answers `fixer`. Verify takes a slot from `machine.headroom` (`auto-writes.ts:89-90`), and the fixer takes none. On 2026-11-01, 8 of 12 slice PRs got a HIGH (plan, Motivation). With the fix, up to 8 opus/high fixers can start in one pass, next to the desks and reviewers on the same machine. Before the fix, each of them died in 2 s.
3. **high — The role gate does not refuse a force push or a push to another branch.** `roleDeniesCommand` (`packages/domain/src/rules/role-gate.ts`) refuses a commit-status write, a reviewer run, any merge, a push to the default branch, and a closing keyword. It does not refuse `git push --force`, `-f`, a `+refspec`, a push to any other branch (another PR's branch or a live desk's branch), or the deletion of a non-default branch. Only Write, Edit and NotebookEdit are path-checked, so `sed -i` or `cat >` through Bash writes a protected path. "Never force-push" is prose in `fixerPrompt` (`fixer-start.ts:51`). CLAUDE.md says "Gates over rules". Before this fix these gaps were dormant. After it, an agent that can use them runs unattended.
4. **high — A HIGH starts the fixer while the desk is live, and the master agent's own fix agents race it.** `highArm` (`slice-pr-next.ts:220-238`) reads no desk state. Only `ciRedArm` checks `desk.dead` (`:264`). So a fixer starts beside a running desk loop, and beside any hand fix agent the master agent started. The master agent started one for every HIGH on 2026-11-01. The bound today is that the fixer pushes `HEAD:<branch>` from a detached head, so a moved branch rejects the push. That bound holds only while no one force-pushes (finding 3). The plan names neither race, and it gives the master agent no way to see that a fixer is in flight.
5. **medium — No live role session has ever proved the role gate.** All 19 fixer logs and `.plot/state/main-repair/run.log` end before the agent runs. The `role-deny` tests are unit tests (`packages/board/test/unit/role-deny-gate.test.ts`). I ran the real CLI once, as fleetd resolves it (`/opt/homebrew/bin/claude` 2.1.231), with the JSON-text form, `--setting-sources user --settings .claude/settings/fixer.json` and `--debug-file`. It answered `OK`, and the log says `Registered 34 hooks from 13 plugins`. The log has no line that shows the `--settings` file's `PreToolUse` hooks registered, so the run proves the start but not the gate.
6. **medium — Role sessions load all of the operator's plugins.** The debug run loaded 13 enabled plugins and their hooks (log lines 43-51 and 206-211), among them oh-my-claudecode and the released plot 2.29.1. `roleCommand` passes the role's settings file but not `Agent settings` (`.plot/agent-settings.json`). Desks pass that file (`.plot/worker-prompt.sh:160`), and `plot-install-prompt.sh:94` reports its absence as a defect ("Every agent it starts loads the operator's plugins"). The fixer prompt carries review findings word for word, and oh-my-claudecode's `UserPromptSubmit` hook reads prompt text for mode keywords.
7. **medium — The plan makes no failed start free and none bounded.** Today `onStarted` fires on spawn, so a run that dies in 2 s reads as `started: true` and spends an attempt. `settleEnded` clears the mark on the next tick, and the second attempt starts at once. `.plot/state/fixer-attempts/2973.json` holds two attempts on one head for that reason. The plan's text "instead of leaving it in flight" does not describe this: the mark is cleared, and the budget is spent. If a failed start becomes free and nothing else bounds it, a lasting failure (CLI missing, auth expired, rate limit) starts a process on every tick without end.
8. **medium — Re-opening spent records starts fixers at deploy time.** Of the 19 records under `.plot/state/fixer-attempts/`, the open PRs #3012, #3021 and #3022 each hold 2 attempts (`gh pr view`). They answer `ticket-not-built` today (`readFixerPass` passes no `ticket` reading). If the slice re-opens them (Open Question 3), three fixers start on the first pass after deploy, on PRs that the master agent may be fixing by hand.
9. **medium — Main-repair is bounded, but a person who repairs main on another branch is not seen.** `startRepair` (`packages/fleet/src/shared/repair-start.ts`) claims `bug/main-repair-<12 hex>` by ref push before it creates a worktree. A lost claim records `outcome: 'lost'` and starts nothing, and `repairAttemptStep` allows one attempt per episode, after a red re-run. That is sound. A person who repairs on any other branch is not seen. `plot-ask.mjs merge` admits only the record's `repairPr` or `revertPr` on a red main, and `repair-pr` refuses a second PR and any other branch name. So a person must win the claim first on the fleet's branch name, and the plan does not say so. `run.json` already names `bug/main-repair-f767111ec489` from the failed run, so the claim race exists today, and the fix adds only the agent.
10. **low — The defect depends on the CLI version.** fleetd's `PATH` (`ps eww` on pid 87231) reaches `claude` through the cmux shim and then `/opt/homebrew/bin/claude` 2.1.231, whose help says `--agents <json>`. The operator's `~/.local/bin/claude` 2.1.316 says `--agents <json-or-file>` ("with --print the path to a file that holds one"). The JSON-text form works on both. The plan should name the version fleetd runs. The fake-CLI test must not assume that every CLI rejects a path.
11. **low — Factual details.** `.plot/state/fixer/` holds 19 logs, not 20 (#2975 has only a lock directory), and all 19 end with `not found`. The fixer budget is the constant `FIXER_ATTEMPTS_BUDGET = 2` (`fixer-attempts.ts:4`), not the `Correction budget` config key. No reviewer or unblocker start calls `roleCommand`. The only callers are `auto-fixer.ts:383` and `repair-role.ts:133`, and the reviewer uses its own charter (`review.ts:333`). The other `--settings` sites (`.plot/worker-prompt.sh:160`, `plot-dispatch.sh:823`) pass a settings path, which `--settings` accepts, so they do not have this defect.

## Amendments I require

- A1. Give the fixer a wall-clock bound: pass `Worker bound` or a new key as `boundSeconds` in `launchFixer`, and test that a run past the bound ends and its mark clears.
- A2. Cap concurrent fixers. Either take an agent slot from the same headroom verify uses, or allow at most N fixers in flight across all PRs (one is enough for the first release). Test that a second PR with a HIGH holds while one fixer runs.
- A3. Extend `roleDeniesCommand` for the fixer and main-repair roles, in this plan or in a slice that merges before the command fix. It must refuse a forced push (`--force`, `-f`, `--force-with-lease`, a `+` refspec), a push whose destination is not the role's own branch (the PR's head branch for the fixer, the claimed `bug/main-repair-*` branch for main-repair), and a branch deletion. Use the `gitPushCalls` parser that the rule already imports. A Bash write to a protected path can stay out of scope, but the plan must name it as a known gap.
- A4. Before approval, state the race rules: (a) a HIGH with a live desk still starts the fixer, and the plan states why that is safe (the push is rejected because the branch moved, which A3 makes a gate), or `highArm` reads `desk` as `ciRedArm` does; (b) the master agent reads `fixerInFlight`, through the attempts file or a `plot-ask.mjs` question, before it starts a hand fix, and the CLAUDE.md master-agent section says so.
- A5. Prove the gate in a live start. One local acceptance step before the fleet runs with the fix: start the fixer command against a scratch repository and confirm that `role-deny` refuses a `gh pr merge` call. CI cannot run this step, but the plan must name it, along with the result it must see.
- A6. Bound a failed start. It does not spend a fix attempt, but it counts against its own cap (for example 3 per PR and head), and after that cap the PR holds with a named reason in the run log. A run detected as failed must not start a new process on every tick. Answer Open Question 3 as "no automatic re-open" (see below).
- A7. Pass `Agent settings` beside the role's settings, or state that roles run with the operator's plugins and why that is acceptable.

## Optional

- Add `--output-format stream-json --verbose` to the role command, and read a failed start as "no `system/init` event before exit". Text such as `not found` in a log is brittle.
- Name in the plan the CLI version that fleetd resolves, and record the `claude` path in the run log on every role start.
- State whether `plot-fleet --stop` ends running fixers or only skips new starts. `auto-writes.ts:77` says a stop skips the start.

## Open questions

- OQ1 (does the runner use a shell): yes. `agent-run-command.ts:65` runs `bash -c '<fragment> "$@"' _ <prompt>`, so `$(cat '<file>')` expands. Keep the file as the carrier: about 1.2 KB is far below ARG_MAX, and the logged command stays short.
- OQ2 (how to detect a failed start): read the exit and the time, not the log text. A run that exits non-zero, or exits before its first stream event (with stream-json, before `system/init`), is a failed start. Record it as a field on the attempt (`start: 'failed'`), not as a separate state, so that `fixerAttemptsSpent` can exclude it and A6's cap can count it.
- OQ3 (does a failed start spend an attempt, and are spent records re-opened): it spends none, and A6 caps it on its own counter. Do not re-open spent records automatically. Three open PRs (#3012, #3021, #3022) would start fixers on the first pass. A person who wants one PR re-armed moves that PR's record aside by hand.
- OQ4 (does the real-CLI case run in CI): only locally, skipped when `claude` is absent. CI holds the fake-CLI parser test. The local case must use the `claude` that fleetd's `PATH` resolves, not the operator's newer binary.

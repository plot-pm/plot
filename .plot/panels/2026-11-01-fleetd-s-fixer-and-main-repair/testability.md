# Testability juror — fleetd's fixer and main-repair agents never start

Position: amend

The fix in Approach 1 is right and small, but the plan's proof does not hold as written. The defect depends on the CLI version: fleetd's PATH resolves `/opt/homebrew/bin/claude` 2.1.231, which reads `--agents` as JSON only, while `~/.local/bin/claude` 2.1.316 on the same machine accepts a file path with `--print`. I ran 2.1.316 once with today's path shape and the fixer started and answered `OK`. So the plan's "real CLI argument parser" case passes on the broken shape on this machine and cannot be the red test; only a fake that models 2.1.231 is. The plan's claim that `repair-role.ts` already returns `'failed'` is false for this failure, and the fixer's failure is not an attempt left in flight but an ended attempt logged as `fixer-end moved`. Both failed-start outcomes are testable with no timing if detection reads the run's own output when the run promise resolves.

## Findings

1. **high — the defect is version-bound, and the plan's real-CLI test case is green on the broken shape.** Evidence: `com.plot-pm.fleetd.plist` PATH is `node v26.13.0 : cmux shim : /opt/homebrew/bin : ...`; the shim strips itself and runs `exec claude`, so `env -i PATH=<that PATH> claude --version` prints `2.1.231`, and its help says `--agents <json>`. The interactive `claude` is `~/.local/bin/claude` 2.1.316, whose help says `--agents <json-or-file>  JSON object defining custom agents, or with --print the path to a file that holds one`. My one real run: `~/.local/bin/claude -p --setting-sources user --agent fixer --agents <scratch>/agents.json --model haiku --max-turns 1 "Reply with the single word OK."` (a copy of `.plot/state/fixer/3023.agents.json`) printed `OK`, exit 0. The 2026-10-29 panel probed CLI 2.1.312 and recorded that `--setting-sources user --agents <file outside the tree> --agent probe2` loaded it (`.plot/panels/2026-10-29-fleet-roles-are-declared-agents/testability.md:19`). That is why the path form was designed: it was correct for the CLI that was probed, and wrong for the CLI fleetd runs. The plan's Motivation states "the CLI's `--agents` flag takes the JSON text" without the version, which is true only for 2.1.231.
2. **high — `repair-role.ts` does not report this failure, contrary to Approach 3.** `startRole` resolves `'started'` as soon as `onStarted` fires (`packages/fleet/src/shared/repair-role.ts:140-144`). `agentRunOf` returns `result.ok` (`:191`). `agentRunCommand` returns `answered(...)`, so `ok: true`, for a non-zero exit, with `end.answer: 'unstarted'` (`packages/domain/src/adapters/agent-run/agent-run-command.ts:74-117`). So the warning "ended without a result" (`repair-role.ts:146`) never fires for `--agent 'main-repair' not found`; only the `endedAt` record is written. The plan's sentence "`repair-role.ts` already returns `'failed'` when the run ends without a result" is false for the measured case.
3. **high — the fixer's failed start is logged as success, not left in flight.** `launchFixer` resolves at `onStarted`, and the later run result is dropped by `if (settled) return;` (`packages/fleet/src/shared/auto-fixer.ts:508`). The next tick reads the pid as dead and `settleEnded` clears the mark and logs `fixer-end moved` (`auto-fixer.ts:244-247`). I read all 19 records in `.plot/state/fixer-attempts/`: none holds an `inFlight` mark, and 15 hold 2 attempts. Approach 3 says "records the attempt as a failed start instead of leaving it in flight", which describes a state that does not occur; the defect to fix is the `moved` outcome and the spent attempt.
4. **medium — only two production call sites build a role command with `--agents`; the reviewer and unblocker do not share it.** `git grep` over `origin/main` finds `roleCommand` imported only by `auto-fixer.ts:383` and `repair-role.ts:133`. The reviewer is built by `reviewerCommand` (`packages/domain/src/rules/review-verdict.ts:157`, called at `packages/board/src/server/entry/review.ts:345`) and passes no `--agents`, `--agent` or `--settings`. The unblocker's `UnblockPorts.run` (`packages/fleet/src/server/entry/registryd.ts:1524`) has no production implementation; `applyUnblockDecisions` is called only in `packages/fleet/test/unit/registryd-tick.test.ts`. The SDK runner's `loadRole` (`agent-run-sdk.ts:309-327`) reads the file itself and passes an object through the SDK, so it has no defect. The `--agent` in `plot-dispatch.sh:353` is a Plot charter flag, not the CLI's. The `--settings "$PLOT_AGENT_SETTINGS"` in `.plot/worker-prompt.sh:160` takes a path, which the CLI accepts. The plan's "the reviewer and unblocker roles share `roleCommand`" is false; the test over every `ROLE_NAMES` entry is still worth keeping because `roleCommand` accepts all four.
5. **medium — why the existing tests passed the broken shape: no test executes the fragment, and no fake run ever ends.** `packages/domain/test/role-command.test.ts:21` pins the defective string as the expected value. `packages/domain/test/agent-run-command.test.ts:248-262` runs a role fragment through a fake `BoundedRun` that never starts bash. `packages/fleet/test/unit/auto-fixer.test.ts:178-190` fakes `agentRun`: in the `starts` case it calls `onStarted` and returns a promise that never settles ("THE RUN NEVER ENDS here"). So the path "a process starts and then ends with an error" has no test by construction, and the plan's Approach 2 fixes only the first of these three gaps.
6. **medium — the exit status alone cannot tell a failed start from a run that ended badly.** `promptExit` answers `unstarted` for every non-zero status with no limit line (`packages/domain/src/rules/prompt-exit.ts:393`), so an agent that ran and then ended non-zero gets the same answer. The only evidence specific to "the agent never ran" is the CLI's line `--agent '<role>' not found` in the run's appended output, which `agentRunCommand` already returns as `finalText`. A pure domain rule over that text is testable against the 19 live log tails with no clock.
7. **medium — the attempts record forbids the write Approach 3 needs.** `FixerAttemptSchema` is `.strict()` and its contract says an attempt is "written once ... and never mutated after the fixer ends"; `inFlight` is the only field a caller may touch (`packages/domain/src/entities/fixer-attempts.ts`, schema doc). `FIXER_ATTEMPTS_VERSION` is a literal `1`. A failed-start field or state changes that contract and the version rule, and the plan does not say so.
8. **low — the live counts differ from the plan.** `.plot/state/fixer/` holds 19 logs and 20 locks (#2975 has a lock and no log), and 19 of 19 logs end with `--agent 'fixer' not found`. The plan says "logs for 20 PRs ... 19 of them end with". Three PRs with 2 spent attempts are still open: #3012, #3021, #3022 (`gh pr list --state open`).
9. **low — Open Question 1 is already answered by the code.** `agentRunCommand` runs `env -u PLOT_REPO_ROOT bash -c '<fragment> "$@"' _ <prompt>` (`agent-run-command.ts:65`), asserted by `agent-run-command.test.ts:58`. `$(cat '<file>')` expands. The JSON is 1257 bytes (fixer) and 1191 bytes (main-repair); macOS `ARG_MAX` is 1 MiB and Linux limits one argument to 128 KiB. A missing file gives `--agents ""` and a `cat` error in the log, which the CLI then refuses; a test should hold that this ends as a failed start too.

## Open questions

- OQ1 (does the runner use `sh -c`): yes. `agentRunCommand` runs `bash -c '<fragment> "$@"'` (`agent-run-command.ts:65`), so `$(cat '<file>')` expands. Keep `$(cat ...)` with `singleQuote` on the path. Close the question.
- OQ2 (how to detect a start that fails before its agent runs): by the run's own appended output, the CLI's `--agent '<role>' not found` line, read when the run promise resolves (A6, A7). Not by the exit code alone, which is non-zero for other endings too, and not by elapsed time. The command runner emits no agent events, so "no first agent event" has nothing to read.
- OQ3 (does a failed start spend a correction attempt): no. The agent did no work, so the budget of 2 must not pay for a CLI defect. To stop a launch on every tick, a failed start holds that PR and head until the role definition or the CLI version changes, and logs the hold once. Do not migrate records automatically. Name the three open PRs with spent budgets (#3012, #3021, #3022) and let the operator remove those three records by name after the fix lands.
- OQ4 (real-CLI case in CI): no. CI has no `claude`, and the real case cannot be the red test (finding 1). Run it locally only, skipped when absent (O2). The fake in A2 is the gate.

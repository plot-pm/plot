# Layering juror: fleetd's fixer and main-repair agents never start

Position: amend

The command shape belongs where the plan puts it: `roleCommand` in the domain builds a shell fragment, the `command` adapter runs it through `bash -c`, and the SDK adapter reads the same `agentsFile` itself. That split has a precedent (`reviewerCommand`, `review-verdict.ts:157`) and keeps the purity gate intact, because the domain only writes a string and never runs it. `--agents "$(cat '<file>')"` is the right seam for a small plan, and an argument array would change the `AgentRun` contract for every board role. Three things through this lens need amendment before approval. First, the root cause is a CLI version split, not a fixed CLI rule: fleetd resolves `claude` to `/opt/homebrew/bin/claude` 2.1.231, which takes only JSON, while `~/.local/bin/claude` 2.1.316 accepts a path under `-p` and started the fixer from the path form in my one run. Second, the failed-start part puts its decision in the wrong layer and claims a behaviour of `repair-role.ts` that is false on main. Third, the planned real-CLI test case cannot detect the defect on a current CLI.

## Findings

1. **high — The plan claims `repair-role.ts` already reports this failure; it does not.** `repair-role.ts:140-155`: `onStarted` resolves `started` to `true` on the pid, so `startRole` returns `'started'` before the CLI exits. `agentRunOf` returns `result.ok` (`repair-role.ts:190`), and `agent-run-command.ts:74-117` answers `ok` for every exit it can read, a non-zero one included (`end: { answer: 'unstarted' }`). So the warning at `:146` fires only when the spawn itself fails, never for `--agent 'main-repair' not found`. Live evidence: `.plot/state/main-repair/run.json` records `startedAt 1793557942178`, `endedAt 1793557944336` (2.2 s) and no warning names the cause. Checked by reading both files on `origin/main` and the live state.
2. **high — The root cause depends on the CLI version, and the plan states it as a fixed CLI rule.** `claude --help` on 2.1.316 reads `--agents <json-or-file>  JSON object defining custom agents, or with --print the path to a file that holds one`. On 2.1.231 it reads `--agents <json>`. fleetd (pid 87231) has `PATH=…/node/v26.13.0/bin:…/cmux-cli-shims/…:/opt/homebrew/bin:…`; the cmux shim removes itself from `PATH` and execs `claude`, which resolves to `/opt/homebrew/bin/claude` 2.1.231. My one run, `claude -p --setting-sources user --agent fixer --agents <path to a copy of 3023.agents.json> --model haiku --max-turns 1`, on 2.1.316 exited 0 and answered `OK`. The JSON-text form works on both versions, so the fix stays correct, but the Motivation must name the version split and the binary fleetd resolves.
3. **high — The planned real-CLI test case cannot fail on today's shape.** Approach step 2 adds a skipped-when-absent case against the real CLI. On any CLI at or after the version that accepts a file (2.1.316 here), the old path form passes, so that case proves nothing about the regression. Only the fake parser holds the 2.1.231 contract.
4. **high — The failed-start decision has no layer named, and the natural place for it is a callback that races the reaper.** `launchFixer` resolves on `onStarted` (`auto-fixer.ts` launchFixer) and the `.then` that later holds the run's `end` returns at once when `settled` is true, so the result is discarded today. The next tick reaps the attempt by pid (`endedFixerAttempts(attempts, world.pidCheck)`, `auto-fixer.ts:300`) and clears the mark (`:243`). A fix that writes "failed start" from that `.then` races the tick and is lost if fleetd restarts between the exit and the write. `CLAUDE.md` *A Decision Reads The Index* asks for a decision over recorded state; the log file is that state.
5. **medium — The CLI's failure line is harness vocabulary and has a declared home.** `packages/domain/src/adapters/harness/limit-lines.ts:1-14` says a harness's message text is a fact about that harness, held as data in an adapter, and matched only in a domain rule (`rules/prompt-exit.ts`) under the 100% branch gate. `--agent '<role>' not found` is the same kind of fact. The plan does not say where its pattern lives or which rule matches it.
6. **medium — The existing `unstarted` answer does not mean "died before its agent ran".** `prompt-exit.ts:393` answers `unstarted` for every non-zero status with no limit line, so a fixer that ran 60 turns and exited 1 reads the same as one that never started. Requirement 3 needs a narrower answer than the adapter gives today.
7. **medium — "The reviewer and unblocker roles share `roleCommand`" is false.** `git grep roleCommand origin/main -- 'packages/*/src/**'` finds two callers, `auto-fixer.ts:383` and `repair-role.ts:133`. The reviewer builds its command with `reviewerCommand` (`review-verdict.ts:169-184`), which passes no `--agents`, `--agent` or `--settings`. The unblocker has no role start through `roleCommand`. Both are names in `ROLE_NAMES` only. Every place that builds a role command with `--agents`, `--agent` or `--settings`: `role-command.ts:62-74` (defective on 2.1.231); `review-verdict.ts:169-184` (no `--agents`, not affected); `worker-prompt.sh:160` and `plot-dispatch.sh:823` (`--settings "$PLOT_AGENT_SETTINGS"`, a path, which both CLI versions accept as `<file-or-json>`, not affected); `plot-dispatch.sh:353` (`--agent` is Plot's own charter flag, not the CLI's).
8. **low — The fixer request does not carry `roleAgent`; the main-repair request does.** `repair-role.ts:175` sets `roleAgent: role`; `launchFixer`'s request has none. The SDK adapter reads `request.roleAgent` (`agent-run-sdk.ts:312, 426`), so the fixer cannot move to the SDK runner without a second change. It does not block this plan.
9. **low — Counts and line numbers.** `role-command.ts:55-75` is correct (the function ends at `:76`). `.plot/state/fixer/` holds 19 logs and 20 PR entries (`2975` has a lock only); all 19 logs end with `not found`, so "19 of 20" is 19 of 19 logs. The fixer budget is `FIXER_ATTEMPTS_BUDGET = 2` in `rules/fixer-attempts.ts:4`, a domain constant, not the `Correction budget` config key the Open Questions cite. 15 of 19 attempt records hold 2 attempts and record no `inFlight`, so their budget is spent.
10. **low — Doc comments that change with the shape.** `role-command.ts:5-7` and `:27` say the file is "passed as `--agents`"; `role-command.test.ts:21` asserts the exact path string; `repair-role.test.ts:86` asserts only `--agent main-repair`. The slice must update all four.

## Amendments I require

- A1. Motivation names the version split: fleetd resolves `/opt/homebrew/bin/claude` 2.1.231 (`--agents <json>`), the interactive shell resolves 2.1.316 (`--agents <json-or-file>` under `--print`). The fix keeps the JSON-text form because both versions accept it.
- A2. Remove the claim that `repair-role.ts` already returns `'failed'` for this case. State that `startRole` returns `'started'` and logs nothing, and add main-repair to the failed-start behaviour.
- A3. Remove "the reviewer and unblocker roles share `roleCommand`". Name the two callers. Keep the all-`ROLE_NAMES` test if wanted, and say it holds the rule, not a live caller.
- A4. The command-shape test runs the `roleCommand` fragment through `agentRunCommand` with a real `boundedRun`, with a fake `claude` first on `PATH` that rejects a non-JSON `--agents` value and prints `--agent '<role>' not found` with a non-zero exit. The test must not exec the fragment with its own `sh -c`, because the shell under test is the adapter's `bash -c '<fragment> "$@"'` (`agent-run-command.ts:65`). Its temp directory is removed by the exact name `mkdtempSync` returned. A mutation back to `singleQuote(role.agentsFile)` must fail it.
- A5. Drop the real-CLI case, or state that it checks only that the new form starts, never that the old form fails.
- A6. The failed-start pattern lives as data in `adapters/harness/limit-lines.ts` (or a sibling data file under `adapters/harness/`), and one domain rule matches it against the run's log, with a non-zero exit, under the 100% branch gate. No `.tsx`, controller or `.then` makes that decision.
- A7. The fixer records the failed start where the attempt is reaped (the pid-dead path at `auto-fixer.ts:243/300`), from the log file fleetd already writes (`.plot/state/fixer/<pr>.log`), so the answer does not depend on a callback that a tick or a restart can outrun. The `.then` in `launchFixer` may also write it, but the reap must give the same record whichever runs first.
- A8. The race test is deterministic: a stub `agentRun` calls `onStarted`, then resolves on a promise the test controls; the test runs the reap tick before and after the run resolves and asserts the same record in both orders. "CI ran green once" is not evidence.
- A9. Split into two slices: slice 1, the command shape and A4 (one file in the domain plus its test; it unblocks the fleet the day it merges); slice 2, the failed-start rule, its harness data, the fixer and main-repair records, and A8, depending on slice 1.

## Optional

- O1. fleetd logs the `claude --version` it resolves at start, so a version split is visible without `ps -E`.
- O2. Pass `roleAgent` on the fixer request too (finding 8), so both role callers carry the same port value.
- O3. `roleAgentsJson` refuses a JSON text over 100 KB. Linux limits one argument to 128 KiB (`MAX_ARG_STRLEN`); macOS `ARG_MAX` is 1048576. The live files are 1191 and 1257 bytes, so this guards a future, not today.
- O4. Write the fragment as `"$(cat -- '<file>')"` so a path that starts with `-` cannot read as a `cat` flag.
- O5. Note in Notes that fleetd's workers resolve the same 2.1.231 binary, and the limit lines in `limit-lines.ts` were measured on 2.1.286 and 2.1.291.

## Open questions

- Does the runner run the fragment through `sh -c`? Yes, through `bash`: `agent-run-command.ts:65` runs `env -u PLOT_REPO_ROOT bash -c '<fragment> "$@"' _ <prompt>`, and both callers build that adapter (`auto-fixer.ts:615`, `repair-start-world.ts:53`). `$(cat …)` expands. Recommendation: keep the file as the carrier, because `RoleAgentRef.agentsFile` is the port value the SDK adapter also reads (`agent-run-sdk.ts:312`); inlining `singleQuote(json)` would also be safe (`singleQuote` escapes any text) but gives the two adapters two carriers. Write in `roleCommand`'s doc comment that the fragment needs a bash runner.
- How is a start that ends before its agent runs detected? By a non-zero exit plus the CLI's `--agent '<role>' not found` line in this run's log, matched by a domain rule over harness data (A6). Not by the absence of a first agent event: the `command` adapter reads free-form text and has no event stream. Record it as a field on the attempt (for example `startFailed: { line }`), set on reap (A7).
- Does a failed start spend a correction attempt? No: no agent ran, so nothing was corrected. `fixerAttemptsSpent` skips an attempt that carries the failed-start field. The 15 spent records predate the field and carry no marker, and all 19 logs prove no agent ran; the plan names a one-time step after slice 2 merges in which a person moves `.plot/state/fixer-attempts/<pr>.json` for the still-open PRs to the Trash, rather than code that rewrites history.
- Is the real-CLI case run in CI? Neither: drop it (A5). CI has no `claude`, and a current local CLI accepts both forms, so the case cannot fail on the defect. The fake parser in A4 is the regression guard and runs everywhere.

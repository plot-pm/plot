### What to build

Seven independent cleanups, each verified against `origin/main` at `142bb5c21`. They share no code path with each other — work them in any order, but keep them as separable commits so a reviewer can check each claim against its own diff.

1. **Move `VERSION_NOT_FOUND` from the shell adapter to the port.** It is `export const VERSION_NOT_FOUND = 'version-not-found';` at `tracker-shell.ts:39`, with the string itself already documented as contract in the port's `versionRead` TSDoc (`ports/tracker.ts:303-308`: *"a reason that starts `version-not-found:`"*). Move the constant's declaration to `ports/tracker.ts`; update the two adapters that import it from `tracker-shell.ts` today — `tracker-jira.ts:21` and `tracker-fixture.ts:20` — to import from the port instead.
2. **Remove `issueListLabelled` from the port and every adapter.** Declared at `ports/tracker.ts:268`; implemented in all six adapters (`tracker-github.ts:145`, `tracker-jira.ts:147`, `tracker-none.ts:33`, `tracker-fixture.ts:186-190`, `tracker-resolve.ts:103`, `tracker-shell.ts:337-346`). Zero production callers remain: `review.ts:232` already calls `issueListWithTitle` instead. Also remove the fixture's now-dead config fields `labelled` (`tracker-fixture.ts:55`) and `issueListLabelledFails?` (`:57-58`), and reword `issueListWithTitle`'s TSDoc at `ports/tracker.ts:278`, which still cross-references the operation you are deleting (`{@link issueListLabelled}`).
3. **Fixture's `versionRead` must count pages through the version-list request, matching the real adapter.** `tracker-jira.ts:216` counts `issues.value.pages + projects.projects.length` — one "page" per project's version-existence check, which is the real request cost wave 2 fixed the shell side of. `tracker-fixture.ts:164-174` does not add this: it reports `pages: pagesOf(Math.min(withVersion.length, limit))` with nothing for the version-list lookup. Bring the fixture's count in line with the adapter's, so a test against the fixture cannot pass while the real page-cost accounting regresses.
4. **State current behaviour in the stale test comment and test names.** `review.test.ts:667-668`'s comment narrates "the old `issueListLabelled` read" in the past tense to explain why `issueListWithTitle`'s title-filtering matters — rewrite it to state what `issueListWithTitle` does now, not what the deleted op used to do. `tracker-shell.test.ts:604` and `:615` name `issueListLabelled` in their *test titles* while actually testing `issueListWithTitle` ("...same as issueListLabelled" / "...same shape as issueListLabelled") — rename both titles to drop the comparison to an operation that no longer exists.
5. **`issue-source.ts` parses the `Tracker` scheme three times — collapse to once.** All three are in `packages/domain/src/rules/issue-source.ts`, the identical idiom (`<value>.trim().split(/\s+/, 1).join('').toLowerCase()`): `issueSource()` at `:62`, `sprintOwner()` at `:135`, `bbIssueCommandMissing()` at `:166`. Extract one helper and use it in all three.
6. **`sprintOwner`'s TSDoc states the drift direction backwards.** The doc (`issue-source.ts:107-127`, above `sprintOwner` at `:131`) justifies declining sprint ownership on a declared external tracker with *"because a shadow sprint board drifts from the one plot would otherwise keep"* — read literally, that blames drift on the board Plot would keep, when the actual reasoning is the reverse: Plot declines to run a second, Plot-owned sprint board specifically because a second board alongside the external tracker's is the one that would drift. Restate the causality so a reader doesn't have to invert it: two independently-updated sprint representations drift apart, so Plot does not create the second one — unless the repository names `Sprint owner: plot` explicitly.
7. **`plot-detect-repo.sh` must count a prefix once per branch, not once per occurrence.** `top_prefix()` (`:62-65`, shared by both the commit-subject and branch-name reads) is `grep -oE '...' | sed ... | sort | uniq -c | sort -rn | head -1` — `grep -oE` emits one match per occurrence, not one per line. Reproduced directly: two branch names, one with a ticket prefix repeated twice in its own name, feeding `top_prefix` reports a count of 3, not 2. The branch-name call site is `:181` (`branch_ticket_count`); the surrounding comment's "each name counted once" (`:178-179`) is true only of the ref-dedup step above it, not of what `top_prefix` itself counts. Fix so one branch containing the prefix twice in its name still counts as one occurrence of that branch having the prefix — e.g. dedupe matches per input line before the aggregate count, or take the first match per line. The commit-subject call site (`:168`, `ticket_count`) shares the same helper; decide whether it needs the same per-line dedup or whether a commit subject's own vocabulary makes a double-prefix subject a legitimate double signal — the plan's slice line names branches, not commits, so default to fixing `top_prefix` only where branches call it unless the shared-helper shape forces otherwise.

### Settled — do not re-derive

**Item 7 of the plan's Motivation ("a repository with no `Tracker` key gets advice that makes Jira the sprint owner") did not reproduce against current `main`.** `bbIssueCommandMissing` (`issue-source.ts:163-170`) already returns `declareOne` — "declare the issue tracker with the `Tracker` config key," naming no tracker — on an empty `declared` string. The `Sprint owner: plot` / `Tracker: jira <base URL>` suggestion only fires on the *other* branch, when `declared` is non-empty and its scheme is `NO_EXTERNAL_TRACKER` (i.e. the repo already wrote `Tracker: plot` and gets told what to add). `issue-source.test.ts:95`, `host.test.mjs:2401-2403` and `issue-source-entry.test.ts:101-104` all confirm the empty-key case already stops at "declare the `Tracker` config key." **Before touching this path, re-check against issue #2483 whether this bullet points at `bbIssueCommandMissing`, or at a different advice surface — `/plot-init` or `/plot-board-setup`'s adoption-proposal logic, which this brief did not audit for this specific claim.** If it is already fixed, say so in the PR description and move on; do not invent a regression to satisfy the plan's wording.

**`skills/plot-board-setup/SKILL.md` already states two separate rules that bear on this, and neither resolves their combination.** Lines 209-229/661-662 say a proposed `ticket.prefix` is evidence for `Tracker: jira`, and a `null` `ticket.prefix` means "ask which tracker, never propose `Tracker: none` from silence." Line 268 separately says an undeclared `Tracker` key reads the same as `Tracker: plot`. What the doc never states is which of those two answers wins when **both** hold at once — no `Tracker` key declared *and* `ticket.prefix` is `null`. Add the missing precedence sentence near one of the two existing passages; do not restate either rule, name which one governs the overlap.

**The empty-stdin entry test is missing an assertion, not asserting the wrong thing.** `issue-source-entry.test.ts:101-104` checks only that the output contains `` `Tracker` config key `` for empty stdin; it makes no claim about `Sprint owner: plot` either way. Add `expect(stdout).not.toContain('Sprint owner: plot')` to the same test — do not write a new test, and do not confuse this with `host.test.mjs:2421`, which already asserts `Sprint owner: plot` is *present* for the separate `Tracker: plot`-declared case and is correct as-is.

**Only three test locations name `issueListLabelled`, not the plan's stated four.** `review.test.ts:667` (comment) and `tracker-shell.test.ts:604`, `:615` (test titles). Treat "four" as approximate; grep `issueListLabelled` across `packages/domain/test/` and `packages/board/test/` yourself before closing this out, in case something shifted since this brief was written — but do not manufacture a fourth to match the number.

**Carried over unchanged.** `plot-host.sh` itself is out of scope for this wave — waves 1 and 2 already closed its `issue-view` and `issue-list --fix-version` defects. The board-side `issue-source.ts` (`packages/board/src/server/entry/issue-source.ts`) does not duplicate the scheme parse; only the domain file does (item 5 above is scoped there alone).

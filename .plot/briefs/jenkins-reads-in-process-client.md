### What to build

An in-process Jenkins HTTPS client with its own credentials, bearer refresh and ledger account, plus the census that measures Jenkins before any read moves. Today fleetd reads Jenkins through `plot-host.sh` and `jen` (a 1,819-line bash script): on a Bitbucket repository with `CI: jenkins` every 60 s PR beat runs `plot-host.sh pr-list --rich`, which starts 3 `jen` trees for the colour map and up to 10 `jen api` trees for 5 rows. No census row names Jenkins, so that count is a code reading and not a measurement.

Build:

- `connector-https.ts` (`packages/domain/src/adapters/host/`): a form body (`application/x-www-form-urlencoded`) on `ConnectorCall`, for the refresh grant. The JSON path stays as it is.
- `adapters/build/jenkins-api.ts`: the one module that builds requests to a Jenkins instance, over `connectorHttps`. No `node:https` import (`scripts/check-host-https-callers.sh` does not change). It holds the instance URL, both headers (`Authorization: Bearer`, `X-Jenkins-Authorization: Basic`), the credential sources, the refresh with its lock, the write-back, the status and redirect rules, and the ledger account.
- `rules/jen-url.ts` and the other declared `jen` duplicates: `jen_instance_url`/`jen_url_for` (no pattern arm), `jen_url_host`, `jen_key_for`, `jen_secret_file`, `jen_save_token`, `jen_job_path` with `jen_urlencode`, `jen_check_http`'s redirect classes, the `.jobs` projection.
- `packages/domain/corpus/record-jenkins-reads.mjs` (model: `record-github-issues-runs.mjs`; lift the `jen` functions with `awk` as `bitbucket-budget-account.corpus.test.ts:52-54` does) and `jen-url.corpus.test.ts` against its committed outputs. The recorder checks `jen` reports `0.4.0`. A person runs it once per `jen` version.
- Census (`packages/fleet/test/census/`): `ci` and `recordOnly` on `CensusFixture`; `ci` in `entryKey`, `rowTitle` and `sizeLine`; a Jenkins route and a token route on `stub-host.ts`; per-run Jenkins answers in `sandbox.ts` and a stub `jen` over the same answers; the pinned sandbox Jenkins environment; the fourth `FIXTURES` entry `{ host: 'bitbucket', desks: 3, openPrs: 5, ci: 'jenkins' }`; row P12 (`green: false`) with its baseline recorded in the story's *Measures*; the HEAD census time stated in the PR.
- `bitbucket-budget-account.corpus.test.ts` gains a row that calls the lifted `budget_account` with `jenkins`.

### Settled decisions — do not re-derive them

- **Credentials: the environment and `jen`'s file backend only (decisions 1, 6, 8).** The client runs no `security` and reads no `.env`. `plot-host.sh` and `jen` read no Jenkins credential from `.env`, so a `.env` source would give the two transports two identities, and `PLOT_HOST_TRANSPORT=shell` would switch more than the transport. fleetd's launchd unit carries `PATH` and `PLOT_REPO_ROOT` only, so `JEN_SECRET_BACKEND=file` never reaches it. The client therefore probes `${JEN_CONFIG_DIR:-${XDG_CONFIG_HOME:-$HOME/.config}/jen}` for `keycloak-token.secret` with no `JEN_SECRET_BACKEND`. A machine with neither source keeps the shell, and fleetd logs the reason once. The operator's own machine uses the Keychain, so it keeps the shell until `JEN_SECRET_BACKEND=file jen auth login`.
- **No organisation's hosts in Plot.** `JEN_URL_PATTERN` and the default `JEN_REALM_URL` name one company. Do not copy them. A bare slug with no `JEN_URL` keeps the shell (`the Jenkins instance is a slug; write its host`). The realm comes from `JEN_REALM_URL`, else the `iss` claim of the stored access token, read without a signature check (the store is the user's own file, mode `0600`). No `iss` keeps the shell (`the stored token names no realm`). `grep -n quatico` over the new files must find nothing.
- **A credential goes only to `https:` or loopback.** The transport admits `http:` for any host (`connector-https.ts:50`, `:175`), so the client is the only guard. It applies to the instance URL, to the realm URL from either source and to the token endpoint.
- **Refresh: write back to the store, under a lock (decision 2, option A).** The bearer lives 300 s and `jen` stores `expires_at` 30 s early, so a long-lived reader refreshes about every 270 s. Option B (refresh in memory only) breaks the operator's `jen` where the realm rotates refresh tokens. The lock is `O_EXCL` on `keycloak-token.lock` in the store directory, stale after 30 s, per user and not per repository: a lock under `.plot/state` would let two fleetds post a grant from one refresh token. Under the lock, re-read the store and adopt a newer blob before posting a grant. On `invalid_grant`, re-read once and adopt a newer blob, else refuse with kind `auth`. An empty or unparseable blob is a torn read of `jen`'s in-place write (`jen:134`): re-read once after 100 ms. Write back through a temp file in the same directory, `O_CREAT | O_EXCL`, mode `0600` at open, then `rename`. Never write the environment or `JEN_TOKEN`, and never migrate or delete a per-instance key (`jen_migrate_instance_keys` is not copied).
- **Status and redirects.** The transport follows no redirect, and a row pins that. `401`, `403`, and a `3xx` to `/oauth2/` or the realm host re-read the source once and retry once, then refuse with kind `auth` and `jen auth login` in `said`. A `3xx` to the instance's own host is an answer. A `3xx` to any other host, or with no `Location`, refuses with kind `unaskable` after one request, so no credential reaches that host.
- **No credential in text.** A refusal's `said` takes only `error` and `error_description` from the token endpoint, never its body. An HTML body is cut to 200 characters with tags removed. A leak row asserts no bearer, refresh or API-token value in fleetd's log, the status line, any ledger line or any `said`. The refresh token never goes in argv.
- **Ledger account (decision 3, option A).** Connector `jenkins`, bucket `''`, account `bitbucketBudgetAccount(null, process.env.PLOT_BUDGET_ACCOUNT)`: the shell's `budget_account jenkins` matches no arm, so the key is `PLOT_BUDGET_ACCOUNT` else `unknown`. Instance requests record basis `predicted`, limit 60, as `ci-limit` does. The refresh POST uses bucket `token` with basis `unknown`: `connectorHttps` keys the slot bound on connector and account (`boundKey`, `:222`) and any entry whose basis is not `unknown` sets it (`:235`), so a `token` entry must not set the bound. Do not change the key; a change belongs to both transports in one later change.
- **Census answers are written per run.** The sandbox commits at run time and every PR head is the `mainSha` that `rev-parse` reads (`sandbox.ts:281`, `:286`), so a recorded build can never name this run's head. Write the Jenkins answers from the run's head SHAs, as the `gh`/`bb` answers are (`answer(...)`, `sandbox.ts:302-347`). One PR branch is `blue` with a `SUCCESS` build of its head, so the shell run's store binds a `checks` word other than `unknown`. The stub `jen` prints the output shapes the recorder took from the real `jen` 0.4.0. Without this the census compares `unknown` with `unknown`.
- **The sandbox starts from `...process.env`.** Set `XDG_CONFIG_HOME` and `JEN_CONFIG_DIR` under the sandbox root and delete `JEN_TOKEN`, `JEN_SECRET_BACKEND`, `JENKINS_USER`, `JENKINS_API_TOKEN`, `JENKINS_INSTANCE` and `PLOT_JENKINS_JOB` before setting the census values. Point both transports at the stub with `JEN_URL=http://127.0.0.1:<port>/jenkins` and `JEN_REALM_URL=http://127.0.0.1:<port>/realm`, and write a `keycloak-token` blob past `expires_at` so the first pass refreshes.
- **`recordOnly` keeps the shared rows honest.** S4 (`fleetd.census.test.ts:279-283`) and P10 (`:341-350`) assert zero on every fixture, and the Jenkins fixture breaks both until the Cutover because `SHELL_RICH_CI` still sends its rich read through the shell. The fixture lists S4, P2, P3, P4, P7, P8, P10 and P11 in `recordOnly`, which skips the `expect` calls and keeps `recordCount`. S8's lower bound still asserts. The three existing fixtures set no `recordOnly`. The PR names each listed row that reads above 0, with its commands.
- **The census key names CI.** Without `ci` in `entryKey`, `compareCensus` keeps the last of two equal keys (`census-report.ts:187`) and compares one fixture only.
- **Vendor gate.** CI's *The domain names no vendor* (`ci.yml:1666-1672`) greps code lines under `packages/domain/src/` outside `adapters/` for `jenkins`, and an import path is a code line. Name new rule modules with no standalone `jenkins` token (`rules/jen-url.ts`). Keep string literals that name `jenkins` inside `adapters/build/`. No module outside `adapters/` imports `./jenkins-pr-checks.js`.
- **The rotation measurement is a person's step.** A person with a device-flow login runs two refreshes from one refresh token against a throwaway session, and records in the story's *Measures* whether the realm rotates refresh tokens for `client_id=cli`, whether reuse of a rotated token revokes the session, and whether `iss` equals the realm URL. An unattended worker cannot log in: leave this step, name it in the PR, and do not write the *Measures* line yourself. The result decides the Cutover (a `PLOT-BLOCKED` marker there if reuse revokes).
- **Census time.** The fourth fixture adds about 240 s. The HEAD census reads 500 s and 591 s on the two latest green `main` runs, so about 740 s to 830 s with it. The cap holds a 1.45 margin only up to 828 s. State the measured time in the PR. Above 828 s, raise `timeout-minutes` in the same PR to 1.45 times the measurement rounded up to a whole minute, and update the comment.
- **Rules carried over, not re-learned.** Absent is not false: a dead session is a refusal of kind `auth`, never an empty answer. Read the status and the redirect, not the emptiness. On a corpus disagreement the branch stops; adjust neither side to make it pass (`CLAUDE.md`, *A Shell Script Asks The Domain*). A corpus test reads recordings only and runs with no host token (`corpus/no-host-token.ts`).

- Composition rows: with only `PATH`, `PLOT_REPO_ROOT` and `HOME` set and a token file under `$HOME/.config/jen`, the composition picks in-process and names the directory; with no token file, or only a `.env` holding `JENKINS_API_TOKEN`, it picks the shell with the reason, logged once.
- Ledger rows: one instance request appends one entry (`jenkins`, `''`, `predicted` 60); one refresh appends one `token` entry with basis `unknown` and leaves the slot bound unchanged.

- The census job is green at the PR's head, and CI's census time is stated in the PR.

Assertions a naive implementation passes without, and what each catches:

- The two-process refresh row uses two repository roots. One root passes with a per-repository lock and the bug it hides is two fleetds over one store.
- The partial-blob reader row polls during the write-back. A plain `writeFile` passes every single-read test.
- The third-host redirect row asserts the stub third host got no request. Without it a client that follows the `Location` passes and leaks both headers.
- The leak row uses recognisable secret values. A refusal that echoes the token endpoint's body passes every status test.
- The `token`-bucket row checks the slot bound. A refresh charged as `predicted` 60 passes the ledger row and moves the bound.

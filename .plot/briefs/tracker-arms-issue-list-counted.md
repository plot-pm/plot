### What to build

`plot-host.sh issue-list --fix-version` (the Jira "which issues ship in this release" read, `:5072` onward) has four separate defects in its argument handling and request accounting. Measured on `origin/main` after wave 1 merged:

- **The version-exists check is duplicated, not uncounted — but it escapes `pages`.** `versionRead` in `packages/domain/src/adapters/tracker/tracker-jira.ts:189-213` already calls `reads.versionList(project)` once per `Ticket prefixes` project before calling `reads.issueListVersion(name, limit)`. That call becomes `walk(['issue-list', '--fix-version', name], limit)` in `tracker-shell.ts:409-410`, and `walk` (`tracker-shell.ts:284-306`) invokes the shell once per PAGE. The shell's own version-exists loop at `plot-host.sh:5152` (one Jira call per `Ticket prefixes` project) reruns on every one of those page calls — so a 3-page read over 2 projects makes the existence loop run 3 times, 6 Jira HTTP calls total. Each one IS recorded in the spend ledger (`jira_curl` → `budget_record_jira` on every call, unconditionally — read it at `:3015-3037` before assuming otherwise), so this is not an unmetered spend. What is wrong is `pages`: `versionRead` computes `issues.value.pages + projects.projects.length` — it adds the project count once, not once per page, so `pages` undercounts the true Jira call total whenever the version read spans more than one page. Fix the undercount, or make the shell check run once regardless of page count — pick one and say which in the PR description; either removes the double-count, and the Open Question below asks which path the plan meant.
- **The cut-result notice is a stderr `echo` already, not a warning that needs demoting.** Re-read `:5227` before changing it: `[ "$cut" = true ] && echo "plot-host: jira issue-list state=$state possibly truncated ..." >&2` already matches the precedent's shape (`pr_list_report_truncation`, `:3221-3241`, "absence, never presence, is the signal", also a stderr `echo`). The plan's Motivation line ("uses a stderr warning, which the sibling plan... reject[s]") describes the state the code was in when issue #2483 was filed; confirm against the sibling review (issue #2259) what specifically it asked for before writing a replacement — the review's two MEDIUM findings are about the duplicated version check above (now this slice's first bullet) and about the notice firing on an exactly-full, complete page, not about stderr-vs-exit-code. Read Open Question 1 below; it is unresolved and this slice must resolve it, not assume it.
- **`--limit` passes a bash regex check and then silently does nothing.** `:5217`'s guard `[[ "$max" =~ ^[0-9]+$ ]] && [ "$max" -gt "$ISSUE_PAGE_ROWS" ]` matches a value like `99999999999999999999` against the regex (true), then `[ "$max" -gt 100 ]` throws `integer expected` to stderr and the test evaluates false — so the whole `&&` chain is false, the refusal never fires, and the oversized value reaches Jira's `maxResults` query param unbounded. Verified by hand: `[ "99999999999999999999" -gt 100 ]` prints `bash: line 5: [: 99999999999999999999: integer expected` and returns non-zero. Bound `--limit` to a range `[` can compare before this test runs.
- **A later `--state` silently drops `--fix-version`.** The arg-parsing loop (`:5085-5097`) sets `state=version` as a side effect of `--fix-version`, but `--state` is a separate case arm that overwrites `state` unconditionally. `issue-list --fix-version 2.28 --state closed` ends with `state=closed`, `fix_version=2.28` still set but never read again — the closed-read branch (`:5173-5185`) ignores `$fix_version` entirely and the version filter silently disappears. Verified by hand by tracing the parse loop with that exact argument order. Decide the arm's own precedent (`--fix-version` wins, as the two flags are not independently meaningful — `--state version` alone, with no `--fix-version`, already has nowhere to get a name from) and refuse the conflicting combination rather than silently resolving it either way.

The plan is canonical; this brief is orientation.

### Settled — do not re-derive

**The spend ledger and the `pages` field are two different things.** Every Jira HTTP call is recorded in `$HOME/.plot/state/budget.tsv` through `budget_record_jira`, with no conditional path around it — confirmed by reading `jira_curl` (`:3015-3037`), which calls it unconditionally after every `curl`, success or failure. "Uncounted" in the plan's Motivation means `pages`, the per-operation count `tracker-jira.ts` reports upward for the adapter's own accounting, not the budget/rate-limit ledger. Do not go looking for a call that evades `budget_record_jira` — none exists in this path, and an attempt to make one "counted" there would fix a thing that was never broken.

**The precedent for a cut-result signal is `pr_list_report_truncation` (`:3221-3241`) and its sibling `pr_list_report_complete` (`:3251-3253`), both stderr, both one line, BOTH SENTENCES OR NEITHER.** The comment at `:3201-3204` states the rule: a reader never sees both for one state, and silence means no claim was owed. The `issue-list --fix-version` cut notice at `:5227` is unpaged (no `--paged` state reaches it unless the plan's design changes that), so there is currently no `pr_list_report_complete`-shaped counterpart for the un-cut case — decide whether one belongs here as part of resolving Open Question 1, consistent with the precedent's "both or neither."

**`[ -n "$found" ] || { echo "version-not-found: $fix_version" >&2; exit 4; }` at `:5152` already fails before any curl is wasted if `jira_ask` itself fails** (`|| exit $?` inside the `for` loop) — absent is not false, a failed lookup must not read as not-found. Keep that `|| exit $?` whatever restructuring the de-duplication above needs; it is the same invariant CLAUDE.md's "The index never says no" section states for a different index, applied here to the version list.

**`ISSUE_PAGE_ROWS` is `100` (`:628`), the same constant used for both the `--paged` default and the unpaged refusal threshold at `:5217`.** Do not hardcode `100` a second time; both guards already share the one constant and a new check should too.

**Carried over unchanged.** `fields=` request shapes, the `person=`/`scope=` splice order, and the `PLOT_JIRA_JQL` override's precedence over everything in this arm are wave 1's territory and untouched here — wave 1's brief already named why they are the way they are. Exit codes stay as the header documents unless this slice's Open Question 3 below decides otherwise for the one code in question.

### Done when

The plan's slice line is the specification: the fix-version check runs once per question and the request goes through the counted path (restated above: the count that was wrong is `pages`, not the ledger), a version list `jq` cannot parse exits as a failed question, `--limit` is bounded before the numeric comparison, a later `--state` does not override `--fix-version`, and the header documents the invocation the adapter uses. The assertions that exist because a naive change would pass without them:

- A `--fix-version` read spanning more than one page reports a `pages` count that matches the actual Jira call total (existence-check calls included), not just `issue pages + project count`. Catches a fix that touches the shell's duplicate check but leaves the TS-side undercount.
- `jq` fed deliberately unparseable version-list JSON (not empty, not valid — malformed) causes `issue-list --fix-version` to exit as a failed question, never as `version-not-found`. Catches a fix that treats "cannot parse" and "parsed, found nothing" as the same outcome.
- `--limit 99999999999999999999` (outside bash integer range) is refused before any curl runs, not silently passed through to `maxResults`. Catches a bound check that still relies on `[ -gt ]` alone without a range pre-check.
- `issue-list --fix-version 2.28 --state closed` (fix-version first, state second) is refused or resolved by a named, tested rule — never silently drops the version filter and runs a plain closed read. Catches the arg-order bug whichever way the fix resolves it.
- `issue-list --state closed --fix-version 2.28` (state first, fix-version second) resolves the same way the other order does — the fix must not depend on argument order to be correct.
- The cut-result notice, whatever its final mechanism, prints for a truly cut page and does not print for a page that came back under the limit — both sides of "both sentences or neither" get a test, the way `pr_list_report_truncation`/`_complete` already do for the PR-list arm.

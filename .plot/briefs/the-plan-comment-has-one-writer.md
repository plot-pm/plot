### What to build

Gap 4 of the plan: the plan-state comment (`<!-- plot:plan-link -->` on a tracked issue) currently has four ways to end up wrong — a lock release that can delete another writer's lock, a failed read-back that silently erases existing ticket/progress lines, a login-scoped comment lookup that posts a second comment when a different GitHub account writes, and a progress write with no phase check inside its lock. Findings #2935 (2 MEDIUM, against `packages/domain/src/adapters/tracker/tracker-plan-state.ts`) and #2924 (3 MEDIUM, against the plan text itself, same code) are the review record of these; this slice is their fix, re-checked against the current code rather than re-litigated.

Four fixes, all in the write path `githubPlanStateWrite` → `plot-host.sh` → `gh`:

### The decisions the plan settles — do not re-derive them

**1. A lock not taken must not be released.** `withIssueLock` (`packages/domain/src/adapters/tracker/tracker-plan-state.ts:127-156`) always returns a release function, even on the two paths where it never actually held the lock: the 5 s `LOCK_WAIT_MS` deadline passing (`:148`), and `link()` failing with a code other than `EEXIST` (`:138`). Both paths `break` out of the loop and fall through to the same unconditional `return` at `:153-155`, which `unlink`s `lockPath` — the file whatever OTHER writer is currently holding. #2935's MEDIUM: "the lock release deletes another writer's lock." Fix: track whether this call actually completed the `link()` that took the lock; return a no-op `async () => {}` when it did not, and make the caller (`githubPlanStateWrite`, `:188`) fail the write on that case rather than proceeding unlocked — the docstring at `:124-125` ("the write proceeds unlocked rather than silently skipping forever") is the behavior being removed, not kept. Do not just extend `LOCK_WAIT_MS`: that narrows the race, it does not close it.

**2. A failed read-back must fail the write, not erase.** `githubPlanStateWrite` (`:191-195`) calls `issue-comment-read` and treats ANY non-zero exit the same as "no comment exists" — `prior` becomes `null` only by construction of `said.code === 0 && said.stdout.trim() !== ''`, so a transport failure (`gh_fail`, exit 3 from `plot-host.sh`) silently reads as empty too. `filled` (`plan-issue-comment.ts:112-116`) then renders a two-line body with no progress line and no ticket links, overwriting whatever the comment held — and `writeWrittenHash` (`:216`) records that shortened body's hash, so a later identical write from the same machine is suppressed by the hash gate and never repairs it. #2935's MEDIUM. Fix: branch on `said.code`, not just on stdout content — a non-zero exit returns `failed()` immediately (same shape as the `issue-label`/`issue-comment` step loop at `:205-215`), and the "no comment, start fresh" interpretation applies only to `code === 0` with empty stdout.

**3. The marker lookup must not be scoped to one login.** `gh_marker_comment_id` (`skills/plot/scripts/plot-host.sh:700`) is NOT the simple "restricted by account" bug the plan motivation implies at a glance — re-read it before touching it: `select($who == "" or (.user.login // "") == "" or .user.login == $who)` already falls back to an unscoped match when `gh api user` answers no login (App token, 403) or the comment has no `user` field. What it still restricts is the ordinary case: two different real logins (a person's machine vs. fleetd's token, or two people) both resolve a login, and the marker match requires them to be equal. That is exactly `test('host: issue-comment with a marker held only by another author's comment posts instead of editing')` in `test/reconcile/host.test.mjs:11149-11157` — a second account's comment is deliberately ignored today, which is the bug. #2924's MEDIUM: "decision D6 and the 'one Plot comment' promise ignore that the comment lookup filters by login." Fix: drop the `.user.login == $who` branch of the `select` — the marker alone decides the match, first by creation (`gh api --paginate` already returns oldest-first; `[0]` after flattening keeps that). This DOES NOT grow the net shell-line count if done by deleting the login-comparison clause rather than adding a new one (`scripts/check-shell-lines.sh`). The existing test above must be rewritten to assert an edit, not a post, when the comment's login differs from the caller's — do not just delete it; a dropped test here would hide the exact regression check gap 4 exists to add. The `$who` computation and the `gh api user` call stay — nothing else in `plot-host.sh` reads `$who` to be sure, but removing the call outright is a larger diff than this fix needs; confirm nothing else uses `$who` before deciding whether to also drop the call itself.

**4. A late progress write must read the phase inside the lock.** `auto-progress.ts`'s `runAutoProgressPass` (`packages/fleet/src/shared/auto-progress.ts:26-50`) decides to write from a pulse that may be stale by the time the write actually lands — fleetd runs detached and the gap between reading `plan.phase === 'approved'` (`:35`) and the eventual `plot-plan-state.sh` call (`:39-47`) is not inside any lock. If a human's Delivered or Released write (through `approve.ts`/`deliver.ts` → `plot-plan-state.mjs`) lands in that gap, the late `approved` progress write can still fire afterward and the comment regresses from "Plan delivered" back to "Plan approved: …, N/M merged". #2924's MEDIUM: "a late progress write can still overwrite a Delivered comment." Fix: the phase check that gates whether a progress write proceeds must happen inside the SAME per-issue lock `githubPlanStateWrite` takes for the label-and-comment write — not before it calls into that path. Read `.plot/state/plan-state-written.json`'s sibling phase record (or re-read the plan's phase on the default branch) after acquiring the lock, immediately before composing the body, and skip the write if the phase has since moved past `approved`. Where exactly this check lives (inside `githubPlanStateWrite` itself, keyed on an optional phase-reread callback, vs. a precondition `runAutoProgressPass` passes through) is this slice's call — the constraint is only that it run after the lock is held, not before `plot-plan-state.sh` is invoked.

**Also carried over unchanged, confirm rather than rediscover:** the hash gate (`alreadyWritten`, `:198`) compares the FULL rendered body including progress/tickets, so fix 2 and fix 4 both change what gets hashed — a write that used to be suppressed as a duplicate may now differ once the read-back or the phase check behaves correctly; that is expected, not a regression. The `released` close (`:219-229`) is deliberately NOT gated by the hash check (the docstring at `:166-168` says why: closing twice is a harmless no-op, and the hash gate must not also suppress the close) — do not fold the close into the `alreadyWritten` branch while touching this function.

### Done when

The plan's `## Done when` table rows for "Plan comment":

|---|---|---|---|

| A failed read-back fails the write | `issue-comment-read` exits 1 | `failed`; no `issue-comment` call; no hash recorded | `packages/domain/test/tracker-plan-state.test.ts` |
| One comment across accounts | `gh` stub: marked comment by login X, current login Y | one comment edited, zero created | `test/reconcile/host.test.mjs` |
| A Delivered write keeps the progress line | prior comment with a progress line; `delivered` write with no `--slice-progress` | the posted body keeps the line | `packages/domain/test/tracker-plan-state.test.ts` |
| A late progress write does not undo a delivery | phase reads `delivered` inside the lock when the progress write runs | no `approved` label, no write | `packages/fleet/test/unit/auto-progress.test.ts` |

Lift from these the assertions that exist because a naive fix would pass without them: the lock test must prove the FOREIGN lock file survives (not just that this call's write failed) — a fix that returns a no-op release but still unlinks under a different code path would pass a "write fails" assertion alone; the read-back test must prove `issue-comment` is never called AND no hash is written — a fix that fails the write but still records a hash would silently suppress the correct retry; the cross-account test must prove exactly one `issue-comment`-shaped edit call and zero post calls — asserting "no error" alone would pass today's broken posting behavior too; the late-write test must construct the race (phase changes between the initial pulse read and the lock being taken), not just check today's already-passing synchronous case.

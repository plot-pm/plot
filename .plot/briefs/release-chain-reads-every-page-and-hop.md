### What to build

`plot-reconcile-scan.sh` section 6 (and the release chain generally) can report a wrong tag, or no tag, for a plan whose PR merged into a branch other than `main`. Issue #2480's findings #2238 and #2202 name three defects on this path:

1. **GitHub side of `pr-merge-dest` (`skills/plot/scripts/plot-host.sh:4181`) reads one page of 100 PRs and promises every merged one.** `gh pr list --head "$ref" --state all --limit 100` has no paging loop. The sibling op `pr-merged` has the same shape and is deliberately unpaged (its header says 100 is "ten times any population measured") — but `pr-merge-dest` serves a *walk*, not a yes/no: a branch with 101+ merged PRs silently drops the ones past the 100th from every hop's candidate list. The Bitbucket arm (`bb_branch_query` → `_bb_paged_walk`) already pages fully (#2484) — only GitHub is capped.
2. **Bitbucket side (`plot-host.sh:4200-4203`) uses `updated_on` as `mergedAt`.** Bitbucket's pull-request payload has no merge timestamp field in this query; `updated_on` is the last-modified time, which can postdate the actual merge (a later comment, label, or re-open/re-close touches `updated_on` without remerging). `pickReleaseHop` (`packages/domain/src/rules/release-chain.ts:125`) orders candidates by `mergedAt` to pick the earliest-qualifying one — a wrong timestamp can pick the wrong hop on a branch with several merged PRs.
3. **The first hop's `previous.mergedAt` starts empty.** `release-chain.ts:153`: `previous = { commit: reading.planCommit, mergedAt: '' }`. `pickReleaseHop` treats an empty/unparseable `mergedAt` as "no ordering signal" and falls into the branch at `:133-136` — any one candidate of unknown containment qualifies unconditioned on time, and two or more are `ambiguous`. The plan's own PR merge time is knowable (the scan already has it, from the `pr-state` row that triggered the walk) and is never passed in, so the first hop is weaker than every later one.
4. **The missing-merge-commit advice is generic and overclaims.** `packages/board/src/server/entry/release-chain.ts:65-68`, `fetchAdvice`: for GitHub it always says `inspect: git fetch --tags origin, then re-run`, regardless of whether the clone was made with `--no-fetch`/is shallow (where a fetch *would* help) or the commit is simply on a branch this clone's remote never carried (where it would not). `refusalText` (`:76-82`) likewise never says that nothing was verified — `host-failed` and `ambiguous` read as resolved facts about the chain rather than "the walk could not finish."

> **Correction to the plan's own citations:** the plan's Motivation section cites `release-chain.ts:65` and `:67` for the advice/cause text. Those lines are in `packages/domain/src/rules/release-chain.ts` only in the sense of line *position* — the actual advice logic (`fetchAdvice`, `refusalText`) lives in `packages/board/src/server/entry/release-chain.ts:65-82`, a different file. `packages/domain/src/rules/release-chain.ts:153` (the empty `previous.mergedAt`) is correctly cited. Don't spend time looking for advice strings in the domain file — there are none; `release-chain.ts` under `rules/` is pure decision logic with no user-facing text.

### Settled decisions — do not re-derive

- **Paging fix is GitHub-only.** Bitbucket's `pr-merge-dest` arm already walks every page (`_bb_paged_walk`, landed under #2484) — do not touch it. Give the GitHub arm the same shape `pr-merged`'s header explicitly declines for itself: this op is a walk's single source of truth per hop, not a yes/no gate, so under-reading here is a silent wrong answer rather than a cheap prefilter. Follow `gh pr list`'s own pagination (`--paginate` with `-q`, or manual `--limit`/cursor loop) — check what `_bb_paged_walk`'s GitHub-side siblings elsewhere in `plot-host.sh` already use before inventing a new pattern.
- **Bitbucket merge time: there is no merge-time field on this endpoint — document the ceiling, don't fake a fix.** `bb pr list`/the pull-requests API for Bitbucket Cloud does not return a merge timestamp; `updated_on` is genuinely the best available. If a per-PR detail call exposes a real merge time, that is a second call per candidate per hop — weigh the cost against `pickReleaseHop`'s actual sensitivity to ordering (it only matters when a branch holds *several* merged PRs *and* containment is `unknown` for more than one). If no better field exists, say so in the slice's PR description and in a one-line comment at the call site — this may be a "measured, not fixed" finding rather than a code change.
- **The first hop's `mergedAt` is fixable without touching `releaseChainStep`'s signature.** `ReleaseChainReading.planCommit` is a bare string (`release-chain.ts:58`); add the plan PR's own merge time as a sibling field (or extend `planCommit` into a `{commit, mergedAt}` pair matching `ReleaseChainPrevious`'s existing shape) and seed `previous` from it at `:153`, instead of hardcoding `''`. The caller (`resolveRelease` in `packages/board/src/server/entry/release-chain.ts:92`) already has this value — it's `input.mergeCommit`'s own merge time from the `pr-state` row the scan read before invoking this walk; check whether `pr-state`'s row currently carries it (`parseRow` at `:139` reads only `mergeCommit` and `base` today — may need a third field).
- **Advice must name what it actually knows.** `fetchAdvice` takes `prSource` but not whether the clone ran `--no-fetch`/is shallow — that information lives with the caller (`plot-reconcile-scan.sh`, which already has `--no-fetch`/`--offline` flags, see `:326`). Thread that signal through (a new parameter, not a new global) so a `--no-fetch` run gets advice that names the flag as the likely cause, and a normal run that still can't find the commit gets different advice (shallow clone, or a destination this remote never held). `refusalText` should distinguish "the walk ran to completion and found no path" from "the walk could not ask the host" — `host-failed` already is a distinct case; make sure its text and the caller's handling don't blur it with `dead-end`/`ambiguous`, which are answered, just answered "no."
- Rules carried over from this repo: arrow functions for every function you write in `packages/domain/**`; TSDoc states behaviour, not history; the layering rule (the board's `release-chain.ts` imports the domain rule and the host/refs ports — it is the controller/adapter boundary, not a place to add host-shelling of its own); `plot-*.sh` is reached only through the `host`/`refs` ports in `.ts` code, never spawned directly.

### Done when

The plan's Changelog bullet 3 (`pr-merge-dest reads every page, the release chain starts at the plan PR's merge time, and a missing merge commit gets advice that depends on --no-fetch and shallow clones`) is the spec. Assertions that exist because a naive fix passes without them:

- A GitHub branch with more than 100 merged PRs still finds the one that carries the previous hop's commit. Catches a fix that raises `--limit` instead of paging — any fixed limit is the same bug at a different threshold.
- The Bitbucket arm's existing full-page walk is untouched — add a test (or confirm one exists) proving `pr-merge-dest` still returns every page on Bitbucket, so this slice doesn't regress #2484 while fixing GitHub.
- `pickReleaseHop`, given two Bitbucket candidates with equal/misleading `updated_on` but one genuinely earlier merge, resolves per whatever the chosen fix is — or, if no fix ships, a comment and the PR description state the ceiling explicitly rather than silence.
- The first hop of a walk, seeded with the plan PR's real merge time, picks correctly between two `unknown`-containment candidates where the old empty-string seed would have returned `ambiguous`. This is the test that proves bullet 3's "starts at the plan PR's merge time" — write it against `releaseChainStep`/`pickReleaseHop` directly, not through the board entry point, so it needs no host.
- `resolveRelease`'s advice differs for a `--no-fetch` run versus a normal one that still can't resolve a commit. Catches a fix that threads the flag through but never branches on it.

Write each as a failing test first, named for the finding (#2238, #2202).

Plus: a changeset (`plot` or `@plot-pm/board` package, description first, `bumps:` block last, optional `plan:` line); no built bundle in the diff (`scripts/check-no-bundle-diff.sh`). Before each push, run `node skills/plot/scripts/board/plot-local-checks.mjs` and run what it prints. The suites in `CI suites` run in CI; a failure there comes back as a correction. `scripts/check-shell-lines.sh` refuses a PR whose shipped shell grows over its merge base — this slice's GitHub paging fix likely touches `plot-host.sh`'s shell; if it grows, remove an equal number of lines elsewhere or move the logic into the domain and ask it through a bundle.

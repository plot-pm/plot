### What to build

The loop as one process. Today `skills/plot/scripts/plot-worker-loop.sh` is 891 code lines in 52 functions (3,202 lines with comments, measured 2026-10-05), it sources four helpers and starts seven bundles, and its decisions sit where no coverage tool reaches. Five failures came out of it and the processes around it on 2026-10-03 and 2026-10-04: an agent that ended its prompt turn on a background job was found "holding work" and the loop cut a new desk over 14 files (#1246); a continued agent had no BuildMonitor and its CI wait expired with CI failed (#1255); a dispatched agent's BuildMonitor missed the run after the correction (#1255); a blocked agent's exit 124 read as a crash on the board (#1250); and the board ran a day and a half on code a later PR had retired. Slices 1 and 2 built the decision (`agentLoop`) and the writes. This slice builds the part that reads the world, asks `agentLoop` what to do and applies the answer, in a loop that lives as long as the agent.

The parts:

- **The entry** `packages/board/src/server/entry/worker-loop.ts`, bundled by `packages/board/build.mjs` to `skills/plot/scripts/board/plot-worker-loop.mjs`. Each pass it gathers the `AgentLoopReadings` (`workflows/agent-loop.ts:27`) through ports, calls `agentLoop`, and hands the decision's writes to `performLoopWrites` (`entry/loop-writes.ts`). It decides nothing: every branch in it is an adapter call or `agentLoop`'s answer. The loop's own waits (a free wait, the usage-limit wait, a CI poll) are the entry's sleeps between passes, and the bound is `agentLoop`'s answer, never a timer the entry owns.
- **The launcher.** The first lines of `plot-worker-loop.sh` read `Worker loop` through `plot-config.sh`. On `js` they `exec node` the bundle beside the script; on `shell` the script continues into its own body. At most 4 lines, default `shell`. With `js` and no bundle the launcher exits 2 with the message form `the-shell-shrinks-into-the-domain` set.
- **The manifest records `loop: js` or `loop: shell`.** Slice 5 counts slices by that line, so the shell body writes it too. Read `update_manifest_on_hop` (`plot-worker-loop.sh:311`) and the manifest writer in `plot-agent-manifest.sh` before you choose where it goes, and check `entities/agent.ts` for the manifest's schema, because the board reads this file.
- **The transcript reading moves into an adapter.** `plot-transcript-quiet.sh` (172 lines, sourced at `plot-worker-loop.sh:89`) is the reading under `idleNow` (`rules/sample.ts:162`, paired with `plot_worker_idle_now` by `corpus/sample.corpus.test.ts`). The JS idle watch needs the same reading without sourcing shell. `slice-spend-file.ts` already knows where the runtime keeps a worktree's transcripts (`transcriptDirFor`); start there. `plot-transcript-quiet.sh` stays on disk until slice 6, because the shell body still sources it. The two readers must agree, so declare the pair in the corpus tier (`packages/domain/corpus/`, `docs/shell-and-domain.md`).
- **The `Worker loop` config key.** Nothing reads it today (`git grep 'Worker loop'` outside `docs/` finds no file). Document it where `Worker bound` is documented (`docs/stories/the-master-agent-holds-the-fleet/DESIGN-agent.md:748` and the `plot-dispatch` skill), and note it as the key slice 6 removes.
- **The board's coverage block** (`packages/board/vitest.config.ts:106`, `coverage.include`) gains `src/server/entry/worker-loop.ts`, at the same 100% thresholds. CI's step *Board loop-writes coverage gate* (`ci.yml:1295`) already runs it; rename the step if its name stops being true.
- **The `loop-js` CI job, the `PLOT_TEST_WORKER_LOOP` switch and a shared sandbox helper** for `test/reconcile/`. Details in the decisions below.

### The decisions the plan settles — do not re-derive them

**The launcher starts no Node in `shell` mode.** `node -e ''` starts in 34 ms, and the launcher runs once per agent life, so the cost is not the reason; the reason is that the default path for an adopting repository must run no Node and need no Node feature. A `shell`-mode launcher that touched Node would add a requirement the plan removed. The key read is the one decision a launcher makes, and slice 6 deletes it with the key. Do not fall back to the shell body when `js` is set and the bundle is missing: a silent fallback is how a fleet runs the wrong loop for a week and the baseline counts the wrong one.

**`Worker command` keeps naming `plot-worker-loop.sh`.** No adopting repository edits its config, and `plot-dispatch --start` refuses any other name. The bundle is reached only through the launcher.

**The test switch lives in the test helpers and nowhere else.** `plot-config.sh` gains no override. The helpers read `PLOT_TEST_WORKER_LOOP` and write `- **Worker loop:** <value>` into each sandbox repository's `## Plot Config`. `test/reconcile/` has no shared sandbox helper today (`ls test/reconcile` finds `fixtures/` and two gate tests, no helper), so this slice adds one, and the files that start a loop use it. An override in `plot-config.sh` would let a stray environment variable change a production loop.

**Two groups of test files, and only one goes to `loop-js`.** `git grep -l plot-worker-loop -- test` lists 30 files on 2026-10-05, 5 under `test/e2e`. Seven of them source the shell body with `PLOT_WORKER_LOOP_SOURCED=1` (`git grep -l PLOT_WORKER_LOOP_SOURCED -- test`): `checkout-yield`, `checks-wait`, `correction`, `deskreset`, `ending`, `marker-writer` and `prompt-resolution`, all in `test/reconcile/`. They test shell functions, not the loop's behaviour, so they stay out of `loop-js` and slice 6 removes them with the body. Re-run both commands on the day; the list moves. The other 23 run on `js` in `loop-js`. Five of the 30 read a BuildMonitor line (`build-monitor-follows`, `buildmonitor`, `checks-wait`, `correction`, `workerloop`): on `js` they take a `BuildPort` fixture instead.

**`loop-js` is its own job, filtered by `paths`, on `pull_request` only, with `timeout-minutes: 20`, in parallel with `validate`.** The contract step already takes 408 to 502 s against its 720 s limit, so the loop's files do not join it (measured 2026-10-04). The `plot-pm` organisation runs at most 20 jobs at once, and over the 24 hours to 2026-10-04T20:45Z the peak was 21 concurrent jobs; jobs from pushes to `main` queued up to 1,077 s while PR jobs queued at most 39 s. A job that ran on every PR would add to that queue. So it runs only on a PR that touches the loop, its workflow, its ports and adapters, or its test files. The PR records the job's run time and its queue time.

**Five rows change behaviour against the shell loop, and this slice is where they take effect.** Read the table in the plan's Design section. The JS loop ends where the shell goes free: an agent-written marker ends `blocked` with exit 0, a spent correction budget ends `blocked` with exit 0 (the shell ends `unstarted`, 1), an unanswered CI wait ends `checks-unanswered`, a moved remote tip ends `checks-unanswered` (`tip-moved`), and an unreadable tip keeps waiting inside `Checks wait`. The exit-0 `blocked` ending is what fixes #1250: the dispatch wrapper turns exit 0 into a `clear` line and a non-zero exit into `gone`, and the board's attention rule reads `gone` as "restart it". Four more rows add a `blocked` declaration where the shell writes only the marker. Each of these is a contract change made on purpose; name it in the PR.

**The CI wait is a declared exception to "A Decision Reads The Index", and the entry stays inside it.** The PR-open reading is asked once per finished prompt, through the host port. The build reading is asked at most once per 60 s per waiting agent, through `BuildPort.runForSha(branch, sha)` (`ports/build.ts`), and the loop records each call in the connector's rate budget. The pushed commit is the desk's `HEAD`, the same commit the BuildMonitor reads. The tip reading is `refs.remoteTip(branch)` (slice 2), a git call that costs no host budget; `unknown` keeps the wait going and is never `other`. The loop never writes the PR index; `fleet.ts` stays its one writer. Until slice 6 the BuildMonitor also polls in `js` mode, so a waiting agent costs about 180 build calls an hour instead of 60: at 8 agents that is 1,440 an hour, inside GitHub's 5,000 REST limit. The plan states no measured REST headroom, because the `gh api rate_limit` readings of rounds 2 to 4 read 0 used while the `X-RateLimit-Used` header read 335. Measure it from the header in this slice and record the number in the PR.

**One writer for the build findings file at a time.** Until slice 6 the BuildMonitor writes the findings file in both modes. In `js` mode the loop reads `BuildPort` for its own decision and writes nothing to that file. A second writer would race the monitor, and the board's reader does not change. The `build-finding` write kind is not in `LoopWrite` today (`loop-writes.ts:20`), which agrees.

**The prompt stays in the agent's process group.** `plot-dispatch.sh --stop` ends an agent by `kill -TERM -<pgid>` because the wrapper, the loop and `claude` share one group (#1084, measured 2026-09-30). `boundedRun` (slice 2) starts the prompt without `detached` for that reason. The entry must start no sidecar and must not `setsid` anything. The dispatch wrapper starts the loop under `set -m` (`plot-dispatch.sh:1505`), and the JS loop inherits that group.

**The prompt is the project's.** The entry runs the prompt the dispatch skill declares: `.plot/worker-prompt.sh` when the project has one, otherwise the shipped prompt. `resolve_prompt_file` (`plot-worker-loop.sh:1551`) and the `plot-prompt` and `plot-prompt-exit` bundles are the shell side. Plot names no harness (Manifesto principle 5). Do not hard-code `claude`.

**The loop carries no state between passes.** `agentLoop` derives where the agent stands from the readings each pass, which is what makes `kill -9` cost one pass. The entry must not cache a decision, a count or a phase in a variable that a restart would lose. A correction count is the manifest's `correctionAttempts`, a start retry is the manifest's `attempts`; read both from the manifest every pass. Two counters stay apart: a correction raises no `attempts`, and a start retry raises no `correctionAttempts`.

**`Worker bound` bounds each prompt run and each free wait, never the loop's whole life.** Every waiting row is inside the bound. Slice 4 adds `PLOT_WAIT_STARTED` so a restart cannot extend a free wait, so keep the wait's start time in one named place in the entry that slice can pass through.

**The entry spawns nothing.** *One place reaches a process* (`ci.yml:659`, `allowed=28`) counts direct `spawn`/`execFile` sites outside `adapters/` and fails when the count grows. Every process this entry needs goes through `boundedRun`, `performer`, `processes` or `refs`. Do not raise `allowed`.

**Cost, measured 2026-10-04.** About +51 to 74 MB resident per agent in `js` mode (a bash loop holds 2 to 5 MB, a long-running Node process with the adapter estate 58 to 81 MB); CPU is negligible. This is the price slice 5 weighs against tokens and the open question on one process per agent or per machine. The operator chose one process per agent on 2026-10-04. Do not move the loop into `plot-registryd`.

**Rules carried over unchanged.** Absent is not false: an `unaskable` or `failed` port answer is not `no`, and a connector that cannot answer reads `unknown`, never "no CI answer". Read the exit code, not the emptiness. A function you write is an arrow (`export const f = (…) => …`), in the board too: the unit is the function, and every function in the new files is yours. TSDoc says what an export does, how it fails and what it returns; the history goes into the commit message. The two bundle gates, `scripts/check-bundle-resolution.sh` and `scripts/check-bundle-attributes.sh`, apply to the new bundle, and `scripts/check-no-bundle-diff.sh` refuses a PR that carries a generated bundle: do not commit `plot-worker-loop.mjs`. `main` builds it after the merge. Add the entry to `build.mjs`, `packages/board/.gitignore` and `packages/board/package.json` `files` together; `plot-transcript-quiet.sh` was once listed in `build.mjs` and in neither of the other two (`packages/board/CHANGELOG.md:1319`).

### Done when

The plan's slice 3 list is the specification: the entry, the launcher, the shell ratchet, the no-bundle exit 2, the manifest's `loop:` line, the transcript adapter, the coverage block, the `loop-js` job with its `paths` filter and the `PLOT_TEST_WORKER_LOOP` switch, the rewritten contract tests, and the baseline record. The operator sets `- **Worker loop:** js` in this repository's `## Plot Config` after the merge, in its own commit; this PR does not set it.

Assertions that exist because a naive implementation passes without them:

- **A `js` loop runs the table, row by row.** One behaviour test per row of the plan's table, through the entry with port fixtures, asserting the ending, the exit code and the declaration. A loop that ran `agentLoop` but dropped the `declaration` write leaves `supervise` answering `correct` to an agent that asked a question, and every other test passes.
- **`kill -9` costs one pass.** Start the loop, kill it between passes, start it again on the same manifest and desk: it resumes from the readings, with no state file of its own. A loop that kept a phase in memory passes every single-process test.
- **The group stop reaches the loop and its prompt.** Start the launcher as the dispatch wrapper does (its own group, under `set -m`), send `SIGTERM` to the negative pgid, and assert that the launcher's node process and the prompt are both gone. Slice 2 proved `boundedRun` alone; this proves the entry did not put anything in another group. Wait on the pids you started, never on a process name.
- **The launcher in the three states.** `shell` runs the body with no `node` on `PATH` (the default path needs none), `js` with a bundle `exec`s it, and `js` with no bundle exits 2 with the set message and does not run the body.
- **The CI wait ends on a moved tip and names the branch.** The remote tip is another commit: the wait ends `checks-unanswered` (`tip-moved`) and the log names the branch that moved (#1199). It never settles on the other commit's build. An `unknown` tip keeps waiting. A naive wait that polls only the build passes without this.
- **A continued desk waits like a dispatched one (#1255).** A desk with no BuildMonitor and a failing build reaches the correction through `BuildPort`, not through a findings file. The test that fails without it is the one that starts the loop with no monitor process.
- **The correction budget counts per slice.** PR #1285 (`bug/the-correction-budget-counts-per-slice`) changes what the shell loop counts. Read its diff and its changeset, and make the JS loop count the same way; the plan's three-count test is the check.
- **The idle watch ends `quiet` and `unreadable`.** The transcript adapter and `plot_worker_idle_now` agree on the corpus fixtures. The corpus test names both answers and the subject on a disagreement; on a disagreement the branch stops, and adjusting either side to pass is the one forbidden move.
- **Source-text assertions become behaviour tests.** Any contract test that greps `plot-worker-loop.sh` for a string is rewritten to assert the behaviour through `js`, and the PR names each. Any other failure against `js` names a behaviour the plan did not list: report it with `PLOT-BLOCKED` and never rewrite the test to pass.
- **The shell ratchet.** `scripts/check-shell-lines.sh pr` passes: the launcher adds at most 4 lines, so remove at least as many shell lines elsewhere in the same change and name each one. The gate stores no number and has no override. Where a rule moves out of shell, write it in the domain and ask it through a bundle.

Plus the repo gates. Before each push, run `node skills/plot/scripts/board/plot-local-checks.mjs` and run what it prints: the tests that name a changed file, `vitest related` and the typecheck of the board and the domain, the gate tests and the `scripts/check-*.sh` gates. The suites in the `CI suites` key, including the board's coverage run and `loop-js`, run in CI, and a failure there comes back as a correction. Do not run `pnpm run test:e2e` locally. Check that the operator's board is not running before you run a board test: a local board test run takes the operator's board down. Run `pnpm board --status` first and stop if the board answers.

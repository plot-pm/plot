### What to build

The plan-state comment writer carries three real defects and three text or dead-code defects, all from review issue #2935. Fix them in `tracker-plan-state.ts` and `plan-issue-comment.ts`. Each behaviour fix gets the test named in *Done when* that fails on `main` first.

1. **Stale-lock break race** (`tracker-plan-state.ts:155-156`). Two waiters both `stat` a lock older than `LOCK_STALE_MS`. The first `unlink`s it and `link`s its own fresh lock. The second then `unlink`s that fresh lock, so two writers hold one issue. The fix must make the break remove only the file whose staleness was observed. A bare second `unlink` cannot do that, and a bare `rename` cannot either: the second waiter's `rename` takes the first waiter's fresh lock the same way. After a `rename` to a unique name, `stat` the renamed file. If it is not stale, it was a fresh lock, so put it back with `link` (which fails harmlessly if someone else already took the path) and keep waiting. Any mechanism that passes the test below is acceptable.
2. **`\r\n` parsing** (`plan-issue-comment.ts:83`). `priorPlanLinesOf` splits on `\n` only. A comment edited in the GitHub web UI comes back with `\r\n`, and the first ticket line keeps a trailing `\r` that `TICKET_LINE` does not match. Split on `/\r?\n/`.
3. **Shared hash file** (`tracker-plan-state.ts:100-106`). `writeWrittenHash` does read-modify-write on one file shared by every issue, with a plain `writeFile` and outside the per-issue lock. Two writes on different issues can each read the old record and lose the other's entry. The per-issue lock does not cover it, because the two writes hold different locks. Do the read-modify-write under one dedicated lock (`withIssueLock` already takes any name, so a fixed name such as `written-hashes` reuses it), and write by temp file plus `rename`.
4. **Docstring** (`plan-issue-comment.ts:74-77`). It says parsing "stops there". The loop does not stop: it keeps collecting ticket lines after the progress line. Correct the text.
5. **Dead ternary** (`tracker-plan-state.ts:92`). `isMissing(error) ? {} : {}` returns `{}` on both branches. Return `{}` and drop `isMissing` if nothing else uses it. The behaviour stays: an unreadable record never blocks a write.
6. **Changelog text.** The published 2.30.0 entry (`CHANGELOG.md:463`) says an identical second write "makes no host call". It does make one: `issue-comment-read` runs on every write that omits a field (`tracker-plan-state.ts:213-215`), deliberately. `CHANGELOG.md` is generated by changesets, so correct the claim in this slice's changeset description, which the next release publishes. Do not edit `CHANGELOG.md`.

The plan is canonical; this is orientation.

### Decisions the plan settles — do not re-derive them

- **The read-back stays.** It is deliberate for progress writes (`:208-212`). The fix for finding 6 is text, not behaviour. Removing the read-back to make the old changelog sentence true would let a late pulse overwrite a delivered or released phase.
- **The 2.30.0 changelog entry stays as published.** The correction goes forward through the changeset.
- **No schema change, no new port, no shell.** The slice touches the TypeScript adapter and one rule only. `plot-host.sh` is not involved.
- **A missing or unreadable hash record still reads `{}`** and never blocks a write; it costs one level trigger. Do not turn it into a refusal while fixing finding 5.
- **A caller that fails to take the lock gets `null` and holds nothing.** Keep that contract for both the issue lock and the new hash lock. A hash-lock timeout must not fail the write: the hash record is an optimisation, so on a timeout skip the record update.

Rules carried over: absent is not false (a missing file is a cold record, not an error); read the exit code, not the emptiness; remove your test fixtures by the exact name `mkdtempSync` returned, never by a glob over the shared temp directory; tests spawn nothing that outlives teardown (`owned-run.sh` fails the run on a leaked entry).

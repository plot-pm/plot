### What to build

Today, `/plot-init` adopts a repository with no notion of role agents at all. `packages/domain/src/rules/adoption.ts`'s `composeAdoption` only ever decides a `## Plot Config` section — it names no `.claude/agents/` file and no `.claude/settings/` file anywhere in its ~560 lines, and `skills/plot-init/SKILL.md` never mentions a role, a reviewer, a fixer, an unblocker or main-repair. Meanwhile `main` has carried the four real files since wave 3 merged: `.claude/agents/{reviewer,fixer,unblocker,main-repair}.md` and `.claude/settings/{reviewer,fixer,unblocker,main-repair}.json`. A repository adopting Plot today gets a config section and a plan skeleton, but none of the role definitions fleetd needs to start a reviewer, fixer, unblocker or main-repair run — `plot-dispatch.sh --start`-style fleet operation on a freshly adopted repo would have no `.claude/agents/<role>.md` to read, because nothing writes one there.

The plan's own words for this slice: "`rules/adoption.ts` decides that an adopting repository gets the four definitions and settings files, and the performer writes them: absent files are written, an existing differing file is reported `stale` and never overwritten, and a second run writes nothing. A test holds this repository's copies equal to the shipped ones."

### Decisions the plan settles — do not re-derive them

- **This repo's own eight files are the fixture, not a template this slice re-authors.** The plan's Design line is explicit: "A test holds this repository's copies equal to the shipped ones." The four `.claude/agents/*.md` files and four `.claude/settings/*.json` files already on `main` (written by wave 3, `feature/role-agent-definitions`) are the content an adopting repository receives verbatim. This slice does not rewrite, retune or "improve" any of the eight files while wiring adoption to them — read them, copy their content into the write path, and prove equality with a test. If a defect in one of the eight files is found while doing this, report it; fixing it here would silently change what every future adopter gets with no plan slice reviewing that change.
- **Three outcomes per file, matching the plan's own words exactly: absent → write it; present and identical → write nothing (a second run is a no-op); present and differing → report `stale`, never overwrite.** `composeAdoption`'s existing shape for every other decision already carries this same posture for `## Plot Config` itself ("adoption refuses rather than appending" on `already-adopted"`) — follow that precedent rather than inventing a fourth outcome (there is no silent merge, no prompt-to-overwrite, and no partial write of some but not all eight files).
- **`composeAdoption` decides; it renders nothing.** The file's own header states the split this repo has held since the function was written: "It renders no file, appends nothing and reads nothing — the performer owns the append." Follow the same split here: `rules/adoption.ts` (or a sibling rule file beside it) decides which of the eight files get written, written-as-stale, or left alone, as **data** the caller acts on — it does not itself call `fs.writeFile` or shell out. Whatever script or performer currently writes the `## Plot Config` section (`plot-write-config.sh`, per `skills/plot-init/SKILL.md` step 3's Model Guidance row) is the natural place for the actual write, or a sibling script beside it — but the decision of *which* files and *what* content is the domain's, the same way every other `composeAdoption` key already is.
- **This is an *additive* adoption step, not a replacement of the existing one.** `skills/plot-init/SKILL.md`'s own stated rule: "Adoption is additive. Nothing existing is moved, rewritten, or deleted." The role-file write sits beside the `## Plot Config` write in step 3 (or as a clearly-scoped new step) — it must not change what `composeAdoption`'s existing `AdoptionDecision`/`AdoptionRefusal` shape returns for the config section, and a repository already carrying a `## Plot Config` (the existing `already-adopted` refusal) should still be eligible to receive the four role files if it lacks them — these are two independent questions ("does this repo have a Plot Config?" vs. "does this repo have role definitions?"), and the plan's wording ("where they are absent") implies the role-file check runs on its own, not gated behind the config-section refusal. Confirm this reading is right before wiring it — if the plan intends the role write to run only on a *fresh* adoption (never on a repo that already has a config section but lacks the role files), that is a materially different scope and worth flagging back rather than guessing silently.
- **"Reported" means surfaced through `AdoptionDecision.gaps` (or a parallel field read the same way), not a thrown error.** Every other divergence `composeAdoption` finds — an unverified default branch, a tracker with no base URL, a single ticket prefix — is carried as a string in `gaps` and printed by the caller; a `stale` role file is the same shape of fact (something a person should look at, not something that should abort the whole adoption). Precedent: "Never fail the whole adoption on one blocked step" (`skills/plot-init/SKILL.md`'s own Decisions/Trade-offs table) and "A failed verification does not fail the adoption" — a `stale` role file is exactly this kind of individually-reported, non-fatal finding.
- **The eight files' own content is already settled and already gated.** `role-gate.ts`'s `PROTECTED_PATH_PREFIXES` already names `.claude/` as a path no fixer/unblocker/main-repair role may ever write — this slice's write path is the *adoption* performer writing these files into a *fresh* repository, which is a different caller under different rules, not a role run touching its own gate. Do not conflate the two; nothing here loosens or touches `role-gate.ts`'s existing protection.
- **`ROLE_NAMES` (`packages/domain/src/rules/role-command.ts:13`, `['reviewer', 'fixer', 'unblocker', 'main-repair'] as const`) is the one place the four role names already live as data.** Derive the four filenames from it rather than hand-listing the names a second time in the new adoption code — a role added or renamed later should need one edit, not two.
- **This plan's Notes name the ownership boundary precisely**: "`/plot-init` provides the definitions through `rules/adoption.ts` and the performer: written where absent, never overwritten, a differing copy reported `stale`." There is no fifth outcome and no ask-the-user path for this step — contrast with the `## Plot Config` section, which does ask about the hub doc, the Definition of Done, the tracker, etc. The role-file step reads purely mechanical (the plan's own Model Guidance table principle: template filling is Small/Haiku-tier) — resist adding a confirmation question for it unless you find a concrete reason the plan's own wording doesn't already answer.

### Done when

The plan's slice line is the specification: "`rules/adoption.ts` provides the definitions to an adopter; absent files written, a differing copy reported `stale`." Read together with the Design section's "Adoption" paragraph above.

Assertions a naive implementation would pass without:

- **A test holding this repository's own eight files equal to what the adoption decision would write for a from-scratch repo** — the plan's own words, quoted above. A implementation that writes *some* correct-looking boilerplate but drifts from the actual shipped `reviewer.md`/`fixer.json`/etc. content would pass a hand-rolled "file gets created" test while failing this one.
- **A test proving each of the three per-file outcomes independently**: file absent → written; file present with byte-identical content → no write (idempotent second run); file present with different content → reported `stale`, file untouched on disk. A test that only checks the absent case would miss a silent overwrite of a repo's customised role definition.
- **A test proving a second adoption run against an already-role-adopted repo writes nothing and reports no `stale`** — the plan's "a second run writes nothing" clause specifically, distinct from the differing-content case above.
- **A test proving the four filenames come from `ROLE_NAMES`**, or at minimum that adding a fifth name to that constant is the only edit a fifth role would require on this slice's side (don't hand-list `'reviewer' | 'fixer' | 'unblocker' | 'main-repair'` a second time somewhere this test can't catch).
- **`skills/plot-init/SKILL.md` documents the new step or decision** — a reader following the skill today has no way to learn that adoption now also provisions role files; the skill's own existing Decisions/Trade-offs table style (a short "what/why" row) is the precedent to extend, not a new prose section.
- `scripts/check-plan-headings.sh` passes if this slice touches the plan file (it shouldn't need to, beyond the `→ #<number>` annotation this brief's Bookkeeping section describes).

Plus: the repo's gates — build artifacts (no committed bundle), a changeset naming `plot` or `@plot-pm/board` per `scripts/check-changeset-packages.sh`, and the TypeScript purity gate if any new file lands under `packages/domain/src/adapters/` (the domain may import `zod` and nothing else outside `adapters/`). Run `node skills/plot/scripts/board/plot-local-checks.mjs` before each push and run what it prints — the suites named in the `CI suites` config key run in CI, not locally. Do not run `pnpm run test:e2e` yourself; it dispatches real workers into sandbox repos and starves the shared machine, and nothing local depends on it passing.

Name the shell gate even though this slice is unlikely to touch a `.sh` file directly: `scripts/check-shell-lines.sh` refuses a PR whose shell under `skills/` is longer than at its merge base. If the write path turns out to need new shell (e.g. a dedicated `plot-write-roles.sh` beside `plot-write-config.sh`), that growth is paid for in the same change — remove shell elsewhere, or push the logic into the domain rule and a thin existing-bundle arm instead. The plan's own precedent (wave 3's brief) leaned toward routing new logic through the domain and an existing bundle rather than a new `.sh` file; the same preference applies here.

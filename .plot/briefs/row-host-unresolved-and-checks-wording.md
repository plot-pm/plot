### What to build

Two independent review findings, both about a value computed once and then worded or defaulted inconsistently at its several call sites.

**#1679 — an unresolved git host silently reads as GitHub.** `resolveBackend` in `packages/fleet/src/shared/pr-refresh.ts:1015-1028` assigns `entry.backend = 'github'` whenever the host CLI's `backend()` call fails or throws (lines 1021, 1023), and the function's own fallback return (line 1027, `entry.backend ?? 'github'`) repeats the same default. Every downstream reader then does `entry.backend ?? 'github'` too — eleven sites in `packages/board/src/server/fleet.ts` (lines 1546, 1550, 1663, 1695, 1829, 1843, 1900, 1937, 1993, 2052, 7135). The review (#1679 M1, filed against PR #1677) named two of them specifically — `refreshIssues` (line 1829, feeding `issueSource`, and line 1843, feeding `trackerForIssues`) and `readIssuesFromStore` (line 1993, feeding `issueSource`) — because `ticketSourceOf` is documented to answer `null` for a `git-host` source with an *unresolved* backend, and a Bitbucket repo whose backend hasn't resolved gets matched against GitHub logins instead, hiding every one of its tickets.

**#1546 — the channel and the board word a missing checks commit two ways.** `checksBinding` in `packages/domain/src/rules/index-findings.ts:68-76` says `'the checks are not bound to a commit'` for an absent `checksSha`; `checksShaSuffix` in `packages/domain/src/rules/checks-reading.ts:134-136` says `' No commit is recorded for these checks.'` for the identical fact. One feeds the IndexMonitor's published evidence strings (the channel); the other feeds `checksVerdict`'s `detail` text (the board's failing/pending badges). The issue also names a live bug in `checksBinding`'s *other* branch: when `checksSha === ''` it renders `for , head X` — a leading comma with nothing before it — which cannot currently be exercised because the adapters (`host-shell.ts:95`, `pr-refresh.ts:1091`) keep `checksSha` from ever being `''`, but the wording fix should not leave that trap in place for whichever future adapter forgets to.

### Settled decisions — do not re-derive them

- **Fix #1679 at the source, then flip every reader.** Change `resolveBackend`'s two fallback assignments (`pr-refresh.ts:1021,1023`) and its own trailing `?? 'github'` (`:1027`) from `'github'` to `''`. That makes "unresolved" a value `entry.backend` can actually hold rather than a state indistinguishable from "confirmed GitHub." Each of the eleven `fleet.ts` call sites still needs its own `?? 'github'` → `?? ''` edit, though — `entry.backend` is a persisted field (`CacheEntry`/registry state) that can hold a stale `'github'` string written before this fix shipped, or can legitimately be `null`/`undefined` the instant a process starts and hasn't asked the host yet, so the per-call-site fallback is real defense, not a second copy of the same bug. `pr-refresh.ts:631` (`limitReadingOf`) already does `entry.backend ?? ''` — it is the one site already correct and the pattern to match everywhere else.
- **This does not need new plumbing to be safe — the consumers already treat an unrecognized backend as "ask nothing" or "cost one," never as a crash.** Confirmed by reading each: `ticketSourceOf(source, backend, listers)` (`packages/domain/src/rules/ownership.ts`) takes `backend: string`, and `packages/domain/test/ownership.test.ts:212-215` already asserts `ticketSourceOf({ ask: 'git-host' }, '', TICKET_SOURCES)` returns `null` — this is the existing cap test #1679 M2 asks you to extend coverage around, not write from scratch. `issueSource` only compares `gitHost` against each lister's `onlyOnHost`; `''` just produces a truthful `nobody` reason instead of a falsely-GitHub one. `prRequestsPerRefresh(backend)` and its backing `PR_REQUESTS_PER_REFRESH` table (`pr-refresh.ts:205-212`) are a plain object lookup — an unrecognized key, `''` included, falls through to the same miss behavior any other unknown string gets (cost 1), never `undefined` or a throw. `prNextDueAt(..., backend = 'github', ...)` uses `backend` the same way, as a lookup key only.
- **#1679 M2's cap test is `packages/board/test/unit/unplanned-issues.test.ts`.** The review's finding: no case there proves the 50-row cap (`ISSUE_LIMIT`, `fleet.ts:208`) while `shown`/`hidden` counts still account for every row, under an unresolved backend. Add that case against `refreshIssues` and/or `readIssuesFromStore` (whichever your fix touches) rather than inventing a new test file — the existing one already imports both via `fleet.js` and exercises `freshCacheEntry`.
- **M3 and L1–L4 from #1679 are out of scope here.** The plan's own Open Questions list M3 ("is the changeset consumed in 2.27.0, so the note is moot?") as undecided, and the slice description names only M1 and the cap test. Do not fix L1–L4 opportunistically; they belong to whichever slice picks up #1679's remainder, if any does.
- **#1546's fix point is `checksShaSuffix`, not `checksBinding`.** Per `CLAUDE.md`'s domain-ownership rule ("every rendered state is a domain property"), promote `checksShaSuffix`'s missing-case string (`checks-reading.ts:135`) to a named export other rule files can import, and have `checksBinding`'s missing-`checksSha` branch (`index-findings.ts:69-71`) call it instead of restating the sentence. **Do not flatten the two functions into one wording wholesale** — `checksBinding` has a clause `checksShaSuffix` has no equivalent for: when `checksSha` is absent but `headSha` is present, it appends `"; head ${row.headSha}"` as extra context. Preserve that addition on top of the shared string; only the "nothing recorded at all" sentence is the one fact both functions must say identically. `checksBinding`'s non-missing branches (`on ${checksSha}` / `for ${checksSha}, head ${headSha}`) have no counterpart in `checksShaSuffix` at all and are untouched by this fix.
- **Close the `''`-renders-as-`for , head X` trap while you're in this code**, even though no adapter currently produces it — a `checksSha === ''` should take the same "nothing recorded" branch as `undefined`, matching `checksShaSuffix`'s own `checksSha === undefined || checksSha === ''` guard, which `checksBinding` currently lacks.
- **Carried-over invariant:** `checksShaSuffix`'s docstring draws a real line — print `checksSha` as the *bound* commit, never `headSha`, because on a host that doesn't bind checks to a commit (Jenkins) only `headSha` exists and printing it as the binding would claim something the host never asserted. `checksBinding`'s `headSha` mention in its missing-`checksSha` branch is additional context, not a claim of binding — keep that distinction legible in whatever shared helper results; do not let the merge imply `headSha` is ever "the commit checks ran against."

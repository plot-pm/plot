Plan 4 of 7 in the sprint "Delivery UI Polish", wave 2 of 2. Wave 1, `feature/delivery-tab-has-one-header`, is merged (#3607). It built the frame, the `deliveryHeader` domain rule and the You, Work items, Fleet and Machine groups. `DeliveryHeader.tsx` takes the Release group as a `release: ReactNode` prop, and today that prop holds the existing `ReleaseCard` or `SprintCard` with its `ReleaseApprove`. This slice fills the Release group for real and deletes both old cards.

### What to build

The release button is decided in the wrong place. `ReleaseApprove.tsx` reads the passkey in its own `useEffect`, calls `releaseCardApprovable` itself, and prints the reason in a span beside the button. A release card exists per `Release:` version (`releaseCards`) and a sprint card per sprint (`sprintCards`), so the Delivery tab shows several bars where the operator asks one question: can a release go out, and what is it made of. This slice adds one Release group over every active sprint — one combined five-state bar, one legend, one status line, one release button in a fixed slot — and moves the button's decision into one domain function, `releaseStatusLine(group, prReading, passkey)`. It also adds the `lastRelease` payload field, so a group with no release targeted still says which version shipped last. The plan is canonical; this brief records what not to re-derive.

Line numbers in the plan are stale: `AgentList.tsx` and `release-card.ts` moved after wave 1 and earlier slices. Find code by symbol, not by the plan's `file:line`.

### Settled decisions — do not re-derive them

- **One combined group over the existing cards, not a new reading.** `releaseCards` builds one card per version and `sprintCards` one per sprint. The combined group is a new shape over those cards, with unit tests beside `packages/domain/test/release-card.test.ts`. A unit test asserts that the combined bar's segment sums equal the sum of the per-sprint bars. Where active sprints name different `Release:` versions, the group title lists them ("2.36.0 · 2.37.0") over the one bar. Rejected: summing in the `.tsx`, because a count computed in a component is testable only by rendering.
- **Five bar states, never four.** The mockup legend shows four. The bar and legend keep the five `SLICE_STATES` segments, `being-built` included; dropping one loses or miscounts slices. The test above catches a four-segment sum that still matches per sprint because it drops the same slices on both sides: build the fixture with a `being-built` slice.
- **Unread is grey, never partial.** Where any sprint in scope has no merge answer (`readingMissing`), the bar is grey and the status line is `RELEASE_READING_MISSING`. The combined bar never shows a partial count. No payload field records when the merge reading was last good, so the line shows the failure only. A fixture with one readable and one unreadable sprint catches a bar that sums only the readable one.
- **The status line is one domain function.** `releaseStatusLine(group, prReading, passkey)` returns the text, the button state and the reason in one result. `ReleaseApprove` takes its enabled state and reason as props, and its own `release-approve-reason` span goes, because the status line shows the reason. The click and the controller call stay unchanged: no controller and no refusal changes (spec non-goal). One unit test asserts that the button state and the status line come from the same `releaseStatusLine` result; without it the two drift apart again, which is how the current split came about.
- **The passkey read moves up.** The `readRegistration` call leaves `ReleaseApprove` and sits with the Release group, which passes its answer in, including the re-read after a click (`ReleaseApprove.tsx`, the `finally` block). `readRegistration` answers `null` before the read and on failure; `releaseStatusLine` must treat `null` as "passkey unread", not as "no passkey registered". Absent is not false.
- **The line reads "Release PR #N ready" with no wait time.** No payload field records when the release PR became ready (`ReleasePrReading`, `release-approvable.ts`), and the release row's `updatedAt` is the PR's last update, not its ready time. Do not show an age derived from `updatedAt`.
- **Several ready release PRs: the lowest version takes the slot** (operator decision 2026-11-20). Order by semver through `normalizeVersion` (`packages/domain/src/entities/version.ts`), never by string comparison, which sorts "2.10.0" below "2.9.0". The status line names the other ready PRs as tuples ("+1 more ready · [PR …]"). After one approval the next payload holds one ready PR fewer and the slot moves to the next lowest version. Unit tests: two ready PRs, one ready and one not, and the slot after the first merges.
- **Release approval stays in the header only** (operator decision 2026-11-20). No You row offers "Approve release", and `placeDelivery` keeps sending release items to `releases` and to no section. Do not add the approval to a section.
- **Fixed release slot.** The release button keeps its position whatever the text length or state. A browser test measures the slot's position under two text lengths.
- **"No release targeted · last vX.Y.Z <date>"** (operator decision 2026-11-20). The group keeps its size: grey bar, that line, and the button in the same slot, drawn disabled with a dashed outline, not a dimmed fill. Its reason comes from `releaseCardApprovable` and `NO_RELEASE_TARGETED`. The dashed outline is a `.delivery-approve:disabled` rule in CSS; a browser test asserts the computed `border-style` is `dashed`, because a dimmed fill passes every other assertion.
- **`lastRelease` is built from files the server already reads.** The payload gains `lastRelease: { tag, date } | null`, with a schema default of `null`. The server builds it in `packages/board/src/server/board.ts` from every plan's `Released: <date>, vX.Y.Z` record (`meta.released_raw`, which `phaseDateOf` already reads). Rejected: reading tags through `Refs.tagsContaining` and `tagDate`; those are the release entry points' path, the payload path reads no tag today, and the field adds no tag read and no tracker query. The records hold two forms, `YYYY-MM-DD, vX.Y.Z` and `YYYY-MM-DD, X.Y.Z` with no `v`, and one record holds a pre-release followed by prose. A domain rule `lastRelease(records)` accepts both forms through `normalizeVersion`, reads the version up to the first space, and picks the highest by semver, with a pre-release below its release. Unit tests: no Released plan gives `null` and the clause reads "No release targeted" alone; two releases on one day; a bare-version record; trailing prose after the version; a pre-release against its release; an unparseable record is skipped. A server test, in a file you name in the PR, asserts the field over a fixture with two Released plans.
- **My sprint with several sprints** (operator decision 2026-11-20). Under the `my-sprint` scope the group combines the sprints `deliveryScope` returns, the active sprints the reader owns and selects. The scope line reads "my sprint · <a>" for one and "my sprints · <a>, <b>" for several; under `release` scope it reads "all sprints · <n> people". The group keeps `SprintCard`'s warning for an Owner that People does not declare (`unknownOwners`). The action slot holds the release PR that the reader's sprints' `Release:` versions bind, or the disabled button with `unboundReason`. A unit test of the combined group asserts different facts for the two scopes.
- **The header ignores Mine.** Wave 1 settled this and the Release group inherits it: read rows through the `all`-mode `deliveryMapping`, as `releaseCardsOf` and `sprintCardViewOf` already do. Add no Mine rule.
- **Words move, they are not copied.** `SEGMENT_WORD` and `SEGMENT_CLASS` live in `SprintCard.tsx`, which this slice deletes, and four files import them (`ReleaseCard.tsx`, `ReleasePersonCards.tsx`, `ReleasePlanParts.tsx`, `unit/release-plan-parts.test.ts`). Move them to the domain view or a shared module first, repoint the remaining importers, then delete the cards. No new `.tsx` word map.
- **Link tuples.** Every artifact the Release group names (release, sprint, PR) is a plan 1 tuple. Reuse the tuple component; do not hand-write an anchor.
- **Rules carried over:** absent is not false (an unread passkey, an absent merge answer and an absent `lastRelease` are each their own state, not "no"); read the exit code, not the emptiness; a decision computed in `.tsx` is a domain property not yet extracted.

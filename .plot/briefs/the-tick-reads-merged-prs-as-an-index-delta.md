### What to build

fleetd's tick asks `pr-list --state merged --limit 500` once per tick (`mergedBranches`, `registryd-main.ts:780`) to learn which branches have landed. That costs about 5 pages (~5 requests) per tick, ~43 ticks/hour idle — about 215 requests/hour, the second-largest idle spender after wave 1's nothing-done step. The PR index (`.plot/state/index/github.json`) already answers "merged" for most branches via its MERGED rows, written by fleetd's own PR refresh every 60 s. This slice makes the tick read the index's MERGED rows plus one cheap host delta (`pr-list --state merged --since <watermark − 60s>`) instead of the full 500-row listing, whenever the store is current and complete — falling back to the full listing otherwise.

### Decisions the plan settles — do not re-derive them

- **A pure domain rule, not a tick-local branch.** Add it beside `indexMergedHeads` in `packages/domain/src/rules/known-pr.ts`. It takes the store (or `null`) and `now`, and answers either `{kind: 'delta', since: <watermark − 60s>}` or `{kind: 'full'}` — mirroring the shape `prWindowFor` (`packages/domain/src/rules/pr-index.ts:380-412`) already uses for the PR-refresh window. **Read `prWindowFor` before writing a new function** — it already answers a near-identical question (full vs. delta against `watermark`/`wholeAt`/`complete`), just scoped to the refresh's own full-read cadence (`PR_FULL_READ_MS`, 24h) rather than this consumer's "store is current and complete" test. Decide and record explicitly whether this is a second declared duplicate (CLAUDE.md *A Shell Script Asks The Domain* corpus-tier reasoning doesn't apply here — both are TS — but the "don't silently drift" principle does) or whether `prWindowFor` itself can be reused/parameterized. Either choice is legitimate; an unexamined copy-paste is not.
- **Only answers `delta` on a strict read.** `full` for: a missing store, a version other than `PR_INDEX_VERSION` (5), `complete: false`, or a missing/empty/unparseable `watermark`. `delta`'s `since` is `watermark − 60s`, rendered in the host's own stamp format (`YYYY-MM-DDTHH:MM:SSZ`) — arithmetic on the host's clock, never this machine's. The live store on `main` today is `v: 4` (started by a stale fleetd process) — until fleetd restarts on current code and writes a v5, complete store, this rule answers `full` and the sample shows the 500-row read exactly as before. That's expected, not a bug to chase.
- **Why 60s of overlap, not 0.** `updated:>` on both hosts is exclusive (`plot-host.sh:4475-4479`): a PR updated in the same second as the watermark is otherwise missed until the next full read (up to 24h). 60s = one `PR_REFRESH_MS`, covering the same-second case plus one refresh interval of host-side ordering skew, at the cost of re-reading at most a minute's worth of merges (comfortably under a 100-row page).
- **The delta is a union, not a replacement.** `mergedBranches` on a `delta` window asks `pr-list --state merged --since <since> --limit 500` once (adds 1 to `tally` — wave 1 already threaded `tally` through this function and the nothing-done/release ports; keep that pattern), and answers the union of (a) the delta call's MERGED heads and (b) `indexMergedHeads` of the stored rows, with `whole: true`. `readQueue` keeps joining rows exactly as it does today (`queue-reading.ts:331-333`) — this slice does not touch that join, only what feeds it.
- **Fallback on any delta trouble.** If the delta call fails, leaves a refusal behind (`partial`/`unaskable`), or comes back with exactly `--limit 500` rows (meaning it may have been truncated), do **not** trust it — fall through to the existing unconditional `pr-list --state merged --limit 500` call in the same tick. Never half-trust a truncated or failed delta by unioning it anyway.
- **The tick line must say which path ran.** `merged-set=` (`registryd.ts:550`) gains the suffix `(delta)` when the delta path answered — i.e. `merged-set=whole(delta)` — by extending `kind` on `MergedSetState` (`queue.ts:180-185`) rather than inventing a second field. A `full`-path tick prints the field exactly as today (no suffix).
- **No new shell.** The host port gains an optional `since` on `prList` (`packages/domain/src/ports/host.ts:311`, currently `prList(state, limit)`), and `host-shell.ts:444` passes it through to `plot-host.sh pr-list --since <iso>` — confirmed already supported on both GitHub and Bitbucket backends (`plot-host.sh:178-184`). This is a port/adapter change, not a new script.
- **The CLAUDE.md licence ships in this slice, not after.** After *The index never says no* in *A Decision Reads The Index*, add the one-consumer paragraph the plan specifies verbatim (plan body, Design step 4, final bullet — the paragraph beginning "**One consumer reads a complete store plus a host delta…**"). Then run `./scripts/check-agents-md.sh --write` to regenerate `AGENTS.md` in the same commit.
- **Carried invariant:** the index never says `pr: 'none'`. A branch absent from both the delta and the stored rows reads *not merged per this read* only — it holds its slice or falls through to the per-branch `queuedHasLanded` ask before any hand-over. Nothing in this slice starts an agent, releases a claim, or deletes a ref off a merged-set miss.

### Done when

The plan's *Merged Delta Read* slice line and the Design §4 bullet are the specification. Lift these, each of which a naive implementation would pass without:

- Unit test: the rule answers `delta` with `since = watermark − 60s` for a current, `complete: true`, version-5 store with a parseable watermark; `full` for a `null` store, `complete: false`, and a `null`/empty/unparseable watermark (catches: trusting a stale or half-written store).
- Unit test: the caller's own decode (before calling the rule) answers `null`/treats-as-full for an old-version (`v: 4`) or unparseable store file — prove this with a fixture at the actual `v: 4` shape, not just a hand-rolled `null` (catches: a version check that only looks at `complete` and ignores `PR_INDEX_VERSION`).
- Unit test: `queueWorldForRepo` (or wherever `mergedBranches` is exercised) with a fixture store and a stubbed host asks exactly one `prList` call with `since` on the `delta` path, and unions its MERGED heads with the rows' non-draft MERGED heads; an OPEN/CLOSED/draft row contributes nothing. A delta that fails, returns a refusal, or returns exactly the 500-row limit triggers a **second** call without `since` and with `--limit 500` (catches: trusting a truncated delta, and catches a fallback that never fires).
- Unit test: a `full`-window store makes exactly one call, with no `since` (catches: accidentally always passing `since`).
- Acceptance per the plan: with fleetd on current code and a version-5, `complete: true` store, a `ps` sample shows one `pr-list --state merged --since … --limit 500` call per tick and no unconditional 500-row call, and the tick line prints `merged-set=...(delta)`. This is a *per-tick* claim — do not compare against `mine=`'s per-hour units (the plan's *Acceptance* section explains why that comparison can't pass: real tick period is 12–40s, not the configured 60s).

# Release Checklist — v2.1.0

RC: **v2.1.0-rc.2** (2026-08-15) — supersedes rc.1, which predated `/plot-init`
and the four-phase model. Test against rc.2.

Delivered plan: [`parallel-agent-fleet`](../plans/2026-08-14-parallel-agent-fleet.md)

## Verification

Automated coverage exists for all of these (157 unit, 9 e2e). **Verify what the
tests cannot**: whether an agent follows the prose, whether the messages make
sense to someone who has not read the scripts, and whether real detached
workers work — every automated test runs `--no-start`.

Walk `docs/fleet-user-test.md` in a real project, then tick:

- [ ] **Waves** — a plan with `### ` subheadings parses; a plan without them still behaves exactly as before
- [ ] **`/plot-fleet`** — reports complete / eligible / blocked understandably, without reading the source
- [ ] **Wave transition** — merging wave 1 flips wave 2 to eligible on the next pulse (the design's core claim)
- [ ] **Claim-by-ref** — two sessions racing one branch: exactly one wins, the loser is told
- [ ] **`/plot-dispatch`** — dry-runs and *asks how many* before fanning out (prose behaviour, not a gate)
- [ ] **Real detached worker** — starts from `Worker command`, opens a PR, and does **not** merge
- [ ] **`--status` / `--stop`** — a live worker is distinguishable from a dead one
- [ ] **Reaper** — an abandoned claim is offered for deletion; a bare claim is not
- [ ] **`/plot-merge-queue`** — the order is trustworthy enough to merge from
- [ ] **Phase gate** — a Draft plan is refused, including when the script is called directly

### Adoption and framing (new since rc.1)

- [ ] **`/plot-init` in a repo that has no Plot** — does it propose rather than
      interrogate? Are its proposals right, and is the one question it insists
      on (which script gates a merge) the right one to be asked?
- [ ] **`/plot-init` detection accuracy** — git host, quality gates, ticket
      scheme, commit notation, existing planning systems. A wrong proposal is
      cheap; a confident wrong one is not
- [ ] **Additive guarantee** — run it in a repo that already has `docs/plans/`
      with loose files. Nothing may be moved, rewritten, or deleted
- [ ] **`plot-context.sh`** — on a plan branch it names the governing plan; on
      an unrelated branch it says so instead of guessing
- [ ] **Four-phase model** — does the map in the intro match how the work
      actually feels, or does it describe a workflow nobody follows?
- [ ] **`/plot-deliver`'s refuting check** — does asking subagents to *disprove*
      deliverables find gaps that the old confirming phrasing missed?

## Known limitations shipping in this release

Not defects. Confirm each is acceptable rather than testing it:

- [ ] Stage 6 (autonomous merge authority) is deliberately deferred — merging stays human
- [ ] Worktrees are not cleaned up automatically; `/plot-reconcile` suggests the commands
- [ ] `Worker command` must be written by the adopting project (Plot hardcodes no agent tooling)
- [ ] Claim commits (`plot: claim …`) appear in each branch's history and in its PR
- [ ] `--loose` degrades to strict without a git host, since PR readiness cannot be verified
- [ ] `/plot-init` has never been run against a repo other than this one — for
      an instruction skill that is the only meaningful test, so this release
      ships it unproven in the field
- [ ] Claim commits (`plot: claim …`) appear in each branch's history; a
      squash merge drops them, a merge commit keeps them

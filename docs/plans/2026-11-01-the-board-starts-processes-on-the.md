# The board starts processes on the /api/board request path

> `GET /api/board` starts dozens of short processes one after another before it answers. On a loaded machine the request outlasts the page's wait, and the page shows "No contact with the board server" while the server is alive.

## Status

- **State:** Approved

- **Sprint:** delivery-loop
- **Issue:** #3017
- **Review:** pr
- **Impl:** own branches
- **Rounds:** 1
- **Approved:** 2026-11-01, Jan Wloka, plan-PR #3018 merged

## Changelog

- `/api/board` reads `## Plot Config` values from a held copy. The copy is checked against the stat of `CLAUDE.md` and `AGENTS.md` on every read, so a config edit shows on the next request and an unchanged config starts no `plot-config.sh`.
- `/api/board` reads git answers that depend only on object ids (the Delivered record, plan authors, the behind count, the default branch, draft plan files) from the domain's oid-keyed walk cache, over the one ref snapshot the request already reads.
- `/api/board` parses a plan once per blob. A warm request starts no `plot-plan-meta.sh` for plans that did not change, and the Stories lanes are computed once per request, not twice.
- A test counts the processes one warm `/api/board` request starts and fails on any start that is not on its named list. At the end of this plan the list holds `git for-each-ref` and `git status --porcelain`.

Board impact: yes, and it is the whole subject. No plan-format change, no schema change, no wire field.

## Motivation

Measured 2026-11-01 on the operator's machine, board pid 28045 on `origin/main` at `eeea594c6` (issue #3017):

- `/api/board` took 7.8 s, 17 s, 22 s, 26 s, and earlier 30 s, 48 s and 61 s. The page showed "No contact" for 17 and later 103 polls. The layering juror measured one request at 12.07 s at load 11.5 (2026-11-01 20:38).
- The board process used 0 % CPU during a request. It waited on its children. Load average was 6 to 9, with one spike to 21. Each process start cost about 180 ms while `syspolicyd` ran at 87 % CPU, and 20 ms after it dropped. So the wall time of a request follows the number of starts it waits on, not its CPU.

The issue sampled every child of the board pid every 0.2 s. That sample holds two populations: the request's own starts and the starts of the refresh loop, which runs in the same process every 5 s (`REFRESH_MS`, `packages/board/src/server/fleet.ts:176`). Read from the code on `origin/main` at `0974e8956`, these starts are on the request path. All four panel jurors found them by reading; no juror counted them per request.

- **Config, about 24 reads per request through four routes.** `readConfigAsync` (`board.ts:651` → `packages/fleet/src/shared/config-reader.ts:36`), `scriptsFor(opts).config` (`fleet.ts:1832`, `Tracker` and `Plan directory`), `planStoreFor(opts).config` (`server-info.ts:115`, `Board command` at `:237`), and the synchronous `readConfig` in `interrogateAvailability` (`index.ts:506` → `interrogate.ts:57`), which blocks the event loop for one `plot-config.sh` run on every request. Each `plot-config.sh get` starts about five processes (`bash`, `grep -q`, `awk`, `grep -m1`, `sed`; `plot-config.sh:290-324`). Two more values, `CI` and `People`, are held for the life of the process with no invalidation, including a failed read (`cachedCi`, `cachedPeople`, `server-info.ts:139-180`).
- **The whole estate is parsed on every request.** `buildBoard` stages the plans and runs `plot-plan-meta.sh` over every plan file (`readPlanMeta`, `board.ts:1454`, called at `:2318`). `origin/main` holds 626 plan files. `collectPlanSources` runs `ls-tree`, `cat-file`, `rev-parse` and `rev-list --count` before the parse (`board.ts:901-935`, `measureBehind` at `:856`). Nothing holds a finished build; two concurrent polls share one build in flight (`controllers/fleet-state.ts:163`). One parse of 620 plans measured 0.52 s CPU (`the-plan-walk-moves-into-the`).
- **The Stories lanes run twice.** `ticketLaneData` runs at `index.ts:493` and again inside `discoveryLanes` (`discovery-lanes.ts:49`). Each run computes the key of `planMetasAtDefault`'s oid cache (`fleet.ts:1589-1603`) before it reads the cache: `Plan directory` (config), `defaultBranchOf` (config, then `bash -c 'git symbolic-ref … | sed …'`), `refs.resolve` and `branchTips`, plus a `Tracker` read (`fleet.ts:1832`). `draftPlanFiles` runs `git show` once per draft branch (`fleet.ts:1812`).
- **The Delivered record costs about four starts per Delivered plan.** `buildBoard` awaits `refs.recordCommit(rel, 'Delivered')` once per Delivered plan, one after another (`board.ts:2321-2332`). 17 of the 626 plans read `State: Delivered`. Each call runs `defaultBranch()` (`refs-git.ts:438-444`, three processes) and then `git log -G … origin/<name>` (`refs-git.ts:647-656`). That is about 68 sequential starts. The issue said "one per plan file"; the count is per Delivered plan.
- **Other git reads per request.** `refsToken` runs `git for-each-ref` (`fleet-state.ts:139`). `planAuthors` runs `git log --diff-filter=AR --name-status` (`refs-git.ts:856-870`). `countBehind` runs `git symbolic-ref` and `git rev-list --count HEAD..<ref>` (`refs-git.ts:717-728`). `treesFor(opts).isClean` runs `git status --porcelain`. `spawnContractReadingFor` (`board.ts:353`) runs `hashFilesSync`, a synchronous `git` start (`refs-git.ts:783`).

**Correction to the issue: the supervisor reading is not on the request path.** `readSupervisor` has one caller, `refresh` (`fleet.ts:2847`). `ensureCache` starts `refresh` without an await, and the pulse runs it every 5 s (`fleet.ts:3199-3210`). The `/api/board` handler (`index.ts:462-540`) reads no supervisor field. `plot-fleetctl.sh --status` takes 3.9 s to 12.8 s, so it overlaps almost every request window, and the sample counted it. The comment at `fleet.ts:2835` is correct.

Two earlier plans moved the same path: `the-read-path-stops-spawning` (2026-08-31) and `the-scan-spawns-git-once-per-question` (2026-08-20). Both are Released. The starts above survived both, and this plan names each one.

## Design

### Approach

**The request reads held values, and each held value names the input that invalidates it.** The request does not read a held payload. The payload mixes values that move on their own clocks (the PR index, the pulse, the supervisor reading), so one payload key would have to cover all of them, and a held payload would add up to one refresh of staleness (about 40 s under the measured load) that the page would then have to show. Each held value below is keyed by an input the request itself checks, so it carries no age.

1. **Config is held per config stamp.** One adapter decorator over `Scripts.config` holds `plot-config.sh` answers. Its stamp is the repository root plus, for each of `CLAUDE.md` and `AGENTS.md`, presence, `mtimeMs`, `size` and `ino`; absence is recorded as a fact. The adapter stats both files on every read, never on a timer. A changed stamp clears the held answers. The held key is (stamp, `get` or `get-raw`, key, fallback). An answer from a failed or timed-out read is never stored. `plot-config.sh` stays the one parser, so no TypeScript duplicate and no corpus pair is added.
2. **All four config routes read through that adapter.** `config-reader.ts` builds its reader with it, so the synchronous `readConfig`, `readConfigAsync`, `scriptsFor(opts).config` and fleetd's `walkOnce` share it. `BuildBoardOptions` gains an optional `config` field so that `planStoreFor(opts).config` and every board route read the same instance and a test can inject a counting fake. `cachedCi` and `cachedPeople` read through it and stop holding a value for the life of the process. Write routes keep reading through the same adapter, which is stamp-checked, so a write route never acts on a stale config value.
3. **How this differs from the cache `the-read-path-stops-spawning` removed.** That cache wrapped the synchronous `readConfig`, and the read path had stopped calling it, so `board.ts:621-626` records it as a cache nothing on the hot path read. Its `configStamp` already stat'ed both files and held `repoRoot`, after two temp repositories with equal mtimes read each other's answers in CI on 2026-08-31. This adapter sits on the seam every route uses, keeps `repoRoot` and adds `ino` and `size`, and stores no failed read. It is needed again because the read path now makes about 24 async config reads per request, and each start costs 20 to 180 ms on this machine whether or not it blocks the loop.
4. **Git answers are held in the domain's walk cache, not in a second board cache.** `cachedRefs` and `WalkCache` (`packages/domain/src/workflows/plan-walk-cache.ts:88`, `:230`, from #2995) gain four keyed operations: `recordCommit` keyed by (`origin/<default>` oid, file, field); `planAuthors` keyed by (`origin/<default>` oid, directory), like `planAdditions`; `countBehind` keyed by (HEAD oid, attached or detached, `origin/<default>` oid); and `defaultBranch` keyed by the snapshot digest. Every cached call reads through the oid in its key, never through a ref name. So `Refs.recordCommit` gains a `ref` parameter and reads `git log` at that oid (`ports/refs.ts:406`, `refs-git.ts:640-657`); `refs-fixture.ts:365` and the callers in `entry/design.ts:170`, `entry/verify.ts:400`, `auto-design.ts:473` and `auto-verify.ts:304` change with it. A failed read is never stored, and the next request asks again.
5. **The board holds one `WalkCache` per `cacheKey(opts)`.** `refsToken` keeps its one `refState('both')` read and passes the snapshot on. `buildBoard` wraps `refsFor(opts)` with `cachedRefs` over that snapshot and calls `begin` and `sweep` once per completed build, so the cache stays bounded by the live estate. `planEstate`, `planMetasAtDefault`'s key, `measureBehind` and the Delivered loop then read `resolve`, `branchTips`, `defaultBranch` and `countBehind` from the snapshot. The default branch is resolved once per request: the `Main branch` config value when it is set, else `origin/HEAD`, which is the order `defaultBranchOf` (`board.ts:1016`) already uses. The plan text and the Delivered record are read at the same oid, so `verificationOf` (`board.ts:2520`) compares two readings of one commit. `draftPlanFiles` reads through `Refs.showFile`, keyed by the draft branch oid.
6. **A plan is parsed once per blob.** The parsed `PlanMeta` is held in the same `WalkCache`, as one more keyed kind beside `parses`, under the key `cachedPlans` already uses: (blob oid, path, prefixes, parser hash, config digest). The board parses with `plot-plan-meta.sh`, whose `PlanMeta` carries fields that the domain's `PlanRecord` does not, so the board cannot read `parses` without a parser contract change; it shares the key rule, the store and the sweep instead. A plan from a ref is keyed by its blob oid. A plan from the working tree is keyed by its git blob id, computed in-process from its bytes. Only missed plans are staged and parsed. The config digest gains `Tracker`, because the parser's `issues` output depends on it (`plot-plan-meta.sh:366-385`); the walk's digest at `fleet-scan.ts:720` gains it in the same slice. `planMetasAtDefault` reads through the same store, and its private `planMetaCaches` (`fleet.ts:1656`) goes. `ticketLaneData` runs once per request, and its answer is passed to `discoveryLanes`.
7. **`hashFilesSync` is held per bundle stat.** The contract reading's hash is re-read only when the bundle file's (`mtimeMs`, `size`, `ino`) changes, so the synchronous start leaves the request.
8. **The count is a ratchet, and it lands first.** The `/api/board` handler body (`index.ts:478-518`) moves into a controller, `boardAnswer(opts, host, port, archived)`, so the count runs without a server and the rendered answer stays a controller result. A board unit test in the `parallel` vitest project mocks `node:child_process` with a pass-through that records `spawn`, `execFile`, `execFileSync` and `spawnSync` with their command lines. Thirteen board modules import `node:child_process` directly, so the module mock is the one seam that sees every start; a counting port sees only adapters. The test stops the refresh clock with a new seam that keeps the caches (`stopFleetRefresh`, `fleet.ts:3323`, clears them), pins the time with `vi.setSystemTime` so the 5 s and 60 s holds in `serverInfo` do not expire, calls `boardAnswer` once to warm, and then asserts the exact list of starts of the second call. It asserts no duration. The ratchet slice records today's list. Each later slice removes its own lines from that list in its own diff, and any line not on the list fails with the list printed.
9. **The read-route gate covers what the handler calls.** `a-read-route-spawns-nothing.test.ts` walks only `boardState`, `fleetState` and `serverInfo`. Its `ENTRIES` gain `boardAnswer`, which reaches `ticketLaneData`, `discoveryLanes`, `planRefAgeSeconds`, `interrogateAvailability` and the other `*Availability` calls. So the ratchet slice moves `interrogateAvailability` onto `readConfigAsync`: one async start replaces one synchronous start, the count stays the same, and the gate passes.

**What the count does not see.** The module mock counts the starts the board makes, not the processes a script starts inside itself. `plot-config.sh get` counts as one start and costs about five processes. The Done-when rows therefore also assert the call count at the config adapter and at `cachedRefs`, so a script's internal cost is not hidden behind one line.

**Layering.** The controller calls the domain. The held config is an adapter decorator in `packages/domain/src/adapters/`, beside `scripts-shell.ts`, and is the only new code that reads the file system for config. `cachedRefs` stays a domain workflow over the `Refs` port. No new spawn site is added outside `adapters/`. Domain code is arrow functions with factual TSDoc.

### Decisions

Decided 2026-11-01 after panel round 1 (`.plot/panels/2026-11-01-the-board-starts-processes-on-the/panel.md`, unanimous amend):

- [x] **The supervisor slice is dropped.** Behaviour 3 already holds on `origin/main` (all four jurors). The safety juror's asked-at time for the stored supervisor reading is a follow-up in `## Notes`, not a slice, for three reasons. It changes no start on the request path, which is this plan's subject. It needs a wire field and a render change. And it edits `refresh` (`fleet.ts:2779-2917`), the function `feature/the-last-scan-modes-run-the-walk` and `feature/the-scan-script-is-a-launcher` edit, so as a slice here it would wait on that chain and hold back this plan's relief.
- [x] **No second oid cache in the board.** The Delivered record and the other per-request git reads extend `cachedRefs`, and the plan parse uses the `WalkCache` key rule and sweep (layering and seams jurors).
- [x] **One config adapter for every route, `plot-config.sh` stays the parser** (all four jurors; the safety juror allowed a TypeScript parser with a corpus pair, which this plan does not take).
- [x] **The count runs in-process with a `node:child_process` mock at a controller** (testability juror). The PATH-shim precedent in `plan-read-shape.test.mjs` also counts the refresh loop, and `stopFleetRefresh` clears the warm caches the count needs.
- [x] **The count lands first as a ratchet** (testability and seams jurors), so each slice carries its own proof.
- [x] **Order after the ratchet: config first.** Config gives the most per request by start count: about 24 script starts at about five processes each. The board waits on starts, not on CPU, so this slice relieves the operator first, and it touches no code the walk or #2993 slices edit. The git-read slice can run beside it. The plan-parse slice saves the most CPU (one 0.52 s parse and 626 staged files per request) and waits on the git-read slice, which builds the board's `WalkCache`.

### Open Questions

- [x] Which remaining starts belong to the object-id key? `git for-each-ref` is the snapshot read itself and stays, one per request. `git rev-parse` and `branchTips` are answered from the snapshot. `rev-list --count` is keyed by (HEAD oid, attached or detached, `origin/<default>` oid). The `--diff-filter=AR` log is keyed by (`origin/<default>` oid, directory). The Delivered `git log -G` is keyed by (`origin/<default>` oid, file, field) after the port change. `git status --porcelain` has no oid and stays on the list. The bundle hash is held per bundle stat.
- [x] Why did `plot-fleetctl.sh --status` run inside the request window? It is the refresh tick's call at `fleet.ts:2847`, which runs every 5 s and often takes longer than 5 s. The sample counted every child of the board pid. It is not a cold request, a stale reading or a second caller.
- [x] What counts as warm, and what is the allowed count? Warm means one `boardAnswer` call has completed on the same estate, the refresh clock is stopped with the caches kept, the time is pinned, and no ref, config file or plan file changed since. The allowed count is an exact list. At the end of this plan it is one `git for-each-ref` and one `git status --porcelain`.

## Notes

- Filed from issue #3017. The plan's `Issue:` field is the only link; nothing is written to the tracker.
- **Follow-up: the stored supervisor reading carries no age.** `SupervisorRun` (`packages/domain/src/rules/supervisor-reading.ts:69-122`) has no asked-at time, and `tickStale` compares a frozen `tickAgeSeconds`. Under the measured load a reading served as `up` can be minutes old, and the same value feeds `fleetOwnsScan` (`fleet.ts:2459`). The fix needs a wire field: the reading carries its asked-at time, render ages `tick_age` by it, and a reading older than a bound reads `unknown` for the verdict and for `fleetOwnsScan`. The read stays on every refresh tick. File it as its own issue, ordered after `feature/the-scan-script-is-a-launcher` (safety juror).
- **Follow-up: the supervisor reading's cadence.** One desk walk of 3.9 s to 12.8 s runs every 5 s whether or not anyone views the board. Reading fleetd's own state instead is a separate change (layering and seams jurors).
- **Follow-up: the board's fleetless scan runs cold every beat.** `ScanState.walkCache` is absent on the board's cache entry (`fleet-scan.ts`). One field would give it the walk cache. It is load on the same machine, not a request-path start (seams juror).
- **Rejected: a held payload built on the beat** (safety, testability and seams jurors' smaller design). It removes every start from the request in one slice, but the page could be one refresh older than the refs (5 s, about 40 s under the measured load) and would need to show that age. The held values in this plan are keyed by inputs the request checks, so they need none.
- **Order with the plan walk and #2993.** `feature/the-last-scan-modes-run-the-walk` and `feature/the-scan-script-is-a-launcher` edit `refresh` and the fleetless scan in `fleet.ts`; no slice here edits `refresh`, so none waits on them. `feature/the-fleet-payload-indexes-its-plans` (`every-plan-reference-shows-its-issue`) builds from the metas `planMetasOf` returns; `feature/the-board-parses-a-plan-once-per-blob` changes the cache under `planMetasAtDefault` and not its answer, so a wait is too strong and the later of the two rebases. `fleet.ts` changed in 24 commits in one week, so every slice here that touches it rebases on `origin/main` before review.
- **Remaining start.** `git status --porcelain` (`treesFor(opts).isClean`) reads the working tree and has no oid. It stays on the list; holding it needs a file-system watch, which this plan does not add.

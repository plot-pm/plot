No file lists the steps in the order a person performs them. The facts below were read from `main` at `532a0e6c6` on 2026-11-21.

**Facts that decide the order and that no adopter-facing file states in one place:**

- Three GitHub Apps are needed. The Review App has the permissions commit statuses: write, pull requests: read and contents: read. The Writer App has contents: write and sits on the ruleset's bypass list. The Merger App has contents: write and pull requests: write and never sits on the bypass list (`docs/review-status-rollout.md:31-38`, `:164-177`, `:190-200`). A fourth App builds Plot's own generated bundles and sits on the ruleset's bypass list (`.github/workflows/build-bundles.yml:3-8`). No adopter step uses it.
- The key of each App lives outside the repository: `${XDG_CONFIG_HOME:-$HOME/.config}/plot/plot-<role>.<app id>.private-key.pem` with `<role>` set to `review`, `writer` or `merger`, mode 600, or the path in `PLOT_REVIEW_APP_KEY`, `PLOT_WRITER_APP_KEY` or `PLOT_MERGER_APP_KEY` (`docs/review-status-rollout.md:54-62`; `docs/plans/2026-11-06-app-keys-resolve-from-one-folder.md`, "Approach"). The Merger App needs another id than the Writer App, or every merge refuses with exit 4 (`docs/review-status-rollout.md:216-218`).
- On GitHub, fleetd merges only when `Merger app` is declared and readable. With the key absent, its merge arm holds every row as `merger-app-missing` (`docs/review-status-rollout.md:157`; `packages/domain/src/rules/merge-identity.ts:12`, `:40`). At start, Plot logs `App key '<key>' is not usable: <reason>` for a declared key that cannot be used (`packages/domain/src/rules/app-key-start-lines.ts`).
- The branch ruleset is a person's act in the host's settings. The live ruleset of this repository, read with `gh api repos/plot-pm/plot/rulesets` on 2026-11-21, targets the default branch and is active. Its rules are `deletion`, `non_fast_forward`, `pull_request` with 0 required approving reviews and `required_status_checks` for `validate` and for `plot/review`, the second pinned to the Review App's integration id. Its bypass list, mode `always`, holds a repository role and two Apps: the Writer App and the App that builds the bundles. The Merger App is not on it.
- The ruleset comes last. It is added after a writer has run for every kind of pull request, "or it blocks merges it was meant to admit" (`docs/review-status-rollout.md:75-85`).
- A release approval through the board needs a passkey. The relying party id is `localhost` (`packages/board/src/server/passkey.ts:16`). A page on another host shows "A passkey works only on http://localhost:<port>" and offers no action (`packages/domain/src/rules/passkey-settings.ts`). The credential sits in `.plot/state/passkey.json` (`packages/domain/src/adapters/passkey/passkey-file.ts`), under `.plot/state/`, which this repository's `.gitignore` lists (line 30). The settings view offers `Register` when no passkey exists. The approval, `POST /api/release-approve`, needs a user-verified assertion from the registered platform authenticator (`AGENTS.md:548`) and merges only a pull request from a `changeset-release/` branch (`packages/domain/src/rules/release-branch.ts:13`).
- The fleet reviews and merges only the branches of plans in the active sprint. With no active sprint, or with two, it reviews and merges nothing (`packages/domain/src/rules/sprint-scope.ts`, the refusals `no-active-sprint` and `multiple-active-sprints`). The scope reads `docs/sprints/active/*.md` (`packages/domain/src/adapters/sprint-scope-ref.ts:82-89`). A person's `sprint: scope change` commit moves the scope (`docs/stories/archived/the-fleet-delivers-a-scope-alone/DESIGN-delivery-loop.md:21`). `/plot-sprint` operates only where Plot owns the sprints, that is, with `Tracker: plot` or `Sprint owner: plot` (`skills/plot-sprint/SKILL.md:18-40`).
- `/plot-fleet --start` needs launchd or systemd, a `Worker command` that runs the loop, a harness on `PATH`, a unit that does not update itself and a `node` at the major that Plot's own `.nvmrc` pins (26) (`skills/plot-fleet/SKILL.md:13-16`, `:167-226`; `skills/plot/scripts/plot-fleetctl.sh`, the `pinned_major` function). fleetd and the board refuse a git older than 2.42 (`skills/plot/scripts/plot-board-probe.sh:29-32`). The board probe compares against the adopting repository's own `.nvmrc` and reports `null` where it has none (`skills/plot/scripts/plot-board-probe.sh:98-116`).
- `python3` is called by `skills/plot/scripts/plot-merge-queue.sh`, `plot-context.sh` and `plot-detect-repo.sh`. `plot-fleetctl.sh` does not call it.
- The shipped worker prompt starts the agent with `--permission-mode bypassPermissions` on the operator's machine (`skills/plot/templates/worker-prompt.sh:188`) and starts no container. The agent runs as the operator's user, so it can read every file that user can read, including the App keys under `~/.config/plot/`. The Writer App sits on the ruleset's bypass list, so its key bypasses the ruleset.
- The default `command` runner has no spend cap. `Agent max spend` and `Slice max spend` bound only the SDK runner, and both are blank by default (`skills/plot/scripts/plot-config.sh:163-168`). Draft plan `the-default-runner-has-a-spend-cap` (PR #3698) adds `Slice max tokens` for both runners.

A machine that sleeps stops fleetd and the board until it wakes. A detached worker cannot answer a prompt, so the operator decides this once, before the first run.
- The reviewer's model, effort and turn limit come from `.claude/agents/reviewer.md`, which `/plot-init` provides (`packages/board/src/server/entry/review.ts:423-430`). A repository whose file is missing or unusable gets a refusal that names the file.

## Design

### Approach

- **One page, `docs/adoption-guide.md`, titled "From install to the first autonomous run".** The path is neutral on purpose: the page covers both tiers, and a file named after the fleet would suggest that every reader needs the fleet. `[question-guide-path]` asks the maintainers to confirm the name.
- **A numbered procedure in the order a person performs it.** Each step has a Do line (the command, or the settings page as a path of menu names) and a Check line (how to know the step worked). A step that needs a hand that no agent has names the person's act. A command sits in a code block.
- **Four levels in two tiers.** The page names the level at the head of each group. The tiers are defined in `docs/automation-spectrum.md` (plan `plots-documents-describe-the-automation-that-runs`, PR #3631): the guide names each tier at its boundary and links that page, and it does not define the tiers again.
- **Links in, no copies.** The README links the page from "Start here" (after the line that names `/plot-fleet --start`) and from no other section; PR #3631 links `docs/automation-spectrum.md` from "Configuration". PR #3631 owns the install section and the "Next" section of `skills/plot/docs/quickstart.md`, and the first link of that "Next" section goes to `docs/automation-spectrum.md`. This plan adds the guide's link below that link.
- **One page owns each fact.** The guide owns the order and the checks. `docs/automation-spectrum.md` owns the two tiers, which stations run by themselves and the switches that turn them on. `docs/review-status-rollout.md` owns the App permissions, the key resolution and the refusals. `skills/plot-fleet/SKILL.md` owns the supervisor's verbs and refusals. The guide links to each and repeats none.
- **Paths, not line numbers.** The guide cites a source by its file path and, where needed, a heading or a symbol name. It cites no line number, because line numbers move: the panel of 2026-11-23 found four of the plan's citations moved within two days.
- **A test holds the guide.** `test/reconcile/adoption-guide.test.mjs` reads the guide and fails where it no longer matches the repository (see the guide-page slice).
- **The guide states its own status.** Its first paragraph says "not yet run end to end by a second person" until the last slice lands. Each open question of this plan that only a second operator can answer appears in the guide as a blockquote that starts with `Open question:` at the step it concerns, so the second operator sees where the guide is thin.
- **No new name for the fleet.** The guide uses the words the repository already uses: the fleet, the supervisor, the agents and the full loop.
- **No version numbers of Apps or UIs that no file gives.** The guide names a setting and not the layout of GitHub's pages.

### Tiers and levels

The guide puts tier one first and marks clearly where tier two begins. `docs/automation-spectrum.md` defines the two tiers ("Plot without a fleet" and "The fleet"). The guide names each tier at its head, links that page for the definition and for which stations run by themselves, and maps its levels onto the tiers. The bullets and the table below brief the guide's author; the guide does not copy the table's "What runs by itself" column.

- **Tier one: Plot without a fleet.** Levels 1 and 2. Level 1 needs the plugin install and `/plot-init`. Level 2 adds `/plot-board-setup` and `/plot-board --start`. Tier one needs no GitHub App, no key, no ruleset, no passkey and no unit. A team can stop after tier one and still use Plot completely. The page says so at the end of tier one.
- **Tier two: the fleet.** Levels 3 and 4. The operator runs tier two. The page opens tier two with a heading that names the boundary, "Tier two: the fleet (operator)", and one paragraph that says who the operator is, what tier two sets up, that a team can stop before it, and how to stop the fleet at once (`/plot-fleet --stop`, or `Auto-dispatch` off).
- **The operator** administers the repository's settings (the Apps and the ruleset), owns the machine that runs the supervisor (the keys and the unit) and opens the board on that machine to register the passkey. One person can hold all three roles. `[question-operator-roles]` asks whether a team can split them.

| Level | Tier | Name | What runs by itself | Steps |
|---|---|---|---|---|
| 1 | one | Plans only | nothing; a person runs every command | 1-4 |
| 2 | one | The board | the board shows the work; a person runs every command | 5 |
| 3 | two | The fleet, a person merges | dispatch of eligible slices (`Auto-dispatch`) and the worker loop; a person reviews and merges | 6-7 |
| 4 | two | The full loop | review (`Auto-review`) and the merge by the Merger App inside the active sprint's scope, and the release preparation; only the plan approval and the release approval wait for a person | 8-14 |

### Steps

Each line gives the step, the command or settings page (Do), the proof (Check) and the person's act (Person). A level ends with what the reader has at that point.

**Level 1: plans only (tier one)**

1. **Check the machine.** Do: confirm `git --version` is 2.42 or later, `command -v claude` answers, and `gh auth status` answers for the repository's host. The board needs Node from step 5 on. Use the major in Plot's `.nvmrc` (26 on `main` at `532a0e6c6`; `nvm install 26 && nvm use 26`), because `/plot-fleet --start` in step 7 refuses any other major. From step 7 on, the machine must run launchd (macOS) or systemd (Linux). `python3` is optional. Check: each command answers. Person: install what is missing. Source: `skills/plot-board-setup/SKILL.md:15`, `skills/plot-fleet/SKILL.md:13-16`.
2. **Install the plugin.** Do: in Claude Code, `/plugin marketplace add plot-pm/plot`, then `/plugin install plot@plot-marketplace` (`README.md:33-38`). Check: `/plugin` lists `plot`, and the version equals the latest release tag. The marketplace installs from the tag `vX.Y.Z`; an update between the release merge and the tag push fails with "Remote branch vX.Y.Z not found" and succeeds a minute later (`RELEASING.md:58-60`). Person: confirm the prompts.
3. **Adopt the repository.** Do: run `/plot-init` in the repository root. It proposes a `## Plot Config` block and writes it with the skeleton, `.plot/worker-prompt.sh`, the key `Worker command: PLOT_UNATTENDED=1 plot-worker-loop.sh`, and the role definitions `.claude/agents/<role>.md`, with `.claude/settings/<role>.json` for the roles that hold a `Bash` or write tool (`skills/plot-init/SKILL.md:611-672`; `packages/domain/src/rules/adoption-roles.ts:6-8`). Check: the proof that `/plot-init` prints, `plot-config.sh get "Plan directory" "docs/plans/"`, echoes the value (`skills/plot-init/SKILL.md:812-822`); `.plot/worker-prompt.sh` exists; `.claude/agents/` holds `reviewer.md`, `fixer.md`, `unblocker.md` and `main-repair.md`; the roles command lists no `gaps`. Person: confirm each proposal, answer the questions that the repository cannot answer, and accept or decline the offered `PreToolUse` gates (`skills/plot-init/SKILL.md:743-783`).
4. **Run one plan by hand.** Do: `/plot-idea`, `/plot-approve`, `/plot-implement` and `/plot-deliver` on a small change (`README.md:48-55`). Check: the plan file reaches `State: Delivered`, and `/plot` reports it. Person: approve the plan. The board-free commands `plot-approve-command.mjs` and `plot-deliver-command.mjs` refuse `PLOT_UNATTENDED=1` (`CHANGELOG.md:169`).

**Level 2: the board (tier one)**

5. **Adopt and start the board.** Do: `/plot-board-setup`, then `/plot-board --start` (key `Board port`, default 7777: `skills/plot-board/SKILL.md:44-49`). Check: `--start` prints the URL, `/plot-board --status` answers, and the setup's own proof fetches the board's data and finds the plan's card (`skills/plot-board-setup/SKILL.md:20-31`). Person: confirm the proposals and open the URL.

*The page ends tier one here: the reader has plans and a board, and a team can stop.*

**Tier two: the fleet (operator)**

**Level 3: the fleet, a person merges**

6. **Decide the cost and the risk, and own the worker prompt.** This step comes before `/plot-fleet --start`. Do: open `.plot/worker-prompt.sh`. It starts `claude -p` with `--permission-mode bypassPermissions` on this machine, because a detached worker cannot answer a prompt (`skills/plot/templates/worker-prompt.sh`). The guide states four facts here. (a) Cost: the default `command` runner has no spend cap today. `Agent max spend` and `Slice max spend` bound only the SDK runner, and both are blank by default (`skills/plot/scripts/plot-config.sh`); the only bounds on a `command` agent are `Worker bound` and `Correction budget`. When plan `the-default-runner-has-a-spend-cap` (draft PR #3698) delivers, this step sets `Slice max tokens` in `## Plot Config`, and its Check reads the value back with `plot-config.sh get "Slice max tokens"`. This plan does not wait for #3698; the slice that folds the second operator's run adds the line if #3698 has delivered by then. (b) Risk: an agent in bypass mode runs as the operator's user and can read every file that user can read, including the Merger and Writer App keys under `~/.config/plot/` and any secret in the repository. The Writer App sits on the ruleset's bypass list, so its key can bypass the ruleset. The guide recommends a separate OS user or a separate machine for the fleet. (c) Availability: on macOS the unit loads into the `gui/<uid>` domain and needs a logged-in session (`skills/plot/units/README.md`); a machine that sleeps stops fleetd and the board until it wakes, and the release approval needs the board at `localhost`. (d) Stop: `/plot-fleet --stop` stops the fleet, and `Auto-dispatch` off stops new dispatches. Check: the file says what the operator wants an agent to be told; the key `Agent settings` names a settings file that turns off plugins that fleet agents must not start, where the operator uses any (`skills/plot/scripts/plot-config.sh`); the operator has chosen the user and the machine that run the fleet. Person: decide to accept bypass mode and an uncapped runner on this user and machine. Nobody else can decide this.
7. **Start the fleet.** Do: `/plot-fleet --once`, which ticks once and installs nothing; then `/plot-fleet --start 3`; then `/plot-fleet --status` (`skills/plot-fleet/SKILL.md:75-165`). On Linux, `sudo loginctl enable-linger "$USER"` keeps the supervisor alive after logout (`skills/plot/units/README.md:137-141`). Check: `--once` prints a `plot-fleetd tick agents=… held=…` line; `--status` exits 0; on macOS `launchctl print "gui/$(id -u)/com.plot-pm.fleetd"` shows the unit and `tail -f .plot/logs/fleetd.log` shows ticks; on Linux `systemctl --user status plot-fleetd` shows the unit and `journalctl --user -u plot-fleetd -f` shows ticks (`skills/plot/units/README.md:59-65`, `:118-124`). Person: read any refusal to the end, because each of the five names its repair; on Linux, run the one `sudo` command. Then switch on dispatch: set `Auto-dispatch` on in the board's fleet controls, or seed `Auto-dispatch: true` in `## Plot Config` (default off; `Parallel agents` defaults to 3; `packages/fleet/src/shared/fleet-settings-store.ts`). The board's switch is stored in `.plot/state/fleet-controls.json`. Check: the next tick hands an eligible slice of an approved plan to a free agent, and `/plot-fleet --status` shows an agent with a `branch:`. Person: approve a plan to give the fleet something to do.

*The page ends level 3 here: the fleet works and a person reviews and merges every pull request. A team can stop here before it creates any App.*

**Level 4: the full loop**

8. **Create the sprint that scopes review and merge.** Do: `/plot-sprint <slug>: <goal>`, then `/plot-sprint <slug> add` for each approved plan, `/plot-sprint <slug> commit` and `/plot-sprint <slug> start` (`skills/plot-sprint/SKILL.md`, the usage table). Check: `docs/sprints/active/` holds exactly one file. Person: choose the scope; a commit named `sprint: scope change` moves it. A repository whose tracker is not Plot needs `Sprint owner: plot` first. The sprint scopes review and merge; fleetd dispatches an approved plan outside the sprint as before (`docs/stories/archived/the-fleet-delivers-a-scope-alone/DESIGN-delivery-loop.md:21`).
9. **Create the three GitHub Apps.** Do: for each of Review, Writer and Merger, in GitHub's settings (Developer settings, GitHub Apps, New GitHub App): set the permissions in `docs/review-status-rollout.md:31-38`, `:169-173` and `:195-198`, clear the webhook, and install the App on this repository only. Check: each App's installation page lists this repository, and the Merger App's id differs from the Writer App's. Person: all of it. Who may create and install an App is open (`[question-app-owner]`).
10. **Store the keys and record the ids.** Do: for each App, generate a private key in the App's settings, save it as `~/.config/plot/plot-<role>.<app id>.private-key.pem` with `chmod 600`, and add `- **Review app:** <app id>`, `- **Writer app:** <app id>` and `- **Merger app:** <app id>` to `## Plot Config`. Add `- **Merge checks:** <the CI job that aggregates your required checks>` (`docs/review-status-rollout.md:43-62`, `:179-186`, `:206-214`; `skills/plot/scripts/plot-config.sh:255`). Check: run `/plot-fleet --restart`, then read the supervisor's log (macOS: `.plot/logs/fleetd.log` and `.plot/logs/fleetd.err`; Linux: `journalctl --user -u plot-fleetd`): no line `App key '…' is not usable` appears. Person: keep every key outside the repository.
11. **Prove each App before gating anything.** Do, in this order, on scratch work: (a) run `plot-review.mjs <pr>` on a scratch pull request and read the `plot/review` status on its head; (b) run `/plot-approve` on a scratch plan and read the author of the new commit on the default branch; (c) merge a scratch pull request through the normal path and read its merged-by field (`docs/review-status-rollout.md:68-73`, `:188`, `:220-223`). Check: the status author is `<review-app-slug>[bot]`, the pushed commit's author is `<writer-app-slug>[bot]`, and the merge shows `<merger-app-slug>[bot]`. Person: run the three proofs and read the three identities. With no Writer key, `/plot-approve` pushes as the ambient git identity and prints a line that says so (`docs/review-status-rollout.md:157`).
12. **Switch on review, prove the review writer, and register the passkey.** This step comes before the ruleset, because `docs/review-status-rollout.md` ("One-time setup, for a repository adopting the gate", steps 5 and 6) requires a running `plot/review` writer for every pull request kind before the rule is added, "or it blocks merges it was meant to admit". Do: set `Auto-review` on (the board's switch, or `Auto-review: true` in `## Plot Config`). With `Auto-review` off, fleetd's release step logs `skipped: auto-review-off` and writes no `plot/review` on the release head (`packages/fleet/src/shared/release-tick.ts`).

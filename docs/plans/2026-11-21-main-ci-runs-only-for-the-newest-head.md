# Main CI runs only for the newest head

> A push to `main` joins one CI concurrency group, so at most one run for an older head finishes and the newest head runs next, and a push whose changes since the last green head are only plan, sprint, index and brief files runs the jobs a plan-only pull request runs, not every suite.

## Changelog

- A merge into `main` no longer waits behind a queue of CI runs for older `main` heads. CI runs for one `main` head at a time; a newer push replaces a run that has not started yet, so the newest head runs next.
- The default-branch reading reads a `main` head whose CI run waits in the group as `pending`, not `unknown`. A person's `plot-ask.mjs merge` therefore refuses `default-branch-unsettled` over a head that no run has tested yet, also after `Checks wait`.
- fleetd's revert arm skips a commit whose CI run was cancelled where the commit changes only plan, sprint, index, release and brief files, and names the next red merge as before. Where such a commit itself turned `main` red, fleetd reverts the next red PR in error; the revert merges, `main` stays red, and the episode ends at `exhausted`.
- fleetd's revert arm no longer waits without end on any other commit whose CI run was cancelled. It ends the episode at `exhausted`, the repair record names that commit as `cancelledSha`, the notification names it, and a person's repair PR can then merge through `plot-ask.mjs repair-pr`. Since the replaced run of every older head is cancelled, more red episodes end at `exhausted` with no automatic revert than today.
- A push to `main` whose changes since the last green `main` run are only plan, sprint, index and brief files runs only the gates, `checks`, `corpus` and `validate`, the jobs a plan-only pull request runs, and not every suite. Such a run took 9.3 to 17.3 min on 2026-11-21, against a median of 148.5 min for a full `main` run.

## Motivation

Measured 2026-11-21 between 06:00 and 11:00 UTC on `plot-pm/plot`:

- The Actions API lists 307 runs in the window: 180 `push` runs on `main` (60 pushes, each starting `CI`, `Release` and `Build bundles`) and 85 `pull_request` runs. The organization is on GitHub's free plan (`gh api orgs/plot-pm` reads `plan.name: free`): 20 concurrent Linux jobs and 5 macOS jobs, shared by both kinds of run.
- Of the 60 first-parent commits on `main`, 46 carry a `plot:` subject that Plot writes itself (13 `plot: book the brief and plan start for …`, 10 `plot: approve …`, `plot: record PR #… for …`, `plot: deliver …`, sprint edits, 2 `plot: build the board artifact`). 9 more are plan-PR merges. 53 of the 60 change only paths under `docs/plans/`, `docs/sprints/` and `.plot/briefs/` (`git log --since=2026-11-21T06:00:00Z --until=2026-11-21T11:00:00Z --first-parent origin/main --name-only`). The other 7 are 4 code PRs (#3596, #3603, #3607, #3615), 2 bundle builds and 1 `challenge-the-plan` round that writes `.plot/panels/`.
- Every `main` push runs every job. The `select` job maps a non-`pull_request` event to every job (`.github/workflows/ci.yml:224`), and its install, build and ask steps run only on `pull_request` (`ci.yml:174-208`). A `main` CI run has 11 jobs.
- Push runs on `main` never cancel each other. The concurrency group for a push is `github.run_id` (`ci.yml:78-80`), and `test/reconcile/release-pr-ci.test.mjs` holds that ("ci.yml gives every main push run its own group"). 22 `main` CI runs were queued at once; 21 were cancelled by hand at 10:35 UTC.
- The 40 newest green `main` CI runs took a median 148.5 min from start to end, at least 19.9 min. The median gap between two pushes was 1.9 min, and only 2 gaps reached 20 min.
- Plan-only pull request runs, which run the job set slice 2 gives a bookkeeping push, took 9.3 to 17.3 min (runs 44893921544, 44894023149, 44877522071, 44876592328, 44876462684, read with `gh api …/workflows/ci.yml/runs?event=pull_request&status=success`).
- fleetd's default-branch reading stayed settled on `b21961602f02` (`plot: move story delivery-tab-reads-at-a-glance to done`, 05:55 UTC) from about 08:28 to 11:30. A merge into `main` needs the reading's settled commit to be the tip, or a green settled commit followed by at most `ANCESTOR_ASKS_MAX` (5) commits that change only Plot's paths (`packages/domain/src/workflows/merge.ts:380-393`, `packages/domain/src/rules/slice-pr-next.ts:476-490`, `packages/domain/src/rules/settled-past.ts:44-50`). Meanwhile fleetd's merge arm held every PR into `main` as `merge-in-flight` (`slice-pr-next.ts:488-489`), and a person's `plot-ask.mjs merge` refused `default-branch-unsettled` (`merge.ts:391-392`). PR #3619 and others waited 3 h with green CI.

`.github/workflows/build-bundles.yml:16-18` already puts every `main` push in one group with `cancel-in-progress: true`, because an older build must not overwrite a newer one.

## Design

### Decisions

- **`cancel-in-progress: false` for the `main` push group.** Decided by the operator on 2026-11-21, against the `true` the request named. With `true`, every push cancels the run in progress. With a median push gap of 1.9 min, a full run of at least 19.9 min and a narrowed run of 9.3 to 17.3 min, a head's run concludes only in a quiet gap longer than one run, and such a gap of 20 min occurred twice in 5 h. The reading would stay settled on an old commit for longer than today. With `false`, one run finishes and the newest pending head runs next, so a head settles within about two run lengths. `build-bundles.yml` uses `true` for a different reason, an older build must not overwrite a newer one, and that reason does not apply to a test run.
- **`.plot/panels/` stays out of `syncPathSet`.** Decided by the operator on 2026-11-21. The set has three readers: `planDataOnly` in slice 2, `settledPast`, which trusts the set past a green settled commit for every merge into `main` (`packages/fleet/src/shared/auto-merge.ts:314-329`), and the sync-PR gate, which decides what a sync pull request from the state ref may carry (`packages/board/src/server/entry/state-sync-gate.ts:46`). Adding the path would widen both trusts to cover a review product, to save a full run on 1 commit in 60. A panel-only push therefore runs every job, which is slower and not wrong.
- **The push guard stays in the `select` shell step and reads the domain's answer; `scripts/ci-job-map.jq` does not change.** The panel named two fixes for the map's second caller: the estate juror kept the jq unchanged and the guard in the shell, the testability juror gave the jq a defaulted `$event` argument. This plan takes the first. The decision whether a push is plan data only is `ciSelection.planDataOnly`, a domain rule with unit rows in `packages/domain/test/ci-selection.test.ts`; the shell step only routes on that field. An `$event` argument would put a second decision into a jq program that has no unit tests and two callers, and the reuse read at `ci.yml:398` would depend on a default it does not pass.

### Approach

**Slice 1, the main concurrency group:**

- **One group for a first `main` push attempt.** The group expression at `ci.yml:79` gains one arm: `(github.event_name == 'push' && github.run_attempt == '1') && 'main-push'`, placed before `github.run_id`. The `on.push` trigger lists only `main` (`ci.yml:6-7`), so the arm cannot match another branch. The `pull_request` arm, the release PR's own group and the `release-dispatch` group do not change.
- **`cancel-in-progress` becomes an expression:** `${{ github.event_name != 'push' }}`. A `pull_request` run and a dispatched run keep `true`. A `main` push run gets `false`: GitHub then keeps the running run and one pending run in the group, and a newer push cancels the pending one before it starts. The reason is the first decision above.
- **A re-run keeps its own group.** fleetd re-runs CI on `main` once per red episode: `rerunFailed` on the first red SHA (`packages/fleet/src/shared/repair-start.ts:137`) and `rerunAll` on the last green SHA (`packages/fleet/src/shared/revert-start.ts:257`). A re-run in `main-push` would replace the newest head's pending run, so the head would read `unknown` until the next push, or a later push would cancel the re-run, which `rerunSettledOf` reads as `pending` with no bound (`packages/domain/src/rules/repair-start.ts:26-37`). `github.run_attempt` is greater than 1 for a re-run, so the re-run falls through to `github.run_id`.
- **A waiting run reads `pending`, not `unknown`.** A run that waits in `ci-main-push` has created no jobs. The in-process connector adds a `CI/validate` entry only for a job that exists (`packages/domain/src/adapters/build/build-actions.ts:84-108`), and `declaredRuns` keeps only that job-form name (`default-branch.ts:60-64`). So today's fold of the head reads `unknown` (`default-branch.ts:97-103`) for as long as the run waits, which is up to one full run. `unknownHeadBound` (`packages/domain/src/workflows/merge.ts:200-210`) would then pass a person's `plot-ask.mjs merge` after `Checks wait` over a head that no run has tested, routinely and not only after a hand cancellation. The run-level row tells the two apart: `runsForShaOf` already returns the `CI` run with status `pending`, `queued` or `waiting` (`build-actions.ts:83`), and `declaredRuns` drops it. The refresh's head fold (`packages/fleet/src/shared/default-branch-refresh.ts:422-424`) therefore asks `candidateRunsOf` (below) and reads its `cancelled` answer as `unknown`. A head whose run waits reads `pending`, `unknownHeadBound` does not fire, and the merge refuses `default-branch-unsettled` until the run concludes. The newest head's run is cancelled only by a newer push, which moves the tip off the reading's head, so the bound still fires only for a run cancelled by hand, as today. The refresh derives `jobForm` as `world.build.system() === 'github-actions'`, the test `registryd-main.ts:4088` applies. `declaredRuns` keeps feeding `timing.observe` and `failingRunsOf`, and the ancestor walk (`settleBehindHead`, `default-branch-refresh.ts:225-249`) keeps `foldRuns(declaredRuns(...))`, since `ancestorStep` passes over `pending` and `unknown` alike (`default-branch.ts:218-221`).
- **What a cancelled run reads as, checked on origin/main.** Four runs cancelled by hand on 2026-11-21 (44891968350, 44887332410, 44883780985, 44880603205) show the job `validate` as `cancelled` with 0 steps on three, and as `success` where it had already concluded. A run cancelled while pending creates no jobs. The declared check is `CI/validate` (`CLAUDE.md` `Default branch checks`), and a job-form name matches only the job entry (`packages/domain/src/rules/default-branch.ts:46-64`). So a cancelled run gives either a `cancelled` entry or no entry:
  - **The reading.** `foldRuns` reads `cancelled` and an empty list as `unknown`, never `red` (`default-branch.ts:97-103`). `advanceSettled` moves only on `red` or `green` (`default-branch.ts:129-134`), so the reading's head stays `unknown` and its settled part stays. The ancestor walk passes over an `unknown` commit as `older` and settles on the newest concluded commit, which is the one whose run ran. No reading holds without end: the newest head's run is never replaced by an older one, so it concludes. No change beyond the waiting-run fold above.
  - **The repair record at the change to red.** It is written on a green-to-red change of the settled part (`default-branch-refresh.ts:437-440`): `lastGreenSha` is the carried green settled commit, `firstRedSha` the new red settled commit. Both are commits whose runs concluded, never a cancelled one, so `bug/main-repair-<12 hex of lastGreenSha>` names a tested commit. No change.
  - **`plot-ask.mjs merge` and fleetd's merge arm.** Both read the same reading. `plot-ask.mjs merge` refuses `default-branch-unsettled` while the tip is not the settled commit and `settledPast` does not cover it (`merge.ts:384-392`); fleetd's merge arm holds the PR as `merge-in-flight` in the same case (`slice-pr-next.ts:480-489`). A cancelled run changes neither. The waiting-run fold above keeps `unknownHeadBound` from passing a waiting head.
  - **The revert arm. This one holds without end, and the slice changes it.** The candidates are the first-parent commits of `lastGreenSha..firstRedSha` (`packages/domain/src/rules/repair.ts:6-17`), and each candidate's runs are folded with `foldRuns` (`packages/fleet/src/shared/revert-start-world.ts:138`). `redMainPicker` answers `hold` for the oldest candidate that is not green and not red (`repair.ts:109-121`), and `redMainStep` then answers `hold` past the repair bound (`repair.ts:261`). A candidate whose run was cancelled never concludes, so the episode stays at `hold` until a green settles, fleetd starts no revert and no further repair, and the episode never reaches `exhausted`, where a person's `plot-ask.mjs repair-pr` is accepted. Today a run cancelled by hand does the same; with this slice every replaced pending run does. `redMainStep` answers `hold` while the head is not the settled commit (`repair.ts:259`), before it reads the picker, so the picker change takes effect only once the head is settled red.
- **The rule change.** `candidateRunsOf(runs, checks, jobForm)` in `packages/domain/src/rules/default-branch.ts` answers `green`, `red`, `pending`, `unknown` or `cancelled`. It takes every run of the commit, not `declaredRuns(...)`, and folds the declared entries with `foldRuns`. Where that fold is `unknown`, it answers `cancelled` where every declared entry concluded `cancelled`. Where no declared entry exists, it reads the runs of the workflow each declared name points into (`workflowOfCheck`): it answers `pending` where one of them reads a pending word, and `cancelled` where every one of them concluded `cancelled`. Every other shape stays `unknown`.
- **The picker skips a cancelled bookkeeping commit.** `RedMainCandidate` (`repair.ts:24-36`) gains `runs: … | 'cancelled'` and `plotDataOnly: boolean`, which is true where the commit changes at least one file and `syncPathVerdict(files, syncPathSet(keys))` is `ok` (`packages/domain/src/rules/state-sync.ts:59-62,84-88`). `revertWorldOf` already reads the commit's files (`revert-start-world.ts:131`); it also reads `Active index` and `Delivered index` beside the two directories it reads (`revert-start-world.ts:76-83`), with `DEFAULT_RELEASE_DIR` as `plotPathSetOf` uses it (`auto-merge.ts:314-329`), and no generated bundle. `redMainPicker` skips a candidate that reads `cancelled` with `plotDataOnly` true, as it skips a green one. The tick's read loop continues past such a candidate too (`revert-start.ts:202` breaks today on the first non-green one). This is the trust `settledPast` already gives the same set past a green settled commit. The cost: a bookkeeping commit can itself turn `validate` red, for example through `scripts/check-plan-headings.sh`. Where its run was cancelled, the picker names the next red merge, fleetd reverts a PR that did not break `main`, and after the revert merges with `main` still red, `redMainStep` answers `exhausted` (`repair.ts:254`). The Changelog states this.
- **A cancelled code commit ends the episode and is named.** For the oldest non-green candidate that reads `cancelled` with `plotDataOnly` false, `redMainPicker` answers `{ cancelled: <sha> }`: its change is in every later candidate, so no later PR may be named in its place. `redMainStep` answers `exhausted` for that answer past the bound, as it does for `unknown` (`repair.ts:263`). The tick's `exhaust` (`revert-start.ts:122-126`) writes the sha into the record and names it in the notification: "no single breaking merge could be named: `<12 hex>` has a cancelled CI run". `RepairRecordSchema` (`packages/domain/src/entities/repair-record.ts:78`) gains `cancelledSha: z.string().optional()`, and `REPAIR_RECORD_VERSION` stays 1. The schema is `.strict()`, so a reader built before this slice reads a record that carries the field as no record (`repair-record.test.ts` "reads an unknown field as no record"); fleetd and `plot-ask.mjs` must run from one build. The field is written only at `exhausted`.
- **`jobForm` reaches the revert world.** `RevertWorldOptions` (`revert-start-world.ts:31-47`) gains `jobForm: boolean`. `registryd-main.ts:4141` sets it to `ci.system() === 'github-actions'`, as `:4088` derives it, and `revert-start-world.ts:138` calls `candidateRunsOf(runs.value, options.checks, options.jobForm)`.
- **The comment.** The block at `ci.yml:57-77` names the new rule: one group for a first `main` push attempt with `cancel-in-progress: false`, the measured push gap, and why a re-run keeps its own group.
- **The gate ranges.** On a push, `check-shell-lines.sh push` (`ci.yml:1856-1864`) and `check-decision-count.sh push` (`ci.yml:1866-1874`) measure `github.event.before..HEAD`. Once a pending run is cancelled, the range of the cancelled head is never measured. Push mode reports and does not refuse, so slice 1 loses a warning and not a gate. Slice 1 accepts that loss; slice 2 closes it.

**Slice 2, the bookkeeping push:**

- **A push needs a CI run that concludes, so the workflow is not skipped.** fleetd and `plot-ask.mjs merge` need a settled reading of the tip. A head with no run reads `unknown`; `advanceSettled` keeps the old settled part (`default-branch.ts:129-134`); the unknown-head bound passes only a person after `Checks wait`, never fleetd (`merge.ts:200-210`, `CLAUDE.md` "One hold reads a non-terminal answer"). A `paths-ignore` on the push trigger would therefore stop every fleetd merge after each bookkeeping push. `settledPast` covers at most 5 such commits past a green settled commit, and a code merge in between ends that cover. This slice keeps a run on every push and makes it short.
- **The narrowed run does not keep pace with the push rate.** A narrowed run took 9.3 to 17.3 min. At the median push gap of 1.9 min, 5 to 9 pushes arrive per run, at or above the cover of 5. So the 5-commit `settledPast` cover may not hold: fleetd's merge arm still holds as `merge-in-flight` and a person's merge still refuses `default-branch-unsettled` for part of every run. The plan accepts that shorter hold. It does not promise no hold: today's hold lasted 3 h, and with both slices it lasts at most about two narrowed runs while only bookkeeping lands.
- **The push asks the same rule as a pull request.** The install, build and ask steps of `select` (`ci.yml:174-208`) also run on `push`. On a push, the changed paths are `git diff --name-only --no-renames <base> HEAD`. Not `HEAD^1`, and not `github.event.before`: with slice 1, an older head's pending run is cancelled, so the newest head's run must cover every commit since the last head CI proved. A narrowed run's base was itself green, so the chain of proven heads holds.
- **A domain rule chooses the base.** `pushSelectionBase({ greenHead, firstParent })` in `packages/domain/src/rules/push-selection-base.ts` answers `{ base: <sha> }` or `{ every: 'api-failed' | 'no-green-run' | 'not-on-line' }`. `greenHead` is the head of the newest `CI` push run on `main` that concluded `success`, `null` where the call failed and `''` where no such run exists. `firstParent` is `git rev-list --first-parent -n 50 HEAD`, `ANCESTOR_WALK_DEPTH` commits. The base must equal one entry of that list, tested by equality and not by an ancestry test; a base off the line or past 50 commits answers `not-on-line`. This is the split `ciReuse` already uses (`packages/domain/src/rules/ci-reuse.ts:205`, called from `ci.yml:419-432` through `plot-ci-reuse.mjs`): the shell collects the values, and the bundle decides. The shell step reads `gh api repos/{repo}/actions/workflows/ci.yml/runs?branch=main&event=push&status=success&per_page=1` (the job already holds `actions: read`, `ci.yml:123-125`) and the `rev-list`, and calls `plot-local-checks.mjs --push-base <green.json> <first-parent.txt>`, a new mode of the entry slice 2 already changes, which prints `base=<sha>` or `every=<reason>`. The push checkout fetches 51 commits of first-parent history (`fetch-depth: 51` on push, `ci.yml:172`). The `plot-local-checks.mjs` row in `skills/plot/scripts/README.md` names the mode.
- **The rule answers whether the range is bookkeeping.** `ciSelection` (`packages/domain/src/rules/local-checks.ts:453-485`) gains `planDataOnly: boolean`: true where at least one non-generated changed path exists and `syncPathVerdict(changed, syncPathSet(keys))` is `ok` (`state-sync.ts:59-62,84-88`). That is the set `settledPast` already trusts past a green settled commit (`auto-merge.ts:314-329`): `Plan directory`, `Active index`, `Delivered index`, `Sprint directory`, `docs/releases/`, `.plot/briefs/` and `.plot/hold`, without the generated bundles. The entry (`packages/board/src/server/entry/local-checks.ts:250-295`) reads the keys it does not read yet and passes them. The 53 measured commits lie in this set; the brief's list (`docs/plans/**`, `docs/sprints/**`, `docs/plans/active/**`, `docs/plans/delivered/**`) misses `.plot/briefs/`, which all 13 brief bookings write. `ciSelection` already treats a `.plot/panels/` path as plan data for a pull request (`packages/domain/test/ci-selection.test.ts:160-167`), and `planDataOnly` answers false for it; the two meanings stay visible in the rows below.
- **The shell routes on the answer, and the map does not change.** The guard at `ci.yml:224` becomes three cases: a `pull_request` run maps as today; a `push` run maps as a pull request's only where the base rule answered a base and `selection.json` carries `planDataOnly: true`, and otherwise selects every job; every other event selects every job. `scripts/ci-job-map.jq` stays as it is, so its second caller, the reuse read at `ci.yml:398`, keeps working unchanged. A plan-only answer maps to `corpus` alone (`ci-selection-jobs.test.mjs` "a plan-only change selects the corpus tier and no other job"), so such a push runs `select`, `gates`, `checks`, `corpus` and `validate`: 5 of 11 jobs before the Plan paths slice of `docs/plans/2026-11-21-reports-name-their-cause-and-ci-selects-their-tests.md` (#3149), and 6 of 11 with `helper-contracts` after it. A push with any path outside the set, a failed install, build or ask, or an `every=` answer from the base rule still selects every job, as `ci.yml:224` does today, and the step summary names the reason.

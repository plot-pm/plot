# Main CI runs only for the newest head

> A push to `main` joins one CI concurrency group, so at most one run for an older head finishes and the newest head runs next, and a push whose changes since the last green head are only plan, sprint, index and brief files runs the jobs a plan-only pull request runs, not every suite.

## Status

- **State:** Draft
- **Type:** infra
- **Review:** pr
- **Impl:** own branches

## Changelog

- A merge into `main` no longer waits behind a queue of CI runs for older `main` heads. CI runs for one `main` head at a time; a newer push replaces a run that has not started yet, so the newest head runs next.
- A push to `main` whose changes since the last green `main` run are only plan, sprint, index and brief files runs only the gates, `checks`, `corpus` and `validate`, the jobs a plan-only pull request runs, and not every suite.
- fleetd's revert arm no longer waits without end on a commit whose CI run was cancelled. It ends the episode at `exhausted`, and a person's repair PR can then merge through `plot-ask.mjs repair-pr`.

## Motivation

Measured 2026-11-21 between 06:00 and 11:00 UTC on `plot-pm/plot`:

- The Actions API lists 307 runs in the window: 180 `push` runs on `main` (60 pushes, each starting `CI`, `Release` and `Build bundles`) and 85 `pull_request` runs. The organization is on GitHub's free plan (`gh api orgs/plot-pm` reads `plan.name: free`): 20 concurrent Linux jobs and 5 macOS jobs, shared by both kinds of run.
- Of the 60 first-parent commits on `main`, 46 carry a `plot:` subject that Plot writes itself (13 `plot: book the brief and plan start for …`, 10 `plot: approve …`, `plot: record PR #… for …`, `plot: deliver …`, sprint edits, 2 `plot: build the board artifact`). 9 more are plan-PR merges. 53 of the 60 change only paths under `docs/plans/`, `docs/sprints/` and `.plot/briefs/` (`git log --since=2026-11-21T06:00:00Z --until=2026-11-21T11:00:00Z --first-parent origin/main --name-only`). The other 7 are 4 code PRs (#3596, #3603, #3607, #3615), 2 bundle builds and 1 `challenge-the-plan` round that writes `.plot/panels/`.
- Every `main` push runs every job. The `select` job maps a non-`pull_request` event to every job (`.github/workflows/ci.yml:224`), and its install, build and ask steps run only on `pull_request` (`ci.yml:176-207`). A `main` CI run has 11 jobs.
- Push runs on `main` never cancel each other. The concurrency group for a push is `github.run_id` (`ci.yml:78-80`), and `test/reconcile/release-pr-ci.test.mjs` holds that ("ci.yml gives every main push run its own group"). 22 `main` CI runs were queued at once; 21 were cancelled by hand at 10:35 UTC.
- The 40 newest green `main` CI runs took a median 148.5 min from start to end, at least 19.9 min. The median gap between two pushes was 1.9 min, and only 2 gaps reached 20 min.
- fleetd's default-branch reading stayed settled on `b21961602f02` (`plot: move story delivery-tab-reads-at-a-glance to done`, 05:55 UTC) from about 08:28 to 11:30. A merge into `main` needs the reading's settled commit to be the tip, or a green settled commit followed by at most `ANCESTOR_ASKS_MAX` (5) commits that change only Plot's paths (`packages/domain/src/workflows/merge.ts:380-393`, `packages/domain/src/rules/slice-pr-next.ts:476-490`, `packages/domain/src/rules/settled-past.ts:44-50`). Every merge into `main` refused `default-branch-unsettled` meanwhile; PR #3619 and others waited 3 h with green CI.

`.github/workflows/build-bundles.yml:16-18` already puts every `main` push in one group with `cancel-in-progress: true`, because an older build must not overwrite a newer one.

## Design

### Approach

**Slice 1, the main concurrency group:**

- **One group for a first `main` push attempt.** The group expression at `ci.yml:79` gains one arm: `(github.event_name == 'push' && github.run_attempt == '1') && 'main-push'`, placed before `github.run_id`. The `on.push` trigger lists only `main` (`ci.yml:6-7`), so the arm cannot match another branch. The `pull_request` arm, the release PR's own group and the `release-dispatch` group do not change.
- **`cancel-in-progress` becomes an expression:** `${{ github.event_name != 'push' }}`. A `pull_request` run and a dispatched run keep `true`. A `main` push run gets `false`: GitHub then keeps the running run and one pending run in the group, and a newer push cancels the pending one before it starts. The reason is the measurement above. With `true`, every push cancels the run in progress; with a median push gap of 1.9 min and a green run of at least 19.9 min, a head's run would conclude only in a quiet gap of 20 min, which occurred twice in 5 h. The reading would stay settled on an old commit for longer than today. With `false`, a head concludes at least once per run length, and the newest head runs next. `[question-cancel-in-progress]` asks a person to confirm this against the brief's `true`.
- **A re-run keeps its own group.** fleetd re-runs CI on `main` once per red episode: `rerunFailed` on the first red SHA (`packages/fleet/src/shared/repair-start.ts:137`) and `rerunAll` on the last green SHA (`packages/fleet/src/shared/revert-start.ts:257`). A re-run in `main-push` would replace the newest head's pending run, so the head would read `unknown` until the next push, or a later push would cancel the re-run, which `rerunSettledOf` reads as `pending` with no bound (`packages/domain/src/rules/repair-start.ts:26-37`). `github.run_attempt` is greater than 1 for a re-run, so the re-run falls through to `github.run_id`. The builder records in the PR that a re-run's group reads `ci-<run_id>` on the first re-run on `main`.
- **What a cancelled run reads as, checked on origin/main.** Four runs cancelled by hand on 2026-11-21 (44891968350, 44887332410, 44883780985, 44880603205) show the job `validate` as `cancelled` with 0 steps on three, and as `success` where it had already concluded. A run cancelled while pending creates no jobs. The declared check is `CI/validate` (`CLAUDE.md` `Default branch checks`), and a job-form name matches only the job entry (`packages/domain/src/rules/default-branch.ts:46-64`). So a cancelled run gives either a `cancelled` entry or no entry:
  - **The reading.** `foldRuns` reads `cancelled` and an empty list as `unknown`, never `red` (`default-branch.ts:97-103`). `advanceSettled` moves only on `red` or `green` (`default-branch.ts:129-134`), so the reading's head stays `unknown` and its settled part stays. The ancestor walk passes over an `unknown` commit as `older` (`ancestorStep`, `default-branch.ts:218-221`; `settleBehindHead`, `packages/fleet/src/shared/default-branch-refresh.ts:225-249`) and settles on the newest concluded commit, which is the one whose run ran. No reading holds without end: the newest head's run is never replaced by an older one, so it concludes. No change.
  - **The repair record.** It is written on a green-to-red change of the settled part (`default-branch-refresh.ts:303-304`): `lastGreenSha` is the carried green settled commit, `firstRedSha` the new red settled commit. Both are commits whose runs concluded, never a cancelled one, so `bug/main-repair-<12 hex of lastGreenSha>` names a tested commit. No change.
  - **`plot-ask.mjs merge` and fleetd's merge arm.** Both read the same reading and refuse `default-branch-unsettled` while the tip is not the settled commit and `settledPast` does not cover it (`merge.ts:380-393`, `slice-pr-next.ts:476-490`). A cancelled run changes neither. The person's unknown-head bound (`unknownHeadBound`, `merge.ts:200`) applies only where the head reads `unknown`; with this slice a head's run is pending until it concludes, so the bound fires only for a run cancelled by hand, as today. No change.
  - **The revert arm. This one holds without end, and the slice changes it.** The candidates are the first-parent commits of `lastGreenSha..firstRedSha` (`packages/domain/src/rules/repair.ts:6-17`), and each candidate's runs are folded with `foldRuns` (`packages/fleet/src/shared/revert-start-world.ts:138`). `redMainPicker` answers `hold` for the oldest candidate that is not green and not red (`repair.ts:109-121`), and `redMainStep` then answers `hold` past the repair bound (`repair.ts:261`). A candidate whose run was cancelled never concludes, so the episode stays at `hold` until a green settles, fleetd starts no revert and no further repair, and the episode never reaches `exhausted`, where a person's `plot-ask.mjs repair-pr` is accepted. Today a run cancelled by hand does the same; with this slice every replaced pending run does.
- **The rule change.** `candidateRunsOf(runs, checks, jobForm)` in `packages/domain/src/rules/default-branch.ts` answers `green`, `red`, `pending`, `unknown` or `cancelled`. It folds the declared entries with `foldRuns`. It answers `cancelled` where that fold is `unknown` and either every declared entry concluded `cancelled`, or no declared entry exists and every run of the workflow each declared name points into (`workflowOfCheck`) concluded `cancelled`. `RedMainCandidate.runs` (`repair.ts:33`) gains `cancelled`, and `revert-start-world.ts:138` calls `candidateRunsOf`. `redMainPicker` answers `unknown` for an oldest non-green candidate that reads `cancelled`: its change is in every later candidate, so no later PR may be named in its place, and `unknown` never reverts. `redMainStep` already answers `exhausted` for a picker `unknown` past the bound (`repair.ts:263`).
- **The comment.** The block at `ci.yml:56-77` names the new rule: one group for a first `main` push attempt with `cancel-in-progress: false`, the measured push gap, and why a re-run keeps its own group.
- **Tests:**
  - `test/reconcile/release-pr-ci.test.mjs`: "ci.yml gives every main push run its own group" becomes "two first-attempt main push runs share `ci-main-push`"; a new row "a main push re-run gets its own group" (`github.run_attempt` `'2'`); "ci.yml cancels a superseded run in its group" becomes a row that evaluates the `cancel-in-progress` expression: `true` for `pull_request` and `workflow_dispatch`, `false` for `push`. `PUSH_CTX`, `PR_CTX` and `DISPATCH_CTX` gain `github.run_attempt`. The release PR, dispatch and "no concurrency group in ci.yml is keyed on the ref" rows stay.
  - `packages/domain/test/default-branch.test.ts`: `foldRuns` reads a `cancelled` `CI/validate` entry as `unknown`; `advanceSettled` keeps the settled part for it; `candidateRunsOf` answers `cancelled` for all-cancelled declared entries, `cancelled` for no declared entry and a cancelled `CI` run, `unknown` for no runs at all, `pending` for one cancelled and one queued entry, and `red` for one cancelled and one failed entry.
  - `packages/domain/test/repair.test.ts`: `redMainPicker` answers `unknown` where the oldest non-green candidate reads `cancelled`, `hold` where it reads `pending` or `unknown`, and skips a green candidate before a `cancelled` one; `redMainStep` past the bound with that answer is `exhausted`.
  - `packages/fleet/test/unit/revert-start.test.ts`: a candidate whose `CI/validate` job concluded `cancelled` reaches the picker as `cancelled`.
  - A changeset for `plot` names the plan.

**Slice 2, the bookkeeping push:**

- **A push needs a CI run that concludes, so the workflow is not skipped.** fleetd and `plot-ask.mjs merge` need a settled reading of the tip. A head with no run reads `unknown`; `advanceSettled` keeps the old settled part (`default-branch.ts:129-134`); the unknown-head bound passes only a person after `Checks wait`, never fleetd (`merge.ts:200`, `CLAUDE.md` "One hold reads a non-terminal answer"). A `paths-ignore` on the push trigger would therefore stop every fleetd merge after each bookkeeping push. `settledPast` covers at most 5 such commits past a green settled commit, and a code merge in between ends that cover. This slice keeps a run on every push and makes it short.
- **The push asks the same rule as a pull request.** The install, build and ask steps of `select` (`ci.yml:176-207`) also run on `push`. On a push, the changed paths are `git diff --name-only --no-renames <base> HEAD`, where `<base>` is the head of the newest `CI` push run on `main` that concluded `success`, read through `gh api repos/{repo}/actions/workflows/ci.yml/runs?branch=main&event=push&status=success&per_page=1` (the job already holds `actions: read`, `ci.yml:124-126`). The base must be on `HEAD`'s first-parent line within `ANCESTOR_WALK_DEPTH` (50) commits, tested by equality over `git rev-list --first-parent -n 50 HEAD` and not by an ancestry test, so the push checkout fetches 51 commits of first-parent history. Not `HEAD^1`, and not `github.event.before`: with slice 1, an older head's pending run is cancelled, so the newest head's run must cover every commit since the last head CI proved. A narrowed run's base was itself green, so the chain of proven heads holds.
- **The rule answers whether the range is bookkeeping.** `ciSelection` (`packages/domain/src/rules/local-checks.ts:453-485`) gains `planDataOnly: boolean`: true where at least one non-generated changed path exists and `syncPathVerdict(changed, syncPathSet(keys))` is `ok` (`packages/domain/src/rules/state-sync.ts:59-62,82-86`). That is the set `settledPast` already trusts past a green settled commit (`packages/fleet/src/shared/auto-merge.ts:314-329`): `Plan directory`, `Active index`, `Delivered index`, `Sprint directory`, `docs/releases/`, `.plot/briefs/` and `.plot/hold`, without the generated bundles. The entry (`packages/board/src/server/entry/local-checks.ts:250-295`) reads the five keys it does not read yet and passes them. The 53 measured commits lie in this set; the brief's list (`docs/plans/**`, `docs/sprints/**`, `docs/plans/active/**`, `docs/plans/delivered/**`) misses `.plot/briefs/`, which all 13 brief bookings write.
- **The map applies the selection to a bookkeeping push only.** `scripts/ci-job-map.jq` takes `--arg event`. For `push` it answers every job unless the answer carries `planDataOnly: true`; then it maps the answer as it maps a pull request's. Today a plan-only answer maps to `corpus` alone (`ci-selection-jobs.test.mjs` "a plan-only change selects the corpus tier and no other job"), so such a push runs `select`, `gates`, `checks`, `corpus` and `validate`: 5 of 11 jobs, with no `helper-contracts`, `board-integration`, census, macOS or e2e job. A push with any path outside the set, a failed install, build or ask, an unread base (API failure, no green run, a base off the line or past 50 commits) still selects every job, as `ci.yml:224` does today, and the step summary names the reason. A dispatched run keeps every job.
- **How the reading treats such a head.** `validate` passes a job that the selection named `false` and that was skipped (`ci.yml:2935-2950`), so the run concludes `success` and its `CI/validate` entry reads `success`. `foldRuns` reads it `green`, `advanceSettled` moves the settled part to the head, and `default-branch-unsettled` lifts for a tip that equals it. No domain reading changes.
- **The comment.** `ci.yml:83-114` ("A push to `main` and a dispatched run also select every job: the full run on `main` is the safety net") names the new exception and its base.
- **Tests:**
  - `packages/domain/test/local-checks.test.ts`: `planDataOnly` is true for `docs/plans/x.md` with `docs/plans/active/x.md`, for `docs/sprints/s.md`, and for `.plot/briefs/b.md`; false for a `.plot/panels/` path, for one code path beside plan files, for a path with `..` segments, for an empty change, and for a change of generated bundles only.
  - `test/reconcile/ci-selection-jobs.test.mjs`: "a push, a dispatch and a failed ask select every job" splits into: a dispatch and a failed ask select every job; a push whose answer carries `planDataOnly: true` maps as a pull request does (`corpus` true, every other job false); a push whose answer carries `planDataOnly: false` or no field selects every job. New rows: on `push`, `select` runs its install, build and ask steps; the push diff reads its base from the newest green push run; an API failure, no green run, or a base not in the first 50 first-parent commits selects every job and names the reason in the summary; `validate` passes such a run with `corpus` success and the tier-2 jobs skipped.
  - A changeset for `plot` names the plan.

### Open Questions

- [ ] `[question-cancel-in-progress]` Slice 1 sets `cancel-in-progress: false` for the `main` push group, not the `true` the request named. With `true`, a push every 1.9 min (median) cancels a run that needs at least 19.9 min, so a head concludes only in a 20-min quiet gap (2 in 5 h). With `false`, one run finishes and the newest pending head runs next. Confirm `false`, or name the push rate at which `true` is wanted.

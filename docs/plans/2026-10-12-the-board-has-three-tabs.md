# The board has three tabs

> The board's tabs Stories, Plans and Agents become Discovery, Planning and Delivery, the old `?tab=` values redirect, the Planning tab shows plans from Design to Testing with a *Show released* checkbox, and the Delivery tab selects the Active sprints in one step, shows a plan-level verification row, and filters its tickets by assignee on the server.

## Design

### Approach

The design spec is [DESIGN-phases.md](../stories/plot-works-in-five-phases/DESIGN-phases.md) §5.

**The tab is a domain answer.** A new rule `boardTabOf(param)` in `packages/domain/src/rules/board-tab.ts` returns the tab and, for an old value, the new value to redirect to: `stories` to `discovery`, `plans` and `board` to `planning`, `agents` to `delivery`. An absent or unknown value answers `planning`, as `plans` is the default today. `App.tsx` calls it in place of `parseTab` and replaces the URL silently, as `parseTab` does today. Every `App.tsx` line the grep above names takes the new value, and `revealBranch` (`:683-685`) writes `?tab=delivery`. The tab names are fixed (D6). The Discovery tab renders today's `StoriesTab` until `tickets-and-stories-have-lanes` rebuilds it.

**The empty-Discovery send.** This plan owns `App.tsx:985-996`, because its lines `:989` and `:991` are among the 31 the rename changes and the lanes plan does not name it. The rename slice keeps the send with the new values: an empty Discovery tab opens Planning. The lanes slice `feature/tickets-and-stories-have-lanes` removes it, because a Discovery tab with ticket lanes is not empty when it holds no story; the rename slice writes that removal into the lanes plan's slice line (`tickets-and-stories-have-lanes.md:273`).

**The Planning tab.** `PhaseColumn` gains `releasedOnly: boolean`, true for a phase whose only plan state is `released`; `phaseColumns` sets it beside `checklist`. `ColumnSchema` gains `releasedOnly: z.boolean().default(false)`, and `board.ts:2336` passes it through the existing spread. `planningColumns(columns, showReleased)` in `workflow-phases.ts` takes any list of `{ releasedOnly?: boolean }` and drops a column whose `releasedOnly` is true unless `showReleased` is on. `Board.tsx` calls it over the payload's `board.columns` before `:212`, so `boardGridColumns` counts the shown columns; *Show released* is per viewer and Released plans already ride the payload. With the default map it answers Design, Development and Testing, and Released with the checkbox on. A custom map (D12, D26) that puts `plan:released` in a phase with another plan state keeps that column whole, so the checkbox never hides a Delivered plan. The sprint filter, the story filter, *Story lanes* and *Only my work* stay. *Show released* is off by default and is kept in the URL (`?released=1`), as `DESIGN-phases.md` §5 states. `?released=1` belongs to the Planning tab alone: the Discovery tab's toggle uses `?archived=1`, because `App.tsx:633-638` keeps every parameter on a tab switch.

**Active sprint (D32).** A button over the existing multiselect, not a second rule. `fleet.sprints` holds only Active sprints, so "the active sprint's rows" is the multiselect with every option selected, and `slugPassesSprintFilter` passes a row in any selected sprint: the union story Open Point 12 asks for. `activeSprintButton(sprints)` beside `sanitizeSelection` in `packages/board/src/app/lib/filters.ts` answers `{ selection, disabled, sentence }`: every slug of `fleet.sprints`, and `disabled` with *No sprint is Active.* for none. The button sets the selection through the existing `setSprintFilter` (`AgentList.tsx:527`); the rows, the exempt mark and the hidden count come from the existing join. Moving that join into the domain changes no behaviour and is outside this plan.

**The plan-level row.** This plan owns one row for a run the fleet makes on a plan rather than on a branch: a plan, a sentence, no branch. Its shape is `PlanLevelRow = { kind: 'verify' | 'spec'; plan: string; reason: string; log: string | null; restart: string | null; stopped: boolean; halted: boolean }` in `packages/board/src/app/lib/agent-rows/plan-level-row.ts`, and `PlanLevelRowView` renders one through `tupleFromPlan` and `TupleRowView`, as `DraftPlanRowView` does. The payload carries no plan file, so the view takes `planFile` from the `path` of the board payload's card whose `slug` is `plan`, as `cardForPlanFile` (`App.tsx:700-709`) matches cards by `path`, and renders the slug with no plan link when no card holds it. Every field comes from the payload; the board computes no command and no reason.

- **Sections.** `AgentList.tsx:1123` renders the *Waiting on you* rows beside `drafts` for the `waiting-on-you` key, and the *Working* rows for the `working` key; the counts at `:1087-1091` add each section's rows.
- **Verification.** `verificationRows(verification)` answers `{ working, waiting, haltedLine }`. `waiting` holds one `kind: 'verify'` row per `verification.rows` row, with `plan` from `slug`, `reason`, `log`, `restart` and `stopped` as given and `halted` from `fleetHalted`. `working` holds one row per `verification.running` slug, with the reason *verification running* and no log and no restart. `haltedLine` is *The fleet starts no verify run until a person restarts one.* when `verification.halted` is true and no `waiting` row carries `halted`, because the row's `reason` already says so otherwise; it is a sentence above the section rows, outside `tupleFromPlan`, and no count includes it. `verification: null` answers no row and no line.
- **The sibling.** `the-fleet-writes-the-design` renders its spec-run rows through the same `PlanLevelRow` and `PlanLevelRowView`, with `kind: 'spec'` and `restart` `plot-design.mjs restart <slug>`; its `specRow` (`the-fleet-writes-the-design.md:54`) writes `halted` from the store's halt.
- The slice closes #1640's *The board row* item (H7).

**The assignee.** `Issue` gains `assignees: string[]`, the tracker's own logins or accounts, `[]` where the tracker states none. A list, because a GitHub issue carries several assignees; a ticket is the reader's when any element resolves to the reader. It is a read, under the reasoning that admitted `status` and `statusCategory` (`issue.ts:25-31`): Plot reads it and never writes it, and the status write's refusal to widen (`ports/tracker.ts:31-41`) does not change. The `plot-host.sh issue-list` arms read it: the GitHub arm adds `assignees` to its `--json` list (`:4732`) and `[.assignees[].login]` to its `jq` projection (`:4734-4736`); the Jira arm adds `assignee` to `fields=` (`:4696`) and projects its `emailAddress`, or its `accountId` where the instance hides the email. The Bitbucket arm is unchanged: `bb issue list` prints no assignee (`plot-host.sh:2132`). Each key goes on an existing line, so the slice adds no net shell lines (`scripts/check-shell-lines.sh pr`).

**The assignee's two read paths.** After the spike `feature/the-fleet-indexes-issues`, the board reads issues on two paths, and the slice carries `assignees` on both:

- **Under a fleet.** `issueOf` (`adapters/tracker/tracker-shell.ts:46`), which `trackerReads` (`:120`) calls, reads the key; the fold's `rowOf` (`packages/fleet/src/shared/issue-refresh.ts:46`, spike) writes it into the index row when it is not empty; `IssueIndexRowSchema` declares `assignees: z.array(z.string()).optional()`, under the spike's *no `.default()`* contract; and `readIssuesFromStore` maps an absent key to `[]` in `IssueRow`.
- **With no fleet.** `refreshIssues`' projection (`fleet.ts:1536-1561`) reads the key from `issue-list` and maps an absent key to `[]`.

`ISSUE_INDEX_VERSION` is not raised. A new reader decodes an old row with no `assignees` as unassigned, and each fleet pass rewrites the index. `.strict()` makes a board built before the slice refuse a row that carries the key, so the board and `plot-fleetd` restart together on the upgrade (Changelog). `IssueRowSchema` gains `assignees` with its doc.

**The ticket owner.** `OwnedRow` gains `{ kind: 'ticket'; assignees: string[]; source: TicketSource | null }`, and `ownership` answers it through `ticketOwnership`. `TicketSource` is `'github' | 'bitbucket' | 'jira'`, and `ticketSourceOf(source, backend)` derives it from the domain's `IssueSource` (`rules/issue-source.ts:27-30`): `tracker` with scheme `jira` is `jira`, `tracker` with scheme `github-issues` (`adapters/tracker/tracker-listers.ts:14-17`) is `github`, and `git-host` takes the resolved backend from `resolveBackend` (`fleet.ts:1633`), never `entry.backend ?? 'github'`. A `git-host` source with a backend that is unresolved or outside `github` and `bitbucket` answers `null`; `nobody` reads no tickets. A `null` source answers `unknown` for every ticket. No parallel resolver exists beside `prOwnership` and `planOwnership`.

- **GitHub and Bitbucket (D33).** Each assignee is a host login, as a PR author is, so the arm compares it to the reader's host login through `resolvePerson` (`entities/person.ts:43`) as `prOwnership` (`ownership.ts:67-73`) does: `mine` when any assignee resolves to the reader, `theirs` when every assignee resolves to another person. An undeclared login resolves to itself, so a GitHub reader owns their own tickets with no `People` entry. The reader is unmatched only with no known login.
- **Jira.** An assignee is a Jira email or account ID, which `People` names as a spelling `jira:<value>` (D21; `parsePersonDirectory` at `person.ts:75`). `mine` when a `jira:` spelling of the reader's handle names any assignee, `theirs` when a `jira:` spelling of another handle names it, `unknown` when no handle declares it, as `planOwnership` (`ownership.ts:83-90`) treats an undeclared spelling.
- **An unassigned ticket.** An empty `assignees` answers `unknown`, as an empty PR author does. `isMine` keeps it, so *Only my work* shows an unassigned ticket and hides only a ticket assigned to somebody else. The inbox default is stricter, because D9 shows "only tickets assigned to the current user": it hides the unassigned ticket and counts it.

**Waiting on you is decided on the server.** The server holds the reader and every open row it read; the client holds 50 rows. So `waitingTickets(rows, inbox, reader, source, complete)` in `packages/domain/src/rules/waiting-tickets.ts` runs in both board issue reads, `refreshIssues` and `readIssuesFromStore`, after the planned filter (`fleet.ts:1579`) and before the cap, and answers `{ tickets, shown, hidden, complete, notice }`. The slice exports `identity` and `people` from `server-info.ts` (`:178`, `:205-216`), and the read builds the `Reader` from them, so no second identity read exists. The rows are every unplanned open row the read holds: the slice waits on `feature/the-index-holds-closed-issues`, from which both reads hold up to `ISSUE_INDEX_OPEN_LIMIT` (1000) open rows with `complete` (`tickets-and-stories-have-lanes.md:73`, `:108`). `inbox` is the unplanned rows of today's `assignee = currentUser()` read, or of `PLOT_JIRA_JQL` where an adopter sets it (`plot-host.sh:4684`): before `feature/the-lanes-read-the-whole-jira-project` it is absent and the open rows are that read; after it the index holds it as `inbox` (`tickets-and-stories-have-lanes.md:117`).

- **A matched reader** sees the union of the `inbox` rows and the open rows whose `ticketOwnership` is `mine`, without duplicates, newest first. So a Jira reader's ticket older than the 1000 newest open rows stays, because the `inbox` page of the same pass holds it. `shown` counts the union, `hidden` counts every other unplanned open row, and `tickets` is the union cut to `ISSUE_LIMIT` (50).
- **The sentences.** `hiddenSentence(hidden, complete)` and `shownSentence(n, total, complete)` beside `waitingTickets` write the text: *127 open tickets are not assigned to you — show every ticket.*, and *at least 997* where `complete` is false, both from `hidden` and never from the limit. *Show every ticket* renders `issues` with `waiting.tickets`, without duplicates, so a reader's own older ticket stays, and states *Showing 50 of 127 open tickets.* (`n` the rendered rows, `total` = `shown` + `hidden`, *at least* where not complete). So nothing is hidden silently (D22).
- **GitHub and Bitbucket, unmatched.** When the reader has no host login, the source is `bitbucket`, which states no assignee, or the source is `null`, the answer is every row, cut to 50, and a notice that names the reason and the count, for example *The board knows no host login for you — showing 50 of 127 open tickets.* A Bitbucket inbox never shows empty because its tickets carry no assignee, and a Bitbucket repository read before `resolveBackend` answers is never read as GitHub.
- **Jira, unmatched (D23).** When no `jira:` spelling names the reader's handle, the answer is the `inbox` rows, or the open rows where `inbox` is absent, with no notice and no count. So no Jira inbox widens at upgrade.
- **Jira, declared but matching nothing (D35).** When the reader's `jira:` spellings name no assignee of the `inbox` rows, or of the open rows where `inbox` is absent, and those rows are not empty, the answer is those rows, as for an unmatched reader, and a notice names the value Jira returns, for example *Jira names your tickets' assignee `5b10ac8d82e05b22cc7d4ef5`; `People` declares `jira:jan.wloka@quatico.com` for jwloka — add `jira:5b10ac8d82e05b22cc7d4ef5` to match.* The reader is not unmatched, and no host call is added.
- **The payload.** `FleetShape` gains `waiting: { tickets: IssueRow[]; shown: number; hidden: number; complete: boolean; notice: string | null; source: TicketSource | null }`, default `null`. `waiting` is `null` only when the read failed or the source is `nobody`, and the section then shows the existing `issueError` or `issueAbsence` sentence. `issues` keeps its meaning, the 50 newest unplanned open rows. The *show every ticket* control is component state, off on each load, as the sprint selection is. The client renders `waiting` and decides nothing; it keeps no branch for a server with no `waiting`, because the server serves the client it builds (`packages/board/package.json:49`).
- ***Only my work*** applies `ticketsForReader(tickets, reader, source, on)`, beside `rowsForReader` in `mine-filter.ts`, at `AgentList.tsx:659`. It runs `isMine` over the ticket arm. In the default view it changes nothing; with *show every ticket* on it hides the tickets assigned to somebody else and keeps the unassigned ones.
- **One owner for the Jira inbox choice.** `waitingTickets` chooses which rows *Waiting on you* shows on every source, the `inbox` rows included. `feature/the-lanes-read-the-whole-jira-project` writes the `inbox` rows into the index and passes them to the board's read, and chooses nothing; its project-wide read waits on this plan's last slice, so the drop of `assignee = currentUser()` lands only after the filter exists (`DESIGN-phases.md` §5 *Scope*).

**Every view state is a domain property.** The tab, the Planning columns, which tickets *Waiting on you* shows, how many it hides and why, the count sentences, and whose a ticket is come from `boardTabOf`, `planningColumns`, `waitingTickets`, `hiddenSentence`, `shownSentence`, `ticketSourceOf` and `ticketOwnership` in `@plot-pm/domain`, with unit tests. The *Active sprint* selection and its disabled state, the plan-level rows and the halted line, and the *Only my work* ticket filter come from the payload through `activeSprintButton`, `verificationRows` and `ticketsForReader`, board helpers with unit tests. The components render them.

### Cost

- **Host and tracker calls.** Zero new calls per scan: the assignee rides the existing `issue-list` reads, and the union and the D35 notice read the `inbox` and open rows the pass already holds. On GitHub the nested `assignees` connection keeps a 100-issue page at 1 GraphQL point (`rateLimit(dryRun:true)`, 2026-10-13).
- **Payload.** One login or email per assignee per ticket. `waiting` adds at most 50 rows to the 4 s `/api/fleet` poll (`App.tsx:33`) beside today's 50 `issues`, about 12 KB. The index grows by about 25 KB at 1000 rows. If the lanes projection copies `assignees`, each lanes row on the 30 s `/api/board` poll (`App.tsx:32`) grows by 15 bytes empty and about 25 bytes with one login: at most about 50 KB on 1000 open and 1000 closed rows, and about 2 KB on this repository's 127 rows. `releasedOnly` adds one boolean per column to `/api/board`; *Show released* adds nothing, because Released plans already ride it.
- **The index version.** None: `assignees` is optional in the row and each reader maps it to `[]`. The board and `plot-fleetd` restart together on the upgrade.
- **Server work.** `waitingTickets` runs once per issue read over at most 1000 open rows and 50 `inbox` rows in memory.
- **Fleet agents.** Six slices, built one after another, spend six fleet agents and six reviews.
- **The waits.** The assignee slice and *Waiting on you* wait on `feature/the-index-holds-closed-issues`, the fourth slice of `tickets-and-stories-have-lanes`, which D29 holds until the lanes spike's Acceptance holds in CI. The tabs, *Active sprint*, the plan-level row and the ticket owner wait on nothing outside this plan.
- **Shell.** The assignee slice adds no net shell lines. The rename slice edits two comments in `skills/plot/scripts/plot-fleet-scan.sh` (`:1883`, `:4152`) and adds no line; every other slice touches no shell.
- **Tests and docs of the rename.** 47 files under `packages/board/test` open the old `agents` value; they keep it and exercise the redirect. Three files click a tab button by its old label and change: `agents-tab.browser.test.ts`, `mine-filter.browser.test.ts`, `unreachable-overlay.browser.test.ts`. `grep -rlE "Agents tab|Plans tab|Stories tab|tab=(agents|plans|stories|board)"` over `skills`, `docs`, `README.md` and `packages/board/src`, outside `docs/plans` and `docs/stories`, names 24 files. The rename changes the 17 current ones: 16 under `packages/board/src` and `plot-fleet-scan.sh`. The 7 dated release lists and sprint files keep their words.
- **Browser tests.** Nine new cases in three existing files, each stubbing the payload with no new board server: *Show released* in `mock-board.browser.test.ts`; the tab redirect, the *Active sprint* click, the plan-level rows in both sections, the hidden-count sentence with *show every ticket* and the unmatched notice in `agents-tab.browser.test.ts`; *Only my work* over tickets in `mine-filter.browser.test.ts`.

# A refused start is retried and named

> A brief run reads the plan at the `origin/<main>` commit that asked for it, and fleetd asks once more when a brief run ends without a brief. A `--start` refusal names its own defect. The write probe and the worker loop name the prompt that a charter declares. A red PR gets one CI re-run per head before a fixer starts.

## Motivation

**A refused brief is never asked again (#3134).** `maybeAutoDispatch` skips every branch in `briefsAsked` (`packages/fleet/src/shared/auto-dispatch.ts:453`) and marks every started ask (`:470`). `outstandingAsks` (`packages/domain/src/rules/brief-budget.ts:34-46`) drops an asked branch only when its brief lands on `origin/<main>`, when it leaves the candidates, or when a usage-limit reset passes. A brief run that ends without a brief therefore holds its branch until fleetd or the board restarts. `askForBrief` already receives the run's end (`packages/fleet/src/shared/brief-ask.ts:168-172`) and passes only `resetEpoch` on. Measured on origin/main:

- `jenkins-sha-runs-build-status-fails`: the approval commit `abedcfb49` landed at 2026-11-03 16:33:41Z, and the brief run started at 16:34Z, read no approved plan and refused. The slice was still `held on no-brief` at 2026-11-04 18:24Z.
- `plot-fleetctl-stop-ignores-dry-run`: the approval commit `ac8f8edd4` landed at 2026-11-04 18:08:38Z, and the brief run started at 18:10Z, read the plan as Draft and refused. The slice was still `held on no-brief` at 18:24Z.

In both cases the pass that asked read the plan as Approved on `origin/<main>` (`findMissingBriefs` reads git, `auto-dispatch.ts:53-70`), and the brief run read the main checkout's working tree: `askForBrief` runs in `tree: opts.repoRoot` (`brief-ask.ts:159`), and `/plot-implement` step 1 parses `docs/plans/*.md` from that tree. Nothing but an operator's own fetch and merge moves that tree (`packages/fleet/src/server/entry/registryd-main.ts:1766-1769`, which measured a 17-minute lag), so a retry against the same tree refuses again. The plan file on `origin/<main>` did not change after either refusal, so a retry keyed on a new plan commit would not fire either.

**A `--start` refusal names one defect for all (#3141).** `plot-dispatch.sh` prints `worker=no-loop` and the hint `A branch dispatch (--restart <branch>) starts a worker on any command.` for every `refused` answer of `startCommand` (`skills/plot/scripts/plot-dispatch.sh:2128-2134`). Only the not-the-loop refusal (`packages/domain/src/rules/start-command.ts:89-93`) has that defect and that repair; the charter refusal (`:98-99`) and the absent-prompt refusal (`:102-109`) print the same footer and a hint that repairs neither. The performer reads only `worker=no-loop` as `unaskable` (`packages/domain/src/adapters/performer/performer-shell.ts:112`).

- `if (runner !== 'command') return null;` (`start-command.ts:97`) runs before the `refused` check (`:98`), so a refused charter on `Agent runner: sdk` passes `--start`, a desk is cut, and the worker loop refuses later (`packages/fleet/src/server/entry/worker-loop.ts:1648-1650` refuses a refused charter on either runner).
- The board entry's header says "It reads stdin, spawns nothing and opens nothing" (`packages/board/src/server/entry/start-command.ts:34`), and the entry reads the charter with `readFileSync` (`:60`) and the prompt file with `existsSync` (`:90`).
- `readNamedCharter` (`start-command.ts:56-65`) copies `read` from `packages/fleet/src/server/entry/prompt.ts:58-69`: ENOENT gives `absent`, any other error `unreadable`. If the two drift, `--start` and the loop disagree about one charter.
- The write probe joins only `FALLBACK_PROMPT` to the repo root (`packages/domain/src/adapters/write-probe/write-probe-shell.ts:86-87`), while the loop launches the prompt that `resolvePrompt` (`packages/domain/src/rules/prompt.ts:40-43`) answers for a declared charter, resolves a slice's own `agent:` charter on a fresh take-up (`worker-loop.ts:2025-2035`), and falls back to the desk's copy where the main checkout holds none (`worker-loop.ts:1641-1647`). The probe tests a file a chartered agent never sources.
- The loop's absent-prompt refusal always says `run plot-install-prompt.sh to write .plot/worker-prompt.sh` (`worker-loop.ts:1654`). For a charter that declares `.plot/prompts/x.sh`, the installer writes the fallback and the declared file stays missing. `missingPrompt` already gives the right repair: `write <path>, which charter '<name>' names` (`start-command.ts:107`).
- The charter-refusal tests check exit 1 and no runs (`packages/fleet/test/unit/worker-loop-run.test.ts:374-380`) or no requests (`packages/fleet/test/unit/worker-loop-sdk.test.ts:444-450`), and neither asserts the attempts the loop recorded. Reverting the no-retry part of the refusal leaves both green.

**Two remaining parts of #3125.**

- `packages/board/test/unit/auto-dispatch-brief-ask.test.ts:513` and `:552` assert `toBeGreaterThan(nowEpoch())` against the wall clock, while the stub prints `resets 11pm (Europe/Berlin)` (`:111`). `resolveReset` resolves a reset up to `PAST_RESET_GRACE_SECONDS` (120 s) in the past to now (`packages/domain/src/rules/prompt-exit.ts:124,258-261`), so between 23:00:00 and 23:02:00 Berlin time the recorded epoch equals now and the strict `>` fails. CI run 42117422301 failed on main at `87d93b8ae` with `expected 1793916015 to be greater than 1793916015`; 1793916015 is 2026-11-05 23:00:15 CET.
- fleetd has no re-run of a failed CI run on a slice PR. The only `rerunFailed` caller is the main-repair arm (`packages/fleet/src/shared/repair-start.ts:137`). On 2026-11-04 PR #3110 was red from 01:31Z to 18:05Z and #3111 from 10:24Z to 18:05Z on one flaky test; on each, the fixer spent both CI attempts, pushed nothing, and named a re-run as the next step for a person.

## Design

### Approach

**Test clock: the brief-ask test owns its clock (#3125):**

- The usage-limit `describe` block (`auto-dispatch-brief-ask.test.ts:501`) calls `vi.useFakeTimers({ toFake: ['Date'] })` and `vi.setSystemTime(new Date('2026-11-05T22:00:15Z'))` before the fixture writes its stub, and `vi.useRealTimers()` after each case. Only `Date` is faked, so the fixture's `settle` loop and the child process keep real timers. The fixture, `nowEpoch` and `Date.now` in `agentRunCommand` (`packages/fleet/src/shared/agent-run-for.ts:97`), which feeds `resolveReset`, then read one clock.
- At that instant `resets 11pm (Europe/Berlin)` (`:111`) lies 15 s in the past, inside the 120 s grace, so the stub changes to print a time two hours after the pinned instant, `1am (Europe/Berlin)`. The expected epoch is a constant: 2026-11-06T00:00:00Z.
- `RECORDS THE RESET EPOCH` (`:505-515`) and `A SECOND WAIT REPLACES THE EPOCH` (`:543-553`) assert the recorded epoch equals that constant. A third case keeps the old stub text at the pinned instant and asserts the recorded epoch equals now, which is the instant that failed in run 42117422301 and the grace rule working as designed.

**Brief retry: a brief run reads the plan that asked for it (#3134):**

- **The prompt pins the commit.** `maybeAutoDispatch` reads the sha of `origin/<main>` once per pass through a synchronous `Refs` read, since the function is synchronous, and `briefAskPrompt` (`brief-ask.ts:73-76`) gains a `sha` argument: `/plot-implement <slug> --at <sha> — write the hand-off brief …`. An unread sha starts no ask that pass.
- **`/plot-implement --at <sha>`.** `skills/plot-implement/SKILL.md` gains the flag beside `--branch`: step 1 reads the plan file at `<sha>` (`git cat-file -e <sha>` first, then `git show <sha>:<plan file>`) and runs its phase test on that text, the way `--branch` already reads `origin/<name>`. The changeset bumps `plot-implement: minor`.
- **The end reaches the pass.** `askForBrief` gains an `onEnd` callback, called from the end handler (`brief-ask.ts:168-172`) for every end that carries no `resetEpoch`. A usage-limit end keeps its wait path through `onLimit`. A start that returned `''`, a start that threw, and a `refused` runner choice (`brief-ask.ts:174-177`, `board-run.ts:207-232`) call neither, and their branch stays marked as today (`auto-dispatch.ts:466-469`), because a broken command must not start a process per pulse.
- **The rules are domain properties.** `brief-budget.ts` gains `BRIEF_ASK_RETRIES = 1` and two functions. `briefAskState(branch, readings)` answers `asked` (a run is live or waits for a reset), `free` (never asked, or its run ended with retries left), or `spent` (its run ended `BRIEF_ASK_RETRIES + 1` times and the brief is still missing). `outstandingEnds(ends, missingBriefs)` keeps the end count of each branch still in `missingBriefs` and drops the others, as `outstandingWaits` (`:55-58`) drops a wait. `outstandingAsks` takes the end counts as a fourth input and keeps only `asked` branches, so a `spent` branch no longer charges the `Parallel agents` cap through `briefAskBudget`.
- **A successful end is not a second ask.** A run that wrote and pushed its brief also calls `onEnd`. The count is read only at the next pass, against that pass's `missingBriefs`, which `findMissingBriefs` reads from `origin/<main>`. A pulse taken before the push lands reads the branch as `free` with one end, and asks once more, which is the one retry and is bounded; the second run finds the brief on `origin/<main>` and ends without a write. The test below pins that this costs at most one extra run and never a third.
- **The pass.** `maybeAutoDispatch` takes `briefEnds: Map<string, number>` beside `briefWaits`, and `packages/fleet/src/shared/auto-writes.ts:90` holds it across passes as it holds the other two. An end drops the branch from `briefsAsked` and adds one to its count. The skip at `auto-dispatch.ts:453` reads `briefAskState`: a `spent` branch is skipped and logged once per daemon life as `auto-dispatch: <slug>'s brief run ended <n> times without a brief for <branch> — log: <log>; Write brief on the board, or /plot-implement <slug>`.
- **The board shows the spent state.** fleetd writes `.plot/state/brief-spent/<branch slug>.json` (`{ branch, slug, ends, log }`) when a branch turns `spent`, and removes it when `outstandingEnds` drops the branch. It reads the files at start, so a restart does not reset the bound. The implement route removes the file for its branch before it starts a brief, so a person's Write brief clears the hold. `BriefReading` in `packages/board/src/server/brief-ask-log.ts` gains `spent: { ends: number; log: string } | null`. `BRIEF_WRITER_STATES` in `packages/domain/src/rules/brief-writer.ts` gains `spent`, ordered after `writing` and before `failed`. The row note (`briefNote`, `packages/board/src/app/lib/agent-rows/row-identity.ts:316`), and `AgentRow` in `packages/board/src/contract/schema.ts` gains `briefSpent`, reads "brief run ended 2 times without a brief", with the log path, beside the existing Write brief action.
- **Unit tests** in `packages/domain/test/brief-budget.test.ts`: an ended ask with retries left is `free`; a second end is `spent`; a `spent` branch is not counted by `briefAskBudget`; a live ask is `asked`; a wait before its reset is `asked`; `outstandingEnds` drops a landed brief's count and keeps a missing one. In `packages/domain/test/brief-writer.test.ts`, each order cell with `spent`. In `packages/board/test/unit/auto-dispatch-brief-ask.test.ts`: the prompt names `--at <sha>` with the sha of `origin/main`; with a `@reads-plan-at` stub that runs `git show <sha>:<plan>` and writes the brief only for `State: Approved`, a working tree holding `State: Draft` and an `origin/main` holding `State: Approved` gets its brief on the first ask; with a new `@ends-briefless` stub that exits 0 and writes no brief, a refused run is asked again on the next pass, and a second refused run is not asked a third time, logs the spent line once and writes the spent file; a run that wrote its brief, read on a pulse that still reads it missing, gets at most one more ask and never a third; a usage-limit end still waits for its reset and spends no retry; a spawn failure and a `refused` runner choice stay marked. In `packages/board/test/unit/brief-ask-log.test.ts`, a spent file reads as `spent`.

**Start refusal: a start refusal names its defect (#3141, part a):**

- **The rule carries a word.** `StartCommand`'s `refused` arm gains `defect: 'no-loop' | 'charter-refused' | 'prompt-absent'` (`start-command.ts:57`). The not-the-loop arm answers `no-loop`, the charter refusal `charter-refused`, and the absent file `prompt-absent`.
- **The charter refusal comes first.** `missingPrompt` checks `resolution.resolve === 'refused'` before the runner gate, so a refused charter refuses on both runners, and the `@param prompt` doc (`start-command.ts:68-70`) states that order. The `sdk` runner is still never refused for an absent file.
- **The entry carries the word on its first line.** The refused answer of `packages/board/src/server/entry/start-command.ts:125` changes from `${why}\n${repair}\n` to `${defect}\t${why}\n${repair}\n`, exit 3 as today. The repair stays the whole text after the first newline, so `start_cmd_repair` reads as today. The entry's header states what it reads: stdin, the named charter file, and whether the resolved prompt file exists. It calls `read` from `packages/fleet/src/server/entry/prompt.ts` in place of `readNamedCharter`; `read` answers `unnamed` for `''`, and `readCharter('', null)` returns `unnamed` too (`packages/domain/src/entities/charter.ts:217`), so the switch keeps every resolution.
- **The shell reads the word, and removes one line.** In `ask_start_command` (`plot-dispatch.sh:1002-1025`), `start_cmd_defect=""` joins the reset on `:1004`, and the two lines `3:*)` and `start_cmd_verb=refused` (`:1018-1019`) become one: `3:*) start_cmd_verb=refused start_cmd_defect=${answer%%$'\t'*}; answer=${answer#*$'\t'}`. `start_cmd_why` and `start_cmd_repair` (`:1020-1021`) keep their text. In the `refused)` branch (`:2128-2134`), the footer prints `worker=${start_cmd_defect}`, and the hint line `:2132` becomes `[ "$start_cmd_defect" != no-loop ] || echo "  A branch dispatch (--restart <branch>) starts a worker on any command." >&2`, one line for one line. The slice removes one shell line net, which `scripts/check-shell-lines.sh` accepts.
- **The performer reads every word.** `performer-shell.ts:112` matches `worker=(no-loop|charter-refused|prompt-absent)` and still answers `unaskable` for each.
- **Tests:** `packages/domain/test/start-command.test.ts`, one cell per `defect`, and a refused charter on the `sdk` runner refuses with `charter-refused`; `packages/board/test/unit/start-command-entry.test.ts`, the refused answer's first line is `<defect>\t<why>`, and an unreadable charter file reads `unreadable` through the shared reader; `packages/domain/test/performer-shell.test.ts`, each footer word reads `unaskable`; `test/reconcile/dispatch.test.mjs`, an absent prompt prints `worker=prompt-absent` and no `--restart` hint, and the not-the-loop refusal prints `worker=no-loop` with the hint.

**Probe and loop: the probe and the loop name the charter's prompt (#3141, part b):**

- **One repair text.** `promptAbsentRepair(resolution)` in `packages/domain/src/rules/start-command.ts` answers `write <file>, which charter '<name>' names` for a `declared` resolution and `run plot-install-prompt.sh to write .plot/worker-prompt.sh from the template` for a `fallback` one. `missingPrompt` (`:102-108`) and the loop (`worker-loop.ts:1654`) both call it, so one unit test holds both texts.
- **The probe resolves as the loop does.** `WriteProbe.check` gains a second input, the prompts to probe: `{ file: string; charter: string | null }[]`, or a refusal reason. `check` probes each distinct file in place of `FALLBACK_PROMPT` (`write-probe-shell.ts:86`), answers `unaskable` with the charter's reason for a refused charter, and names the probed file in every `unaskable` reason.
- **The fleetd caller probes each agent it starts.** `probeBeforeStarting` (`registryd-main.ts:1959-1974`) resolves one prompt per `worker-start` write. A write that names a branch resolves that slice's own `agent:` charter through `sliceAgentOf` (`worker-loop.ts:2410`), the reading the loop uses on a fresh take-up (`:2025-2035`). A free agent's write names no branch (`packages/domain/src/workflows/assign.ts:189`), so it resolves the fallback prompt, the one a free loop sources until a slice names a charter. Each resolution uses the prompt answer of `packages/fleet/src/server/entry/prompt.ts:78-79` (`answer`), the resolver the loop calls (`worker-loop.ts:1636`). Where the main checkout holds no file and the write's desk holds one, the probe probes the desk's copy, as the loop does (`worker-loop.ts:1641-1647`).
- **The board caller.** `packages/board/src/server/entry/write-probe.ts:58`, which `plot-fleetctl.sh --start` runs before any slice exists, probes the fallback prompt and the prompt of the charter that `PLOT_AGENT` names in its environment, and names both in its answer.
- **The loop names the declared file.** `worker-loop.ts:1654` reads the resolution's verb and charter name from the line it already splits (`:1636`) and calls `promptAbsentRepair`.
- **The tests pin the no-retry rule.** `worker-loop-run.test.ts:374-380` asserts `r.calls.attempts` equals `[]`, checked against the case's `maxStartRetries: 1` (`:376`). The sdk rig has no `calls.attempts`: it writes attempts through `raiseAttempts` into its state (`worker-loop-sdk.test.ts:94-96`). The slice adds a recorder there, and `worker-loop-sdk.test.ts:444-450` asserts it holds no raise.
- **Tests:** `packages/domain/test/start-command.test.ts`, both `promptAbsentRepair` texts; `packages/domain/test/write-probe-shell.test.ts`, a declared charter's prompt is probed and `FALLBACK_PROMPT` is not read, a refused charter answers `unaskable` with its reason, and an absent declared file names that file; `packages/fleet/test/unit/registryd-main.test.ts` (`probeBeforeStarting`, `:1150`), a `worker-start` for a slice whose plan line names a chartered agent probes the charter's declared file and never `FALLBACK_PROMPT`, and a desk that holds the prompt the main checkout lacks is probed there; `worker-loop-run.test.ts`, a declared charter with an absent prompt logs the `write <file>, which charter '<name>' names` repair; both charter-refusal tests fail when a retry is restored.

**CI re-run: a red PR is re-run once per head (#3125):**

- **Consistent with the fixer plan.** `docs/plans/2026-11-20-the-fleet-fixes-every-red-or-conflicting-pr.md` replaced the fixer's arm walk with `fixerPrNext` (`packages/domain/src/rules/slice-pr-next.ts:575-597`) and added `conflictArm` before `ciRedArm` (merged as #3603, `39cd0b4da`). The walk is `[reviewRunArm, fixerInFlightArm, highArm, conflictArm, ciRedArm]` (`:589`). This slice inserts `ciRerunArm` between `conflictArm` and `ciRedArm`: GitHub runs no `pull_request` checks for a conflicting merge ref, so a re-run there is useless.
- **The arm.** `ciRerunArm` reads the row and a new `rerun` field on `FixerReading`. It answers `{ step: 'rerun', head }` where the row's `ciChecks` reads `failing` on `checksSha === headSha`, the CI-red budget is not spent, `deskGone` (`slice-pr-next.ts:349-356`, the shared desk test of `ciRedArm` and `conflictArm`) holds, and the record holds no re-run for this head. Where a re-run for this head is recorded with `answer: 'asked'` and no reading after it, it answers `hold('rerun-running')`: a `failing` row read before the re-run took effect is the first red read again, not a second red. Where the record notes a `pending` or `green` reading on this head after the re-run, or the re-run's answer is `failed` or `unaskable`, it answers `none('rerun-done')`, and `ciRedArm` then starts the fixer on the next `failing` row. Where `Checks wait` has passed since the re-run's `at` with no such reading, it answers `none('rerun-unseen')`, so a re-run that never started cannot hold the PR for ever. It answers `none('no-ci-red')` otherwise.
- **The record.** `FixerAttemptsRecordSchema` (`packages/domain/src/entities/fixer-attempts.ts`) gains an optional `reruns: { headSha, at, answer: 'asked' | 'failed' | 'unaskable', cleared?: string }[]`, where `cleared` is the time the tick first read `pending` or `green` on that head after `at`. `FIXER_ATTEMPTS_VERSION` stays 1, as in the conflict slice: an older build reads a record with the new field as unreadable, and an unreadable record holds every fixer on that PR. A re-run spends no fixer attempt.
- **Every file the change needs:**

  - `packages/domain/src/ports/fixer-attempts.ts` (`:29-81` holds `read`, `append`, `markInFlight`, `markStart`, `markPushed`): `markRerun(pr, rerun)`, which creates a v1 record with `attempts: []` where the PR has none (`auto-fixer.ts:466` reads `attempts === 'none'` today), and `markRerunCleared(pr, head, at)`.
  - `packages/domain/src/adapters/fixer-attempts/fixer-attempts-file.ts`: both methods.
  - `packages/domain/src/rules/fixer-attempts.ts`: `rerunOnHead(record, head)`, and `fixerReadingOf` (`:119`) carries its answer.
  - `packages/domain/src/rules/slice-pr-next.ts`: `FixerReading` (`:38`) gains `rerun: 'none' | 'running' | 'done' | 'unseen'`; `SlicePrStep` (`:177-191`) gains `{ step: 'rerun'; head: string }`; `ciRerunArm`; the walk at `:589`. No consumer of `SlicePrStep` switches over it exhaustively (`auto-merge.ts:281`, `auto-review.ts:122`, `auto-ticket.ts:266`, `auto-fixer.ts:456`), so the new variant changes no other arm.
  - `packages/domain/src/rules/fixer-start.ts`: the CI-red brief line.
  - `packages/fleet/src/shared/auto-fixer.ts`: `FixerTickWorld.attempts` (`:65`) picks the two new methods; `FixerTickWorld` gains `build: Pick<BuildPort, 'rerunFailed'>`; the tick carries out the `rerun` step and marks a cleared reading.
- **The tick.** On a `rerun` step `fixerTick` writes the re-run record first with `answer: 'asked'`, then calls `rerunFailed(row.head, head)` (`packages/domain/src/ports/build.ts:144`). An `unaskable` answer (Jenkins, `build-jenkins.ts:215`, or no build, `build-none.ts:36`) rewrites the entry as `unaskable`, and a failed call rewrites it as `failed`; both end the re-run round for that head. Where the row reads `pending` or `green` on a head whose re-run has no `cleared`, the tick calls `markRerunCleared`. The run log names each re-run with the PR, the head and the answer.
- **The fixer brief.** `fixerPrompt` for CI-red evidence (`fixer-start.ts:14`) says "the failed jobs were re-run once on this head and failed again" only where the head's re-run answered `asked`. For `failed` and `unaskable` it says that no re-run ran, so the fixer may still name a re-run as the next step for a person.
- **Bitbucket.** Its rows carry no `ciChecks`, so the arm never fires there, as `ciRedArm` does not.
- **The escalation differs from #3125.** #3125 asks that a second failure on one head go to a person with both run ids. Here a second red goes to the fixer, and a person sees it once the CI-red budget of 2 is spent. The cost a person pays on every genuine red is one extra CI round before a fixer starts.

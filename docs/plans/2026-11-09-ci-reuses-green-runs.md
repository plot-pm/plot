# CI reuses green runs

> On a pull request, `select` skips a job that an earlier run of the same pull request passed, while the base SHA of that run's merge equals the base SHA of this run's merge, the difference between the two merges selects no input of the job, and the job's test selection is the same in both runs. The skipped job reports `reused:<sha>`, `validate` accepts it, and any move of the base re-runs every job.

The step summary names the run and the head SHA each skipped job reuses.
- A push to `main`, a dispatched run, a run on the release PR (`changeset-release/*`), a re-run (`Re-run all jobs`, run attempt 2 or later), and every run after the base branch moved run every selected job, as today.
- The checks page shows a reused job as a grey `skipped` with no text, the same as a job the selection did not name. `select` emits one `reused` notice per reused job, and its step summary names the source run, its head SHA and its conclusion, and for each reusable job that runs, the reason it was not reused.

Board impact: none on the plan format, the template, the helper scripts or the `docs/plans` layout. A reused job reads `skipped` in the check rollup, and `validate` stays the one required check, so `checks-verdict.ts` reads the same run shape.

## Motivation

`quality-gates-fail-fast` (delivered 2026-11-09) shipped the tiers, the census halves and the local check order, and deferred its fourth slice, `infra/ci-skips-unchanged-inputs`. Its first Open Question named the risk: "A pull request run tests the merge of its head with `main` … Reusing it after `main` moved skips a job whose real input changed." A person decided at approval whether the slice ships; this plan takes it over with the rule decided on 2026-11-09.

The cost the slice targets is still there. On sprint PR #3237, head `8437242ef` changed only documents since `a269f54d6`, and its run took about 45 minutes, against about 33 minutes for the green run before it (`quality-gates-fail-fast`, *Motivation*). `select` diffs `HEAD^1 HEAD` on the pull request's merge commit (`ci.yml:175`), so it reads the whole pull request against its base, not the change since the last green run. A sprint PR's diff spans most packages, so most of its pushes select most suites; several runs on `sprint/the-board-reads-the-channel` selected only `corpus`.

**The expected saving, measured by the cost juror over the 500 newest `pull_request` runs (2026-11-05 to 2026-11-09, 4.1 days).** The repository is public, so hosted runner minutes are not billed; the target is wall-clock on sprint PRs, chiefly the census. `main` moves about 3.8 times per hour, and of 183 consecutive push pairs on one branch 84 (46 %) kept the base: 59 of 95 on sprint PRs, 25 of 88 on other PRs. Without `ci-cancels-superseded-runs`, 37 runs would reuse at least one job, about 850 runner-minutes, 750 of them on sprint PRs. With it, 51 of 76 eligible pairs had the next push arrive before the earlier run ended, and the adjacent-pair saving falls to about 200 runner-minutes over 10 runs, 2 to 3 runs per day. Where the census is reused, the critical path falls from about 35 minutes to `checks` (about 8 minutes). The base move is read as a proxy: `origin/main` gained a first-parent commit between the two runs' `created_at`.

## Design

This plan has no `Story:`. It touches `select`, the `if:` of the reusable jobs and `validate` in `.github/workflows/ci.yml`. The open plan `ci-cancels-superseded-runs` (PR #3305, branch `origin/idea/ci-cancels-superseded-runs`, slice branch `infra/ci-cancels-superseded-runs`, group key `pr-<number>` for `pull_request` runs) touches the `concurrency:` block (`ci.yml:57-68`), and `sprint-prs-run-ci` in this batch touches the `on:` block (`ci.yml:3-7`) and the merge-base gates. No two of the three change the same lines.

### Approach

**The reuse rule, decided 2026-11-09 (jwloka).** A green job of an earlier run is reused only while the base SHA in that run's merge equals the base SHA in this run's merge. Any move of the base re-runs every job. A pull request run checks out `refs/pull/<n>/merge` (`ci.yml:140-144`, `fetch-depth: 2`), so `HEAD^1` is the base branch's tip that the run tested and `HEAD^2` is the pull request's head. Two runs with the same `HEAD^1` tested the same base. Their merge trees do not differ only by the head change `H1..H2` (`HEAD^2(earlier)..HEAD^2(now)`): when the branch rebases or merges its base between the two runs while the base itself stays the same, a path can hold the same text in `H1` and `H2` and still differ between the two merges. Example: `main` changes `f` from `x` to `y`; `H1` never touched `f`, so the first merge holds `y`; the author merges `main` into the branch and resolves `f` back to `x` in `H2`; `git diff H1 H2` omits `f`, and the second merge holds `x`. The rule therefore compares `diff(H1, H2) ∪ (P1 △ P2)`, where `P1` and `P2` are the two runs' changed-path lists (`changed.txt`, `ci.yml:175`, the diff `HEAD^1 HEAD` of each merge). A path in neither list equals the base in both merges, so the union covers every difference a clean merge can make. The decision about the base stands; this is how the rest of the tree is checked.

**Slice 1: every run records what it tested.** The Actions API gives a `pull_request` run's `head_sha` (the pull request head) and no merge SHA, so a later run cannot learn the earlier run's base from the API. `select` records it:

- A new step after checkout, on `pull_request` only, uploads an artifact named `ci-inputs-<HEAD^1>-<HEAD^2>` with `actions/upload-artifact`, pinned by the SHA the census halves use (`ci.yml:687`), and `retention-days: 7` as for the census reports (`ci.yml:693`). The file inside holds the two SHAs, the changed-path list `changed.txt` (`P` above), and the selection outputs (each job's flag, `contracts_tests` and `corpus_tests`). A later run reads it.
- The name carries the two SHAs, so a later run filters on them from `GET /repos/{owner}/{repo}/actions/runs/{run_id}/artifacts` without a download, and downloads the record only for a run whose recorded base equals its own `HEAD^1`. The list endpoint also returns expired artifacts with `expired: true`; the read drops them, so the 7-day retention bounds the age of a source.
- The step is `continue-on-error: true`. A run that uploads no record is never a source, and nothing else changes. This slice changes no job's result, and it ships first so that the second slice finds records.

**Slice 2: `select` reads the earlier runs and skips what it may reuse.**

- **The read.** A step `Read the earlier green runs`, on `pull_request` only and `continue-on-error: true`, asks `gh api` with `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}`, through the three-attempt `api()` helper of `release.yml:258-272`. `select` gains a job-level `permissions:` block with `contents: read` and `actions: read`. A job-level block replaces the workflow-level one (`ci.yml:54-55`), so `select` names `contents: read` again; `relay-validate` holds `actions: read` for the same kind of read (`release.yml:242-244`, beside `statuses: write`). The workflow-level `contents: read` stays for every other job.
- **The call order and its budget.** The read lists the 20 newest completed `pull_request` runs of `ci.yml` on `github.head_ref` in one call, whose rows already carry `conclusion`, `head_sha` and `pull_requests`, and filters on them first. Newest first, it reads a run's artifact names, skips a run with no unexpired record, and stops at the first run whose recorded base differs from `HEAD^1`, because the base only advances; an early stop can lose a reuse and never add one. It downloads the record and reads the jobs only of a run whose recorded base equals `HEAD^1`. Measured at the peak of 16 non-release PR runs in one hour (2026-11-09 10:00 UTC), the unordered read (1 list plus 2 calls for each of 20 runs, 41 calls) would spend 656 of the 1,000 calls per hour of `GITHUB_TOKEN`, which `release.yml` shares; the ordered read expects 2 to 4 calls, one download and 0 to 1 fetch per run.
- **The diff per source.** For each distinct earlier head, the step fetches that commit (`git fetch --depth=1 origin <sha>`) and writes `git diff --name-only --no-renames <earlier head> HEAD^2`, joined with the symmetric difference of the earlier run's recorded `changed.txt` and this run's. It runs `plot-local-checks.mjs --ci --files` over that list and maps the answer to jobs with the same jq program as `Map the selection to jobs` (`ci.yml:182-228`). That program moves to `scripts/ci-job-map.jq` and both steps read it, so one map answers both diffs. A commit that cannot be fetched (the head was force-pushed away and collected) gives no diff, and that run is not a source.
- **The decision is a domain rule.** `packages/domain/src/rules/ci-reuse.ts` exports `ciReuse(readings)`, an arrow function over values, as `ciSelection` is (`packages/domain/src/rules/local-checks.ts`). The readings are this run's event, `head_ref`, run attempt, base and head SHAs and selection and, per earlier run, its id, its pull request numbers, its `head_sha`, its conclusion, its recorded base, head and selection, its job conclusions and the job map of its reuse diff. For each reusable job it answers `reused:<earlier head sha>` with the source run's id and conclusion, or no reuse with a reason: `base moved`, `input changed`, `selection changed`, `no record`, `not green` or `read failed`. It answers no reuse for every job when the event is not `pull_request`, when `head_ref` starts with `changeset-release/` (the release PR's `pull_request` run is the one whose `validate` the ruleset counts, and the cancels plan isolates it too), or when the run attempt is greater than 1, so `Re-run all jobs` is a full run and a person who doubts a reused green can force one. An earlier run is a source for a job only when:
  - its recorded base equals this run's `HEAD^1`;
  - its recorded head equals its own `head_sha`, and its `pull_requests` names this pull request's number (a fork or a second pull request on a branch of the same name is never a source);
  - the job ended `success` in it, whatever the run's own conclusion: a run that ended `success`, `failure` or `cancelled` is a source for each job that ended `success` in it, because each job is judged on its own result and `validate` already reads them one by one (a job that the earlier run itself reused ended `skipped` and is not a source, so reuse never chains past the run that ran the job);
  - the job map of its reuse diff (`diff(H1, H2) ∪ (P1 △ P2)`) names the job `false`;
  - its recorded selection for the job equals this run's: the job's flag, and `contracts_tests` for `helper-contracts` and `corpus_tests` for `corpus`. `CLAUDE.md` holds the `Local checks` key, and the job map drops markdown outside `skills/` from `$wide` (`ci.yml:203`), so a push that edits only that key selects no job by path and can still widen `contracts_tests` (`ci.yml:213`).

  The newest run that holds for a job wins. The census is one unit: `census-head`, `census-base` and `census-compare` are reused together when `census-compare` ended `success`.
- **The bundle.** `skills/plot/scripts/board/plot-ci-reuse.mjs` reads the readings file, calls `ciReuse` and prints one `reuse_<key>=<value>` line per job for `$GITHUB_OUTPUT`. It prints a value only in the form `reused:<40 hex>` and prints an empty value for anything else, so a malformed value runs the job: `validate` reads only `helper-contracts` and `board-integration` (`needs:` at `ci.yml:2613`), and for the other five reusable jobs no later check would catch a malformed skip. It writes a table to `select`'s step summary (job, source run as a link `${{ github.server_url }}/${{ github.repository }}/actions/runs/<id>`, source head SHA, base SHA, source run conclusion, or the reason for no reuse) and emits one `::notice title=reused::<job> reused from run <id> at <sha>` per reused job. A failed read or bundle writes one summary line and one `::warning::` ("reuse read failed at <call>: every selected job runs"). It reaches no host: the `gh api` step makes every call, so the rule stays synchronous and testable without a mock (*A note on shape*, `CLAUDE.md`).
- **The outputs.** `select` gains `reuse_corpus`, `reuse_macos`, `reuse_contracts`, `reuse_board` and `reuse_census`. Each is empty or `reused:<40 hex>`. The selection outputs (`ci.yml:107-117`) do not change, and the selection still fails open: a failed read, a failed fetch or a failed bundle leaves every `reuse_*` output empty, and every selected job runs.
- **The jobs.** `corpus` (`ci.yml:269`), `macos-shell-contract` (`:425`), `census-head` (`:563`), `census-base` (`:698`), `census-compare` (`:846`), `helper-contracts` (`:910`) and `board-integration` (`:1074`) each add `&& needs.select.outputs.reuse_<key> == ''` to their `if:`. `gates`, `checks` and `validate` never reuse: `gates` holds the static gates for every change, and `checks` holds the unit suites and e2e behind step conditions (`ci.yml:2296`, `:2535`, `:2564`, `:2575`, `:2585`).
- **`validate`.** `require` (`ci.yml:2659-2668`) takes a fourth argument, the job's `reuse_*` output. `skipped` passes when the selection named the job `false`, as today, or when the reuse output matches `^reused:[0-9a-f]{40}$`. Any other `skipped` fails, and a malformed reuse value fails. The step's env gains `HELPER_CONTRACTS_REUSED` and `BOARD_INTEGRATION_REUSED`. `validate` reads only `needs.*` outputs, and the value holds the head SHA and no run id, so `select`'s summary names the source run and `validate`'s names the job and the head SHA. A reused `skipped` passes only while `gates` ended `success`, which `require gates` (`ci.yml:2669`) holds today and a test holds after this change. `corpus`, `macos-shell-contract` and the census are not in `validate`'s `needs:` and stay outside it.
- **Never on `main` or a dispatch.** The read step runs only on `pull_request`, and the bundle prints empty outputs for any other event. A push to `main` keeps the full run as the safety net for a selection miss (`ci.yml:78-82`), and the release dispatch keeps its pinned full run (`ci.yml:39-43`).

**With `ci-cancels-superseded-runs`.** That plan gives a pull request's runs one concurrency group, so a new push cancels the run on the older head. A job that ended `success` before the cancel is a source; a job that the cancel stopped ended `cancelled` and is not. On a pull request with quick successive pushes, reuse therefore starts from the jobs that finished before each cancel: 7 of the 10 newest `pull_request` runs on `sprint/the-board-reads-the-channel` ended `cancelled`, some after `validate` passed (run 42605350975: `validate` at 11:15:59, the run complete at 11:24:52). The two plans merge in either order.

**With `sprint-prs-run-ci`.** On a slice PR into a sprint branch, `HEAD^1` is the sprint branch's tip, so "the base is unchanged" means "the sprint branch's SHA is unchanged", not `main`'s. Every slice merged into the sprint branch moves that base for every other open slice PR, and their next runs reuse nothing. The rule compares SHAs and reads no branch name, so it needs no change for a sprint base. A sprint PR into `main` reuses while `main` does not move.

**What reuse cannot see.** A flaky test that passed once stays reused until the base moves or the head changes one of its job's inputs. The 7-day retention of the record bounds how old a source can be. A job's real input outside the `Local checks` map (a runner image update, a third-party action) is not in the diff either. The reuse diff has one residual: a path in both `P1` and `P2` that holds the same text in `H1` and `H2` is in neither `diff(H1, H2)` nor `P1 △ P2`, and its two merges can still differ when git merges it textually under two different merge bases. The full run on `main` after the merge is the net for all three, and `Re-run all jobs` forces a full run on the pull request.

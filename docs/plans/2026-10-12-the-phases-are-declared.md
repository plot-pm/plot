# The phases are declared

> A `Workflow phases` key in `## Plot Config` maps each phase name to the plan states and story statuses it holds, Plot ships the five agentic-workflow phases as the default, and the domain answers a plan's or story's phase from the declared map instead of from `toBoardPhase` and `storyPhase`.

## Changelog

- A `Workflow phases` key in `## Plot Config` declares the board's phases and the plan states and story statuses each one holds. A repository that declares none gets Discovery, Design, Development, Testing and Released.
- With the default phases, no plan reads in Discovery, and a Draft plan reads in the Design column. The plans board draws only the phases that hold a plan state, so it shows no Discovery column.
- Upgrade note: a repository with no `Workflow phases` key sees its Draft plans move from Discovery to Design on upgrade. No plan file, command or config key changes. To keep the earlier columns, declare `Workflow phases: Discovery = plan:draft, story:*; Design = plan:design; Development = plan:approved; Testing = plan:delivered; Released = plan:released`. The `story:*` member keeps every story in a declared phase, so the story lanes still draw.
- A plan card in `State: Design` offers Approve and Interrogate, as a Draft card does.
- `/plot-idea` asks whether a plan carries significant design decisions, and writes `State: Design` on yes. An unattended run with no answer in its prompt writes `State: Draft`.
- A *Needs design* action moves a Draft plan to Design, from the board or from the command line. It writes where the plan lives: on the open plan PR's branch, on the work branch, or on the default branch.
- Plot's docs, `/plot` and the manifesto name the five default phases and the `Design` plan state, and call the `State:` words states, not phases. The fourth activity is Testing, not Endgame.

## Design

### Approach

The design spec is [DESIGN-phases.md](../stories/plot-works-in-five-phases/DESIGN-phases.md) §2, §3 and §8.

**Two words.** A *state* is the `State:` word in a plan file. A *phase* is a declared column. New code and changed prose name a plan's state `state`. `PlanReadings.phase` (`rules/phase.ts:115`), the script `plot-phase-gate.sh` and the wire key `phase` of the transition write (`transitions/plan.ts:133`) hold a state under the old name, and this plan does not rename them.

**A released decision reversed.** The released plan `2026-08-16-board-shows-discovery` (v2.5.0) decided that "Draft is the discovery phase" (its `:58`) and put Draft plans in a Discovery column. D1 and D2 reverse that decision: Discovery holds stories only, and a Draft plan reads in Design. This plan keeps that plan's measurement that a column that can never hold a card is a defect, and draws no Discovery column on the plans board.

**The declaration.** A new rule, `packages/domain/src/rules/workflow-phases.ts`, exports `parsePhaseMap(value)` and `DEFAULT_PHASE_MAP`. `parsePhaseMap` takes the key's text and returns an ordered phase map, or a refusal that names the entry and the reason. The key name and the grammar are D25 (DESIGN-phases.md §2): one line, `;` between phases, `,` between members, each entry `<name> = plan:<state>, story:<status>, …`, every member with its `plan:` or `story:` prefix, and `story:*` for every status. A phase name outside the five default names is valid, and nothing refuses it (D26). `plan:rejected` and `plan:superseded` cannot be declared. A state or status in two phases is a refusal. The split into entries follows `rules/local-checks.ts:73-82`, but `parseLocalChecks` skips a malformed entry and `parsePhaseMap` refuses it.

**The default.** `DEFAULT_PHASE_MAP` is `Discovery = story:*; Design = plan:draft, plan:design; Development = plan:approved; Testing = plan:delivered; Released = plan:released`. A unit test asserts that its names equal `BOARD_PHASES` in order. `BOARD_PHASES`, the `Phase` type, `phaseOrder` (`workflow.ts:80`) and `DevelopmentWorkflow` (`workflow.ts:176-186`) stay as the default map's names; no production code outside `entities/workflow.ts` reads `phaseOrder` or `DevelopmentWorkflow`. Plot's own `CLAUDE.md` declares the default as the `Workflow phases` key, and `./scripts/check-agents-md.sh --write` regenerates `AGENTS.md`.

**The phase of a plan and a story.** `phaseOfPlan(map, readings)` replaces `toBoardPhase`, and `phaseOfStory(map, status)` replaces `storyPhase`. The readings are the plan state and an optional `deliverable` flag. A deliverable plan reads in the phase that holds `plan:delivered`; when no phase holds it, the plan stays in the phase of its state. A state no phase holds answers `null`, as `toBoardPhase` does for `rejected` today. `planPhases(map)` answers the names of the declared phases that hold at least one `plan:` member, in declared order. The tracer refinement of DESIGN-phases.md §3 belongs to `design-work-proves-the-path`, which adds the marker. `phaseOfStory` has no production caller in this plan, as `storyPhase` has none today; its first caller is the Discovery tab of `tickets-and-stories-have-lanes`. Stories stay in Discovery whatever the map says (D27): `planPhases(map)` counts only `plan:` members, so the Planning tab's columns show plans only, also for a phase that holds `story:` members too, and the Discovery tab lists every story.

**Workflows and leadership.** `phaseWorkflows(map)` derives the workflow list per phase: a lifecycle workflow belongs to the first declared phase that holds a state it acts on. `approve` acts on `draft` and `design`, `dispatch`, `implement` and `deliver` act on `approved`, and `release` acts on `delivered`. With the default map the answer equals today's `PHASE_WORKFLOWS`, and a unit test asserts that equality. `PHASE_WORKFLOWS` becomes `phaseWorkflows(DEFAULT_PHASE_MAP)`, and the doc block at `workflow.ts:126-137` states the new rule. `PHASE_LEADERSHIP` stays keyed by the five default names, and a declared phase outside them carries no leadership (D26).

**View states are domain properties.** CLAUDE.md *Every rendered state is a domain property* and DESIGN-phases.md §8 put every decision the board renders in the domain. This plan adds two rules, and the components only read their answers:

- `phaseColumns(map)` answers one entry per name of `planPhases(map)`: `{ name, leadership, accent, checklist }`. `leadership` is the `PHASE_LEADERSHIP` entry for a default name and `null` for any other. `accent` is the name when it is one of the five default names and `neutral` otherwise, and `PHASE_ACCENT` maps each default name and `neutral` to a CSS class, so a declared phase outside the five gets the neutral accent (D26). `checklist` is true for the phase that holds `plan:delivered` and false for every other. The column schema (`schema.ts:736`) carries the three fields, the server builds the columns from `phaseColumns(map)` at `board.ts:2252`, and `Board.tsx:217-224`, `Swimlanes.tsx:161-163` and `PlanCard.tsx:368` read them.
- `cardControls(readings)` answers which controls a card offers, from the plan state, `status` (`planStatus`, `rules/phase.ts:147-163`) and `started`: `approve` and `interrogate` on a `draft` or `design` plan, `dispatch` where `status` is `approved` or `in-progress`, and `readyToStart` where `dispatch` holds and the plan records no `Started:`. `CardSchema` gains `controls`, and `isDraft`, `isApproved` and `isReadyToStart` (`PlanCard.tsx:40-85`) read `controls.approve`, `controls.dispatch` and `controls.readyToStart`. `menus.tsx:1204` and `:1464-1466` follow through those predicates. A Design card therefore offers Approve, which is what `phaseWorkflows` says and what the `approve` transition accepts; the `approve` command keeps its own preconditions and refusals, which the card does not copy.

**`status` answers, and no `state` field is added.** `CardSchema` already carries `status` (`schema.ts:599`). It answers `isApproved` and `isReadyToStart`: `approved` and `in-progress` hold exactly when the state is `approved` and the plan is not deliverable, which is today's Development column. It does not answer Draft against Design, because `planStatus` folds both into `draft` or `open` (`rules/phase.ts:161`). That distinction is needed only inside `cardControls`, which reads the state on the server, so the wire carries `controls` and no `state`. `App.tsx:877` reads `c.status === 'released'`, and the `started` assignment at `board.ts:2204` reads `controls.dispatch`.

**The board.** The board server reads the key through the plan store's `config(key, fallback)` (`ports/plan-store.ts:133`) as a fourth member of the concurrent config reads at `board.ts:1871-1875`, so the read adds no serial spawn. It parses the value with `parsePhaseMap` and puts `phaseColumns(map)` on the payload as the column list. On a refusal the board renders the default map and puts the refusal text on the payload, and `Board.tsx` shows it above the columns. The plans board draws one column per entry, so the default map draws no Discovery column. The board's own phase readers move to the map:

- **The wire.** The three fields typed `z.enum(BOARD_PHASES)`, `schema.ts:425` (card), `:736` (column) and `:2486` (row, nullable), become strings, and a payload test asserts that each names a phase of the payload's column list. The re-export of `toBoardPhase` (`schema.ts:1349`) goes. `toggle` (`Board.tsx:173`) takes a string.
- **Other literals.** `phaseDateOf` (`board.ts:1165-1177`) keys on the plan state and the `deliverable` flag, so each card keeps today's date. `LANE_PHASES` (`Swimlanes.tsx:66`) and `plansInStory` (`StoryModal.tsx:84`) read the payload's column list. `mock-fleet.ts` keeps the default names, and its two `idea/` rows (`:306`, `:325`) read Design, the phase that holds `plan:draft`.
- **Card order in a shared column.** With the default map, Draft and Design cards share the Design column. A Design card sorts by its `Design:` date, newest first. A Draft card has no record and carries `''`, so Draft cards follow the dated cards in the order they arrive, as Discovery cards do today (`Board.tsx:96`, the `phaseDate` doc at `schema.ts:600-626`).
- **Rows.** `rowsFromPulse` (`server/fleet.ts:4910`) takes the parsed map as a parameter. The fleet render reads the key once per render as one more member of its concurrent reads at `server/fleet.ts:6526`, and passes the map at the call at `:6555`, so no serial `plot-config.sh` spawn is added. `:5463` reads `phaseOfPlan(map, { state })` with no `deliverable` flag, so a row does not auto-bump, as today. `:5842` gives an `idea/` row the phase that holds `plan:draft`.
- **The auto-bump** at `board.ts:2082-2115` reads `phaseOfPlan(map, { state, deliverable })`. `toBoardPhase` and `rowPhase` go, with the re-export at `server/fleet.ts:2269` and the export list entry at `:2506`.

**The fleet reads no phase name.** `packages/fleet/src` reads no phase name today (a grep for the five names, `BOARD_PHASES`, `toBoardPhase`, `storyPhase` and `rowPhase` returns zero, 2026-10-12), and no slice adds one. The board server's `fleet.ts` is board code, and the board slice moves its two phase readers. The board slice's acceptance is a payload unit test, with no browser, over the map `Idea = plan:draft, plan:design; Build = plan:approved; Done = plan:delivered, plan:released`: every card, column and row names one of those three phases, `controls.approve` is true on every Draft and Design card and on no other, only `Done` has `checklist`, no column has `leadership`, and every column's `accent` is `neutral`.

**Needs design.** A new transition `needsDesign(plan, input)` in `transitions/plan.ts` moves `draft` to `design` and refuses every other state by name. It writes `State: Design`, a `Design:` record (`<date>, <who>, <channel>`, the shape of `Approved:`, where the channel is `board` or `cli`) and an empty `## Spec` section with the placeholder `_To be filled in during Design._`. The record-field union at `transitions/plan.ts:138` and the state union at `:133-136` gain `'Design'` and `'design'`, and `PlanRecordWrite.field` at `workflows/decision.ts:76` gains `'Design'`. The comment at `plot-plan-meta.sh:246-248` changes in place to that shape, with no net shell lines. `cardControls` gains `needsDesign`, true on a `draft` plan only, and the board shows a *Needs design* button where it holds; the row menu's Commission entry (`menus.tsx:1466`) reads the same field, which keeps today's answer (Draft only). A plan moved to Design takes the person arm at approval from the day `feature/the-design-approvals-are-gated` of `design-work-proves-the-path` lands (`approvalArm` keys on the `design` state), so every test in this slice that approves a `design` plan passes `--who` with a handle from `People`. The slice waits on that spike, so no plan reaches `State: Design` through *Needs design* before the person arm exists.

**Where the write lands.** A workflow of the same name in `workflows/needs-design.ts` decides the writes, as `workflows/approve.ts` does for approval. It writes the plan where the plan lives, so the state reaches the ref that D13 merges:

- **A plan with an open plan PR** (`Review: pr`, PR state `OPEN`): the commit goes onto the plan PR's head branch, in a worktree checked out on that branch, and the push writes that branch itself (`push`, `onto: ''`). The plan PR then carries `State: Design`, and approving the spike merges it with that state onto the default branch (D13, `design-work-proves-the-path`). This is also where `the-fleet-writes-the-design` puts its spec commit (story Open Point 9).
- **`Impl: same branch`**: the caller's checkout, with no push, as `/plot-approve` records there.
- **Any other plan** (`Review: in-session` or `ballot`, on the default branch): a booking worktree on `plot/needs-design-<slug>` cut from `origin/<main>`, pushed onto the default branch through the shared ladder (`entry/ladder.ts`) with its micro-PR fallback, as `bookApproval` does (`entry/approve.ts:667-700`).
- **A `Review: pr` plan with no open plan PR** is refused as `plan-pr-absent`, with the PR state in the text, and nothing is written.

The bundle and the endpoint write the state receipt through `recordStateReceipt(ctx.repoRoot, rel, 'Design')` (`server/entry/ladder.ts:64`) after the plan file is written, in the caller's checkout, as `entry/approve.ts:346` does for `Approved`; that checkout's `.plot/state/state-receipts/` is where the state gate looks (`gate.ts:231`). The receipt writer is TypeScript, so `plot-state-receipt.sh` and `check-shell-lines.sh` see no change. The bundle refuses under `PLOT_UNATTENDED=1`, because D3 gives the move to a person and the fleet never decides it. `owningCommand` gains a `design` arm that names the bundle, and its fallback text names the lifecycle `Draft > Design > Approved > Delivered > Released`. The controller gate's action list (`controller-gate.ts:11`, `:50`) and `_action_of` (`plot-state-receipt.sh:173-180`) do not list *Needs design*: like `idea` and `commission`, the action carries no action receipt.

**The bundle's registrations.** `board/plot-needs-design.mjs` is built from `packages/board/src/server/entry/needs-design.ts`. It needs a `shipped…` output in `packages/board/build.mjs` (the pattern at `:1208-1209`), a `-merge` line in `.gitattributes` (the pattern at `:58`, gated by `scripts/check-bundle-attributes.sh`) and a row in `skills/plot/scripts/README.md` (gated by `scripts/check-helper-table.sh`).

**The controller prose.** `CLAUDE.md:499` counts the endpoints ("Nine actions exist as controller endpoints today … A tenth, `merge`, has no endpoint"), and one sibling changes the list: `the-fleet-writes-the-design` removes `commission` with `POST /api/commission`. `design-work-proves-the-path` adds no name, because its spike approval is the `--spike` mode of the `approve` endpoint; it adds one clause for `--spike` to the same paragraph. The same paragraph names `plot-needs-design.mjs` as a route with no board that the controller gate does not see. `:518` adds `plot-needs-design.mjs` to the writers whose receipt admits a `State:` change. `AGENTS.md` follows.

**The design question in `/plot-idea`.** D3 gives the question to `/plot-idea`, and the plan keeps it out of the ceremony questions: MANIFESTO Principle 10 (`MANIFESTO.md:79`), the plot-idea frontmatter and `CLAUDE.md:166` name two ceremony questions, and they stay at two. A new step after step 4 of `skills/plot-idea/SKILL.md` asks *"Does this plan carry significant design decisions?"* and records the answer as `State:`, not as a ceremony answer. On yes, the plan file is created with `State: Design` and the empty `## Spec` section. A new file passes the state gate, because the gate admits a creation (`rules/state-transition.ts:137`). The default answer is no. Under `PLOT_UNATTENDED=1` the step reads the answer from the prompt; with none, it writes `State: Draft` and names the skipped question in the output, so no model decides design (D3). The board's idea prompt (`server/idea.ts:279`, "Stop at Draft") runs unattended and gives no answer, so a board-started plan is Draft; the prompt does not change. The summary's Progress line (`skills/plot-idea/SKILL.md:415`) prints `[x] Draft > [x] Design > [ ] Approved > …` for a Design plan. The Model Guidance table gives the step the Mid tier: a Mid model recommends an answer, and a Small model asks.

**The prose.** The plan states stay as they are, and `Design` joins them as the optional state between Draft and Approved. Where the prose names the `State:` words, it calls them states: `CLAUDE.md` *Phase Guardrails* (`:205`) becomes *State Guardrails* and `:207-209` say "Five plan states" and "the current state"; the mentions at `CLAUDE.md:530`, `:537` and Principle 7 at `MANIFESTO.md:55` say "state guardrails"; `MANIFESTO.md:101` says "Plot's plan states (below)", and `:148` says "five plan states" with `Design` optional; `skills/plot/SKILL.md:170` *Plan Phases* becomes *Plan States* with a `State` column; `README.md:65` says "Four plan states, and an optional fifth" and its diagram adds Design. No heading link points at the two renamed headings (grep for `#phase-guardrails` and `#plan-phases`, 2026-10-12). The declared phases go where the prose names columns or activities: the activity table in `MANIFESTO.md:99-111` names Testing in place of Endgame and adds Released, `MANIFESTO.md:156` says "Testing fixes", and `skills/plot/SKILL.md:182` no longer says that a plan has no Testing phase. After the slice, "phase" in these files means a declared column and "state" means a `State:` word, and the one shared name, `Design`, is a state that the default map places in the phase of the same name.

**Adopting repositories.** D12 applies the default map to every repository that declares no key. On upgrade such a repository sees its Draft plans in Design and no Discovery column on the plans board. *Versioning* in `CLAUDE.md` puts "breaking workflow changes" under Major. This change breaks no workflow: every command, transition, refusal, plan file and config key keeps its meaning, a Draft card keeps its Approve control, and the only change an operator sees is the column a Draft card renders in, plus Approve on a Design card. A workflow that ran before the upgrade runs after it with no action, and one declaration restores the earlier columns. The changesets therefore bump `plot` and `@plot-pm/board` minor, as a new section of the config and new behaviour (*Minor*: "new sections, new patterns, expanded coverage"). The release note is the Changelog's upgrade bullet.

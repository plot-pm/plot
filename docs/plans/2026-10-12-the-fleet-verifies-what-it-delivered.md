# The fleet verifies what it delivered

> For each Delivered plan the fleet runs a verification panel against the merged work on the default branch, writes a verification record into the plan, opens one `ai-generated` issue per refuted claim, flags a refuted plan, and keeps a manual release checklist for the endgame round. Release stays a person's act.

## Changelog

- The fleet verifies every Delivered plan that is not a tracer plan against the commit that delivered it, including a plan that `/plot-deliver` already panelled at delivery: each Changelog entry and acceptance claim is judged supported or refuted by a gated juror line, and the plan gains a `Verified:` record and a `## Verification` section. The run executes the default branch's scripts, bundles and skill text against the pinned code, and the record names both commits. A plan delivered again after `/plot-reject` is verified again. The `Auto-verify` setting turns the run on and off, and the `Verify command` key names its runner.
- `board/plot-verify.mjs` prepares a pinned run, folds the jurors' verdicts into one line per claim, and books the record onto the default branch. `plot-local-checks.mjs --files <path>` takes the changed files from a list, and refuses an argument it does not know.
- `/plot-panel` takes a list of commitment labels, gates each label per juror, and sends a juror back once with every refusal; it reconciles the first label of the list. An optional `Prefix` parameter names the juror and moderation files.
- The fleet opens one issue, labelled `ai-generated`, for each refuted claim where the repository's issue source (`issueSource`) resolves to a declared `Tracker` with a connector, and the board flags a plan with a refuted claim. `/plot-release` lists refuted and unverified plans before it cuts a release.
- A failed verification run shows in *Waiting on you* with its log, its reason and the restart command. One plan stops after 3 consecutive failed runs, and the fleet starts no run after 3 consecutive failed runs across plans until a person restarts one.
- `/plot-deliver --verify <slug>` runs the verification panel on a Delivered plan by hand, at the delivery commit or at a commit the person names, and replaces the record.
- The fleet keeps a manual release checklist for the human testing round in `docs/releases/vnext-checklist.md`. `/plot-release rc` adds the RC line to it in place, and the final release renames it to `docs/releases/v<version>-checklist.md`.

## Design

### Approach

The design spec is [DESIGN-phases.md](../stories/plot-works-in-five-phases/DESIGN-phases.md) §6, *In Testing*.

**Spike first.** The riskiest mechanism is the pinned run: the default branch's tools run against the pinned delivery commit and produce a gated record per claim. The first slice, `feature/a-pinned-run-verifies-one-plan`, is the plan's spike (`design-work-proves-the-path`, *The marker*). It builds that run end to end on one Delivered fixture plan, with juror files written by the test and no model, so CI judges the mechanism. Its *Acceptance* items decide whether a person confirms the remaining slices or rewrites them. The annotation gates nothing until `design-work-proves-the-path` ships its spike machinery, so D29 decides the route: the plan is approved whole, and right after the approval its six other branches are held in `.plot/hold` until a person removes the holds (*Notes*).

**The claims.** `claimsOf(plan)` numbers the plan's `## Changelog` entries in file order, then the items of an `## Acceptance` section where the plan has one. Claim numbers are read from the plan at the pinned commit, so a later edit of the Changelog does not renumber a run's claims. `plot-verify.mjs claims <slug> <sha>` prints the numbered list as `<n>. <claim text>`, one claim per line. No line starts with `Claim-<n>:`, so a juror that copies the list into its verdict file writes no line the gate reads as a commitment; a test asserts that no output line matches `^Claim-[0-9]+:`. `/plot-deliver` step 5.1 does not run in verify mode, so the jurors and the fold number one list.

**The pinned commit.** A run judges the plan at its delivery commit: the newest first-parent commit on the default branch whose diff adds a filled `Delivered:` line to the plan file. A new refs operation `recordCommit(file, field)` answers it with one `git log`. Every slice of the plan has merged at that commit. A plan delivered later can still have merged a slice before it, so the pin narrows the window in which a later change can refute a claim and does not close it. A person who wants to judge a claim at a later commit runs `/plot-deliver --verify <slug> --at <sha>` (below), and the record names that commit.

**The tools come from the default branch.** The rule: a run executes the default branch's scripts, bundles and skill text, and reads only the plan, its code and its `## Plot Config` at the pinned commit. `plot-verify.mjs prepare <slug> [--at <sha>]` builds two detached trees under `.plot/state/verify/<slug>/` with the trees port's `add` (`ports/trees.ts:242`):

- `tools/` at `origin/<main>`, fetched at the start of the run. It needs no install, because the scripts and bundles under `skills/plot/scripts/` run without `node_modules`.
- `pin/` at the pinned commit. `prepare` runs `pnpm install --frozen-lockfile` in it once and records the seconds. No script installs at a desk today; a desk's agent installs because `CLAUDE.md` tells it to, so the run owns its install.

Every command of the run is the tools tree's copy, called by absolute path with the pinned tree as its working directory: `node <tools>/skills/plot/scripts/board/plot-local-checks.mjs --files <list>`, `plot-verify.mjs` and `plot-panel.mjs`. `plot-local-checks.mjs` takes the repository root from its working directory and its scripts from its own location (`local-checks.ts:190-196`), so the pinned tree's `Local checks` key names the checks and main's code runs them. The skill text comes from the tools tree too: the run's prompt names `<tools>/skills/plot-deliver/SKILL.md` § *Verify mode* and `<tools>/skills/plot-panel/SKILL.md` by path, and the run does not invoke an installed `/plot-deliver`. A `prepare` started from another copy of the bundle hands over to the tools tree's copy once the tree exists, so the version that runs is main's. The record names the tools commit beside the delivery commit and the judged commit.

`prepare` refuses, and the run fails with the reason in its log, when the fetch fails, when a tree cannot be added, when the tools tree holds no `plot-verify.mjs` or `plot-local-checks.mjs` bundle (`tools-unavailable: <path>`), when no delivery commit exists (`pin-not-found`), or when the install exits non-zero (`install-failed`). `plot-local-checks.mjs` refuses an argument it does not know with exit 2 from this slice on, so a later change of its arguments fails loudly instead of checking nothing.

**Where the trees live.** `.plot/state/` is ignored (`.gitignore:30`) and lies outside `Worktree root`. The reaper and the reconcile scan list a worktree with no `.plot-worker.pid` only under `Worktree root` (`packages/board/src/server/entry/reap.ts:595-596`, `skills/plot/scripts/plot-reconcile-scan.sh:2593-2595`), and the fleet scan lists a worktree only with its branch (`plot-fleet-scan.sh:1810-1816`), so no reader shows a verify tree as a desk, and no shell line changes. `prepare` removes an earlier slug's trees with `removeOnly` before it adds new ones, and the fleet removes the trees of a run whose `.plot-verify.pid` names a dead process at the start of each pass.

**The verification record.** A Delivered plan gains two things:

```markdown
- **Verified:** 2026-10-20, delivery 2026-10-19 at 1a2b3c4, judged at 1a2b3c4 with tools at 9f8e7d6, 5 supported, 1 refuted

## Verification

- Claim-1 supported — <claim> — 3 of 3 (executed: behaviour, deliverable)
- Claim-4 refuted — <claim> — behaviour refuted; deliverable, changelog supported — #1712
- Claim-5 refuted — <claim> — changelog refuted — no issue: <the tracker port's reason>
```

`verificationOf(plan, deliveryCommit)` reads them and answers `unverified`, `supported`, `refuted` or `stale`, with the refuted claims, their issue numbers, the delivery date and the commits. It answers `stale` when the record's delivery date differs from the plan's current `Delivered:` value, when the plan has no `Delivered:` value, or when `deliveryCommit` is given and differs from the record's delivery commit. The board and the fleet both pass `recordCommit(file, 'Delivered')`, so both give one answer after a same-day rejection and second delivery. The board reads it in its scan for Delivered plans only: 0 today, and about 5.4 a day until they are released. It answers `unverified` with no badge for a tracer plan. The rule reads text and one reading, so the board can ask it on every render. The record is not a `State:` change, so `plot-state-gate.sh` is not involved.

**A rejected plan.** `/plot-reject` replaces the `Delivered:` line with `Rejected:` and keeps every other record (`skills/plot-reject/SKILL.md:111-112`). The plan then has no `Delivered:` value, so `verificationOf` answers `stale` and the card shows no badge from the old record. When the plan is delivered again, its new `Delivered:` date or delivery commit differs from the record's, the plan reads `stale`, and the fleet verifies it as it verifies an `unverified` plan. `/plot-reject` does not change.

**Tracer plans.** A plan with `Tracer: yes` (D15) never reads in Testing (D5, D14, `DESIGN-phases.md:114`), and D18 verifies a plan in Testing. The fleet starts no run for a tracer plan, `--verify` and `prepare` refuse one and name D5, and `verificationOf` answers `unverified` for it with no badge. The claims of a tracer plan carried with its first dependent are judged where the dependent's Changelog states them. The `tracer` field comes from `plot-plan-meta.sh`, which `feature/a-slice-is-marked-spike` of `design-work-proves-the-path` adds; the record slice and the run slice wait on it.

**The panel is `/plot-deliver` step 5's panel.** The fleet's run is `/plot-deliver --verify <slug>`, a new mode of the existing skill with its own *Verify mode* section. It replaces three steps and reuses the rest:

- Step 2's phase check is inverted: verify mode refuses a plan that is not Delivered (or Released, for a person's run) and refuses a tracer plan. Step 2's "Already delivered." answer does not apply in verify mode.
- Step 5.1 is replaced by `plot-verify.mjs prepare`, which writes the claims and the file list.
- Step 5.2 runs as written, with step 5's three lenses and rubric, the `verify-` file prefix and the Commitment list below. Step 5.2b, the per-PR fallback without `/plot-panel`, does not run: verify mode with no `plot-panel` skill text in the tools tree is a failed run that names the missing file.
- Step 5.3 does not run. The record comes from `plot-verify.mjs fold` over the juror files, never from the moderation. `/plot-panel` still writes the moderation to `verify-panel.md` for a person to read.
- Steps 4 and 4b run read-only and hand the jurors the plan's merged PRs, as at delivery. Steps 6 to 9 do not run, so verify mode flips no phase. `plot-verify.mjs record` books the record.

It hands `/plot-panel` the Commitment list `Position`, `Evidence`, `Claim-1` … `Claim-<n>`, shown to the jurors in the form `commitmentLine` renders (`panel.ts:90-91`):

```
Position: <supported|refuted>
Evidence: <executed|read>
Claim-1: <supported|refuted>
Claim-2: <supported|refuted>
```

A line pasted from this form fails the gate, because `<supported|refuted>` is not a word in the vocabulary. The form `Claim-1: supported | refuted` would pass as `supported`, because `readJuror` keeps the first word (`panel.ts:148-151`), so no brief or prompt of the run shows it. `Position` is first in the list, so `/plot-panel` reconciles it and the moderation reports the plan.

**The per-claim send-back.** `/plot-panel`'s Commitment parameter becomes a list of one or more labels, each with its own words. Step 2's brief shows every label. Step 3 runs one `plot-panel.mjs check` call per label per juror. Step 4 sends a juror back once, with every refusal text of that juror appended, so a juror that omits `Claim-3:` is asked again for it. A juror refused on any label after its one send-back makes the panel refused, as step 4 already rules for one label. Step 5 pipes the first label's readings into `plot-panel.mjs reconcile`, which takes one reading per juror (`packages/board/src/server/entry/panel.ts:71-89`). The deliverable juror of round 3 ran the gate 26 times against five scratch files with this vocabulary: a missing label, the pasted form and two values for one label each exit 3, and `Claim-10:` does not satisfy `Claim-1:` (`.plot/panels/2026-10-12-the-fleet-verifies-what-it-delivered/round3-deliverable.md`, *Gate run*), so the change is in `skills/plot-panel/SKILL.md` only. A caller that passes one label sees no change. `/challenge-the-plan` passes one. `/plot-deliver` step 5 keeps passing `Position` alone and keeps its own `Evidence` check (`skills/plot-deliver/SKILL.md:315-320`), so an `Evidence:` refusal at delivery still gets no send-back; only verify mode passes the list. The fleet implements no part of the panel. What it adds is the fold below.

**Juror commands.** A juror runs what a claim says where the pinned tree allows: the commands that the tools tree's `plot-local-checks.mjs --files <list>` prints in the pinned tree, and the plan's own bundles there. At the pinned commit the script's own source of changed files is empty, because `changedFiles` diffs `origin/<main>...HEAD` (`packages/domain/src/adapters/refs/refs-git.ts:309-317`) and the delivery commit is an ancestor of main. So `prepare` writes the plan's own files to `<list>`: for each merged slice branch, the host's merge commit (`host.prMergeCommit`) and the files that commit gave the default branch (`refs.commitFiles`, `git show -m --first-parent`), as `packages/board/src/server/controllers/deliverability.ts:140-150` reads them. With `--files <path>`, `plot-local-checks.mjs` takes the changed files from that list alone, in place of both `changedFiles('HEAD')` and `workingChanges()` (`local-checks.ts:99-101`), because the pinned tree holds no work of its own. A branch whose merge commit the host does not name is listed in the brief as unread, and a claim that depends on it is committed `Evidence: read`.

**The CI-suite guard.** The controller gate refuses a `CI suites` command only for `PLOT_UNATTENDED=1` in a linked worktree that holds `.plot-worker.pid` (`packages/board/src/server/entry/gate.ts:416-421`, `:473`). `prepare` writes `.plot-verify.pid` at the root of `pin/`, the run sets `PLOT_UNATTENDED=1`, and the gate's desk test (`underDesk`, and the CI-suite arm at `:473`) reads either marker. The pin gets its own marker because the fleet scan, the reaper and the desk adapters read `.plot-worker.pid` as a slice agent's desk. `.gitignore` gains `.plot-verify.pid` beside `.plot-worker.pid` (`:63`), and `prepare` also writes it to the shared `info/exclude` through `excludePath` (`ports/trees.ts:547`), because a pinned commit's `.gitignore` predates the line. The gate a session runs is the installed plugin's copy, so the guard holds once a plugin release carries the change; until then the run's prompt states the rule, and the spike does not depend on it. A juror starts no board or fleet command. A claim that only a CI suite proves is judged from the CI run on the plan's merge commits and committed `Evidence: read`, as the one committed delivery panel did for `fleet.test.mjs`.

**File names.** `/plot-panel` gains an optional fifth parameter, `Prefix`, default empty, applied to every juror file and to the moderation. `jurorPath` and `moderationPath` (`panel.ts:49`, `:58`) take it, and `plot-verify.mjs fold` reads the juror files through `jurorPath`, its first production caller. The verification run passes `verify-`, so it writes `.plot/panels/<slug>/verify-<lens>.md` and `verify-panel.md` and never overwrites the Draft rounds' `panel.md`. A second run moves the earlier `verify-*` files to `verify-<n>-*` before it starts.

**The fold.** `foldVerification(claims, jurors)` is a domain rule. It reads every juror file once per claim label through `readJuror` and gives one line per claim:

- `supported` when every juror commits `supported` for that claim.
- `refuted` when one or more jurors commit `refuted` for that claim. The line names the lenses on each side. One refutation decides, because step 5 asks every juror to refute (Principle 12) and a person reads the issue.
- No record when `readPanel` answers `refused` for any label. The run counts as failed, and `plot-verify.mjs fold` exits non-zero and names the label and the juror.

The line carries which jurors committed `Evidence: executed`.

**Booking the record.** `perform-fs.ts` skips the `commit` and `push` write kinds (`packages/domain/src/adapters/performer/perform-fs.ts:68-69`), and the pinned tree is detached at an old commit, so neither tree can carry the record. `plot-verify.mjs record <slug>` books it as `entry/deliver.ts` books a delivery: a booking worktree on `plot/verify-<slug>` from a fresh `origin/<main>` (`trees.addBranch`), the plan written there, the paths staged through the trees port, and `commitAndPush` (`packages/board/src/server/entry/ladder.ts:123`), which pushes onto the default branch and falls back to a micro-PR on rejection. It then removes the booking worktree with its branch and both verify trees.

**The run.** `plot-fleetd` asks `verificationOf` for every plan that reads `State: Delivered` and is not a tracer plan, including a plan that `/plot-deliver` step 5 panelled at delivery: the delivery panel writes no record, so the plan reads `unverified` and the fleet verifies it again (D18). The selection is by state, not by date: every plan that reads Delivered when the switch is on is eligible, and no Released plan is. For an `unverified` or `stale` plan with no run going and a `ready` retry verdict, it starts one run through the layering rule: the fleet's controller asks the domain, and `startBoardRun` (`packages/fleet/src/shared/board-run.ts:184`) starts the process under the log kind `verify`, which joins the closed `KINDS` list (`packages/fleet/src/shared/agent-log.ts:317-329`) so the log sweep removes its files. The runner is the `Verify command` key, with a prompt naming the tools tree's *Verify mode* section, the slug and `PLOT_UNATTENDED=1`. The key is its own, as `packages/fleet/src/shared/implement-run.ts:22-42` states the rule *one capability, one key*. This repository declares it with `--model opus`, as step 5 asks a Frontier tier for the panel (`skills/plot-deliver/SKILL.md:191`). An absent key starts nothing, and the fleet's status names the key, as `interrogateAvailability` does (`interrogate.ts:40-53`).

**Capacity.** Today a verify process would count 0 against `Parallel agents`: `scaleUp` counts registered agents, idle ones included (`const running = readings.agents.length` at `packages/domain/src/workflows/assign.ts:227`), and a verify process is not a registered agent. Every registered agent holds a slot, so a fleet that auto-dispatch grew to its cap never has a free slot, and a rule that waited for one would never start a run. `fleetSize` cannot refuse one more process either: a starved machine still gets a ceiling of 1 (`packages/domain/src/rules/fleet-size.ts:88`, `:169`). The plan builds this instead:

- A domain rule `verifyStart(readings)` answers whether this pass starts a run. It starts one when `Auto-verify` is on, `Verify command` is declared, no verify run is going, the fleet is not halted (*A failed run*), an eligible plan exists, no slice is held `no-free-agent` in this pass, and `machineDefers` (`packages/domain/src/rules/auto-dispatch.ts:404`) answers null. `machineDefers` defers on a `starved` machine and honours the `Machine override` key, as automatic dispatch does. Otherwise `verifyStart` answers the first reason that held, and the fleet's status shows it.
- While a run is going, `scaleUp` counts it in `running` (`assign.ts:227` becomes registered agents plus going verify runs), so the fleet starts one slice agent fewer for its duration.
- The real count: the machine runs at most `Parallel agents` registered agents plus one verify process. The verify process holds a moderator and three `Task` jurors, so 4 Frontier contexts. A full fleet of idle agents does not stop a run; a slice that waits for a free agent does, and so does a starved machine.

**Cost.** At about 5.4 Delivered plans a day, a repository with the switch on pays about 5.4 runs a day, 4 Frontier contexts each, one `pnpm install` and two worktree adds each, and gets about 5.4 record pushes to `main` a day, the same count as delivery. Each push runs the three `main` workflows. A path filter on those workflows is outside this plan. One run at a time keeps up with 5.4 plans a day only while a run takes under about 4.4 hours. No run duration exists to measure, because no verify run exists; the one committed delivery panel recorded no time. So the fleet's state records each run's start, install seconds, end and outcome, and the fleet's status reports the waiting count, so the backlog is visible from the first day. A run that reaches `Worker bound` (28800 s here) is stopped and counts as failed.

**Refused runs.** Every refusal that survives the send-back is a failed run, so the rate decides whether the run removes work from a person. Measured on this branch: 10 moderations under `.plot/panels/` record their gate, and in all 10 every juror committed on the first run, with one label per juror. No run has gated 2 + N labels; N is the number of claims, mean 2.68 and maximum 8 over the 65 plans delivered in October. The send-back lets each juror miss labels once. The plan states no expected rate, because none is measured; the spike measures the fold's side of it and the guard below bounds the rest.

**A failed run.** A run that exits non-zero, reaches `Worker bound`, or whose fold is refused after the send-back is a failed run. The fleet records it with automatic delivery's mechanism rather than a second one. The in-flight store gains the kind `verify` beside `'dispatch' | 'deliver'` (`packages/fleet/src/shared/in-flight-store.ts:100-127`), with its own file `auto-verify-in-flight.json` holding the running pid per slug and the `failures` map. Each failure goes through `recordDeliveryFailure` and each start through `retryVerdict` (`packages/domain/src/rules/auto-deliver.ts:61-133`), with the plan's delivery commit as the reading, so one plan backs off after a failure and stops after `AUTO_DELIVER_MAX_FAILURES` = 3, and a new delivery starts its count again. The file also holds `lastSuccessAt`. Verification adds one fleet-wide stop that auto-delivery does not have: `verifyStart` answers `halted` when three failure records carry a `lastAt` later than `lastSuccessAt`. Auto-delivery's failures are a fact of one plan's git state. A verify run's common causes, a broken tools tree, an install, a panel gate the jurors miss, fail every plan alike, and a per-plan stop alone would spend up to 3 runs of 4 Frontier contexts on each Delivered plan before it stopped. `verificationRow(plan, runState)` is a domain property that puts a failed run in *Waiting on you* (`packages/board/src/app/lib/agent-rows/sections.ts:26`) with its log, its reason and the restart command `/plot-deliver --verify <slug>`. The same row names a halted fleet and the three plans. `the-board-has-three-tabs` renames that tab to Delivery and keeps the section's content (D9).

**The switch.** The `Auto-verify` key seeds an `autoVerify` field in `.plot/state/fleet-controls.json`, beside `autoDispatch` (`packages/fleet/src/shared/fleet-settings-store.ts:56-68` for the keys and defaults; the field and the exact-literal rule at `:90`, `:118`, `:139` and `:161`). It defaults OFF, by the same rule: the exact literal `true` turns it on, anything else reads as off. Off starts no run and stops none.

**Writing the record.** `PlanRecordWrite.field` (`workflows/decision.ts:76`) gains `Verified`, and `PlanRecordWrite` gains an optional `mode: 'replace'`. `withRecord` (`workflows/rendering.ts:66-93`) fills a placeholder or appends, and never replaces a filled line; with `mode: 'replace'` it replaces the filled line of that field in `## Status`, and where none exists it fills or appends as today. Only the `Verified` write passes `replace`, so every other record keeps its behaviour. A new write kind `plan-section` replaces or adds one `##` section of a plan file, with its renderer in `workflows/rendering.ts` and its performer in `adapters/performer/perform-fs.ts`. The verify workflow emits the `plan-record` write, `plan-section`, the checklist file where the checklist rule allows it, one `commit` (`plot: verify <slug>`) and one `push`, and `plot-verify.mjs record` performs the last two (*Booking the record*). A plan Released while its run was going keeps the record, so no paid run is discarded; the checklist leaves it out.

**Issues for refuted claims.** The tracker port gains `issueOpen({ title, body, labels })`, and `plot-host.sh` gains an `issue-open` op for `jira` and `github-issues`. The verify workflow resolves the port through `trackerForIssues`, which `tickets-and-stories-have-lanes` builds in its spike `feature/the-fleet-indexes-issues`, together with `trackerGitHost`; the `unaskable` reason sentence ships in its `feature/the-tracker-lists-closed-issues`, on which `feature/a-tracker-opens-an-issue` waits. The resolver follows `issueSource`: `tracker` resolves to the declared connector, which opens the issue; `git-host` resolves to the read-only `trackerGitHost`, which answers `unaskable` on `issueOpen` as it does on `statusWrite`; `nobody` resolves to `trackerNone` with the source's reason. The issue reads and the issue write therefore follow one decision. The port's doc names it as the second write Plot makes to a tracker, decided by D11, and keeps its refusal of every other widening; the five sites in Motivation say so. The order makes the open idempotent: the fold, then one `issueOpen` per refuted claim with no issue number yet, each number written to `.plot/state/verify/<slug>.json` as it returns, then the record's commit and push carrying the numbers. A push that fails is retried on the next pass from the state file, and opens nothing again. A re-verification opens nothing for a claim whose earlier line already carries a number. It finds that line by the claim's text, not its number, because `--at` can read a Changelog with a different order; a claim whose text changed is a new claim.

**No issue.** An `unaskable` answer writes the claim's line as `no issue: <reason>`, with the port's own reason. `trackerGitHost` gives *no Tracker declared; the git host's issues are read-only to Plot*. `trackerNone` gives the reason `issueSource` stated (`packages/domain/src/rules/issue-source.ts:51-63`), for example *no connector lists issues from the declared tracker `linear`*. This repository declares no `Tracker`, so its own runs open zero issues; the refuted badge, *Waiting on you* and `/plot-release`'s list carry the signal instead. Declaring `Tracker: github-issues` here is a config change for the operator, not a slice of this plan.

**The flag.** `planStatus` is not changed. A new card property `verification` carries `verificationOf`'s answer, and a refuted plan shows a *refuted* badge with the count. Before step 1, `/plot-release` lists every refuted plan and every unverified Delivered plan in the release, in both the RC and the final path, and the person decides. An unverified plan is listed because a plan Released before its run is never verified: measured over ten plans dated 2026-09-29, Delivered to Released took one to two days. A refuted plan that needs more slices goes back to Approved through the existing `/plot-reject`, and its next delivery is verified again (*A rejected plan*).

**Re-verification.** `/plot-deliver --verify <slug> [--at <sha>]` is the one path a person uses to write a record over an existing one. A person runs it after a fix lands, or to restart a failed or halted run; it clears the plan's failure record and, for a halted fleet, the halt. With no `--at`, it judges the delivery commit again; with `--at`, the named commit. It replaces the `## Verification` section and the `Verified:` line, keeps each issue number on its claim's line, and adds a Notes line naming the earlier record. The fleet never re-runs a plan whose record is current; it runs a `stale` one. Closing an issue stays a person's act (D11).

**The release checklist.** The badge must read the RC checklist from `rc` until the final release, so the file keeps one name through the RC round:

- The verify workflow rewrites `docs/releases/vnext-checklist.md` in the record's own commit, so it costs no extra push, and only while the file carries no `RC:` line.
- Its shape is `/plot-release rc`'s: one `- [ ]` item per feature or bug plan delivered since the last release tag, from its Changelog, with `verified N/N` beside it; refuted plans under a `## Refuted` heading with their issue numbers; the two sign-off lines empty.
- `/plot-release rc` with a `vnext-checklist.md` adds the RC line and the version heading to it in place and keeps its name; with none, it writes `v<version>-checklist.md` as today.
- From the RC line on, the fleet leaves the file alone, so the RC's items and ticks stay as the person left them, and the record of a plan verified during the RC round still lands in its plan.
- The final `/plot-release` renames a `vnext-checklist.md` that carries an `RC:` line to `docs/releases/v<version>-checklist.md`. The next run writes a new `vnext-checklist.md`.
- `/plot-release` with no argument looks for an open RC checklist with `docs/releases/v*-checklist.md` (`skills/plot-release/SKILL.md:191`), which matches `vnext-checklist.md`. That step reads a `vnext-checklist.md` as an RC checklist only when it carries an `RC:` line.
- `vnext` sorts after every `v<digit>` name, so `board.ts:421-422` reads it whenever it exists.

The fleet fills no sign-off line, as `/plot-release` already forbids an agent (`skills/plot-release/SKILL.md:244-246`).

**What stays human.** The fleet delivers nothing new, releases nothing, fills no sign-off, closes no issue and re-runs no plan whose record is current (D11).

## Motivation

Bitbucket Cloud allows 1,000 repository-data requests per hour per user account for a user API token, and the limit applies to the account as a whole: the bitbucket.org website fails for the same user while the limit is spent. A 429 for a user API token carries no `Retry-After` and no `X-RateLimit-*` headers (Atlassian support ticket BBS-258355, 2026-11-19; agent-skills PR #133, body section *Why*). One runaway caller can therefore lock its owner out of the website for hours, and Atlassian measured that case on a Quatico account on 2026-11-18 (Notes, *The Atlassian ticket*).

`bb` now keeps the budget for every caller on a machine (agent-skills PR #133, released in v3.22.0 on 2026-11-20 as `bb` 1.15.0, `cli/bb:5`). It records each request per account and per UTC hour, refuses above 800 requests in the last 3,600 s with exit 75 (`BB_BUDGET_DEFAULT=800`, `cli/bb:225`), and after a 429 pauses every `bb` process of the account for 300 s, doubling to 3,600 s (`bb_pause_after_429`, `cli/bb:530`).

Plot does not take part in that budget, and spends more of it than it needs to, in four ways. References are to `origin/main` at `21ae2c638`.

- **A listing asks once per branch and per state.** fleetd's full listing read (`readBitbucketListing`, `packages/fleet/src/shared/fleet-scan.ts:612`) sweeps every tracked branch once for `open` and three times for `all`, and every Bitbucket listing asks one request per state (`STATES`, `packages/domain/src/adapters/host/bitbucket-pr-listing.ts:17`; `bb_state_listing`, `skills/plot/scripts/plot-host.sh:1437`). This is the request shape that Atlassian's first recommendation names. *Requests per pass* below has the arithmetic.
- **The prediction is 12.5 times too high for a user token.** `DEFAULT_PREDICTED_HOST_LIMIT = 10_000` (`packages/domain/src/rules/declared-host-limit.ts:5`), and the shell predicts the same 10000 (`plot-host.sh:3572`). PR #3579 chose 10000 as "Atlassian's scaled cap" (`plot-config.sh:233-238`). Atlassian documents that cap only for workspace, project and repository access tokens and Forge `asApp` requests; a user API token stays at 1,000 (PR #3579 body, *Atlassian's documentation*).
- **fleetd's requests are invisible to `bb`.** Since `bitbucket-and-jira-read-in-process`, fleetd reads Bitbucket over Node HTTPS (`packages/domain/src/adapters/host/bitbucket-api.ts`). Its requests are not in `bb`'s ledger, so `bb` admits 800 more requests while fleetd spends from the same 1,000. fleetd also ignores `bb`'s pause file, and a 429 that fleetd receives starts no pause for `bb`.
- **`plot-host.sh` reads `bb`'s exit 75 as a failure in most ops.** `host_failure_kind` (`plot-host.sh:778`) maps the words "rate limited" to `throttled`, but only `pr_list_failed` (`:845`) turns that into exit 5 (`:857`). The other Bitbucket ops pass the error to `die3` (`:685`), and `refusalKindOfExit` (`packages/domain/src/adapters/host/host-shell.ts:199`) reads exit 3 as `failed`. A caller then counsels looking instead of waiting.

Operator decision, 2026-11-20: the Bitbucket default prediction is 800 an hour, the same as `bb`'s ceiling.

Operator decision, 2026-11-20: both clients apply one ceiling, read with `bb`'s rule. `BB_HOURLY_LIMIT` sets it (default 800, `0` turns it off, and an invalid value gets the answer `bb` gives). `Host rate limit` is the prediction only; it may lower the ceiling and never raise it. One rule in `rules/bb-ledger.ts` decides the ceiling and the limit reading for the in-process client and for the shell, and a reading with `remaining` 0 always carries a reset time.

Operator decision, 2026-11-20: the craftamap probe is replaced by one identity check on the cached `bb --version`, which exits 3 and names the install command. `bb --version` and `bb rate-limit --json` run as `command bb`, outside the `bb()` wrapper.

## Design

### Approach

**The `bb` formats this plan reads and writes.** Read from `cli/bb` at agent-skills `2c904ab17` (release v3.22.0). Every slice treats these as `bb`'s contract and changes none of them.

- **State directory** (`bb_state_path`, `cli/bb:295`; `bb_state_dir`, `cli/bb:312`): `$BB_STATE_DIR`, else `$XDG_STATE_HOME/bb`, else `$HOME/.local/state/bb`. An empty variable counts as unset. A missing directory is created with mode 700. An existing directory is used as it is if it is writable and searchable.
- **Account key** (`bb_account_key`, `cli/bb:335`): the first 12 hex characters of the SHA-256 of the email lowercased with `tr '[:upper:]' '[:lower:]'`. `bb` takes the email from `BB_EMAIL`, else from the keychain (`cli/bb:59-68`). `tr` lowercases by the locale's character classes, and leaves non-ASCII letters alone in the C locale.
- **Request file:** `requests-<key>-<YYYYMMDDHH>.log`, one file per UTC hour. Each request appends one line: the epoch second in decimal digits and `\n` (`bb_request_guard`, `cli/bb:607`). `bb` appends before it sends, so a request that Bitbucket answers with 429 counts. A request that `bb` refuses does not count.
- **Count** (`bb_budget_count`, `cli/bb:376`): lines of the previous and the current hour's files that are all digits, at most 12 characters, later than `now - 3600` and not later than `now`. At the ceiling `c`, the next free second is the `(n - c + 1)`-th oldest counted line plus 3600. A missing file holds no request. A file that exists and cannot be read makes the count unknown.
- **Prune** (`bb_budget_prune`, `cli/bb:399`): each guarded request deletes the request files of every account whose hour stamp is older than the previous hour. A file that stays does no harm.
- **Pause file** (`bb_pause_read`, `cli/bb:428`): `pause-<key>`, one line `<end epoch> <length s>\n`. It is valid only as exactly two whole numbers of at most 12 digits, leading zeros not counted, with a length above 0. Anything else is no pause.
- **Stale pause** (`bb_pause_is_stale`, `cli/bb:452`): a pause with more than its length plus `BB_PAUSE_SKEW=5` s left (`cli/bb:228`) counts as no pause.
- **Pause after a 429** (`bb_pause_after_429`, `cli/bb:530`): with no stored pause, or one that ended 3,600 s ago or longer, the length is 300 s. One that ended less than 3,600 s ago doubles its length, at most 3,600 s. A numeric `Retry-After` raises the length to at least its value. The end is `now + length`. A pause that is still active keeps the later of its end and `now + Retry-After` (300 s without one), and the larger length.
- **Pause write** (`bb_pause_write`, `cli/bb:488`): the line goes to `pause-<key>.XXXXXX` in the same directory and is renamed into place. Just before the rename the writer reads the stored pause again and keeps a later, non-stale end and the larger length, so parallel 429s cannot shorten a pause.
- **Ceiling** (`bb_hourly_limit`, `cli/bb:355`): `BB_HOURLY_LIMIT`, else 800; `0` turns the ceiling off and still records; more than 9 digits reads as 999999999; any other value prints `error: BB_HOURLY_LIMIT must be a whole number, got '<value>'` and exits 1 (`cli/bb:358-360`).
- **Refusal words:** at the ceiling `error: rate limited — <n> requests in the last hour from this machine; next request at <HH:MM:SSZ> (in <s> s)`; during a pause `error: rate limited — bb paused until <HH:MM:SSZ> after Bitbucket refused a request (in <s> s)`; after a 429 `error: rate limited — <message>` (`cli/bb:196-200`), and on a later page `error: rate limited after <rows> rows — <message>` (`cli/bb:719-724`). The words avoid the digits 429 on purpose (`cli/bb:182-188`).
- **Fail open:** an unusable state directory, an unreadable request file, a garbage line, a line from the future and a stale pause never block a request. `bb` warns once per process and sends.
- **`bb rate-limit --json`** (`cmd_rate_limit`, `cli/bb:3228`): prints `{requests, ceiling, paused_until, wait_seconds}` and sends nothing. `requests` is null where the count is unknown, `ceiling` is null with the ceiling off, `paused_until` is epoch seconds or null, and `wait_seconds` is 0 when a request can go out now. It exits 75 during a pause or at the ceiling and 0 otherwise.

**Measured on this machine, 2026-11-20:** `/opt/homebrew/bin/bb` reports `bb 1.13.0 (quatico-bb — brew install quatico-solutions/tap/quatico-bb)` and answers `bb rate-limit --json` with `unknown command: rate-limit` and exit 1. A `bb` older than 1.15.0 is therefore the normal case until the tap update reaches every machine. With it, only fleetd's requests are counted, and slice 4 keeps today's limit line.

### Requests per pass

Counted from the code on `origin/main` at `21ae2c638`, for a repository with N = 53 tracked branches, R pull requests in all states, O open pull requests, and one page per branch query. fleetd's in-process listing (`bitbucket-pr-listing.ts`) sends the same requests as `plot-host.sh pr-list`, and `corpus/bitbucket-pr-listing.corpus.test.ts` holds the two to one answer.

| Path | Today | After slice 1 |
|---|---|---|
| fleetd scan, full read (`fleet-scan.ts:620-623`) | `open` sweep 53 × 1 + `all` sweep 53 × 3 = **212** | ⌈R / 50⌉ + ⌈O / 50⌉ |
| fleetd scan, delta (`fleet-scan.ts:625-628`) | 1 `open` page + 3 windowed states = **4** | ⌈O / 50⌉ + 1 |
| fleetd scan, a refused delta and its full retry (`:631-634`) | 4 + 212 = **216**, priced as 4 | ⌈O / 50⌉ + 1 + full |
| PR pass, delta (`pr-refresh.ts:297`) | 3 windowed states = **3** | 1 |
| `pr-list --branch` × N (`bb_branch_sweep`, `plot-host.sh:1251`) | N × states: **159** for `all` | N = **53** |
| `pr-state <branch>` (`plot-host.sh:4108-4116`) | 1 to 3 | 1 |
| idle pass `pr-merged`, per unsettled worktree branch (`IDLE_MERGE_REASK_MS`, `rules/slice-idle.ts:205`) | 1 per 10 min | unchanged |

**The cadence keeps a listing's share near 60 requests an hour.** `listingSpend` starts from `LISTING_REFRESH_MS` (60 s, `fleet-scan.ts:67`) times the listing's price (`listing-spend.ts:81`), so a delta priced 4 runs every 240 s: 15 listings × 4 = 60 requests an hour. The PR pass spaces its 3 requests 180 s apart, also 60 an hour. A full read is due once per 24 h (`PR_FULL_READ_MS`, `pr-refresh.ts:379`). `scanListingCost` (`fleet-scan.ts:255`) prices a full read 53 × 3 = 159, 53 below the 212 it sends.

**A refused delta is where today's cost grows without bound.** A refused delta retries as a full read in the same pass and is priced as a delta. The delta's open half asks `--limit 49` (`fleet-scan.ts:626`), and a page at that cap makes no whole-page claim, so `foldScanListing` refuses it (`no-whole-page-claim`, `rules/scan-listing.ts:312`). In a repository with 49 or more open pull requests, every pass therefore sends 216 requests every 240 s: **3,240 requests an hour** before any stretch by the observed rate. With the 10000 prediction no gate stops it. The idle pass adds up to 53 × 6 = 318 an hour where no worktree branch has a settled MERGED row.

**Expected after slice 1, at today's cadence:** the scan listing and the PR pass stay near 60 requests an hour each, because the cadence is derived from the price. A refused delta costs ⌈O / 50⌉ + 1 + ⌈R / 50⌉ + ⌈O / 50⌉ instead of 216; for R = 300 and O = 60 that is 3 + 8 = 11 requests, about 165 an hour if every delta refuses. The 49-open-PR refusal ends, because the open half walks every page and claims whole by the host's `size`. The total for 53 branches is about 120 requests an hour with every idle branch settled, and at most about 440 with none settled, against at least 3,600 today in the refusal case.

### Slice design

**Slice 1, one listing request.** Every Bitbucket pull request listing asks all its states in one paginated request, and a listing never asks once per branch and per state.

- **The plain listing** asks `GET /2.0/repositories/<ws>/<repo>/pullrequests?state=OPEN&state=MERGED&state=DECLINED&pagelen=50&fields=…`, Atlassian's first recommendation, and follows `next` to the end or to the row limit. The comment *THE STATES STAY SEPARATE CALLS* (`plot-host.sh:1416`) measured that one union lost 12 of 14 declined rows; it read one page only. A walk that follows `next` to the end has no such loss, so the slice replaces that comment with the walk's rule. A walk that stops at a row limit claims whole for no state; the PR pass's full read sets its limit to 3 × `PR_LIMIT` (`pr-refresh.ts:351`), so it reads at least the rows that three per-state reads of 1,000 read.
- **A query with `q=`** puts the states inside it as `(state="OPEN" OR state="MERGED" OR state="DECLINED")`, because `q=` overrides a `state=` parameter (`plot-host.sh:1316-1319`). This covers the window (`bb_window_listing`, `:1338`; `windowState`, `bitbucket-pr-listing.ts:156`) and the branch query (`bb_branch_query`, `:1179`; `sweepState`, `bitbucket-pr-listing.ts:182`).
- **The `fields` filter** names `next`, `size` and each `values.*` field that the row projection reads (`bb_state_row` and the `pr-list` arm's projection in `plot-host.sh`; `project` in `bitbucket-pr-listing.ts`). A test asserts that every field the projection reads is in the filter, so a missing field fails a test and never reads as empty.
- **fleetd's full read stops sweeping.** `readBitbucketListing`'s full read becomes one all-state walk to the end plus the open walk, and keeps only the rows of tracked branches, so the rendered listing equals today's sweep listing on the same fixture. The delta's open half walks every page and claims whole by `size`, as `bb_window_listing` does, so 49 or more open pull requests no longer refuse every delta.
- **The sweep is bounded.** `pr-list --branch` asks one request per branch for all asked states, and `pr-state <branch>` asks one request and keeps its rank (open, then merged, then declined) over the rows it gets.
- **The price matches the requests.** `scanListingCost` prices a Bitbucket full read as ⌈R / 50⌉ + ⌈O / 50⌉ from the last listing's row counts (2 where none is held) and a delta as ⌈O / 50⌉ + 1; `PR_REQUESTS_PER_REFRESH.bitbucket` becomes 1, and its comment (`pr-refresh.ts:264-296`) states the new arithmetic. The PR pass's cadence is derived from that number, so it stays near 60 requests an hour.
- **The request-count test.** A stub host counts requests per pass for N = 1, 53 and 200 tracked branches: a full read sends ⌈R / 50⌉ + ⌈O / 50⌉ and a delta ⌈O / 50⌉ + 1, independent of N. A shell test counts `api` calls of a stub `bb` for `pr-list --state all`, `pr-list --branch` × 53 and `pr-state`. `corpus/bitbucket-pr-listing.corpus.test.ts` keeps the shell and the in-process listing to one answer.
- **The shell-lines ratchet.** `scripts/check-shell-lines.sh pr` must not read higher than at the merge base; the per-state loops in `pr_list_states`' Bitbucket callers and `bb_branch_sweep`'s state handling shrink.

**Slice 2, the default.** `DEFAULT_PREDICTED_HOST_LIMIT` becomes 800, and `budget_reading`'s Bitbucket arm (`plot-host.sh:3572`) prints 800 where the key is unset or does not read as a limit. `corpus/declared-host-limit.corpus.test.ts` keeps holding `declaredHostLimit` and the shell to one answer; its "not vacuous" check (`:63-66`) gains `expect(shellValues).toContain('800')`, so the empty case is proved too. `Host rate limit` keeps its precedence: `X-RateLimit-Limit` on a reply, then the key, then 800. The comments and docs that name 10000 as the default change: `bitbucket-api.ts:84` and `:165`, `plot-host.sh:3557` and `:5718`, and `plot-config.sh:233-238`, which also says that neither client sends an access token today, so a value above 800 has no effect yet. These tests pin 10000 as the default and change to 800: `packages/domain/test/declared-host-limit.test.ts:10-16`, `packages/domain/test/host-reads.test.ts:161` and `:179`, `packages/domain/test/bitbucket-api.test.ts:272` (the name), `:286` and `:350` (the values), and `test/reconcile/host.test.mjs:7120`. The 10_000 values at `bitbucket-api.test.ts:320`, `:328`, `:336` and `:341`, and those in `budget.test.ts` and `concurrency.test.ts`, are stated headers and stay.

**Slice 3, one ledger.** The in-process client takes part in `bb`'s budget as one more `bb` caller.

- **The ceiling.** `rules/bb-ledger.ts` exports `bbCeiling(hourlyLimit, declared)`. It reads `BB_HOURLY_LIMIT` with `bb`'s rule: unset or empty is 800, `0` is off, more than 9 digits is 999999999, and any other value is invalid. The ceiling is the smaller of that number and the declared `Host rate limit` where the key declares one; the default prediction of 800 does not lower it. With `BB_HOURLY_LIMIT=0` and no declared key there is no ceiling. An invalid value refuses every request as `failed`, with `bb`'s words `error: BB_HOURLY_LIMIT must be a whole number, got '<value>'`, as `bb` exits 1 on every command. So fleetd never applies a higher ceiling than `bb`, and an operator who sets `Host rate limit` above 800 cannot lock `bb` out of the shared ledger.
- **The limit reading.** `bbLimitReading({requests, ceiling, pausedUntil, waitSeconds}, declared, now)` in the same file answers a `LimitReading` with basis `predicted`: `limit` = the ceiling (the prediction where the ceiling is off), `remaining` = `limit` − `requests`, floored at 0, or null where `requests` is null or the ceiling is off. Where `remaining` is 0, `resetAt` is the pause's end where one holds, else `now + waitSeconds` where that is above 0, else the next free second by this ceiling where the request lines are known (the client), else `now + 3600` s (the shell, where `bb`'s JSON carries no line times and a declared limit below `bb`'s ceiling stops first). `remaining` 0 never carries a null reset, so `rateLimitOf` (`packages/board/src/app/lib/agent-rows/delivery-readings.ts:99`) cannot stick at `exhausted`. Unit cases cover `requests: null`, the ceiling off, declared below and above the ceiling, a pause, and `remaining` 0 with `waitSeconds` 0.
- **Before each request**, the client reads the pause file of its account key. While a non-stale pause holds it sends nothing and answers `throttled` with `waitMs` set to the pause's end minus now. Next it counts the last 3,600 s; at the ceiling it sends nothing and answers `throttled` with `waitMs` set to the next free second minus now. Otherwise it appends one line to the current hour's request file, prunes as `bb` does, and sends. The guard wraps each `transport.exchange` call, so the second exchange after a 401 in `request` (`bitbucket-api.ts`) is guarded and counted too. A refused request appends no line to either ledger, so the guard runs before `connectorHttps.exchange` takes a slot and records a `BudgetEntry`.
- **The refusal's words are `bb`'s words.** A ceiling refusal says `rate limited — <n> requests in the last hour from this machine; next request at <HH:MM:SSZ> (in <s> s)`, and a pause refusal says `rate limited — bb paused until <HH:MM:SSZ> after Bitbucket refused a request (in <s> s)`. A 429 keeps `throttledOf`'s kind and words (`connector-https.ts:126`).
- **The board names the cause.** `bbThrottleCause(said)` in `rules/bb-ledger.ts` answers `ceiling`, `paused` or `host` from those fixed phrases, for the client's words and for `bb`'s stderr alike. The quota sentence (`host-notes.ts:356`) and the fleet-scan sentence (`host-notes.ts:499`) read it: `ceiling` says this machine's hourly ceiling is spent and names the next free time, `paused` says `bb` is paused after a rate limit and names its end, and `host` keeps today's words. A unit test covers each sentence.
- **After a 429**, the client writes or extends the pause with `bb`'s rule and `bb`'s merge-before-rename, and its `throttled` refusal carries the stored pause's end as `waitMs`.
- **The limit it records.** `spend` (`bitbucket-api.ts`) records `bbLimitReading` over the count after this request. A reply with a numeric `X-RateLimit-Limit` keeps basis `actual`, as PR #3579 settled.
- **The account key.** `bb`'s ledger is keyed by the user, because Bitbucket's limit is per user. The client computes the key from the email it already resolved (`BB_EMAIL` from the environment or `.env`, `bitbucket-api.ts`), lowercasing ASCII `A`–`Z` only, so fleetd and `bb` meet in one file when both read the same email. Plot's own `budget_account` for Bitbucket stays the workspace (`rules/bitbucket-budget-account.ts`, `plot-host.sh:3469`): it keys Plot's `budget.tsv`, a different ledger, and this plan changes neither key. Where the client's email differs from the keychain email that `bb` reads, the two write two ledgers. The client logs once per process the key, the request file it writes (`<state dir>/requests-<key>-<YYYYMMDDHH>.log`) and its own count, so a person can compare the file with `ls` of that directory and the count with `bb rate-limit`'s `requests`.
- **Concurrency.** A request line is at most 13 bytes, below `PIPE_BUF` (512 bytes on macOS, 4,096 on Linux), and goes out as one `O_APPEND` write, so parallel writers in fleetd and in `bb` never interleave a line. The pause file is replaced by a rename only. There is no lock, as in `bb`: parallel callers can pass the ceiling by a few requests, and the 200 requests between 800 and 1,000 absorb that.
- **Fail open, as `bb` does.** An unusable state directory, an unreadable request file, a failed append or a failed pause write sends the request with no budget and logs one warning per process. A stale or garbage pause file is no pause.
- **Test isolation.** The adapter reads the state path from `options.env` and never from `process.env`. Every existing `bitbucketApi(...)` construction in a test (`packages/domain/test/fixtures/bitbucket-replay.ts:117`, `census/sandbox.unit.test.ts:176` and `:195`, and the domain tests) passes a temp ledger. The census sandbox adds `BB_STATE_DIR`, `XDG_STATE_HOME` and `BB_HOURLY_LIMIT` to the variables it deletes (`packages/fleet/test/census/sandbox.ts:297-301`). A test that answers 429 then cannot write a pause file into a person's real `bb` state.
- **Tests the slice names.** Six writers append in parallel and no line tears, after `test/reconcile/budget.test.mjs:337`. The request and pause lines are byte-exact (`<epoch>\n`, `<end> <len>\n`). Each fail-open path sends exactly one request and logs one warning per process. `delivery-readings.test.ts` and the `machine-health` tests gain a predicted Bitbucket bucket that is free, one at 0 with a reset, and a GitHub bucket whose Delivery-tab reading does not change.

**The layering decision for slice 3: a domain rule plus an adapter.** The format and every verdict are rules, and the file IO is an adapter, because *The Layering Rule* says no domain behaviour lives outside the domain and the purity gate (`.github/workflows/ci.yml:1659-1678`) lets the domain import only `zod`. So `packages/domain/src/rules/bb-ledger.ts` holds pure functions over values: the hour stamps of a second, the lowercase step of the account key, the state-path choice, the ceiling, the count and next free second over the two files' text, the pause parsed from its text, the stale test, the pause after a 429 from the stored pause, the merge before the rename, the guard's verdict (`send`, `paused`, `ceiling`), the limit reading and the throttle cause. `packages/domain/src/adapters/host/bb-ledger-file.ts` resolves the state directory from the environment it is given, hashes the key with `node:crypto`, reads, appends, prunes and renames. `bitbucketApi` takes it as one more seam with a production default, the way it takes `budget` and `slots` (`bitbucket-api.ts:74-77`). It is not a new port: the ledger is reached only by an adapter, and the domain decides from the readings it is given, which is the *readings as values* shape of the layering rule. The precedent is `adapters/build/jenkins-api.ts`, which reads and writes `jen`'s token store under `JEN_CONFIG_DIR` with a temp file and a rename (`jenkins-api.ts:225-319`).

### Open Questions

- [ ] **The access-token path.** Atlassian's fourth recommendation is a credential of its own for automation, a repository or workspace access token, so that automation cannot lock the owner out of the website. - [ ] **A `bb` call that `bb` refused still writes a row to Plot's `budget.tsv`.** The `bb()` wrapper records a call for every exit (`plot-host.sh:3846-3853`), and exit 75 is both "sent and refused with 429" and "never sent".

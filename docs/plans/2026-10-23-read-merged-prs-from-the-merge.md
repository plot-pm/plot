# Bitbucket: an old merged PR stops reading as no PR

> On Bitbucket the host lists one page of 50 PRs per state, and Plot reads that page as the whole answer. This plan makes the Bitbucket listing follow every page up to the caller's limit, makes the wave gate read up to 20 000 merges, and makes `/plot-deliver` step 4 ask the host about each unresolved branch by name. The *state unknown* note on three July plans on ewz-kus-portal comes from HTTP 429 (#333), and this plan leaves it out of scope.

## Motivation

Measured 2026-10-23 on ewz-kus-portal (Plot 2.28.0, bb 1.11.2): `plot-host.sh pr-list --state merged --limit 1000` returns 50 rows and prints *"possibly truncated (50 rows, requested limit 1000 unprovable)"*. Three Delivered July plans show under *Not started* with *state unknown — the host's answer is incomplete*, while the board keeps hitting HTTP 429 (#333).

Read on `origin/main` at `8f87cb9c4` (2026-10-26), the short listing is read as a whole one:

- `bb_state_listing` (`plot-host.sh:1393-1406`) asks one page of `pagelen=50` per state and never follows `next`.
- `pr_list_report_truncation` (`plot-host.sh:3250`) prints *possibly truncated* on stderr and returns 0. `pr_list_states` returns 0 when every state answered (`plot-host.sh:1544`).
- `scripts-shell.ts:99` maps exit 0 to `answered`. `answerKind` (`rules/pr-index.ts:90-95`) then returns the window's kind, a full read folds as `whole`, and `wholenessAfter` writes `complete: true` (`rules/pr-index.ts:268-269`).
- The Delivered plan `bitbucket-and-github-listings-read-one` (#2484) made `bb_branch_query`, `pr-merged-heads` and the `pr-review` arm follow `next`. It did not change `bb_state_listing`.
- #2400 (`plot-host-bitbucket-pr-list-reads`) planned to page `bb_state_listing` through `bb pr list --all`. It was delivered with no code on 2026-10-26: PR #2422 merged at 14:19:47Z holding only its claim and the blocker commit `f576060de`, and `b2df79eaf` delivered it. `6666041ff` rejected it, and fleetd's auto-deliver delivered it again 43 s later in `c67b5cd1f` (#2713). On main #2400 is Delivered, carries a `Rejected:` record, and its Changelog line describes paging through `bb pr list --all`, which is not on main. This plan's slice 1 does the paging and supersedes #2400.
- The Released plan `2026-09-20-a-pr-list-reads-every-page` (#333, 2.19.0) rejected paging the listing in its section *Why not page the list*: a paged refresh cost about 21 requests, and the derived cadence stretched the refresh interval from 240 s to 1260 s. Since then the refresh reads deltas through `bb_window_listing` and makes a full read once per 24 h (`PR_FULL_READ_MS`, `pr-refresh.ts:331`). A paged full read therefore adds 21 requests per day, and `PR_REQUESTS_PER_REFRESH.bitbucket` stays 3 (Cost). The per-branch query that #333 shipped stays, and slice 3 uses it.

Measured 2026-10-26 on ewz-kus-portal (read-only `bb api` GET, bb 1.11.2): the unfiltered listing holds 10 open, 3527 merged and 147 declined PRs (`size` at `pagelen=1`). The first `state=MERGED&pagelen=50` page is sorted by `updated_on`, newest first, and not by PR number: PR #3725 down to #3678, oldest `updated_on` 2026-10-02.

Delivery has the same gap. For a branch the PR index cannot answer, `plot-impl-status.sh:269` asks `pr-list --state merged --limit 500`. On Bitbucket that call returns one page of 50 rows.

The merge log is not the fix for the three July plans. Measured 2026-10-26 on ewz-kus-portal (read-only, `origin/develop` as fetched 2026-10-23): the Delivered plans `ewzkus-3518-invoice-aggregation`, `ewzkus-3711-sammelrechnungen-anzeige` and `ewzkus-3712-liegenschaft-suche` name slice PRs #3488, #3489 and #3490. All 11 slice branches of the July plans have no ref on origin, so the scan reads them in the refless arm (`branch-state.ts:238-268`). That arm answers `unknown` only while the host is throttled (`branch-state.ts:259-267`). The *state unknown* note on those plans therefore comes from HTTP 429.

A Bitbucket merge commit carries the subject `Merged in <branch> (pull request #N)`. On ewz-kus-portal, `git log origin/develop --merges` reads 2340 merges in 0.02 s, and the scan's walk stops at 2000 (`plot-fleet-scan.sh:472`).

## Design

### Approach

1. **The Bitbucket listing follows `next`.** `bb_state_listing` asks `bb api` with `pagelen=50` through `_bb_paged_walk` (`plot-host.sh:1132-1148`) in a row-limit mode. The walk follows each page's `next` link and stops when it holds `--limit` rows or a page has no `next`, so it reads at most `ceil(limit / 50)` pages. It trims the last page to the limit. A call with no `--limit` reads one page, as today. The walk writes the `next` reading of the page where it stopped to `BB_LIST_NEXT_FILE`, as `bb_state_listing` does today (`plot-host.sh:1404`), and writes `1` when it trimmed that page. So `pr_list_report_truncation` prints *page complete* only for a state that ended before the limit, and *possibly truncated* for a state that reached it, also where the limit is not a multiple of 50 (`plot-host.sh:3262-3265` compares no row count with the limit). The `bitbucket ignores --limit` notice (`plot-host.sh:4771`) goes.
2. **Exit codes keep their meanings.** A walk that reaches the limit exits 0 and prints no line of its own; `pr_list_report_truncation` prints the *possibly truncated* line. This is what the GitHub arm does at its limit (`plot-host.sh:4735-4736`). It departs from the rule at `plot-host.sh:1097-1103`, which makes a walk stopped by its page cap return exit 3, so that "the answer may be short" has one exit code. The departure holds for the row-limit mode only: a listing that stops at the caller's limit returned the answer the caller asked for, and the *possibly truncated* line says that more rows exist. Without a row limit the walk keeps its page cap (`BB_BRANCH_QUERY_PAGE_CAP`, `plot-host.sh:1193`) and exit 3, so `bb_branch_query` and the `pr-review` reads (`plot-host.sh:4309-4311`) do not change. Slice 1 adds the departure to the walk's header. A page that fails after page 1 fails its whole state with the host's own exit code and prints none of that state's rows, as `_bb_paged_walk` does. `pr_list_states` then counts that state as failed: exit `PR_LIST_PARTIAL_RC` (7, `plot-host.sh:935`) when another state answered, and the failure's own code when none did. That is the meaning `plot-host.sh:960-970` already documents. The refresh folds exit 7 as `partial`, and `wholenessAfter` writes `complete: false` (`rules/pr-index.ts:268`). Slice 1 makes the next full read wait out the failure grace (Cost).
3. **The queue keeps 500 on GitHub and asks 50 on Bitbucket.** `registryd-main.ts:791` asks `prList('merged', 500)` on every 60 s tick (`registryd.ts:80`). After step 1 a 500-row Bitbucket listing costs 10 requests per tick. Slice 1 makes the limit follow the backend word, which `host.backend()` already gives `prIndexRows` (`registryd-main.ts:846`): 500 on GitHub, 50 on Bitbucket. On Bitbucket the queue then reads the same 50 rows as today for the same 1 request. On GitHub nothing changes: one `gh` call either way, and the 500 rows are the fix that `registryd-main.ts:784-789` records for #707 and #710. The index's MERGED rows join the queue's set on every pass (`queue-reading.ts:331-333`). On GitHub the index holds the 1000 most recent PRs across all states, because the full read asks `--state all --limit 1000` in one call (`pr-refresh.ts:1499-1500`). On Bitbucket, after step 1, it holds up to 1000 PRs per state.
   - **An empty or old-version index.** `prIndexRows` returns `[]` when the store is missing or its `v` is not `PR_INDEX_VERSION` (5, `entities/pr-index.ts:12`; `registryd-main.ts:843-849`). The queue then reads the listing alone. A listing with no refusal reads as whole (`registryd-main.ts:806-807`), so `landedWithoutListing` does not run (`queue-reading.ts:335-337`). On GitHub the queue holds 500 rows, as today. On Bitbucket it holds 50 rows, as today, and a slice whose predecessor merged outside them stays on `waits` until fleetd's next full read writes a v5 store; `prWindowFor` returns a full read for a store it cannot read (`rules/pr-index.ts:392`). This is the #707/#1454 failure, and slice 1 makes it no worse on either host. Slice 1 tests it.
4. **The wave gate reads up to 20 000 merges.** `MERGE_SCAN_LIMIT` (`plot-fleet-scan.sh:472`), `MERGE_WALK_LIMIT` (`registryd-main.ts:599`) and the corpus default `readMergeSubjects(…, limit = 2000)` (`packages/domain/corpus/production.ts:286-290`) rise from 2000 to 20 000. The scan keeps its saturation report (`plot-fleet-scan.sh:481-483`). `registryd-main.ts` has no saturation report, and this plan adds none: at 20 000 the cap is 8.5 times the largest measured log. The walk feeds the wave gate only, and its reading is never written to the PR index.
5. **Step 4 asks by name, once.** `plot-impl-status.sh:265-271` passes every un-annotated branch that the index could not answer as a repeated `--branch` to its one `pr-list --state merged --limit 500` call. On Bitbucket, `--branch` runs `bb_branch_sweep` (`plot-host.sh:1222`): one `bb_branch_query` per branch, each following `next` since #2573. On GitHub, one branch maps to `--head` (`plot-host.sh:4488`), and several branches keep the listing. The helper still makes one `pr-list` call per plan. On Bitbucket that call costs one request per branch, so the header's *constant in branch count* (`plot-impl-status.sh:253-254`) becomes false, and slice 3 rewrites it.

### Deliver Gate Overlap

The deliver controller already asks the host by name: `deliverabilityOf` (`packages/board/src/server/controllers/deliverability.ts:182`) calls `Host.prMerged` for each branch the index cannot answer, and `plot-host.sh pr-merged` follows `next`. The gate therefore finds an older merged PR today. Slice 3 changes the step-4 report only.

Slice 3 keeps a shell lookup, for two reasons:

- Step 4 reports PR numbers. Step 5's jurors diff each PR, and the optional back-fill writes `→ #N` (`skills/plot-deliver/SKILL.md:124-150`). `plot-ask.mjs deliverable` returns `merged`, `unmerged` and `deferred` and no PR number (`DeliverabilityAnswer`, `controllers/deliverability.ts:14-38`).
- The slice adds no rule. The host's `MERGED` answer decides, as today and as *One Answer To "Did This Land"* requires. The slice changes which host query the existing lookup sends.

The duplicate is the host request, not a rule: on Bitbucket a delivery asks each unresolved branch twice, once in step 4 and once in the controller. Cost counts both.

### Merge-Subject Rows

This plan writes no merge-subject row into the PR index, and `PR_INDEX_VERSION` stays 5 (`entities/pr-index.ts:12`). Three facts decide it:

- *Answers, never verdicts* (CLAUDE.md, *A Decision Reads The Index*): the index holds bought answers. A merge-subject reading costs 0.02 s of local git on the largest measured estate, so a stored copy is a cache that git can reach.
- Every reader of a terminal row decides something destructive or feeds such a decision. `pr-index-lookup-answer.ts:61` answers `plot-impl-status.sh` for `/plot-deliver`. `packages/board/src/server/controllers/deliverability.ts:167` answers the deliver controller. `merged-desk.ts:33-34` sets desk state in `drop.ts` and `registry.ts`. A subject row in `rows` reaches all three through `isTerminalRow` (`merged-row.ts:17-18`), and `docs/domain/merge-subject.md:53-62` forbids a subject in a destructive decision.
- The three July plans in Motivation left no subject, so subject rows would not answer them.

With no subject rows, the daily `whole` fold (`rules/pr-index.ts:146-154`, `PR_FULL_READ_MS` at `pr-refresh.ts:331`) has no row of this plan to erase. A `whole` fold re-lists every row once per 24 hours, and that fold is the one answer that sees a deleted PR (`rules/pr-index.ts:149-151`).

If the operator wants subject rows in the store regardless, the mechanism is a v6 store with a separate `subjects` array beside `rows`, re-derived by `pr-refresh.ts` on every fold. `rows` keeps its contract, *"exactly what the host answered"*, and no existing reader sees a subject. Open Points hold this decision.

- **The daily full read spends 24 requests in one refresh.** `PR_REQUESTS_PER_REFRESH.bitbucket` stays 3 (`pr-refresh.ts:249`). It prices a request that every refresh makes, and the full read runs once in about 480 refreshes. Declaring 24 would stretch every refresh from 180 s to 24 minutes to pay for one call a day. The same rule keeps the pending-check re-ask out of the table (`pr-refresh.ts:194-203`). Per day the refresh spends 1440 + 21 requests instead of 1440.
- **A `partial` full read waits.** Today `prWindowFor` returns a full read for an incomplete store (`rules/pr-index.ts:394`) before it reads the failure grace (`:409-410`). A partial answer is not thrown (`pr-refresh.ts:1530`), so it sets no `prFullReadFailedAt` (`:1811`) and gets no back-off (`:1786-1792`). After paging, a state that keeps failing would cost up to 24 requests every 180 s instead of 3. Slice 1 therefore records `prFullReadFailedAt` for a partial full read, applies the rate-limit back-off when the missing state was throttled, and makes `prWindowFor` read the grace before it returns a full read for an incomplete store: inside the grace, a store with a watermark gets a delta. While one state keeps failing, an hour then costs one full read and 19 deltas: 24 + 19 × 3 = 81 requests, against 60 today.
- **One 429 empties a state.** A page that fails fails its whole state (Approach 2). The cost juror measured HTTP 429 on 6 of 7 listing GETs on ewz-kus-portal at about 14:56Z on 2026-10-26, while the single-PR endpoint answered. On a throttled account the paged walk fails its merged state, and the full read folds `partial` and waits as above.
- **A state above the limit still records `complete: true`.** ewz-kus-portal's 3527 merged PRs exceed `PR_LIMIT = 1000` (`pr-refresh.ts:303`). The walk stops at 1000 rows, prints *possibly truncated*, and exits 0, so the full read folds as `whole`. The store then runs deltas and reads in full once per 24 h, at 24 requests. The GitHub arm does the same at 1000 today. Open Points hold this.
- On Bitbucket, `--rich-open` only sets `rich=1` (`plot-host.sh:4521-4572`). A full read folds mergeability for each `OPEN` row: one `git fetch` per base and one `merge-tree` per open PR (`plot-host.sh:2117-2131`). Paging adds no open row on ewz-kus-portal, where the 10 open PRs fit one page.
- Slice 2: 0 requests. The walk costs 0.02 s at 2340 merges.
- Slice 3: on Bitbucket, one `/plot-deliver` run asks 1 request per unresolved un-annotated branch in step 4, plus one `pr-state` call per branch that resolves (`plot-impl-status.sh:334`), and the controller asks the same branches again through `Host.prMerged`. On GitHub, step 4 stays 1 call.
- **The review-bypass section reads every listed PR's review.** `readMerged` (`review-bypass.ts:42-63`) calls `prReview` for each listed merged PR, and the rule applies `since` only afterwards (`packages/domain/src/rules/review-bypass.ts:46-48`). Slice 1 makes `readMerged` skip a PR whose `mergedAt` is before `since` before it calls `prReview`. On Bitbucket `mergedAt` comes from `updated_on`, which is never earlier than the merge, so the skip never drops a PR merged after `since`. ewz-kus-portal does not set `Review required since`, so the measured estate does not run this section.

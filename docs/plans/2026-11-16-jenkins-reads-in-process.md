# Jenkins reads in-process

> fleetd reads Jenkins over Node's HTTPS client inside the build connector, not through one `plot-host.sh` and one `jen` process tree per question: the branch-colour map and the sha lookups that the rich PR read overlays on its checks, and the build port's three reads. The connector keeps its own credentials, its own bearer refresh, its own account and its own budget. Every rule copied out of `plot-host.sh` or `jen` is a declared duplicate with a corpus test, and `PLOT_HOST_TRANSPORT=shell` is the way back.

### Credentials, measured 2026-11-16

- `jen` 0.4.0 sends two headers (`jen_auth_args`, `jen:307-317`): `Authorization: Bearer <keycloak access token>` for the oauth2-proxy, and `X-Jenkins-Authorization: Basic <user:api-token>` for Jenkins' own realm. `jen` adds the second header only where a user and a token both exist.
- The bearer comes from `JEN_TOKEN`, or from the secret `keycloak-token`: a JSON blob with `access_token`, `refresh_token` and `expires_at` (`jen_save_token`, `jen:150-155`, which stores `now + (expires_in // 300) − 30`). Where `expires_at` has passed, `jen` posts `grant_type=refresh_token` with `client_id=cli` to `${JEN_REALM_URL}/protocol/openid-connect/token` and stores the answer (`jen:185-200`). `JEN_REALM_URL` reads the environment and defaults to `https://id.quatico.dev/realms/quatico` (`jen:28`). `jen` passes the refresh token as a `curl -d` argument (`jen:194-197`), so any process on the machine can read it from `ps` while that `curl` runs.
- The bearer on this machine lives 300 s (`exp − iat` of the access token's claims; `azp: cli`). `jen` stores `expires_at` 30 s early (`jen:155`), so a long-lived reader refreshes about every 270 s.
- The Jenkins user and API token come from `JENKINS_USER` and `JENKINS_API_TOKEN`, or from the per-instance secrets `jenkins-user:<key>` and `jenkins-token:<key>` (`jen_jenkins_user`, `jen_jenkins_token`, `jen:269-270`). `<key>` is `jen_key_for` (`jen:81`): the resolved URL's lowercased host and port (`jen_url_host`, `jen:66`). A legacy key under the raw slug migrates on read (`jen_migrate_instance_keys`, `jen:230-260`). The bearer is realm-wide; the API token is per instance.
- The secret store is the macOS Keychain service `jen` by default where `security` exists, a file per key under `$JEN_CONFIG_DIR` with `JEN_SECRET_BACKEND=file`, and nothing on the `env` backend (`jen_secret_backend`, `jen:115-118`). `JEN_CONFIG_DIR` defaults to `${XDG_CONFIG_HOME:-$HOME/.config}/jen` (`jen:31`). The file for a key maps `:` and `/` to `_` and appends `.secret` (`jen_secret_file`, `jen:121`). `jen` writes it with `( umask 077; printf '%s' "$2" > file )` (`jen:134`): a truncate and a write in place, with no lock and no rename. This machine uses the Keychain (`jen -I apps auth status`: `Secret store: keychain`, `Jenkins auth: OK`), and `~/.config/jen` does not exist.
- The instance URL: `JEN_URL` overrides every instance (`jen_instance_url`, `jen:85-88`). Otherwise a value with a scheme passes through, a value with a dot is a host under `https://`, and a slug expands through `JEN_URL_PATTERN` (`jen_url_for`, `jen:50-60`). `jen:6` assigns `JEN_URL_PATTERN` as a constant, `https://jenkins-ci-{slug}.internal.quatico.dev`, so the environment cannot change it. Plot reads the slug as the part of `Jenkins instance` before the first `/`, and the job path as the rest (`plot-host.sh:1770-1779`, `:1895-1899`, `:2027`). `jen_job_path` turns `a/b` into `/job/a/job/b` and percent-encodes a branch through `jq @uri` (`jen:475-498`). `job list --json` prints `.jobs` of `api/json?tree=jobs[name,_class,color]` (`jen:1033-1044`), and `job view` asks `tree=name,fullName,url,_class,color,…,lastBuild[…]` (`jen:1086`).
- `jen_check_http` (`jen:348-366`) classifies a `3xx` by the host its `Location` names: `/oauth2/` or the realm host is a dead session, the instance's own host is an answer, and any other host is *unexpected redirect*. A `401` and a `403` take one path.
- fleetd's launchd unit carries `PATH` and `PLOT_REPO_ROOT` and no other variable (`skills/plot/units/com.plot-pm.fleetd.plist:54-70`, and the installed unit). So fleetd never sees `JEN_SECRET_BACKEND`, `JEN_CONFIG_DIR`, `XDG_CONFIG_HOME`, `JEN_URL`, `JEN_REALM_URL`, `JENKINS_USER`, `JENKINS_API_TOKEN` or `PLOT_BUDGET_ACCOUNT` from the operator's shell.
- `plot-host.sh` reads no Jenkins credential from `.env`: its `read_env_var` callers serve Bitbucket and Jira only (`:3071`, `:3097`).

The risk is medium, as the story says: bearer expiry. A reader that holds a 300 s bearer and refreshes it in memory can invalidate the refresh token `jen` holds, where the realm rotates refresh tokens. Then the operator's next `jen` call reads *session expired and refresh failed* (`jen:204`).

## Design

### Approach

**The model is `bitbucket-and-jira-read-in-process`.** Its Jira chain gives the shape: a client over the shared transport, then the reads with a corpus test, then a cutover that a census row holds. The shared transport exists: `connectorHttps` (`packages/domain/src/adapters/host/connector-https.ts:152`) takes the connector word, the account, the slot key and the spend reading from its caller and chooses none of them. `jira-api.ts` (`adapters/tracker/`) already builds on it outside `adapters/host/`. This plan builds no second transport, and `scripts/check-host-https-callers.sh` does not change: the Jenkins client imports no `node:https`.

**No organisation's hosts in Plot.** `jen`'s defaults (`JEN_URL_PATTERN` at `jen:6`, `JEN_REALM_URL` at `jen:28`) name one company's hosts, and Plot copies neither (*Project-Agnostic Design*). The client resolves the instance URL from `JEN_URL`, or from a `Jenkins instance` slug part that holds a dot (a host, under `https://`). A bare slug with no `JEN_URL` resolves no URL in-process, and the composition keeps the shell with the reason `the Jenkins instance is a slug; write its host`. The realm URL comes from `JEN_REALM_URL`, else from the `iss` claim of the stored access token, which Keycloak sets to the realm URL. `JEN_REALM_URL` takes priority where both exist. Under fleetd's unit `JEN_REALM_URL` is never set, so `iss` is the realm source fleetd uses on an operator's machine. An access token that does not parse as a JWT, or that carries no `iss`, keeps the shell with the reason `the stored token names no realm`. The client reads `iss` without a signature check: the store file is the user's own with mode `0600`, and a process that can write it can already read the refresh token in it, so that file mode is what makes trusting the unsigned claim safe. The client sends a credential only to an `https:` URL or to a loopback host (`127.0.0.1`, `::1`, `localhost`). The rule applies to the instance URL, to the realm URL from either source and to the token endpoint, and a URL that breaks it keeps the shell with a named reason and sends no request. The client is the only guard for this rule, because the transport admits `http:` for any host (`connector-https.ts:50`, `:175`).

**The vendor gate and the file layout.** The CI gate *The domain names no vendor* (`ci.yml:1666-1672`) greps every code line under `packages/domain/src/` outside `adapters/` for the word `jenkins` (case-insensitive, `\b` on both sides), and an import path is a code line: `import … from './jenkins-pr-checks.js'` matches. So the layout follows three rules. The string literals that name `jenkins` (the connector word, the reason texts) stay in `adapters/build/`. The new rule modules carry names with no standalone `jenkins` token: `rules/jen-url.ts` for the copied `jen` rules, and `rules/ci-build-map.ts`, `rules/ci-sha-runs.ts` and `rules/ci-build-rows.ts` for the copied `plot-host.sh` rules (`jen` is not in the gate's word list). No module under `packages/domain/src/` outside `adapters/` imports `./jenkins-pr-checks.js`: today none does (its callers are the board entry and the corpus, through the package export `./rules/*`), and no new rule imports it. The adapters under `adapters/build/` and `adapters/host/`, where the gate does not look, compose `rules/jenkins-pr-checks.ts` with the new rules, and a type that two rules share lives in one of the vendor-free modules. The gate reads no file name, so `rules/jenkins-pr-checks.ts` keeps its name.

**Slice 1: the Jenkins client.**

- **The transport takes a form body.** `connector-https.ts` sends only JSON today (`JSON.stringify` at `:174`, `Content-Type: application/json` at `:190`). Slice 1 adds a form body (`application/x-www-form-urlencoded`) to `ConnectorCall`, for the refresh grant. The JSON path does not change, and a transport row holds both.
- `adapters/build/jenkins-api.ts` is the one module that builds requests to a Jenkins instance, over `connector-https.ts`. The slug part and job path come from `Jenkins instance` or `JENKINS_INSTANCE`, split at the first `/`, and `PLOT_JENKINS_JOB` overrides the job, as `plot-host.sh:1770-1779` does.
- **The declared duplicates of `jen`.** The client copies these `jen` 0.4.0 rules, and each one is a declared duplicate: `jen_instance_url` and `jen_url_for` for scheme, host and `JEN_URL` (`rules/jen-url.ts`, without the pattern arm), `jen_url_host` and `jen_key_for` (the secret key), `jen_secret_file` (the file name), `jen_save_token` (`expires_at` is now plus `expires_in`, else 300 where absent, minus 30), `jen_job_path` with `jen_urlencode`, `jen_check_http`'s redirect classification, and the `.jobs` projection of `job list --json`. CI installs no `jen`, so the corpus rows read a recording: `packages/domain/corpus/record-jenkins-reads.mjs`, modelled on `record-github-issues-runs.mjs`, checks that the installed `jen` reports `0.4.0`, lifts the named functions out of it with `awk` (as `bitbucket-budget-account.corpus.test.ts:52-54` lifts `budget_account`), runs them over a fixed list of slugs, hosts, URLs, keys, token answers, job paths, branches and `Location` values, and commits the outputs. `jen-url.corpus.test.ts` compares the TypeScript rules with those outputs. The client reads the canonical per-instance key only, and never migrates or deletes a key (`jen_migrate_instance_keys`, `jen:228-262`, is not copied), so fleetd is never a second writer of the per-instance secrets. A person runs the recorder once per `jen` version, and the corpus tier reads the committed files only.
- **Credentials (decisions 1, 6 and 8).** The sources are the environment and `jen`'s file backend, in that order, and nothing else. The environment gives `JENKINS_USER` and `JENKINS_API_TOKEN`, and `JEN_TOKEN` as a bare bearer with no refresh. The file backend lives at `${JEN_CONFIG_DIR:-${XDG_CONFIG_HOME:-$HOME/.config}/jen}`. The client probes that directory with no `JEN_SECRET_BACKEND` and uses it where `keycloak-token.secret` exists there, so fleetd under its unit (`PATH`, `PLOT_REPO_ROOT`, and the `HOME` launchd gives a user agent) finds it. A machine with neither source keeps the shell, and fleetd logs the reason once. The client reads no `.env` for Jenkins and runs no `security`. It sends the two headers as `jen` sends them, never in argv, a file other than the store, or a log line. A file store that the operator's `jen` no longer uses (it moved to the Keychain) reads as a dead session: the refusal names the directory and the fix, `JEN_SECRET_BACKEND=file jen auth login`.
- **Bearer refresh and the second writer (decision 2).** The client holds the Keycloak blob in memory and adopts the stored one where it is newer. Before a refresh it takes a lock between Plot processes, then re-reads the store. The lock is per user and keyed by the `jen` store directory, not by repository: `O_EXCL` on `keycloak-token.lock` in the store directory itself, beside `keycloak-token.secret`, stale after 30 s. The bearer is realm-wide and the store is per user, so two fleetds that serve two `CI: jenkins` repositories over one store take one lock; a lock under a repository's `.plot/state` would let both post a grant from one refresh token. Where the stored blob's `expires_at` lies ahead, it adopts that blob and posts no grant. Otherwise it posts the refresh grant as a form body and writes the answer back in `jen_save_token`'s format. On `invalid_grant` it re-reads the store once, adopts a newer blob where one exists, and refuses with kind `auth` otherwise. An empty or unparseable blob is a torn read of `jen`'s in-place write: the client re-reads once after 100 ms before it refuses. `jen` takes no lock (`jen:134`), so the lock serialises Plot processes only, and the re-reads bound the race with `jen`.
- **Write-back (decision 2).** The client writes only to the file backend it read. It creates a temporary file in the same directory with `O_CREAT | O_EXCL` and mode `0600` at open, writes the blob, and renames it over `keycloak-token.secret`. It never writes the environment or `JEN_TOKEN`.
- **The rotation measurement is a person's step.** Before the Client branch merges, a person with a device-flow login runs two refreshes from one refresh token against a throwaway session at the realm, and records in the story's *Measures* whether the realm rotates refresh tokens for `client_id=cli`, whether reuse of a rotated token revokes the session, and whether the access token's `iss` equals the realm URL. An unattended worker (`PLOT_UNATTENDED=1`) cannot log in, so the slice's worker leaves this step to the person and names it in the PR. **The result decides the Cutover.** `jen` takes no lock (`jen:134`), so a refresh by `jen` and one by fleetd from the same refresh token within one round trip stays possible after every guard above. Where reuse of a rotated refresh token revokes the session, that race logs the operator out of `jen` and stops fleetd's Jenkins reads until `jen auth login`, so the Cutover holds: the Cutover slice stops with a `PLOT-BLOCKED` marker that names the measurement, and a person decides. Where reuse does not revoke the session, the Cutover proceeds, and the accepted cost of a lost race is one `invalid_grant` answer followed by one re-read of the store.
- **Status codes and redirects.** The transport follows no redirect, and a row pins that. A `401` or a `403`, and a `3xx` to `/oauth2/` or the realm host, re-read the source once and retry once; a second one is a refusal of kind `auth` whose `said` names the source and the fix, `jen auth login`. A `3xx` to the instance's own host is an answer, as in `jen`. A `3xx` to any other host, or with no `Location`, is a refusal of kind `unaskable` that sends no second request, so neither credential reaches the `Location` host.
- **No credential in text.** A refusal's `said` takes only `error` and `error_description` from the token endpoint, never its body. A Jenkins HTML body is cut to 200 characters with tags removed. No log line, ledger line, status line or `said` holds a bearer, a refresh token or an API token.
- **Account, bucket and basis (decision 3).** Every Jenkins request carries the connector `jenkins`, the bucket `''` and the account `bitbucketBudgetAccount(null, process.env.PLOT_BUDGET_ACCOUNT)` (`rules/bitbucket-budget-account.ts:22`): `PLOT_BUDGET_ACCOUNT`, else `unknown`. That is all of the shell's Jenkins account: `jen()` calls `host_slot_take jenkins ''` and `budget_record_call jenkins ''` (`plot-host.sh:3910`, `:3929`), and both resolve `budget_account "${2:-$1}"` (`:3863`), so the empty second argument falls back to `budget_account jenkins`, which matches no arm of `budget_account` (`:3523-3543`). `bitbucket-budget-account.corpus.test.ts` gains a row that calls the lifted `budget_account` with the argument `jenkins`. With no rate-limit header, an instance entry records basis `predicted` with limit 60, as `ci-limit` does (`plot-host.sh:5927`). The slot bound follows `host_concurrency_bound` (`:3828`) over the same reading. A `429` maps to `throttled` through `throttledOf` (`connector-https.ts:119`).
- **The token endpoint charges its own bucket.** The refresh POST goes through `connectorHttps` under the connector `jenkins`, the same account, and the bucket `token`. So it is metered, it does not count against the instance's limit of 60, and the request-count row compares instance requests only. `connectorHttps` keys the slot bound on connector and account only (`boundKey`, `connector-https.ts:222`), and any entry whose basis is not `unknown` sets it (`:235`). So a `token` entry records basis `unknown`, and only the instance entries' `predicted` 60 sets the Jenkins slot bound. A shell refresh happens inside one `jen` call and charges no line of its own.
- **The census sees Jenkins.** `stub-host.ts` gains a Jenkins route on the stub server that serves the `job view`, `job list` and `api/json?tree=builds[…]` answers and refuses a request that lacks either header, and a token route that answers the refresh grant. The sandbox points both transports at it with `JEN_URL=http://127.0.0.1:<port>/jenkins` and `JEN_REALM_URL=http://127.0.0.1:<port>/realm`, which `jen` and the client both honour, and writes the census credentials as a file backend under the sandbox `HOME` (`.config/jen/`), with a `keycloak-token` blob past `expires_at` so the first pass refreshes.
- **The census writes its Jenkins answers per run.** The sandbox commits at run time, and every PR head is the `mainSha` that `rev-parse` reads (`sandbox.ts:281`, `:286`), so a recorded build can never name this run's head. The sandbox therefore writes the Jenkins answers per run from the run's actual head SHAs, as it writes the `gh` and `bb` answers (`answer(...)`, `sandbox.ts:302-347`), and the stub server and the stub `jen` both serve them from those files. The answers give one PR branch the colour `blue` (`checks` green) and a `SUCCESS` build whose `lastBuiltRevision` is that branch's head, so `rowsToBind` asks for its SHA and `bindChecks` binds a real colour, and the comparison of `checks` words with the shell run compares a bound word rather than `unknown` with `unknown`. The stub `jen` prints, for each command, the output shape the recorder took from the real `jen` 0.4.0, filled from the per-run answers; the recordings of the real `jen` are the corpus source for shapes, and a corpus row proves the stub's output shape against them. They supply no census SHA.
- **The sandbox carries no inherited Jenkins identity.** The sandbox env starts from `...process.env` (`sandbox.ts:199-200`) and deletes only the Bitbucket, Plot and systemd keys. The sandbox sets `XDG_CONFIG_HOME` to `$HOME/.config` and `JEN_CONFIG_DIR` to `$HOME/.config/jen` inside the sandbox root, and deletes the inherited `JEN_TOKEN`, `JEN_SECRET_BACKEND`, `JENKINS_USER`, `JENKINS_API_TOKEN`, `JENKINS_INSTANCE` and `PLOT_JENKINS_JOB` before it sets the census values. So a runner image that sets `XDG_CONFIG_HOME` does not move the probe outside the sandbox, and a runner `JEN_TOKEN` does not skip the refresh the fixture sets up.

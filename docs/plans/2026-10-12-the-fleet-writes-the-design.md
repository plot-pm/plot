> For a plan that a person put in `State: Design` and whose spec is empty, the fleet commissions an agent to write the spec, and after a person approves a plan's spike, automatic dispatch starts it. Approval stays a person's act.

## Motivation

Both write a `Design:` record and the `## Spec` placeholder `SPEC_PLACEHOLDER` (`packages/domain/src/workflows/needs-design.ts:5`).
- Since #1634, `sliceVerdict` admits the approved spike of a Design plan and refuses its other slices (`packages/domain/src/rules/eligible.ts:127-134`). Automatic dispatch still skips every non-`approved` plan, at six places in `packages/domain/src/rules/auto-dispatch.ts`: `planAutoDispatch` (`:531`), `startableBranches` (`:582`), `skippedClaimedBranches` (`:617`), `firstBrieflessBranch` (`:656`), `skippedPlans` (`:733`) and `dispatchCandidates` (`:798`). ## Design

### Approach

The design spec is [DESIGN-phases.md](../stories/plot-works-in-five-phases/DESIGN-phases.md) §6, *In Design*.

**The person's decision.** The fleet writes a spec only for a plan that a person already put in Design. `State: Design` comes from `/plot-idea` (#1628) or *Needs design* (#1633), each with a `Design:` record that names who decided, and the state gate refuses a `State:` change by any other writer. The fleet moves no plan into Design (D3). The spec it writes is a proposal on a draft PR: a person merges it or closes it, and a person later approves the plan through the person arm. An operator opts in with `Auto-design: true`; the default is off. `Auto-design` governs only the runs the fleet starts on its own: a person's `restart` starts one run whatever it says (D36), as `/plot-deliver --verify` does for verification.

**The reach (D34).** The fleet reads a Design plan's text at `origin/<main>` through `refs.showFile`, as `readVerifyCandidatesWith` does (`packages/fleet/src/shared/auto-verify.ts:293-330`). The pulse also carries plans that only a prefixed branch holds: the scan reads `origin/<main>` first, then each prefixed branch's tree for the plans the default branch does not carry (`skills/plot/scripts/plot-fleet-scan.sh:143-158`). So a `Review: pr` plan that *Needs design* moved on its open plan PR's head (`packages/domain/src/workflows/needs-design.ts:116-131`) is in the pulse with `phase: 'design'`, and `showFile` at `origin/<main>` fails for it. Such a plan goes into the reader's `unread` list, `designWork` answers `none`, the fleet records no failure and shows no row. Under D13 that plan reaches the default branch when a person approves its spike, and the fleet writes its spec from then on. A `Review: pr` Design plan with no spike never reaches the default branch in Design, because its approval merges the plan PR and writes `State: Approved` in one act (`packages/domain/src/workflows/approve.ts:337-358`). `Review: NONE` and an empty `Review:` take the `pr` arm in both workflows (`needs-design.ts:117-121`, `approve.ts:464`). An `Impl: same branch` plan writes `State: Design` in the caller's checkout (`needs-design.ts:108-121`), and its spike approval pushes that branch, not the default branch (`approve.ts:534-537`), so the fleet reaches it only after that branch merges. D34 accepts these limits and adds no reading of open plan PRs.

**The spike.** No new rule. The six `plan.phase !== 'approved'` filters in `rules/auto-dispatch.ts` admit a `design` plan too, and the scan's `wave.verdict` decides, as it does for an approved plan. `sliceVerdict` answers `eligible` for the approved spike only, so every other slice of a Design plan stays out. Because `dispatchCandidates` (`:798`) and `firstBrieflessBranch` (`:656`) admit it, a briefless spike enters `missingBriefs`, is reported `no-brief`, is offered to the `Brief command` and is not dispatched. `skippedPlans` (`:726-787`) admits a `design` plan only when it has an eligible slice, so a Design plan with no approved spike does not join the `no-eligible-wave` line that `packages/fleet/src/shared/auto-dispatch.ts:368-373` prints on every pulse. The two `hasEligible` reads in the fleet (`auto-dispatch.ts:243`, `:282`) admit a `design` plan the same way, so a spike that waits at the cap is named.

**What the fleet reads.** `specOf` moves from `packages/board/src/server/entry/needs-design.ts:146-163` into the domain beside `SPEC_PLACEHOLDER`, and the board entry imports it. Five rules in `packages/domain/src/rules/design-work.ts` use it:

- `specIsEmpty(text)`: true when `specOf(text)` is `''` or `SPEC_PLACEHOLDER`. A section that holds only a link to a `DESIGN-*.md` file counts as written.
- `designWork(readings: { state: string; text: string; specRef: ClaimAnswer; prRetry: boolean })`: for a `design` plan with `specIsEmpty(text)`, `write-spec` when `specRef` is `absent`, and `open-pr` when `specRef` is `work` and `prRetry` is true (the plan's failure record under the current `Design:` commit reads `pr-not-opened`); otherwise `none`. `specRef` is `claimTip`'s answer (`rules/claim.ts:40`, type `ClaimAnswer` at `:15`) for `idea/<slug>-spec` on origin, so `unknown` answers `none`. The spike does not change the answer: a spec and a spike are two forms of design work (DESIGN-phases.md §4), and the spike dispatches through the verdict whatever the spec says.
- `specStart(input)`, beside `verifyStart`: refuses on local readings only, in this order: `off`, `running` (a spec run or a verify run is going), `declined` (the store's mark), `halted`, `stopped`, `waiting`, `queue-unread`, `no-free-agent`, `starved` (without `Machine override`). It answers `ask-host` when none applies. A plan with a restart mark passes `off`, `declined`, `halted`, `stopped` and `waiting` once (D36); it does not pass `running` or the three slot refusals, so the restarted run waits for a free slot. An `open-pr` answer passes the slot refusals, because it starts no agent. The input names its readings as `VerifyStartInput` does (`rules/auto-verify.ts:124-149`).
- `specDeclined(pr: PrLookup | 'unknown', answeredPr: number)`: the host check, read only after `specStart` answers `ask-host`. It answers `host-unknown` when the host cannot answer, `declined` when the branch's newest PR is closed or merged and its number is above `answeredPr`, `pr-open` when that PR is open (start nothing, record nothing), and `start` otherwise. A closed PR at or below `answeredPr` is one a person already answered with a restart, so the restart wins over it.
- `specRow(slug, designCommit, store, log, going, now)`, beside `verificationRow` (`rules/auto-verify.ts:321`): a section, `working` for a going run or `waiting-on-you` for a plan whose failure record carries the current `Design:` commit or whose orphan record reads `no-pr`, and an entry of the shared plan-level shape `{ kind: 'spec', plan, reason, log, restart, stopped, halted }`; `null` otherwise. `halted` is the store's halt, the field the shared shape names; no per-row `fleetHalted` exists. The board renders it and decides nothing.

**What is shared with auto-verify.** The spec run imports every part of the verify run that is not about verification, and copies nothing that is a rule:

- `packages/domain/src/rules/fleet-run.ts` takes from `rules/auto-verify.ts` the store type (`VerifyStore`, `:27`) as `RunStore`, `VERIFY_HALT_AFTER` (`:21`) as `RUN_HALT_AFTER`, `recordVerifyFailure` (`:46`) as `recordRunFailure`, `verifyRetryVerdict` (`:61`) as `runRetryVerdict`, `failuresSinceSuccess` (`:73`) and `verifyHalted` (`:84`) as `runHalted`, plus `slotRefusal`, the three last refusals of `verifyStart` (`:164-179`: `queue-unread`, `no-free-agent`, `starved`). `auto-verify.ts` re-exports them under their current names and `verifyStart` calls `slotRefusal`, so no verify caller changes.
- `RunStore` holds the shared fields: run records, failures and `lastSuccessAt`. The design store adds four design-only fields: `declined[slug]` (the `Design:` commit and the PR number), `answeredPr[slug]`, `restart[slug]` (the `Design:` commit of a pending restart) and `orphans[slug]` (a `work` ref's tip and its PR reading).
- `packages/fleet/src/shared/fleet-run.ts` takes from `packages/fleet/src/shared/auto-verify.ts` the state file reader and writer (`readVerifyState` `:161`, `updateVerifyState` `:192`, over a path argument), `pidAlive` (`:207`), `verifyRunGoing` (`:225`, as `runGoing`), `boundSecondsOf` (`:393`) and the status line format of `verifyStatusLines` (`:584`).
- Each run keeps its own prompt, its own candidate reader (Delivered plans at the delivery commit against Design plans at `origin/<main>`) and its own settlement arms. These answer different questions, so they are not a duplicate of one rule, and no corpus pair is needed.

**The spec run.** `packages/fleet/src/shared/auto-design.ts`:

- Two `## Plot Config` keys. `Design command` names the runner; an absent key starts nothing, also on a restart. It is its own key under the one-capability-one-key rule (`packages/fleet/src/shared/implement-run.ts:22-33`): writing a spec is not the idea binding. `Auto-design` turns the fleet's own runs on for the literal `true` only, and defaults off. The slice adds both to this repository's `## Plot Config`, beside `Verify command` and `Auto-verify: false` (`CLAUDE.md:102-103`): `Design command` with the `Idea command`'s `claude -p --model opus` line, and `Auto-design: false`.
- The order of a pass. For each plan, fleetd folds the restart marks (below), reads `designWork` and `specStart` from local state, and asks the host only on `ask-host`: one `host.prState('idea/<slug>-spec')` read (`packages/domain/src/ports/host.ts:161`) into `specDeclined`. So a pass that refuses on `off`, `running`, `declined`, `halted`, `stopped`, `waiting` or a slot makes no host call. On `declined`, fleetd writes `declined[slug]` with the `Design:` commit and the PR number into the store, starts nothing, and reads the mark on every later pass with no host call.
- The claim. On `start`, fleetd pushes `idea/<slug>-spec` to origin with one empty `plot: claim idea/<slug>-spec` commit (`CLAIM_SUBJECT_PREFIX`, `rules/empty-claim.ts:12`) through `Trees.addBranch`, `Trees.commit` and `Trees.push` (`packages/domain/src/ports/trees.ts:280`, `:403`, `:419`). A rejected push means another machine holds the run, and nothing starts. The branch on origin is the one-run record: every machine reads it, and it is in git (Manifesto Principle 1). The commit-time phase gate exempts `idea/` (`packages/domain/src/rules/phase-gate.ts:62-67`), so the spec commits pass it. The start consumes the restart mark.
- The tree. The agent works in its own worktree at `.plot/state/design/<slug>/`, checked out on `idea/<slug>-spec`, never in the operator's checkout. The directory sits beside the verify run's `verifyRunDir` (`auto-verify.ts:47`), so `Worktree root` keeps only slice desks. fleetd removes the worktree and its local branch with `Trees.removeWithBranch` (`trees.ts:296`) when it settles the run.
- The bound. `startBoardRun` takes `boundSeconds` from `Worker bound` (28800 in this repository, `DEFAULT_VERIFY_BOUND_SECONDS` where absent), as the verify run does (`auto-verify.ts:393`, `:526-536`).
- The prompt. *Commission design*'s prompt turned around: read the plan and its story, write the spec into `## Spec`, commit and push `idea/<slug>-spec`, change no `State:` line, approve nothing, write nothing to a tracker, and open no PR.
- The PR. fleetd opens the PR itself, through `Host.prCreate` (`host.ts:222`), with the title `plot: the spec of <slug>` and `draft: true`. Why fleetd and not the agent: the fleet then reads the outcome itself, a failed `pr-create` becomes a recorded failure instead of a silent `work` branch, and the agent needs no host CLI. The slice adds an optional `draft` field to `PrCreateRequest` (`host.ts:90-99`), rewrites the TSDoc at `host.ts:80-88` to say a caller sets `draft` for a proposal that waits for a person and omits it for a finding, and `packages/domain/src/adapters/host/host-shell.ts:352-366` passes `--draft`, which `plot-host.sh pr-create` already takes (`plot-host.sh:3871`). On Bitbucket, `--draft` depends on the `bb` version (`plot-host.sh:435`); a create that `bb` refuses is a `pr-not-opened` failure and retries as one. Existing callers omit the field and keep a ready PR.
- The cap. A going spec run counts in `scaleUp`'s `running` (`packages/domain/src/workflows/assign.ts:229`) beside `verifying`, so it starts one slice agent fewer. `specStart` refuses while a verify run goes, and `verifyStart` gains the same refusal for a going spec run, so the machine keeps the `Parallel agents` + 1 bound that DESIGN-phases.md §6 states. The verify pass runs before the spec pass, so when both may start, the verify run starts.

**Settling a run.** After the run's process ends, fleetd fetches and reads `claimTip` of `origin/idea/<slug>-spec`, then settles by one arm and removes the worktree. A `work` ref with a written spec reads `prState` before it creates, so a PR that already exists is not created twice:

| Ref reads | Also read | Outcome | Ref |
|---|---|---|---|
| `work` | spec written on the branch; `prState` finds an open PR | success: `lastSuccessAt` moves, which clears the halt | kept, the PR's head |
| `work` | spec written; no open PR; `prCreate` answers | success | kept, the PR's head |
| `work` | spec written; `prState` or `prCreate` fails | failure `pr-not-opened` | kept; a later pass retries the PR |
| `work` | spec empty on the branch; `prMerged` reads `not-merged` | failure `spec-empty` | deleted |
| `claim-only` | none | failure `no-commit` | deleted |
| `absent` | none | failure `no-branch` | none |
| `unknown` | none | unsettled; the next pass reads again | untouched |

A failure goes through `recordRunFailure`, keyed by the commit that added the plan's `Design:` record (`refs.recordCommit(file, 'Design')`, `packages/domain/src/ports/refs.ts:358`), and `runRetryVerdict` answers `waiting` (60 s, then 120 s, `packages/domain/src/rules/auto-deliver.ts:74-112`) or `stopped` after 3. A `pr-not-opened` failure retries through `designWork`'s `open-pr`: when `specStart` passes its budget refusals, fleetd repeats only the PR step of the table (`prState`, then `prCreate`) and starts no agent, so the retry needs no slot. Three failures across plans since the last success halt every spec run. The store `.plot/state/auto-design-in-flight.json` is machine-local (`.gitignore:30`), so the counts hold per machine.

**One writer of the store.** fleetd is the only writer of `auto-design-in-flight.json`. `plot-design.mjs restart` writes its outcome to a separate mark file, `.plot/state/design/restart/<slug>.<epoch-ms>.json`, through a temp file and a rename. At the start of each spec pass, fleetd reads every mark file, folds them into the store in one `updateRunState` step, and then removes exactly the files it read; a mark written during the pass is a new file and folds on the next pass. Why a mark file and not a lock: `updateVerifyState` is atomic only inside one process (`auto-verify.ts:183-205`), the fleet package holds no file lock today, and a lock adds a stale-lock state that a crashed process leaves behind. With a mark file each file has one writer, the shape that CLAUDE.md's *One writer* rule names for the PR index.

**Deleting a remote ref.** No port operation deletes a branch on origin today: `Trees.deleteBranch` (`trees.ts:331`) is local. The spec-run slice adds `Trees.deleteRemoteBranch(branch, expectedTip)`, which runs `git push --force-with-lease=refs/heads/<branch>:<tip> origin --delete <branch>` in `trees-git.ts`, so it deletes only the tip that was read; `trees-fixture.ts` gains the same operation. A `work` ref holds commits, so every deletion of a `work` spec ref reads `host.prMerged` (`host.ts:174`, the `mergedAt` reading) first and deletes only on `not-merged`, never on a PR's `state` (CLAUDE.md, *One Answer To "Did This Land"*).

**A crashed or orphaned run.** A run's record in the store survives a stopped fleetd and a machine restart. On each pass, a record with no end code whose pid is dead past the start grace (`runGoing`) settles through the table above. A `claim-only` spec ref that no run record on this machine names, and whose claim commit is older than `Claim stale after` (24 h, above the 8 h `Worker bound`), is another machine's lost run: fleetd records failure `stale-claim` and deletes the ref. A `work` spec ref that no run record on this machine names, and whose claim commit is older than `Worker bound`, is a run whose machine died after the agent pushed: fleetd reads `prState` once per tip, stores the answer in `orphans[slug]`, and, when no PR exists, shows a *Waiting on you* row with reason `no-pr` and the restart command. It counts no failure and deletes nothing, because the ref holds a person's possible work. A directory under `.plot/state/design/` with no run record is removed with `Trees.removeWithBranch`.

**The person's controls.** `node skills/plot/scripts/board/plot-design.mjs restart <slug>` reads the spec ref, the store and the host, then acts by one arm and writes a mark file:

- `absent`: a `start` mark for the plan's `Design:` commit, with `answeredPr` set to the number of the branch's newest closed PR, if any.
- `claim-only` with no going run on this machine: deletes the ref, then as `absent`.
- `claim-only` or any ref with a going run on this machine: refuses `running`.
- `work` with an open spec PR: refuses `open-pr`, naming the URL.
- `work` with no PR and the spec written on the branch: opens the draft PR through `Host.prCreate` and writes a `pr-opened` mark, which fleetd folds as a success.
- `work` with no PR and the spec empty, or with a closed PR: deletes the ref when `prMerged` reads `not-merged`, then as `absent`.
- `work` whose PR merged: refuses `merged`; the plan's text on `origin/<main>` decides from then on.
- `unknown`, or a host that cannot answer: refuses `unknown`.

fleetd folds a `start` mark by clearing the plan's failure record and `declined` mark, setting `restart[slug]` and raising `answeredPr[slug]`. `specStart` then lets the plan pass `off`, `declined`, `halted`, `stopped` and `waiting` once, and `specDeclined` reads the closed PR the person answered as answered. So after a person closes a spec PR, a restart starts one run on the next pass with a free slot, also while `Auto-design` is off or spec runs are halted. That run's success moves `lastSuccessAt` and lifts the halt for every plan; its failure retries under `runRetryVerdict`, and the old closed PR declines it again on no pass. `/plot-fleet --status` prints the same line as the row, and `/api/fleet` carries the rows in a `design` field.

**The cost.** One spec run is one `Design command` context (Opus, by the line this slice adds), at most two host reads (`prState` before the claim and `prState` before `prCreate`) and three host writes: the claim push, the agent's push and `prCreate`. A pass that refuses on a local reading makes no host call, so a stopped, halted, waiting or slot-starved plan costs nothing per 60 s pass (`PASS_INTERVAL_MS`, `packages/fleet/src/server/entry/worker-loop.ts:114`). A failed run adds at most one `prMerged` read and one ref deletion; a `pr-not-opened` retry costs one `prState` and one `prCreate` and no agent; an orphan `work` ref costs one `prState` per tip. Runs follow a person's act or `Auto-design: true`, plus at most two automatic retries per plan before `stopped`, on each machine: with N machines a plan can cost up to 3N failed runs (Open Point 3). 0 plans read `State: Design` on `main` today.

The first slice is a spike that builds the issue gate and its spend sharing with the PR pass.

## Design

### Approach

The design spec is [DESIGN-phases.md](../stories/plot-works-in-five-phases/DESIGN-phases.md) §5, *Discovery*. The lanes are a view: no decision reads the issue index, and the board renders its open and closed rows as it renders non-terminal PR rows from the PR store (`fleet.ts:1624-1647`).

**This plan's spike.** The riskiest mechanism is the issue gate and its spend sharing with the PR pass: three panel rounds read it, and each found a wire the previous revision missed. So the first slice is a spike, `feature/the-fleet-indexes-issues`, alone under the first slice heading and annotated `<!-- spike -->` as `design-work-proves-the-path` *The marker* defines it, and CI judges the mechanism. The spike builds the smallest fixture of the whole path: fleetd folds today's open read (`issue-list --limit 50`, one page, the call the board makes today at `fleet.ts:1490`) into `issues.json` on the issue gate, writes the gate's `nextAt`, `backoffUntil` and request count into the file (D28), the PR pass reads them, and the board under a fleet reads its inbox from the file and stops its own 60 s call. It adds no shell line and reads no closed issue. Its Acceptance (*Acceptance*, *The spike*) names what it must show before the remaining slices are confirmed. The annotation gates nothing until `feature/a-slice-is-marked-spike` ships. Until then D29 decides the route: the plan is approved whole, and right after the approval its five other branches are held in `.plot/hold` until a person removes the holds (*Notes*).

**The issue source decides, and the port follows it.** A new resolver `trackerForIssues(declared, gitHost, context)` in `adapters/tracker/tracker-resolve.ts` reads `issueSource`: `tracker` resolves to `trackerFor(declared)`, `git-host` resolves to a new read-only implementation `trackerGitHost`, and `nobody` resolves to `trackerNone` with the source's reason. `trackerGitHost` is built from `trackerReads` (`tracker-shell.ts:120-170`) with the git host's backend word (`github`, `bitbucket`) as its connector tag, so it lists through `plot-host.sh issue-list` as the GitHub and Jira connectors do, and its `limit()` reports the `host` connector's own bucket: it reads through the git host connector's account, spends that budget, and is not a connector with a budget of its own. It answers `unaskable` on `statusWrite`, so a repository that declared no tracker gets no tracker write. `trackerFor` and `statusWrite` do not change.

**`unaskable` carries its reason.** Today `unaskable()` carries no text (`port-result.ts:12`, `:37`). `feature/the-tracker-lists-closed-issues` gives the `unaskable` result an optional `reason`, and two implementations fill it: `trackerGitHost` answers every write with *no Tracker declared; the git host's issues are read-only to Plot*, and `trackerNone` answers every operation with the reason `issueSource` stated (`rules/issue-source.ts:51-63`). A caller that reads only `why` sees no change. `issueOpen` of `the-fleet-verifies-what-it-delivered` returns the same reasons, and its `no issue: <reason>` line prints them.

**The port doc changes with it.** Four passages contradict `trackerGitHost`, and the spike, which builds it, rewrites all four:

- `ports/tracker.ts:70-75` (*A TRACKER IS NOT A GIT HOST*) keeps `unaskable` for a repository that declared no tracker. It changes to: such a repository reads its issues from its git host through `trackerGitHost`, as `issueSource` decides, and answers `unaskable` on every write; `trackerNone` answers the `nobody` source.
- `ports/tracker.ts:77-82` (*EVERY IMPLEMENTATION IS A CONNECTOR*) says each implementation owns its own budget. It changes to: every implementation but `trackerGitHost` is a connector with its own budget; `trackerGitHost` reads through the git host connector's account and budget, and its `limit()` reports that connector's buckets only (`tracker-shell.ts:156-161`).
- The `@returns` lines at `ports/tracker.ts:106` and `:119` say `unaskable` where the issue source is `nobody`.
- `CLAUDE.md:372-384` (*There are now two connector ports*) says the tracker's implementations are two connectors that never see each other's budget, and that a repository with no `Tracker` key gets `trackerNone`. It changes to: the tracker's declared implementations are connectors with budgets of their own; a repository with no `Tracker` key reads issues read-only through `trackerGitHost` on the git host's budget, and `trackerFor` still resolves it to `trackerNone` for the write, which answers `unaskable` including the write (`:381-384` keeps its reason). `AGENTS.md` follows through `./scripts/check-agents-md.sh --write`.

**Closed issues on the port.** `Tracker` gains `issueListClosed(since, limit)`, which lists issues closed at or after `since`, newest first, without bodies. `Issue` gains `closedAt: string | null`, the tracker's own closing time; `null` on an open issue and on a closed issue whose tracker states no date. No `open` field is added: a row's openness is the list that returned it. `plot-host.sh issue-list` gains `--state open|closed` (default `open`) and `--since <iso>`:

| Source | Closed read | `closedAt` |
|---|---|---|
| GitHub | the open arm with `gh_state=closed`, `--search "closed:>=<since>"` and `closedAt` in `--json`, `--limit <n>` | `closedAt` |
| Jira | `project IN (<Ticket prefixes>) AND resolved >= "<since>"`, with today's assignee clause until *The Jira project scope* below drops it, `ORDER BY resolved DESC`, 100 rows a page, the adapter's `nextPageToken` loop to `<n>` | `resolutiondate` |
| Bitbucket | exit 4: `bb issue list` prints no closing date | — |

The Jira closed read requires `Ticket prefixes`: with none declared it exits 4 with the reason, because an unscoped `resolved >=` query reads the whole instance (`plot-host.sh` `tracker_projects`). `PLOT_JIRA_JQL` overrides the inbox read only, and the closed read does not read it. A read that returns `<n>` rows reports `complete: false`. Each arm records one budget call per page: the GitHub arm records one `budget_record_call` per 100 rows past the first, because the `gh` wrapper records one call per process (`plot-host.sh:3382-3388`), and `jira_curl` records each page itself (`:2648`).

**Pages.** A page is 100 rows on every source: `gh issue list --limit <n>` pages by 100 inside one process, and the Jira arms ask `maxResults=100` (`ISSUE_PAGE_ROWS`), where today's default is 50 (`plot-host.sh:4689`). The Jira page loop lives in the TypeScript adapter, not in the shell: `trackerReads` calls `issue-list` once per page with `--page-token <t>`, and the Jira arm prints the response's `nextPageToken` as a last JSON line, which the adapter strips. So one shell call reads one page, `jira_curl` records it, and the shell holds no loop.

**The open list.** The fold asks for every open issue up to `ISSUE_INDEX_OPEN_LIMIT = 1000`, with the GitHub per-page record above and the adapter's Jira page loop, and reports `complete: false` at the limit. Planned tickets stay in the index; the inbox filter (`fleet.ts:1577`) moves to the board's read, so the Delivery tab's *Waiting on you* keeps today's content and the Discovery lanes get the planned tickets.

**The issue index.** fleetd writes the issue index; the board never writes it.

- **Writer.** `fleetIssues(world, state, warn)` in a new `packages/fleet/src/shared/issue-refresh.ts` runs the pass `refreshIssueIndex`. The fleet clock runs it beside `fleetPrs` (`fleet-clock.ts:149`), and `registryd-main.ts:2013-2020` builds both. Its `IssueWorld` holds the tracker from `trackerForIssues`, the `issueSource` reading, the issue index store, and a read-only view of the PR state's backoff (*Backoff* below). The issue pass never writes `PrState`, and the PR pass never writes `issues.json`. A failure of one pass does not blank the other. A test `packages/fleet/test/unit/one-issue-index-writer.test.ts` asserts one caller of the encoder, in the shape of `one-pr-index-writer.test.ts`.
- **Shape.** `entities/issue-index.ts` exports `IssueIndexSchema`, `decodeIssueIndex`, `encodeIssueIndex` and `ISSUE_INDEX_VERSION`. One file per repository, `.plot/state/index/issues.json` under the common git dir. The name never matches a PR index file, which is `<connector>.json` (`pr-index-file.ts:31`). `PLOT_ISSUE_INDEX_HOME` overrides the directory, and `scripts/owned-run.sh` sets it beside `PLOT_PR_INDEX_HOME` (`:246`). The file holds:
  - `v`; `source`, the `issueSource` answer the pass read (`tracker` with its scheme, or `git-host` with its backend); `connector` and `account`, the connector and account the pass's requests were recorded under (`github`, `bitbucket` or `jira`);
  - the issue gate (D28): `requests`, the request count of the last pass; `nextAt`, when the issue gate next opens; `backoffUntil`, the end of a wait the host named, or `null`;
  - `at`, the time of the last answered open read; the last pass's `answer` (`answered`, `unsupported`, `failed`) with its reason and `failedAt`;
  - the open rows with `complete`; the closed rows with `since`, `complete` and the closed read's own answer, absent until `feature/the-index-holds-closed-issues` (an absent `closed` decodes as *not read*, so the field needs no version raise); and, for a Jira source after *The Jira project scope*, the `inbox` rows.

  A `Tracker: github-issues` repository and a git-host GitHub repository both write `issues.json`; their `source` tells them apart. A `nobody` source writes no file: nothing was read and nothing was spent, and the board derives the `nobody` reason from its own `issueSource` reading.
- **`source` is a key, not a verdict.** A reader compares the file's `source` with its own `issueSource` reading and refuses the rows on a mismatch. No reader decides a lane, a lifecycle step or a spend from `source`. `connector`, `account`, `requests` and `backoffUntil` record what the pass did and what the host said, which config cannot re-derive afterwards. `nextAt` is the gate's schedule, derived from `requests`: D28 places it in the file so that the board can read the gate under a fleet, and no decision about a plan, a slice or a merge reads it. So *Answers, never verdicts* (`CLAUDE.md:487`) holds, and `default-branch.json` stays its one sanctioned exception (`:485`).
- **One file per repository, against `DESIGN-index.md`.** `DESIGN-index.md:57` places one index file per connector per repository, and `:128` keeps the watermark per connector because two hosts have two accounts and two rate windows. An issue pass reads exactly one source, the one `issueSource` picks, so a repository's issue index spends exactly one connector, and the file names it in `connector` and `account`. The PR pass shares the gate only with a file whose connector and account are its own (*The PR pass reads the issue gate*). The name is `issues.json` and not `<connector>.json`, because `github.json` is the PR index's file. The jira row at `DESIGN-index.md:122` describes a delta read with a daily full read; this plan builds no delta, because each pass replaces two bounded sets (*Fold*). `feature/the-index-holds-closed-issues` amends that row and `:57` to say so.
- **Fold.** Each answered pass replaces the rows whole: the open list, and the closed issues since `at − 14 days`. Nothing is a delta, so there is no watermark, no `updatedAt` and no separate periodic full read: every pass is the full read of both bounded sets. A ticket that reopens leaves the closed set and enters the open set at the next pass.
- **A failed pass.** It keeps the previous rows and their `at`, and records `answer: failed`, `failedAt` and the reason, as `refreshIssues` keeps its last good list today (`fleet.ts:1466-1470`). `at` moves only on an answered read, as `askedAt` does in `CLAUDE.md` *A Decision Reads The Index*. A failed pass still writes `requests` and `nextAt`, and `backoffUntil` on a rate refusal, because a refused request is spent. The lanes then draw the kept rows under one line, *The last ticket read failed at <failedAt>: <reason>. Showing tickets read at <at>.* A failed pass with no kept rows shows that line in place of the lanes. A closed read that fails or answers `unsupported` while the open read answered leaves Open and In progress drawn and puts its own sentence in Done.
- **The issue gate.** `issueIntervalMs(requests)` in `packages/domain/src/rules/cadence.ts` answers `max(ISSUE_REFRESH_MS, requests × ISSUE_PAGE_MS)`, both 120 000 ms, where `requests` is the request count of the last pass. So the fold spends `requests × 3 600 000 / issueIntervalMs(requests)` = 30 requests an hour for every pass of one request or more (`issueSpendPerHour`), on any repository and source. The bound is per fleetd and repository, not per account: two repositories with fleets on one account spend 60. On this repository a full pass reads 2 open pages (108 issues) and 2 closed pages (154 closed in 14 days): 4 requests, a pass every 480 s. The spike's pass reads one page, every 120 s. The issue gate does not stretch with the account's load; the 30 is its bound.
- **The PR pass reads the issue gate (D28).** `PrWorld` (`pr-refresh.ts:106-119`) gains one optional reader, `issueGate(): Promise<IssueGateReading | null>`, where `IssueGateReading` holds `connector`, `account`, `requests`, `nextAt` and `backoffUntil`. fleetd's reader decodes `issues.json`. The board's no-fleet reader returns the same fields from `CacheEntry` (*The board's read*). `PrState` (`pr-refresh.ts:38-75`) does not change. `refreshPrs` reads the gate once per pass, right after the spend read at `pr-refresh.ts:1341`:
  - **The backoff first.** Where the reading's connector and account are the PR pass's own and `backoffUntil` lies in the future, the pass asks the host nothing and sets `prNextAt = max(prNextAt, backoffUntil)` with `prNextIsBackoff` true. So a shared backoff never moves the PR gate earlier.
  - **Then the subtraction.** A domain rule `cadenceRateOf(rate, gate, backend, account, now)` in `rules/cadence.ts` answers the rate the cadence divides by: `perHour − issueSpendPerHour(gate.requests)`, floored at 0, where the reading's connector and account match and `nextAt` lies no more than one issue interval in the past; otherwise `perHour` unchanged. A Jira reading or a reading on another account subtracts nothing, because `spend-rate` reads only the git host connector's account (`plot-host.sh:5236-5237`) and `budget_record_jira` records under `jira` (`:2688-2691`). A stale reading subtracts nothing, because a fold that stopped spends nothing. The three `scheduleNextPr` calls (`:1619`, `:1691`, `:1738`; defined at `:1024-1033`) receive the subtracted rate. `entry.prSpendPerHour` (`:1345`) and the limit reading (`:1352-1356`) keep the unsubtracted rate, so the banner shows the account's whole spend.
- **Backoff.** A host rate refusal of an issue read writes `backoffUntil`, now plus the wait the host named, into `issues.json`, and the issue gate stays shut until then. The issue gate also stays shut while the PR state's own backoff holds (`prNextIsBackoff` with `prNextAt` in the future), where the fold's connector and account are the PR pass's; `IssueWorld` reads that from fleetd's memory and never writes it. A Jira refusal, or a refusal on another account, backs off the issue gate alone, and the PR pass ignores it by the connector condition.
- **`PR_REQUESTS_PER_REFRESH`** (`pr-refresh.ts:181`) prices `pr-list` alone after `feature/the-index-holds-closed-issues`: `github` stays 1, and its comment says that the issue reads run on their own gate; `bitbucket` falls from 4 to 3, because `bb issue list` leaves the board's no-fleet PR unit (`fleet.ts:1694-1703`). fleetd's `refreshPrs` makes no `issue-list` call today, so 4 over-declares fleetd's Bitbucket spend now.
- **Cost, measured and computed.** The live ledger `~/.plot/state/budget.tsv`, read on 2026-10-12 at 15:58 and not written, holds 7 799 GitHub GraphQL, 424 GitHub core and 80 Bitbucket requests between 2026-10-11 16:36 and 2026-10-12 15:58. Over the 15 full hours that hold a request, GitHub GraphQL spent 276 to 1 226 requests an hour, median 409. The hour from 14:00 on 2026-10-12 spent 1 226, the load that round 2 measured as 1 145 an hour. That is the live baseline. The ledger names no caller, so the split between PR, issue and other requests below is computed from the code's rules, not measured. On this account the other spenders (about 400 an hour) exceed the PR pass's share of 60, so `targetStretch` answers `MAX_CADENCE_STRETCH` (`cadence.ts:136-140`) and the PR pass refreshes every 480 s before and after this plan; the subtraction changes nothing here. For a quiet account, the round-3 cost juror's replay of `cadenceStretch` gives the stretched figures.   On this account the plan saves 30 GitHub requests an hour with a fleet and adds 22.5 without one. On a quiet account it adds 22.5 to 30 and buys a PR refresh of 60 s on GitHub and 180 s on Bitbucket. The Bitbucket ledger holds 10 to 30 requests an hour, so the quiet rows apply there: Bitbucket rises by 24 to 30 an hour, to 90, on the host whose account-wide HTTP 429 the cost table records (`pr-refresh.ts:157-160`). A Bitbucket pass is one request, because `bb issue list` has no pages and no closed read. A Jira source spends the git host on PRs alone, unchanged, and at most 30 Jira requests an hour, where today the board's inbox call spends 60 Jira requests an hour under a fleet. The PR column counts questions, and the rich GitHub `pr-list` question can make two host calls (`pr-refresh.ts:1424-1426`), so it is a floor; the issue columns count pages.

**The board's read.** The board follows the PR store's switch, `fleetOwnsPrs` (`fleet.ts:1619`), and not the file's validity. With a fleet, its periodic refresh reads the issue index and asks the host nothing; a missing file, or a file whose `source` differs from the board's own `issueSource` reading, shows *the fleet has left no issue index to read*, as `readPrsFromStore` does (`fleet.ts:1636`), and a `nobody` reading shows its own reason and reads no file. With no fleet, `refreshIssues` reads the same rows into memory on its own `issueIntervalMs` gate, kept on `CacheEntry` as `issueNextAt`, `issueRequests` and `issueBackoffUntil`, which the board's no-fleet `PrWorld.issueGate` returns (the world is built at `fleet.ts:1663-1671`), and writes no file. In both modes `refreshIssues` and the fold call `trackerForIssues(…).issueList(…)` in place of `hostSaid(['issue-list', …])` (`fleet.ts:1490`), so one shell op has one route: with `ISSUE_LIMIT` (50) in the spike, and with `ISSUE_INDEX_OPEN_LIMIT` and `.issueListClosed(since, ISSUE_INDEX_OPEN_LIMIT)` from `feature/the-index-holds-closed-issues` on. The inbox (`entry.issues`) and the lanes come from the same pass, so one ticket cannot show two states on two tabs; on a Jira source after D23 they come from two reads of that pass. A `nobody`, `unaskable` or `failed` answer with no rows reaches the lanes as `issueAbsence` text, never as three empty lanes.

**The payloads.** The lanes' open and 14-day closed rows ride the board payload (`/api/board`, polled every 30 s, `App.tsx:31`), without bodies, at most 1000 of each. The 4 s `/api/fleet` payload (`App.tsx:32`) carries `issues`, the rows that pass the inbox filter, newest first, capped at `ISSUE_LIMIT` (50) as today, and `waiting`, the server's answer of `waitingTickets`: at most 50 `tickets`, the counts `shown` and `hidden`, `complete`, `notice` and `source`. No closed row rides `/api/fleet`.

**The toggle's closed read.** With the toggle on, the tab asks `GET /api/issues/closed`, which calls `trackerForIssues(…).issueListClosed(null, 1000)`. The tab asks once when the toggle turns on and once on a page load with `?archived=1`, and never on a poll. The board keeps the answer for `max(issueIntervalMs(requests), issueIntervalMs(p))`, where `requests` is the issue gate's last pass and `p` the toggle read's own page count, and serves it to every tab in that time. Under a fleet the board reads the gate's `requests`, `nextAt` and `backoffUntil` from `issues.json` (D28); with no fleet it reads them from `CacheEntry`. While `backoffUntil` lies in the future, or the toggle's own last read met a rate refusal, the endpoint serves the kept answer, or the backoff's reason, and asks nothing. The toggle's own refusal stays in the board's memory: the board writes no file, and fleetd learns of the refusal only through `spend-rate` and its own next refusal. The answer is not written to the index.

`/plot-fleet --status` now reports whether the supervisor PROCESS is alive, where it reported only whether its launchd label was loaded. A loaded label and a running process are different facts, and launchd holds the label after the process it names has exited — measured twice in ninety minutes on 2026-09-22, `--status` said `supervisor: running`, no `registryd.mjs` process existed, and `launchctl list` showed the label with `-` in its FIRST column, which is launchd saying no pid. An operator was told the fleet was healthy while dispatched slices sat unserved. The reading is `supervisor_pid`, which already existed in the file and is scoped to the label, and never `ps | grep`, which a sibling agent's command line can flip and which would silently regress the systemd arm where `is-active` already answers correctly. The state is most often a throttled crash loop rather than launchd declining to act: `KeepAlive: true` does restart the daemon, measured at `runs` 38 → 39 → 40 in about forty seconds, which makes the defect worse rather than milder because a crash-looping label reports `running` at every moment between restarts. Three answers where there were two — a loaded label with a live process is `running` and exits 0, a loaded label with none is `loaded, not running` and exits 1, and an unloaded label is unchanged. Both readings print on separate lines rather than folding into one verdict, which is all that survives of the `plot-boardctl.sh` precedent: its two-facts-must-agree rule belongs to `--stop`, where a wrong guess kills a process. The whole arm now takes each reading exactly once and routes the prose, the `install=` field and the exit code through that single capture — `supervisor_loaded` was called four times here and two of those ran after the message was printed, the last of them composing the exit code from the label alone, so a change to the prose alone would have printed the truth and still exited 0. `install=` gains `loaded-not-running` rather than reusing `running`, because accepting `running` beside `exit 1` puts the same contradiction one field deeper and a caller reading the field while reading the code would have to know which to believe. The exit code stays 0 or 1: `supervisorState` gates on exactly those two and answers `unknown` for everything else, so a third code would render *could not ask* from precisely the machines that most need an alarm, and the state travels as a field for that reason. The last tick's age prints as evidence and nothing derives liveness from it, since a busy daemon between ticks has not written for up to 60 seconds. `--status` still starts nothing and the repair goes in the message. `supervisorState` maps the new word onto the existing `died` rather than earning a fifth state, decided on what a reader does next: both `installed` and `loaded-not-running` mean the supervisor was started, is gone and nothing stopped it, so both want the log read before the next start, which is `died`'s own semantics and its own repair. `SupervisorState` therefore stays four-valued and no schema, banner or renderer moves. Rendering it as plain `down` was the half worth refusing, because `down` prints *start it* and starting a crash-looping supervisor runs straight back into whatever killed it. `fleet_install_state` takes both readings as optional arguments and probes when it is not told, so `--stop`'s `state:` line and the sourced test seam keep answering exactly what they answered before. `stubPlatform` now emits a pid for the healthy case: a bare `exit 0` made `supervisor_pid` parse empty, so the old loaded stub WAS the loaded-but-dead machine, and that contract moved rather than regressed. All three rows run on CI's `ubuntu-latest` through the `PATH` seam, and both mutants were measured — restoring `supervisor_loaded; exit $?` and answering `loaded-not-running` unconditionally each fail exactly one test.

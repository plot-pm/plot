`/plot-board-setup` now refuses a `Jenkins instance` that names no job path, instead of reporting it verified. Filed as #913 from a live adoption: the config carried the slug alone, setup reported healthy, and every PR on the resulting board rendered `checks: unknown` under *"WAITING ON A MACHINE — could not reach the host"*. Measured on that instance with `pr-list --rich`, a slug-only value returned **no rows** where `<slug>/quaweb/continuous-build` returned **4 PRs, all `checks: green`** — `plot-host.sh:702` states the contract (`<slug>` or `<slug>/<job/path>`, the remainder being the multibranch container) and adoption never enforced it. THE FAILURE IS NARROWER THAN "SETUP REPORTS GREEN": `jen_auth` already answers `unknown` when no instance resolves, so a **missing** key was refused correctly all along; the defect was that a **present but incomplete** value read `ok` while a wholly absent one read `unknown`, so a partial value scored strictly better than no value — the worse of the two failures passing the gate. Reachability and usefulness are different questions, and setup asked the first while reporting on the second: `auth` says the *server* answers, and the job path addresses the *container* a branch's builds live in. `plot-board-probe.sh` now emits `jen.job` and `jen.job_source` (`instance`, `override` or `none`) and the skill acts on them, which is this estate's own split — scripts collect and report, skills interpret and refuse — and is what makes the gates executable, since a test can call the probe and cannot call skill prose. **It makes no network call, and asking Jenkins could not answer it:** measured live 2026-09-15 against the #913 instance, a slug-only value resolves a **non-empty** job list — four entries, not zero — so the broken configuration answers and answers `ok`, and a gate pinning *"resolves zero branch jobs"* would pin a behaviour this estate never produces. **The scheme and authority are stripped before splitting**, because the estate accepts a URL form and the naive `${value#*/}` is wrong in both directions — reproduced across all four measured forms before the fix: `https://host/` yields `/jenkins.example.com/`, non-empty and therefore **accepted while being exactly the #913 defect**, and `https://host/job/path` yields a job path with the host glued on; the bare-hostname case is refused correctly only by accident, since hostnames have no slash. A slug-only value **with `PLOT_JENKINS_JOB` set is accepted**, since `plot-host.sh:3197` honours that variable and a caller holding the path separately has a working configuration; a fresh multibranch container with no children is **not** flagged, because it names a path and the reading stops there; and a repository declaring no Jenkins at all still reads `unknown` exactly as before, since a refusal firing on absence would be a new bug. Twelve tests call the probe directly and were verified by mutation rather than by passing: replacing the strip with the naive split kills exactly the four URL and trailing-slash gates. `jen` is invoked **zero times** by the new reading, pinned with a stub that records each invocation rather than one that answers and forgets. No new config key — the job path rides the instance value, since a multibranch container is the *parent* of the branch and cannot be derived from it. `plot-host.sh` is deliberately unchanged: the same latent split bug lives there confined to one op that exits 4, and promoting it into a refusal that blocks adoption would widen the blast radius.
